# 流媒体技术完整体系：从底层协议到行业应用

> 一套面向后端工程师的流媒体技术全景教程。从"流"的本质和底层协议出发，系统学习编解码、传输、流媒体服务器，再延伸到 IPTV、直播、视频监控、视频会议等行业应用场景。零基础也能跟着学，学完后能为任何流媒体相关行业设计技术方案。

---

## 这套教程能帮你做什么

读完整个系列，你将：

### 1. 掌握底层技术原理
- 理解"流"的本质：为什么浏览器不支持 RTSP/RTMP
- 掌握全协议栈：RTSP/RTMP/SRT/HLS/WebRTC/DASH 各自解决什么问题
- 理解编解码：H.264/H.265/AV1，为什么电视盒子不卡浏览器卡
- 理解传输层：TCP vs UDP vs QUIC，RTP/RTCP 如何工作

### 2. 具备工程实践能力
- 选型流媒体服务器：SRS vs MediaMTX vs ZLMediaKit
- 搭建完整推拉流链路：OBS 推流 → 服务器转码 → 浏览器播放
- 解决性能瓶颈：多分屏（16/32/64 路+）不卡顿，WebCodecs 硬件解码
- FFmpeg 实战：推流、拉流、转码、录像

### 3. 理解行业应用场景
- **视频监控**：RTSP 摄像头接入、DVR/NVR 演进、主/子码流、GB28181 国标
- **直播**：RTMP 推流、CDN 分发、连麦互动
- **IPTV/网络电视**：组播技术、电视盒子原理、EPG 节目指南
- **视频会议**：WebRTC P2P/SFU/MCU、低延迟优化
- **在线教育**：大班课直播、小班课互动、连麦混合架构、白板同步
- **远程医疗**：多方会诊、手术示教、隐私合规与留痕
- **OTT 平台**：多码率 ABR、CDN 预加载、AV1 编码
- **边缘 AIoT**：无人机/机器狗推流、弱网优化、边缘计算
- **流媒体安全**：推流/播放鉴权、防盗链、HLS AES-128 与 DRM

## 核心结论速览

### 1. 流媒体协议地图（2026 年现状）

```
来源端（接入）              服务端转换              播放端（浏览器）
────────────────────────────────────────────────────────────────
IP 摄像头 ──→ RTSP ──┐
OBS 直播 ───→ RTMP ──┤                   ┌─→ HLS/LL-HLS ──→ 5-10s 延迟
无人机 ─────→ SRT ───┤→ 流媒体服务器 ────┼─→ HTTP-FLV ───→ 1-3s 延迟
浏览器推流 ─→ WHIP ──┘  (SRS/MediaMTX)  └─→ WebRTC(WHEP)→ 200ms 延迟
```

**关键点**：浏览器**无法**直接播 RTSP/RTMP，必须经过服务端协议转换。

### 2. 为什么电视盒子能流畅接流，浏览器 16 路就卡？

```
电视盒子：专用 H.264/H.265 解码芯片
         解码 1 路 1080p 流 < 1% CPU
         16 路并发 = 16 个独立硬件解码器

浏览器：  依赖 CPU 软件解码（或有限的硬解加速）
         16 个 <video> 标签 = 16 路并发解码 → CPU 爆炸
```

**解决方案**：WebCodecs API → 浏览器直接调用 GPU 硬件解码器（类似电视盒子）

### 3. 流媒体服务器选型（2026 年）

| 服务器 | 最佳场景 | 核心特点 |
|--------|---------|---------|
| **SRS** | 大规模直播、WebRTC 互动 | 高并发、功能完整、社区活跃 |
| **MediaMTX** | Go 项目、轻量级路由、边缘设备 | 纯 Go、可嵌入、配置简单 |
| **ZLMediaKit** | IP 摄像头监控、GB28181 接入 | 国标支持好、协议网关 |

参考：[流媒体服务器对比](https://docs.zlmediakit.com/reference/documents/exclusive_features.html)

### 4. 编解码器选型（2026 年）

| 编解码器 | 压缩率 | 编码速度 | 硬件支持 | 许可费 | 推荐场景 |
|---------|-------|---------|---------|--------|---------|
| **H.264** | 基准 | 最快 | 最广 | 有 | 默认选择 |
| **H.265** | 2x | 慢 | 较广 | 高 | 高清监控 |
| **AV1** | 2.5x | 很慢 | 增长中 | 免费 | OTT 点播 |
| **VP9** | 1.8x | 慢 | 中等 | 免费 | YouTube |

参考：[编解码器对比 2026](https://colinmackay.net/guides/h264-vs-h265-vs-av1-2026)

### 5. 协议延迟对比

| 协议 | 典型延迟 | 适用场景 |
|------|---------|---------|
| RTSP/RTP | 低（< 1s） | 摄像头接入 |
| RTMP | 低-中（1-3s） | 推流到服务器 |
| SRT | 低-中（可调） | 弱网推流 |
| HTTP-FLV | 中（1-3s） | 国内直播 |
| HLS | 高（5-10s） | 大规模分发 |
| LL-HLS | 中（2-5s） | 低延迟大规模 |
| WebRTC | 极低（200ms） | 实时互动 |

参考：[协议对比矩阵](https://www.forasoft.com/learn/video-streaming/articles-streaming/protocol-comparison-matrix)

## 动手实践环境准备

```bash
# 1. FFmpeg 7.x+（必装）
brew install ffmpeg        # macOS
apt-get install ffmpeg     # Ubuntu

# 2. VLC 播放器（测试各种流）
brew install --cask vlc    # macOS

# 3. SRS 流媒体服务器（推荐）
docker run -d --name srs \
  -p 1935:1935 \   # RTMP
  -p 8080:8080 \   # HTTP-FLV / HLS
  -p 1985:1985 \   # HTTP API
  -p 8088:8088 \   # WebRTC
  registry.cn-hangzhou.aliyuncs.com/ossrs/srs:5

# 4. MediaMTX（Go 项目备选）
docker run -d --name mediamtx \
  -p 8554:8554 \   # RTSP
  -p 8888:8888 \   # HLS
  -p 8889:8889 \   # WebRTC
  -p 1935:1935 \   # RTMP
  bluenviron/mediamtx

# 5. 模拟 RTSP 摄像头（无真实设备时）
ffmpeg -re -stream_loop -1 -i test.mp4 \
  -c copy -f rtsp rtsp://localhost:8554/cam1

# 6. 模拟 RTMP 推流（OBS 场景）
ffmpeg -re -stream_loop -1 -i test.mp4 \
  -c copy -f flv rtmp://localhost:1935/live/stream1

# 7. 验证播放
ffplay rtsp://localhost:8554/cam1                    # RTSP
ffplay rtmp://localhost:1935/live/stream1            # RTMP
curl http://localhost:8080/live/stream1.m3u8          # HLS
```
