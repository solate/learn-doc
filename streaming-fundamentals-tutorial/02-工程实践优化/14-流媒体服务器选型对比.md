## 一、主流流媒体服务器概览

| 服务器 | 语言 | 协议支持 | 许可证 | 定位 |
|--------|------|---------|--------|------|
| **SRS** | C++ | RTMP/HLS/WebRTC/SRT | MIT | 国内最成熟全协议服务器 |
| **ZLMediaKit** | C++ | 全协议（含 WebRTC/GB28181） | MIT | 高性能，安防国标接入首选 |
| **MediaMTX** | Go | 全协议（含 WHIP/WHEP） | MIT | Go 项目首选，零配置 |
| **Nginx-RTMP** | C | RTMP/HLS | BSD | 轻量，适合简单场景 |
| **Ant Media** | Java | 全协议 | Apache/商业 | 企业级，有 SFU |
| **Wowza** | Java | 全协议 | 商业 | 传统商业方案 |
| **LiveKit** | Go | WebRTC（SFU） | Apache | 专注 WebRTC 多人 |
| **Janus** | C | WebRTC | GPL | 插件化 WebRTC 网关 |

## 二、SRS（Simple Realtime Server）

### 2.1 架构特点

SRS 是国内使用最广泛的开源流媒体服务器，由国内团队开发，文档和社区中文友好。

```
客户端
  ↓ RTMP / SRT / WebRTC
SRS 核心层
  ├── 协议解析（RTMP/HLS/DASH/SRT/WebRTC）
  ├── 流管理（发布/订阅）
  ├── 转码（可选，调用 FFmpeg）
  ├── 集群（Edge/Origin 模式）
  └── HTTP API
  ↓
输出：HLS / DASH / HTTP-FLV / WebRTC
```

**核心优势**：
- 协议支持最全（RTMP/HLS/DASH/SRT/WebRTC/WHIP/WHEP）
- 集群模式支持大规模分发
- HTTP API 完善，易于集成
- SRS 5.0 重写了 WebRTC 支持，延迟可达 200ms

### 2.2 典型配置

```nginx
# srs.conf
listen              1935;    # RTMP 端口
max_connections     1000;
http_api {
    enabled         on;
    listen          1985;    # API 端口
}
http_server {
    enabled         on;
    listen          8080;    # HTTP 分发端口
}
vhost __defaultVhost__ {
    # 开启 HLS
    hls {
        enabled         on;
        hls_path        ./objs/nginx/html;
        hls_fragment    10; # 10 秒分片
        hls_window      60; # 60 秒窗口
    }
    # 开启 HTTP-FLV（低延迟，约 1-3s）
    http_remux {
        enabled     on;
        mount       [vhost]/[app]/[stream].flv;
    }
    # 开启 WebRTC
    rtc {
        enabled     on;
        rtmp_to_rtc on;    # RTMP 推流自动转 WebRTC
        rtc_to_rtmp on;    # WebRTC 推流自动转 RTMP
    }
}
```

### 2.3 SRS 集群架构

```
[编码器] → [Origin 源站 SRS]
                 ↓
           [Edge 边缘 SRS 1]  → 播放器（华北）
           [Edge 边缘 SRS 2]  → 播放器（华南）
           [Edge 边缘 SRS 3]  → 播放器（海外）
```

**拉流模式**：Edge 按需从 Origin 拉流，Origin 不主动推。

## 三、ZLMediaKit

### 3.1 定位与特点

ZLMediaKit 是基于 C++11 开发的高性能流媒体服务框架，国内安防领域的事实标准之一，与 SRS 并称国产 C++ 流媒体服务器双雄。

**核心优势**：
- **性能极高**：基于 epoll 事件驱动，单机可承载数万路流转发
- **WebRTC 原生支持**：不是协议转封装，而是原生集成 WebRTC 协议栈，延迟可低至 300ms 内
- **GB28181 国标支持最完善**：海康/大华等摄像头、NVR 的国标 GB/T 28181 接入是杀手锏
- **Hook 回调机制**：`on_publish` / `on_play` / `on_stream_changed` / `on_stream_not_found` 等事件回调业务后端，天然适配鉴权和动态业务逻辑
- RESTful HTTP API 可动态增删流、查询在线流列表

```
推流端
  ├── RTSP（摄像头）──┐
  ├── RTMP（OBS）────┤
  ├── GB28181（IPC）─ → ZLMediaKit ── → HLS / HTTP-FLV / WebSocket-FLV / WebRTC
  ├── SRT ────────────┤                    ↑
  └── WebRTC ─────────┘            Hook 回调 Go 后端鉴权/登记
```

### 3.2 典型配置

```ini
# config.ini
[api]
apiDebug=1
# 调用 HTTP API 的鉴权密钥
secret=035c73f7-bb6b-4889-a715-d9eb2d1925cc

[rtc]
# WebRTC 对外公网 IP（NAT 场景必须配置）
externIP=1.2.3.4
port=8000

[rtsp]
port=554

[http]
port=80

[hook]
# 事件回调到业务后端
enable=1
on_publish=http://backend.example.com/hook/on_publish
on_play=http://backend.example.com/hook/on_play
on_stream_changed=http://backend.example.com/hook/on_stream_changed
```

**播放地址**：

```
RTSP:     rtsp://server/live/test
HLS:      http://server/live/test/hls.m3u8
HTTP-FLV: http://server/live/test.live.flv
WebRTC:   http://server/index/api/webrtc?app=live&stream=test&type=play
WHEP:     http://server/index/api/whep?app=live&stream=test
```

### 3.3 与 Go 后端集成（Hook 鉴权）

ZLMediaKit 不做业务鉴权，全部交给 Hook 回调业务后端，这正是 Go 后端发挥的地方：

```go
// ZLMediaKit on_publish Hook → Go 后端验证推流 Key
// ZLMediaKit POST JSON 到配置的 hook 地址，根据返回 code 决定是否放行
func (h *StreamHandler) ZLMOnPublish(c *gin.Context) {
    var req struct {
        MediaServerID string `json:"mediaServerId"`
        App           string `json:"app"`
        Stream        string `json:"stream"`
        Params        string `json:"params"` // 推流 URL 中的查询参数（如 ?key=xxx）
    }
    if err := c.ShouldBindJSON(&req); err != nil {
        c.JSON(http.StatusOK, gin.H{"code": -400, "msg": "bad request"})
        return
    }

    // 验证推流 Key，并登记流信息（后续 on_stream_changed 管理在线状态）
    valid, err := h.streamSvc.ValidateStreamKey(c.Request.Context(), req.App, req.Stream, req.Params)
    if err != nil || !valid {
        // code != 0 即拒绝推流
        c.JSON(http.StatusOK, gin.H{"code": -1, "msg": "invalid stream key"})
        return
    }
    c.JSON(http.StatusOK, gin.H{"code": 0})
}
```

**HTTP API 查询在线流**：

```go
// GET http://server/index/api/getMediaList?secret=xxx&app=live&stream=test
func (s *StreamService) GetOnlineStreams(ctx context.Context) ([]StreamInfo, error) {
    url := fmt.Sprintf("http://%s/index/api/getMediaList?secret=%s", s.zlmHost, s.zlmSecret)

    // ...
}
```

### 3.4 ZLMediaKit vs SRS

| 维度 | ZLMediaKit | SRS |
|------|-----------|-----|
| 定位 | 高性能流媒体**框架**，二次开发友好 | 开箱即用的流媒体**服务器** |
| WebRTC | 原生集成，低延迟更稳 | 5.0 重写后可用 |
| GB28181 | 原生支持，安防首选 | 需搭配专用网关 |
| 配置方式 | config.ini + Hook 回调业务侧 | 独立配置文件自足 |
| 集群 | 依赖外部（自研或配合 CDN） | 内置 Edge/Origin 集群 |
| 语言 | C++（二次开发门槛较高） | C++ |

## 四、MediaMTX（原 rtsp-simple-server）

### 4.1 为什么 Go 项目首选 MediaMTX

**MediaMTX 的核心优势**：
- 纯 Go 实现，与 Go 项目天然契合
- 零代码集成：一个 YAML 配置文件搞定一切
- 支持协议最全（包括 WHIP/WHEP/WebRTC）
- 内存占用低，单进程可处理数百路流

```yaml
# mediamtx.yml
protocols: [udp, tcp, tls, rtsps, rtmps]

paths:
  all:
    # 任何路径都接受推流
    source: publisher

  live/camera1:
    # 固定源：从摄像头 RTSP 拉流
    source: rtsp://192.168.1.100/stream
    sourceOnDemand: true  # 有人看才拉流
```

### 4.2 MediaMTX 协议互转

MediaMTX 最强大的特性：**任意协议互转**：

```
推流端 → [任意协议] → MediaMTX → [任意协议] → 播放端

RTSP 推流 → MediaMTX → HLS 播放
RTMP 推流 → MediaMTX → WebRTC 播放
WebRTC 推流（WHIP）→ MediaMTX → HLS/RTMP/RTSP
SRT 推流 → MediaMTX → HLS/WebRTC
```

**实际配置示例**：
```yaml
paths:
  live:
    # 接受所有协议推流
    # 自动生成以下地址：
    # RTSP:    rtsp://server:8554/live
    # RTMP:    rtmp://server/live
    # HLS:     http://server:8888/live/index.m3u8
    # WebRTC:  http://server:8889/live
    # WHIP:    http://server:8889/live/whip
    # WHEP:    http://server:8889/live/whep
    
    runOnPublish: ffmpeg -i rtsp://localhost:8554/$MTX_PATH -c copy /recordings/$MTX_PATH_%Y%m%d_%H%M%S.mp4
```

### 4.3 与 Go 项目集成

**方式 1：进程方式（推荐）**：
```go
// 在 Go 应用中启动 MediaMTX 子进程
func startMediaMTX(configPath string) (*exec.Cmd, error) {
    cmd := exec.Command("mediamtx", configPath)
    cmd.Stdout = os.Stdout
    cmd.Stderr = os.Stderr
    return cmd, cmd.Start()
}
```

**方式 2：API 控制**：
```go
// MediaMTX 提供 HTTP API
func addPath(pathName string, source string) error {
    payload := map[string]any{
        "source": source,
        "sourceOnDemand": true,
    }
    body, _ := json.Marshal(payload)
    resp, err := http.Post(
        "http://localhost:9997/v3/config/paths/add/"+pathName,
        "application/json",
        bytes.NewReader(body),
    )
    // ...
    return err
}
```

## 五、Nginx-RTMP

### 5.1 适合场景

Nginx-RTMP 模块简单可靠，适合：
- 已有 Nginx 部署，顺便加流媒体功能
- 只需要 RTMP 接收 + HLS 分发
- 不需要 WebRTC/SRT 等复杂协议

**局限**：
- 已停止维护（最后更新 2018 年）
- 不支持 WebRTC、SRT
- 高并发下不如 SRS/MediaMTX

### 5.2 Nginx-RTMP 配置

```nginx
rtmp {
    server {
        listen 1935;
        chunk_size 4096;

        application live {
            live on;
            record off;

            # 接收 RTMP 推流后，自动切成 HLS
            hls on;
            hls_path /var/www/html/hls;
            hls_fragment 3;
            hls_playlist_length 60;

            # 推流鉴权回调
            on_publish http://backend.example.com/auth;
        }
    }
}

http {
    server {
        listen 80;
        location /hls {
            types { application/vnd.apple.mpegurl m3u8; }
            root /var/www/html;
            add_header Cache-Control no-cache;
            add_header Access-Control-Allow-Origin *;
        }
    }
}
```

## 六、LiveKit（WebRTC SFU）

### 6.1 专注 WebRTC 多人场景

LiveKit 是 Go 实现的 WebRTC SFU，专为视频会议和多人互动直播设计：

```
特性：
- Simulcast + SVC 自适应码率
- 基于 WHIP/WHEP 推拉流
- 内置录制（存 S3/OSS）
- SDK 支持：iOS/Android/Web/Unity
- Go/Node/Python/Rust 服务端 SDK
```

**适合场景**：
- 多人视频会议
- 直播连麦/PK（多人实时互动）
- 在线教育互动课堂

```go
// Go 服务端控制 LiveKit 房间
import lksdk "github.com/livekit/server-sdk-go/v2"

func createRoom(roomName string) error {
    client := lksdk.NewRoomServiceClient(
        "https://livekit.example.com",
        "api-key",
        "api-secret",
    )
    _, err := client.CreateRoom(ctx, &livekit.CreateRoomRequest{
        Name:            roomName,
        MaxParticipants: 50,
        EmptyTimeout:    300, // 5 分钟无人自动销毁
    })
    return err
}
```

## 七、选型决策矩阵

### 7.1 按场景选择

| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| 监控视频（RTSP → HLS） | MediaMTX | 零配置 RTSP 拉流转 HLS |
| 安防国标平台（GB28181 接入） | ZLMediaKit | 原生 GB28181，海康/大华即插即用 |
| 直播平台（RTMP → HLS/WebRTC） | SRS | 协议最全，集群成熟 |
| Go 项目内嵌流媒体 | MediaMTX | 同语言，API 友好 |
| 视频会议/连麦 | LiveKit | 专业 SFU，SDK 齐全 |
| 超大规模（10万+ 并发） | SRS 集群 + CDN | 经过验证的大规模方案 |
| 简单推流转 HLS（有 Nginx） | Nginx-RTMP | 够用且简单 |
| 企业级付费支持 | Wowza / Ant Media | 有商业支持 |

### 7.2 资源消耗对比

**单路 1080p@4Mbps 流的资源消耗**：

| 服务器 | CPU | 内存 | 备注 |
|--------|-----|------|------|
| SRS | ~2% | ~20MB | 纯转发，不转码 |
| ZLMediaKit | ~1% | ~20MB | 纯转发性能最强 |
| MediaMTX | ~1% | ~15MB | Go GC 略低 |
| Nginx-RTMP | ~1% | ~10MB | 极轻量 |
| 带转码（SRS+FFmpeg） | ~30-80% | ~200MB | CPU 主要消耗在 FFmpeg |

## 八、生产部署建议

### 8.1 推荐架构（中小规模直播）

```
[编码器/OBS]
    ↓ RTMP/SRT/WHIP
[流媒体入口服务器 - SRS/MediaMTX]
    ├── WebRTC 低延迟播放（<500ms）
    ├── HTTP-FLV 低延迟播放（~1-3s）
    └── HLS 切片 → 对象存储（OSS/S3）
                         ↓
                    [CDN 全球分发]
                         ↓
                    [HLS 播放器]
```

### 8.2 鉴权集成

```go
// SRS 推流鉴权：SRS 回调 Go 后端验证 stream key
// POST /auth/on_publish
// Body: {stream: "xxx", key: "yyy"}

func (h *StreamHandler) OnPublish(c *gin.Context) {
    var req struct {
        Stream string `json:"stream"`
        Key    string `json:"key"`
    }
    c.ShouldBindJSON(&req)

    // 验证 stream key
    valid, err := h.streamSvc.ValidateStreamKey(c.Request.Context(), req.Stream, req.Key)
    if err != nil || !valid {
        c.JSON(http.StatusForbidden, gin.H{"code": 403})
        return
    }
    c.JSON(http.StatusOK, gin.H{"code": 0})
}
```

## 九、本篇小结

| 服务器 | 最适合 |
|--------|--------|
| **SRS** | 国内直播平台，全协议，集群 |
| **ZLMediaKit** | 安防 GB28181 国标接入，WebRTC 低延迟，高性能转发 |
| **MediaMTX** | Go 项目集成，摄像头接入，协议互转 |
| **Nginx-RTMP** | 简单 RTMP→HLS，已有 Nginx 环境 |
| **LiveKit** | 视频会议，多人连麦，WebRTC SFU |
| **Wowza** | 企业级商业项目 |

对于本系列的目标场景（Go 后端 + 监控/直播），**MediaMTX 是首选**（零配置、Go 友好、协议全）；接入海康/大华等国标设备或追求 WebRTC 低延迟选 **ZLMediaKit**；中大规模公网直播考虑 **SRS**。

## 动手实践

### 练习1：Docker 快速拉起四款服务器对比
```bash
# SRS 4.0
docker run -d --name srs -p 1935:1935 -p 1985:1985 -p 8080:8080   ossrs/srs:4 ./objs/srs -c conf/docker.conf

# ZLMediaKit
docker run -d --name zlmediakit -p 1935:1935 -p 554:554 -p 80:80 -p 8000:8000/udp   zlmediakit/zlmediakit:master

# MediaMTX
docker run -d --name mediamtx -p 1936:1935 -p 8554:8554 -p 8889:8889   bluenviron/mediamtx:latest

# Nginx-RTMP (tiangolo/nginx-rtmp)
docker run -d --name nginx-rtmp -p 1937:1935 -p 8080:8080   tiangolo/nginx-rtmp
```
**预期输出**：四容器都启动后，用 `ffmpeg -re -i test.mp4 -c copy -f flv rtmp://localhost:1935/live/stream` 分别推流到各服务器（注意 MediaMTX/Nginx-RTMP 映射到非默认 RTMP 端口），观察日志和内存占用差异。

### 练习2：SRS vs ZLMediaKit vs MediaMTX 并发连接压测
```bash
# 用 ffmpeg 并发拉取50路 HLS（模拟高并发）
for i in $(seq 1 50); do
  ffmpeg -i http://localhost:8080/live/stream.m3u8     -t 30 -f null - 2>/dev/null &
done
wait
# 同时监控：docker stats srs zlmediakit mediamtx
```
**预期输出**：记录三者在50路并发时的 CPU/内存占用。ZLMediaKit 在高并发下通常 CPU 最稳（epoll + C++），MediaMTX 内存略低（Go runtime）。

### 练习3：选型决策演练
根据以下场景判断最优选型：
1. **安防平台，RTSP 接入 + HLS 播放，200路**：MediaMTX（RTSP 原生支持强，Go 集成友好）
2. **互联网直播，大规模 CDN 分发**：SRS（HLS 集群、边缘节点成熟）
3. **GB28181 国标监控平台，接入海康/大华 NVR**：ZLMediaKit（原生 GB28181 支持，Hook 回调业务后端）
4. **WebRTC SFU 会议**：Mediasoup 或 Janus（专用 SFU，非通用流媒体服务器）

## 常见问题排查

| 现象 | 可能原因 | 解决方法 |
|------|---------|---------|
| SRS 启动后端口无法访问 | 防火墙或 Docker 端口映射错误 | `docker ps` 确认端口映射，检查 iptables |
| ZLMediaKit WebRTC 播放失败 | NAT 后未配置 externIP | 在 `config.ini` 的 `[rtc]` 段配置对外公网 IP |
| ZLMediaKit Hook 不触发 | hook 地址不通或返回非 JSON | 确认后端接口可访问，且返回 `{"code": 0}` 格式 |
| MediaMTX 路径 404 | path 配置的 source 不匹配 | 检查 `mediamtx.yml` 中 paths 配置，path 名要与推流 URL 一致 |
| Nginx-RTMP 推流断连 | 没有配置 application | `nginx.conf` 中必须有 `application live { live on; }` |
| 高并发下 CPU 满载 | 服务器做了不必要的转码 | 确认为 `-c copy` 透传模式，禁用自动转码 |
| 重启后推流 Key 失效 | 服务器 session 状态丢失 | 重连推流，或配置持久化 session |
| 内存持续增长 | HLS 分片未及时清理 | 设置 `hls_list_size` 和 `delete_segments` 限制驻留分片数 |

| 术语 | 英文 | 说明 |

| Hook | Web Hook | ZLMediaKit 的事件回调机制，推流/播放/流变化时 HTTP 通知业务后端 |

| Nginx-RTMP | nginx-rtmp-module | Nginx 的 RTMP 模块，轻量级推流接收 |
| Origin | Origin Server | 源站，直接接收推流的节点 |
| Edge | Edge Server | 边缘节点，从源站拉流后分发给播放客户端 |
| 并发连接数 | Concurrent Connections | 同时连接到服务器的客户端数量，是选型的核心指标 |
| vhost | Virtual Host | SRS 中虚拟主机概念，隔离不同域名/业务的配置 |
