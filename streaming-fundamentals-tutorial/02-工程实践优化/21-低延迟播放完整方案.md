# 低延迟播放完整方案

> **适合读者**：需要 < 3 秒端到端延迟的实时监控/直播开发者  
> **核心问题**：延迟从哪里来？怎么系统性地压到最低？

---

## 一、延迟来自哪里

从摄像头到用户眼睛，延迟累积在每个环节：

```
摄像头采集 → 编码缓冲 → 网络传输 → 服务器缓存 → CDN → 播放器缓冲 → 解码渲染
  ~50ms        ~200ms      ~50ms        ~200ms        ~100ms   ~1000ms      ~50ms
                                                              ↑
                                                         最大来源：播放器缓冲
```

**各方案延迟范围**：

| 方案 | 典型端到端延迟 | 适用场景 |
|------|--------------|---------|
| WebRTC | 50-500ms | 视频通话、实时互动 |
| WebSocket+FLV | 1-3s | 监控、直播互动 |
| LL-HLS（低延迟HLS） | 2-5s | CDN分发、直播 |
| 标准 HLS | 6-30s | 点播、无延迟要求 |
| RTMP → HLS | 10-30s | 旧方案 |

## 二、WebSocket + FLV 方案（监控首选）

最适合安防监控的低延迟方案：

```
RTSP摄像头 → FFmpeg → FLV over WebSocket → 浏览器 mpegts.js
延迟：1-3 秒
```

### 2.1 后端推流

```go
// Go 实现：FFmpeg 输出 FLV，通过 WebSocket 推给浏览器
func serveStream(w http.ResponseWriter, r *http.Request) {
    conn, err := upgrader.Upgrade(w, r, nil)
    if err != nil {
        return
    }
    defer conn.Close()

    rtspURL := r.URL.Query().Get("url")

    // FFmpeg 输出 FLV 到 stdout
    cmd := exec.CommandContext(r.Context(), "ffmpeg",
        "-rtsp_transport", "tcp",
        "-i", rtspURL,
        "-c:v", "copy",          // 不转码，直接封装
        "-c:a", "aac",
        "-f", "flv",             // FLV 格式
        "pipe:1",                // 输出到 stdout
    )

    stdout, err := cmd.StdoutPipe()
    if err != nil {
        return
    }
    cmd.Start()
    defer cmd.Process.Kill()

    buf := make([]byte, 32*1024) // 32KB 读取缓冲
    for {
        n, err := stdout.Read(buf)
        if err != nil {
            return
        }
        if err := conn.WriteMessage(websocket.BinaryMessage, buf[:n]); err != nil {
            return // 客户端断开
        }
    }
}
```

**这段代码的三个生产陷阱**（demo 可跑，直接上生产会翻车）：

1. **一个连接一个 FFmpeg 进程**：上面是「单路单看」模型——10 个人看同一摄像头 = 10 路独立 RTSP 拉流 + 10 个 FFmpeg 进程，摄像头出口带宽和服务器 CPU 都撑不住。生产必须做**源流复用**：一路拉流 fan-out 给 N 个客户端（自己实现 hub/broadcast，或干脆交给 SRS/ZLMediaKit 这类服务器，它们原生支持）。
2. **`?url=` 是 SSRF 漏洞**：客户端可传任意 RTSP 地址让服务器去连，等于开放内网探测入口。必须改成传流 ID、服务端查白名单映射真实地址，并叠加接口鉴权。
3. **音频编码注意**：安防摄像头音频常见 G.711/G.726，`-c:a aac` 会触发转码增加延迟和 CPU；若源已是 AAC 应改 `-c:a copy`，无音频的流直接 `-an` 去掉。

**为什么 `-rtsp_transport tcp`**：RTSP 默认 UDP 传输，丢包表现为花屏/绿块；TCP 重传保证画面完整，代价是抖动时延迟略增。监控场景画面完整性优先，选 TCP。

### 2.2 前端播放（mpegts.js）

```html
<video id="v" controls></video>
<script src="https://cdn.jsdelivr.net/npm/mpegts.js/dist/mpegts.min.js"></script>
<script>
const player = mpegts.createPlayer({
  type: 'flv',
  isLive: true,
  url: `ws://server:8080/ws/stream?url=${encodeURIComponent(rtspUrl)}`,
}, {
  enableWorker: true,
  liveBufferLatencyChasing: true,   // 自动追赶缓冲
  liveBufferLatencyMaxLatency: 1.5, // 最大允许1.5秒缓冲
  liveBufferLatencyMinRemain: 0.5,  // 保留0.5秒作为播放平滑用
});
player.attachMediaElement(document.getElementById('v'));
player.load();
player.play();
</script>
```

**关键配置说明**：
- `liveBufferLatencyChasing: true`：当缓冲超出时自动加速播放追赶
- `liveBufferLatencyMaxLatency: 1.5`：缓冲超过1.5s就加速
- 实测效果：浏览器端稳定在 1-2 秒延迟

> **⚠️ 自动播放策略**：浏览器禁止有声自动播放，`player.play()` 在页面刚加载时大概率被拦截（`NotAllowedError`）。监控页两种解法：
> - 视频设 `muted` 属性静音自动播放，UI 上提供「开启声音」按钮（监控场景常规做法）
> - 或在用户首次点击/交互后再调用 `play()`
>
> 排查时先看控制台有没有 `play() failed because the user didn't interact with the document first`。

## 三、HTTP-FLV 完整技术链路

### 3.1 HTTP-FLV vs WebSocket-FLV 对比

**两种 FLV 流式传输协议**：

| 维度 | HTTP-FLV | WebSocket-FLV |
|------|---------|---------------|
| **协议** | HTTP/1.1 长连接（Transfer-Encoding: chunked） | WebSocket（全双工） |
| **端口** | 80/443（HTTP/HTTPS） | 80/443（ws/wss） |
| **延迟** | 1-3 秒 | 1-2.5 秒（略低 200-500ms） |
| **浏览器兼容** | 全支持（HTTP 长连接是标准特性） | 需 WebSocket API（IE10+） |
| **CDN 友好度** | ✅ 极好（CDN 原生支持 HTTP） | ⚠️ 一般（部分 CDN 不缓存 WebSocket） |
| **防火墙穿透** | ✅ 极好（HTTP 协议） | ✅ 好（WebSocket 握手是 HTTP） |
| **服务端开销** | 低（HTTP 长连接，无状态） | 略高（WebSocket 需维护连接状态） |
| **适用场景** | CDN 分发、公网直播 | 内网监控、实时互动 |

**选型建议**：
- **直播平台（需 CDN）**：HTTP-FLV（CDN 缓存友好，运维成本低）
- **内网监控**：WebSocket-FLV（延迟略低，适合局域网）
- **混合场景**：优先 HTTP-FLV，降级 WebSocket-FLV

### 3.2 HTTP-FLV 工作原理

**完整链路**：
```
RTMP 推流端（OBS） → 流媒体服务器（SRS/ZLMediaKit）
                              ↓
                     HTTP-FLV 服务端点（HTTP 长连接）
                              ↓
                     持续推送 FLV Tag 流
                              ↓
                     浏览器（flv.js/mpegts.js/jessibuca）
                              ↓
                     MSE 硬解 或 WASM 软解
```

**关键技术点**：
1. **HTTP 长连接（Chunked Transfer Encoding）**：
   - 客户端发起 HTTP GET 请求：`GET /live/stream.flv HTTP/1.1`
   - 服务器返回：`Transfer-Encoding: chunked`
   - 连接保持打开，持续推送 FLV Tag 数据块
   - 不需要 `Content-Length`（因为直播流长度未知）

2. **流式传输（Streaming）**：
   - 服务器不等待完整文件生成，收到 RTMP 推流即刻转发 FLV Tag
   - 客户端边接收边解析，无需等待完整文件下载

3. **零转码开销**：
   - RTMP 消息（Message Type 8/9）与 FLV Tag **格式完全一致**
   - 服务器只需去掉 RTMP Chunk Header，直接输出 FLV Tag
   - CPU 占用极低，单核可支持数千路转发

### 3.3 服务端配置（SRS）

**SRS 配置示例**（`srs.conf`）：

```nginx
# RTMP 推流接收
listen              1935;
max_connections     1000;
daemon              off;
srs_log_file        ./objs/srs.log;

vhost __defaultVhost__ {
    # RTMP 推流配置
    rtmp {
        enabled         on;
    }
    
    # HTTP-FLV 拉流配置
    http_remux {
        enabled     on;
        mount       [vhost]/[app]/[stream].flv;  # 访问路径格式
        hstrs       on;  # HTTP 流式传输
    }
    
    # 低延迟优化
    min_latency     on;   # 最小延迟模式（禁用 GOP 缓存）
    gop_cache       off;  # 关闭 GOP 缓存（降低首屏延迟）
    queue_length    10;   # 减少播放端队列长度
    
    # HLS 转码（可选）
    hls {
        enabled         on;
        hls_path        ./objs/nginx/html;
        hls_fragment    2;   # 2 秒切片（低延迟）
        hls_window      10;  # 保留 10 个切片
    }
}

# HTTP-FLV 服务端点
http_server {
    enabled         on;
    listen          8080;
    dir             ./objs/nginx/html;
}
```

### 3.5 前端播放器选择

**三大主流播放器对比**：

| 播放器 | 解码模式 | H.265 支持 | 延迟 | 维护状态 | 适用场景 |
|--------|---------|-----------|------|---------|---------|
| **flv.js** | MSE 硬解 | ❌ | 1-3s | 停止维护（2018） | H.264 通用场景 |
| **mpegts.js** | MSE 硬解 | ❌ | 1-3s | 低频维护 | H.264 直播/监控 |
| **jessibuca** | MSE + WASM | ✅ WASM 软解 | 1-3s | 活跃维护 | H.265 监控场景 |

**推荐选型**：
- **H.264 流 + 通用场景**：mpegts.js（轻量、稳定）
- **H.265 流 + 监控场景**：jessibuca（唯一免费支持 H.265 的开源方案）
- **遗留项目**：flv.js（停止维护，不推荐新项目）

> **⚠️ iOS Safari 不支持 MSE——最容易踩的坑**
>
> 上面三个播放器都依赖 MSE（Media Source Extensions），而 **iPhone/iPad 的 Safari 至今不支持 MSE**（jessibuca 的 WASM 模式可用但性能差、发热严重，多路画面不可用）。移动端选型结论：
>
> | 平台 | 可选方案 | 延迟 |
> |------|---------|------|
> | 桌面 Chrome/Edge/Firefox | FLV（mpegts.js / jessibuca） | 1-3s |
> | Android 微信/浏览器 | FLV 或 WebRTC | 1-3s / <500ms |
> | **iOS Safari / 微信** | **只能 HLS（延迟高）或 WebRTC（<500ms）** | 6-15s / <500ms |
>
> 需要手机看监控的产品，要么接受 iOS 上 HLS 的高延迟，要么 iOS 端走 WebRTC——没有第三条路。

### 3.6 flv.js 播放示例（H.264 only）

```html
<!DOCTYPE html>
<html>
<head>
  <meta charset="UTF-8">
  <title>HTTP-FLV 播放 - flv.js</title>
</head>
<body>
  <video id="videoElement" controls style="width: 100%; max-width: 800px;"></video>
  
  <script src="https://cdn.jsdelivr.net/npm/flv.js/dist/flv.min.js"></script>
  <script>
    if (flvjs.isSupported()) {
      var videoElement = document.getElementById('videoElement');
      var flvPlayer = flvjs.createPlayer({
        type: 'flv',
        isLive: true,
        url: 'http://localhost:8080/live/test.flv',
      }, {
        enableWorker: true,              // Web Worker 解复用（推荐）
        enableStashBuffer: false,        // 直播模式禁用预读缓冲
        stashInitialSize: 128,           // 初始缓冲 128KB
        
        // 低延迟配置
        isLive: true,
        lazyLoad: false,
        lazyLoadMaxDuration: 0.2,        // 最大延迟加载时长
        deferLoadAfterSourceOpen: false,
        
        // 自动清理旧数据（避免内存泄漏）
        autoCleanupSourceBuffer: true,
        autoCleanupMaxBackwardDuration: 30,  // 保留最近 30 秒
        autoCleanupMinBackwardDuration: 20,  // 缓冲小于 20 秒时才清理
      });
      
      flvPlayer.attachMediaElement(videoElement);
      flvPlayer.load();
      flvPlayer.play();
      
      // 错误处理
      flvPlayer.on(flvjs.Events.ERROR, (errorType, errorDetail) => {
        console.error('播放错误:', errorType, errorDetail);
        if (errorType === flvjs.ErrorTypes.NETWORK_ERROR) {
          console.log('网络错误，尝试重连...');
          flvPlayer.unload();
          flvPlayer.detachMediaElement();
          flvPlayer.attachMediaElement(videoElement);
          flvPlayer.load();
        }
      });
    }
  </script>
</body>
</html>
```

### 3.9 延迟优化技巧

**服务端优化（SRS/ZLMediaKit）**：

```nginx
# SRS 低延迟配置
vhost __defaultVhost__ {
    min_latency     on;    # 关键：最小延迟模式
    gop_cache       off;   # 关闭 GOP 缓存（牺牲首屏速度，降低延迟）
    queue_length    10;    # 减小播放队列长度（默认 30）
    
    # 关键帧间隔要求（推流端配置）
    # 建议 GOP = 1-2 秒（30-60 帧）
}
```

**推流端优化（FFmpeg）**：

```bash
ffmpeg -re -i rtsp://camera/stream \
  # 低延迟编码参数
  -c:v libx264 -preset ultrafast -tune zerolatency \
  -g 30 -keyint_min 30 -sc_threshold 0 \  # GOP = 1 秒（30fps）
  
  # 减少缓冲
  -fflags +nobuffer -flags +low_delay \
  -strict experimental -avioflags direct \
  
  # 音频配置
  -c:a aac -b:a 128k \
  
  # 输出 RTMP
  -f flv rtmp://localhost/live/test
```

**前端优化（播放器配置）**：

```javascript
// mpegts.js 低延迟配置
const player = mpegts.createPlayer({
  type: 'flv',
  isLive: true,
  url: 'http://localhost:8080/live/test.flv',
}, {
  enableWorker: true,
  enableStashBuffer: false,            // 禁用预读缓冲
  
  // 核心：追帧策略
  liveBufferLatencyChasing: true,      // 开启追帧
  liveBufferLatencyMaxLatency: 1.5,    // 最大延迟 1.5s
  liveBufferLatencyMinRemain: 0.3,     // 最小保留 0.3s（可再调小）
  
  // 内存清理
  autoCleanupSourceBuffer: true,
  autoCleanupMaxBackwardDuration: 20,  // 只保留 20 秒历史
  autoCleanupMinBackwardDuration: 10,
});
```

**延迟分析**：

| 环节 | 延迟 | 优化方法 |
|------|------|---------|
| **摄像头采集** | 50-100ms | 无法优化（硬件限制） |
| **编码缓冲** | 100-300ms | 使用 `-tune zerolatency`，减小 GOP |
| **网络传输** | 20-100ms | 局域网 < 20ms，公网视距离 |
| **服务器转发** | 10-50ms | 关闭 GOP 缓存，减小队列长度 |
| **播放器缓冲** | 500-2000ms | **最大来源**，优化追帧策略 |
| **解码渲染** | 30-50ms | MSE 硬解 < WASM 软解 |

**总延迟目标**：1-2 秒（优化后）

### 3.10 生产环境部署清单

```nginx

}

server {
    listen 80;
    server_name live.example.com;
    
    # HTTP-FLV 代理
    location /live/ {
        proxy_pass http://srs_http_flv;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        
        # 关键：禁用缓冲
        proxy_buffering off;
        proxy_cache off;
        
        # CORS 配置（如果前端跨域）
        add_header Access-Control-Allow-Origin *;
        add_header Access-Control-Allow-Methods "GET, OPTIONS";
        
        # 超时配置
        proxy_connect_timeout 5s;
        proxy_send_timeout 300s;
        proxy_read_timeout 300s;
    }

    # WebSocket-FLV 代理（ws/wss）
    location /ws/ {
        proxy_pass http://srs_http_flv;
        proxy_http_version 1.1;

        # 关键：WebSocket 协议升级头，少了这两行握手直接失败
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;

        proxy_buffering off;
        proxy_read_timeout 3600s;   # WS 长连接，超时给长一点
    }
}
```

> **HTTPS 页面强制 wss**：前端页面部署在 HTTPS 下时，浏览器禁止连 `ws://`（混合内容拦截），必须用 `wss://`。在 nginx 上配好证书后，上面的 `/ws/` location 自动同时服务 ws 和 wss，无需改流媒体服务器。

### 3.11 首屏延迟 vs 稳态延迟（一组必须理解的 tradeoff）

本文前面讲的都是**稳态延迟**（画面播出后落后实时多少），但用户的第一感知是**首屏延迟**（点击播放后多久出画面）。两者优化方向经常相反：

**为什么出画面要等 IDR 帧**：H.264/H.265 的 P/B 帧依赖前面的帧解码，播放器（MSE）必须从一个 IDR 关键帧开始才能解码。如果播放器在 GOP 中间接入流，只能丢弃数据、干等下一个 IDR：

```
GOP = 2s 的流，最坏情况首屏要等接近 2 秒
|IDR|—P—P—P—...—P—P—|IDR|—P—P—...
                 ↑
           播放器在这里接入，前面全废，等到下一个 IDR
```

**服务端 GOP 缓存的作用与代价**：
- `gop_cache on`：服务器缓存最近一个 GOP，新观众接入**立即**补发上一个 IDR → 首屏快，但观众起点是「最多一个 GOP 前的旧画面」→ **稳态延迟变大**（之后靠追帧慢慢消化）
- `gop_cache off`（3.9 节的低延迟配置）：接入即最新帧，但无 IDR 就只能等 → **首屏变慢**

**实践结论**：

| 场景 | 推荐配置 | 理由 |
|------|---------|------|
| 监控大屏（常开不切换）| `gop_cache off` + 短 GOP（1s）| 首屏最多等 1s 可接受，稳态延迟优先 |
| 频繁切换摄像头 | `gop_cache on` + 追帧配置 | 切换要秒出画面，延迟靠追帧消化 |
| GOP 很长（>5s 的摄像头）| 必须 `gop_cache on` | 否则首屏最坏等 5s+，不可接受 |

推流端把 GOP 控制在 1-2s 是两个目标共同的优化——首屏等待和追帧压力都随 GOP 缩短而减小。

## 四、LL-HLS 方案（CDN 场景）

适合需要 CDN 分发 + 低延迟的场景。

> **⚠️ 重要纠正：FFmpeg 原生 hls muxer 生成不了真 LL-HLS**
>
> 网上常见的「`-hls_time 1` + `-http_persistent 1` 就是 LL-HLS」说法是**错的**。真 LL-HLS 需要服务端实现三个协议特性：
> 1. **部分分片**（`EXT-X-PART`）：把 1 个切片再切成 200-500ms 的 part，不用等整段切完
> 2. **阻塞式 playlist 请求**（`_HLS_msn` / `_HLS_part` 查询参数）：客户端「挂着等」，服务端有新分片才返回
> 3. **fMP4 切片**（`hls_segment_type fmp4`，CMAF）
>
> FFmpeg 的 hls muxer 不支持前两条，`-http_persistent 1` 只是 HTTP keep-alive，**不是 HTTP/2 push**。照那种命令做出来的是「短切片普通 HLS」，延迟 3-6s，且 CDN 不识别 `_HLS_*` 参数时阻塞请求直接失效。

**两条可行路线**：

**路线 A：流媒体服务器生成真 LL-HLS**（推荐）

SRS 6.x / OvenMediaEngine 等服务器原生支持 LL-HLS 输出，推流端只需要普通 RTMP：

```bash
# 推流端就是普通推流，LL-HLS 由服务器生成
ffmpeg -re -i rtsp://camera/stream \
  -c:v libx264 -preset veryfast -b:v 1500k -g 30 \
  -c:a aac -b:a 128k \
  -f flv rtmp://srs-server/live/stream
```

```nginx
# SRS 6.x 开启 LL-HLS（低延迟 HLS）
vhost __defaultVhost__ {
    hls {
        enabled         on;
        hls_fragment    1;    # 1 秒切片
        hls_window      6;
    }
}
```

**前提**：CDN 必须支持 LL-HLS（透传 `_HLS_msn`/`_HLS_part` 阻塞请求和部分分片），否则中间缓存会把 LL-HLS 退化成普通 HLS。国内 CDN 支持度参差，接入前实测确认。

**路线 B：短切片 HLS 折中**（CDN 不支持 LL-HLS 时）

接受 4-8s 延迟，换 CDN 全兼容：

```bash
ffmpeg -re -i rtsp://camera/stream \
  -c:v libx264 -preset veryfast -b:v 1500k -g 30 \
  -c:a aac -b:a 128k \
  -f hls \
  -hls_time 1 \              # 1 秒切片
  -hls_list_size 6 \
  -hls_flags +independent_segments+program_date_time \
  -hls_segment_type fmp4 \   # fMP4（CMAF），比 mpegts 切片开销小
  output.m3u8
```

**播放端配置（hls.js）**：

```javascript
const hls = new Hls({
  lowLatencyMode: true,   // 服务端是真 LL-HLS 时才生效；普通 HLS 下是无害的空配置
  backBufferLength: 10,
});
hls.loadSource('https://cdn.example.com/stream/output.m3u8');
hls.attachMedia(video);
```

> `lowLatencyMode: true` 只负责「服务端支持 LL-HLS 时启用部分分片加载和阻塞请求」，它**不会**把普通 HLS 变成低延迟——服务端不支持时延迟照旧。

## 七、延迟监控与告警

### 7.1 先搞清楚：PTS 不是墙上时钟

一个常见误解：「从 TS 包里解析 PTS，跟系统时间一比就是端到端延迟」。**这是错的**——PTS 是流内部的相对时钟（90kHz 时基的相对值，起点由编码器定），跟现实时间没有对应关系，`time.Unix(0, pts)` 算出来的是无意义数字。

正确做法有三种，按可靠性排序：

### 7.2 方法一：画面烧录时间戳（最可靠，推荐验收用）

推流端用 `drawtext` 把**推流时刻的系统时间**画进画面，播放端肉眼或截图比对：

```bash
ffmpeg -re -f lavfi \
  -i "testsrc=size=1280x720:rate=30,drawtext=text='%{localtime}.%{eif\:mod(n,30)*33\:d\:3}':fontsize=48:fontcolor=yellow:x=10:y=10" \
  -c:v libx264 -tune zerolatency -preset ultrafast -g 30 \
  -f flv rtmp://localhost/live/latency
```

播放端截图，用「当前真实时间 − 画面里的时间」即端到端延迟。摄像头场景同理：摄像头 OSD 时间本身就是烧录在画面里的时钟。

### 7.3 方法二：FFmpeg 把墙上时钟写进时间戳（程序化测量）

推流时加 `-use_wallclock_as_timestamps 1`，PTS 就变成采集时刻的 Unix 时间，服务端/播放器解析后即可程序化计算：

```bash
ffmpeg -use_wallclock_as_timestamps 1 \
  -fflags +genpts -rtsp_transport tcp -i rtsp://camera/stream \
  -c copy -f flv rtmp://server/live/stream
```

```go
// 此时 PTS 才是 Unix 时间（毫秒），可以做差
func measureLatency(ptsMillis int64) time.Duration {
    return time.Since(time.UnixMilli(ptsMillis))
}

// 超过阈值告警
if latency := measureLatency(pts); latency > 5*time.Second {
    log.Warn().Dur("latency", latency).Str("stream", streamID).Msg("延迟超标")
    metrics.LatencyGauge.WithLabelValues(streamID).Set(latency.Seconds())
}
```

注意：摄像头直接推 RTMP 时这个选项作用在 FFmpeg 侧，测的是「FFmpeg 收到帧 → 播放」的延迟，不含摄像头到 FFmpeg 的链路。

### 7.4 方法三：SEI timecode（编码器级，最精确）

编码器在 SEI 消息里嵌入 `time_code`（H.264/H.265 标准支持），解码端解析 SEI 拿采集时刻。精度最高，但需要播放器支持 SEI 解析（jessibuca 支持，mpegts.js 需自行扩展），工程成本最高。

## 本篇小结

| 需求 | 推荐方案 | 延迟 |
|------|---------|------|
| 安防监控（无CDN，桌面端）| WebSocket+FLV+mpegts.js | 1-3s |
| 直播（需CDN）| 真 LL-HLS（SRS 6.x）+ hls.js | 2-5s |
| CDN 不支持 LL-HLS | 短切片 HLS 折中 | 4-8s |
| **iOS 端（Safari/微信）** | **HLS 或 WebRTC（无 MSE，FLV 不可行）** | 6-15s / <500ms |
| 实时互动 | WebRTC WHIP/WHEP | < 500ms |
| 传统兼容 | RTMP → 标准HLS | 6-15s |

关键原则：
1. **缓冲是延迟的主要来源**，缩小 GOP/切片 + 配置客户端追帧策略是最有效的手段
2. **先分清首屏延迟和稳态延迟**，GOP 缓存开关对两者的影响相反（见 3.11）
3. **先确认终端平台再选方案**——iOS 不支持 MSE 这一条会直接否决 FLV 系方案

**进阶阅读**：mpegts.js 的完整生命周期管理、MSE API 深入、16 路流管理、Canvas 画框坐标系统等工程实践详见 👉 [第 21.5 篇 — MSE 与前端播放器工程实践](21.5-MSE与前端播放器工程实践.md)

func (h *StreamHandler) StreamFLV(c *gin.Context) {
    path := c.Query("path")
    // 升级为 WebSocket
    conn, err := h.upgrader.Upgrade(c.Writer, c.Request, nil)
    if err != nil {
        return

        return conn.WriteMessage(websocket.BinaryMessage, data)
    })

    }
}

## 常见问题排查

| 现象 | 可能原因 | 解决方法 |
|------|---------|---------|
| 播放器延迟越来越大（延迟爬升）| 追帧策略未开启 | 启用 `liveBufferLatencyChasing: true` |
| 追帧时画面跳顿 | 追帧加速比太大 | 增大 `liveBufferLatencyMinRemain`（如0.5s）|
| 切换播放方案后黑屏 | 旧 player 实例未销毁 | 切换前调用 `player.destroy()` |
| WebSocket FLV 连接断开不重连 | 前端无重连机制 | 监听 `close` 事件，指数退避重连 |
| WebRTC 延迟稳定但偶尔跳变 | 网络抖动导致 jitter buffer 突然增大 | 检查 TURN 服务器负载，使用稳定网络 |
| `play()` 无画面无声音，控制台报 NotAllowedError | 浏览器自动播放策略拦截 | 视频加 `muted` 静音播放，或等用户交互后再 play |
| iPhone 上 FLV 播放器黑屏/报错 | iOS Safari 不支持 MSE | iOS 端切换 HLS 或 WebRTC 方案 |
| 多人同时看同一路摄像头时服务器 CPU 飙高 | 每个连接独立拉流+转封装 | 源流复用（一路拉流 fan-out），或交给 SRS/ZLMediaKit |
| HTTPS 页面下 WebSocket 连不上 | 混合内容拦截 / nginx 缺 Upgrade 头 | 改用 wss://，nginx 加 `Upgrade`/`Connection` 头（见 3.10）|
| 点击播放后好几秒才出画面 | GOP 太长且关了 GOP 缓存 | 缩短 GOP 到 1-2s，或开启 `gop_cache`（见 3.11）|

## 术语表

| 术语 | 英文 | 说明 |
|------|------|------|
| 追帧 | Live Buffer Latency Chasing | 播放器检测到延迟超阈值时自动加速播放来消除缓冲 |
| HTTP-FLV | HTTP-FLV | 通过 HTTP 长连接或 WebSocket 传输 FLV 流，延迟约1-3s |
| 延迟爬升 | Latency Creep | 直播播放中缓冲持续累积导致延迟不断增大的现象 |
| liveBufferLatencyMaxLatency | Max Latency | mpegts.js 触发追帧的延迟阈值 |
| stashBuffer | Stash Buffer | mpegts.js 输入数据的预读缓冲，直播建议关闭 |
| 首屏延迟 | First Frame Latency | 点击播放到画面出现的时间；受 GOP 长度和 GOP 缓存策略直接影响 |
| 稳态延迟 | Steady-state Latency | 播放稳定后画面落后实时的时间；本文优化清单主要针对它 |
| IDR 帧 | IDR Frame | 可独立解码的关键帧，播放器必须从 IDR 开始才能解码，是首屏延迟的决定因素 |
| GOP 缓存 | GOP Cache | 服务端缓存最近一个 GOP 供新观众立即起播；开=首屏快但稳态延迟大 |
| MSE | Media Source Extensions | 浏览器 JS 侧喂流解码的 API，FLV 系播放器的根基；iOS Safari 不支持 |
| LL-HLS | Low-Latency HLS | 基于部分分片（EXT-X-PART）+ 阻塞请求的低延迟 HLS，需服务端与 CDN 同时支持 |
