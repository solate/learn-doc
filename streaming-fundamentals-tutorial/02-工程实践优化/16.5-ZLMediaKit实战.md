## 一、ZLMediaKit 核心特性回顾

第 14 篇已经给出结论：接入海康/大华等国标设备、追求 WebRTC 低延迟、需要海量流转发时选 ZLMediaKit。本篇把它当作生产组件真正用起来。

### 1.1 流的四元组模型

理解 ZLMediaKit 的一切 URL 和 API 都要从四元组开始。MediaMTX 里一路流就是一个 `path`，而 ZLMediaKit 用四个元素标识一路流：

```
schema（协议类型）+ vhost（虚拟主机）+ app（应用名）+ stream（流 ID）

例：rtmp://192.168.1.10/live/camera_001
     └─ schema: rtmp
        vhost: __defaultVhost__（IP 访问时为默认虚拟主机）
        app:   live
        stream: camera_001
```

同一份数据可以同时以多种 schema 存在（rtsp/rtmp/hls/ts/fmp4 各一个 MediaSource），它们共享同一份原始数据，按需转封装。**推流用一种协议进来，播放用任何协议出去**，这是 ZLMediaKit 的核心工作方式。

```
推流端                       ZLMediaKit                    播放端
  ├── RTSP（摄像头）──┐       ┌── RtspMediaSource ──→ RTSP / WebRTC 播放
  ├── RTMP（OBS）────┤       ├── RtmpMediaSource ──→ RTMP / HTTP-FLV / WS-FLV
  ├── GB28181 RTP ───┼──→ 转协议 ──→ HlsMediaSource ──→ HLS 播放
  ├── SRT ───────────┤       ├── TSMediaSource  ──→ HTTP-TS / WS-TS
  └── WebRTC ────────┘       └── FMP4MediaSource ──→ HTTP-fMP4 / WS-fMP4
                                     ↑
                          Hook 回调 Go 后端（鉴权/状态/按需拉流）
```

### 1.2 与 MediaMTX 的模型对照

第 16 篇用 MediaMTX 实现了摄像头管理，同样的场景换 ZLMediaKit，概念映射如下：

| 概念 | MediaMTX | ZLMediaKit |
|------|----------|------------|
| 流标识 | `path`（单级字符串） | `app + stream` 四元组 |
| 拉流配置 | `paths.xxx.source: rtsp://...` | `addStreamProxy` API（动态，不写配置文件） |
| 推流鉴权 | `authMethod: http` 回调 | `[hook] on_publish` 回调 |
| 按需拉流 | `sourceOnDemand: true` | `on_stream_not_found` Hook + `addStreamProxy` |
| 无人观看断开 | `sourceOnDemandCloseAfter` | `on_stream_none_reader` Hook |
| 动态管理 | REST API `/v3/config/paths/*` | REST API `/index/api/*` |
| 事件通知 | `runOnPublish` 执行命令 | Hook 事件 HTTP 回调（结构化 JSON） |

可以看出：**MediaMTX 把策略写进 YAML，ZLMediaKit 把策略交给业务后端**。流多、规则活（按用户权限动态放行、按设备状态决定是否拉流）的场景，ZLMediaKit 的 Hook 模型更顺手；这也是安防平台普遍选它的原因之一。

## 二、快速启动

### 2.1 Docker 启动

官方镜像一条命令拉起（HTTP 容器内 80 端口，映射到宿主机 8080）：

```bash
docker run -id \
  --name zlmediakit \
  -p 1935:1935 \          # RTMP
  -p 8080:80 \            # HTTP（HLS/HTTP-FLV/API）
  -p 8443:443 \           # HTTPS
  -p 8554:554 \           # RTSP
  -p 10000:10000 \        # RTP 代理（TCP）
  -p 10000:10000/udp \    # RTP 代理（UDP，GB28181 单端口模式）
  -p 8000:8000/udp \      # WebRTC
  -p 9000:9000/udp \      # SRT
  zlmediakit/zlmediakit:master
```

**注意**：如果要接 GB28181 设备且用多端口收流模式，还需要映射 `30000-35000/udp` 端口段（见第六节）。

推一路流验证：

```bash
ffmpeg -re -i test.mp4 -c copy -f flv rtmp://localhost:1935/live/test

# 查询在线流（secret 是默认值，见 2.2）
curl "http://localhost:8080/index/api/getMediaList?secret=035c73f7-bb6b-4889-a715-d9eb2d1925cc"
```

### 2.2 默认端口与 secret

| 服务 | 默认端口 | 协议 | 说明 |
|------|---------|------|------|
| RTMP | 1935 | TCP | 推流/播放 |
| RTSP | 554 | TCP | 推流/播放 |
| HTTP | 80 | TCP | HLS/HTTP-FLV/REST API 共用 |
| HTTPS | 443 | TCP | 同上的 TLS 版本 |
| WebRTC | 8000 | UDP（TCP 兜底） | STUN/DTLS/SRTP 全走这个端口 |
| SRT | 9000 | UDP | SRT 推拉流 |
| RTP 代理 | 10000 | TCP/UDP | GB28181 单端口模式收流 |
| RTP 端口段 | 30000-35000 | UDP | GB28181 多端口模式收流 |

**必须立即修改默认 secret**。`config.ini` 中 `[api] secret` 是调用 REST API 的鉴权密钥，所有镜像出厂值相同；且通过 `127.0.0.1` 访问可以免密。生产部署务必：改 secret + 不要把 API 端口暴露到公网。

```ini
# config.ini
[api]
apiDebug=0
secret=换成自己的随机UUID
```

### 2.3 播放地址规则

一路 `rtmp://host/live/test` 推上来后，所有协议的播放地址（HTTP 端口按上面映射是 8080）：

| 协议 | 播放地址 |
|------|---------|
| RTSP | `rtsp://host:554/live/test` |
| RTMP | `rtmp://host:1935/live/test` |
| HTTP-FLV | `http://host:8080/live/test.live.flv` |
| WebSocket-FLV | `ws://host:8080/live/test.live.flv` |
| HTTP-TS | `http://host:8080/live/test.live.ts` |
| HTTP-fMP4 | `http://host:8080/live/test.live.mp4` |
| HLS | `http://host:8080/live/test/hls.m3u8` |
| WebRTC | `POST http://host:8080/index/api/webrtc?app=live&stream=test&type=play` |
| WHEP | `http://host:8080/index/api/whep?app=live&stream=test`（标准化拉流，见第 13 篇） |

几点说明：
- **`.live.flv` 是新代码后缀**（老版本是 `.flv`），`.live.ts` / `.live.mp4` 的 `live` 同理，用于和 MP4 点播区分。
- WebRTC 没有标准信令，ZLMediaKit 用 HTTP POST 交换 SDP：请求体是 offer SDP，响应体是 answer SDP。浏览器打开 `http://host:8080/webrtc/` 可以用官方自带测试页直接验证。
- URL 查询参数（如 `?token=xxx`）会原样传给 Hook 的 `params` 字段，这是鉴权的载体。

## 三、配置详解

ZLMediaKit 用 `config.ini`（Docker 部署挂载到容器内覆盖默认配置）。生产常用的几个段：

### 3.1 核心段示例

```ini
# config.ini

[api]
apiDebug=0
# REST API 鉴权密钥（必改！）
secret=your-own-uuid-here

[hook]
# Hook 总开关，默认 0；开启后推拉流都会走鉴权
enable=1
# 推流鉴权（返回 code!=0 拒绝）
on_publish=http://backend:8081/api/v1/zlm/on_publish
# 播放鉴权
on_play=http://backend:8081/api/v1/zlm/on_play
# 流注册/注销（同步在线状态到业务库）
on_stream_changed=http://backend:8081/api/v1/zlm/on_stream_changed
# 播放时流不存在（按需拉流的入口）
on_stream_not_found=http://backend:8081/api/v1/zlm/on_stream_not_found
# 无人观看（配合 auto_close 自动断开拉流）
on_stream_none_reader=http://backend:8081/api/v1/zlm/on_stream_none_reader
# MP4 录制完成（文件路径入库，时间轴回放用）
on_record_mp4=http://backend:8081/api/v1/zlm/on_record_mp4
# GB28181 收流超时
on_rtp_server_timeout=http://backend:8081/api/v1/zlm/on_rtp_server_timeout
# 回调超时与重试
timeoutSec=10
retry=1

[rtc]
# 对客户端可见的 IP，NAT/云服务器部署必填公网 IP
externIP=
# UDP 端口，NAT 端口映射时内外必须一致
port=8000

[rtp_proxy]
# GB28181 单端口模式收流端口
port=10000
# 多端口模式端口范围（同时约束 RTSP UDP 端口）
port_range=30000-35000
# 收流超时
timeoutSec=15

[record]
# MP4 录制的 app 名，点播也只允许这个 app
appName=record

[protocol]
# 转协议开关：用不到的输出关掉，省 CPU
enable_hls=1
enable_rtsp=1
enable_rtmp=1
enable_ts=0
enable_fmp4=0
enable_mp4=0        # 推流即录像（一般不用，按需用 API 开启）
# 无人观看时直接关流（置 1 则不再触发 on_stream_none_reader 回调）
auto_close=0
```

### 3.2 转协议开关的性能含义

`[protocol]` 段的 `enable_*` 决定每路流进来后生成哪些 MediaSource。**默认全开**意味着 1000 路流即使只用 HTTP-FLV 播放，也在持续切 HLS 分片、组 TS 流——全是白烧的 CPU。生产上按实际使用的播放协议收敛，是 ZLMediaKit 调优的第一步。

## 四、RESTful API 与 Go 客户端封装

### 4.1 常用 API 速查

所有 API 都是 `GET/POST /index/api/xxx?secret=xxx&...`，返回 JSON 统一为 `{"code":0, "msg":"", "data":...}`，`code != 0` 即失败。

| API | 作用 |
|-----|------|
| `getMediaList` | 在线流列表（schema/app/stream/观看人数/创建时间） |
| `addStreamProxy` | 添加拉流代理：从远程 URL 拉流转成本地流（按需回源的核心） |
| `delStreamProxy` | 删除拉流代理（用 add 返回的 key） |
| `listStreamProxy` | 拉流代理列表 |
| `addStreamPusherProxy` | 转推代理：把本地流推向其他服务器 |
| `close_streams` | 关闭流（按 vhost/app/stream/schema 过滤） |
| `getServerConfig` / `setServerConfig` | 读取/修改运行时配置 |
| `getAllSession` / `kick_session` | 会话管理与踢人 |
| `startRecord` / `stopRecord` / `isRecording` | 动态 MP4 录制控制 |
| `getSnap` | FFmpeg 截图（封面帧） |
| `openRtpServer` / `closeRtpServer` / `listRtpServer` | GB28181 收流端口管理（见第六节） |
| `startSendRtp` / `stopSendRtp` | 把流转成 RTP 发出（国标级联） |

### 4.2 Go 客户端封装

对照第 16 篇的 MediaMTX 客户端，写一个同风格的 ZLMediaKit 客户端：

```go
// pkg/zlmediakit/client.go
package zlmediakit

type Client struct {
    baseURL    string
    secret     string
    httpClient *http.Client
}

func NewClient(baseURL, secret string) *Client {
    return &Client{
        baseURL:    baseURL,
        secret:     secret,
        httpClient: &http.Client{Timeout: 5 * time.Second},
    }
}

// call 统一处理 secret、错误码
func (c *Client) call(ctx context.Context, api string, params map[string]string, out any) error {
    q := url.Values{}
    q.Set("secret", c.secret)
    for k, v := range params {
        q.Set(k, v)
    }
    req, err := http.NewRequestWithContext(ctx, http.MethodGet, c.baseURL+"/index/api/"+api+"?"+q.Encode(), nil)
    if err != nil {
        return xerr.Wrap(xerr.ErrInternal.Code, "构造ZLM请求失败", err)
    }
    resp, err := c.httpClient.Do(req)
    if err != nil {
        return xerr.Wrap(xerr.ErrInternal.Code, "调用ZLM API失败", err)
    }
    defer resp.Body.Close()

    var result struct {
        Code int             `json:"code"`
        Msg  string          `json:"msg"`
        Data json.RawMessage `json:"data"`
    }
    if err := json.NewDecoder(resp.Body).Decode(&result); err != nil {
        return xerr.Wrap(xerr.ErrInternal.Code, "解析ZLM响应失败", err)
    }
    if result.Code != 0 {
        return xerr.Newf(xerr.ErrInternal.Code, "ZLM API %s 失败: code=%d msg=%s", api, result.Code, result.Msg)
    }
    if out == nil {
        return nil
    }
    return json.Unmarshal(result.Data, out)
}

// MediaInfo 一路在线流（getMediaList 返回项）
type MediaInfo struct {
    Schema      string `json:"schema"`      // rtsp/rtmp/hls/ts/fmp4
    Vhost       string `json:"vhost"`
    App         string `json:"app"`
    Stream      string `json:"stream"`
    Ready       bool   `json:"ready"`             // 是否就绪可播
    TotalReader int    `json:"totalReaderCount"`  // 总观看人数
    CreateStamp int64  `json:"createStamp"`       // 流创建时间（秒级时间戳）
    OriginURL   string `json:"originUrl"`         // 拉流代理的源地址
}

// GetMediaList 查询在线流
func (c *Client) GetMediaList(ctx context.Context) ([]MediaInfo, error) {
    var list []MediaInfo
    if err := c.call(ctx, "getMediaList", nil, &list); err != nil {
        return nil, err
    }
    return list, nil
}

// AddStreamProxy 添加拉流代理（远程流 → 本地 app/stream）
// 返回 key，用于 DelStreamProxy
func (c *Client) AddStreamProxy(ctx context.Context, app, stream, srcURL string, enableMP4 bool) (string, error) {
    var data struct {
        Key string `json:"key"`
    }
    err := c.call(ctx, "addStreamProxy", map[string]string{
        "vhost":      "__defaultVhost__",
        "app":        app,
        "stream":     stream,
        "url":        srcURL,
        "rtp_type":   "1", // 1=TCP（摄像头 UDP 易丢包，生产建议 TCP）
        "enable_hls": "1",
        "enable_mp4": strconv.FormatBool(enableMP4),
    }, &data)
    if err != nil {
        return "", err
    }
    return data.Key, nil
}

// DelStreamProxy 删除拉流代理
func (c *Client) DelStreamProxy(ctx context.Context, key string) error {
    return c.call(ctx, "delStreamProxy", map[string]string{"key": key}, nil)
}

// CloseStreams 关闭一路流（推流端和拉流代理都会被断开）
func (c *Client) CloseStreams(ctx context.Context, app, stream string) error {
    return c.call(ctx, "close_streams", map[string]string{
        "app": app, "stream": stream,
    }, nil)
}
```

### 4.3 场景：摄像头管理（对照第 16 篇）

第 16 篇用 `AddPath` 把摄像头注册到 MediaMTX，ZLMediaKit 版本几乎一样，只是"注册"变成了"添加拉流代理"：

```go
// service/camera_service.go

type CameraService struct {
    zlm        *zlmediakit.Client
    cameraRepo repository.CameraRepo
}

// 上线摄像头：ZLM 添加拉流代理，立即生成一路可播的流
func (s *CameraService) BringOnline(ctx context.Context, cameraID string) error {
    camera, err := s.cameraRepo.GetByID(ctx, cameraID)

        return err
    }
    _, err = s.zlm.AddStreamProxy(ctx, "live", cameraID, camera.RTSPURL, false)
    return err

// 获取播放地址（对照 16 篇同款方法，仅端口和路径规则不同）
```

## 五、Hook 事件回调与 Go 后端集成

Hook 是 ZLMediaKit 与业务后端的黏合剂：**ZLMediaKit 只管流，不管谁有权限看、流对应哪个设备**——全部通过 HTTP 回调交给后端裁决。

### 5.1 事件列表

| 事件 | 触发时机 | 典型用途 |
|------|---------|---------|
| `on_publish` | 有人推流 | 推流鉴权 |
| `on_play` | 有人播放 | 播放鉴权（含 HLS/FLV/WebRTC 全协议） |
| `on_stream_changed` | 流注册/注销 | 同步在线状态到数据库 |
| `on_stream_not_found` | 播放的流不存在 | **按需拉流**（回源） |
| `on_stream_none_reader` | 流无人观看 | 自动关闭省资源 |
| `on_record_mp4` | MP4 切片完成 | 录像文件入库（时间轴回放） |
| `on_rtp_server_timeout` | GB28181 收流超时 | 通知信令服务器重发 INVITE |
| `on_flow_report` | 流量统计 | 计费 |
| `on_server_keepalive` | 服务器保活 | 多节点健康检查 |

所有回调都是 POST JSON，**响应必须 HTTP 200 + `{"code": 0, "msg": "success"}`**；鉴权类事件返回非 0 code 即拒绝。

### 5.2 推流/播放鉴权（on_publish / on_play）

推流端把 token 放在 URL 参数里（`rtmp://host/live/test?token=xxx`），ZLMediaKit 原样带给 Hook：

```go
// internal/handler/stream/zlm_hook.go

// ZLMOnPublish ZLMediaKit on_publish 回调：验证推流 token
func (h *StreamHandler) ZLMOnPublish(c *gin.Context) {
    var req struct {
        MediaServerID string `json:"mediaServerId"`
        Schema        string `json:"schema"`
        App           string `json:"app"`
        Stream        string `json:"stream"`
        Params        string `json:"params"` // URL 查询参数原文，如 "token=xxx"
        IP            string `json:"ip"`
    }
    if err := c.ShouldBindJSON(&req); err != nil {
        c.JSON(http.StatusOK, gin.H{"code": -400, "msg": "bad request"})
        return
    }

    params, _ := url.ParseQuery(req.Params)
    token := params.Get("token")

    // 只允许业务侧登记过的 app（如 live/camera），防止陌生 app 推流
    if req.App != "live" {
        c.JSON(http.StatusOK, gin.H{"code": -1, "msg": "forbidden app"})
        return
    }
    valid, err := h.streamSvc.ValidatePushToken(c.Request.Context(), req.Stream, token)
    if err != nil || !valid {
        // code != 0：ZLMediaKit 立刻断开这次推流
        c.JSON(http.StatusOK, gin.H{"code": -1, "msg": "invalid token"})
        return
    }
    c.JSON(http.StatusOK, gin.H{"code": 0, "msg": "success"})
}

// ZLMOnPlay on_play 回调：验证播放 token（逻辑同上，验完后可选返回 close_streams 等）
func (h *StreamHandler) ZLMOnPlay(c *gin.Context) {
    // 与 ZLMOnPublish 同构：解析 params 中的 token，
    // 按用户/设备权限校验后返回 {"code":0} 或 {"code":-1}
    ...
}
```

`on_play` 覆盖**所有播放协议**——HLS、HTTP-FLV、WebRTC 播放前都会回调，不像 Nginx-RTMP 只能拦推流。

### 5.3 在线状态同步（on_stream_changed）

流注册/注销时触发。**一个必踩的坑**：同一份数据按协议注册，`on_stream_changed` 会对 `rtsp/rtmp/ts/hls/fmp4` 各回调一次（受 `stream_changed_schemas` 配置过滤），同一路流"上线"可能连续触发多次。业务侧只关心"这路流在不在"，必须去重：

```go
// ZLMOnStreamChanged 同步流在线状态
func (h *StreamHandler) ZLMOnStreamChanged(c *gin.Context) {
    var req struct {
        Schema string `json:"schema"`
        App    string `json:"app"`
        Stream string `json:"stream"`
        Regist bool   `json:"regist"` // true=注册 false=注销
    }
    if err := c.ShouldBindJSON(&req); err != nil {
        c.JSON(http.StatusOK, gin.H{"code": -400, "msg": "bad request"})
        return
    }

    // 只认一种 schema，天然去重（不同协议的注册/注销时序可能交错，
    // 混用多个 schema 判断会造成在线状态抖动）
    if req.Schema != "rtmp" {
        c.JSON(http.StatusOK, gin.H{"code": 0})
        return
    }

    // 更新业务库在线状态 + WebSocket 通知前端设备上下线
    if err := h.streamSvc.SyncStreamState(c.Request.Context(), req.App, req.Stream, req.Regist); err != nil {
        log.Error().Str("stream", req.Stream).Bool("regist", req.Regist).Err(err).Msg("同步流状态失败")
        // 状态同步失败不应阻断回调，ZLMediaKit 重试机制会补一次
    }
    c.JSON(http.StatusOK, gin.H{"code": 0})
}
```

### 5.4 按需拉流（on_stream_not_found + on_stream_none_reader）

第 16 篇里 MediaMTX 用 `sourceOnDemand: true` 实现按需拉流；ZLMediaKit 把这件事拆成两个 Hook，**控制权完全在业务后端**：

```go
// ZLMOnStreamNotFound 播放的流不存在 → 尝试回源拉流
func (h *StreamHandler) ZLMOnStreamNotFound(c *gin.Context) {
    var req struct {
        App    string `json:"app"`
        Stream string `json:"stream"`
        Params string `json:"params"`
    }
    _ = c.ShouldBindJSON(&req)

    // 查业务库：这路流是否有对应设备、拉流地址是什么
    camera, ok, err := h.cameraSvc.FindByStreamID(c.Request.Context(), req.Stream)
    if err != nil || !ok {
        // 找不到也返回 code 0，否则 ZLMediaKit 会按 retry 配置反复重试回调
        c.JSON(http.StatusOK, gin.H{"code": 0})
        return
    }

    // 回源：添加拉流代理，流注册后播放器自动出画面
    if _, err := h.zlm.AddStreamProxy(c.Request.Context(), req.App, req.Stream, camera.RTSPURL, false); err != nil {
        log.Error().Str("stream", req.Stream).Err(err).Msg("按需拉流失败")
    }
    c.JSON(http.StatusOK, gin.H{"code": 0})
}

// ZLMOnStreamNoneReader 无人观看 → 关闭拉流代理，释放带宽
func (h *StreamHandler) ZLMOnStreamNoneReader(c *gin.Context) {
    var req struct {
        App    string `json:"app"`
        Stream string `json:"stream"`
    }
    _ = c.ShouldBindJSON(&req)
    _ = h.zlm.CloseStreams(c.Request.Context(), req.App, req.Stream)
    c.JSON(http.StatusOK, gin.H{"code": 0})
}
```

组合效果：**播放器请求流 → 不存在则回源拉摄像头 → 有人看就一直转 → 最后一个人走了就断开**。全链路无需在 ZLMediaKit 侧配置任何静态信息，设备增减只改业务库。

安防国标平台的经典开源组合 wvp-GB28181-pro 用的正是同一套机制，只不过 `on_stream_not_found` 触发的不是 `addStreamProxy`，而是向摄像头发 SIP INVITE 点播（见下节）。

## 六、GB28181 国标接入

### 6.1 信令与媒体分离：wvp-GB28181-pro + ZLMediaKit

GB28181 = SIP 信令 + RTP 媒体流。**ZLMediaKit 只实现媒体面**（收 RTP/PS 流、转协议分发），SIP 信令（注册、目录订阅、INVITE 点播、PTZ 控制）需要一个信令服务器。业界标准组合：

```
摄像头（海康/大华）                    Go 业务后端（你写的）
   │                                     │
   │ SIP REGISTER/INVITE                 │ 设备/通道管理、用户权限
   ▼                                     ▼
┌─────────────────┐  HTTP API  ┌──────────────────┐
│ wvp-GB28181-pro │──────────→ │ ZLMediaKit       │
│ （SIP 信令服务器）│ openRtpServer│ （媒体服务器）    │
└─────────────────┘            └──────────────────┘
   │                                  ▲
   │  INVITE 时指定收流端口             │ RTP/PS（媒体流）
   └──通知摄像头往这个端口推──────────────┘
                                     │ 转协议
                                     ▼
                          HLS / HTTP-FLV / WebRTC 播放器
```

wvp-GB28181-pro（Java/Spring Boot）通过与 ZLMediaKit 完全相同的 Hook + REST API 集成——也就是说**你看懂了第五节，就看懂了 wvp 的下半身**。wvp 管设备和信令，ZLMediaKit 管流，两者通过 `mediaServerId` 互相识别。

### 6.2 单端口模式 vs 多端口模式

ZLMediaKit 收 GB28181 的 RTP 流有两种打开方式，由 `openRtpServer` 的参数决定：

| 模式 | 端口 | 区分方式 | 适用 |
|------|------|---------|------|
| 多端口模式 | 每设备分配 30000-35000 中一个 | 端口即设备 | 设备少，网络简单 |
| 单端口模式 | 统一 10000 | SSRC（INVITE 时下发） | 设备多，防火墙友好 |

```bash
# 多端口：指定端口打开收流服务（port=0 则从 30000-35000 随机分配）
curl "http://localhost:8080/index/api/openRtpServer?secret=xxx&port=30001&tcp_mode=0&stream_id=gb_34020000001320000001"

# 单端口复用模式：所有设备共用 10000，靠 SSRC 区分
curl "http://localhost:8080/index/api/openRtpServerMultiplex?secret=xxx&port=10000&tcp_mode=1&stream_id=gb_34020000001320000001"
```

单端口模式大幅减少防火墙开孔和 Docker 端口映射（不用映射 30000-35000 整段），是云上部署的首选；代价是对 TCP 模式有要求（`tcp_mode=1`），部分老设备只支持 UDP 指定端口，要留多端口模式兜底。

### 6.3 点播完整时序

```
播放器          Go后端          wvp(ZLM)         摄像头
  │ GET /play    │                │                │
  │────────────→│                │                │
  │              │ on_stream_not_found             │
  │              │←──────────────│                │
  │              │ SIP INVITE（指定收流端口+SSRC）   │
  │              │───────────────────────────────→│
  │              │                │   RTP/PS 流    │
  │              │                │←───────────────│
  │              │                │ 流注册 on_stream_changed
  │              │←──────────────│                │
  │ HLS/FLV/WebRTC 地址            │                │
  │←────────────│                │                │
  │ 播放         │───────────────────────────────→│
```

无人观看后由 `on_stream_none_reader` 触发 wvp 向摄像头发 SIP BYE，停止推流，整条链路资源全部释放。

### 6.4 级联与转推（startSendRtp）

ZLMediaKit 不仅能收 RTP，还能把本地流**转成 RTP/PS 发出去**——`startSendRtp` 用于国标级联（下级平台把流推给上级平台）或对接只收 RTP 的第三方系统。参数核心是目标 IP、端口、SSRC，配合 `on_send_rtp_stopped` 回调感知发送中断。

## 七、录像与截图

### 7.1 MP4 录制的三种触发方式

| 方式 | 命令 | 适用 |
|------|------|------|
| 全局推流即录 | `[protocol] enable_mp4=1` | 很少用：所有流都录，磁盘黑洞 |
| 拉流代理时录制 | `addStreamProxy` 带 `enable_mp4=1` | 摄像头 7×24 录像 |
| 动态开始/停止 | `startRecord` / `stopRecord` API | 事件触发录像（告警前后 N 分钟） |

录制文件落在 `www/record/` 下（`[record] appName=record` 约束 app 名），每个切片完成触发一次 `on_record_mp4` Hook：

```go
// ZLMOnRecordMP4 录像切片完成：文件路径入库，供时间轴回放查询（见第 23 篇）
func (h *StreamHandler) ZLMOnRecordMP4(c *gin.Context) {
    var req struct {
        App      string `json:"app"`
        Stream   string `json:"stream"`
        FilePath string `json:"file_path"` // 相对 www 的路径
        StartTime int64  `json:"start_time"` // 秒级时间戳
        TimeLen  float64 `json:"time_len"`   // 时长（秒）
    }
    if err := c.ShouldBindJSON(&req); err != nil {
        c.JSON(http.StatusOK, gin.H{"code": -400})
        return
    }
    // 入录像索引表：设备ID + 起止时间 + 文件路径 + 时长
    if err := h.recordSvc.SaveSegment(c.Request.Context(), req.Stream, req.FilePath, req.StartTime, req.TimeLen); err != nil {
        log.Error().Str("file", req.FilePath).Err(err).Msg("录像索引入库失败")
    }
    c.JSON(http.StatusOK, gin.H{"code": 0})
}
```

### 7.2 截图与点播

```bash
# getSnap：FFmpeg 对一路流截一帧（封面、告警快照），带缓存过期
curl "http://localhost:8080/index/api/getSnap?url=rtsp://localhost/live/test&secret=xxx&timeout_sec=10&expire_sec=30"
```

MP4 点播无需额外组件：文件放进 `www/record/`，直接 `http://host:8080/record/xxx.mp4` 就是 HTTP 点播；加 `.live.flv` 后缀还能以 HTTP-FLV 直播形式流化播放（服务端解复用 MP4），支持从任意时间点拖动进流。

## 八、生产部署建议

### 8.1 Docker Compose（Go 后端 + ZLMediaKit）

```yaml
services:
  backend:
    build: .
    ports:
      - "8081:8081"

  zlmediakit:
    image: zlmediakit/zlmediakit:master
    ports:
      - "1935:1935"
      - "8080:80"
      - "8554:554"
      - "8000:8000/udp"
      - "10000:10000"
      - "10000:10000/udp"
    volumes:
      - ./zlm/config.ini:/opt/media/conf/config.ini
      - ./zlm/www:/opt/media/www          # 录像、截图落盘
    depends_on:
      - backend
    restart: unless-stopped
```

### 8.2 NAT / 公网部署的三个坑

1. **`[rtc] externIP` 必须填公网 IP**：容器/云主机内是内网地址，WebRTC 的 ICE candidate 会把内网 IP 报给浏览器，连接必失败。留空时自动取网卡 IP，在 NAT 后取到的是错的。
2. **WebRTC 端口映射内外必须一致**：`8000/udp` 映射成其他宿主机端口，ICE 对不上号；官方明确要求 NAT 映射端口与监听端口一致。
3. **GB28181 多端口模式要映射整段 `30000-35000/udp`**：设备直推 ZLMediaKit，端口对不上就收不到流；改用单端口模式（10000）可绕开。

### 8.3 性能要点

- 多线程 + epoll 事件驱动，按需转协议（lazy 生成 MediaSource），无观看者的协议不消耗 CPU
- 高并发场景先做三件事：`[protocol]` 收敛输出协议、开启按需拉流（无人观看即断）、确认没有意外开启转码
- 官方基准测试显示纯转发场景单机可承载数千至上万路播放（取决于码率与网卡），远超大多数业务需要；瓶颈通常先出现在磁盘（HLS 分片、MP4 录制）而不是转发本身

## 九、本篇小结

| 需求 | 实现方式 |
|------|---------|
| 理解一切 URL | 四元组：schema/vhost/app/stream |
| 推流/播放鉴权 | `[hook] on_publish` / `on_play` 回调 Go 后端 |
| 在线状态同步 | `on_stream_changed`（按单一 schema 去重） |
| 按需拉流 | `on_stream_not_found` → `addStreamProxy` 回源 |
| 无人观看断开 | `on_stream_none_reader` → `close_streams` |
| GB28181 接入 | wvp-GB28181-pro（SIP 信令）+ ZLMediaKit（RTP 媒体） |
| 国标收流端口 | 单端口模式（10000，SSRC 区分）/ 多端口模式（30000-35000） |
| 录像 | `enable_mp4` / `startRecord` + `on_record_mp4` 入库 |
| WebRTC 公网部署 | `externIP` 填公网 IP，8000 端口映射内外一致 |

一句话选型回顾：**MediaMTX 面向"配置即所得"的通用转发，ZLMediaKit 面向"业务深度介入流生命周期"的平台化场景**——Hook 全托管 + GB28181 原生媒体面，是安防平台选它的根本原因。

## 动手实践

### 练习1：Docker 拉起并全协议播放验证
```bash
# 启动（见 2.1 完整命令）
docker run -id --name zlmediakit -p 1935:1935 -p 8080:80 -p 8554:554 \
  -p 8000:8000/udp -p 10000:10000 -p 10000:10000/udp zlmediakit/zlmediakit:master

# 推流
ffmpeg -re -i test.mp4 -c copy -f flv rtmp://localhost:1935/live/test

# 依次验证
ffplay rtsp://localhost:8554/live/test                                    # RTSP
ffplay http://localhost:8080/live/test.live.flv                           # HTTP-FLV
ffplay http://localhost:8080/live/test/hls.m3u8                           # HLS
curl "http://localhost:8080/index/api/getMediaList?secret=035c73f7-bb6b-4889-a715-d9eb2d1925cc"  # API
# 浏览器打开 http://localhost:8080/webrtc/ 选 stream=test 播放             # WebRTC
```
**预期输出**：四种协议全部出画面；`getMediaList` 返回的 data 数组里能看到 rtsp/rtmp/hls 等多个 schema 条目——直观感受"一路流多个 MediaSource"。

### 练习2：on_publish 推流鉴权
```ini
# config.ini 的 [hook] 段
enable=1
on_publish=http://localhost:8081/api/v1/zlm/on_publish
```
先用 5.2 的 Go handler 启动后端，然后分别推流：
```bash
# 无 token：被拒绝，ffmpeg 立刻报 Connection refused / 推流中断
ffmpeg -re -i test.mp4 -c copy -f flv "rtmp://localhost:1935/live/test"

# 带 token：正常推流
ffmpeg -re -i test.mp4 -c copy -f flv "rtmp://localhost:1935/live/test?token=valid-token"
```
**预期输出**：无 token 推流被 ZLMediaKit 立即断开（容器日志可见 on_publish 返回非 0）；带 token 推流成功。把 `enable` 改回 0 对比：鉴权完全失效。

### 练习3：按需拉流全链路
启动后端（实现 5.4 的两个 handler），在业务库登记一路摄像头（没有真摄像头可用另一个 MediaMTX/ZLM 实例的流代替），然后**直接播放这路从未推过的流**：
```bash
# 不推流，直接请求播放
ffplay http://localhost:8080/live/cam001/hls.m3u8
```
**预期输出**：ZLMediaKit 日志出现 `on_stream_not_found` 回调 → 后端调 `addStreamProxy` 回源 → `on_stream_changed` 注册 → 播放器出画面。关闭 ffplay 等待 `on_stream_none_reader` 触发后，`getMediaList` 里这路流消失——完整的按需生命周期。

## 常见问题排查

| 现象 | 可能原因 | 解决方法 |
|------|---------|---------|
| WebRTC 播放连不上/黑屏 | NAT 后 `externIP` 未配置或端口映射不一致 | `[rtc] externIP` 填公网 IP；8000/udp 映射内外端口保持一致 |
| API 调用返回 403 或无权限 | 未带 secret 或 secret 不对 | 请求带 `secret` 参数；127.0.0.1 访问可免密 |
| Hook 完全不触发 | `[hook] enable` 默认为 0 | 配置 `enable=1` 并重启 |
| on_stream_changed 重复触发 | 一路流按协议多次回调 | 后端按单一 schema（如 rtmp）过滤去重 |
| 推流秒断 | on_publish 返回 code != 0 | 检查后端返回体是 HTTP 200 + `{"code":0}` |
| on_stream_not_found 死循环 | 后端拉流失败仍返回非 0，触发 ZLM 重试 | 拉不成也返回 `{"code":0}`，拉流失败自行告警 |
| addStreamProxy 拉不到流 | 源 URL 错误或 UDP 丢包 | `rtp_type=1` 强制 TCP；用 ffplay 先验证源 URL 可用 |
| GB28181 收不到流 | 多端口模式端口段未映射 | 映射 30000-35000/udp，或改用单端口模式（10000） |
| 录像文件找不到 | 未挂载 www 目录 | 挂载 `./zlm/www:/opt/media/www`，文件在 `www/record/` 下 |
| getMediaList 里流一直在 | 拉流代理无人看未断开 | 检查 `on_stream_none_reader` 是否配置、`auto_close` 是否误设 |
