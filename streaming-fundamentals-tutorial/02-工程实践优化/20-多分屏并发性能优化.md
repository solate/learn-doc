# 多分屏并发性能优化（16/32/64 路+）

> **适合读者**：安防/工业场景下需要同时渲染多路视频的全栈开发者
> **核心问题**：我有 N 路摄像头，怎么在网页上同时看？16 路怎么跑起来？64 路、100 路为什么不卡？
> **前置阅读**：第 16 篇（MediaMTX 实战）、第 21 篇（低延迟播放完整方案）。本篇聚焦"多路并发"这个维度，单路播放、播放器内核细节不重复展开。

---

## 一、先把需求定义清楚

收到"多分屏"需求时，先问三个问题，答案直接决定技术选型：

| 问题 | 决定什么 |
|------|---------|
| 同时要看几路？ | 整条链路的规模档位（本文核心，见第七节决策表） |
| 能接受多少延迟？ | 协议选择（HLS / WS-FLV / WebRTC） |
| 预览还是看清细节？ | 分辨率与码率策略（子码流 vs 主码流） |

本文的主线场景取一个典型答案：**16 路摄像头、4×4 分屏、延迟 3 秒内、预览看概况、双击某一路放大后要看清细节**。

多分屏要同时解决三件事：

1. **跑得起来**：端到端链路打通——摄像头 → 流媒体服务器 → 浏览器网格（第二节）
2. **扛得住**：路数上去后服务端 CPU、带宽、浏览器都不爆（第三~六节）
3. **看得清**：预览小画面省资源，放大后切主码流（贯穿全文）

完整链路只有三跳，但每一跳在"×16、×64"之后都会出问题：

```
摄像头 RTSP  →  [流媒体服务器]  →  [浏览器]
 (主/子码流)    拉流/转封装/转码     网格渲染 + 解码
```

## 二、最小可用方案：16 路监控从零到能看

> 本节回答"我现在有 16 路要监控，怎么做"。全部代码可直接复制运行。跑通本节，"会做多分屏"就成立了；后面所有章节都是把这件事放大到 64 路、100 路时怎么不崩。

### 2.1 协议选型

| 协议 | 延迟 | 多路并发友好度 | 监控分屏结论 |
|------|------|--------------|------------|
| HLS | 6-15s | 好（纯 HTTP，CDN 友好） | ✗ 延迟不可接受，仅做兼容兜底 |
| HTTP-FLV / WS-FLV | 1-3s | 好（一路一条连接） | ✓ **本篇基线方案** |
| WebRTC | <500ms | 中（每路一个连接/PC） | 高端需求，详见第 21 篇 |

监控分屏首选 **WS-FLV**：延迟够低、前端用 mpegts.js 成熟稳定、服务端 ZLMediaKit/SRS 原生支持。

### 2.2 后端：把 16 路子码流接进来

**第一步：确认每路摄像头的子码流地址。** 摄像头通常提供两条码流：

```
主码流(Main Stream)：1080p/4MP，码率 2-8Mbps，详情查看用
子码流(Sub Stream)：360p/D1，码率 256-512kbps，分屏浏览用
```

| 品牌 | 主码流 | 子码流 |
|------|--------|--------|
| 海康 | `rtsp://ip:554/Streaming/Channels/101` | `rtsp://ip:554/Streaming/Channels/102` |
| 大华 | `rtsp://ip:554/cam/realmonitor?channel=1&subtype=0` | `subtype=1` |

**第二步：注册到流媒体服务器（以 ZLMediaKit 为例）。** 用拉流代理把摄像头子码流接进来，服务器负责转封装成 WS-FLV 输出：

```bash
# 注册一路（16 路就是循环 16 次，由 Go 后端调 API 完成）
curl "http://localhost:8080/index/api/addStreamProxy?secret=你的secret\
&vhost=__defaultVhost__&app=live&stream=cam-01\
&url=rtsp://admin:pass@192.168.1.101/Streaming/Channels/102\
&auto_close=1"

# auto_close=1：无人观看时自动断开对摄像头的拉流，不浪费摄像头连接
# 播放地址（WS-FLV）：ws://localhost:8080/live/cam-01.live_flv
```

**MediaMTX 用户**的等价配置（完整说明见第 16 篇）：

```yaml
# mediamtx.yml
paths:
  cam-01:
    source: rtsp://admin:pass@192.168.1.101/Streaming/Channels/102
    sourceOnDemand: true   # 有人看才拉流，无人 15s 后自动断开
  cam-02:
    source: rtsp://admin:pass@192.168.1.102/Streaming/Channels/102
    sourceOnDemand: true
  # ... 16 路逐个配置
```

注意 MediaMTX 不输出 FLV，浏览器侧要走它的 WebRTC（`http://localhost:8889/cam-01`）或 HLS 输出，前端把 mpegts.js 换成对应的拉流方式即可，网格布局代码不变。

**第三步：Go 后端提供摄像头列表 API**，返回 `[{id, name, playUrl}]`，前端据此渲染网格。摄像头管理系统的完整设计（增删改、鉴权、动态注册）在第 16 篇 5.1 节，此处不重复。

**没有真摄像头？** 用 FFmpeg 模拟 16 路（`testsrc2` 会画时间码，方便肉眼测延迟）：

```bash
# 16 路模拟摄像头：360p、10fps、GOP 1s、300kbps —— 参数故意贴合子码流规格
for i in $(seq -w 1 16); do
  ffmpeg -re -f lavfi -i "testsrc2=size=640x360:rate=10" \
    -c:v libx264 -g 25 -b:v 300k \
    -f rtsp rtsp://localhost:554/live/cam-$i &
done
```

### 2.3 前端：4×4 网格 + 16 个播放器

```html
<!-- index.html -->
<div id="grid"></div>

<style>
  #grid {
    display: grid;
    grid-template-columns: repeat(4, 1fr);   /* 4×4 分屏 */
    gap: 2px;
    width: 100vw;
    height: 100vh;
    background: #000;
  }
  .video-cell {
    position: relative;
    background: #111;
    min-width: 0;            /* 关键：防止单格内容把网格撑爆 */
  }
  .video-cell video {
    width: 100%;
    height: 100%;
    object-fit: contain;     /* 保持宽高比，不拉伸 */
  }
  .video-cell .name {
    position: absolute;
    left: 4px;
    top: 4px;
    font-size: 12px;
    color: #fff;
    text-shadow: 0 0 2px #000;
  }
</style>
```

```javascript
// main.js —— 16 路全部播放
const cameras = Array.from({ length: 16 }, (_, i) => ({
  id: `cam-${String(i + 1).padStart(2, '0')}`,
  name: `摄像头 ${i + 1}`,
}));

const grid = document.getElementById('grid');
const players = new Map();   // id -> mpegts.Player，统一管理生命周期

function createCellAndPlay(cam) {
  const cell = document.createElement('div');
  cell.className = 'video-cell';
  cell.innerHTML = `
    <video muted autoplay playsinline></video>
    <span class="name">${cam.name}</span>`;
  grid.appendChild(cell);

  // 监控必须 muted：浏览器自动播放策略只允许静音视频自动播放
  const player = mpegts.createPlayer({
    type: 'flv',
    url: `ws://localhost:8080/live/${cam.id}.live_flv`,
    isLive: true,
  }, {
    enableWorker: true,             // 解封装移到 Worker，减轻主线程
    enableStashBuffer: false,       // 直播关闭预读缓冲，降延迟
    stashInitialSize: 128,          // 初始缓冲 128KB（注意单位是 KB，写 128*1024 等于 128MB！）
    liveBufferLatencyChasing: true, // 追帧：缓冲落后超过阈值自动跳到最新
  });
  player.attachMediaElement(cell.querySelector('video'));
  player.load();
  player.play();
  players.set(cam.id, player);
}

cameras.forEach(createCellAndPlay);
```

16 个格子、每格一个独立的 `<video>` + mpegts.js 实例——这就是多分屏的全部本体。没有魔法，一个网格容器 + N 个播放器实例而已，**难的全在 N 变大之后**。

### 2.4 布局切换（1/4/9/16 宫格）

分屏产品的基本交互：工具栏切换宫格数，双击某格全屏。核心是**先销毁再重建**：

```javascript
const LAYOUTS = {
  1:  { cols: 1, count: 1  },
  4:  { cols: 2, count: 4  },
  9:  { cols: 3, count: 9  },
  16: { cols: 4, count: 16 },
};

function switchLayout(n, cameraList) {
  // 关键：先销毁全部旧 player 再重建。
  // 不 destroy 直接换 DOM = WebSocket 连接和 MSE 缓冲全部泄漏，切几次布局页面就卡死。
  players.forEach((p) => p.destroy());
  players.clear();
  grid.innerHTML = '';
  grid.style.gridTemplateColumns = `repeat(${LAYOUTS[n].cols}, 1fr)`;

  cameraList.slice(0, LAYOUTS[n].count).forEach(createCellAndPlay);
}
```

生产级的布局管理（非宫格布局、双击放大、断线重连、按需激活）在第 21.5 篇（MultiStreamManager）和第 21.6 篇（jessibuca 版 4/9/16 切换）有完整实现，思路一致。

### 2.5 跑通之后，问题才刚开始

16 路跑通只是"能用"。接下来把三个数字调大——路数 16→64、观看者 1→100、终端从工作站换成办公 PC——会依次触发三类故障：

1. **服务器 CPU 满**：你在为每一格的格式转换付费（第四节解决）
2. **同一路摄像头被重复拉 N 次**：连接数爆炸，摄像头扛不住（第五节解决）
3. **浏览器先卡后崩**：它根本解码不动这么多路（第三、六节解决）

## 三、瓶颈定位：64 路为什么卡

### 3.1 四个环节的压力分布

```
摄像头 RTSP  →  [拉流层]  →  [转码层]  →  [分发层]  →  [浏览器渲染层]
                  CPU/带宽     CPU/GPU       CDN/内存       GPU/JS线程
```

| 环节 | 64路瓶颈 | 典型症状 |
|------|---------|---------|
| 拉流层 | 每路独立 RTSP 连接，64 路 = 64 个连接；N 个观看者 × N 倍 | 连接数超限，摄像头掉线 |
| 转码层 | H.264→H.264 软编，64 路 × CPU | CPU 100%，转码队列堆积 |
| 分发层 | 服务器→浏览器带宽，64 路 × 1Mbps = 64Mbps | 出口带宽打满 |
| 渲染层 | 浏览器同时解码 64 个 `<video>` | 页面卡死、帧率下降、内存暴涨 |

### 3.2 渲染层根因：浏览器解码的隐形上限

很多人在服务端做足了优化，最后死在浏览器上。先理解一个 `<video>` 标签的真实成本——它不是一个"窗口"，而是一条完整管线：

```
WebSocket 拉流 → JS 解封装(mpegts.js) → MediaSource 缓冲 → 解码(硬/软) → 合成上屏
```

每一路都要付出四项开销：

- **解码算力**：一路 720p30 H.264 软解约占满一颗中档 CPU 核心；4 路 1080p 软解就能报废一颗 4 核 CPU。16 路软解在浏览器里根本不可行。
- **硬解配额**：浏览器的硬件解码器实例有限（Chrome 经验值大约 8~16 路同时硬解，取决于 GPU、驱动、平台），超出的路会**静默回退软解**——这是"前 8 路流畅、第 9 路开始整体变卡"的元凶，没有任何报错。
- **内存**：每路 MSE 缓冲 + 解码器上下文约 20~50MB。64 路 = 1.5~3GB，直接把标签页推下悬崖。
- **DOM/合成**：64 个 video 元素的合成与重排，主线程掉帧，UI 点不动。

对比专用设备：监控 NVR、电视盒子用专用解码 ASIC 芯片，64 路 D1 解码占用不到 15% CPU。浏览器是通用平台，拼专用芯片的解码密度必输。所以浏览器侧的思路只有三条：**少解码**（按需激活）、**解小一点**（服务端降规格）、**换更省的解码路径**（WebCodecs）。

H.265 的额外提醒：Chrome 的 MSE 对 H.265 支持看平台（依赖硬解 + 系统支持），监控大量 H.265 摄像头时要么服务端统一转 H.264，要么前端走 WASM 软解（jessibuca）——解码路径与降级策略详见第 21.5 篇，此处不展开。

## 四、服务端降载：性价比最高的三个杠杆

按投入产出比排序：前三个杠杆（子码流、降帧率、缩 GOP）**优先在摄像头端配置，零服务器成本**；只有摄像头不支持时才落到服务端转码。

### 4.1 杠杆一：子码流，带宽直降 90%

```
主码流 1080p × 64 路 = 192Mbps
子码流 360p × 64 路 ≈ 19.2Mbps（64 × 300kbps）
```

分屏预览用子码流，双击放大再切主码流。这是多分屏的第一原则，其余一切优化都建立在它之上。

### 4.2 杠杆二：降帧率，预览 5fps 足够

监控预览的目的是"看见有没有人/车"，人眼不需要 30fps。帧率降到 1/6，解码与带宽近似线性下降：

- **优先在摄像头端配**（零成本）：海康/大华的子码流都可以直接设成 360p@10fps 或 720p@5fps（Web 管理页 → 视频/编码 → 子码流参数）。
- **服务端转码时顺路降**（有成本）：

```bash
ffmpeg -i rtsp://camera/sub-stream \
  -vf fps=5 \
  -c:v h264_nvenc -b:v 300k \
  -f hls output.m3u8
```

注意：`-c copy` 透传改不了帧率——帧率是编码参数，改它必须重编码。所以顺序是：**先在摄像头上配好子码流规格，尽量保住 `-c copy`**。

### 4.3 杠杆三：缩短 GOP，首帧秒开

GOP（两个 I 帧的间隔）决定两件事：

1. **首帧时间**：播放器中途加入流，必须等到下一个 I 帧才能开始解码。GOP 4s → 平均等 2s，用户感知就是"点了要愣一下才出画面"。
2. **切片下限**：`-c copy` 时 HLS 只能在关键帧处切片，GOP 长度是 `hls_time` 的实际下限。

摄像头默认子码流 GOP 通常 2~4s（25fps × 50~100 帧）。分屏场景建议：

- **摄像头端**：把 I 帧间隔改成 1s（25 帧）→ 首帧 < 0.5s。
- **服务端转码时**：`-g 25 -force_key_frames "expr:gte(t,n_forced*1)"`。

成本：I 帧比 P 帧大，码率涨 10~20%——用子码流省下来的预算足够覆盖。

### 4.4 零转码透传：能不转就不转

摄像头输出的已经是 H.264 时，只需换容器，不重新编码：

```
RTSP(H.264) → 直接封装 → HLS(H.264 TS) / FLV → 浏览器
                   ↑
                零转码，CPU 几乎不消耗
```

```bash
# 只换容器，不重新编码（-c copy 是关键）
ffmpeg -i rtsp://camera/stream \
  -c copy \
  -f hls \
  -hls_time 2 \
  -hls_list_size 5 \
  output.m3u8
```

**适用场景**：RTSP 已经是 H.264，浏览器可以直接播放（90%+ 情况）。`-c copy` 是多分屏性能的最大杠杆，见第九节基准。

### 4.5 必须转码时用硬件加速

H.265 摄像头、需要降帧率/降分辨率、需要加水印——这些场景必须重编码，上 GPU：

```bash
# NVIDIA GPU 转码
ffmpeg -hwaccel cuda -hwaccel_output_format cuda \
  -i rtsp://camera/stream \
  -c:v h264_nvenc -preset p4 -b:v 800k \
  -c:a aac -b:a 64k \
  -f hls output.m3u8

# Intel QSV（服务器常见）
ffmpeg -hwaccel qsv -i rtsp://camera/stream \
  -c:v h264_qsv -b:v 800k \
  -f hls output.m3u8
```

**GPU 并发能力参考**：

| GPU | 最大并发 H.264 解码 | 最大并发 H.264 编码 |
|-----|-------------------|-------------------|
| RTX 3080 | 64+ 路 1080p | 受驱动会话数限制（GeForce 新驱动限 8 路 NVENC 会话，可用社区补丁解锁） |
| T4（云服务器）| 128 路 720p | 64 路 720p |
| A10 | 200+ 路 1080p | 100+ 路 1080p |

解码不受会话数限制（拼吞吐量）；编码在 GeForce 卡上有并发会话数上限，数据中心卡（T4/A10）没有——选卡时注意这个坑。

### 4.6 Go 调度多路转码任务

必须转码的路数多时，用一个工作池控制并发，别让 64 个 ffmpeg 进程同时把 GPU/CPU 打爆：

```go
type TranscodeJob struct {
    ID        string
    InputURL  string
    OutputDir string
}

type TranscodePool struct {
    jobs    chan TranscodeJob
    workers int
}

func NewTranscodePool(workers int) *TranscodePool {
    p := &TranscodePool{
        jobs:    make(chan TranscodeJob, 100),
        workers: workers,
    }
    for i := 0; i < workers; i++ {
        go p.worker()
    }
    return p
}

func (p *TranscodePool) worker() {
    for job := range p.jobs {
        cmd := exec.Command("ffmpeg",
            "-hwaccel", "cuda",
            "-i", job.InputURL,
            "-c:v", "h264_nvenc", "-preset", "p4",
            "-f", "hls", "-hls_time", "2",
            filepath.Join(job.OutputDir, "stream.m3u8"),
        )
        if err := cmd.Run(); err != nil {
            log.Error().Err(err).Str("id", job.ID).Msg("转码任务失败")
        }
    }
}

func (p *TranscodePool) Submit(job TranscodeJob) {
    p.jobs <- job
}
```

worker 数量 = GPU 能扛的并发编码路数（按上表估），队列兜住峰值。

## 五、连接与分发层优化

### 5.1 连接复用：StreamHub

默认情况下，N 个观看者 × M 路视频 = N×M 条到源端的拉流连接。连接复用的原则是：**每一路流只从源拉一次，扇出给所有订阅者**。

先说结论：这一层通常直接由流媒体服务器承担（MediaMTX 的 `sourceOnDemand`、ZLMediaKit 的拉流代理都是这个语义），**优先用现成的**。只有在自研拉流分发（如 gortsplib 直接拉流 + 自己管理分发）时才需要写下面这个 StreamHub——完整可运行版本：

```go
// StreamHub：每路流一个会话，引用计数归零才断开对源端的拉流
type StreamHub struct {
    mu      sync.Mutex
    streams map[string]*StreamSession
}

type StreamSession struct {
    cancel   context.CancelFunc
    refCount int                      // 订阅者数量（统一在 hub.mu 下访问，避免竞态）
    mu       sync.RWMutex
    subs     map[chan []byte]struct{} // 每个订阅者一个独立 channel
}

func (h *StreamHub) Subscribe(streamID string) (<-chan []byte, func()) {
    h.mu.Lock()
    defer h.mu.Unlock()

    sess, ok := h.streams[streamID]
    if !ok {
        ctx, cancel := context.WithCancel(context.Background())
        sess = &StreamSession{
            cancel: cancel,
            subs:   make(map[chan []byte]struct{}),
        }
        h.streams[streamID] = sess
        go h.pullStream(ctx, streamID, sess) // 每路流唯一一个拉流 goroutine
    }
    sess.refCount++

    ch := make(chan []byte, 64) // 约 2 秒缓冲

    sess.mu.Lock()
    sess.subs[ch] = struct{}{}
    sess.mu.Unlock()

    unsubscribe := func() {
        h.mu.Lock()
        defer h.mu.Unlock()
        sess.mu.Lock()
        delete(sess.subs, ch)
        sess.mu.Unlock()
        sess.refCount--
        if sess.refCount == 0 {
            sess.cancel() // 最后一个订阅者离开，断开拉流
            delete(h.streams, streamID)
        }
    }
    return ch, unsubscribe
}

// pullStream：从源端读数据，扇出给所有订阅者
func (h *StreamHub) pullStream(ctx context.Context, streamID string, sess *StreamSession) {
    // 实际生产中这里从 RTSP/流媒体服务器读数据（FFmpeg pipe、gortsplib 等）
    for {
        select {
        case <-ctx.Done():
            return
        default:
        }
        data := readChunk(streamID) // 伪代码：读一段流数据
        if len(data) == 0 {
            return
        }
        sess.mu.RLock()
        for ch := range sess.subs {
            select {
            case ch <- data:
            default: // 慢消费者：丢帧而不是阻塞广播（监控宁丢不堵）
            }
        }
        sess.mu.RUnlock()
    }
}
```

三个设计要点（也是自写扇出最容易错的地方）：

1. **引用计数在 `hub.mu` 下读写**：订阅/退订与"归零断流"必须互斥，否则会出现"新订阅者刚拿到会话，旧订阅者把流断了"的竞态。
2. **慢消费者丢帧**：广播用 `select + default` 非阻塞投递，一个卡顿的浏览器绝不能拖慢其他所有观看者。
3. **会话由 hub 统一生命周期**：pullStream 退出（源断开）时会话从 map 移除，下一个订阅者触发重连。

**效果**：同一摄像头无论多少观看者，只维持 1 条源端连接；无人观看自动断开。

### 5.2 分发层：HLS 缓存

HLS 是纯 HTTP 文件，给 Nginx 加缓存让多个观看者共享同一份切片，源端只出一份流量：

```nginx
server {
    location /hls/ {
        types {
            application/vnd.apple.mpegurl m3u8;
            video/mp2t ts;
        }
        root /var/www;

        # TS 切片缓存 10 秒（与 hls_time 相等）
        add_header Cache-Control "public, max-age=10";

        # M3U8 不缓存（实时更新）
        location ~* \.m3u8$ {
            add_header Cache-Control "no-cache";
        }
    }
}
```

观看人数多、路数多时，出口带宽是"路数 × 单路码率 × 观看人数"——100 个安保同时看 16 路 = 服务端出口 480Mbps，这时要上 CDN/多级转发，见第 22 篇。

### 5.3 分发层：WebSocket 推送 + 前端 MSE 播放

HLS 延迟 6-20s，分屏监控通常要 < 3s，基线方案用 WS-FLV：

```
后端: RTSP → 转封装 → FLV over WebSocket
前端: mpegts.js 消费 WS 流
延迟: 1-3 秒
```

```go
// Go WebSocket 推流：每个观看者一路一个订阅，断开自动退订
http.HandleFunc("/ws/stream", func(w http.ResponseWriter, r *http.Request) {
    conn, _ := upgrader.Upgrade(w, r, nil)
    defer conn.Close()

    streamID := r.URL.Query().Get("id")
    ch, unsubscribe := hub.Subscribe(streamID)
    defer unsubscribe()

    for data := range ch {
        if err := conn.WriteMessage(websocket.BinaryMessage, data); err != nil {
            return // 客户端断开，退出循环触发 unsubscribe
        }

})
```

## 六、突破浏览器上限：客户端四级方案

服务端把流降到 360p@5fps 之后，浏览器的解码压力已大幅下降。但路数到了 32/64/100，`<video>` 路线本身的天花板（3.2 节）还在，按投入从低到高上这四级方案。

### 6.1 方案一：WebCodecs + Canvas 渲染

`<video>` + MSE 的问题在于整条管线是黑盒：解码调度、缓冲策略、帧数据都控制不了。WebCodecs 把解码器直接暴露给 JS：

```
<video> 路线：  WS → mpegts.js 解封装 → MediaSource → 浏览器解码 → <video>
WebCodecs 路线：WS → 解封装 → VideoDecoder(可编程) → VideoFrame → <canvas>
```

与 `<video>` 路线相比：

- 解码器实例自己创建/销毁，`decodeQueueSize` 可观测——多路时能做**显式调度**，而不是被动等浏览器静默降级
- 没有 MSE SourceBuffer 的双份缓冲，内存省一半以上
- 拿到 `VideoFrame` 可以直接缩放、叠加（AI 画框、电子放大、多路拼一画布）
- 诚实地说：**同样受 GPU 硬解配额限制**。WebCodecs 不是"无限解码"，而是"同样的配额、更省的用法、可控的降级"

单路核心代码：

```javascript
class WebCodecsCell {
  constructor(canvas, codec = 'avc1.640028') {
    this.canvas = canvas;
    this.ctx = canvas.getContext('2d');
    this.codec = codec;   // 从流的 sequence header 解出，或摄像头规格表查到
    this.decoder = null;
    this.source = null;
    this.lastUrl = null;
  }

  start(streamUrl) {
    this.stop();
    this.lastUrl = streamUrl;

    // 解码器：出帧直接画，出错走重连
    this.decoder = new VideoDecoder({
      output: (frame) => this.draw(frame),
      error: (e) => this.reconnect(e),
    });
    this.decoder.configure({
      codec: this.codec,
      optimizeForLatency: true,   // 延迟优先：不等重排，尽快出帧
    });

    // 拉流 + 解封装。教学协议：1 字节帧类型 + 8 字节时间戳 + H.264 裸流
    // （生产上用 FLV/TS + 成熟 demuxer，见本节末尾提示）
    this.source = new WebSocket(streamUrl);
    this.source.binaryType = 'arraybuffer';
    this.source.onmessage = (ev) => {
      if (this.decoder.state !== 'configured') return;
      const view = new DataView(ev.data);
      const isKey = view.getUint8(0) === 1;
      const ts = Number(view.getBigUint64(1));   // 微秒
      this.decoder.decode(new EncodedVideoChunk({
        type: isKey ? 'key' : 'delta',
        timestamp: ts,
        data: new Uint8Array(ev.data, 9),
      }));
      // 队列持续上涨 = 解码跟不上码率，生产实现应在此丢帧到下个关键帧
    };
  }

  draw(frame) {
    this.ctx.drawImage(frame, 0, 0, this.canvas.width, this.canvas.height);
    frame.close();   // 不 close 的 VideoFrame 会占住 GPU 内存，多路几分钟就崩
  }

  reconnect(err) {
    console.error('解码错误，重建链路', err);
    setTimeout(() => this.start(this.lastUrl), 1000);
  }

  stop() {
    if (this.source) this.source.close();
    if (this.decoder && this.decoder.state !== 'closed') this.decoder.close();
  }
}
```

多路分屏管理器——和第二节的 mpegts.js 版结构完全一致，只是"player"换成了 WebCodecsCell：

```javascript
const cells = new Map();   // camId -> WebCodecsCell

function switchLayout(n, cameras) {
  cells.forEach((c) => c.stop());   // decoder.close() 立刻释放硬解实例
  cells.clear();
  grid.innerHTML = '';
  grid.style.gridTemplateColumns = `repeat(${Math.ceil(Math.sqrt(n))}, 1fr)`;

  cameras.slice(0, n).forEach((cam) => {
    const cell = document.createElement('div');
    cell.className = 'video-cell';
    const canvas = document.createElement('canvas');
    cell.appendChild(canvas);
    grid.appendChild(cell);

    const wc = new WebCodecsCell(canvas, cam.codec);
    wc.start(cam.streamUrl);
    cells.set(cam.id, wc);
  });
}

// 16 / 32 / 64 路切换就是换个 n —— 这正是本篇动手实践练习 2
```

H.264 的 codec 字符串（如 `avc1.640028`）从流的 AVCDecoderConfigurationRecord 前 4 字节解出（profile、constraints、level 各 1 字节拼十六进制），或在转码时固定。

**生产提示**：解封装（FLV/TS → 帧裸流）是体力活，自写用于学习；生产直接用带 WebCodecs 输出的播放器（jessibuca 系列的 webcodec 模式、EasyPlayer 等），或复用 mpegts.js 的 demux 层。与 jessibuca 的完整对比在第 21.6 篇。

### 6.2 方案二：解码与渲染搬进 Worker（OffscreenCanvas）

WebCodecs 路线再进一步：整条管线（WebSocket → 解封装 → VideoDecoder → OffscreenCanvas）全部能在 Web Worker 里跑，主线程只留 UI：

```
主线程                          Worker
─────                          ──────
<div> 容器        ──控制权──▶   OffscreenCanvas（canvas.transferControlToOffscreen）
布局切换 / 工具栏               WebSocket 拉流
                               VideoDecoder 解码
                               drawImage 上屏
```

- `VideoDecoder`、`WebSocket`、`OffscreenCanvas` 在 Worker 中全部可用
- 100 路解码也不掉 UI 交互——卡的是 Worker，滚动和按钮始终流畅
- 多个 Worker 分摊解码时，帧数据跨线程传递可用 `SharedArrayBuffer` 零拷贝共享

`SharedArrayBuffer` 要求页面处于**跨域隔离**状态，Nginx 加两个响应头：

```nginx
add_header Cross-Origin-Opener-Policy same-origin;
add_header Cross-Origin-Embedder-Policy require-corp;
```

代价：页面上所有跨域资源（CDN 的 JS/CSS/图片）都必须带 CORP 头，否则直接加载失败——这是很多团队上了 SharedArrayBuffer 后整页白屏的原因。先用普通 `postMessage` 传 `ArrayBuffer`（拷贝一份，每帧几 MB 的开销通常可接受）往往就够了。

### 6.3 方案三：按需激活 + 静态缩略图（100 路也稳）

前两个方案优化"同时解码的路数"，这个方案直接减少"需要解码的路数"，是性价比之王：

**组合拳**：

- 屏幕内的格子：真实拉流播放（**活跃**）
- 屏幕外/列表页/非焦点：静态截图，每隔几秒刷新（**非活跃**）
- 双击放大：该路切主码流重连看细节，其余路降为缩略图

实测结构：**100 路监控 = 屏内 16 路活跃 + 84 路缩略图**，浏览器始终只解码 16 路。

**缩略图来源**——服务端对已在拉流的子码流定时抽帧（不新增摄像头连接）：

```bash
# 每 5 秒覆盖写同一张 jpg；-update 1 是"持续输出单帧"的关键参数
ffmpeg -i rtsp://camera/sub-stream \
  -vf fps=1/5 -update 1 -q:v 5 \
  /www/thumbs/cam-01.jpg
```

前端 `<img>` 定时刷新该 URL 即可（配合 ETag/304 省带宽）。

**前端激活逻辑**（IntersectionObserver，滚动容器内同样适用）：

```javascript
const observer = new IntersectionObserver((entries) => {
  entries.forEach(({ target, isIntersecting }) => {
    const cam = target.dataset.camId;
    const cell = cellMap.get(cam);
    if (!cell) return;
    if (isIntersecting) {
      cell.activate();    // 建连接、启动解码
    } else {
      cell.deactivate();  // 断开连接，格子换成 <img> 缩略图
    }
  });
}, { threshold: 0.1 });

document.querySelectorAll('.video-cell').forEach((cell) => observer.observe(cell));
```

**翻页分屏**是同一思想的最低成本版本：默认 4×4 = 16 路 + 翻页按钮，就敢说"支持 64 路"——64 路在服务端都是活的，浏览器按页消费。低端 PC 场景（6×6 = 36 路已经卡）直接靠它解决。

### 6.4 方案四：WebRTC 多路复用（连接开销的极限优化）

WS-FLV 每路一条 WebSocket，64 路 = 64 条连接 + 64 套 TLS 握手。WebRTC 可以把多路视频装进**一个** PeerConnection（unified-plan 多 track），共用一套 ICE/DTLS/SRTP 传输：

- 浏览器侧：一个 `RTCPeerConnection`，`addTransceiver` × N（recvonly）
- 服务端侧：需要 SFU 能力，按观看者的订阅情况选择性转发 track

这是视频会议的标准架构（第 29 篇详解），大型监控指挥墙会用到。代价是服务端复杂度上一个量级，16~64 路常规监控用不到——记住有这个选项即可。

另有"DataChannel 传流"的野路子（把视频当私有二进制协议走 DataChannel），失去了 RTP 的重传与拥塞控制能力，不推荐。

## 七、按规模选方案：决策表与带宽账

### 7.1 决策表

| 并发规模 | 推荐方案 | 关键配置 |
|---------|---------|---------|
| ≤16 路 | `<video>` + mpegts.js / jessibuca（第二节基线） | 子码流 + `-c copy` + GOP 1s |
| 16~64 路 | 基线 + 按需激活 + 翻页；流畅度要求高再上 WebCodecs | 降帧率 5~10fps + 缩略图 |
| 64~100+ 路 | 缩略图墙为主（点开才拉流），WebCodecs + Worker 渲染为辅 | 服务端抽帧 + 限额活跃路数 |
| 专用监控中心 | 本地客户端（Electron/Qt）或专业解码卡 | NVR/ASIC 硬解 64+ 路 |

### 7.2 带宽账（服务端 → 单个观看浏览器）

| 场景 | 单路码率 | 总带宽 | 结论 |
|------|---------|--------|------|
| 16 路主码流 1080p H.265 | 3Mbps | 48Mbps | 内网千兆勉强，办公 WiFi 放弃 |
| 16 路子码流 360p | 300kbps | 4.8Mbps | ✓ 任何网络都能跑 |
| 64 路子码流 360p | 300kbps | 19.2Mbps | 有线网可接受 |
| 64 路 D1 @ 5fps | 300kbps | ≈19Mbps | ✓ 极限但可行 |
| 100 路缩略图墙（16 活跃 + 84 静图） | — | < 6Mbps | ✓ 唯一现实的百路方案 |

再乘上观看人数：出口带宽 = 路数 × 单路码率 × 观看人数。人多了上 CDN/多级转发（第 22 篇）。

```
64路摄像头（子码流 360p / 5-10fps / GOP 1s —— 摄像头端配置好）

    └─ 双击放大切主码流，缩小切回子码流
```

## 九、性能基准参考

| 方案 | 8核CPU | 最大并发路数 | 延迟 |
|------|--------|------------|------|
| RTSP→HLS 软件转码 | 100% CPU | ~16路 720p | 6-15s |
| RTSP→HLS 仅封装(-c copy) | <5% CPU | **128路+** | 6-15s |
| RTSP→WebSocket FLV 软件 | 40% CPU | ~32路 720p | 1-3s |
| RTSP→WebSocket FLV GPU | <10% CPU | **64路+ 1080p** | 1-3s |

**关键结论**：`-c copy` 零转码是多分屏服务端性能的最大杠杆，能提升 8 倍并发数；而浏览器侧的"按需激活"是总杠杆——**不解码的路数才是真的省了**。

## 本篇小结

多分屏的完整方法论，按优先级：

1. **先跑起来**：子码流 + WS-FLV + CSS Grid 网格（第二节），16 路一天落地
2. **服务端三杠杆**：子码流、降帧率、缩 GOP——全部优先在摄像头端配置，零成本
3. **零转码透传**（`-c copy`）：CPU 从转码地狱到接近 0
4. **连接复用**：每路流一条源连接，无人观看自动断开（优先用流媒体服务器现成能力）
5. **按需激活**：屏内播放、屏外缩略图，浏览器侧性价比之王
6. **WebCodecs**：需要 32/64 路同屏流畅时的上限突破，同样受硬解配额限制但可控可调度
7. **按规模选方案**：不要硬扛——翻页和缩略图墙不丢人，卡死的监控墙才丢人

## 常见问题排查

| 现象 | 可能原因 | 解决方法 |
|------|---------|---------|
| 16 路分屏后浏览器内存暴增 | 每路独立缓冲区未限制大小 | `stashInitialSize: 128`（单位 KB），`enableStashBuffer: false` |
| 切换分屏布局后部分路黑屏 | player 实例未正确 destroy 再重建 | 切换前调用 `player.destroy()`，再创建新实例 |
| 前 8 路流畅，第 9 路开始整体变卡 | 浏览器硬解配额用尽，静默回退软解 | 服务端降分辨率/帧率；按需激活减少活跃路数；上 WebCodecs 显式调度 |
| WebCodecs 页面运行几分钟渐渐卡死 | `VideoFrame` 未 close / 解码器未 close | 每次 draw 后 `frame.close()`；切布局时 `decoder.close()` |
| 双击放大后画面模糊 | 放大后仍在播子码流 | 放大时切主码流重连，缩小时切回子码流 |
| 高并发下服务器 CPU 满 | 每路都在服务端做转码 | 确认摄像头编码已是 H.264，服务端用 `-c copy` 透传 |
| 点击后要等 1-2 秒才出画面 | GOP 太长，播放器在等下一个 I 帧 | 摄像头端 I 帧间隔缩到 1s，或转码时 `-g 25` |
| GPU 转码到第 9 路报错 | GeForce 驱动限制 8 路 NVENC 会话 | 数据中心卡（T4/A10）无限制；或降低单路编码规格 |
| WebSocket 断开后不重连 | 前端未实现重连逻辑 | 监听 `player.on(mpegts.Events.ERROR, ...)` 触发重连 |
