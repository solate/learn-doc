# 流媒体安全：鉴权、防盗链与 DRM

> **适合读者**：需要把流媒体系统从"能跑通"推向"能上线"的后端工程师  
> **前置知识**：[第 15 篇：SRS 部署与配置实战](15-SRS部署与配置实战.md)、[第 16 篇：MediaMTX 实战](16-MediaMTX实战.md)、[第 22 篇：CDN 分发与边缘加速](22-CDN分发与边缘加速.md)  
> **核心问题**：播放地址被盗链怎么办？付费内容被录播搬运怎么办？什么场景必须上 DRM？

---

## 一、威胁模型：你的流会被怎么"偷"

读完本节，你能对照自己的系统，列出每一层缺口分别对应哪种攻击。

流媒体系统的安全问题和普通 Web 不同：**视频 URL 是要分发给千家万户的**，天然暴露；而内容本身有价值，值得攻击者花功夫。典型威胁有四类：

```
① 盗链        别人的网站/APP 直接嵌你的播放地址
              → 流量从他那边看，带宽费从你这边出

② 盗播/搬运   付费课程/赛事被拉流后转推到别处直播，
              或录下来二次分发

③ 接口白嫖    绕过你的前端页面，用脚本直接拉流
              （URL 规律被摸清：/live/cam_001、cam_002...）

④ 推流劫持    推流密钥泄露，攻击者往你的直播间推任意内容
              （钓鱼、违规内容，封号的却是你）
```

| 威胁 | 攻击者成本 | 造成的损失 | 防御层 |
|------|-----------|-----------|--------|
| 盗链 | 极低（复制 URL） | 带宽成本激增 | 播放鉴权（第四节） |
| 盗播 | 中（写拉流脚本） | 付费收入流失 | 内容加密 + 水印（五、七节） |
| 接口白嫖 | 低（看请求规律） | 带宽 + 数据泄露 | 短时效签名 URL（第四节） |
| 推流劫持 | 低（密钥泄露即成功） | 业务/合规风险 | 推流鉴权（第三节） |

> **先想清楚你防的是谁**。防"顺手复制 URL 的人"和防"专职搬运团队"，成本差一个数量级。第八节的决策表按内容价值给出推荐组合。

## 二、安全分层总览：纵深防御

读完本节，你能建立"每层各挡一类攻击"的整体图，不再指望某个单点方案解决所有问题。

```
                     谁能推流？            谁能播放？
                        │                    │
┌───────────────────────┼────────────────────┼──────────────────┐
│ 第 1 层  推流鉴权      │ on_publish 回调     │                  │
│ 第 2 层  播放鉴权      │                    │ on_play 回调 +    │
│          （身份层）    │                    │ 短时效签名 URL    │
├───────────────────────┴────────────────────┴──────────────────┤
│ 第 3 层  内容加密（持有合法 URL 也拿不到可播放的内容）           │
│          HLS AES-128  →  DRM（Widevine/FairPlay/PlayReady）    │
├───────────────────────────────────────────────────────────────┤
│ 第 4 层  传输加密      HTTPS / DTLS-SRTP（防链路窃听）          │
├───────────────────────────────────────────────────────────────┤
│ 第 5 层  水印溯源      内容最终还是可能被录屏 → 溯源追责         │
└───────────────────────────────────────────────────────────────┘
```

关键认知：

1. **鉴权（1、2 层）挡"进不来"，加密（3 层）挡"拿到了也看不了"，水印（5 层）兜"看了还敢传播"**。三层互不可替代。
2. 传输加密（HTTPS）只保证链路安全，**不提供任何访问控制**——它防的是第三方窃听，防不了拿到 URL 的人。
3. 越往下成本越高：鉴权几乎免费，AES-128 便宜，DRM 贵（证书 + License 服务 + 兼容性测试）。按需往下走。

## 三、推流端鉴权：守住入口

读完本节，你能为推流入口加上回调鉴权，并管理好推流密钥。

推流是最危险的入口：**攻击者一旦拿到推流地址，伤害是即时的**（推违规内容、覆盖正常直播）。三家服务器都支持把推流事件回调给业务后端，由后端决定放行与否：

| 服务器 | 配置方式 | 回调时机 | 放行/拒绝 |
|--------|---------|---------|----------|
| SRS | `http_hooks.on_publish` | 收到 RTMP/WHIP 推流 | HTTP 200 放行，其他拒绝 |
| MediaMTX | `authMethod: http` + `authHTTPAddress` | 推/拉流请求到达 | 2xx 放行，401 拒绝 |
| ZLMediaKit | `[hook] on_publish` | 推流注册时 | JSON `{"code":0}` 放行 |

Go 后端的鉴权回调（以 ZLMediaKit 参数风格为例，SRS 同理）：

```go
// POST /api/v1/zlm/on_publish
// ZLMediaKit 回调参数：app、stream、ip、params（URL 上携带的自定义参数）
func onPublish(c *gin.Context) {
    var req struct {
        App    string `form:"app"`
        Stream string `form:"stream"`
        IP     string `form:"ip"`
        Params string `form:"params"`
    }
    if err := c.ShouldBind(&req); err != nil {
        c.JSON(200, gin.H{"code": 401, "msg": "参数错误"})
        return
    }

    // 推流密钥放在 params 里：?key=xxxx
    // 密钥是推流时动态签发的，与频道绑定、有过期时间
    u, err := url.ParseQuery(req.Params)
    if err != nil || !streamKeySvc.Verify(req.Stream, u.Get("key")) {
        log.Warn().Str("stream", req.Stream).Str("ip", req.IP).Msg("推流鉴权拒绝")
        c.JSON(200, gin.H{"code": 401, "msg": "invalid stream key"})
        return
    }

    c.JSON(200, gin.H{"code": 0}) // 放行
}
```

**推流密钥的管理规则**（比鉴权代码本身更重要）：

1. **密钥与频道绑定**，不是全局一个密码；泄露一个只影响一个频道。
2. **短时效**：开播时签发，有效期等于预计直播时长，下播即失效。
3. **可轮换**：后台支持一键作废重发（密钥疑似泄露时）。
4. **日志留痕**：每次拒绝都记录 IP，连续失败触发告警（有人在扫描你的推流入口）。

WHIP 推流的场景（浏览器/OBS 走 HTTP），用标准 `Authorization: Bearer <token>` 头（WHIP 协议原生支持，见[第 13 篇](../01-底层技术基础/13-WHIP-WHEP标准化推拉流.md)），不要把 token 拼在 URL 上——URL 会进访问日志。

## 四、播放端鉴权：短时效签名 + on_play 回调

读完本节，你能设计"播放地址 5 分钟后失效"的机制，并知道它和 CDN 签名的分工。

[第 22 篇](22-CDN分发与边缘加速.md)已经详细讲了 **CDN 侧签名 URL**（Type A：`MD5(uri-ts-rand-uid-key)`）以及它和缓存命中率的冲突（签名参数必须从缓存键剔除）。本节讲与之互补的**源站侧鉴权**，两者分工：

```
观众播放 http://cdn.example.com/live/room1.m3u8?ts=1760000000&sign=xxx
                                      │
                    ┌─────────────────┴──────────────────┐
                    │ CDN 边缘节点                        │
                    │ 校验签名（ts 未过期 + sign 正确）    │
                    │ 命中缓存直接返回，未命中回源         │
                    └─────────────────┬──────────────────┘
                                      │ 回源（可再开"回源鉴权"）
                    ┌─────────────────┴──────────────────┐
                    │ 源站流媒体服务器                     │
                    │ on_play 回调业务后端：              │
                    │   这个用户能看这个频道吗？           │
                    │   （会员到期？并发路数超限？封禁？） │
                    └────────────────────────────────────┘
```

- **CDN 签名**管"这个 URL 是不是我签发的、过没过期"——它不知道用户是谁。
- **on_play 回调**管"这个用户现在还能不能看"——会员到期、多设备并发超限、房间封禁这类**实时业务判断**，只有业务后端能做。

### 短时效 Token 的实现

```go
// 生成播放地址：有效期 5 分钟，绑定用户与频道
func (s *PlayService) SignURL(userID, channel string, ttl time.Duration) string {
    expire := time.Now().Add(ttl).Unix()
    raw := fmt.Sprintf("%s|%s|%d|%s", channel, userID, expire, s.secret)
    sign := fmt.Sprintf("%x", md5.Sum([]byte(raw))) // md5 仅示意，生产建议 HMAC-SHA256
    return fmt.Sprintf("%s/live/%s.m3u8?uid=%s&expire=%d&sign=%s",
        s.cdnBase, channel, userID, expire, sign)
}
```

两个易错点：

1. **有效期不是越长越省事**。签名 24 小时有效 = 被复制出去 24 小时内都能看。直播场景 1-5 分钟足够，播放器在临近过期时向后端要新地址（刷新动作对用户无感，因为 m3u8 分片地址不变时播放器不会重连）。
2. **签名别进缓存键**。分片级 URL 不要逐个签名——只签 m3u8/MPD 索引（CDN 不会缓存带签名参数的索引），分片走无参地址，否则命中率归零（[第 22 篇](22-CDN分发与边缘加速.md)的详细论证）。

## 五、内容加密：HLS AES-128

读完本节，你能理解 AES-128 HLS 的保护边界——它挡得住盗链，挡不住有心录播。

鉴权解决"拿不到 URL"，但合法观众播放时，内容终究是明文到达客户端的。**HLS AES-128** 是第一档内容加密：

```
m3u8 索引：
  #EXT-X-KEY:METHOD=AES-128,URI="https://api.example.com/keys/room1.key?token=xxx"
  #EXTINF:4.0,
  seg0.ts          ← AES-128 加密后的分片
  seg1.ts

播放流程：
  播放器 → GET m3u8 → 发现 KEY 行 → 带 token 请求密钥接口
        → 拿到 16 字节密钥 → 逐分片解密 → 播放
```

用 FFmpeg 生成加密 HLS（密钥文件格式见[第 27 篇](../03-行业应用场景/27-电视盒子内部原理.md)的完整命令）：

```bash
# key_info 文件三行：密钥 URI / 密钥 hex / IV hex
ffmpeg -i source.mp4 \
  -c copy -f hls -hls_time 4 \
  -hls_key_info_file key_info \
  out.m3u8
```

**安全性的核心不在加密本身，而在密钥接口**。分片加密是标准操作，攻击者的目标是密钥：

1. 密钥接口必须鉴权（登录态/token），且和 m3u8 的签名是**同一个会话**签发的——否则拿到 m3u8 就等于拿到密钥。
2. 密钥下发可加**设备数/并发限制**（一个 token 最多 N 个设备取密钥）。
3. 可以按用户派生密钥（密钥 = HMAC(masterKey, userID)），配合第七节的水印实现"密钥即指纹"。

**诚实的边界**：AES-128 的解密发生在客户端播放器里，`F12 → Network` 就能看到密钥请求。它防的是"复制 URL 分享"和批量爬流脚本（配合短时效签名，脚本需要先登录拿 token 才能取密钥），**防不了愿意动手抓包的人**。要挡住后者，需要 DRM。

## 六、DRM：Widevine / FairPlay / PlayReady

读完本节，你能判断自己的内容是否值得上 DRM，以及上 DRM 的完整链路包含什么。

DRM（Digital Rights Management，数字版权管理）和 AES-128 的本质区别：**解密过程被放进硬件信任执行环境（TEE，Trusted Execution Environment）**，应用层代码（包括浏览器扩展、抓包工具）接触不到明文密钥和解密后的帧。

### 三大体系

| DRM 体系 | 所有者 | 覆盖端 | 信任级别 |
|----------|--------|--------|---------|
| Widevine | Google | Chrome / Android / Firefox / 智能电视 | L1（硬件 TEE）/ L3（软件） |
| FairPlay | Apple | Safari / iOS / iPadOS / tvOS | 全硬件 |
| PlayReady | Microsoft | Edge / Windows / Xbox | 硬件 |

浏览器播放加密内容走 **EME（Encrypted Media Extensions）** API：播放器（hls.js/自研）通过 EME 向浏览器的 DRM 模块请求解密，DRM 模块再向你的 **License 服务器**申请许可证——License 里才包含内容密钥，且可以限制（绑定设备、限制时长、离线策略）。**License 服务器是你控制权的落点**：可以按用户发放、按设备数限制、随时吊销。

```
播放器(hls.js) ──EME──→ 浏览器 DRM 模块 ──License请求──→ 你的 License 服务器
     │                        │                            │
     │ 拿到加密分片            │ 密钥只在 TEE 内解密          │ 校验：这个用户
     │ （CMAF + cbcs 加密）    │ （应用层拿不到明文密钥）      │ 买了这场赛事吗？
     ▼                        ▼                            ▼
  正常解码播放            抓包/录屏工具拿不到解密后画面      发放/拒绝 License
```

**CMAF + cbcs**（第 11 篇）在这里发挥作用：同一份 `cbcs` 模式加密的分片可以同时被三种 DRM 解密，不需要按 DRM 体系分别存储三份——存储和转码成本不翻三倍。

### 什么场景值得上 DRM

| 内容 | 推荐 |
|------|------|
| 版权影视 / 体育赛事（单场内容价值高、盗版动机强） | 值得，DRM 是行业标配（Netflix/爱优腾全用它） |
| 付费课程（单份价值中、受众面窄） | 通常 AES-128 + 显式水印够用，DRM 视盗版情况再上 |
| 企业内部监控 / 内部培训 | 不值得——账号鉴权 + 水印即可，DRM 的证书与集成成本不划算 |

成本清单（评估时别只看技术）：三家体系的证书/合作申请（FairPlay 需要向 Apple 申请 FPS 证书）、License 服务器（自建或买云服务）、播放端集成（EME 各家实现差异）、测试矩阵（浏览器 × 设备 × DRM 组合）。**DRM 是一项运营成本，不是一次性开发成本。**

## 七、水印与溯源：最后一道防线

读完本节，你能理解为什么"防"永远不完美，以及"溯源"如何补上闭环。

内容一旦能被看到，就理论上能被录屏（手机对着屏幕拍是最原始也最无解的方式）。水印的作用从"防止"变为**"威慑 + 追责"**：

1. **显式水印**：播放时叠加用户 ID/手机号后四位（半透明、位置随机漂移防遮挡）。成本≈0，对"随手分享到群里"的场景威慑极大——溯源二维码直接指向泄漏者。
2. **隐式水印**：频域水印嵌入画面（肉眼看不出，专用工具提取），抗转码、抗裁剪。用于版权内容的取证级追溯，成本高，配合 DRM 使用。
3. **密钥即指纹**（第五节提到的按用户派生密钥）：即使录播者抹掉可见水印，从盗版内容解出的密钥也能反推泄漏账号。

监控类系统水印还有第二个用途：**合规留痕**（操作员工号 + 时间戳叠加在画面上，作为证据链的一环，见[第 29.6 篇](../03-行业应用场景/29.6-远程医疗视频会诊.md)医疗会诊的实践）。

## 八、安全等级决策表

把前七节收拢成一张选型表。**从上往下按内容价值和预算选，不要一步到位上 DRM**：

| 档位 | 场景 | 推荐组合 | 增量成本 |
|------|------|---------|---------|
| L0 | 公开免费内容（监控大屏公开流、公益直播） | HTTPS + CDN 签名 URL（仅防盗链） | ≈0 |
| L1 | 注册用户可见（企业内训、社区直播） | L0 + on_play 回调（实时权限） + 显式水印 | 低 |
| L2 | 付费内容（课程、会员点播） | L1 + HLS AES-128 + 密钥接口鉴权 + 按用户派生密钥 | 中 |
| L3 | 版权内容（影视、赛事、首发内容） | L2 + DRM（三体系）+ CMAF cbcs + 隐式水印 | 高（含运营） |
| 特殊 | 内部监控视频 | 账号鉴权 + 内网/VPN + 工号水印（内容不上 CDN） | 低 |

> 注：监控视频通常**不经过公网 CDN**——它不是"分发给更多人"，而是"特定人调阅"，隔离比加密更重要。

## 动手实践

### 练习1：推流鉴权回调（防推流劫持）

```bash
# 1. 启动带鉴权回调的 MediaMTX（authHTTPAddress 指向本地 Go 服务）
# mediamtx.yml:
#   authMethod: http
#   authHTTPAddress: http://localhost:8081/api/v1/streams/auth
docker run -d --name mediamtx -p 8554:8554 -p 8888:8888 \
  -v $(pwd)/mediamtx.yml:/mediamtx.yml bluenviron/mediamtx:latest

# 2. 无密钥推流（应被拒绝，服务器返回 401）
ffmpeg -re -i test.mp4 -c copy -f rtsp rtsp://localhost:8554/live/room1 && echo "❌ 不该成功"

# 3. 带正确密钥推流（成功）
ffmpeg -re -i test.mp4 -c copy \
  -f rtsp "rtsp://localhost:8554/live/room1?key=demo-key-123"
```

```go
// 本地回调服务：密钥硬编码仅作演示，生产环境查库 + 过期时间
func main() {
    r := gin.Default()
    r.POST("/api/v1/streams/auth", func(c *gin.Context) {
        key := c.Query("key")
        if key != "demo-key-123" {
            c.Status(401)
            return
        }
        c.Status(200)
    })
    r.Run(":8081")
}
```

**预期输出**：无密钥推流被拒（FFmpeg 报 401/Unauthorized），带密钥推流成功，`curl http://localhost:8888/live/room1.m3u8` 能取到索引。

### 练习2：AES-128 HLS + 密钥接口鉴权

```bash
# 1. 生成 16 字节密钥与 key_info 文件
openssl rand -hex 16 > enc.key
printf "https://api.example.com/keys/room1.key?token=demo\n%s\n%s\n" \
  "$(cat enc.key)" "$(openssl rand -hex 16)" > key_info

# 2. 生成加密 HLS
ffmpeg -i test.mp4 -c copy -f hls -hls_time 4 \
  -hls_key_info_file key_info out/mystream.m3u8

# 3. 验证分片确实加密：直接解码会报错
ffprobe -v error -show_frames out/seg0.ts 2>&1 | head -3
```

**预期输出**：`out/` 下的 m3u8 含 `#EXT-X-KEY:METHOD=AES-128`；直接 `ffplay out/seg0.ts` 无法播放（缺密钥）；把 key_info 第一行换成 `enc.key` 本地路径后 ffplay 能播（模拟"拿到密钥才能看"）。再观察：密钥 URI 指向需要 token 的接口——没有 token 的请求拿不到密钥，这就是第五节说的"密钥接口才是核心"。

### 练习3：短时效播放 token 的过期验证

```go
func TestSignURLExpire(t *testing.T) {
    svc := NewPlayService("test-secret", "http://cdn.example.com")

    url1 := svc.SignURL("user1", "room1", 5*time.Minute)
    if !svc.Verify("room1", url1) {
        t.Fatal("5 分钟内的签名应通过校验")
    }

    // 生成一个 1 秒过期的签名，睡 2 秒后校验
    url2 := svc.SignURL("user1", "room1", 1*time.Second)
    time.Sleep(2 * time.Second)
    if svc.Verify("room1", url2) {
        t.Fatal("过期签名不应通过校验")
    }

    // 换用户校验（签名绑定用户，不能串用）
    if svc.VerifyForUser("user2", "room1", url1) {
        t.Fatal("签名与用户绑定，他人使用应拒绝")
    }
}
```

**预期输出**：三个断言全部通过——未过期通过、过期拒绝、跨用户拒绝。

## 常见问题排查

| 现象 | 可能原因 | 解决方法 |
|------|---------|---------|
| 开了签名 URL 后 CDN 命中率暴跌 | 签名参数进了缓存键 | 在 CDN 配置里把签名参数从缓存键剔除（见第 22 篇） |
| 播放器播 30 秒后卡死 | 签名 URL 过期早于播放时长 | 索引签名有效期覆盖直播时长，或播放器临近过期时刷新地址 |
| AES-128 在 Safari 播不了，Chrome 正常 | Safari 对 KEY URI 的 CORS 限制更严 | 密钥接口响应加 `Access-Control-Allow-Origin` 与正确的 Content-Type |
| on_play 回调偶尔超时导致误踢 | 回调服务慢（查库 200ms+） | 回调内部加短缓存（用户权限缓存 30s）；回调超时配置为"失败放行 + 异步核查"的策略要谨慎评估 |
| WHIP 推流带 Bearer token 被拒 | 服务器未启用 token 校验或跨域预检失败 | 确认服务器 WHIP 鉴权配置；OPTIONS 预检请求也要正确响应 |
| DRM 内容在某些安卓机黑屏 | 该机型只有 Widevine L3 或证书过期 | License 服务按设备能力降级；测试矩阵覆盖低端机型 |
