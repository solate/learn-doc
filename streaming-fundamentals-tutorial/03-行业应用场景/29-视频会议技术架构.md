## 一、三种架构：一张表看懂

视频会议只有三种服务端形态，先记住这张对比表再往下读：

| 指标 | P2P（点对点） | MCU（多点控制单元） | SFU（选择转发单元）★ |
|------|--------------|-------------------|-------------------|
| 服务端处理 | 无 | 解码 → 合并 → **重新编码** | **不解码，只转发 RTP 包** |
| 每人上行 | N-1 路 | 1 路 | 1 路 |
| 每人下行 | N-1 路 | **1 路**（合并流） | N-1 路（可 Simulcast 降档） |
| 服务端 CPU | 无 | 极高（每增 1 人全量转码） | 极低（转发≈内存拷贝） |
| 带宽压力 | 上行爆炸 | 下行最省 | 下行较高，弱网可降层 |
| 适用场景 | 1对1 通话 | 硬件会议室终端 | 软件会议（主流） |
| 代表 | 直接 WebRTC | OpenMCU | LiveKit / mediasoup / Janus |

**一句话本质区别**：

- **MCU** 把"多人画面合并成一路"再发给每个人——下行最省，代价是服务器每增一人就要全量解码+转码，贵。
- **SFU** 是"我收到谁的流，就原样转给其他人"——服务器几乎零成本，把"收 N 路、本地排布、本地混音"的复杂度全部推给客户端。

> **回答开篇问题**：Zoom、腾讯会议、Google Meet 全部是 **SFU + Simulcast** 架构（自研或基于 mediasoup/LiveKit 同款技术）。MCU 只在硬件视频会议终端（老牌 Polycom 机型）还有市场。

### 为什么超过 2 人必须上服务器

```
P2P，10 人会议：
  每人要把自己的视频同时发给其余 9 人 → 上行 9 路
  同时解码其余 9 人的视频            → 下行 9 路
  单端 18 路收发，全房间峰值 90 路连接
  ↳ 上行带宽和客户端 CPU 最先爆炸

SFU，同样 10 人：
  每人只管 1 路上行到 SFU            → 上行 1 路
  SFU 原样转发给其他 9 人            → 下行 9 路（弱网可给低清层）
  ↳ 单端 10 路，服务器扛住全部转发
```

### 关于 SFU 的两个高频误解

1. **SFU 解不解码音频？** 默认和视频一样**不解码**，每路音频原样转发给订阅者，由**客户端本地混音**把多人人声叠加播放。SFU 只在需要"合成一路输出给外部"时才解码混音——比如录制、转 RTMP 广播。
2. **服务端怎么知道"谁在说话"？** 靠的不是解码。浏览器发出的音频 RTP 包自带头扩展（RFC 6464）逐包标注音量，SFU 读这个字段就知道谁在发声，用于说话人高亮和自动切换主画面。

## 二、会议系统整体架构（后端视角）

一个会议系统 = **两条完全独立的通道**。媒体和信令分离，是后端最容易忽略的设计前提：

```
客户端                     │                    后端
                          │
  ┌───────────────┐       │      ┌────────────────────────────┐
  │ Web 客户端       │◄─────┼─────►│ 信令/业务服务（WebSocket）     │
  │ 摄像头/麦克风/屏幕 │ 信令 │    WS │ 房间·成员·SDP交换·入会鉴权·数据通道│
  └───────┬───────┘  SDP  │      └────────────────────────────┘
          │              │
          │ 媒体 RTP/RTCP │      ┌────────────────────────────┐
          │ （SRTP 加密）  │      │ SFU 媒体服务器（纯转发）          │
          └─────────────►│      │ 不管业务，只做流的路由与转发        │
                          │      └────────────────────────────┘
                          │      ┌────────────────────────────┐
                          │      │ TURN 中继（NAT 穿透保底）       │
                          │      └────────────────────────────┘
```

各组件职责（各一行，理解分工即可）：

- **信令/业务服务**：房间状态、成员进出、转发 SDP（offer/answer）与 ICE 候选、签发入会 Token。**不碰媒体流**，WebSocket 一个通道全包。
- **SFU 媒体服务器**：纯转发。只关心"谁推了几条轨、谁订阅谁、每条轨转哪几层"，并**针对每个订阅者独立做转发决策**。
- **TURN 中继**：双方都穿不过对称 NAT 时的保底路径（原理见第 12 篇）。会议系统必须搭——最需要连的用户往往就是穿透失败的那批。
- **DataChannel**：WebRTC 内置的低延迟数据通道，复用媒体连接、不挤信令服务器。举手、实时字幕、教学画笔全走这里。
- **Token（JWT）**：客户端持 Token 才允许进房间、订阅别人。Token 里注明"房间名 + 角色"，SFU 和业务服务各验一遍，它是入会的唯一真相源。

### 完整链路：一个参会者从加入到被看到

```
1 入会  → 客户端 → WS 信令服务：请求入会（携带 Token）
2 鉴权  → 信令服务校验 → 返回房间内已有成员的轨道信息
3 协商  → 客户端 ↔ SFU 完成 Offer/Answer + ICE 通道建立
          ↳ ICE/DTLS/SRTP 细节在第 12 篇，之后就是加密密道
4 推流  → 客户端把摄像头（可 Simulcast 三路）推上 SFU —— 1 路上行
5 转发  → SFU 把这一路按订阅关系复制给房间其他 N-1 人
6 订阅  → 新进者收到房间内现有 N-1 路 → 本地解码、排网格、混音
```

一句话记住这条链：**入会靠信令，说话靠推流，看见靠转发，混音在本地。**

## 三、主流 SFU 开源方案

| 框架 | 语言 | 特点 | 谁在用 |
|------|------|------|--------|
| **LiveKit** | Go | 云原生、文档最全、开箱即用（部署/录制/Egress 全家桶） | Go 后端首选 |
| **mediasoup** | C++/Node | 性能天花板，纯 SFU 库（信令完全自写） | Jitsi Meet |
| **Janus** | C | 老牌稳健，插件生态丰富 | 网关/会议 |
| **ion-sfu** | Go | pion 系、轻量，适合读源码理解协议 | 教学/小型项目 |

**选型一句话**：想快点上功能直接选 LiveKit；追求极致性能且愿意自己写信令选 mediasoup；想研究 SFU 内部实现就读 ion-sfu。

## 四、LiveKit 快速部署 + 入会 Token

```bash
# Docker 启动 LiveKit SFU
docker run -d \
  --name livekit \
  -p 7880:7880 -p 7881:7881 \
  -p 7882:7882/udp \
  -v $PWD/livekit.yaml:/etc/livekit.yaml \
  livekit/livekit-server \
  --config /etc/livekit.yaml
```

```yaml
# livekit.yaml
port: 7880
rtc:
  tcp_port: 7881
  udp_port: 7882
  use_external_ip: false   # 生产必须 true，否则 ICE 拿到内网地址

keys:
  APIxxxxxxxxxx: "secretxxxxxxxxxx"
```

```go
// Go 中生成入会 Token —— 客户端持此 Token 才能 join 房间
import "github.com/livekit/protocol/auth"

func GenerateJoinToken(apiKey, apiSecret, roomName, participantName string) (string, error) {
    at := auth.NewAccessToken(apiKey, apiSecret)
    grant := &auth.VideoGrant{
        RoomJoin: true,
        Room:     roomName,
    }
    at.AddGrant(grant).
        SetIdentity(participantName).
        SetValidFor(2 * time.Hour)

    return at.ToJWT()
}
```

## 五、Simulcast 与带宽自适应（SFU 的灵魂）

Simulcast 是 SFU 支持数百人的关键：发送端同时推**三路不同分辨率**，SFU **针对每个订阅者**独立选择转发哪一层：

```
参与者 A 同时推：
  ├── 1080p 高清（rid=h）
  ├── 360p  中清（rid=m）
  └── 180p  低清（rid=l）

SFU 每条转发路径各自选层：
  └─► 宽带用户 B → 转发 1080p
  └─► 手机用户 C → 转发 360p
  └─► 弱网用户 D → 转发 180p
```

三个关键点：

1. **选层是每个订阅者独立的**——A 的编码成本只产生一次（推三路），但 10 个订阅者可以拿到 10 种不同层，服务器零转码。
2. **换层不重新协商**：SFU 只切换"转发哪一层 RTP"，客户端无感知——**这就是"弱网无卡顿"的真正来源**。
3. **SVC vs Simulcast**：Simulcast 推多路、选一路；SVC 推一路（自带空间+时间层）、SFU 丢高层子流。SVC 更省上行，但编码复杂，**目前业界主流是 Simulcast**（SVC 详见第 12 篇）。

### 与 WebRTC 拥塞控制配合

接收端用 RTCP 反馈（REMB/TWCC，见第 12 篇）持续上报带宽，SFU 收到反馈就把该订阅者切到匹配的层，视频降级但**音频永不停**。

浏览器端设置三路编码参数：

```javascript
const sender = pc.getSenders()[0];
const params = sender.getParameters();
params.encodings = [
    { rid: 'h', maxBitrate: 3000000 },  // 高质量
    { rid: 'm', maxBitrate: 1000000, scaleResolutionDownBy: 2 },
    { rid: 'l', maxBitrate: 200000, scaleResolutionDownBy: 4 },
];
await sender.setParameters(params);
```

## 六、会议特有功能：屏幕共享 / 录制 / 静音

### 屏幕共享 = 第二路视频轨道

浏览器 `getDisplayMedia()` 生成**独立的高清视频轨**，作为 sendonly 轨道发布，不占摄像头轨。所以会议系统要从数据结构上支持"**一个参与者多条视频轨 + 每条轨可选层**"——SFU 的订阅模型天然支持。

### 录制 = Egress"虚拟参会者"

```go
// 通过 Egress 录制 LiveKit 房间
func RecordRoom(ctx context.Context, roomName, s3URL string) error {
    egress := livekit.NewEgressServiceClient(conn)
    _, err := egress.StartRoomCompositeEgress(ctx, &livekit.RoomCompositeEgressRequest{
        RoomName: roomName,
        Output: &livekit.RoomCompositeEgressRequest_S3{
            S3: &livekit.S3Upload{
                AccessKey: os.Getenv("AWS_ACCESS_KEY"),
                Secret:    os.Getenv("AWS_SECRET"),
                Bucket:    "recordings",
                Key:       fmt.Sprintf("%s-%d.mp4", roomName, time.Now().Unix()),
            },
        },
    })
    return err
}
```

Egress 的实现本质是一个**自带转码的订阅者**：它像普通参会者一样订阅房间所有流，但不转发——**解码、混音、合成布局、输出 MP4/HLS**。所以"录制会明显拉高服务器负载"是必然的（这是 SFU 唯一需要解码的场景），生产上 Egress 要独立部署节点。

### 静音是发送端行为

静音 = 发送端停推音频轨，SFU 不再把该音频转发给任何人，其他人自然安静。**不需要任何服务端处理**——转发模型的又一个好处。

## 七、生产化：从单节点到集群

| 阶段 | 做法 | 一句话 |
|------|------|--------|
| 单机 POC | 一台 LiveKit + 一台业务服务 | 现在就能跑（见动手实践） |
| 多房间扩容 | 按一致性哈希把不同房间路由到不同 SFU 节点 | **房间是天然的负载单元** |
| 跨地域 | 就近 SFU + 全局 TURN 集群 | 延迟与穿透两手抓 |
| 录制规模 | Egress 独立节点池 | 别和媒体转发抢 CPU |

## 本篇小结

| 场景 | 推荐架构 |
|------|---------|
| 1对1 通话 | WebRTC P2P |
| 小型会议（< 10 人） | SFU（LiveKit） |
| 大型会议（> 100 人） | SFU + Simulcast |
| 硬件会议室 | MCU |
| 直播连麦 | SFU（嘉宾）→ 混流 → HLS（观众） |

**一句话总纲**：会议系统 = 信令服务 + SFU 转发 + Token 鉴权；视频不解码、混音在客户端；全链路唯一要解码的地方是录制（Egress）。

### 练习1：部署 + 验证 LiveKit
正文第四节已给出部署命令和配置，补一个可校验输出的启动方式：

### 练习2：JavaScript 客户端加入会议室
```javascript
import { Room, RoomEvent, Track } from 'livekit-client';

const room = new Room();
await room.connect('wss://your-livekit-server', token);

// 发布本地摄像头和麦克风
await room.localParticipant.enableCameraAndMicrophone();

// 订阅远端参与者的媒体流
room.on(RoomEvent.TrackSubscribed, (track, publication, participant) => {
  if (track.kind === Track.Kind.Video) {
    const videoElement = document.createElement('video');
    track.attach(videoElement);
    document.getElementById('remote-videos').appendChild(videoElement);
  }
});
```
**预期输出**：两个浏览器标签页加入同一房间，互相看到对方摄像头画面，音视频延迟 < 300ms。

### 练习3：Go 后端创建会议室 + 下发入会 Token
```go
import lksdk "github.com/livekit/server-sdk-go"

func (s *MeetingService) CreateRoom(ctx context.Context, roomName string) error {
    roomClient := lksdk.NewRoomServiceClient("https://livekit-server", "api-key", "api-secret")
    _, err := roomClient.CreateRoom(ctx, &livekit.CreateRoomRequest{
        Name:            roomName,
        EmptyTimeout:    300, // 无人5分钟后自动销毁
        MaxParticipants: 20,
    })
    if err != nil {
        return xerr.Wrap(xerr.ErrInternal.Code, "创建会议室失败", err)
    }
    log.Info().Str("room", roomName).Msg("会议室已创建")
    return nil
}

func (s *MeetingService) GenerateToken(roomName, identity string) (string, error) {
    at := auth.NewAccessToken("api-key", "api-secret")
    grant := &auth.VideoGrant{RoomJoin: true, Room: roomName}
    at.AddGrant(grant).SetIdentity(identity).SetValidFor(time.Hour)
    return at.ToJWT()
}
```
**预期输出**：服务端创建房间并下发 Token，客户端凭 Token 加入对应房间。

## 常见问题排查

| 现象 | 可能原因 | 解决方法 |
|------|---------|---------|
| 加入会议室失败（ICE 失败）| LiveKit 无公网 IP 或 UDP 端口未开放 | 配置 `use_external_ip: true`，开放 UDP 端口范围 |
| 视频画面模糊 | Simulcast 给订阅者选了低分辨率层 | 检查订阅者带宽，或强制订阅高质量层 |
| 回音/啸叫 | 回声消除（AEC）未生效 | 浏览器 `echoCancellation: true`，用耳机 |
| 人数超过 10 人后卡顿 | SFU 服务器带宽不足，订阅者未降层 | 开启 Simulcast，订阅方按带宽选低质量层 |
| 屏幕共享黑屏 | 浏览器权限未授予 | 允许"屏幕录制"，macOS 需在系统偏好设置授权 |
| 说话人高亮不切换 | 音频电平检测未依赖 RFC 6464 头扩展 | 检查 SFU 是否解析 audio-level 扩展 |

## 术语表

| 术语 | 英文 | 说明 |
|------|------|------|
| SFU | Selective Forwarding Unit | 选择性转发单元，会议服务器按订阅关系转发每路流 |
| MCU | Multipoint Control Unit | 多点控制单元，服务端混流后发送一路给每个参与者 |
| Simulcast | Simulcast | 同时推多路分辨率，接收方各取所需 |
| rid | RTP Stream ID | SDP 中标识 Simulcast 各层的 `a=rid` 字段（h/m/l） |
| SVC | Scalable Video Coding | 单流含多层，SFU 丢高层子流实现降级 |
| Egress | Egress | SFU 的"录制和流输出"模块，本质是解码混流的虚拟参会者 |
| DataChannel | DataChannel | WebRTC 低延迟数据通道，承载举手/字幕等 |
| 回声消除 | AEC (Acoustic Echo Cancellation) | 消除扬声器被麦克风拾取回声的算法（客户端侧） |
