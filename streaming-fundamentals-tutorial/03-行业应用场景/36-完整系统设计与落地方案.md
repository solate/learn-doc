## 一、系统全景：一个平台的四条主链路

以"**多租户视频监控与管理平台**"为例，覆盖摄像头接入到前端播放的完整链路。

```
┌──────────────────────────────────────────────────────────────────────┐
│ 设备层          接入层           处理层          业务层          前端  │
│                                                                      │
│ IPC摄像头  ──RTSP──→ MediaMTX ──原样转发──→ 实时流 HLS/FLV/WebRTC ──→ │
│ NVR录像机  ──RTSP──→ 集群     ←─ FFmpeg ─→ 旁路分段录像 ──→ MinIO    │
│ 推流设备   ──RTMP──→          ←── AI ────→ 抽帧/推理/事件             │
│ IoT传感器  ──MQTT──→ EMQX  ──→           事件/告警/通知              │
│                                                                      │
│           ← Go 业务后端（REST API + 鉴权/生命周期回调）→               │
│           ← PostgreSQL + Redis →        ← Prometheus →              │
└──────────────────────────────────────────────────────────────────────┘
```

**看一个流媒体系统的正确姿势，不是"有哪些模块"，而是"数据怎么流"。** 它由四条**相互独立、可单独伸缩**的主链路组成：

### 链路 1：实时播放（无状态，核心是协议转换）

```
摄像头 RTSP ──推→ MediaMTX(接入层) ──按路数扩展──→ 播放端
                                  ├─ RTSP 直拉   : 低延迟, 但公网/浏览器不友好
                                  ├─ WebRTC/WHEP : ~200ms, 对讲等强交互场景
                                  └─ HLS/LL-HLS  : 2-5s, 全平台兼容、可过 CDN = 默认
```

**一句话决策**：监控默认 **HLS**（兼容一切、可走 CDN、浏览器直播）；只有"必须低延迟交互"的场景才引入 WebRTC。分发协议按场景选，不是全都要（[第 21 篇](../02-工程实践优化/21-低延迟播放完整方案.md)）。

### 链路 2：推流鉴权 + 在线状态（设备"上线"的动态闭环）

这是平台与接入层**唯一必写的联动**，用 MediaMTX 两级钩子实现：

```
IPC 推流 rtmp://media/live/{stream_key}?token=xxx
  ▼  MediaMTX 请求 HTTP 鉴权钩子（JSON: path+query+action）
后端: 校验 token/租户 → 200 放行 | 401 拒绝
  ▼
推流建立 → runOnPublish 通知 → streams 表 status=on, last_online_at
断推      → runOnUnpublish     → status=off
兜底: 健康检查协程定期核对，异常掉线也能收敛（[第 24 篇](24-视频监控行业技术架构.md)第六章）
```

```yaml
# mediamtx.yml —— 接入层最小配置
authMethod: http
authHTTPAddress: http://backend:8080/api/v1/streams/auth   # 放行=200 | 拒绝=401，推流/播放同走
runOnPublish:   "curl -s http://backend:8080/api/v1/streams/on-publish?path=$MTX_PATH"
runOnUnpublish: "curl -s http://backend:8080/api/v1/streams/on-unpublish?path=$MTX_PATH"
paths:
  "~^live/(.+)$": { source: publisher }    # 动态路径, 任意 stream_key 可接入
hls: yes
hlsSegmentDuration: 2s
hlsPartDuration: 200ms                     # LL-HLS: 首屏/切换更快
webrtc: yes
```

> **鉴权（auth 钩子）≠ 生命周期（runOnPublish）**：前者每次推/拉流都校验、结构化 JSON、同时管住推流和播放；后者只在流建立/断开时通知一次，用于更新在线状态。别让"状态更新"堵在鉴权路径上。

### 链路 3：录像与回放（唯一的重量级存储）

```
旁路 ffmpeg -c copy ──每10分钟切一段──→ MinIO 对象存储
  （不转码: 零画质损失 + 极小 CPU）
     │ 写完一段 → recording_segments 落一行索引
     ▼
前端时间轴: 按 (camera_id, start_time) 范围查分段 → 拼 VOD m3u8 回放
```

**一句话认知**：录像走**对象存储 + 分片索引**，不靠单机硬盘——回放、扩容、保留策略全部基于索引做，物理文件随时可搬。（深度见 [第 23 篇](../02-工程实践优化/23-录像存储与时间轴回放.md)，事件触发录像见 [第 35 篇](35-AI实时检测集成.md)第七节）

**录像容量速算（记住换算方法，别背数字）**：

```
1 Mbps ≈ 0.125 MB/s ≈ 10.8 GB/天 ≈ 324 GB/月/路
→ 100 路 1Mbps 存 30 天 ≈ 32.4 TB —— 所以默认只录主码流, 子码流(300kbps)只给预览/AI
```

### 链路 4：AI 检测与告警（旁路，绝不影响播放）

```
播放主链路 `-c copy` 原样转发
      └→ 抽帧 360p/2fps → Redis Stream → GPU 推理 → 事件表
           → 告警规则匹配（类型/置信度/时间段）→ 冷却去重 → 通知 + 触发录像
```

```go
// 冷却去重：同(摄像头,事件类型) 30s 内只打扰一次
key := "alert:" + cameraID + ":" + eventType
ok, _ := rdb.SetNX(ctx, key, 1, 30*time.Second).Result()
if !ok {
    return // 冷却期内, 跳过
}
```

**设计铁律**：AI 再慢也堵不住播放——它走独立队列、与主链路并联（[第 35 篇](35-AI实时检测集成.md)）。本篇只补它落库落表的部分。

**四条链路汇总——数据落在哪：**

| 链路 | 关键组件 | 数据落点 | 单点深度 |
|------|---------|---------|---------|
| 实时播放 | MediaMTX → HLS/WebRTC | 无状态 | 16/20/21 篇 |
| 鉴权/在线 | MediaMTX 钩子 → Go | `streams` | 22.5/24 篇 |
| 录像回放 | ffmpeg → MinIO → Go | `recording_segments` | 23 篇 |
| AI 告警 | Go + GPU + Redis | `events` + `alerts` | 35 篇 |

## 二、关键设计决策：先问为什么

真正的设计能力 = 每个决策都能一句话说清理由。八项核心决策速查：

| 决策点 | 结论 | 一句话理由 | 参考篇 |
|--------|------|-----------|--------|
| 接入服务器 | MediaMTX | 钩子全、WebRTC/HLS/RTSP 齐、Go 生态 | 14/16 |
| 拉流策略 | 按需拉流为主 | 常拉流畅，但路数一多带宽/CPU 扛不住 | 24 |
| 播放协议 | HLS 默认 + WebRTC 补充 | 兼容性优先，强交互才要 200ms | 21 |
| 录像方式 | 旁路 ffmpeg `-c copy` 分段 | 不转码=省算力、零画质损失 | 23 |
| 存储 | MinIO 对象存储 | 分片索引 + 无限扩容 + 生命周期清理 | 23 |
| AI 接入 | 旁路抽帧 + Redis Stream | 延迟绝不进播放链路 | 35 |
| 安全 | HTTP 鉴权钩子 + 短时效播放 token | 守推流入口 + 防盗链 | 22.5 |
| 设备接入 | ONVIF/GB28181 网关 | 海康/大华等走国标 `gb28181` 协议 | 25 |

## 三、数据库设计（四张业务核心表）

多租户规则一句话：**所有业务表带 `tenant_id`，查询强制按租户过滤；媒体层共享，靠 token 里的租户标识区分，业务各自落库。**

### 1. 摄像头表 `cameras`（设备资产）

```sql
CREATE TABLE cameras (
    camera_id      VARCHAR(20) PRIMARY KEY,
    tenant_id      VARCHAR(20) NOT NULL,
    name           VARCHAR(100) NOT NULL,
    rtsp_url       VARCHAR(500),              -- 设备真实地址(只后端可用, 不下发前端)
    stream_key     VARCHAR(100),              -- 对外推流/播放标识(关联 streams)
    protocol       VARCHAR(20) NOT NULL DEFAULT 'rtsp', -- rtsp/gb28181/onvif
    status         SMALLINT NOT NULL DEFAULT 0, -- 0:离线 1:在线(由链路2维护)
    last_online_at BIGINT NOT NULL DEFAULT 0,
    location_name  VARCHAR(200),
    latitude       DECIMAL(10,7),
    longitude      DECIMAL(10,7),
    created_at     BIGINT NOT NULL DEFAULT 0,
    updated_at     BIGINT NOT NULL DEFAULT 0,
    deleted_at     BIGINT NOT NULL DEFAULT 0
);
CREATE INDEX idx_cameras_tenant ON cameras(tenant_id);
```

### 2. 流任务表 `streams`（把"一路实时流"变成一等公民）

一台摄像头对应一条流任务，状态由链路 2 回调 + 健康检查共同驱动：

```sql
CREATE TABLE streams (
    stream_id      VARCHAR(20) PRIMARY KEY,
    tenant_id      VARCHAR(20) NOT NULL,
    camera_id      VARCHAR(20) NOT NULL,
    stream_key     VARCHAR(64)  NOT NULL,     -- 推流/播放 URL 里的标识
    server_node    VARCHAR(64),               -- 当前绑定的 MediaMTX 节点(集群时有意义)
    status         SMALLINT NOT NULL DEFAULT 0, -- 0:off 1:on 2:error
    last_online_at BIGINT NOT NULL DEFAULT 0,
    created_at     BIGINT NOT NULL DEFAULT 0,
    UNIQUE(tenant_id, stream_key)
);
```

### 3. AI 事件表 `events` + 告警表 `alerts`（事实 vs 待办）

**设计要点：事件 = 发生的事实（只落库，AI 写）；告警 = 需要人处理的（规则引擎升级、才通知）。** 两者分离，AI 只写事件，报警频率由规则控制：

```sql
CREATE TABLE events (
    event_id     VARCHAR(20) PRIMARY KEY,
    tenant_id    VARCHAR(20) NOT NULL,
    camera_id    VARCHAR(20) NOT NULL,
    event_type   VARCHAR(30) NOT NULL,        -- person/car/fire/intrusion
    confidence   DECIMAL(4,3) NOT NULL,
    snapshot_key VARCHAR(500),                -- 事件截图(MinIO), 供回溯
    ts           BIGINT NOT NULL,             -- 帧上时间戳
    created_at   BIGINT NOT NULL DEFAULT 0
);
CREATE INDEX idx_events_camera_time ON events(camera_id, ts);

CREATE TABLE alerts (
    alert_id     VARCHAR(20) PRIMARY KEY,
    tenant_id    VARCHAR(20) NOT NULL,
    camera_id    VARCHAR(20) NOT NULL,
    event_id     VARCHAR(20),                 -- 关联源头事件
    alert_type   VARCHAR(50) NOT NULL,
    confidence   DECIMAL(4,3),
    rule_id      VARCHAR(20),
    snapshot_key VARCHAR(500),
    event_time   BIGINT NOT NULL,
    handled      BOOLEAN NOT NULL DEFAULT FALSE,
    handled_by   VARCHAR(20),
    handled_at   BIGINT NOT NULL DEFAULT 0,
    remark       VARCHAR(500),
    created_at   BIGINT NOT NULL DEFAULT 0
);
CREATE INDEX idx_alerts_tenant_time ON alerts(tenant_id, event_time DESC);
```

### 4. 录像分段表 `recording_segments`

```sql
CREATE TABLE recording_segments (
    segment_id   VARCHAR(20) PRIMARY KEY,
    tenant_id    VARCHAR(20) NOT NULL,
    camera_id    VARCHAR(20) NOT NULL,
    file_key     VARCHAR(500) NOT NULL,       -- MinIO 对象键 {tenant}/{camera}/{ts}.mp4
    start_time   BIGINT NOT NULL,             -- 毫秒时间戳
    end_time     BIGINT NOT NULL,
    duration     INTEGER NOT NULL,            -- 秒
    file_size    BIGINT NOT NULL DEFAULT 0,
    status       SMALLINT NOT NULL DEFAULT 1, -- 1:已上传完整 2:缺失(待对账)
    created_at   BIGINT NOT NULL DEFAULT 0
);
CREATE INDEX idx_segments_camera_time ON recording_segments(camera_id, start_time);
CREATE INDEX idx_segments_tenant_time  ON recording_segments(tenant_id, start_time DESC);
```

**索引理由**：时间轴回放永远按"同一摄像头 + 时间范围"查，`(camera_id, start_time)` 一个复合索引足够；第二个只服务租户级列表。别给每列都建索引。

## 四、API 设计（一版够用的接口面）

| 分组 | 方法与路径 | 作用 |
|------|-----------|------|
| **设备管理** | `GET /api/v1/cameras` | 摄像头分页列表（含在线状态）|
| | `POST /api/v1/cameras` | 添加摄像头（生成 stream_key）|
| | `PUT /api/v1/cameras/{id}` | 修改（改地址后触发停流重连）|
| | `DELETE /api/v1/cameras/{id}` | 删除（停流 + 清理录像策略）|
| | `POST /api/v1/cameras/{id}/ptz` | 云台控制（[第 24 篇](24-视频监控行业技术架构.md)）|
| **流控制** | `GET /api/v1/streams/{id}/url` | 取播放地址（短时效签名）|
| | `POST /api/v1/streams/{id}/start` · `/stop` | 按需拉流启停 |
| | `POST /api/v1/streams/auth` | MediaMTX 鉴权钩子（[第四节代码](#动手实践)）|
| | `POST /api/v1/streams/on-publish` · `on-unpublish` | 生命周期回调 |
| **录像回放** | `GET /api/v1/recordings?camera_id=&start=&end=` | 时间轴分段列表 |
| | `GET /api/v1/recordings/playlist` | 动态 VOD m3u8（[第 23 篇](../02-工程实践优化/23-录像存储与时间轴回放.md)）|
| **AI 告警** | `GET /api/v1/events?camera_id=&type=&start=&end=` | 事件列表 |
| | `GET /api/v1/alerts?handled=false` | 待处理告警 |
| | `POST /api/v1/alerts/{id}/handle` | 处置告警 |

**三类鉴权要分清（落地最易踩的坑）**：

| 调用方 | 鉴权方式 | 说明 |
|--------|---------|------|
| 前端管理 API | JWT（用户登录）| 正常业务会话 |
| MediaMTX 钩子 | 内网白名单 + 固定密钥 | **不是**用户登录，只校验"是可信中继" |
| 播放 URL | 短时效签名（含过期时间）| 防盗链（[第 22.5 篇](../02-工程实践优化/22.5-流媒体安全鉴权防盗链与DRM.md)第四章）|

## 五、多路并发管理：把"一路流"管好

摄像头从几十路到几千路，后端关心的是**路数的生命周期**，不是单路细节：

```
状态机:  off ──start──→ connecting ──推流成功──→ on ──断推/超时──→ off
                           │ 失败/断流 ↓
                           └──→ error ──指数退避重试──→ connecting
```

三个必答问题：

1. **谁在拉流？** 后端按需出图才调度 ffmpeg 拉流进程，空闲回收——而不是每台摄像头常驻一路进程（常拉只在"必须秒级出画"的少量重点路用，见 [第 24 篇](24-视频监控行业技术架构.md)第六章）。
2. **挂了怎么办？** 拉流进程用"守护 + 指数退避"自动重启，绝不让用户看黑屏还得人工干预：

```go
// 进程池：一路一个 ffmpeg 子进程，退出自动重登
func (m *Manager) EnsureRunning(w *Worker) {
    if w.running() {
        return // 进程还在, 不动
    }
    time.Sleep(m.backoff(w.restartN))        // 指数退避: 1s→2s→4s→…上限30s
    cmd := exec.CommandContext(w.ctx, "ffmpeg",
        "-rtsp_transport", "tcp", "-i", w.cam.RTSPURL,
        "-c", "copy", "-f", "flv", w.outputURL) // -c copy 不转码省 CPU
    if err := cmd.Start(); err != nil {
        m.setStatus(w.cam.ID, "error")
        return
    }
    w.cmd, w.restartN = cmd, w.restartN+1
    go cmd.Wait()                            // 进程退出 → 下个 tick 触发重登
}
```

3. **什么时候停？** 无人观看的按需流定时回收（对应停止拉流）——省下的正是扩容的钱。

## 六、部署与监控

### 单机开发版（docker-compose）

```yaml
services:
  mediamtx:
    image: bluenviron/mediamtx:latest
    ports: ["1935:1935", "8554:8554", "8889:8889", "8888:8888"] # RTMP/RTSP/WebRTC/HLS
    volumes: ["./mediamtx.yml:/mediamtx.yml"]
    depends_on: [backend]                     # 鉴权钩子要先于推流可用

  backend:
    build: .
    ports: ["8080:8080"]
    environment: { DB_HOST: postgres, REDIS_ADDR: redis:6379, MINIO_ENDPOINT: minio:9000 }

  postgres: { image: postgres:16, environment: { POSTGRES_DB: video_platform, POSTGRES_PASSWORD: secret } }
  redis:    { image: redis:7-alpine }
  minio:
    image: minio/minio
    command: server /data --console-address ":9001"
    ports: ["9000:9000", "9001:9001"]
    volumes: ["minio_data:/data"]

  prometheus: { image: prom/prometheus, ports: ["9090:9090"] }  # 监控
  grafana:    { image: grafana/grafana, ports: ["3000:3000"], environment: { GF_SECURITY_ADMIN_PASSWORD: admin } }
  emqx:       { image: emqx:latest, ports: ["1883:1883", "18083:18083"] }
```

### 生产集群（按路数扩容）

| 组件 | 生产方案 | 备注 |
|------|---------|------|
| Go 后端 | K8s 2-4 Pod | 无状态，HPA 自动扩缩 |
| MediaMTX | 按路数分节点 | 单节点 50-100 路，按摄像头分布拆分 |
| PostgreSQL | 主从 + PgBouncer | 读写分离 |
| Redis | 哨兵 3 节点 | 冷却/流状态，可容忍丢失 |
| MinIO | 分布式 4 节点 | 纠删码 + 生命周期自动清理 |
| EMQX | 3 节点集群 | MQTT 消息 |

### 监控告警：上线前至少配这三条

Prometheus 采集 Go 应用指标（Prometheus client 暴露 `records_free_bytes` 等业务指标）、MediaMTX 指标（JSON 接口用 json_exporter 接入）、录制磁盘。**告警阈值应是"出了事能半夜叫醒人"的程度**：

```yaml
# prometheus.rules.yml —— 5 分钟窗口内判定
groups:
  - name: video-platform
    rules:
      - alert: StreamsOfflineSurge        # 大量流集体掉线 = 接入节点挂了
        expr: sum(streams_status) by(tenant) < 2
        for: 3m
      - alert: PublishAuthRejected        # 推流鉴权失败突增(被扫/配置错)
        expr: rate(streams_auth_total{result="rejected"}[5m]) > 10
        for: 5m
      - alert: RecordDiskCritical         # 录制盘要满, 录像随时停
        expr: records_free_bytes / records_total_bytes < 0.2
        for: 10m
```

Grafana 关键面板：**在线路数、鉴权成功率、拉流进程数、磁盘可录天数**（`磁盘剩余 ÷ 日均消耗`，比"剩余 30GB"更有判断力）。

**性能基线（经验值，非硬标准）**：单台 8C16G 后端可支撑数十路转码进程池或 100+ 路纯转发；需要多码率转码才上 GPU（1 张 RTX 3080 ≈ 64 路 720p H.264）；每路 HLS ≈ 2-3 个文件描述符，`ulimit -n 65536`。

## 七、落地路线：先通一条，再长成平台

不要先设计完再动手。**按链路复杂度递增、每阶段都有可验收交付物**：

| 阶段 | 周期 | 验收标准 | 覆盖 |
|------|------|---------|------|
| **P1 单路跑通** | 1-2 周 | 1 路 RTSP 进 MediaMTX，浏览器 HLS 秒开（延迟 < 5s）| 链路1（[16·17](../02-工程实践优化/16-MediaMTX实战.md)）|
| **P2 平台化** | 2-4 周 | cameras CRUD + 鉴权钩子 + 在线状态；50 路中坏 1 路不影响其他 | 链路2（[22.5](../02-工程实践优化/22.5-流媒体安全鉴权防盗链与DRM.md)·24）|
| **P3 录像回放** | 4-8 周 | 分段录像进 MinIO、时间轴秒开回放；30 天保留自动清理 | 链路3（[23](../02-工程实践优化/23-录像存储与时间轴回放.md)）|
| **P4 AI 告警** | 8-12 周 | 旁路抽帧→推理→事件/告警→通知；带冷却与置信度门槛 | 链路4（[35](35-AI实时检测集成.md)）|

**坑位信号**：P1 跑不通先别进 P2 的并发优化；P2 鉴权没闭环别急着录 AI 的像——每一阶段的"动手实践"都能验证。

### 练习 2：用 Go 实现最小鉴权服务（核心业务最小闭环）

```go
// 拿它当起点，按第四节 API 接口面逐条补齐（cameras CRUD / recordings / alerts）
package main

import (
    "crypto/hmac"
    "crypto/sha256"
    "encoding/hex"
    "encoding/json"
    "net/http"
    "os"
    "strings"
)

var secret = []byte(os.Getenv("STREAM_SECRET")) // 生产按 stream_key 从库查, 不硬编码

// HMAC-SHA256 签名（与设备端/播放端一致）
func hmacSign(path string) string {
    mac := hmac.New(sha256.New, secret)
    mac.Write([]byte(path))
    return hex.EncodeToString(mac.Sum(nil))
}

// MediaMTX HTTP 鉴权钩子: publish(推流)/read(播放) 都走这里，200=放行 401=拒绝
func auth(w http.ResponseWriter, r *http.Request) {
    var req struct {
        Path   string `json:"path"`
        Query  string `json:"query"`   // 推流 URL 的 ?token=xxx
        Action string `json:"action"`  // publish / read
    }
    if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
        w.WriteHeader(http.StatusUnauthorized)
        return
    }
    token := strings.TrimPrefix(req.Query, "token=")
    if token == "" || token != hmacSign(req.Path) {
        w.WriteHeader(http.StatusUnauthorized) // 401 → MediaMTX 拒绝该推流
        return
    }
    w.WriteHeader(http.StatusOK)              // 200 → 放行
}

func main() {
    http.HandleFunc("/api/v1/streams/auth", auth)
    http.ListenAndServe(":8080", nil)
}
```

```bash
STREAM_SECRET=devsecret go run main.go &
# 用 openssl 算同一个 HMAC 当 token（与 Go hmacSign 完全一致）→ 推流成功
TOKEN=$(printf 'live/cam_1' | openssl dgst -sha256 -hmac devsecret | awk '{print $2}')
ffmpeg -re -stream_loop -1 -i test.mp4 -c copy -f flv "rtmp://localhost/live/cam_1?token=$TOKEN"
# 错 token → 401 拒绝（ffmpeg 报认证失败）
ffmpeg -re -stream_loop -1 -i test.mp4 -c copy -f flv "rtmp://localhost/live/cam_1?token=wrong" 2>&1 | tail -2
```

**预期输出**：正确 token 能推上、浏览器能看；错 token 被拒；后端日志有鉴权记录。把 `?token` 换成播放地址签名就是同一条防线（[第 22.5 篇](../02-工程实践优化/22.5-流媒体安全鉴权防盗链与DRM.md)）。

### 练习 3：并发压测（验证进程池与按需回收）

```bash
# 模拟 30 路同时入拉（单机 30 个 ffmpeg 进程 ≈ 2GB 内存, 是本地合理上限）
for i in $(seq 1 30); do
  ffmpeg -re -stream_loop -1 -i test_low.mp4 -c copy -f flv "rtmp://localhost/live/cam_$i?token=$TOKEN" 2>/dev/null &
```

## 常见问题排查

| 现象 | 可能原因 | 解决方法 |
|------|---------|---------|
| 鉴权钩子不触发 | 回调 URL 写死 `localhost`，容器内不通 | 用 `backend:8080` 服务名或宿主 IP |
| 放行了但流不可播 | 放行 ≠ 就绪，按需拉流才有 prepared 状态 | 回调只置 `on`，联动拉流调度（状态机）|
| 租户 A 看到租户 B 的流 | 播放 URL 没携带/校验租户签名 | 签名里含 tenantID + 过期时间 |
| 告警风暴 | 事件无冷却 + 置信度门槛过低 | Redis 冷却 key + 事件/告警两级分离 |
| 回放时间轴空白 | 分段上传失败未对账 | `status=2` 标记缺失 + 定时对账重传 |
| 集群扩容后部分流"漂移" | 回调把流绑到已挂节点 | `server_node` 心跳巡检 + 重新绑定 |
| 录制盘满导致静默失败 | 只监控系统盘，没监控录盘 | 录盘剩余 < 20% 告警（第六节）|

## 术语表

| 术语 | 英文 | 说明 |
|------|------|------|
| 按需拉流 | On-demand Pull | 有观众才拉流，省资源；常拉反之 |
| 指数退避 | Exponential Backoff | 重试间隔 1s/2s/4s 递增，防重连风暴 |
| 鉴权钩子 | Auth Hook | MediaMTX 每次推/拉流请求后端，决定放行/拒绝 |
| 生命周期回调 | Publish Callback | 流建立/断开时通知一次，用于更新在线状态 |
| 短时效签名 URL | Signed URL | 带过期时间和签名的播放地址，防盗链 |
| 事件 vs 告警 | Event vs Alert | 事件=事实只落库；告警=需处理才通知 |
| 对账 | Reconciliation | 定期核对文件与索引，补齐缺失分段 |
