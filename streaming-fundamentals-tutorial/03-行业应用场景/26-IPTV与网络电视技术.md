# IPTV 与网络电视技术

> **适合读者**：想搞懂"运营商电视是怎么送到我家电视"的后端开发者
> **核心内容**：先一句话定义 IPTV → 建立单播/组播/广播直觉 → IGMP 报名机制 → 一条直播流全链路 → EPG 与 M3U 数据格式 → 组播的出口转内销
> **本篇主线**：先记住一句话——**IPTV = 运营商在自家专用 IP 网里，用组播把电视送到你家机顶盒**。组播是命根子，先搞清楚它，后面全通了。

读完本篇，你能做到：

1. **说清三者差异**：单播 / 组播 / 广播分别是什么，为什么电视直播离不开组播
2. **解释换台原理**：换台 = 退一个组播组 + 进另一个组播组（IGMP Leave + Join）
3. **走通全链路**：从内容源编码 → 头端分发 → 光猫/路由器 → 机顶盒，逐段说出发生了什么
4. **搞懂数据格式**：M3U 频道列表和 XMLTV 节目单靠什么对上号（tvg-id），EPG 为什么不显示
5. **理解落地玩法**：组播出不了公网，出口必须"转成 HTTP"，知道这一刀切在哪

## 一、先用一句话定义 IPTV

**IPTV（Internet Protocol TV）= 运营商在自家专用 IP 网络里，通过组播把电视信号送到你的机顶盒。**

这句话里的三个关键词，每个都别绕过去：

- **自家专用 IP 网**：网络是运营商自己的，想保证画质就能保证（QoS），网内每个节点都能配合做组播。这是 IPTV 和互联网电视最本质的区别——**网络归属**。
- **组播**：直播的带宽解决方案，本篇文章的主角。
- **机顶盒**：专为电视设计的解码终端，接收组播、硬解、输出 HDMI。

> 一句话：**IPTV 是"运营商的电视"，OTT 是"互联网的电视"，有线电视是"广电的电视"。** 区别不在"用什么协议"，而在"网络是谁的"。

## 二、建立直觉：单播 / 组播 / 广播

网络里只有三种向观众送数据的玩法：

| 方式 | 一句话 | 比喻 |
|------|--------|------|
| **单播 Unicast** | 一对一的传输，一个人看一份，人越多服务器发的越多 | 点外卖：一个客人做一份餐 |
| **组播 Multicast** | 一对多的传输，**只发一份**，网络在有观众的分叉点才复制 | 发报纸：印一次，送报车只进有订户的小区 |
| **广播 Broadcast** | 一对全的传输，不管你要不要都塞给你 | 广场大喇叭 |

单播和组播的差距，算一笔账就懂了。假定 10 万人同时在看央视一套（1080p ≈ 4 Mbps/路）：

- **单播**：服务器得发 10 万份 = 400 Gbps。观众越多，带宽越爆炸。互联网电视（OTT）就活在这么贵的模式里。
- **组播**：内容源只发 1 份，沿途路由器/交换机在"有人要看"的分叉点复制一份。**消耗的带宽只和"有多少个频道在播"有关，和"有多少人在看"无关**。10 万人看和 1 万人看，网络开销一样。

广播和组播一样"一源多发"，但关键区别在**发不发**：

- 广播：**发出去，网段里所有人都被迫收到**，即使没人想看（所以平常不用于正经传输）。
- 组播：**先报名，后接收**。网络只在"报名了的"链路上复制，没人看的频道在网络里不占带宽。

> 记住这句：**广播是"我塞给你"，组播是"你要我才给"。** 正因为组播有这个"先加入、后接收"的机制，IPTV 才养得起电视直播——这是整篇的根基。

**但那句话还有个尾巴**：组播要求从内容源到你家的**每一跳网络设备都支持组播**（沿途复制）。公共互联网不支持、也不愿意路由组播，所以组播只能活在运营商自建的专网里。这就是 IPTV 必须用运营商专网的第二个理由。

## 三、报名机制：IGMP（组播的会员制）

前面说"你要我才给"——"要"这个动作，就是机顶盒向最近的路由器喊话。管理这个喊话的协议叫 **IGMP**。

一句话版本，两个字就够了：

- **加入（IGMP Join）**：机顶盒说"我要看 239.1.1.1 这个频道"，路由器记下来，开始往这个方向的端口复制数据；
- **退出（IGMP Leave）**：机顶盒说"我不看了"，路由器立刻停止复制；
- 路由器还会定期发"查询"：**"还有人看 239.1.1.1 吗？"** 没人应，就把这组的复制停掉，释放带宽。

**换台的底层动作 = 退掉旧频道的组播组 + 加入新频道的组播组**，各是一条 IGMP 消息。你看电视时按遥控器"换台"，机顶盒做的就是这两件事。

> 范围提示：IGMP 只管**机顶盒↔路由器**这一跳；路由器**之间**的组播路径由另一套协议（PIM，常用 PIM-SM 稀疏模式）决定。后端开发理解到"IGMP 报名、PIM 组路"就够了。

**组播地址长什么样**：224.0.0.0/4 是组播地址段（D 类地址）。业界约定，239.0.0.0/8 用于本地/企业网内的"管理域组播"，IPTV 频道常见做法就是**一个频道 = 一个 239.x 组播地址 + 端口**：

```
央视一套 → udp://239.1.1.1:5000
央视五套 → udp://239.1.1.2:5000
湖南卫视 → udp://239.1.2.1:5000
```

## 四、全链路：一条直播流从内容源到家

把上一节的零件拼起来，一条直播流的完整旅程：

```
卫星/演播室信号          （专业广播信号 SDI/HD-SDI）
   │
   ▼
编码器           实时编码为 H.264/H.265 + AAC，打包成 TS 流
   │
   ▼
IPTV 头端（播出中心）   把每个频道推到一个组播地址，一直推
   │                  频道1 → 239.1.1.1:5000，频道2 → 239.1.1.2:5000
   ▼
运营商城域/接入网       组播数据只在"有人看的频道 + 有人看的方向"上复制
   │                  （沿途是交换机、OLT、光猫）
   ▼
你家机顶盒            1. 开机先 IGMP Join 加入要看的频道
                     2. 收 UDP 数据，解出 TS 流里的视频/音频/节目信息
                     3. 硬解芯片解码 → HDMI → 电视屏幕
```

四个关键认知：

1. **电视频道是"常开的流"**：只要有人看，头端就一直往那个组播地址发数据；没人看了，路由器查询后自动掐掉。
2. **"加入组播组"≠"自动收到数据"**：你加入后，沿途每一跳才明白"这里有观众"，开始往你的方向复制。
3. **TS 里不只有画面**：TS（MPEG 传输流）除了视频音频，还内置着一张张元数据表——频道号/频道名（SDT）、正在播的节目信息（EIT）。机顶盒的 EPG 节目单，很多就来自流里随身带的 EIT 表。
4. **UDP 无重传**：组播直播走 UDP，丢包不会重发，画面会短暂花屏/卡顿后自己恢复。这是 IPTV 和网页视频的最大体验差异之一。

## 五、点播与时移：为什么这里不用组播

组播只对**一群人在同一时刻看同一份内容**（直播）有价值。而点播（VOD）每个人看的片子都不一样，彼此没有共享可言，天生只能**单播**——走 HTTP（HLS/DASH），和 OTT 平台完全一样。所以 IPTV 实际是**"直播走组播 + 点播走 HTTP"双轨并存**。

另外你还会在 IPTV 里碰到**时移（回看）**：把正在播的直播存成"录好的片"，让你回放、暂停、拖进度条。它本质上是把直播变成点播——所以同样走单播，一份一份喂给每个观众。

## 六、三张面孔：IPTV vs OTT vs 有线电视

| 维度 | 有线电视 | **IPTV** | **OTT**（爱奇艺/腾讯等） |
|------|---------|---------|-------------------------|
| 网络归属 | 广电同轴专用网 | 运营商专用 IP 网 | 公共互联网 |
| 直播传输 | 广播（所有频道一股脑发给你） | **组播（看哪个传哪个）** | HTTP 单播（每观众一份） |
| 画质保障 | 物理线路独占 | QoS + 组播，稳定 | Best-effort，看网络脸色 |
| 终端 | 机顶盒 | 机顶盒 | 手机/电视 App、浏览器 |
| 换台速度 | 极快（本地切） | 快（IGMP 换组） | 慢（重新拉一条 HTTP 流） |
| 收费 | 月租 | 月租（常与宽带捆绑） | 会员订阅 |

盯住对角线看：**网络是自己的 → 能用组播 + 能保画质；网络是公共的 → 只能单播 + 尽力而为。** 这也是你感觉 OTT 的"频道"更像 App、IPTV 才像"电视"的根本原因。

## 七、数据格式：EPG 与 M3U

机顶盒/播放器要正常服役，还靠两份数据：**节目单（EPG）** 和 **频道列表（M3U）**。

### 7.1 EPG：电视节目时刻表

EPG（Electronic Program Guide）= 电子节目指南，告诉用户"现在几点，这个频道在播什么"。IPTV 常用的标准格式是 **XMLTV**——一份 XML，`<channel>` 定义频道，`<programme>` 定义一次节目：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<tv>
  <channel id="CCTV1">
    <display-name lang="zh">CCTV-1 综合</display-name>
  </channel>
  <programme start="20260729140000 +0800" stop="20260729150000 +0800" channel="CCTV1">
    <title lang="zh">新闻联播</title>
  </programme>
</tv>
```

### 7.2 M3U：频道的"通讯录"

M3U 是频道列表的事实标准——每条记录一个频道名和它的流地址：

```m3u
#EXTM3U

#EXTINF:-1 tvg-id="CCTV1" tvg-name="CCTV-1 综合" group-title="央视",CCTV-1 综合
udp://@239.1.1.1:5000

#EXTINF:-1 tvg-id="CCTV5" tvg-name="CCTV-5 体育" group-title="央视",CCTV-5 体育
udp://@239.1.1.2:5000
```

### 7.3 两块拼图靠 tvg-id 对上号——EPG 不显示的钥匙

上面 M3U 每条里的 **`tvg-id="CCTV1"` 必须和 XMLTV 里 `<channel id="CCTV1">` 的 id 一字不差**。播放器靠这个 id 把"画面频道"和"节目单"关联起来：

- 对上了 → 换到该频道，旁边显示节目名；
- 对不上 → 画面正常，但**节目单永远是空的**。

> 一句话：**M3U 管"有哪些频道、地址在哪"，XMLTV 管"每个频道在播什么"，tvg-id 是两者之间的主键。** 排查 EPG 不显示，第一步就是去比 tvg-id 是否完全一致。

## 八、出口转内销：组播出不了公网，就转成 HTTP

组播活在运营商网内，而绝大多数用户其实在互联网上（手机、平板、电脑，甚至家庭中兴起的各类盒子）。所以"把 IPTV 变成互联网能播的内容"是常态工程：**在网内接住组播流，转成 HTTP（HLS / HTTP-FLV），再走普通单播分发**。

```
运营商组播 239.1.1.1:5000
   → ffmpeg / MediaMTX 接收并转成 HLS
   → 互联网 CDN / 服务器
   → 手机、电脑、电视盒子 App
```

一条命令就是全部（`-c copy` 不转码，直接改封装）：

```bash
ffmpeg -i "udp://@239.1.1.1:5000" -c copy \
  -f hls -hls_time 4 -hls_list_size 10 -hls_flags delete_segments \
  /var/www/hls/cctv1/index.m3u8
```

频道多就交给现成的网关——MediaMTX 天然支持"组播源 → 多协议输出"（见 [第 16 篇](../02-工程实践优化/16-MediaMTX实战.md)）：

```yaml
# mediamtx.yml：每个频道一个 path，source 指向组播地址
paths:
  cctv1:
    source: udp://239.1.1.1:5000
  hunan:
    source: udp://239.1.2.1:5000
```

顺便记住这条手感：**转出的 HLS `hls_time` 决定用户换台/点开出画的延迟**——4 秒切片 ≈ 4-8 秒才出画，要快就切到 2 秒，或改用 HTTP-FLV/WebRTC（参见本系列的 [第 21 篇](../02-工程实践优化/21-低延迟播放完整方案.md)）。

## 本篇小结

| 问题 | 一句话答案 |
|------|-----------|
| 什么是 IPTV？ | 运营商在自家专用 IP 网里、用组播传输的有线电视 |
| 组播为什么省带宽？ | 一份数据多人共享，开销按频道数算、不按观众数算 |
| 频道怎么才能收到？ | 机顶盒先 IGMP Join 加入组，网络才开始沿线复制 |
| 换台是什么？ | Leave 旧组 + Join 新组，两条 IGMP 消息 |
| 点播/时移为什么走单播？ | 每个人看的内容不同，没有共享可占 |
| 手机/电脑怎么看 IPTV？ | 组播出不了公网，服务端先转成 HLS/HTTP-FLV 的 HTTP 单播 |
| EPG 节目单哪来的？ | XMLTV 格式，靠 tvg-id 和 M3U 频道对上号 |

## 动手实践

> 不必有运营商网络——**你自己在这台电脑上搭一套迷你 IPTV 网**：ffmpeg 当"头端/编码器"，ffplay 当"机顶盒"，把"组播"这个抽象概念变成眼睛能看到的现象。四个练习由浅入深。

### 练习 1：组播"一源多收"——看到一份数据被两台"机顶盒"同时收到

```bash
# ① 准备一个 2 分钟的测试视频（已有视频文件可跳过）
ffmpeg -f lavfi -i testsrc2=duration=120:size=1280x720:rate=25 -pix_fmt yuv420p sample.mp4

# ② 「头端」：把一个频道以 TS 流发到组播地址 239.1.1.1:5004
ffmpeg -re -stream_loop -1 -i sample.mp4 -c copy -f mpegts udp://239.1.1.1:5004

# ③ 两个「机顶盒」同时加入这个组（开两个终端分别执行）
ffplay -window_title "STB1" udp://@239.1.1.1:5004
ffplay -window_title "STB2" udp://@239.1.1.1:5004
```

**你会看到**：②在跑、③两个窗口同时在播——**同一份数据，被两台"机顶盒"独立收到**。现在关掉 STB2，STB1 完全不受影响继续播。"加入才发、退出即停"就是组播的会员制，也正是机顶盒开机/关机/换台时的网络行为。这就是你和"组播"之间的手感。

> **踩坑必读**：组播默认会走"默认出口网卡"，本机演示要绑到 loopback 才稳。发送端和接收端都加 `?localaddr=127.0.0.1`：
> `udp://239.1.1.1:5004?localaddr=127.0.0.1`（发送）、`udp://@239.1.1.1:5004?localaddr=127.0.0.1`（接收）。
> 若你的环境仍收不到，说明主机/系统禁了组播，退一步把地址换成单播 `udp://127.0.0.1:5004` 做演示——项目真正落在运营商网络时，同样的命令对着真实组播地址跑即可。

### 练习 2：换台 = 退一组、进一组

再开一个"频道 2"，用一个不同画面方便肉眼区分：

```bash
# 「头端」频道 2：用彩条发生器直接当信号源，发到另一个组播地址
ffmpeg -re -f lavfi -i smptebars=duration=120:size=1280x720:rate=25 \
  -c:v libx264 -preset ultrafast -f mpegts "udp://239.1.1.2:5004?localaddr=127.0.0.1"
```

然后在"机顶盒"里来回切：

```bash
ffplay "udp://@239.1.1.1:5004?localaddr=127.0.0.1"   # 频道 1（testsrc2 测试卡画面）
# Ctrl+C 退出，再执行：
ffplay "udp://@239.1.1.2:5004?localaddr=127.0.0.1"   # 频道 2（彩条）
```

**你会理解**：所谓换台，本质就是退掉频道 1 的组播组、加入频道 2 的组播组——在真实网络里这两步就是 IGMP Leave + Join。再配合前面的 tcpdump（`sudo tcpdump -i lo 'udp and dst 239.1.1.1' -c 5`），你能亲眼看到数据包的目标地址是 D 类组播地址，payload 是约 1316 字节（7 个 TS 包）的一段数据。

### 练习 3：出口转内销——把"运营商频道"转成浏览器能播的 HLS

```bash
# 接住组播流，切成 HLS 供互联网设备播放（-c copy 不重编码）
ffmpeg -i "udp://@239.1.1.1:5004?localaddr=127.0.0.1" -c copy \
  -f hls -hls_time 2 -hls_list_size 10 -hls_flags delete_segments \
  /tmp/iptv/cctv1/index.m3u8

# 起个静态服务器，用 VLC / 浏览器（hls.js 类播放器）打开
cd /tmp/iptv && python3 -m http.server 8080
# → http://localhost:8080/cctv1/index.m3u8
```

**你会得到手感**：组播只活在"网内"，任何"出网播放"都必须先转成 HTTP 单播——这就是运营商/第三方把 IPTV 内容搬到互联网产品上的那道必经工序（对应正文第八节）。顺便试一下把 `-hls_time` 从 2 改成 8 再播，感受换台/首帧出画明显变慢。

### 练习 4：用 Go 让播放器"显示节目单"（tvg-id 对上号的复现）

```go
// XMLTV 节目单：M3U 的 tvg-id 与 XMLTV 的 channel id 对上，就能输出"频道此刻在播什么"
package main

import (
	"encoding/xml"
	"fmt"
)

const xmltv = `<?xml version="1.0" encoding="UTF-8"?>
<tv>
  <channel id="CCTV1"><display-name lang="zh">CCTV-1 综合</display-name></channel>
  <programme start="20260729140000 +0800" stop="20260729150000 +0800" channel="CCTV1">
    <title lang="zh">新闻联播</title>
  </programme>
</tv>`

type Channel struct {
	ID   string `xml:"id,attr"`
	Name string `xml:"display-name"`
}
type Programme struct {
	Channel string `xml:"channel,attr"`
	Start   string `xml:"start,attr"`
	Stop    string `xml:"stop,attr"`
	Title   string `xml:"title"`
}
type TV        struct { Channels []Channel `xml:"channel"`; Programmes []Programme `xml:"programme"` }

func main() {
	var tv TV
	if err := xml.Unmarshal([]byte(xmltv), &tv); err != nil {
		panic(err)
	}
	now := "20260729150000" // 模拟"当前时间"，格式与 EPG 相同
	for _, c := range tv.Channels {
		for _, p := range tv.Programmes {
			if p.Channel == c.ID && p.Start <= now && now < p.Stop {
				fmt.Printf("%s 现在播《%s》\n", c.Name, p.Title)
			}
		}
	}
}
// 输出：CCTV-1 综合 现在播《新闻联播》
// 把 M3U 的 tvg-id 从 "CCTV1" 错写成 "CCTV1zjcwms"，再跑一次——节目单就为空了。
```

**你会踩到**：`p.Channel == c.ID` 匹配不上就是 EPG 空白的最常见根因（正文 7.3）。你在真实项目里"接入 IPTV 数据源"做的事，就是把这两份数据拉下来、对齐、提供给播放端。

## 常见问题排查

| 现象 | 可能原因 | 解决方法 |
|------|---------|---------|
| 组播收不到数据 | 所在网络不支持组播 / 未加入组；家庭宽带一般不做组播 | 本机演示加 `?localaddr=127.0.0.1`；生产环境确认沿途交换机/路由器开了 IGMP |
| 换台/点开出画慢（3-8 秒） | HLS `hls_time` 切片大，或组播→HTTP 转换链路延迟 | 转出端 `hls_time=2`，或改用 HTTP-FLV / WebRTC |
| 画面偶尔花屏/顿一下又恢复 | 组播走 UDP 无重传，丢包即丢帧 | 组播对"最后一公里"质量敏感；关键内容可在端侧加纠错或允许重传单播 |
| EPG 节目单空白 | M3U 的 tvg-id 与 XMLTV 的 channel id 不一致 | 用脚本校验两侧 id 集合一致（练习４已演示） |
| 多台电视同时看不同频道就卡 | 组播被"翻译"成了多份单播（IGMP 代理没生效） | 确认光猫/路由器开启了 IGMP Proxy，而非逐台单播转发 |
| 4K 频道缓冲 | 4K 单播流每路约 15 Mbps，或组播路径丢包 | 检查实际带宽；组播带宽与频道数成正比，先查丢包率 |

## 术语表

| 术语 | 英文 | 一句话说明 |
|------|------|-----------|
| 单播 / 组播 / 广播 | Unicast / Multicast / Broadcast | 一对一 / 按需一对多 / 无差别一对全 三种传输模型 |
| IPTV | Internet Protocol TV | 运营商在自己 IP 网里用组播送的电视 |

| IGMP | Internet Group Management Protocol | 机顶盒↔路由器的组播"报名"协议（Join/Leave/查询） |
| PIM | Protocol Independent Multicast | 路由器之间的组播路径协议（常见 PIM-SM） |
| TS | MPEG Transport Stream | 直播的容器格式，视频/音频/元数据装在同一流里传输 |
| EPG / XMLTV | Electronic Program Guide | 电子节目指南；XMLTV 是存储节目单的 XML 标准 |
| M3U | M3U Playlist | 频道列表格式，IPTV 频道列表事实标准 |
| tvg-id | — | M3U 与 XMLTV 之间的主键，两边对不上节目单即空白 |
| STB | Set-Top Box | 机顶盒 |
| VOD / TSTV | Video on Demand / Time-Shifted TV | 点播 / 时移（直播存储回看） |
