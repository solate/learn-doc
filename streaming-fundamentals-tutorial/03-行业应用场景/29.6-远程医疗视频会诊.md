# 远程医疗视频会诊

> **适合读者**：互联网医疗、远程会诊平台、医院信息化方向的后端工程师  
> **前置知识**：[第 12 篇：WebRTC 协议栈详解](../01-底层技术基础/12-WebRTC协议栈详解.md)、[第 29 篇：视频会议技术架构](29-视频会议技术架构.md)、[第 22.5 篇：流媒体安全](../02-工程实践优化/22.5-流媒体安全鉴权防盗链与DRM.md)  
> **核心问题**：既要"看得清、绝不能掉线"，又要"必须留证、严格保护隐私"——两组方向相反的要求如何同时满足？

---

## 一、远程医疗不是"视频会议加个白大褂"

读完本节，你能向产品方解释清楚医疗视频和普通会议的三个本质差异。

技术上远程会诊确实大量复用视频会议的能力（第 29 篇），但把它当"会议项目"做会栽在三个坑里：

| 维度 | 普通视频会议 | 远程医疗会诊 |
|------|-------------|-------------|
| **可靠性** | 掉线重连即可接受 | 一次专家会诊约了三方专家 40 分钟，**中断即事故** |
| **录制** | 可选功能，用户可拒绝 | **法定留痕义务**：诊疗过程需可追溯（依据卫健委互联网诊疗管理相关规定），拒绝录制 = 会诊无效 |
| **隐私等级** | 一般个人信息 | 患者影像属于**敏感个人信息**：泄露有直接法律后果（数据安全法/个人信息保护法） |

一句话总结：**会议系统优化的是"体验"，医疗系统优化的是"不出事"**。这个定位差异决定了后面每一节的取舍。

> 本章只讲技术架构与工程取舍。医疗业务合规的具体要求（互联网诊疗资质、执业范围、病历管理）随监管政策演进，落地前以当时有效的法规和医院合规部门意见为准——工程师的职责是把"留痕、加密、审计"这些技术能力准备好。

## 二、三类业务形态与技术选型

读完本节，你能按业务形态直接套用对应的技术方案。

远程医疗不是单一场景，至少三类形态的延迟、分辨率、接入方式完全不同：

```
形态 A：轻问诊（1v1）
  患者手机 ←→ 医生工作台            WebRTC P2P，180s 内的短会话
  主要是"看气色、问情况"，720p 足够

形态 B：多方专家会诊（3-9 方）
  患者端 + 本地医生 + 3-5 位外地专家   SFU 房间（第 29 篇）
  1080p 起步、全程录制、证据链水印

形态 C：手术示教 / 远程指导
  手术室（术野摄像机 4K、内镜、超声）  采集卡/编码器 → RTSP/SRT 推流
  → 示教室大屏 / 专家端              延迟 < 500ms，分辨率优先于帧率
```

| 维度 | A 轻问诊 | B 多方会诊 | C 手术示教 |
|------|---------|-----------|-----------|
| 拓扑 | P2P | SFU | 单向推流（RTSP/SRT）+ 语音回传 |
| 延迟 | < 300ms | < 500ms | 画面 < 500ms，音频指导 < 200ms |
| 分辨率 | 720p | 1080p | 4K 术野 / 1080p 内镜 |
| 录制 | 按平台策略 | **必须** | **必须** |
| 最大风险 | 掉线 | 录像管理失控 | 画质不足误判 + 掉线 |

形态 B、C 都有"一路特殊的流"——形态 B 是患者（可能卧床、手持设备），形态 C 是医疗设备视频源，第三节专门讲后者。

## 三、医疗影像源接入：摄像头之外的"摄像头"

读完本节，你能为手术室和检查设备设计正确的视频接入方案，并分清 DICOM 与流媒体的边界。

形态 C 的视频源不是 USB 摄像头，而是**本身带 HDMI/SDI 输出的医疗设备**：

```
术野摄像机（4K）──┐
内窥镜主机 ────────┤ HDMI/SDI ──→ 硬件编码器 ──→ SRT/RTSP 推流 ──→ 流媒体集群
超声主机 ──────────┘（手术室侧）    （H.265 硬编码）              │
                                                                  ├── 示教室大屏（LL-HLS/RTC）
                                                                  ├── 专家端（WebRTC）
                                                                  └── 录制服务（留证）
```

为什么必须用硬件编码器而不是软件 + 采集卡凑合：

1. **手术室不能进"通用电脑"**：无尘消毒环境、设备准入，一台嵌入式编码器（或设备自带推流模块）才是能进手术室的形态。
2. **4K 术野画面对分辨率极度敏感**：缝合、止血的细节判断依赖画面，H.265 4K 硬编码是底线，软编占满 CPU 且丢帧。
3. **弱网用 SRT**（第 9 篇）：医院上行带宽不总是可靠，SRT 的 ARQ 重传在 2-5% 丢包下保持画面完整，RTMP 在同样网络下早就花屏。

**DICOM 与流媒体的边界**（容易混的两个体系）：

| | DICOM（医学数字成像通信） | 流媒体（RTSP/SRT/WebRTC） |
|---|---|---|
| 用途 | **诊断级**影像（CT/MR/超声存档） | **交流级**画面（示教、会诊看一眼） |
| 画质 | 无损/诊断级压缩，可调窗（灰度增强） | 有损压缩，够看即可 |
| 系统 | PACS（影像归档与通信系统） | 流媒体服务器 |
| 结论 | **不要试图用流媒体传诊断影像，也不要用 PACS 做示教**——会诊中需要调阅患者历史 CT，走 PACS/Web 查看器嵌入，与视频会诊窗口并列展示 | |

## 四、隐私与留痕：必须录，但只能特定人看

读完本节，你能设计"录制即证据"的完整证据链，并处理端到端加密与云端录制的天然矛盾。

这是远程医疗区别于一切其他场景的核心章节。要求一：**必须录制**（留痕）；要求二：**严格限制访问**（隐私）。两者叠加意味着：录像的**每一秒访问都要可审计**。

### 证据链水印

录像画面叠加不可擦除的取证信息，逐帧嵌入：

```
┌──────────────────────────────────────┐
│ [画面]                                │
│                                       │
│  会诊ID: C20260929-017                │  ← 录像与业务记录关联的锚点
│  张医生(心内科) 李医生(影像科)          │  ← 在场人员（工号+科室）
│  2026-09-29 10:32:15 (+08)            │  ← 帧级时间戳（NTP 校准）
│                          患者ID: P***482│ ← 患者脱敏显示
└──────────────────────────────────────┘
```

水印在**录制服务的合成阶段**烧进画面（FFmpeg `drawtext`/`drawbox` 滤镜），而不是前端叠加——前端叠加可以被录屏绕过，服务端烧录不能。

### 录像的生命周期管理

```
录制 → 加密存储 → 授权访问 → 审计 → 到期销毁
  │        │          │         │        │
  水印烧录  对象存储    最小授权原则  每次访问   保留期满足
  双轨录制  服务端加密  (医患关系链   全量日志   法规要求后
          + 密钥分级   内的指定人)   含截图      到期硬删除
```

工程要点：

1. **存储加密 + 密钥分级**：录像用服务端加密（对象存储 SSE 或应用层 AES-256，见[第 22.5 篇](../02-工程实践优化/22.5-流媒体安全鉴权防盗链与DRM.md)），取回密钥需要二次授权——防止"有存储读权限的运维"就能看患者录像。
2. **访问即审计**：谁、何时、看了哪段录像（精确到时间段），全量记录；患者有权查询谁看过自己的会诊录像（个人信息保护法要求的可追溯）。
3. **到期硬删除**：保留期限是策略问题（通常"病历级"保存年限），但删除必须是硬删除 + 密钥销毁，不是"界面上不可见"。

### 端到端加密与云端录制的矛盾

WebRTC 的 DTLS-SRTP 是端到端加密（第 12 篇），但**云端录制要求服务端能解密**——鱼与熊掌不可兼得。工程上的取舍：

| 方案 | 隐私 | 录制 | 适用 |
|------|------|------|------|
| SFU 中转 + 服务端录制（SRTP 到 SFU 解密） | 服务端可信边界内 | ✅ | **形态 B 会诊的主流选择**：信任边界 = 医院控制的机房/私有云 |
| 真·端到端加密（Insertable Streams） | 最高 | 各端本地录制再上传 | 高敏场景（心理治疗类），代价是丢端即丢证 |
| 患者侧知情提示 + 画面脱敏选项 | 中 | ✅ | 问诊类：患者可关闭摄像头改纯音频 |

> 结论：**绝大多数会诊选方案一，把工程重心放在"可信边界的加固 + 审计"上，而不是追求营销意义上的端到端**——医疗的法律要求是"可追溯"，不是"谁都解不开"。

## 五、可靠性：会诊不允许"掉线重来"

读完本节，你能设计一条"逐级降级但会诊不中断"的保障链，并落地会前网络预检。

专家时间按分钟计费，会诊中断等于三方白等。可靠性设计分**会前**和**会中**两段：

### 会前：网络质量预检（预约成功后自动执行）

```javascript
// 入会前 30 秒探测：直接对 SFU 发起一次 ICE + 短推拉流采样
async function preflightCheck(sfuUrl) {
    const stats = await probeNetwork(sfuUrl); // RTT、丢包、抖动、可用码率
    const report = {
        rtt: stats.rtt,           // 期望 < 100ms
        packetLoss: stats.loss,   // 期望 < 3%
        jitter: stats.jitter,     // 期望 < 30ms
    };
    if (report.rtt > 200 || report.packetLoss > 8) {
        return { ok: false, advice: "当前网络不建议视频会诊，建议切换 WiFi 或准备电话兜底" };
    }
    return { ok: true, report };
}
```

预检结果随预约记录入库：不达标时**提前 30 分钟通知患者换网络**，好过会诊开始后现场救火。

### 会中：降级链 + 不对称保障

```
网络恶化（getStats 连续 N 个采样超阈值）
    │
    ▼ 逐级降级（原则同第 29.5 篇，但医疗侧有两点不同）
  ① 视频降档 → 音频优先（医生的话一个字都不能丢）
  ② **医生端画质保底 360p，患者端可降到纯音频**
     （不对称：医生要看患者/影像，患者听清医嘱即可）
  ③ 视频中断 → 音频桥（电话拨入会议室）
  ④ 全中断 → 主持人转电话会议，会诊记录补记"网络中断改电话"
```

会中监控与告警：会议服务端对每路流做质量采样（丢包/RTT/分辨率），**连续 10 秒劣质自动告警到会务支持人员**（不是只给用户看个"网络差"图标）——医疗场景要求"有人盯着的可靠性"。

## 六、与院内系统集成

读完本节，你能设计会诊室从预约到归档的完整生命周期。

远程医疗平台不是孤立系统，会诊记录必须回到医院的病历体系：

```
预约排班（HIS 对接）
    │ 生成会诊单：患者、参与专家、时间
    ▼
会前 30min：自动开通
    ├── 创建 RTC 房间 + 逐人签发入会 Token（短时效，见 22.5 篇）
    ├── 执行双方网络预检
    └── 预拉取患者历史 DICOM 影像到会诊界面（PACS 调阅）
    ▼
会诊进行（10:00-10:40）
    ├── 媒体：SFU 房间（形态 B）/ RTSP 推流（形态 C）
    ├── 录制：服务端双轨录制 + 证据链水印
    └── 事件：入会/离会/网络事件全部入库
    ▼
会诊结束：自动收尾
    ├── 录制转码 → 加密落对象存储 → 密钥入库（分级授权）
    ├── 生成结构化会诊记录（Markdown/表单）→ 归档 EMR
    ├── 录像索引与病历关联（会诊ID 贯穿两套系统）
    └── 房间销毁、Token 全部过期
    ▼
事后
    ├── 复诊调阅：授权医生按会诊ID 检索，看录像/读记录
    └── 审计：访问日志对外可查（患者知情）
```

工程要点：

1. **会诊 ID 是贯穿所有系统的主键**：RTC 房间、录像文件、水印、病历记录、审计日志全部用它关联——事故回溯时能"一键拉齐"。
2. **房间的创建与销毁是自动的**，不依赖人工点击：预约驱动（定时任务/消息驱动），医生无感知。Token 在会诊结束后台强制过期（防止房间被复用）。
3. **接口形态**：HIS/EMR 多为院内既有系统，对接走其提供的标准接口（HL7/FHIR 或数据库视图），**不要让流媒体系统直接写病历库**——会诊平台只交付"结构化记录 + 录像索引"两样产物。

### 练习3：会前网络预检（Go 后端侧阈值判断）

```go
// 客户端上报 getStats 采样，后端给出是否建议视频会诊的结论
func (s *PreflightService) Evaluate(ctx context.Context, r *ProbeReport) *PreflightResult {
    if r.RTTMs > 200 || r.PacketLossPct > 8 || r.JitterMs > 50 {
        log.Warn().Interface("report", r).Msg("网络预检不达标")
        return &PreflightResult{OK: false,
            Advice: "当前网络不建议视频会诊：建议切换网络或启用电话兜底"}
    }
    return &PreflightResult{OK: true}
}
```

**预期输出**：构造三组输入（RTT 80ms/丢包 1% → 通过；RTT 250ms → 拒绝并给出建议；丢包 10% → 拒绝）验证阈值分支——第五节预检逻辑的后端形态。

## 常见问题排查

| 现象 | 可能原因 | 解决方法 |
|------|---------|---------|
| 会诊录像回放黑屏 | 录制服务拉流用了子码流/分辨率配错 | 检查录制源配置（形态 B 录 SFU 侧，形态 C 录编码器主码流） |
| 水印在回放中缺失 | 前端叠加方案被绕过（录的是原始流） | 水印必须在录制合成阶段烧录，不接受前端叠加 |
| 术野画面糊、专家无法辨认组织 | 码率给了帧率（按直播参数配） | 示教流参数：分辨率优先、H.265、4K 8-16Mbps、帧率 25fps 够用 |
| 手术室推流偶发花屏 | 医院上行网络丢包，RTMP 无重传 | 换 SRT（latency 300-800ms），见第 9 篇 |
| 会诊结束 Token 仍可入会 | Token TTL 设成了 24h 默认值 | Token 过期时间绑定会诊排班结束时间 + 15min 缓冲 |
| 录像被无关人员访问 | 对象存储桶策略过宽（域内可读） | 桶私有 + 取回走业务层授权（医患关系校验）+ 访问审计 |
| PACS 影像调阅卡顿 | 会诊时才去拉全量 DICOM | 预约成功后预取当次需要的影像序列到会诊工作台 |
