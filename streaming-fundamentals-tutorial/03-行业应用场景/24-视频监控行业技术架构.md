## 二、设备形态演进：从 DVR 到 NVR 到云平台

读完本节，你能理解"编码位置"的迁移是监控行业架构演进的主线，以及为什么 IP 摄像头天生就是一台小流媒体服务器。

监控行业二十年的演进，本质是**编码位置从中心不断向边缘移动**的过程：

### DVR 时代（模拟监控）

```
模拟摄像头 ──同轴电缆(BNC)──→ DVR（硬盘录像机）
                                ├── 视频采集卡：模拟信号数字化
                                ├── 编码芯片：压缩为 H.264     ← 编码在这里
                                ├── 硬盘阵列：存储录像
                                └── 局域网客户端软件查看
```

- **摄像头是"哑设备"**：只输出模拟电信号（CVBS），编码、存储全部集中在 DVR 里。
- 布线用同轴电缆，传输距离 300m 内，一根线一路视频。
- 想远程看？DVR 挂在局域网，只有厂商私有客户端能连。

### NVR 时代（IP 监控，当前主流）

```
IP 摄像头（IPC）──网线(PoE 供电)──→ NVR（网络硬盘录像机）
  │ 自带编码芯片                    ├── 收流：从摄像头拉 RTSP     ← 只收不编
  │ 自带 Web/RTSP 服务              ├── 存储：RAID 硬盘阵列
  │ 输出已压缩的 H.264/H.265        └── 转发：分发给客户端
  ▼
（摄像头本身就是一台专用流媒体服务器）
```

- **编码移到了摄像头内部**：IPC = 传感器 + 编码芯片 + 嵌入式 Linux + RTSP 服务。这就是[第 7 篇](../01-底层技术基础/07-RTSP协议详解.md)说"RTSP 是摄像头拉流标准"的历史渊源——每颗 IP 摄像头出厂就跑着 RTSP 服务。
- **NVR 变成"哑管道"**：只负责收流、存储、转发，不再承担编码（这就是 DVR 与 NVR 的本质区别：**DVR 编码+存储，NVR 只存储转发**）。
- 网线 + PoE（供电走网线），交换机组网，一颗摄像头就是一个网络节点。

### 云平台时代（VSaaS，视频监控即服务）

```
边缘侧                                云端
NVR / 边缘流媒体网关                    ├── 接入集群（流媒体服务器组）
  │ 按需/事件触发出流 ──────────────→   ├── 对象存储（录像）
  │ 常驻 30 天热数据（本地兜底）          ├── AI 分析（第 35 篇）
  ▼                                    └── 多租户业务平台（Web/APP）
本地看、本地存，云端调阅、云端分析
```

云边协同的取舍由**带宽成本**决定：100 路 × 4Mbps 全量上云 = 400Mbps 专线，费用不可接受；所以边缘常驻存储 30 天热数据，云端只拉**事件片段**（AI 告警前后 30s）或**按需调阅**（用户点开哪路看哪路，见第六节按需拉流）。

| 维度 | DVR（模拟） | NVR（IP） | 云平台（VSaaS） |
|------|------------|-----------|----------------|
| 摄像头 | 模拟（哑设备） | IP（内置编码） | IP |
| 编码位置 | DVR 集中编码 | 摄像头端 | 摄像头端 |
| 存储 | DVR 本地 | NVR 本地 | 边缘热存 + 云端冷存 |
| 远程访问 | 厂商私有客户端 | 局域网/厂商云 | 任意浏览器/APP |
| 扩展性 | 受采集卡路数限制 | 加摄像头加交换机 | 近乎无限（集群扩展） |
| 典型规模 | 4-32 路 | 8-256 路 | 千路~城市级 |

> 混合形态（Hybrid DVR）同时接模拟与 IP 摄像头，存在于模拟向 IP 迁移的过渡期项目。新项目一律 IP 摄像头 + NVR/流媒体服务器，模拟设备只在做旧系统对接时会遇到。

## 三、典型技术架构

### 小型系统（< 100 路）

```
摄像头 RTSP
    ↓
MediaMTX / SRS（单节点）
    ├── HLS/FLV 分发给浏览器
    └── FFmpeg 录制到本地磁盘

Go 后端（管理录像、设备、用户）
PostgreSQL（元数据）
浏览器前端（分屏播放）
```

推荐技术：
- 流媒体：MediaMTX（配置简单，支持 RTSP/RTMP/HLS/WebRTC）
- 录像：FFmpeg `-f segment`
- 存储：NFS 共享磁盘（>= 4TB SAS）

### 中型系统（100-1000 路）

```
摄像头集群
    ↓
[接入节点 × N]（每节点处理 50-100 路）
    │ 视频流不经过主服务器
    ↓
[MediaMTX 集群] ← 级联
    │
    ├── [录像存储集群]（分布式NAS / MinIO）
    └── [实时分发] → CDN / Nginx 反向代理
    │
[Go 主控服务]（统一管理）
[PostgreSQL + Redis]
[Prometheus + Grafana 监控]
```

### 大型系统（1000+ 路，城市级）

```
[省级/市级数据中心]
    │ GB28181 联网
    ├── 平台层（EasyNVR / 海康 VMS / 视频云平台）
    └── 应用层（GIS 地图定位 + AI 分析 + 统一门户）

[区县节点]
    │ GB28181 / SIP
    └── [NVR 录像机] ← 摄像头接入
```

## 四、双码流机制：主码流与子码流

读完本节，你能理解"一颗摄像头同时输出两路流"为什么是监控系统的第一优化杠杆——多分屏、移动端、带宽、存储全部由它决定。

### 概念

IP 摄像头**默认同时输出两路（部分型号三路）已编码的流**，共用一个传感器，分辨率和码率不同：

| 流 | 典型参数 | 用途 |
|----|---------|------|
| **主码流**（Main Stream） | 1080p/4K，2-8Mbps，H.265 | 录像存储、单路详情查看、AI 分析 |
| **子码流**（Sub Stream） | D1(704×576)/480p，0.3-1Mbps | 多分屏预览、移动端、低带宽链路 |

```
            ┌─ 主码流 1080p 4Mbps ──→ 录像 / 单路放大 / AI
IPC 摄像头 ─┤
            └─ 子码流 D1 0.5Mbps ──→ 16 分屏预览 / 手机 APP
```

### 为什么这是第一优化杠杆

算一笔账：16 分屏预览（[第 20 篇](../02-工程实践优化/20-多分屏并发性能优化.md)的核心场景）：

```
用主码流：16 路 × 4Mbps = 64Mbps 带宽 + 16 路 1080p 解码（浏览器软解直接卡死）
用子码流：16 路 × 0.5Mbps = 8Mbps 带宽 + 16 路 D1 解码（普通浏览器轻松）
```

第 20 篇讲的"服务端降分辨率"方案，本质就是服务端转码模拟出子码流——**如果摄像头自己有子码流，根本不需要服务端转码**，这是零成本方案。多分屏优化的优先级应该是：**先接子码流（免费），不够再上 WebCodecs 硬解（客户端），最后才是服务端转码（烧 CPU）**。

对存储同样成立：录像写主码流保证取证质量，预览走子码流；事件片段（告警前后 30s）可以再降帧率。1 路 1080p 主码流 4Mbps 存 30 天 ≈ 1.3TB，子码流 D1 0.5Mbps 存 30 天 ≈ 160GB——**存储容量规划必须按"主/子码流分别保留多少天"两个参数算**，混在一起算必然翻车。

### URL 形态

不同厂商的 RTSP 路径约定不同，接入层要按厂商适配（常见形态）：

```bash
# 通用形态：rtsp://user:pass@ip:554/...
# 海康：通道号 + 01 主码流 / 02 子码流
rtsp://admin:pass@192.168.1.64:554/Streaming/Channels/101   # 1 通道主码流
rtsp://admin:pass@192.168.1.64:554/Streaming/Channels/102   # 1 通道子码流

# 大华：subtype=0 主码流 / 1 子码流
rtsp://admin:pass@192.168.1.108:554/cam/realmonitor?channel=1&subtype=0
rtsp://admin:pass@192.168.1.108:554/cam/realmonitor?channel=1&subtype=1
```

工程实践：`cameras` 表同时存 `rtsp_url_main` 和 `rtsp_url_sub` 两个字段，预览接口返回子码流地址、详情/录像接口返回主码流地址——**切换流是业务语义（预览 vs 取证），不是播放器行为**。

| 协议 | 适用设备 | 延迟 | 特点 |

## 六、关键功能实现

### 设备在线状态检测

```go
// 定时 RTSP 探活（每30秒检查一次）
func (s *CameraService) CheckOnlineStatus(ctx context.Context, cameraID, rtspURL string) bool {
    // 用 ffprobe 尝试连接（超时5秒）
    ctx, cancel := context.WithTimeout(ctx, 5*time.Second)
    defer cancel()

    cmd := exec.CommandContext(ctx, "ffprobe",
        "-v", "error",
        "-rtsp_transport", "tcp",
        "-i", rtspURL,
    )
    err := cmd.Run()
    online := err == nil

    // 更新状态
    if err := s.repo.UpdateOnlineStatus(ctx, cameraID, online); err != nil {
        log.Error().Err(err).Str("id", cameraID).Msg("更新摄像头状态失败")
    }

    return online
}
```

### PTZ 控制（云台控制）

```go
// ONVIF PTZ 控制
type PTZCommand struct {
    Pan   float32  // 水平移动速度 -1.0 ~ 1.0
    Tilt  float32  // 垂直移动速度 -1.0 ~ 1.0
    Zoom  float32  // 缩放速度 -1.0 ~ 1.0
}

// 通过 ONVIF 发送 PTZ 命令
func (s *CameraService) SendPTZ(ctx context.Context, cameraID string, cmd PTZCommand) error {
    camera, err := s.repo.GetByID(ctx, cameraID)
    if err != nil {
        return xerr.Wrap(xerr.ErrNotFound.Code, "摄像头不存在", err)
    }

    // ONVIF PTZ ContinuousMove
    soapBody := fmt.Sprintf(`<tptz:ContinuousMove>
        <tptz:ProfileToken>%s</tptz:ProfileToken>
        <tptz:Velocity>
            <tt:PanTilt x="%.2f" y="%.2f"/>
            <tt:Zoom x="%.2f"/>
        </tptz:Velocity>
    </tptz:ContinuousMove>`, camera.OnvifProfileToken, cmd.Pan, cmd.Tilt, cmd.Zoom)

    return s.sendOnvifRequest(ctx, camera.OnvifURL, soapBody)
}
```

### 拉流策略：常拉 vs 按需

100 路摄像头，是 7×24 全部拉到服务器，还是有人看才拉？这是接入层的核心成本决策：

| 策略 | 实现 | 带宽/资源 | 首开延迟 | 适用 |
|------|------|----------|---------|------|
| **7×24 常拉** | 启动时全量拉流 | 100 路 × 4Mbps 常驻 | < 1s | 大屏有人盯、AI 常开、录像必须持续 |
| **按需拉流** | 用户请求到达时才向摄像头拉流 | 只拉被看的路 | +1-2s（拉流建立时间） | 查看率低的路（多数路一天看不了几次） |
| **事件触发** | AI/告警触发时才拉 | 最低 | +1-2s | 只关心事件、不需要巡检 |

按需拉流的实现入口：

- **MediaMTX**：path 配置 `runOnDemand`（收到播放请求时执行拉流命令）+ `sourceOnDemand`/`sourceOnDemandCloseAfter`（无人观看自动断开）
- **ZLMediaKit**：`on_stream_not_found` Hook 回调业务后端，后端调 `addStreamProxy` 动态拉流；`on_stream_none_reader` 无人观看回调（详见[第 16.5 篇](../02-工程实践优化/16.5-ZLMediaKit实战.md)）

```
用户点开 cam_42 → 播放请求到达服务器 → 流不存在？
    │ 是 → 触发按需拉流（RTSP 向摄像头建链，1-2s）
    │      → 流就绪 → 播放开始
    │      → 无人观看 30s 后自动断开与摄像头的连接
    ▼ 否（已在拉）→ 直接播放
```

> 注意与第一节架构的联动：**录像和 AI 分析需要持续流**（事件不能凭空录、检测不能凭空跑），所以真实系统通常是混合策略——重点路常拉（录像+AI）、普通路按需（预览）。把"哪些路常拉"做成业务库里的摄像头属性，而不是写死配置。

## 七、视频墙与解码上墙

读完本节，你能区分"浏览器多分屏"与"指挥中心上墙"两类需求，并为后者选对硬件方案。

### 需求差异

[第 20 篇](../02-工程实践优化/20-多分屏并发性能优化.md)解决的是**浏览器里的多分屏**（值班坐席在自己电脑上看）；而指挥中心/安保中心还有第二类需求——**把监控画面输出到物理大屏**（拼接屏、电视墙），即"上墙"：

```
                     ┌── 坐席客户端（每人一台 PC，浏览器多分屏，第 20 篇方案）
监控接入集群 ────────┤
                     └── 视频墙（整面墙的拼接大屏，1/4/9/16 宫格轮巡显示）
                              ▲
                              │ HDMI
                       解码上墙设备
```

### 两条上墙路线

| 路线 | 原理 | 优劣 | 成本 |
|------|------|------|------|
| **硬件解码器/解码矩阵** | 专用盒子拉网络流 → ASIC 硬解 → HDMI 输出到大屏 | 稳定、7×24 不死机、单盒 1-16 路；是传统安防行业的标准做法（类比[第 4 篇](../01-底层技术基础/04-硬件编解码vs软件编解码.md)的电视盒子 ASIC） | 每路几百~上千元 |
| **上墙服务器 + 软解** | 一台 GPU 服务器跑解码程序，HDMI 输出合成画面 | 灵活（任意宫格、轮巡、跨协议混源）；但软解路数受 GPU 限制，需配套保活监控 | 服务器 + 运维成本 |

选型经验：**轮巡需求强（如 64 路按 16 路一组自动轮播）选硬件方案**——轮巡意味着长期满负荷运行，专用设备比通用服务器省心；**多源混排（监控流 + GIS 地图 + 数据看板上同一面墙）选上墙服务器**。

### 与坐席端的区别

上墙流是"**输出给大屏的一路合成画面**"，与坐席客户端互不影响：坐席在自己浏览器里看哪路、PTZ 控制哪路是独立的会话；大屏通常只做显示（轮巡/固定宫格），控制权在坐席。系统设计时把"上墙"当作一种特殊的**播放端**（一路消费流的订阅者），不要让它侵入接入层的架构。

## 八、高可用设计

```
客户端请求
    │
[负载均衡 Nginx/Traefik]
    │
    ├── [Go 主控服务 A]  ─┐
    └── [Go 主控服务 B]  ─┤→ [PostgreSQL 主从]
                          └→ [Redis 哨兵集群]

流媒体层（独立集群）：
    ├── [MediaMTX 节点 1]  → 接入摄像头 1-50
    ├── [MediaMTX 节点 2]  → 接入摄像头 51-100
    └── [MediaMTX 节点 3]  → 接入摄像头 101-150
```

**故障转移**：摄像头断线自动重连（MediaMTX 内置重连）。

节点级故障：接入节点宕机时，该节点的摄像头要能漂移到其他节点——摄像头归属关系存数据库（而非节点本地配置），节点通过"认领"机制（如分布式锁 + 心跳注册）接管漂移过来的拉流任务。

## 动手实践

### 练习1：MediaMTX 多摄像头接入与健康检查
```bash
# mediamtx.yml：批量配置100台摄像头自动拉流
# paths:
#   cam_~^[0-9]+$:
#     source: rtsp://admin:pass@192.168.1.$MTX_PATH/stream
#     sourceProtocol: tcp
#     runOnNotReady: curl -X POST http://backend/api/v1/cameras/offline?id=$MTX_PATH

docker run -d --name mediamtx   -p 8554:8554 -p 9997:9997   -v $(pwd)/mediamtx.yml:/mediamtx.yml   bluenviron/mediamtx:latest

# 查询当前在线摄像头数量
curl -s http://localhost:9997/v3/paths/list |   python3 -c "import sys,json; d=json.load(sys.stdin); print('在线:', sum(1 for p in d['items'] if p['ready']))"
```
**预期输出**：`在线: N`（N 为当前有推流的摄像头数量）。

### 练习2：Go 实现摄像头在线状态同步
```go
// 定时轮询 MediaMTX API，同步摄像头状态到数据库
func (s *CameraService) SyncOnlineStatus(ctx context.Context, tenantIDs []string) error {
    resp, err := http.Get(s.mediamtxAPIURL + "/v3/paths/list")
    if err != nil {
        return xerr.Wrap(xerr.ErrInternal.Code, "查询 MediaMTX 失败", err)
    }
    defer resp.Body.Close()

    var result struct {
        Items []struct {
            Name  string `json:"name"`
            Ready bool   `json:"ready"`
        } `json:"items"`
    }
    json.NewDecoder(resp.Body).Decode(&result)

    onlineSet := make(map[string]struct{})
    for _, item := range result.Items {
        if item.Ready {
            onlineSet[item.Name] = struct{}{}
        }
    }

    cameras, err := s.repo.ListByTenantIDs(ctx, tenantIDs)
    if err != nil {
        return xerr.Wrap(xerr.ErrInternal.Code, "查询摄像头列表失败", err)
    }

    var onlineIDs, offlineIDs []string
    for _, cam := range cameras {
        if _, ok := onlineSet[cam.StreamPath]; ok {
            onlineIDs = append(onlineIDs, cam.CameraID)
        } else {
            offlineIDs = append(offlineIDs, cam.CameraID)
        }
    }

    if err := s.repo.BatchUpdateStatus(ctx, onlineIDs, 1); err != nil {
        log.Error().Err(err).Msg("批量更新在线状态失败")
    }
    if err := s.repo.BatchUpdateStatus(ctx, offlineIDs, 0); err != nil {
        log.Error().Err(err).Msg("批量更新离线状态失败")
    }
    return nil
}
```
**预期输出**：数据库中摄像头的 status 字段与 MediaMTX 实际推流状态保持同步。

### 练习4：模拟主/子码流双流接入
```bash
# 同一源模拟两路不同规格的流（真实摄像头一颗芯片输出两路，这里是等价模拟）
ffmpeg -re -stream_loop -1 -i test_1080p.mp4 \
  -c copy -f rtsp rtsp://localhost:8554/cam1/main   # "主码流"：1080p 原规格

ffmpeg -re -stream_loop -1 -i test_1080p.mp4 \
  -vf scale=704:576 -c:v libx264 -b:v 500k -g 50 \
  -f rtsp rtsp://localhost:8554/cam1/sub            # "子码流"：D1 低码率

# 对比两路流的规格与码率
ffprobe -v error -select_streams v:0 \
  -show_entries stream=width,height,bit_rate -of csv=p=0 rtsp://localhost:8554/cam1/main
ffprobe -v error -select_streams v:0 \
  -show_entries stream=width,height,bit_rate -of csv=p=0 rtsp://localhost:8554/cam1/sub
```
**预期输出**：主码流为 1920×1080、码率数 Mbps；子码流为 704×576、码率约 500kbps。把两路分别填进 4 分屏预览（sub）与单路详情（main），体会第四节"预览用子码流"的带宽差——16 路预览场景下差距是 8 倍。

## 常见问题排查

| 现象 | 可能原因 | 解决方法 |
|------|---------|---------|
| 摄像头 RTSP 连接超时 | 摄像头在 NAT 后面，UDP 不通 | MediaMTX 配置 `sourceProtocol: tcp` 强制 TCP |
| 大量摄像头接入后内存暴增 | 每路保留完整 GOP 缓存 | 关闭 MediaMTX 的 GOP 缓存，或限制 `readBufferCount` |
| 摄像头断流后状态未更新 | 轮询间隔太长 | 缩短状态同步任务间隔至 30s，并利用 `runOnNotReady` 回调即时通知 |
| 跨租户数据泄露 | Service 层未正确过滤 tenantID | 检查所有 repo 查询是否传入了 `tenantIDs` 参数 |
| 播放流延迟高 | Edge 节点未配置，所有流量走源站 | 部署 SRS/Nginx Edge 节点分担播放压力 |
| 多分屏预览卡顿 | 预览误用了主码流（1080p 高码率） | 预览一律用子码流地址；主码流只留给单路详情与录像 |
| 录像磁盘容量规划总不够 | 存储按单码率估算，主/子码流与保留天数混算 | 按第四节公式分主/子码流两个参数分别计算，再加 20% 余量 |
| 视频墙个别画面黑屏 | 解码器路数超限或该路流不存在 | 检查解码器并发路数上限；上墙的流建议常拉策略，不要按需 |
| 主/子码流切换瞬间黑屏 1-2 秒 | 切流后播放器等待下一个关键帧（I 帧） | 拉流端配置短 GOP（如 1s）；或服务端预拉取使切换目标流已就绪 |
