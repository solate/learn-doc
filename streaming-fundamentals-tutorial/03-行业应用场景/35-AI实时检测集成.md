# AI 实时检测集成（不阻塞播放链路）

> **适合读者**：需要在视频流上叠加 AI 能力（目标检测/人脸识别/行为分析）的后端开发者
> **核心问题**：AI 推理慢（GPU 也要 5-100ms/帧），如何加上 AI 又不拖垮视频播放链路？

**读完你能学会**：让 AI 走旁路、播放主链路零改动的完整管线——抽帧怎么抽、推理放哪、帧队列怎么解耦、结果怎么回前端、异常怎么触发录像，每层为什么那样选。

---

## 一、核心原则：AI 旁路，绝不串进播放链路

```
❌ 错误：AI 串进播放链路
RTSP → AI 推理(50ms/帧) → 推流 → 播放器
                            ↑ 每帧都被 AI 挡 50ms → 卡顿、延迟爆炸

✅ 正确：播放与 AI 并联
RTSP →[分流]→ 直接推流 → 播放器          （主链路零改动、零额外延迟）
             └→ 抽帧(360p/3fps) → 帧队列 → AI 推理 → 结果
```

**一句话认知**：给播放器的那份流**原样快速转发**；给 AI 的那份可以**降分辨率、降帧率、排进队列慢慢算**——AI 的延迟永远不会加到播放延迟上。

---

## 二、整体架构：责任分家

```
摄像头 RTSP ──→ [分流器/ffmpeg] ──原样转发──→ 流媒体服务器 → 播放器
                    │
                    └─抽帧(降分辨率/帧率)─→ 帧队列(异步) ─→ GPU 推理服务
                                                                │
                                      ┌──────────┬──────────────┘
                                      ▼          ▼
                                WebSocket   事件录像/告警
                                前端 Canvas 叠加框
```

每层负责一件事，各自独立伸缩：

| 环节 | 选型 | 为什么放这里 |
|------|------|------------|
| 抽帧 | ffmpeg 管道 / OpenCV | 入口处就把 AI 输入降为 360p、2-5fps，GPU 不用浪费在高清上 |
| 帧队列 | 有界 channel / Redis Stream / Kafka | 抽帧与推理**解耦**：推理再慢也不阻塞抽帧（见四）|
| 推理 | ONNX Runtime + GPU | 单帧 20-100ms 必须与主链路并行（见五）|
| 结果回传 | WebSocket | ~毫秒级到前端，叠框才实时（见六）|
| 异常处理 | 事件触发录像 + 告警 | 检测只是"看到了"，落库/录像/通知才闭环（见七）|

视频路数多了加分流器，AI 推不动了加 GPU worker，前端掉线了结果照常落库——每一块互不拖累。

## 三、抽帧：怎么把帧从流里拿出来

两种主流方式，选一个即可：

| 方式 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| ffmpeg 管道 | 子进程拉流、按需抽帧写入管道 | 命令即代码，跨摄像头通用 | 一路一个子进程，断流要自己重连 |
| OpenCV `VideoCapture` | 进程内解码，`grab()/retrieve()` 取帧 | 少一个子进程、可控性最强 | RTSP 断连处理要自己写，解码吃进程 CPU |

### 3.1 ffmpeg 一进两出（一条命令同时干两份活）

```bash
ffmpeg -rtsp_transport tcp -i rtsp://admin:***​*@camera.local/live \
  # 输出1：-c copy 原样转发给流媒体服务器（不重新编码，零画质损失、零延迟）
  -map 0:v:0 -c copy -f flv rtmp://media.local/live/stream1 \
  # 输出2：降分辨率 + 降帧率，只给 AI 用
  -map 0:v:0 -vf fps=3,scale=640:360 -pix_fmt rgb24 -f rawvideo pipe:1
```

**要点（都是踩坑换来的）**：
- `-map 0:v:0` 把源视频**显式分别绑给两个输出**——不写的话 ffmpeg 自动分配流，行为不可预测；
- 输出1 `-c copy`、输出2 `-vf` 互不干扰，清晰度与延迟完全留给播放链路；
- `rawvideo + rgb24` 是**定长帧**（640×360×3 = 691200 字节），读取端按固定大小切帧最省事；若抽成 `mjpeg`，帧是变长的，要按 `FFD8…FFD9` 标记自己拼接。

> 提示：已有流媒体网关（如 MediaMTX / ZLMediaKit）时，也可直接调它的截图/抽帧接口，不用自己跑 ffmpeg——原理一致，省一路进程。

### 3.2 生产者：读到帧就投进帧队列（非阻塞）

```go
// 抽帧生产者：拉 RTSP，降采样，投进帧队列
func (p *FrameProducer) Run(ctx context.Context) {
    cmd := exec.CommandContext(ctx, "ffmpeg",
        "-rtsp_transport", "tcp", "-i", p.rtspURL,
        "-map", "0:v:0", "-vf", "fps=3,scale=640:360",
        "-pix_fmt", "rgb24", "-f", "rawvideo", "pipe:1")
    stdout, _ := cmd.StdoutPipe()
    if err := cmd.Start(); err != nil {
        log.Error().Err(err).Str("camera", p.cameraID).Msg("ffmpeg 启动失败")
        return
    }

    frameSize := 640 * 360 * 3
    buf := make([]byte, frameSize)
    for {
        // ReadFull：一次读齐一整帧，断流/帧不完整即返回
        if _, err := io.ReadFull(stdout, buf); err != nil {
            log.Warn().Str("camera", p.cameraID).Msg("抽帧流断开，等待重连")
            return // 外层用循环 + 退避重启 Run 实现自动重连
        }
        frame := make([]byte, frameSize)
        copy(frame, buf)
        p.push(ctx, Frame{
            CameraID: p.cameraID, W: 640, H: 360,
            Data: frame, Ts: time.Now().UnixMilli(),
        })
    }
}
```

## 四、帧队列：抽帧与推理解耦的关键

核心矛盾：**抽帧（3fps 很轻）和推理（100ms/帧很重）速度不一样**。不排队改同步调用，AI 一慢整条链路就堵。队列就是中间的缓冲池，而且必须**有界**——满了丢旧帧保吞吐，不能让 AI 的慢反过来拖住抽帧。

| 方案 | 适用场景 | 特点 |
|------|---------|------|
| 有界 channel | 单机、全进程内 | 零依赖；但抽帧与推理必须在同一进程，GPU 扩展受限 |
| **Redis Stream** | **中小规模、学习首选（本文示例）** | 消费者组自动负载均衡、ACK 确认机制、天然跨进程 |
| Kafka | 大规模（几十路以上、要重放审计）| 吞吐最高、可重放；但组件重、运维贵 |

### 4.1 生产者：投帧（`MAXLEN` 限长防堆积）

```go
func (p *FrameProducer) push(ctx context.Context, f Frame) error {
    jpg := p.jpegEncode(f) // 帧入队前压成 JPEG，体积小、Redis 友好
    _, err := p.redis.XAdd(ctx, &redis.XAddArgs{
        Stream: "frames",
        MaxLen: 2000,     // 只保留最近 2000 帧（约 10 分钟@3fps），防止无限积压
        Approx: true,     // ~近似裁剪，删除成本低
        Values: map[string]any{
            "camera_id": f.CameraID, "jpg": jpg, "ts": f.Ts,
        },
    }).Result()
    return err
}
```

> 生产上若帧大，建议 JPEG 再大也是几十 KB；原始帧 MB 级时改存对象存储，消息里只放 `bucket/key`。

### 4.2 消费者：GPU worker 按组消费

```go
// 推理 worker：组内多个 worker 自动瓜分不同帧，天然水平扩展
func (w *AIWorker) Consume(ctx context.Context) {
    for {
        res, err := w.redis.XReadGroup(ctx, &redis.XReadGroupArgs{
            Group:    "ai",            // 消费者组：多个 worker 组内负载均衡
            Consumer: w.id,            // 每个 worker 唯一 ID
            Streams:  []string{"frames", ">"}, // ">" = 只读还没人读过的
            Count:    1,               // 一次取 1 帧，正好对应一次 GPU 推理
            Block:    5 * time.Second, // 队列空时阻塞等待，不空转烧 CPU
        }).Result()
        if err == redis.Nil || len(res) == 0 { continue }
        if err != nil { log.Error().Err(err).Msg("读帧队列失败"); time.Sleep(time.Second); continue }

        msg := res[0].Messages[0]
        f, err := decodeFrame(msg)
        if err == nil {
            boxes := w.infer(ctx, f)                  // GPU 推理（见五）
            w.publishResult(ctx, f.CameraID, f.Ts, boxes) // 推前端/触发录像（见六、七）
            // 处理完才 ACK：worker 崩溃时这笔帧会交给组内其他人重试，不丢帧
            w.redis.XAck(ctx, "frames", "ai", msg.ID)
            w.redis.XDel(ctx, "frames", msg.ID)
        }
    }
}
```

**单机简化版（原理上等价）**：进程内就用有界 channel + 非阻塞投递，满了直接丢帧：

```go
select {
case ch <- frame: // 有空间，投进去
default:          // 满了，丢帧（AI 忙不过来时保持抽帧不掉速）
}
```

## 五、AI 推理：模型选型 + GPU 加速

### 5.1 模型怎么选

| 任务 | 常用模型 | 备注 |
|------|---------|------|
| 目标检测（人/车/物）| YOLOv8 / YOLO11 | 640×640 输入，GPU 20-50ms/帧，最通用 |
| 人脸检测 + 识别 | SCRFD + ArcFace | 先检测人脸，再提特征向量比对库 |
| 人数/轨迹统计 | YOLO + ByteTrack | 检测后做跨帧跟踪（`TrackID`），才能计数不重复 |
| 姿态/动作识别 | RTMPose | 输出人体关键点，喂给行为分析 |

### 5.2 ONNX Runtime + CUDA 推理（Go）

```go
import ort "github.com/yalue/onnxruntime_go"

func NewDetector(modelPath string) (*Detector, error) {
    ort.SetSharedLibraryPath("/usr/lib/libonnxruntime.so") // 注意装 CUDA 版 so
    if err := ort.InitializeEnvironment(); err != nil { return nil, err }

    opts := ort.NewSessionOptions()
    opts.AppendExecutionProvider_CUDA() // 关键：切到 GPU，推理省 5-10 倍

    in, _ := ort.NewTensor(ort.NewShape(1, 3, 640, 640), make([]float32, 1*3*640*640))
    out, _ := ort.NewEmptyTensor[float32](ort.NewShape(1, 84, 8400))
    sess, err := ort.NewAdvancedSession(modelPath,
        []string{"images"}, []string{"output0"},
        []ort.ArbitraryTensor{in}, []ort.ArbitraryTensor{out}, opts)
    return &Detector{session: sess, input: in, output: out}, err
}

func (d *Detector) Detect(ctx context.Context, img image.Image) ([]Box, error) {
    // 1. 预处理：缩放 640x640 → 归一化 [0,1] → NCHW
    data := preprocess(img)
    copy(d.input.GetData(), data) // 复用预分配 tensor，避免每帧重建
    if err := d.session.Run(ctx); err != nil { return nil, err }
    // 2. 后处理：output0[1,84,8400] = 8400 个候选框(位置+80类置信度)
    //    NMS：同一目标有大量重叠框，按置信度排序、删掉 IoU > 0.45 的重复框
    return postprocess(d.output.GetData(), 0.5 /*置信度阈值*/, 0.45 /*IoU 阈值*/), nil
}
```

**为什么 8400 个框？** YOLO 在多层特征网上滑窗产生 8400 个候选，几乎全是重叠/低分的，NMS 的作用就是把它们收敛成"一个目标一个框"。通常在 **[第 2 篇](02-视频编码深度解析.md) 讲帧结构**、**[第 32 篇](32-边缘AIoT设备推流.md) 讲边缘设备**上，都有 AI 与视频配合的前置概念。

> 只跑 CPU（无 GPU）：640 输入 + YOLOv8 约 100-300ms/帧，还需把抽帧率压到 1fps 以下才跟得上。

## 六、结果回传：WebSocket 实时叠框

AI 结果用 WebSocket 管道直推前端，前端 Canvas 画在 `<video>` 上。**坐标为 0~1 归一化**：前端乘自己画面的实际宽高，天然适配不同分辨率。

```go
type Box struct {
    X, Y, W, H float32 // 归一化坐标（0~1）
    Label      string  `json:"label"`
    Conf       float32 `json:"conf"`
    TrackID    int     `json:"track_id"` // 跟踪 ID：同一目标跨帧不变，前端框才不跳
}

type DetectionMsg struct {
    CameraID string `json:"camera_id"`
    Ts       int64  `json:"ts"`
    Boxes    []Box  `json:"boxes"`
}
```

```go
// 广播：每个客户端一个"有界发送队列"
// 关键：慢消费者（前端掉线/卡顿）直接断开，绝不阻塞 AI 推理环路
func (h *Hub) Broadcast(cameraID string, msg []byte) {
    for _, c := range h.clientsByCamera[cameraID] {
        select {
        case c.send <- msg: // 有空间，投递
        default:            // 队列满了 = 前端跟不上，踢掉这个客户端
            h.RemoveClient(c)
        }
    }
}
```

**前端 Canvas 叠加**：

```javascript
ws.onmessage = (event) => {
  const r = JSON.parse(event.data);
  ctx.clearRect(0, 0, canvas.width, canvas.height);
  r.boxes.forEach(b => {                    // 服务端已归一化到 0~1
    const x = b.x * canvas.width, y = b.y * canvas.height;
    const w = b.w * canvas.width, h = b.h * canvas.height;
    ctx.strokeStyle = b.conf > 0.9 ? '#ff0000' : '#ffaa00';
    ctx.lineWidth = 2;
    ctx.strokeRect(x, y, w, h);
    ctx.fillText(`${b.label} ${(b.conf * 100).toFixed(0)}%`, x, y - 5);
  });
};
```

## 七、事件触发录像：让检测有闭环

检测到异常**只推送还不够**——要能落库留证、触发录像、发告警。两种录像方案：

| 方案 | 做法 | 适用 |
|------|------|------|
| 事件触发 | 异常瞬间起录 30s | 只关心异常，存储最省（本文示例）|
| 环形缓存 | 常录最近 5 分钟，异常时把"事发前"也保留 | 需要还原事发经过 |

```go
// 高置信度目标 → 事件入库 + 触发 30s 录像 + 推送前端
func (w *AIWorker) HandleEvent(ctx context.Context, cameraID string, ts int64, box Box, snapshotJPG []byte) {
    if box.Conf < 0.85 { return } // 置信度门槛，压误报

    go func() { // 异步处理，不拖慢推理循环
        // 1. 事件落库：供平台按"某时段有哪些事件"检索
        w.events.Create(ctx, &Event{CameraID: cameraID, Label: box.Label, Ts: ts, Snapshot: snapshotJPG})
        // 2. 触发录像：拉该摄像头 RTSP 原样存 30s（-c copy 不转码）
        go w.recorder.StartClip(ctx, cameraID, 30*time.Second)
        // 3. 告警推送（短信/IM 通知，此处略）
        w.notify(ctx, cameraID, ts, box)
    }()
}

// 按需录像：把 RTSP 原样存成一段 mp4
func (r *Recorder) StartClip(ctx context.Context, cameraID string, dur time.Duration) error {
    out := fmt.Sprintf("records/%s_%d.mp4", cameraID, time.Now().UnixMilli())
    cmd := exec.CommandContext(ctx, "ffmpeg",
        "-rtsp_transport", "tcp", "-i", r.rtspOf(cameraID),
        "-t", fmt.Sprintf("%.0f", dur.Seconds()), "-c", "copy", "-f", "mp4", out)
    return cmd.Run()
}
```

## 八、抽帧率怎么定：按场景选，别一律高帧率

| 场景 | 推荐 AI 帧率 | 说明 |
|------|------------|------|
| 人流/告警级 | 1fps | 慢变化，1s 一次足够 |
| 人脸识别 | 2-5fps | 人脸通常停留 > 500ms |
| 行为分析 | 5-10fps | 需要时序信息 |
| 车牌识别 | 10-15fps | 车辆运动快 |
| 实时多目标追踪 | 25-30fps | 需要逐帧关联的极端场景 |

**决策铁律**：先按场景定帧率，再把推理耗时压进可用预算。不够就**降低分辨率或加 GPU worker**，而不是盲目升帧率——多数监控场景 2fps 已经够告警和定位。

## 本篇小结

| 学习点 | 一句话方案 |
|--------|-----------|
| 不阻塞播放 | AI 走旁路抽帧，播放链路 `-c copy` 原样转发 |
| 解耦伸缩 | 抽帧 → 队列 → 推理，用有界队列/`MAXLEN` 防堆积，互不拖累 |
| 省算力 | 360p + 2-5fps + GPU；绝不把全高清全帧率喂给 AI |
| 结果闭环 | WebSocket 叠框 + NMS 去重 + 置信度门槛 + 事件触发录像 |
| 可扩展 | 推理进程与媒体进程分离，靠 Redis Stream 消费者组加 worker |

## 动手实践

### 练习1：抽帧 → Redis Stream → 消费者组
按第三节写 `FrameProducer`（JPEG 化后 `XAdd`），按第四节起 2 个 `Consumer`，观察：
```bash
# 队列长度是否稳定（不无限涨=有界生效）
redis-cli XLEN frames
# 消费者组内两个 worker 各消费了多少帧（大致均分）
redis-cli XINFO GROUPS frames
```
**预期输出**：`XLEN` 稳定在 `MAXLEN` 以内；两个 worker 消费量接近均分；把推理函数里 `time.Sleep(100ms)` 模拟慢推理，队列不清空但**抽帧生产端不掉速**。

### 练习2：ONNX Runtime 推理 + NMS
按第五节把一张本地图片过一遍模型：
```go
// 预处理：image.Decode → 缩放 640x640 → [0,1] → NCHW
tensor, _ := ort.NewTensor(ort.NewShape(1, 3, 640, 640), preprocess(imgData))
out, _ := ort.NewEmptyTensor[float32](ort.NewShape(1, 84, 8400))
err := sess.Run(ort.NewRunOptions(), []ort.Tensor{tensor}, []ort.Tensor{out})
```
**预期输出**：GPU 上单帧 10-30ms，CPU 上 100-300ms；`postprocess` 返回的框数远小于 8400（NMS 后只剩真正目标）。调 `IoU` 从 0.45 到 0.35，对比重叠框数变化。

### 练习3：WebSocket 叠框 + 事件触发录像（完整闭环）
把推理结果按第六节推前端、置信度 > 0.85 的按第七节触发录像。
**预期输出**：浏览器上实时画出检测框，延迟约 200-500ms（推理+网络）；触发事件后 `records/` 目录出现 30s 录像片段，`events` 表出现事件记录。

## 常见问题排查

| 现象 | 可能原因 | 解决方法 |
|------|---------|---------|
| 推理跟不上帧率（>50ms/帧）| CPU 推理、模型太大 | 上 CUDA；或降输入 640→320、降帧率 |
| 帧队列持续积压、`XLEN` 只涨不跌 | 消费者太少 | 加 worker（消费者组自动分摊）；并把 `MAXLEN` 当兜底 |
| 摄像头断流导致 AI 全部停摆 | ffmpeg 抽帧子进程退出 | `-stimeout` 参数 + 退出后循环重启 + 断流告警 |
| 消息体过大拖慢 Redis | 塞了原始帧 | 压 JPEG，或存对象存储、消息只放 key |
| Canvas 叠框与视频错位 | 用了像素坐标 | 服务端发归一化坐标，前端乘实际宽高 |
| 检测框抖动频繁（帧出帧没）| 置信度太低误检 | 提高到 0.6+，或连续 3 帧确认（时序滤波）|
| NMS 后重叠框仍多 | IoU 阈值过高 | 0.45 → 0.35 |
| WebSocket 链路阻塞推理 | 广播同步写死 | 每客户端有界发送队列，慢了直接踢（见六）|

|------|------|------|
| 旁路抽帧 | Bypass Frame Sampling | 从主播放链路分出一支，降采样后供 AI 分析，不影响播放 |
| 有界队列 | Bounded Queue | 容量固定的队列，满了丢新帧而非阻塞生产者 |
| Redis Stream | Redis Stream | Redis 内置消息队列，支持消费者组与 ACK 确认 |
| 消费者组 | Consumer Group | 组内 worker 自动分担消息，单个失败可重试 |
| ACK | Acknowledgment | 消费成功确认，防止崩溃导致消息丢失 |
| ONNX | Open Neural Network Exchange | 跨框架模型交换格式，可直接加载到推理引擎 |
| NMS | Non-Maximum Suppression | 非极大值抑制：删掉同一目标的重叠冗余框 |
| IoU | Intersection over Union | 两框交集/并集比，判重叠程度（NMS 阈值用）|
| 归一化坐标 | Normalized Coordinates | 0~1 范围坐标，乘以实际宽高得到像素，适配多分辨率 |
| 事件触发录像 | Event-triggered Recording | 检测到异常才起录一段，省存储 |
