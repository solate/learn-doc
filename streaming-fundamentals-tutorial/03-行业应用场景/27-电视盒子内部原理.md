# 电视盒子内部原理

> **适合读者**：给电视/盒子上线过播放功能、或想搞懂"一台几百块的盒子凭什么 4K 不卡"的后端/客户端开发者
> **核心内容**：给盒子一个精确的身份 → 拆硬件 → 走一遍启动流程 → 跟着一条视频流从网络走到屏幕 → 套回 Android 软件栈 → 亲手写一个硬解播放器 → 掌握遥控器交互与 adb 排障
> **本篇主线**：先记住一句话——**电视盒子 = 一台砍掉除"看视频"以外所有能力、专门为解码优化、用遥控器控制的 Android 小电脑**。它不神秘：视频能不能播、卡不卡，本质都归结为"一条视频流如何从网络走到屏幕"的那条链路。

读完本篇，你能做到：

1. **一句话说清盒子**：盒子和手机/电脑的本质差异在哪，为什么它能便宜地播 4K
2. **看懂硬件**：一颗 SoC 里谁负责什么，为什么"解码靠 VPU，CPU 只是调度员"
3. **走通启动流程**：从通电到桌面都发生了什么，为什么看启动日志/懂固件有意义
4. **讲清解码链路**：数据从网卡到屏幕的每一步谁在干活，硬解为什么省电又省 CPU
5. **写出能硬解 HLS 的播放器**：ExoPlayer 最小可用代码 + 缓冲调参 + 判断硬解是否生效
6. **掌握盒子特有开发**：遥控器焦点导航、十英尺 UI、常用的 adb 排障命令

## 一、先建立直觉：盒子是一台"只留下视频能力"的电脑

假如任务让你造一台"300 块钱让客厅电视能播网络视频"的机器，你会怎么设计？大概率你会：

- 去掉键盘鼠标 → 换成一个几十块的遥控器；
- 不需要大内存大硬盘 → 够跑 Android 和 App 就行；
- 抠掉一切和"画面"无关的算力 → 把预算全砸在**视频解码**上；
- 固定体积、一直插电 → 不需要考虑电池和便携。

结果就是电视盒子。它本质上是**一台精简到极致的 Android 计算机**，省下来的每一分钱，都花在了"让 4K 视频流畅"这一件事上。

**盒子 vs 手机 vs 电脑**：

| 维度 | 电视盒子 | 手机 | 电脑 |
|------|---------|------|------|
| 核心任务 | 播放视频（固定） | 什么都能干 | 什么都能干 |
| 解码 | 专用硬件 VPU，硬解是刚需 | 有硬件解码，但面向移动功耗 | 看 CPU/独显，能力差别大 |
| 交互 | 遥控器方向键，10 英尺，无触摸屏 | 触摸 | 键鼠 |
| 输出 | 固定 HDMI 到电视 | 自带屏幕 | 显示器 |
| 运行 | 7×24 插电、固定机位 | 随身、待机 | 桌面 |
| 价格 | 几十到几百元 | 千元起 | 数千元起 |

三个值得带走的推论：

1. **"便宜"的来源**：解码被做成了专用硬件（SoC 集成），量一大单价就便宜，而不是靠堆通用算力。
2. **"能播 4K"的来源**：解码由硬件完成，根本不需要 CPU 堆料——这决定了它花小钱办大事。
3. **"交互简单"的来源**：遥控器 + 无触摸屏，决定了整套 UI 范式（后面第八节展开）。

> 一句话：**盒子不是"弱化的电脑"，而是"把外设和算力全部让位给解码的专用电脑"。** 理解了这一点，后面每一节的问题都会自然有答案。

## 二、拆开看：一颗 SoC 装下了整台电脑

**SoC（System-on-Chip，片上系统）**：过去需要多块芯片分工才干得完的活（CPU、显卡、网卡、内存控制器……），现在全部集成到**一颗芯片**里。盒子的主机板上，主要就是一颗 SoC + 内存颗粒 + 存储 + 几个接口电路。

```
┌─ 盒子主机板 ────────────────────────────────┐
│   ┌────────────────────────────────────┐   │
│   │             SoC（一颗芯片）             │   │
│   │   ┌───────┐   ┌───────┐   ┌───────┐ │   │
│   │   │  CPU  │   │  GPU  │   │  VPU  │ │   │
│   │   └───────┘   └───────┘   └───────┘ │   │
│   │   ┌──────┐   ┌──────┐   ┌────────┐  │   │
│   │   │内存控制器│   │ WiFi/网口│   │HDMI 控制器│  │   │
│   │   └──────┘   └──────┘   └────────┘  │   │
│   └───────────────┬────────────────────┘   │
│       内存       存储        网口/天线       HDMI  USB
└───────────────────┴────────────────────────┘
```

每个部件各干各的活，谁也替代不了谁：

| 部件 | 作用 | 在"播放"这件事里的角色 |
|------|------|------------------------|
| CPU | 通用计算、跑 Android 和 App | 调度员：跑业务逻辑，不碰大数据搬运 |
| GPU | 图形渲染、图层合成 | 渲染 UI，协助最终的画面合成/缩放 |
| **VPU** | **专做视频编解码的硬件引擎** | **核心打工人：4K/8K 硬解全靠它** |
| 内存（DDR） | 程序 + 数据缓冲区 | 压缩分片、解码中间帧暂时住在这 |
| 存储（eMMC） | 装系统、装 App | —— |
| 网络（WiFi/网口） | 上网 | 视频流进盒子的第一站 |
| HDMI 控制器 | 按电视的时序把像素送出去 | 画面的最后一公里 |

**关键认知（全篇最值钱的一句）**：盒子"能不能播 4K、卡不卡"，看的**不是 CPU，是 VPU**。CPU 的存在只是让系统"转起来"，视频的每一帧数据根本不需要它一块块搬。所以一台 CPU 很弱的老盒子同样可能流畅播 4K——只要它有一颗合格的 VPU。

**主流盒子 SoC 一览**：

| 芯片 | 厂商 | 定位 | 亮点 |
|------|------|------|------|
| S905X4 | 晶晨 Amlogic | 国内入门到主流，量最大 | AV1 硬解，性价比之王 |
| RK3588 | 瑞芯微 Rockchip | 旗舰 | 8K 解码 + 强力 NPU，AI 也扛得住 |
| RTD1319 家族 | 瑞昱 Realtek | 认证盒子常见 | 稳定、认证成本低，海外品牌机顶盒常用 |
| H618 / H713 | 全志 Allwinner | 超低价 | 百元级盒子主力，够用 |

> 选型速记：**要便宜、量大买晶晨 S905 系；要高配带 AI 买瑞芯微 RK3588；要超低价买全志 H 系。** 别把高通 8295 这类车机芯片当成盒子典型——那是给汽车座舱的，定位和价差都不同。高端国际产品还有英伟达 Tegra X1（Shield 家族）那一档，这里按下不表。

## 三、从通电到桌面：盒子的启动流程

盒子为什么一开机就能直接看到桌面？因为它埋了一条从"裸芯片"到"Android 桌面"的固有链路。每一个环节都不可省略，也是你能干预盒子固件的地方：

```
通电
  → BootROM（芯片出厂固化的第一段代码，谁都改不了）
  → 引导程序 U-Boot（初始化内存，加载系统分区）
  → Linux 内核（把 VPU / 网络 / HDMI 等外设驱动起来）
  → init → 系统服务（SurfaceFlinger、媒体服务等）
  → Android 框架
  → Launcher（Leanback 桌面）
```

**后端开发者为什么值得懂这段**：

- 盒子启动日志是排障第一步——系统起没起来、是死在 U-Boot 还是死在 Android，问题性质完全不同；
- "刷机 / 改固件 / 变砖"改的就是这条链路上的镜像分区（boot、system、vendor）；
- 驱动在 vendor 分区，所以"换个系统玩玩"必须靠厂商适配。

一段真实的启动日志（串口或 `adb logcat -b all`）长这样：

```
[  0.000000] Booting Linux on physical CPU 0x0000000000
[  1.214653] init: starting service 'surfaceflinger'...
[  1.238725] SurfaceFlinger: boot animation started
[  3.982021] ActivityManager: Start proc com.android.launcher
[  4.120312] ActivityManager: Displayed com.android.launcher/.MainActivity
```

> 一句话：**开机 = 从"芯片出厂代码"一路接力到"App 桌面"**，每一棒是谁、在干什么，你应该说得出来。

## 四、核心链路：一条视频流变成画面的每一步

现在进入正题。把前面学的零件全部串起来，一条直播/点播视频从"进盒子"到"上电视"要经过五站：

```
① 网络接收（网卡 DMA）
     无线/有线 → 网卡直接把数据 DMA 写进内存（CPU 不搬）
      ↓
② 解复用 Demuxer（CPU，轻活）
     从 TS / MP4 / FLV 容器里，把"视频流、音频流、字幕"分离出来
      ↓
③ 视频硬解（VPU，重活）
     CPU 把压缩帧"喂"给 VPU 解码器 → 产出 YUV 原始像素帧（放进共享内存）
      ↓
④ 合成（SurfaceFlinger + GPU / HWC）
     把视频层、UI 层、字幕层合成为一帧（缩放、色彩转换、透明叠加）
      ↓
⑤ HDMI 输出（显示控制器）
     按电视的时序逐行读取像素 → 屏幕亮起
```

**逐站拆解**：

**① 网络接收**：网卡（WiFi 芯片 / 以太网）收到数据后，通过 **DMA（Direct Memory Access，直接内存访问）** 直接写入内存缓冲。这一路上不需要 CPU 一块块拷贝——这是整个"高效链路"的起点。

**② 解复用**：这步是 CPU 干的，但很轻——它只是"拆包"，把容器格式里的视频包、音频包分门别类。数据量是解码后的百分之一量级，CPU 完全扛得住。

**③ 视频硬解（全篇的心脏）**：压缩帧被送往 VPU。VPU 内部常驻多个解码器实例（比如一个 H.264、一个 H.265），一个接一个算出原始像素帧。结果不搬回 CPU 内存，而是放进**共享内存（dmabuf/Ion）**直接给下一步用。这是"硬解"与"软解"的分水岭：

- **软解**：CPU 用软件算法模拟解码。4K H.265 一帧的运算量让 CPU"寝食难安"——多核满载还掉帧，功耗和发热全上来了；
- **硬解**：VPU 是专门为解码设计的硬件电路，同一帧它"眨眼"就完，CPU 占用常常只有个位数百分比。

**④ 合成**：屏幕上不止视频，还有界面、字幕、台标。Android 的合成器 SurfaceFlinger 负责在 **vsync（垂直同步）** 的节拍下把所有图层合成为一帧，缩放和颜色转换可以交给 GPU 或显示硬件（HWC，Hardware Composer）。这正是盒子 GPU 很弱却也能输出 4K 的原因——它没在解码，只干"摆图层"这种轻活。

**⑤ HDMI 输出**：合成完的一整帧交给 HDMI 控制器，按 60Hz/120Hz 的时序送出去，电视收到就是画面。（HDR 也在这关分出高下：HDR10/HLG/杜比视界需要 SoC 支持并走 HDMI 元数据通道。）

**"谁在干活"速查表**：

| 环节 | 干活的 | 强度 | 数据量 |
|------|--------|------|--------|
| 接收 | 网卡 DMA | 硬件直通 | 中（压缩后） |
| 解复用 | CPU | 轻 | 小 |
| 解出像素 | **VPU** | **重但专精** | 大（YUV 原始帧） |
| 合成 | GPU / HWC | 轻 | 中 |
| 输出 | HDMI 控制器 | 硬件 | 大 |

**三个必须带走的关键认知**：

1. **数据绕开 CPU**：压缩流和解码后的帧都通过"共享内存 + 硬件单元"直接传递，CPU 从头到尾只当"指挥"，没在"搬运"。所以硬解画质更好、功耗更低、价格更便宜——这是盒子能"花小钱办大事"的底层原因。
2. **编码支持 = VPU 能力**：盒子支不支持某个格式（H.265 4K？AV1？），查的不是"系统新不新"，而是 VPU 的编码支持清单。这也是选盒子/排障时最该问的一个问题。
3. **解码节奏 vs 显示节奏**：解码是"一帧一帧来"，显示是"按 vsync 节拍走"，二者靠 SurfaceFlinger 的缓冲协调；跳帧、画面撕裂（割裂感）往往出在这一步。

> 一句话：**盒子的所有本事都在这条链路上——它把最重的解码活换成了一颗专用的硬件引擎，剩下的全是轻活。**

## 五、软件栈：Android 怎么指挥盒子干活

硬件再强，也要 Android 来调度。盒子的媒体栈是一套清晰的"分层电话"：

```
┌───────────────────────────────┐
│  App（ExoPlayer / Kodi / WebView）│ ← 用统一的 MediaCodec API
├───────────────────────────────┤
│  MediaExtractor（解复用）       │
├───────────────────────────────┤
│  MediaCodec（编解码统一接口）    │   ← 你打交道最多的一层
├───────────────────────────────┤
│  Codec2 / OMX（framework 侧）  │   ← 解码器真名 c2.amlogic.* / omx.*
├───────────────────────────────┤
│  HAL + 内核驱动                 │   ← 厂商实现，接真实 VPU
├───────────────────────────────┤
│  VPU 硬件                       │
└───────────────────────────────┘
```

**三个名字，记住就够了**：

| 名词 | 是什么 | 意义 |
|------|--------|------|
| MediaCodec | Android 暴露给所有 App 的编解码统一 API | App 写一次，硬解软解通吃 |
| Codec2 | 新一代编解码框架（替代老 OMX） | 厂商解码器名叫 `c2.*`，老的 `omx.*` 也兼容保留 |
| HAL | 硬件抽象层，framework 与厂商代码的分界线 | 厂商自己实现，App 不用管 |

**一次 `player.prepare()` 之后的"电话"**：

```
ExoPlayer.configure(MediaCodec, 视频格式)
  → 系统查"哪颗解码器支持这个格式"
      → 硬解优先（c2.amlogic.* 这类）→ 拿到就交给 VPU
      → 没有硬解，落到软解兜底（c2.android.* / OMX.google.*）
  → 编码器硬件 session 建立成功
  → 一路喂压缩帧，一路收 YUV 帧，送进播放管线
```

注意中间那步的选择——**"硬解优先、软解兜底"正是 ExoPlayer 的默认行为**。下一节就把它变成你能亲手控制、能亲眼确认的事。

## 六、动手写播放器：ExoPlayer 硬解 HLS

在 Android TV / 盒子上播 HLS 流，业界标准就是 **ExoPlayer（Google 官方，Media3）**。它替你做了三件事：协议栈（HLS/DASH 解析）、解码选择（硬解优先、软解兜底）、渲染与音画同步。

### 6.1 最小可运行版本

```kotlin
// build.gradle: implementation "androidx.media3:media3-exoplayer:1.x.x"
class MainActivity : AppCompatActivity() {
    private lateinit var player: ExoPlayer

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)

        player = ExoPlayer.Builder(this)
            .setMediaSourceFactory(DefaultMediaSourceFactory(this)) // 内含 HLS/DASH 解析器
            .build()

        val playerView = findViewById<PlayerView>(R.id.player_view)
        playerView.player = player
        playerView.useController = true // 遥控器可用默认控制条

        // .m3u8 后缀会被默认识别为 HLS，无需显式指定 MIME
        player.setMediaItem(MediaItem.fromUri("https://cdn.example.com/live/stream.m3u8"))
        player.prepare()
        player.play()
    }

    override fun onDestroy() {
        super.onDestroy()
        player.release()
    }
}
```

### 6.2 让你"看见"硬解是否生效（盒子排障最常用的一招）

给播放器挂一个 EventLogger，实际选中的解码器就会打进 logcat：

```kotlin
player.addAnalyticsListener(EventLogger(log))
// logcat 里搜 "video decoder"，会看到二选一：
// I ...: video decoder: c2.amlogic.videodecoder.avc  ← 硬件（走 VPU）
// I ...: video decoder: c2.android.avc.decoder        ← 软件（兜底）
```

想明确控制解码器行为，可以用 `setVideoDecoderFactory`：

```kotlin
player = ExoPlayer.Builder(this)
    .setVideoDecoderFactory(
        DefaultVideoDecoderFactory(
            this,
            /* enableDecoderFallback= */ true, // 找不到硬解时允许回退软解
        )
    )
    .build()
```

### 6.3 低延迟缓冲（直播场景）

播放器默认喜欢把缓冲区填得大大的来防卡顿。直播要低延迟，就得拧小：

```kotlin
val loadControl = DefaultLoadControl.Builder()
    .setBufferDurationsMs(
        1000,   // 目标最小缓冲 1s
        5000,   // 目标最大缓冲 5s —— 足够小，直播延迟才低
        500,    // 开始播放所需 500ms
        500     // 重缓冲后恢复所需 500ms
    )
    .build()
```

**直播 vs 点播的配置差异**：

| | 直播（live） | 点播（VOD） |
|---|---|---|
| 缓冲目标 | 小（秒级），代价是卡顿概率变高 | 大，随便预加载 |
| 首帧/换台 | 越快越好 | 要求不高 |
| seek | 追直播（对时轴 seek） | 正常 seek |

### 6.4 内容加密：盒子播 DRM 内容的"硬门槛"

视频服务常给内容加一层 DRM。盒子上最关键的是 **Widevine** 的分级：

- **L1（硬件安全）**：解密发生在安全环境（TEE）里，密钥不经过 App、不进可读内存 → 能放 4K 会员内容；
- **L3（软件安全）**：密钥在普通软件栈处理 → 只能放低分辨率。

很多白牌盒子硬件够格但没过 L1 认证，于是同一条会员 4K 片源，手机能放 4K、盒子只能放 1080p。**排查"为什么 4K 内容放不了"时，先查的就是这个**。（这也解释了为什么 NetFlix/爱奇艺的盒子上 4K 比手机难得多。）

自己做内部系统、想"加密防拷"，用最简单的 **AES-128 加密 HLS** 就够（FFmpeg 一行）：

```bash
openssl rand 16 > enc.key
# keyinfo 三行分别是：key 的 URL、本机 key 文件路径、IV（可留空）
printf "https://server/enc.key\nenc.key\n\n" > enc.keyinfo

ffmpeg -i input.mp4 -c copy \
  -hls_key_info_file enc.keyinfo \
  -f hls -hls_time 4 output.m3u8
```

> 至此你已经有了一张"真硬解 + 可控延迟 + 可加锁"的牌。还差两块拼图：声音怎么办、遥控器怎么办。

## 七、声音：也是一场"二选一"

视频走 VPU，音频则是个多面手——盒子对音频有两条出路：

1. **解码后走（PCM）**：盒子自己把 AAC/Opus 解成 PCM 裸数据，混进 HDMI 送出去。绝大多数场景走这条。音频解码比视频轻太多，软解功耗也低，SoC 内部还有音频 DSP 帮忙——所以**音频通常不强调"硬解"**，和视频完全两个待遇。
2. **直通（bitstream passthrough）**：遇到杜比/DTS 这类**编码过的位流**，盒子不解码，原封不动通过 HDMI 塞给**外接功放/回音壁**，由它们去解。这样能保留完整多声道/全景声，但要求盒子本身支持直通、电视到功放那条链路也通。

一句话：**视频是"盒子解码、电视只当屏"；音频是"盒子可能解、也可能只当传话筒"。**

两个必碰的接口名词：

- **ARC / eARC**：HDMI 上的"返回音频通道"——电视把收到的音频回传给功放的那条回头路。eARC 带宽大，能跑杜比全景声这类高码率音频。
- **A/V 同步**：音频和视频走的是两条路，天然不同步。播放器用时间戳（PTS）把声画对齐。**你"感觉对不上"时，先查时间基准，而不是怀疑解码。**

> 后端开发在这块的实际工作，通常是：给播放器配准音频格式（PCM vs passthrough）、管好声画同步、调延时——而不是自己重造解码轮子。

## 八、遥控器与十英尺 UI：TV 开发的"第二课"

手机 App 用手指点；盒子 App 用**方向键加确认键**在界面上"爬行"。这是 TV 开发与手机开发最大的认知差异——**焦点（Focus）模型**：

```
概念：任何时刻，界面上只有一个"拥有焦点的 View"（通常带高亮边框）
操作：方向键把焦点从一个 View 移到另一个 → OK 键触发点击

移动规则：默认按布局几何就近，但你可以显式指定"离开它往哪走"
  android:nextFocusUp / nextFocusDown / nextFocusLeft / nextFocusRight
```

**盒子 App 的地基**（Google 规范，算硬性要求）：

- `android:focusable="true"`：焦点只在"可聚焦"的 View 身上；
- **Leanback 库**：Google 为 TV 做的整套 UI 组件（Browse 流式页面、卡片行等），焦点导航的麻烦替你想好大半；
- **十英尺 UI**：人在沙发上看，字要大、操作要少——别把手机 UI 直接搬上来；
- 声明 `android:touchscreen="notouch"`：告诉系统这台设备没有触摸屏。

**遥控器常用键映射**：

| 遥控器按键 | Android KeyCode |
|-----------|----------------|
| 上 / 下 / 左 / 右 | `KEYCODE_DPAD_UP / DOWN / LEFT / RIGHT` |
| OK / 确认 | `KEYCODE_DPAD_CENTER` 或 `KEYCODE_ENTER` |
| 返回 | `KEYCODE_BACK` |
| 播放 / 暂停 | `KEYCODE_MEDIA_PLAY_PAUSE` |
| 快进 / 快退 | `KEYCODE_MEDIA_FAST_FORWARD` / `KEYCODE_MEDIA_REWIND` |

一个最朴素的处理示例：

```kotlin
override fun onKeyDown(keyCode: Int, event: KeyEvent?): Boolean {
    return when (keyCode) {
        KeyEvent.KEYCODE_DPAD_CENTER, KeyEvent.KEYCODE_ENTER -> {
            playSelectedChannel(); true
        }
        else -> super.onKeyDown(keyCode, event)
    }
}
```

> 一句话：**手机 App 的关键词是"点击"，TV App 的关键词是"焦点"——先让焦点听话，界面导航就通了。**

## 九、调试工具箱：一杯茶的 adb 排障

盒子开发一半时间在生产，一半在 `adb`。以下命令值得背下来。

**0. 连上它**
```bash
adb connect 192.168.1.50:5555   # 盒子的开发者选项里开"网络 ADB"
adb devices                     # 确认连接
```

**1. 查这台盒子支持哪些硬解**（判断"能不能播 4K"靠这张清单，不是靠嘴）
```bash
adb shell cat /vendor/etc/media_codecs.xml   # 编解码器能力清单（具体路径因厂商而异）
# 里面会出现类似片段：
#   <MediaCodec name="c2.amlogic.videodecoder.avc" type="video/avc" ... />
#   <VideoCapabilities minFrameWidth="2" ... maxWidth="3840" maxHeight="2160" ... />
#                                           ↑ 4K 解不解得了，就看这个能力的上限
```

**2. 确认"播放时到底在用硬解还是软解"**
```bash
adb shell dumpsys media.codec | head        # 当前正在工作的编解码实例
# 播放时若看到 omx.google.* / c2.android.* 的软件解码器，说明硬解没兜住
adb shell top -n 1                          # 看 CPU：解码 4K 却占用个位数 → 硬解生效；
                                            # CPU 高得离谱 → 大概率在软解
```

**3. 抓播放相关日志**
```bash
adb logcat -s ExoPlayerImpl:V MediaCodec:V   # 按标签过滤（标签因版本而异）
adb install -r myapp.apk                      # 装 APK
adb shell screencap -p /sdcard/screen.png && adb pull /sdcard/screen.png ./
```

**4. 看显示参数**
```bash
adb shell wm size        # 分辨率
adb shell wm density     # 密度
```

**排障心智模型（见到问题先归位）**：

```
播放不出画面
  ├─ 网络/地址问题 → 先能 curl 到 m3u8 再说
  ├─ 服务端格式问题 → ffprobe 看流格式
  ├─ 盒子解码问题 → 查 media_codecs.xml + logcat 里的解码器名
  ├─ 系统问题 → 启动日志 / 内存压力
  └─ 应用问题 → PlayerView 绑定、权限、焦点
```

## 本篇小结

| 问题 | 一句话答案 |
|------|-----------|
| 盒子到底是什么？ | 一台砍掉其他能力、专为解码优化、遥控器控制的 Android 小电脑 |
| 为什么这么便宜还能播 4K？ | 解码交给内置硬件 VPU，CPU 只当调度员 |
| 决定"能不能播"的是什么？ | 一颗 SoC 里 VPU 的解码能力清单（H.265/AV1 + 分辨率上限） |
| 视频从网络到屏幕经过什么？ | 网卡 DMA → 解复用 → VPU 硬解 → 合成 → HDMI |
| 硬解和软解差在哪？ | 硬解用专用硬件、CPU 占用个位数；软解 CPU 满载还掉帧 |
| MediaCodec 是什么？ | 所有播放器统一调硬件/软件解码的那层 API |
| ExoPlayer 默认怎么选解码器？ | 硬解优先，找不到才回退软解 |
| 音频怎么走？ | 大多数盒子自己解码（PCM）；杜比/DTS 可直通给功放 |
| 盒子 4K 内容放不了？ | 先查 Widevine L1（硬件 DRM）认证，再查解码清单 |
| TV App 和手机 App 最大差别？ | 手机靠点击，电视靠"焦点导航"（遥控器方向键） |

## 动手实践

> 前面九节是"看"，这几节是"做"。四个练习从"能播出来"到"看见解码器在替谁干活"，在盒子上或电脑上都可复现。

### 练习 1：在盒子上用 ExoPlayer 播一条 HLS 直播流

```kotlin
// 环境：一台开了网络 ADB 的盒子 + Android Studio（项目用 Media3）
class MainActivity : AppCompatActivity() {
    private lateinit var player: ExoPlayer

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)

        player = ExoPlayer.Builder(this)
            .setMediaSourceFactory(DefaultMediaSourceFactory(this))
            .build()
        findViewById<PlayerView>(R.id.player_view).player = player

        player.setMediaItem(MediaItem.fromUri("http://server/hls/live/stream.m3u8"))
        player.prepare()
        player.play()
    }

    override fun onDestroy() {
        super.onDestroy()
        player.release()
    }
}
```
**你会看到**：盒子屏幕出画。若你从 [第 16 篇](../02-工程实践优化/16-MediaMTX实战.md) 起一个本地 MediaMTX/ffmpeg 的 HLS 流来播，那就是一次完整的"起流 → 播放"闭环。

### 练习 2：让遥控器方向键控制焦点

```kotlin
// 用 Leanback 的 BrowseSupportFragment 搭频道列表，方向键即可在卡片间爬行
class ChannelFragment : BrowseSupportFragment() {
    override fun onActivityCreated(savedInstanceState: Bundle?) {
        super.onActivityCreated(savedInstanceState)
        headersState = HEADERS_ENABLED
        title = "我的频道"

        val rowsAdapter = ArrayObjectAdapter(ListRowPresenter())
        // 往 rowsAdapter 里按行放卡片……卡片记得设 focusable=true
        adapter = rowsAdapter
    }
}

// 处理 OK 键
override fun onKeyDown(keyCode: Int, event: KeyEvent?): Boolean {
    return when (keyCode) {
        KeyEvent.KEYCODE_DPAD_CENTER, KeyEvent.KEYCODE_ENTER -> {
            playSelectedChannel(); true
        }
        else -> super.onKeyDown(keyCode, event)
    }
}
```
**你会看到**：方向键能选中不同卡片，OK 键触发播放——焦点导航跑通了。**你会踩到**：某张卡片始终点不到，多半是它忘了 `android:focusable="true"`。

### 练习 3：让解码器"现身"——确认正在硬解

```bash
# 播放自己的 HLS 流时，边播边查：
adb shell dumpsys media.codec | head -30      # 找正在工作的解码器
adb shell top -n 1                            # 看进程 CPU
```
**你会看到**：日志里出现 `c2.amlogic.*`（或你盒子厂商名的解码器）→ 硬解；CPU 占用保持个位数 → 印证硬件在干活。若出现 `c2.android.* / omx.google.*` 软解名 → 说明该格式没有硬解可用，就从 `media_codecs.xml` 开始排查（对应正文第九节）。

### 练习 4：在电脑上"假装"当一次电视盒子——感受硬解省了多少 CPU

就在你的笔记本上，用 FFmpeg 对比"软解 vs 硬解"4K 素材的 CPU 开销，把第四节"数据绕开 CPU"这句话变成数字：

```bash
# ① 造一条 4K 测试片（10 秒；macOS 上 x265 若没装，用 libx264 亦可，VideoToolbox 一样支持）
ffmpeg -f lavfi -i testsrc2=size=3840x2160:rate=30:duration=10 \
       -c:v libx265 -preset ultrafast 4k_sample.mp4

# ② 软解（CPU 硬算），看 user（CPU 时间）
/usr/bin/time -p ffmpeg -i 4k_sample.mp4 -f null - 2>&1 | grep -E "real|user|sys"

# ③ 硬解（macOS 上自动用 VideoToolbox；Windows/Linux 可换 -hwaccel d3d11va / vaapi）
/usr/bin/time -p ffmpeg -hwaccel videotoolbox -i 4k_sample.mp4 -f null - 2>&1 | grep -E "real|user|sys"
```
**你会看到**：②的 `user`（CPU 时间）高出一个量级，③明显更快——同一个文件，一个靠 CPU 苦算，一个靠硬件"眨眼"。盒子里的 VPU 之于 MediaCodec，就是这个 VideoToolbox 之于 FFmpeg 的角色。（注意：电脑硬解 ≠ 盒子真实表现，但"专用硬件解码省 CPU"的因果感是真实的。）

## 常见问题排查

| 现象 | 可能原因 | 解决方法 |
|------|---------|---------|
| 4K 视频卡顿、CPU 飙升 | 该格式的硬解不可用，在软解 | 查 `media_codecs.xml` 是否支持该格式+分辨率；换 H.264 或降分辨率对比验证 |
| HLS 流无法播放（老盒子） | 系统/播放器不支持 fMP4 分片 | 升级 Media3；或服务端改用 .ts 分片的 HLS |
| 遥控器点击无响应 | View 没设 `focusable=true` | XML 加 `android:focusable="true"`，检查焦点链 |
| 会员 4K 内容只能放 1080p | 盒子只有 Widevine L3（软件 DRM） | 换有 L1 认证的盒子；这是硬件门槛，软件无法绕过 |
| DRM 内容报 401 | License 服务器鉴权失败 | 检查 License URL 与 Header 配置 |
| 有声音但画面黑着 | 合成/显示链问题，或 HDR 输出不兼容 | 先切 SDR 输出验证；再查 SurfaceFlinger 日志 |
| 声音不对（没声/声道不对） | 直通设置与功放不匹配 | PCM 与 passthrough 二选一测试；确认 eARC/ARC 链路 |
| ADB 连不上 | 未开"网络 ADB"，或盒子 IP 变了 | 开发者选项中开启；核对 IP 与端口 |

## 术语表

| 术语 | 英文 | 一句话说明 |
|------|------|-----------|
| SoC | System-on-Chip | 把 CPU/GPU/VPU/控制器集成进一颗芯片，盒子的心脏 |
| VPU | Video Processing Unit | 专做视频编解码的硬件引擎，盒子硬解的唯一来源 |
| GPU | Graphics Processing Unit | 干 UI 渲染和图层合成；盒子 GPU 普遍不强但够用 |
| DMA | Direct Memory Access | 外设不经过 CPU 直接读写内存，数据搬运的"直通车" |
| MediaCodec | MediaCodec | Android 给所有 App 的统一编解码接口，硬解软解通吃 |
| Codec2 / OMX | Codec2 / OpenMax | 两代编解码框架；新 Codec2（`c2.*`），老 OMX（`omx.*`）兼容保留 |
| 软解 / 硬解 | SW / HW decode | CPU 算 vs 专用硬件算；盒子 4K 必须靠硬解 |
| SurfaceFlinger | SurfaceFlinger | Android 的窗口合成器，把视频层/UI 层合成一帧 |
| vsync | Vertical Sync | 显示器的刷新节拍，合成器按它出帧，避免撕裂/跳帧 |
| YUV | YUV | 解码输出的原始像素格式（亮度+色度分离），比 RGB 省带宽，适合硬件链 |
| passthrough | Bitstream Passthrough | 音频位流不解码、原样直通给功放处理 |
| ARC / eARC | Audio Return Channel | HDMI 上的返回音频通道；eARC 带宽更大，可跑全景声 |
| TEE | Trusted Execution Environment | 安全执行环境，Widevine L1 解密发生的地方 |
| Widevine L1/L3 | Widevine | 谷歌 DRM 分级：L1=硬件安全（可放 4K 内容），L3=软件安全 |
| Leanback | Leanback Library | Google 给 TV/盒子的 UI 组件库，焦点导航的标配 |
| DPAD | Directional Pad | 遥控器方向键，对应 `KeyEvent.KEYCODE_DPAD_*` |
| 十英尺 UI | 10-foot UI | 面向 3 米外观看的界面设计：字大、操作少 |
