> **适合读者**：在线教育、企业培训、大班直播类平台的后端工程师

## 一、教育场景的三种形态

读完本节，你能根据课程形态直接判断该用直播架构还是会议架构。

教育是"直播"和"会议"两种技术的交叉路口，先分清形态再谈架构：

| 形态 | 规模 | 延迟要求 | 互动性 | 合适的架构 |
|------|------|---------|--------|-----------|
| **大班课**（公开课、名师 lecture） | 1 对 1 千 ~ 10 万 | 3-10s 可接受 | 弱（弹幕/答题） | 直播架构（第 28 篇） |
| **小班课**（K12 班课、口语营） | 2-16 人 | < 300ms | 强（人人开麦） | 会议架构 SFU（第 29 篇） |
| **1v1**（答疑、辅导） | 2 人 | < 300ms | 最强 | WebRTC P2P 即可 |

**教育特有的延迟分层**是选型的关键判断：

- **老师在讲，学生在听**——直播延迟 5 秒完全无感（学生看到的是"5 秒前的课堂"）；
- **老师提问，学生要答**——这 5 秒立刻变成灾难（老师说"听懂的扣 1"，5 秒后才知道响应）。所以凡是**有实时互动环节的课堂，互动部分必须走 RTC**。

> **常见误判**：把大班课做成万人 RTC 房间。SFU 转发不转码（第 29 篇），1 万路下行就是 1 万路带宽直出，成本是 CDN 分发的几十倍；而大班课 95% 的时间只有老师在说话——用 RTC 扛万人，花的钱都浪费在"听"上。正确做法是：**听走 CDN，说走 RTC**（见第四节）。

## 二、大班课：复用直播架构

读完本节，你能给出万人课堂的完整链路与成本结构。

大班课在技术上就是一场直播（第 28 篇的架构原样适用），差异在业务层：

```
老师端（OBS / 网页推流）
    │ RTMP 或 WHIP 推流
    ▼
流媒体集群（SRS / MediaMTX，Origin-Edge）
    │ 转码集群：1080p 主流 + 480p 低码率流（弱网学生）
    ▼
CDN（LL-HLS / HTTP-FLV）
    │
    ▼
学生端（hls.js / mpegts.js 播放器）

    ┄┄┄┄┄┄┄┄ 以下不走媒体流，走业务通道 ┄┄┄┄┄┄┄┄
    弹幕/答题/签到：WebSocket 长连接（第 28 篇的 IM 架构，教育化处理见第五节）
    课件翻页事件：同一个 WebSocket 通道
```

与秀场直播的三个业务差异：

1. **码率策略不同**：课程画面以 PPT 文字为主，**静态内容多、运动少**——同等内容可以用更低码率；但 PPT 小字对分辨率敏感，低码率档位不要低于 480p，否则字幕糊掉（影响的是教学效果，不只是观感）。
2. **观看时长长**：一节课 45-90 分钟，CDN 流量成本按峰值带宽计费时，要注意"全国统一上课时间"造成的整点峰值（比秀场直播陡峭得多）——提前预热 CDN 边缘节点。
3. **回看是刚需**：直播即录像（第 23 篇），下课后 1 小时内出回放是基本要求（补课场景见第八节）。

## 三、小班课：RTC 互动

读完本节，你能复用会议架构搭起 16 人互动课堂，并理解教育场景的三个特殊处理。

小班课就是一个会议房间（SFU 选型与部署直接看[第 29 篇](29-视频会议技术架构.md)），教育场景的增量需求有三点：

**1. 双流：摄像头 + 屏幕/课件**

老师和学生的"面子"与"里子"是两路流：

```
老师端同时发布：
  ├── 摄像头流（360p 足矣——学生更关心课件清晰度）
  └── 屏幕共享流（1080p，PPT 文字必须锐利）

学生端订阅：
  ├── 老师屏幕流（必须）
  ├── 老师摄像头流（小窗）
  └── 其他学生摄像头流（按需：看谁在说话显示谁）
```

屏幕共享流的编码参数和摄像头不同：帧率可以低（PPT 翻页 5fps 够），但**每次翻页要强制关键帧**，且码率策略偏静态（Screencast 屏幕共享编码，WebRTC 的 `contentHint: "detail"`）。

**2. Simulcast 是弱网学生的生命线**（第 29 篇）：每个学生按自己的网络订阅高/中/低档，家里 WiFi 差的学生看 180p 摄像头 + 完整音频，**音频永不降档**（第九节）。

**3. 房间生命周期与课堂绑定**：排班系统开课自动建房、生成入会 Token（[第 29 篇](29-视频会议技术架构.md)练习 3 的 LiveKit Token 模式），下课自动结束录制、销毁房间。房间 ID 与课程 ID 在业务库关联，回放才能挂到课表上（房间完整状态机见第六节）。

## 四、大班课 + 连麦：混合架构（本章核心）

读完本节，你能画出"万人听课、随时举手上台"的混合链路，并处理两个时间线的对齐问题。

这是教育场景最经典的难题：**大班课用 CDN（5s 延迟），被点名上台的学生用 RTC（200ms），两拨人在同一个课堂里**。

```
                    ┌─────────────────────────────────┐
                    │  RTC 连麦房间（SFU，<300ms）      │
 老师A ──┐          │                                 │
 学生B ──┼─────────→ │  连麦者：老师 + 被点名的学生      │
 学生C ──┘          └───────────┬─────────────────────┘
                                 │ 服务端合流（MCU 式）
                                 │ 把房间多路流混成一路
                                 ▼
                    RTMP 转推 → 流媒体集群 → CDN（LL-HLS）
                                 │
                    ┌────────────┴───────────────────┐
                    ▼                                ▼
              其余 9997 名观众（HLS，3-5s）      云端录制 → 回放

 信令面（WebSocket）：
   学生举手 → 老师批准 → 信令服务通知学生B"上台"
   → 学生B 播放器从 HLS 切换到 RTC 拉流
   → 下台时切回 HLS
```

三个关键设计：

**1. 合流在服务端，不在老师端。** 连麦房间里的多人画面由服务端混流成一路标准直播流再转推 CDN——观众端只是一个普通播放器，完全不感知房间里发生的事。混流可以用 FFmpeg（拉 N 路 WebRTC/SRT 转码拼接）或专用 MCU 组件，选型看延迟预算：FFmpeg 合流链路延迟约 1-2s，能接受则成本最优。

**2. 上台/下台的切换体验。** 学生从 HLS 切到 RTC 时，画面会"跳到最新"（跨过 3-5 秒的 CDN 延迟）——这是**特性不是 bug**：上台者必须和老师同处一个时间线。反向（下台切回 HLS）同理。切换瞬间给个转场动画即可，学生感知是"进入实时模式"。

**3. 延迟差对互动设计的影响。** 观众比连麦者慢 3-5 秒，意味着：弹幕答题的"正确答案揭晓"要考虑观众端还没看到题面（出题后老师留 5 秒缓冲）；老师读弹幕提问时观众看到的提问是 5 秒前的——**运营上要培训老师预留延迟**，技术上无解，这是 CDN 分发的物理属性。

## 五、互动与消息：弹幕、答题、签到

读完本节，你能设计承载万人在线互动的消息架构，并处理答题与签到的服务端职责。

大班课的互动不走媒体通道，走独立的 WebSocket 消息服务（第 28 篇直播 IM 架构直接复用），但教育场景给消息服务增加了三个直播场景没有的服务端职责：

```
学生端（WebSocket 长连接）
    │  弹幕 / 答题 / 签到 / 举手  上行
    ▼
消息网关（水平扩容、按教室路由、过滤与限频）
    │
    ▼
互动服务（答题聚合、签到幂等去重、举手审批）
    │  结果与事件  下行
    ▼
学生端（弹幕滚动、答案揭晓、签到确认）
```

1. **答题统计在服务端聚合**：万人同时作答，不能把 1 万份答案全量广播。学生端只上报"选了什么"，服务端聚合每课堂每题的票数 + 参与人数，再广播**统计结果**（"81% 选 A"）而不是原始答案——下行量从 O(万人) 降到 O(题目数)。
2. **签到要扛并发尖峰 + 天然幂等**：开课瞬间万人同时点击。客户端节流（每人每节课只发一次），服务端按"课堂 + 学生"做幂等去重，签到结果异步写库、不阻塞消息返回。
3. **消息必须带统一时间戳**：互动消息与音视频是两条通道（白板同理，见第七节），事件入库打统一时间轴，回放时才能把"当时有哪些学生答了什么"还原到对应时间线。

## 六、课堂生命周期与业务系统

读完本节，你能设计从排课到回放归档的课堂状态机，并用信令层实现权限与纪律。

课堂不是"一场直播"，而是一段**有开始和结束的业务生命周期**：媒体系统只处理"课中"，业务系统负责课前的预约建课、课中的权限纪律、课后的归档出回放。

```
课前：排课 → 预约媒体资源（CDN 流名 / RTC 房间 + 逐人签发入会 Token）
      → 教室链接与课件、花名册绑定
课中：开课（主讲推流触发）→ 学生凭 Token 入会
      → 互动（答题/签到/连麦/白板）与纪律（禁言/踢人）并行
课后：下课事件 → 停流、触发录制收尾 → 转码归档出回放（第八节）→ 挂到课程页
```

三个业务要点：

1. **课堂状态机驱动一切**：`未开始 → 直播中 → 已结束 → 已生成回放`。状态转换由事件触发（下课按钮 / 排课定时），媒体启停与录像开关都挂在状态机上——避免"忘了开录像 / 忘了关直播"。
2. **角色与纪律是信令层动作**：主讲（唯一推流者）/ 助教（可禁言、踢人、发通知）/ 学生（只订阅）。全场静音、踢人、禁言在业务服务的权限层执行（吊销/重签 Token、发指令到消息服务），再由 SFU / 播放器端配合生效——不做成媒体层硬操作。
3. **花名册与出勤**：课堂绑定班级花名册，学生入会即签到（复用第五节幂等去重），出勤记录与课程表关联；回放补看的学生自动补签到。

## 七、课件与白板同步

读完本节，你能理解"白板是数据流不是视频流"，并做出正确的技术选型。

新手最容易犯的错：**把课件/白板当作一路视频流来推**。错误的原因：

| 维度 | 课件当视频推 | 课件当数据同步 |
|------|-------------|---------------|
| 带宽 | 持续 500kbps-2Mbps | 翻页时几 KB |
| 文字清晰度 | 1080p 视频流里的 PPT 小字被压缩成糊 | 矢量/位图原样渲染，放大不糊 |
| 回放 | 和视频绑死 | 可独立回放、可检索 |
| 弱网 | 网差 = 课件糊成马赛克 | 网差只影响翻页延迟 |

正确架构：**白板走数据通道（WebSocket 或 WebRTC DataChannel），音视频走媒体流，两条通道时间轴对齐**：

```
老师端
  ├── 媒体流：摄像头 + 麦克风 ──→ SFU/CDN ──→ 学生播放器
  └── 信令流：翻页/画笔/激光笔事件 ──→ WebSocket ──→ 学生端白板组件
        （事件带课堂时间戳，录制时与媒体轨对齐）
```

白板事件的同步语义（乱序重绘、中途加入的学生要拿到"当前页 + 已有笔迹"）属于实时协作数据同步问题（操作变换 OT / 无冲突复制 CRDT），是独立的技术领域——**不要自己发明**，用成熟白板 SDK，或把事件存环形缓冲 + 快照（每页存一份位图快照 + 后续增量）的简单方案。

录制时注意**双轨对齐**：白板事件流和音视频流分别存，回放引擎按统一时间戳驱动两边——这样回放时学生还能"拖动白板翻页"而不是被动看一段糊掉的视频。

## 八、课堂录制与补课

读完本节，你能设计"下课 1 小时出回放"的录制链路。

| 录制方案 | 实现 | 适用 |
|---------|------|------|
| 合流单轨 | 服务端把老师 + 课件混成一路录制（MCU 输出直接落盘） | 大班课（回放就是"再看一遍直播"） |
| 双轨分离 | 摄像头轨、白板轨分开录，回放时合成 | 小班课/1v1（回放可只看白板、倍速、拖动） |
| 按需点播 | 录制 → 转码 → 切 HLS → 对象存储 | 复用[第 23 篇](../02-工程实践优化/23-录像存储与时间轴回放.md)方案 |

补课场景的三个细节：

1. **断点续看**：学生中途断线重连后，直播流从"最新"继续（直播语义）；但补课时要从断点看（点播语义）——录制服务把分片实时写入对象存储，回放入口提供"从第 N 分钟开始"。
2. **录制权限**：不是所有课都允许回放（家长隐私顾虑、版权课），录制策略要做成课程属性而非全局配置。
3. **加密与防盗**：付费课程的回放是盗版重灾区，签名 URL + AES-128 的组合见[第 22.5 篇](../02-工程实践优化/22.5-流媒体安全鉴权防盗链与DRM.md)。

## 九、弱网学生的体验优化

读完本节，你能设计一条"逐级降级但不掉线"的体验保障链。

在线教育的用户网络质量方差极大（同一节课里既有千兆光纤也有 4G 山区信号），降级链设计目标：**宁可降质，绝不掉课**：

```
网络质量（WebRTC getStats / 播放器缓冲监测）
    │
    ▼
降级顺序（从上到下逐级触发，网络恢复逐级回升）：
  ① 视频 720p → 360p → 180p          （Simulcast 换层 / ABR 降档）
  ② 视频帧率 30 → 15 → 5             （PPT 课 5fps 完全可看）
  ③ 只保留音频 + 白板位图快照          （白板是数据流，几乎不占带宽）
  ④ 音频降码率 48kbps Opus            （最后一个降，最先恢复）
  ⑤ 兜底：电话拨入 / 图文直播           （极端弱网，课堂不中断）
```

两个原则：

- **音频永远最后降**：教学场景"听得见"比"看得见"重要得多——老师的声音是主线，画面是辅助。WebRTC 的 SDP 里给音频轨设置更高优先级（`priority: high`）。
- **降级要提前、恢复要滞后**（滞回）：丢包率 5% 就开始降，恢复到 2% 且稳定 30 秒才升档——频繁升降档比稳定低档更伤体验。

## 动手实践

### 练习1：大班课最小链路与延迟测量

```bash
# 1. 启动 MediaMTX（支持 LL-HLS）
docker run -d --name mediamtx -p 8554:8554 -p 8888:8888 -p 1935:1935 \
  bluenviron/mediamtx:latest

# 2. 老师端推流（OBS 或 FFmpeg 模拟）
ffmpeg -re -i lecture.mp4 -c:v libx264 -preset veryfast -b:v 1200k \
  -c:a aac -b:a 64k -f flv rtmp://localhost:1935/live/class1

# 3. 学生端用 hls.js 播放 http://localhost:8888/live/class1/index.m3u8
# 4. 老师端对着秒表读时间，学生端截图对比 —— 记录端到端延迟
```

**预期输出**：HLS 播放延迟 3-8 秒；把 MediaMTX 的 `hlsPartDuration` 调到 200ms（LL-HLS）后延迟降到 2-4 秒。体会第一节"讲课可容忍"的延迟量级。

### 练习2：小班课 + 屏幕共享（复用第 29 篇部署）

```javascript
// 浏览器端：同时发布摄像头 + 屏幕（双流）
const pc = new RTCPeerConnection();

const cam = await navigator.mediaDevices.getUserMedia({ video: true, audio: true });
cam.getVideoTracks()[0].contentHint = "motion"; // 摄像头：动态
pc.addTrack(cam.getVideoTracks()[0], cam);

const screen = await navigator.mediaDevices.getDisplayMedia({ video: true });
screen.getVideoTracks()[0].contentHint = "detail"; // 课件：清晰优先，帧率可低
pc.addTrack(screen.getVideoTracks()[0], screen);
```

**预期输出**：另一位参会者小窗看摄像头、主窗看屏幕共享；打开任务管理器对比"屏幕共享走 detail 提示"后，PPT 翻页文字更清晰、帧率更低（约 5-15fps）——验证第三节的 contentHint 差异。

### 练习3：举手连麦信令（WebSocket 消息序列）

```json
{"type": "raise_hand", "studentId": "s1024", "ts": 1760000000}
{"type": "invite_to_stage", "studentId": "s1024", "rtcRoomId": "class1-stage", "token": "eyJ..."}
{"type": "stage_joined", "studentId": "s1024"}
{"type": "leave_stage", "studentId": "s1024", "resumeUrl": "http://cdn.example.com/live/class1.m3u8"}
```

**预期输出**：用两个浏览器标签 + WebSocket 调试工具（或 wscat）模拟老师端与学生端，走完"举手 → 邀请（下发 RTC 房间与 Token）→ 上台 → 下台（下发回切 HLS 地址）"全流程。注意邀请消息里包含 RTC 入会凭证、下台消息里包含回切地址——第四节切换体验的后端支撑就这两个字段。

## 常见问题排查

| 现象 | 可能原因 | 解决方法 |
|------|---------|---------|
| 万人开课时 CDN 边缘节点被打穿 | 整点上课，峰值带宽陡峭 | 提前 10 分钟预热（低码率垫片流占住边缘缓存）；按区域分级扩容 |
| 小班课学生看老师屏幕"糊" | 屏幕流按摄像头参数编码（运动优化） | `contentHint: "detail"` + 提高码率上限 + 关闭 B 帧 |
| 连麦后观众听到双重声音 | 合流输出混入了房间回声 + 学生端又播了 CDN 流 | 上台者客户端静音 HLS 播放（信令切换时强制执行） |
| 上台学生画面比老师慢 3 秒 | 上台者实际走的是 CDN 流而非 RTC | 检查 invite 消息的 RTC 地址与 Token 是否生效，播放器是否真正切换 |
| 开课瞬间万人签到把消息服务打满 | 签到并发尖峰 + 客户端重复点击 | 客户端节流（每节课只发一次）；服务端按"课堂+学生"幂等去重；签到结果异步落库不阻塞返回 |
| 答题计票不准 / 一人多票 | 未按学生去重 | 服务端按"课堂 + 学生 + 题号"幂等，重复作答只记第一次 |
| 白板笔迹丢失/乱序 | 数据通道消息无序或中途加入未同步快照 | 事件加序号重排；新加入者先发当前页位图快照再发增量 |
| 课堂录制回放音画错位 | 白板轨与媒体轨时间戳基准不同 | 统一用 NTP/服务器时间戳，录制启动时校准基准偏移 |

## 术语表

| 术语 | 英文 | 说明 |
|------|------|------|
| 大班课 | Large-scale Live Class | 1 对多的直播形态课堂，走 CDN 分发 |
| 小班课 | Small Interactive Class | 多人强互动课堂，走 RTC SFU |
| 连麦 | Co-hosting / Guest Mic | 观众被邀请进入实时互动区的混合直播模式 |
| 合流 | Stream Mixing | 服务端把多路 RTC 流混成一路直播流 |
| contentHint | Content Hint | WebRTC 中标识流内容类型（动态/精细）的编码提示 |
| Simulcast | Simulcast | 同一发送端同时发布多档分辨率，接收端按带宽选层 |
| 课堂状态机 | Class State Machine | 未开始→直播中→已结束→已生成回放 的课堂生命周期管理 |
| 花名册 | Roster | 课堂绑定的学生名单，决定谁能入会与签到 |
| 幂等去重 | Idempotency Key | 按"课堂+学生+题号"去重，防止重复签到/重复答题计票 |
| 白板同步 | Whiteboard Sync | 通过数据通道同步课件/笔迹事件而非视频画面 |
| 滞回 | Hysteresis | 降级与恢复使用不同阈值，避免频繁切换 |
