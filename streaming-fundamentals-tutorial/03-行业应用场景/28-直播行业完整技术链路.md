# 直播行业完整技术链路

> **适合读者**：构建直播平台的后端开发者  
> **核心内容**：推流→转码→分发→播放，一条完整链路逐环拆解

---

## 一、直播链路全图

```
主播端                服务端                         观众端
  │                     │                               │
OBS/手机 ──RTMP/WHIP──→ 接入服务器(SRS/MediaMTX)          │
  │        on_publish 推流鉴权 → ↓                       │
  │            转码服务器（FFmpeg 多码率）                │
  │            1080p / 720p / 480p HLS 切片              │
  │                     │ 分发(回源/预热)                 │
  │              CDN 源站 ──→ 边缘节点 ×N                │
  │                     │ HLS(m3u8) / HTTP-FLV            │
  │                     └──────────────────────────→ 观众
  │                                                       播放器
  │               业务服务（Go）
  │               ├── 直播间管理（状态机）
  │               ├── 弹幕（WebSocket + Redis）
  │               ├── 礼物/打赏（校验→扣减→广播）
  │               └── 连麦（WebRTC SFU + 混流）
```

**链路关键点**：观众永远接触不到推流端（RTMP），只从 CDN 边缘拉 HTTP 协议（HLS/HTTP-FLV）。
每一环解决一个问题——本章按「推流→转码→分发→播放→互动→录制」顺序全部打通。

## 二、推流接入：OBS → SRS

**推流协议选型**：
- **RTMP**：主流，OBS / 手机端 App 原生支持（详见第 8 篇）
- **WHIP**：浏览器直接推流（WebRTC 封装，详见第 13 篇）

SRS 接收推流，并把推流/断流事件回调给业务服务做鉴权与状态管理：

```
vhost __defaultVhost__ {
    http_hooks {
        enabled       on;
        on_publish    http://localhost:8080/api/v1/streams/on_publish;
        on_unpublish  http://localhost:8080/api/v1/streams/on_unpublish;
    }
}
```

**推流鉴权（防盗推）**：业务服务生成限时 Token 拼在推流地址后面，SRS 收到推流请求先回调询问「这个流密钥 + Token 合法吗」，合法才放行。

```go
// 生成推流 Token（限时 24h）
func GeneratePushToken(streamKey, secretKey string) string {
    expire := time.Now().Add(24 * time.Hour).Unix()
    raw := fmt.Sprintf("%s-%d-%s", streamKey, expire, secretKey)
    sign := fmt.Sprintf("%x", md5.Sum([]byte(raw)))
    return fmt.Sprintf("?expire=%d&sign=%s", expire, sign)
}

// 验证推流 Token：签名匹配 + 未过期才放行
func verifyToken(streamKey, token, secretKey string) bool {
    q, _ := url.ParseQuery(strings.TrimPrefix(token, "?"))
    expire, _ := strconv.ParseInt(q.Get("expire"), 10, 64)
    sum := fmt.Sprintf("%x", md5.Sum([]byte(fmt.Sprintf("%s-%d-%s", streamKey, expire, secretKey))))
    return sum == q.Get("sign") && time.Now().Unix() < expire
}

// SRS on_publish 回调：HTTP 200 放行，否则拒绝（与第 22.5 篇一致）
func (h *StreamHandler) OnPublish(c *gin.Context) {
    var req struct {
        StreamKey string `json:"stream"`
        Token     string `json:"token"`
    }
    if err := c.ShouldBindJSON(&req); err != nil {
        c.JSON(401, gin.H{"code": 401})
        return
    }
    if !verifyToken(req.StreamKey, req.Token, h.secretKey) {
        c.JSON(403, gin.H{"code": 403})
        return
    }
    c.JSON(200, gin.H{"code": 0}) // 200 = 放行
}
```

## 三、多码率转码

一路推流进来，转成 1080p/720p/480p 三路：画质给大屏观众、低码率给弱网观众，由播放器按带宽**自动切换**（ABR）。

```go
// 一路推流输入，输出三种码率
func StartMultibitrateTranscode(ctx context.Context, inputURL, outputDir string) error {
    profiles := []struct {
        Name    string
        Bitrate string
        Size    string
    }{
        {"1080p", "3000k", "1920x1080"},
        {"720p", "1500k", "1280x720"},
        {"480p", "600k", "854x480"},
    }

    args := []string{"-re", "-i", inputURL}

    for _, p := range profiles {
        out := filepath.Join(outputDir, p.Name, "stream.m3u8")
        os.MkdirAll(filepath.Dir(out), 0755)
        args = append(args,
            "-c:v", "libx264", "-preset", "veryfast",
            "-b:v", p.Bitrate, "-s", p.Size,
            "-c:a", "aac", "-b:a", "128k",
            "-f", "hls", "-hls_time", "2",
            "-hls_list_size", "10",
            "-hls_flags", "delete_segments",
            out,
        )
    }

    cmd := exec.CommandContext(ctx, "ffmpeg", args...)
    log.Info().Strs("args", args).Msg("启动多码率转码")
    return cmd.Run() // 直播持续期间常驻，放在 goroutine 里跑
}
```

三路输出要用一个**主播放列表（master playlist）**汇总，播放器才拿得到「我有哪几个码率」：

```m3u8
#EXTM3U
#EXT-X-STREAM-INF:BANDWIDTH=3000000,RESOLUTION=1920x1080
1080p/stream.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=1500000,RESOLUTION=1280x720
720p/stream.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=600000,RESOLUTION=854x480
480p/stream.m3u8
```

> 关键帧对齐、ABR 切换细节见第 18 篇。转码是直播里**最贵的一环**（非线性 CPU 成本），峰值只用主码率的场景（户外、小直播间）可以考虑跳过转码直接分发原始流。

## 四、CDN 分发与观众播放（链路闭环）

转码输出的是一个 master.m3u8 + 一堆 2 秒切片，要推送到 CDN 源站，观众从**最近的边缘节点**拉取。这一环让链路真正闭合：

```
播放器请求 → CDN 边缘(最近节点) → 命中? 直接回 │ 未命中 → 回源站拉一次，缓存本地
                                      ↓
            拿到 master → 按带宽选 720p/stream.m3u8 → 逐片拉取 .ts 边下边播
```

```bash
# 观众看到的播放地址长这样：
#   http://play.example.com/live/room123/index.m3u8
# 验证链路：
curl -s http://play.example.com/live/room123/index.m3u8   # 能拿到 master 列表
ffplay http://play.example.com/live/room123/index.m3u8    # 能直接播放出画面
```

**直播分发必须盯的两个指标**（CDN 原理详见第 22 篇）：
- **回源率**：观众多、回源少才省钱——m3u8 用 `no-cache` + ETag 回源校验，切片 `public, max-age` 长缓存
- **预热**：开播前把 master + 首批切片提交给 CDN 预热 API，否则第一个观众承担全量回源，开播瞬间卡

**防盗链**靠 CDN 鉴权 URL（时间戳签名），与推流鉴权是两码事，详见第 22.5 篇。
**降低延迟**：需要 1-3s 延迟的国内直播换 HTTP-FLV，需要 200ms 互动级的用 WebRTC WHEP，见第 21 篇。

## 五、弹幕系统（WebSocket + Redis）

**上行**：客户端 WebSocket 发弹幕 → 服务端校验（敏感词、频控）→ 入库。
**下行**：广播给房间内所有连接，同时写进 Redis Stream 供进房观众回放。

```go
// 弹幕房间管理
type DanmuRoom struct {
    mu      sync.RWMutex
    clients map[string]*websocket.Conn
    roomID  string
    rdb     *redis.Client
}

func (r *DanmuRoom) Broadcast(msg *DanmuMessage) {
    // 1. 持久化到 Redis Stream（进房时可回放历史弹幕）
    r.rdb.XAdd(context.Background(), &redis.XAddArgs{
        Stream: fmt.Sprintf("danmu:%s", r.roomID),
        MaxLen: 1000, // 只保留最近 1000 条
        Values: map[string]interface{}{
            "user":    msg.UserID,
            "content": msg.Content,
            "time":    msg.Timestamp,
        },
    })

    // 2. 快照出客户端列表，锁外写——慢连接不能卡住全局广播锁
    r.mu.RLock()
    clients := make([]*websocket.Conn, 0, len(r.clients))
    for _, conn := range r.clients {
        clients = append(clients, conn)
    }
    r.mu.RUnlock()

    // 3. 广播
    data, _ := json.Marshal(msg)
    for _, conn := range clients {
        if err := conn.WriteMessage(websocket.TextMessage, data); err != nil {
            log.Warn().Msg("弹幕发送失败，客户端已断开")
        }
    }
}
```

**历史弹幕**：观众进房先读 Stream 尾部再进入实时订阅，观感上弹幕不会断：

```go
// 进房时回放最近 100 条历史弹幕
msgs, _ := r.rdb.XRangeN(context.Background(), "danmu:"+roomID, "-", "+", 100).Result()
```

**多实例扩展**：内存广播只对**同一进程**的连接生效。多实例部署时改为「客户端→任意实例→Redis Pub/Sub 房间频道→所有实例订阅→各自广播给本机连接」，广播逻辑不变，只是消息来源多了一个订阅通道。

## 六、礼物与打赏系统

**关键原则**：金额永远走服务端事务（客户端报的礼物信息一律不信任），成功后异步广播全站特效。

```go
func (s *GiftService) SendGift(ctx context.Context, userID, anchorID, giftID string) error {
    // 1. 事务：余额扣减（条件写进 UPDATE，防并发超扣）+ 礼物流水入库
    err := s.db.Transaction(func(tx *gorm.DB) error {
        // UPDATE users SET balance = balance - price WHERE user_id=? AND balance >= price
        // INSERT INTO gift_records(user_id, anchor_id, gift_id, amount)
        return nil
    })
    if err != nil {
        return xerr.Wrap(xerr.ErrInsufficientBalance.Code, "余额不足", err)
    }
    // 2. 事务成功后才广播礼物事件，观众端统一播特效
    s.hub.Broadcast("gift:"+anchorID, json.Marshal(giftMsg))
    return nil
}
```

上线必做三件事：**限频**（防刷屏，连续礼物合并成一次特效）、**主播收益异步入账**（结算脚本，不等直播结束）、**流水可对账**（礼物总单数 = 用户扣费单数）。

## 七、连麦（WebRTC）

主播与嘉宾实时音视频互动：

```
主播 A                        嘉宾 B
WebRTC Offer ──→ SFU ──→ WebRTC Answer
                  │
                  ├── 将嘉宾画面合并到主播推流（服务端混流）
                  └── 观众端看到 PIP（画中画）
```

混流命令：

```bash
# FFmpeg 把主播流 + 嘉宾流合并为一路（画中画）
ffmpeg \
  -i rtmp://localhost/live/host \
  -i rtmp://localhost/live/guest \
  -filter_complex \
    "[0:v][1:v]overlay=W-w-10:H-h-10[out]" \  # 右下角画中画
  -map "[out]" -map "0:a" \
  -c:v libx264 -preset veryfast \
  -c:a aac \
  -f flv rtmp://localhost/live/mixed
```

> 连麦会话与直播间状态联动，见第八节；SFU 选型（Livekit/mediasoup）见第 29 篇。

## 八、直播间状态机

状态迁移由 SRS 推流/断流回调驱动，心跳超时做兜底：

```
pending ──on_publish──→ live ──on_unpublish / 心跳超时──→ ended
   │                        │
   └──────── 人工下架 ───────┴─────────────→ banned（封禁）
```

```go
type LiveStatus string
const (
    LiveStatusPending LiveStatus = "pending" // 未开播
    LiveStatusLive    LiveStatus = "live"     // 直播中
    LiveStatusEnded   LiveStatus = "ended"    // 已结束
    LiveStatusBanned  LiveStatus = "banned"   // 被封禁
)

// SRS on_publish 回调更新状态
func (s *LiveService) OnStreamPublish(ctx context.Context, streamKey string) error {
    room, err := s.repo.GetByStreamKey(ctx, streamKey)
    if err != nil {
        return xerr.Wrap(xerr.ErrNotFound.Code, "直播间不存在", err)
    }
    if room.Status == string(LiveStatusBanned) {
        return xerr.New(xerr.ErrForbidden.Code, "直播间已被封禁")
    }
    return s.repo.Update(ctx, room.RoomID, map[string]interface{}{
        "status":     LiveStatusLive,
        "start_time": time.Now().UnixMilli(),
    })
}

// SRS on_unpublish 回调：主播掉线/主动关播
func (s *LiveService) OnStreamUnpublish(ctx context.Context, streamKey string) error {
    room, err := s.repo.GetByStreamKey(ctx, streamKey)
    if err != nil {
        return xerr.Wrap(xerr.ErrNotFound.Code, "直播间不存在", err)
    }
    // 联动：结束连麦会话 → 录制封片上传 → 状态置 ended
    return s.repo.Update(ctx, room.RoomID, map[string]interface{}{
        "status":  LiveStatusEnded,
        "end_time": time.Now().UnixMilli(),
    })
}

// 兜底：回调丢失（进程崩溃、异常退出）时，靠心跳超时自动关播
// 客户端每 N 秒上报心跳更新 last_heartbeat，
// 定时任务扫描「live 且 last_heartbeat < now-60s」的房间批量标记 ended。
```

> 注意：主播推流断了但没走回调，直播间会**僵尸挂着**（观众看着卡死的画面）——心跳兜底是生产上线前必须做的。

## 九、录制与回放

直播记录是刚需（回看、复盘、监管留证）。最省的做法：**录转码前的原始流**（省一份转码 CPU），用 FFmpeg 分段切片：

```bash
# 边转码边分段录制（按 1 小时切一个新文件）
ffmpeg -i rtmp://localhost/live/room123 \
  -c:v copy -c:a copy   \            # 直接拷贝，不重编码
  -f segment -segment_time 3600 \
  -segment_format mp4 \
  out/room-%Y%m%d%H.mp4
```

**断流封片**：on_unpublish 回调触发时，把最后一个不完整切片封成完整文件，连同 m3u8 一起转存 S3，观众走第 23 篇的点播回放链路。回放与直播共用「直播 → 分片 → 点播」的转换，只是播放入口从实时索引换成完整索引。

## 本篇小结

直播平台核心模块：

| 模块 | 技术方案 |
|------|---------|
| 推流接入 | SRS/MediaMTX + RTMP/WHIP |
| 推流鉴权 | on_publish 回调 + MD5 签名 Token |
| 多码率转码 | FFmpeg 多输出 + master playlist（ABR） |
| CDN 分发/播放 | 边缘节点 + HLS/HTTP-FLV，m3u8 短缓存、切片长缓存 |
| 弹幕 | WebSocket 广播 + Redis Stream 历史回放 + Pub/Sub 跨实例 |
| 礼物 | 服务端事务扣款 → 异步广播特效 |
| 连麦 | WebRTC SFU（Livekit/mediasoup）|
| 状态机 | 开播/断流回调 + 心跳超时兜底 |
| 录制 | FFmpeg 分段切片 → 封片存 S3 → 点播回放 |

**预期输出**：OBS 推流后 ffplay 播放出画面，延迟约 8-15s（标准 HLS）；SRS API 返回当前在线人数。这是第 1 篇「流」最直观的一次目视验证。

### 练习2：WebSocket 弹幕系统（Go）
```go
// 弹幕广播：收到弹幕后向房间内所有连接广播
type DanmuHub struct {
    rooms map[string]map[*websocket.Conn]struct{}
    mu    sync.RWMutex
}

func (h *DanmuHub) Broadcast(roomID string, msg []byte) {
    h.mu.RLock()
    defer h.mu.RUnlock()
    for conn := range h.rooms[roomID] {
        conn.WriteMessage(websocket.TextMessage, msg)
    }
}

// Handler 升级 WebSocket 并加入房间
func (h *DanmuHub) Join(c *gin.Context) {
    roomID := c.Query("room_id")
    conn, _ := upgrader.Upgrade(c.Writer, c.Request, nil)
    h.mu.Lock()
    if h.rooms[roomID] == nil {
        h.rooms[roomID] = make(map[*websocket.Conn]struct{})
    }
    h.rooms[roomID][conn] = struct{}{}
    h.mu.Unlock()
    defer func() {
        h.mu.Lock(); delete(h.rooms[roomID], conn); h.mu.Unlock()
        conn.Close()
    }()
    for {
        _, msg, err := conn.ReadMessage()
        if err != nil { break }
        h.Broadcast(roomID, msg)
    }
}
```
**预期输出**：多个浏览器连接同一房间，一端发弹幕后所有端实时收到，延迟 < 100ms。把它接上第五节的历史弹幕，进房也能看到之前的弹幕。

### 练习3：推流鉴权闭环（生成 → 校验 → 单测）
```go
// 给第二节的 GeneratePushToken / verifyToken 写单测，验证闭环
func TestVerifyToken(t *testing.T) {
    secret := "my-secret"
    token := GeneratePushToken("room123", secret)

    if !verifyToken("room123", token, secret) {
        t.Fatal("合法 Token 不应被拒绝")
    }
    forged := strings.Replace(token, "sign=", "sign=0000", 1)
    if verifyToken("room123", forged, secret) {
        t.Fatal("被篡改的 Token 不应通过")
    }
    if verifyToken("other-room", token, secret) { // 串密钥对不上
        t.Fatal("错房间的 Token 不应通过")
    }
}
```
**预期输出**：合法 Token 通过、篡改签名拒绝、过期拒绝，配合 SRS on_publish 回调实现「非授权推流进不来」。

## 常见问题排查

| 现象 | 可能原因 | 解决方法 |
|------|---------|---------|
| OBS 推流断连 | 服务器带宽不足或防火墙拦截 1935 | 检查服务器上行带宽，开放 TCP 1935 端口 |
| 直播延迟突然增大 | CDN 节点异常，流量绕远路 | 检查 CDN 健康状态，切换备用 CDN |
| 观看人数统计不准 | 播放器重连导致重复计数 | 用 session ID 去重，断线 30s 内重连算同一用户 |
| 弹幕消息丢失 | WebSocket 消息未 ACK，服务端丢弃 | 关键弹幕改用 Redis Pub/Sub + 持久化，非关键弹幕允许丢 |
| 连麦卡顿 | WebRTC SFU 带宽不足 | 配置 Simulcast，低带宽时降级到低分辨率 |
| 主播断流但状态仍是 live | 断流回调丢失（进程崩溃/异常退出） | 客户端心跳上报 + 定时扫描兜底，超时自动标记 ended |
| 观众黑屏 | CDN 回源失败，切片还没生成 | 等 1-2 个切片周期再播；curl 源站 m3u8 检查内容 |
| 观看人数多但回源率很高 | 鉴权 URL 每次都变，CDN 缓存全 MISS | 用 CDN 防盗链方案而非每次不同参数的签名 URL（见 22.5） |

## 术语表

| 术语 | 英文 | 说明 |
|------|------|------|
| 串流密钥 | Stream Key | 主播推流时用于标识房间的唯一密钥 |
| 主播放列表 | Master Playlist | 列出各码率子播放列表的 m3u8，播放器据此做 ABR |
| 切片 | Segment | HLS 把直播切成 2-10s 的小文件（.ts/.fmp4）逐个拉取 |
| ABR | Adaptive Bitrate | 根据观众带宽自动切换码率，弱网降清晰度不卡死 |
| 弹幕 | Danmaku | 飘过屏幕的实时评论，直播互动的核心功能 |
| 连麦 | Co-streaming | 主播与嘉宾通过 WebRTC 实时视频连线 |
| 礼物特效 | Gift Animation | 观众送礼物时触发的全屏动画效果 |
| 推流码率 | Bitrate | 主播推流的编码码率，直接影响画质和带宽消耗 |
| 在线人数 | Concurrent Viewers | 当前同时在观看直播的用户数量 |
| 回源 | Origin Pull | 边缘节点没缓存时回源站拉内容，回源率是 CDN 成本核心指标 |
