# 云游戏流媒体技术

> **适合读者**：对云游戏技术原理感兴趣的开发者  
> **核心问题**：云游戏为什么难？延迟从哪来？技术上如何解决？

---

## 一、云游戏 vs 普通视频流媒体

| 维度 | 普通流媒体（Netflix）| 云游戏 |
|------|---------------------|--------|
| 延迟要求 | < 3s 可接受 | **< 80ms 必须**（否则操作感差）|
| 交互性 | 单向（服务端→客户端）| **双向**（操作 → 服务端 → 画面）|
| 内容 | 预先录制/转码 | **实时渲染**（GPU 实时出帧）|
| 帧率 | 30fps 足够 | **60fps 以上**（FPS 游戏需 120fps）|
| 码率 | 2-8Mbps | **10-30Mbps**（高画质游戏）|

**一句话认知**：普通流媒体是"把已经存在的视频搬运给用户"；云游戏是"在你眼前把画面**现做出来**，且下一帧什么样由你上一条操作决定"。所以它的难点从"怎么传得快"变成"怎么**做一个全闭环**还够快"。

---

## 二、核心认知：双向闭环与"一帧的旅程"

云游戏本质不是"发视频流"，是搭了一条 **输入上行 + 画面下行** 的闭环。用户按一下键，要跑完整个环路才算"有反应"。

```
用户按键 ──上行──→ 云端游戏进程(按输入渲染新一帧) ──下行──→ 屏幕显示出动作
     服务端不可见                              用户不可见
          <------------ 约 80ms 环路（不是单程，是往返）------------>
```

**一帧的旅程**（按 60fps / RTT 20ms 的理想情况）：

| 时刻 | 发生了什么 | 累计延迟 |
|------|-----------|---------|
| t=0 | 你按下 W，客户端采集 | 0 |
| t≈10ms | 输入上行至云端（RTT 的一半）| 10ms |
| t≈27ms | 游戏进程完成本帧渲染（60fps 的预算只有 16.6ms）| 27ms |
| t≈30ms | 帧被捕获 | 30ms |
| t≈35ms | 硬件编码完成（NVENC ≈ 5ms）| 35ms |
| t≈45ms | 下行传输 + 解码完成 | 45ms |
| t≈55ms | 合成显示（VSync 缓冲 < 8ms）| ≈55ms，留 25ms 余量打满 80ms |

**看懂这张表，就看懂了云游戏**：环路延迟 = 网络往返（RTT）＋ 运算延迟（渲染/编码/解码）＋ 缓冲（越小越好）。其中只有网络延迟由物理距离决定、不可压缩；运算延迟靠硬件与参数压缩；缓冲是纯浪费，必须压到最低。

## 三、延迟预算：80ms 在哪花

| 环节 | 目标耗时 | 技术手段 |
|------|---------|---------|
| 输入采集 | < 5ms | 低层 API 轮询 + 时间戳 |
| 网络传输（上行一半）| < 10ms | 就近接入，服务器靠近用户 |
| 服务端渲染 | < 16.6ms（60fps 一帧）| GPU 渲染，预分配资源 |
| 画面捕获 | < 3ms | 引擎直出（见 5.1）|
| 视频编码 | < 5ms | NVENC 硬件编码 |
| 网络传输（下行一半）| < 10ms | WebRTC / 私有 UDP 协议 |
| 视频解码 | < 5ms | 硬件解码 |
| 显示缓冲 | < 8ms | 低延迟显示器 |
| **合计** | **< 80ms** | 端到端环路 |

**推导结论**：网络占了 20ms RTT，即用户必须落在服务器约 2000km 范围内（光速物理上限）。这就是为什么云游戏一定要**就近建节点**——延迟物理上压不掉的只有这一段。

## 四、传输选型：为什么选 WebRTC，而不是 RTMP / HLS

这个问题问穿了，就理解了云游戏的一半技术选型：

| 需求 | RTMP | HLS（LL-HLS）| WebRTC |
|------|------|-------------|--------|
| 传输层 | TCP 推流 | TCP 分片 | **UDP**（RTP）|
| 端到端延迟 | ≈1-3s | ≈1-2s | **< 100ms** |
| 双向数据通道 | ❌ 无 | ❌ 无 | ✅ data channel 传输入 |
| NAT 穿透 | 无（要公网推流地址）| 无 | ✅ ICE / STUN / TURN |
| 丢包补偿 | 无（TCP 内建重传）| 无 | ✅ FEC + RTX 内建 |
| 拥塞自适应 | 无 | 有（分片级）| ✅ GCC 动态调码率 |

**核心一句话**：`RTMP` / `HLS` 走 TCP，一丢包就整流重传、重传期间**整个画面卡住**；WebRTC 走 UDP，丢包不重传整流，而是靠 `FEC` / `RTX` 在**应用层做精准的"丢了哪包补哪包"**，画面可以边轻抖边持续往前播。云游戏宁可丢两帧，也不能停顿 200ms。再加上 WebRTC 的 data channel 能随路传输入、ICE 能穿 NAT 打手机网络，它几乎是唯一把"低延迟 + 双向 + 弱网抗性"凑齐的协议栈。

## 五、服务端链路：渲染 → 捕获 → 编码

### 5.1 渲染与画面捕获（最容易忽略的延迟来源）

游戏进程在 GPU 渲染，产出的是**显存纹理**，不是字节流。把纹理变成可编码的数据只有两条路：

- **屏幕抓取**：Windows 用 DXGI Desktop Duplication、macOS 用 ScreenCaptureKit、移动端靠系统录屏。通用，但要走"显存 → 系统内存 → 编码器"多一跳，且吃 CPU，延迟 5-15ms，画质还有损。
- **引擎直出（SDK 方式）**：GeForce NOW / 腾讯云游的做法——游戏内 SDK 直接每天拿到纹理句柄，交给 NvPipe / NVENC，**延迟接近 0**。

**结论**：商用云游戏全部走"引擎直出"，屏幕抓取只是兜底兼容方案。

### 5.2 低延迟编码：参数背后的"为什么"

渲染帧是原始数据，带宽撑不住，必须编码。但编码天生引入延迟，四个旋钮各管一件事：

| 旋钮 | 作用 | 云游戏取舍 |
|------|------|-----------|
| **B 帧** | 双向参考帧，压缩率更高，但要多看 2-3 帧未来画面 | 禁用或最多 1 层（`-bf 0`）|
| **GOP 大小** | 关键帧间隔。太大 → 丢包后恢复慢、进房卡 | 500ms-1s（`-g 30~60`）|
| **码控模式** | VBR 峰值码率会瞬间冲爆链路 | 恒定码率 CBR + 极小 buffer |
| **编码器模式** | 编码耗时必须压进单帧预算 | 硬件 ULL / 最快预设（1080p60 → < 16.6ms）|

```bash
# 低延迟编码核心参数（逐条对应上表）
ffmpeg -f rawvideo -video_size 1920x1080 -framerate 60 -i /dev/video0 \
  -c:v h264_nvenc -preset p1 -tune ll       # 最快预设 + 低延迟调优
  -bf 0 -g 60                               # 禁 B 帧；关键帧间隔 1s
  -rc cbr -b:v 20M -bufsize 2M -zerolatency 1  # 恒定码率 + 极小编码缓冲
  -f rtp "rtp://client:5004"
```

### 5.3 下行传输

编码后的帧按 RTP 分包发出，客户端用 **Jitter Buffer（10-20ms）** 垫平网络抖动。两条保命原则：**关键帧只能靠重传保**（丢一帧就断片），非关键帧丢了靠 FEC 恢复——这正是下一节的内容。

## 六、弱网对抗：丢包下怎么保流畅

手机 4G / WiFi 场景下，丢包 0.5%-2% 很常见。看视频丢包是"卡一下子"，云游戏丢包是"**操作失灵一下子**"，完全不能忍。三个手段按强度排序：

| 手段 | 原理 | 代价 | 适用 |
|------|------|------|------|
| **FEC（前向纠错）** | 发冗余包，丢了直接重组，不等任何确认 | 码率 +20~30% | 随机 · 少量丢包，主力 |
| **NACK / RTX 重传** | 丢了指定包，请求重发，等一个 RTT | +RTT（10-20ms）| 关键帧、集中突发丢包 |
| **码率 / 帧率自适应** | GCC / TWCC 探测到拥塞立刻降档 | 画质下降 | 持续拥塞 |

**降档的铁律顺序**：先降码率保住帧率 → 再降帧率保住流畅 → 最后才降分辨率。云游戏**宁可画质差，不能操作卡**——卡顿一秒等于"神仙打架一秒没动"。

**一句话**：弱网对抗的本质是"丢包处理快不快 + 拥塞响应早不早"。这套机制 WebRTC 栈里内建齐全，这正是云游戏非它不可的核心理由（呼应第四节）。

## 七、输入上行 + 音频：环路另一侧

### 7.1 输入上行链路

- **采集**：键盘 / 鼠标 / 手柄用低层 API 轮询，每秒采样数百次，带毫秒时间戳。
- **传输**：WebSocket 或 data channel，载荷只有几十字节，但必须带客户端时间戳，服务端据此算出单程时延。
- **注入**：按时间戳排入游戏输入队列，防止乱序导致"先来后到"错位。

```go
// WebSocket 接收玩家输入，注入游戏输入队列
type GameInput struct {
    Timestamp int64   `json:"ts"`   // 客户端采集时刻(毫秒) → 用于计算单程延迟
    Keys      uint32  `json:"keys"` // 按键位图
    MouseX    float32 `json:"mx"`
    MouseY    float32 `json:"my"`
    Buttons   uint8   `json:"btns"`
}

func (s *GameSession) HandleInput(msg []byte) {
    var input GameInput
    if err := json.Unmarshal(msg, &input); err != nil {
        return
    }
    // 延迟补偿：用采集时刻反推单程延迟，供调优与预测
    latency := time.Now().UnixMilli() - input.Timestamp
    s.inputQueue <- CompensatedInput{
        Input:   input,
        Latency: time.Duration(latency) * time.Millisecond,
    }
}
```

### 7.2 音频：常被忽略的另一半

- 音频同样要求低延迟（主流要求 **< 40-50ms**），WebRTC 默认用 **Opus 20ms 帧**。
- **音画同步是坑**：视频缓冲和音频缓冲不一致就会嘴型对不上。云游戏的做法是让音频贴着视频时间线走，**不做大幅音频缓冲**——宁可听到轻啵啵声采样差错，也不要"动了嘴、声音迟到"。

## 八、GPU 虚拟化：成本核心

一块高端 GPU 数万元，不可能每个玩家独占一块。多租户分摊是云游戏能盈利的根基：

- **vGPU / MIG 切分**：一块物理 GPU 切成多个逻辑 GPU，各跑一个游戏实例（性能隔离）。
- **时间片调度**：多路游戏共用一块 GPU，按帧轮流执行——你玩我渲染。人越少帧率越高，人多时降帧率保运行。
- **池化分配**：玩家进房时从空闲池拉一块 GPU，退出即回收；配合容器镜像，实现"点击后 < 10 秒开玩"（预热热池 + 秒级拉起）。

## 十、关键挑战

1. **GPU 资源调度**：一台 GPU 虚拟化给多个游戏实例（见第八节，成本与体验的平衡点）
2. **快速启动**：用户点击后 < 10s 进入游戏（预热热池 + 容器镜像秒起）
3. **存档同步**：云端存档实时备份，客户端退出时无感同步
4. **DRM 版权**：游戏版权控制，杜绝截图/录屏/串流劫持

## 本篇小结

学完本篇，用三句话概括云游戏：

1. 它本质是一个 **输入上行 + 画面下行 的闭环**，延迟看环路（RTT 往返）不看单程。
2. 延迟压缩顺序：**吃满渲染帧预算 + 引擎直出捕获 + 硬件低延迟编码 + WebRTC 传输 + 客户端零缓冲**。
3. 弱网保流畅的优先级铁律：**丢包用 FEC/重传补，拥塞先降码率再降帧率再降分辨率**。

核心难点不是"流媒体技术本身"，而是**把上面每一项都压到极限、再缝合成一个 80ms 的闭环**。

## 动手实践

### 练习1：测量 RTT 基线，换算环路延迟
```bash
# 测量到游戏服务器的 RTT（影响环路延迟的核心变量）
ping -c 20 game-server.example.com | tail -1
# rtt min/avg/max/mdev = 12.3/14.1/18.5/1.8 ms

# 环路延迟 ≈ RTT(20ms) + 运算(40ms) + 缓冲(20ms)
# 目标：RTT < 60ms 时环路线路乐观；> 100ms 时操作感明显滞后
# 查看网络路径跳数，排查中间经过了哪些节点
traceroute game-server.example.com
```
**预期输出**：ping 得到 RTT 均值，`traceroute` 展示路径。RTT > 60ms 时云游戏操作延迟感明显，> 100ms 严重影响体验。

### 练习2：低延迟推流配置（云游戏场景）
```bash
# 服务端捕获本机画面 → NVENC 编码 → WebRTC 推送
# 关键：禁用 B 帧、小 GOP、恒定码率、编码器零延迟模式
ffmpeg -f x11grab -framerate 60 -i :0.0+0,0 \
  -c:v h264_nvenc -preset p1 -tune ll -zerolatency 1 \
  -bf 0 -g 60 -rc cbr -b:v 6000k \
  -f whip http://localhost:8889/game/room1/whip
```
**预期输出**：游戏画面通过 WebRTC（WHIP/WHEP）推到 MediaMTX，浏览器拉流延迟 < 100ms。试着把 `-bf 0` 去掉对比码率变化，体会"禁 B 帧换压缩率"的取舍。

## 常见问题排查

| 现象 | 可能原因 | 解决方法 |
|------|---------|---------|
| 操作延迟明显（> 150ms）| 服务器离用户太远，RTT 高 | 用户所在地部署边缘节点 |
| 画面撕裂 | VSync 与编码时序不同步 | 启用 NVENC `aq-strength` + 固定帧率输出 |
| GPU 峰值负载时卡顿 | 编码队列溢出、帧被丢 | 监控编码负载，限帧率防峰值超载 |
| 弱网下花屏/碎块 | 丢包未启用 FEC，只靠重传 | 检查 FEC 预设，>0.5% 丢包开启 ULPFEC + 码率自适应 |
| 移动端解码延迟高 | 缺少 H.264 硬解 | 检查 `MediaCodec`，确认走硬件解码器 |
| 音画不同步 | 音视频缓冲不一致，音频缓冲过大 | 关掉音频大幅缓冲，音频对齐视频时间线 |
| WebRTC 连接不稳定 | UDP 被运营商 QoS 限速 | TURN 服务器做 TCP 回退，或上 QUIC |

## 术语表

| 术语 | 英文 | 说明 |
|------|------|------|
| 环路延迟 | Loop Latency | 从用户输入到屏幕显示的整个往返，目标 < 80ms |
| RTT | Round-Trip Time | 一帧上下行往返总时延，网络部分的核心指标 |
| 输入延迟 | Input Latency | 用户操作到服务端收到指令的时延 |
| 引擎直出 | Engine Direct Capture | SDK 直接拿 GPU 纹理给编码器，绕过屏幕抓取 |
| NVENC ULL | Ultra Low Latency | NVIDIA 编码器超低延迟模式，减编码缓冲 |
| GOP | Group of Pictures | 关键帧间隔，越小丢包恢复越快、码率略升 |
| FEC | Forward Error Correction | 冗余包前向纠错，不等重传直接恢复丢包 |
| NACK / RTX | Negative ACK / Retransmission | 指定包重传机制，关键帧保障 |
| Jitter Buffer | 抖动缓冲 | 客户端垫平网络抖动的缓冲，越大延迟越高 |
| vGPU / MIG | GPU Virtualization | 物理 GPU 切分为多个逻辑 GPU 供多租户 |
| VSync | Vertical Sync | 垂直同步，控制帧输出时序防画面撕裂 |
