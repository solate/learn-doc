#### 第 20 篇：多分屏并发性能优化（16/32/64 路+）⭐
- 问题根因：N 个 <video> 标签 = N 路并发解码 → CPU/GPU 爆炸（4 路 1080p ≈ 100% CPU）
- 浏览器限制分析：<video> 硬件解码器数量上限（Chrome ≈ 8 个），超过自动降级软解
- 电视盒子对比：专用 ASIC 硬件解码芯片，64 路 D1 < 15% CPU
- 服务端降载方案（优先级最高）：
  - 服务端按需缩放分辨率（预览用 360p/D1，详情用 1080p）
  - 转码时降低帧率（预览 5fps 已足够）
  - GOP 关键帧加密优化：缩短 I 帧间隔降低首帧延迟
- 客户端方案 1：WebCodecs API 硬件解码
  - 绕过 <video> 标签限制，直接调用系统硬件解码器
  - 理论上限：GPU 并发解码路数（取决于显卡，一般 16-64 路）
  - VideoDecoder API 使用方法，输出到 OffscreenCanvas
- 客户端方案 2：OffscreenCanvas + Worker 渲染
  - 解码和渲染移到 Web Worker，不阻塞主线程
  - 多 Worker 并行，避免单线程瓶颈
  - SharedArrayBuffer 传递帧数据（需要 COOP/COEP 响应头）
- 客户端方案 3：按需激活（Lazy Activation）
  - 只激活可见区域的流（Intersection Observer API）
  - 翻页/缩略图预览时用静态图，放大时才建立视频连接
  - 实测效果：100 路预览 = 屏幕内 16 路活跃 + 84 路静态缩略图
- 客户端方案 4：WebRTC DataChannel 复用
  - 单一 WebRTC 连接传递多路流（通过 DataChannel 多路复用）
  - 避免每路流独立 ICE 建立开销
- 网络带宽计算：
  - 16 路 1080p 30fps H.265：16 × 3Mbps = 48Mbps（服务端到客户端）
  - 64 路 D1 5fps：64 × 0.3Mbps = 19Mbps（可接受）
- 不同规模的推荐方案：
  - ≤16 路：浏览器 <video> + 服务端降分辨率
  - 16-64 路：WebCodecs + OffscreenCanvas + 降分辨率
  - 64+ 路：本地 C++ 客户端（Electron/Qt）或专用解码卡
- 动手实践：实现 WebCodecs 多分屏播放器（支持 16/32/64 路切换）
