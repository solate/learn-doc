## 一、为什么电视盒子不卡、浏览器 16 路就卡？

这是流媒体工程中最经典的问题，根本原因是**解码路径完全不同**：

```
电视盒子（ARM SoC，如海思 Hi3798）：
┌─────────────────────────────────────────────┐
│ H.264 码流 → 专用 VPU（视频处理单元）          │
│              ↓ 硬件电路直接解码                │
│              ↓ 解码 1080p 消耗 < 1% CPU        │
│              ↓ 16 路 = 16 个独立硬解通道        │
│              → 送入显示流水线 → HDMI 输出       │
└─────────────────────────────────────────────┘
CPU 负载几乎为零，全由硬件完成。

浏览器（Chrome on x86 PC）：
┌─────────────────────────────────────────────┐
│ H.264 码流 → <video> 标签                     │
│              ↓ JS 调用 MSE（Media Source Ext） │
│              ↓ 浏览器解封装                    │
│              ↓ GPU/CPU 解码（受浏览器策略控制） │
│              16 个 <video> = 16 路并发解码     │
│              → CPU/GPU 内存瓶颈                │
└─────────────────────────────────────────────┘
```

**问题的核心**：传统 `<video>` 标签的硬件解码由浏览器决定，无法精细控制；而且 16 个独立 MediaSource 实例内存开销极大。

## 二、软件编解码：CPU 干所有事

软件编解码指用 CPU 指令集（x86/ARM SIMD）实现的编解码算法。

### 软件编解码的特点

| 特性 | 说明 |
|------|------|
| **质量** | 最好（充分利用算法优化，如 libx264 的 RD 优化） |
| **兼容性** | 最强（纯软件，无驱动依赖） |
| **CPU 占用** | 高（1080p 解码约 20-40% 单核，编码更高） |
| **灵活性** | 最高（可调节所有参数） |
| **延迟** | 可控（preset 从 ultrafast 到 veryslow） |

### 软件编解码的 CPU 开销参考

```
解码（软件，x86 现代 CPU）：
  720p  H.264  ≈ 5-10% 单核
  1080p H.264  ≈ 15-25% 单核
  1080p H.265  ≈ 25-40% 单核（复杂度更高）
  4K    H.264  ≈ 60-80% 单核

编码（libx264，preset medium，1080p）：
  1080p H.264  ≈ 80-100% 单核
  编码速度约 30-60 fps（实时需要 > 25fps）
```

16 路 1080p 软解 = 16 × 25% = 400% CPU，需要 4 个物理核心全部用于解码，显然不可行。

## 三、硬件编解码：专用芯片分担 CPU

硬件编解码依赖专用的视频处理单元（VPU/Video Engine），这些电路针对特定编解码算法进行硬件实现。

```
硬件解码流程：
  码流 → DMA 送入 GPU/VPU 内存
        ↓ 专用解码电路（ASIC）
        ↓ 输出 YUV 原始帧到显存
        ↓ 直接送显卡渲染 → 屏幕
  CPU 参与极少（仅解析码流头部）
```

### 硬件解码的优势

| 特性 | 软件 | 硬件 |
|------|------|------|
| CPU 占用 | 高 | 极低（< 1%） |
| 功耗 | 高 | 低（专用电路效率高） |
| 并发路数 | 受 CPU 核数限制 | 受硬件解码器数量限制 |
| 画质 | 与码流相同 | 与码流相同（解码无质量损失） |
| 支持格式 | 任意（软件实现） | 有限（依赖芯片支持） |

**注意**：解码没有质量损失（只是把码流还原成原始帧），有质量差异的是**编码**（见第六节）。

## 五、浏览器中的硬件解码：WebCodecs API

**WebCodecs** 是 W3C 标准（2021 年正式）的浏览器低级媒体 API，允许 JavaScript **直接调用硬件编解码器**。

### 传统方案 vs WebCodecs 方案

```
传统方案（16路卡顿根源）：
  16个 <video> 标签
  ↓ 浏览器创建 16 个 MSE 实例
  ↓ 每个实例独立缓冲区（16 × 30-50MB = 480-800MB 内存）
  ↓ 16路 JS → 16路解码 → 16路 Canvas 绘制
  结果：内存爆炸，UI 线程卡死

WebCodecs 方案（多路不卡）：
  1 个 WebSocket/WebTransport 连接
  ↓ 拉取所有码流
  ↓ WebCodecs VideoDecoder（直接调用硬件）
  ↓ 解码结果 VideoFrame → OffscreenCanvas
  ↓ 1 个 Canvas 分区渲染 16路
  结果：内存可控，CPU 极低
```

### WebCodecs 代码示例

```javascript
// 创建硬件加速解码器
const decoder = new VideoDecoder({
  output: (videoFrame) => {
    // videoFrame 已解码，直接绘制到 Canvas
    ctx.drawImage(videoFrame, x, y, width, height);
    videoFrame.close(); // 释放 GPU 内存（必须！）
  },
  error: (err) => console.error('解码错误:', err),
});

// 配置解码器（H.264）
decoder.configure({
  codec: 'avc1.42E01E',    // H.264 Baseline
  hardwareAcceleration: 'prefer-hardware',  // 优先硬件
  optimizeForLatency: true, // 低延迟模式
});

// 喂入码流数据（EncodedVideoChunk）
decoder.decode(new EncodedVideoChunk({
  type: 'key',  // 关键帧
  timestamp: pts,
  data: nalUnitData,  // H.264 NAL 单元
}));

// 检查浏览器是否支持硬件加速
const support = await VideoDecoder.isConfigSupported({
  codec: 'avc1.42E01E',
  hardwareAcceleration: 'prefer-hardware',
});
console.log('硬件加速支持:', support.supported);
```

| Chrome | 94+ | 完整支持 |
| Edge | 94+ | 完整支持 |

## 六、编码质量对比：软件 vs 硬件

**解码**没有质量差异（只是还原码流），**编码**有质量差异：

```
相同码率（4 Mbps，1080p H.264）下的主观质量对比：

libx264 (软件, preset medium)  → PSNR ~38-40dB（最好）
h264_nvenc (NVIDIA,质量模式)  → PSNR ~35-37dB（略差 5-10%）
h264_qsv (Intel QSV)          → PSNR ~34-36dB（略差）
h264_videotoolbox (Apple)     → PSNR ~33-35dB（略差）
```

**什么情况下质量差异可以接受？**

| 场景 | 推荐 | 理由 |
|------|------|------|
| 离线批量转码（归档/点播） | 软件（libx264） | 质量最优，时间不紧 |
| 实时直播推流（OBS/RTMP） | 硬件（NVENC） | 速度优先，质量损失可接受 |
| 视频会议编码 | 硬件 | 延迟更低，实时优先 |
| 监控录像转码 | 硬件 | 高并发，降 CPU 成本 |
| OTT 点播母版制作 | 软件 | 永久存储，追求最佳画质 |

## 七、服务器端硬件加速选型

### NVIDIA NVENC（最主流）

```bash
# 检查 NVENC 支持
nvidia-smi  # 确认 GPU 存在
ffmpeg -encoders 2>/dev/null | grep nvenc

# NVENC 编码（实时转码，1080p → 720p）
ffmpeg -i input.mp4 \
  -c:v h264_nvenc \
  -preset p4 \          # p1(最快低质) ~ p7(最慢高质)，p4 是平衡
  -cq 23 \              # 恒定质量模式（类似 CRF）
  -b:v 0 \              # cq 模式下 b:v 设为 0
  -profile:v high \
  -c:a copy \
  output_nvenc.mp4

# NVDEC 硬件解码 + NVENC 硬件编码（完全 GPU 流水线）
ffmpeg -hwaccel cuda -hwaccel_output_format cuda \
  -i input.mp4 \
  -c:v h264_nvenc -preset p4 -cq 23 \
  -c:a copy \
  output_cuda.mp4
```

### Intel QSV（低功耗服务器）

```bash
# 检查 QSV 支持
ls /dev/dri/  # renderD128 存在即可

ffmpeg -init_hw_device qsv=hw -filter_hw_device hw \
  -i input.mp4 \
  -c:v h264_qsv \
  -global_quality 23 \
  -preset faster \
  -c:a copy \
  output_qsv.mp4
```

### Apple VideoToolbox（macOS 开发环境）

```bash
ffmpeg -i input.mp4 \
  -c:v h264_videotoolbox \
  -b:v 5M \              # VideoToolbox 不支持 CRF，需指定码率
  -profile:v high \
  -c:a copy \
  output_vt.mp4
```

### 并发转码能力参考

| GPU | NVENC 并发流数 | 适用场景 |
|-----|-------------|---------|
| RTX 4090 | 无限制（官方取消限制） | 开发/测试 |
| A100 | 无限制 | 生产级大规模转码 |
| T4（云服务器） | 32路 1080p | 性价比最高的云 GPU |
| GTX 16xx | 3路（Turing消费级限制） | 不推荐生产用 |

## 九、常见问题排查

**Q：ffmpeg 报错 "No NVENC capable devices found"？**

```bash
# 确认 NVIDIA 驱动版本（需 ≥ 418.30）
nvidia-smi | head -3

# 确认 FFmpeg 编译时包含 NVENC
ffmpeg -version 2>/dev/null | grep nvenc

# 如果 FFmpeg 没有 NVENC 支持，需要重新编译或使用 nvidia 提供的版本
```

**Q：VideoToolbox 编码输出质量很差？**

VideoToolbox 不支持 CRF，只能用 `-b:v` 指定码率。建议：
```bash
ffmpeg -i input.mp4 -c:v h264_videotoolbox \
  -b:v 8M -maxrate 10M -bufsize 16M \  # 设置目标码率+最大码率
  -c:a copy output.mp4
```

**Q：WebCodecs 解码出来画面绿屏或花屏？**

原因：解码器没有收到 SPS/PPS（初始化信息）就开始解码了。确保第一个 chunk 是包含 SPS+PPS 的关键帧，类型设为 `'key'`。

**Q：服务器端 QSV 编码出错 "cannot load shared library libmfx.so"？**

```bash
# 安装 Intel Media SDK 运行时
apt-get install intel-media-va-driver vainfo
# 验证
vainfo | grep H264
```

## 本篇小结

1. **根本原因**：电视盒子有专用 VPU，浏览器 `<video>` 标签依赖 CPU/浏览器决策，16路并发导致 CPU 瓶颈
2. **硬件解码无质量损失**：只有硬件编码质量略逊于软件编码（约 5-10%）
3. **WebCodecs API**：2021 年 W3C 标准，允许 JS 直接调用 GPU 硬件解码器，是多路监控的关键技术
4. **NVENC 最主流**：NVIDIA GPU 编码，生产环境首选，A100/T4 无并发路数限制
5. **选型原则**：实时/高并发用硬件，追求最佳质量/离线转码用软件
