## 一、什么是"流"？— 从最基础的问题说起

### 1.1 文件 vs 流：本质区别

读完本节，你能理解为什么"边传边播"在技术上比"下载后播放"复杂得多。

我们先从最熟悉的场景开始。你用微信发一张图片给朋友，背后的过程是：

```
发送方 → 完整上传图片到服务器 → 服务器存储 → 接收方完整下载 → 打开查看
```

这是典型的**文件传输**模型：数据先完整存储，再完整读取。播放本地视频文件也是同样的逻辑——文件在磁盘上，播放器从磁盘读，简单可靠。

**流媒体（Streaming Media）与之的根本区别在于时序性**：

```
生产者（摄像头/直播端）        消费者（播放器）
        │                           │
        │ ──帧1──帧2──帧3──帧4──▶  │
        │   数据边产生边传输         │
        │   消费者边接收边播放       │
        │                           │
        ↓（时间轴）                 ↓
```

流媒体的核心特征是**时序依赖**：帧 2 必须在帧 1 之后播放，帧 100 依赖前面的 I 帧（关键帧）解码。这带来了几个文件传输不存在的挑战：

| 维度 | 文件传输 | 流媒体传输 |
|------|---------|-----------|
| 数据完整性 | 传完再用，可校验 | 边传边用，容错要求高 |
| 时序要求 | 无顺序要求 | 严格时序，乱序就花屏 |
| 丢包处理 | 重传即可 | 重传可能导致播放卡顿 |
| 缓冲策略 | 不需要 | 必须有缓冲区平衡抖动 |
| 带宽适应 | 固定大小 | 需动态调整码率（ABR） |

### 1.2 为什么"边传边播"技术上更难？

读完本节，你能理解流媒体系统面临的三个核心技术挑战。

**挑战 1：网络抖动（Jitter）**

网络传输时延不是恒定的。同样大小的数据包，这次 10ms 到达，下次可能 80ms 才到。如果播放器不做任何处理，视频就会忽快忽慢，甚至卡顿。

解决方案是**播放缓冲区（Playout Buffer）**：提前缓存 2-5 秒的数据，用缓冲区吸收网络抖动。这也是为什么视频流开始播放前要"缓冲"的原因。

**挑战 2：丢包处理**

TCP 有丢包重传机制，但重传会引入延迟。对于实时流媒体，等待重传可能比丢掉这帧更糟糕——因为下一帧已经到了，旧帧已经"过期"。

这就是为什么实时视频（如视频通话）通常用 **UDP** 而非 TCP：宁可丢帧，也不要卡顿等待。

**挑战 3：编解码同步**

视频流和音频流是分开传输的，播放时必须保持同步（嘴型对上声音）。RTP 协议通过时间戳机制解决音视频同步问题，这将在第 6 篇详细讲解。

## 二、流媒体的三大核心场景

读完本节，你能根据业务需求判断应该采用 VOD、Live 还是 RTC 方案。

### 2.1 点播（Video On Demand，VOD）

**场景**：用户随时可以播放已录制好的视频，如 Netflix、B 站、YouTube 上的视频。

**技术特征**：
- 视频内容已完整存储在服务器
- 用户可以**任意跳转**（Seek）到任意时间点
- 延迟要求**宽松**：哪怕缓冲 10 秒，用户可以接受
- 可以预先转码为多种码率，支持自适应码率（ABR）

**典型技术栈**：S3/OSS 存储 + FFmpeg 转码 + HLS/DASH 分发 + CDN 加速

### 2.2 直播（Live Streaming）

**场景**：实时发生的事件直播给观众，如游戏直播、新闻直播、体育赛事。

**技术特征**：
- 内容实时产生，不能 Seek 到"未来"的时间点
- 延迟要求**中等**：3-10 秒可接受（观众不需要和主播实时互动）
- 需要处理**突发并发**：一场比赛开球瞬间可能百万人同时观看
- 通常需要 CDN 分发降低源站压力

**典型技术栈**：OBS 推流（RTMP）→ SRS 流媒体服务器 → HLS/HTTP-FLV → CDN → 播放器

### 2.3 实时通信（Real-Time Communication，RTC）

**场景**：双向或多向实时视频通话，如视频会议、在线教育、远程医疗、视频客服。

**技术特征**：
- **延迟要求极严苛**：> 300ms 就会感觉到"说话延迟"，> 1s 对话就非常别扭
- 双向互动：每个参与者既是发送方也是接收方
- 网络条件变化剧烈时，宁可降低画质也要保持流畅
- 不需要 CDN，但需要信令服务器和 TURN 中继服务器

**典型技术栈**：浏览器 WebRTC → STUN/TURN 服务器（ICE 穿透）→ SFU 服务器（多人转发）

### 2.4 三种场景技术差异对比

| 维度 | 点播（VOD） | 直播（Live） | 实时通信（RTC） |
|------|-----------|------------|---------------|
| 延迟要求 | 不敏感（秒级） | 中等（3-10s） | 极严苛（< 300ms） |
| 内容来源 | 预录制 | 实时采集 | 实时采集（双向） |
| 是否可 Seek | ✅ 任意跳转 | ❌ 只能看当前 | ❌ 实时对话 |
| 典型并发 | 高（CDN 分发） | 极高（百万级） | 中等（会议室规模） |
| 推荐协议 | HLS/DASH | RTMP 推 + HLS/WebRTC 播 | WebRTC（WHIP/WHEP） |
| 典型延迟 | 缓冲可达 10s+ | 3-10s | 50-300ms |

> **判断法则**：如果用户需要和主播/对方"实时互动"（连麦、提问即答），选 RTC；如果只是观看，选 Live 或 VOD。

## 三、流媒体技术演进史（1995→2025）

读完本节，你能理解每个协议"为什么出现"，以及它解决了什么前代协议的痛点。

### 3.1 RealPlayer 时代（1995-2005）：流媒体的起源

1995 年，RealNetworks 发布了 RealPlayer，这是第一个被大众使用的流媒体播放器。它使用专有的 RTSP/RTP 协议。

**当时的问题**：
- 拨号网络（56kbps），视频只能压缩到极低码率
- 客户端需要安装专用插件
- 协议是私有的，生态封闭

**留下的遗产**：RTSP 协议至今仍是 IP 摄像头的主流接入协议。绝大多数海康威视、大华摄像头默认使用 RTSP 协议，这正是 RTSP 的历史渊源。

### 3.2 Flash/RTMP 时代（2005-2015）：直播的黄金时代

Adobe Flash 和 RTMP（Real-Time Messaging Protocol）协议的出现，开创了网络直播的黄金时代。

**为什么 RTMP 成功**：
- Flash 插件覆盖率超过 95%，无需额外安装
- RTMP 延迟低（1-3 秒），适合直播
- 简单的推流 URL：`rtmp://server:1935/live/stream`
- OBS、直播姬等工具都支持

**Flash 死亡（2020）后 RTMP 为何还活着**：
Flash 播放器被淘汰，但 **RTMP 的推流端**（OBS→服务器这一段）并没有死。原因是：
1. RTMP 推流协议简单、延迟低、工具支持好
2. 服务器收到 RTMP 流后，可以转换为浏览器支持的 HLS 或 HTTP-FLV
3. 所以现在的直播链路通常是：**OBS（RTMP推）→ 服务器（转换）→ 浏览器（HLS/HTTP-FLV播）**

### 3.3 HLS/CDN 时代（2009-2020）：大规模分发的解法

2009 年，Apple 发布了 HLS（HTTP Live Streaming）协议，彻底改变了流媒体的分发方式。

**HLS 的核心创新**：把视频流切成一段段 2-10 秒的小文件（TS 分片），通过普通 HTTP 协议分发。

```
传统流媒体（RTSP/RTMP）：       HLS 分发：
                                 
服务器 ──持久连接──▶ 播放器      服务器
                                 ├── index.m3u8   ← 播放器先获取索引文件
                                 ├── seg001.ts    ← 再依次下载分片
                                 ├── seg002.ts
                                 └── seg003.ts
```

**为什么这个设计天才**：
1. **CDN 友好**：TS 分片是普通 HTTP 文件，可以被 CDN 缓存，轻松扛住百万并发
2. **防火墙友好**：HTTP 80/443 端口，任何网络都通
3. **iOS/Safari 原生支持**：Apple 在 iOS 上内置支持，解决了移动端问题

**HLS 的代价**：延迟高。每个分片 2-10 秒，加上播放器预缓冲 2-3 个分片，总延迟通常 5-30 秒。

### 3.4 WebRTC 时代（2015 至今）：实时通信标准化

2015 年前后，Google 主导推进的 WebRTC 逐渐成熟，W3C 于 2021 年正式发布 WebRTC 1.0 Recommendation，2025 年进一步完善。

**WebRTC 解决的核心问题**：浏览器内置实时视频通信能力，无需插件。

**WebRTC 的技术组合**：
```
采集层：   getUserMedia() → 摄像头/麦克风
传输层：   ICE/STUN/TURN  → NAT 穿透（直连或中继）
加密层：   DTLS-SRTP      → 端到端加密
信令层：   WebSocket/HTTP → SDP Offer/Answer 协商
```

**WebRTC 的延迟优势**：50-300ms，比 HLS 低 20-100 倍。

**WebRTC 的局限性**：
- 多人场景需要 SFU/MCU 服务器，架构复杂
- 信令层没有统一标准（直到 WHIP/WHEP 出现）
- 对网络质量要求较高

### 3.5 CMAF/WHIP 新时代（2020 至今）：统一与标准化

**CMAF（Common Media Application Format，2016/2020）**：
苹果和微软联合推出，用 fMP4 格式统一 HLS 和 DASH，消除格式碎片化。2026 年，CMAF 已成为新项目的默认选择。

**WHIP（WebRTC-HTTP Ingestion Protocol，RFC 9725，2025.03）**：
解决了 WebRTC 信令层混乱的问题。一个 HTTP POST 请求就能完成 SDP 协商，推流变得像 RTMP 一样简单。

### 3.6 RTP over QUIC (RoQ)：下一代传输层

读完本节，你能理解为什么 QUIC 可能成为未来流媒体传输的新基础。

**RoQ 的背景：RTP/UDP 的痛点**

传统 RTP over UDP 在实时流媒体中工作良好，但存在几个问题：

1. **队头阻塞（Head-of-Line Blocking）在 TCP 中无解**：视频会议等场景需要同时传多路流（视频 + 音频 + 屏幕共享），如果用 TCP，一个包丢失会阻塞所有流
2. **NAT 穿透复杂**：UDP 需要 STUN/TURN 辅助，增加部署复杂度
3. **缺少拥塞控制**：纯 UDP 需要应用层自己实现拥塞控制（如 WebRTC 的 GCC 算法）

**QUIC 的三大优势**

QUIC（Quick UDP Internet Connections）是 Google 开发、IETF 标准化的传输层协议，HTTP/3 的底层就是 QUIC。

```
QUIC = UDP + 可靠传输 + 多路复用 + 内置加密
```

| 特性 | TCP | UDP + RTP | QUIC |
|------|-----|-----------|------|
| 队头阻塞 | ❌ 严重（一个包阻塞所有） | ✅ 无（但需要应用层处理） | ✅ 无（流级别隔离） |
| 连接建立 | 3 次握手（150ms） | 无握手（0ms） | 1 次握手（~50ms） |
| 加密 | TLS 需额外握手 | 无（需上层 DTLS） | ✅ 内置加密 |
| NAT 友好 | 中等 | 较差（需 STUN/TURN） | ✅ 好（基于 UDP） |
| 丢包恢复 | 重传整个包 | 应用层决定 | 选择性重传 |

**RTP over QUIC (RoQ) 标准化进展**

2025 年 IETF 发布了 RoQ 的草案（draft-ietf-avtcore-rtp-over-quic），核心思路是：

```
传统架构：
视频流 ──RTP/UDP──▶ 网络 ──RTP/UDP──▶ 接收端
音频流 ──RTP/UDP──▶ 网络 ──RTP/UDP──▶ 接收端

RoQ 架构：
视频流 ──\
音频流 ──-──RTP/QUIC（单一连接，多路复用）──▶ 接收端
屏幕流 ──/
```

每路流在 QUIC 的独立 Stream 中传输，一路丢包不影响其他路。

**未来应用场景**

1. **视频会议**：多人会议中的多路流（视频 + 音频 + 屏幕共享）通过单一 QUIC 连接传输，降低 NAT 穿透复杂度
2. **云游戏**：游戏画面 + 音频 + 控制指令，需要极低延迟且不同流的优先级不同
3. **5G 边缘计算**：移动网络环境下，QUIC 的连接迁移能力（Connection Migration）可以无缝切换基站

**为什么 RoQ 还没有大规模部署？**

截至 2026 年，RoQ 仍在标准化阶段，主要挑战：

- 现有设备（摄像头/编码器）几乎全部只支持 RTP/UDP 或 RTMP
- QUIC 库的成熟度和性能优化仍在进行中
- 需要流媒体服务器（SRS/MediaMTX）升级支持

但 QUIC 在 HTTP/3 中的成功证明了其可行性，未来 5-10 年内 RoQ 有望成为实时流媒体的新标准。

## 四、推流协议 vs 分发协议：为什么需要两套协议？

读完本节，你能画出完整的"一路视频流从采集到播放"的链路图，并说出每段用什么协议。

### 4.1 问题的起源

初学者最常见的困惑：**"为什么摄像头用 RTSP，直播用 RTMP 推流，观众却用 HLS 看？同一个视频，为什么需要这么多协议？"**

答案在于：视频流的不同阶段，面对的技术约束完全不同。

### 4.2 两类不同角色的需求

**推流端（Producer Side）的需求**：
- 实时性：延迟要低（摄像头 / OBS → 服务器）
- 稳定性：能处理弱网、断线重连
- 简单：编码器（摄像头/OBS）容易接入
- **代表协议**：RTSP（摄像头拉流）、RTMP（直播推流）、SRT（弱网推流）

**分发端（Consumer Side）的需求**：
- 规模：CDN 可以缓存，扛住百万并发
- 兼容性：浏览器/手机/电视都能播
- 网络适应：弱网自动降低分辨率（ABR）
- **代表协议**：HLS/DASH（大规模分发）、HTTP-FLV（低延迟）、WebRTC（实时互动）

### 4.3 完整协议链路图

```
【采集端】                【服务端】                【播放端】
                          
IP 摄像头                                          浏览器/App
  │ RTSP（拉）           ┌──────────────────┐        ├─ HLS (5-10s延迟)
  ├────────────────────▶│                  │────────▶├─ HTTP-FLV (1-3s)
  │                     │  流媒体服务器     │        └─ WebRTC (200ms)
OBS / 直播姬             │  (SRS/MediaMTX/  │
  │ RTMP（推）           │   ZLMediaKit)    │       移动端 App
  ├────────────────────▶│                  │────────▶├─ HLS (iOS/Android)
  │                     │  负责：          │        └─ RTMP (部分App)
无人机 / 远程摄像         │  ・协议转换      │
  │ SRT（推）            │  ・转码          │       智能电视 / IPTV
  └────────────────────▶│  ・录像          │────────▶└─ HLS/DASH
                         │  ・分发          │
                         └──────────────────┘
                              │ CDN 回源
                              ▼
                          CDN 边缘节点（缓存分片）
```

**关键认知**：流媒体服务器是核心枢纽，负责协议转换。同一路视频，进来是 RTMP，出去可以同时是 HLS、HTTP-FLV 和 WebRTC。

## 五、为什么浏览器不能直接播 RTSP/RTMP？

读完本节，你能向同事解释为什么视频监控系统需要一个"流媒体网关"。

### 5.1 浏览器的安全模型限制

**原因 1：浏览器禁止任意 TCP/UDP 连接**

RTSP 需要建立 TCP 连接到摄像头的 554 端口，然后通过 RTP/UDP 传输媒体数据。浏览器的 JavaScript 安全沙箱明确禁止直接建立原始 TCP/UDP socket。

> 允许浏览器直连任意端口 = 允许网页扫描你的内网设备 = 严重安全漏洞

**原因 2：RTMP 依赖持久 TCP 连接**

浏览器只支持 HTTP/HTTPS、WebSocket 两类主要协议（加上 WebRTC）。RTMP 是基于独立 TCP 的私有协议，浏览器没有内置支持，Flash 时代是靠插件实现的。

### 5.2 技术实现限制

**原因 3：浏览器不支持 RTSP/RTMP 的媒体解封装**

即使绕过网络限制，浏览器的 `<video>` 标签也不认识 RTMP 的 FLV 封装格式或 RTSP 的 RTP 包。HTML5 视频只支持 MP4/WebM/HLS 等浏览器原生格式。

### 5.3 解决方案：服务端协议中转

```
❌ 错误理解：浏览器 ──RTSP──▶ 摄像头（行不通）

✅ 正确架构：
摄像头 ──RTSP──▶ 流媒体服务器 ──HLS/HTTP-FLV/WebRTC──▶ 浏览器
                  （协议转换）        （浏览器支持的格式）
```

这就是为什么几乎所有视频监控系统都需要一个"流媒体服务器"或"视频网关"。

## 七、动手实践

### 实践 1：感受延迟差异——对比播放 RTSP / HLS / 本地文件

**目标**：直观感受三种方式的延迟差异，建立"协议延迟"的感性认知。

**前提准备**：

```bash
# 安装 FFmpeg（必须）
brew install ffmpeg          # macOS
sudo apt-get install ffmpeg  # Ubuntu

# 安装 VLC 播放器
brew install --cask vlc      # macOS

# 启动 SRS 流媒体服务器（Docker）
docker run -d --name srs \
  -p 1935:1935 \
  -p 8080:8080 \
  -p 1985:1985 \
  registry.cn-hangzhou.aliyuncs.com/ossrs/srs:5
```

**步骤 1：用 FFmpeg 模拟推流**

```bash
# 下载测试视频（30秒 Big Buck Bunny 片段）
curl -L -o test.mp4 "https://sample-videos.com/video321/mp4/720/big_buck_bunny_720p_1mb.mp4"

# 推流到 SRS（-re 表示按实时速率推送，模拟直播）
ffmpeg -re -stream_loop -1 -i test.mp4 \
  -c copy -f flv rtmp://localhost:1935/live/test
```

**步骤 2：三种方式对比播放**

```bash
# 方式 A：本地文件播放（参考基准，0延迟）
ffplay test.mp4

# 方式 B：HLS 播放（预期延迟 5-15s）
ffplay http://localhost:8080/live/test.m3u8

# 方式 C：RTMP 播放（预期延迟 1-3s）
ffplay rtmp://localhost:1935/live/test
```

**预期结果**：

| 方式 | 推流时间戳 vs 播放时间戳 | 体感延迟 |
|------|----------------------|---------|
| 本地文件 | 相同 | 0ms |
| RTMP | 落后推流 1-3s | 明显但可接受 |
| HLS | 落后推流 5-15s | 明显延迟 |

> **观察方法**：在推流终端窗口和播放窗口同时显示当前系统时间（可以在桌面显示时钟），对比播放内容的"时刻"与实际时刻的差距。

### 实践 2：用 ffprobe 分析流信息

**目标**：学会用 ffprobe 查看任意流的编码格式、分辨率、码率等基本信息。

```bash
# 分析本地视频文件
ffprobe -v quiet -print_format json -show_streams test.mp4

# 分析 HLS 流（注意：需要推流进行中）
ffprobe -v quiet -print_format json -show_streams \
  http://localhost:8080/live/test.m3u8
```

**关键字段说明**：

```json
{
  "codec_name": "h264",        // 视频编码器
  "width": 1280,               // 分辨率宽
  "height": 720,               // 分辨率高
  "r_frame_rate": "30/1",      // 帧率 30fps
  "bit_rate": "1500000"        // 码率 1.5Mbps
}
```

### 实践 3：观察 HLS m3u8 分片结构

**目标**：理解 HLS 协议的工作原理——看懂 m3u8 索引文件。

```bash
# 查看 m3u8 内容（需要推流进行中）
curl http://localhost:8080/live/test.m3u8
```

**预期输出**：

```m3u8
#EXTM3U
#EXT-X-VERSION:3
#EXT-X-TARGETDURATION:10
#EXT-X-MEDIA-SEQUENCE:5
#EXTINF:9.960000,
/live/test-5.ts
#EXTINF:10.000000,
/live/test-6.ts
#EXTINF:9.040000,
/live/test-7.ts
```

**解读**：
- `EXT-X-TARGETDURATION:10` → 每个分片约 10 秒
- `EXT-X-MEDIA-SEQUENCE:5` → 当前最新序号是 5（前面的已过期）
- 播放器每隔几秒刷新一次 m3u8，下载最新分片，这就是"延迟来源"

**实际环境说明**：你可能看到的是这样的输出：

```m3u8
#EXTM3U
#EXT-X-STREAM-INF:BANDWIDTH=1,AVERAGE-BANDWIDTH=1
/live/test.m3u8?hls_ctx=xxxxx
```

这是 **Master Playlist（主播放列表）**，用于多码率自适应（ABR）。即使只有一个码率，生产环境也常用这种两层结构。要看到上面示例中的 `.ts` 分片列表，需要访问 Master Playlist 指向的 **Media Playlist（媒体播放列表）**：

```bash
# 方法 1：手动拼接（用你看到的 hls_ctx 值）
curl "http://localhost:8080/live/test.m3u8?hls_ctx=xxxxx"

# 方法 2：自动提取并访问
curl -s http://localhost:8080/live/test.m3u8 | grep '\.m3u8' | head -1 | xargs -I {} curl "http://localhost:8080{}"
```

这时你会看到包含 `test-5.ts`、`test-6.ts` 等分片的列表，也就是上面预期输出的内容。

## 八、常见问题排查

| 问题 | 可能原因 | 排查方法 | 解决方案 |
|------|---------|---------|---------|
| **播放器显示"加载中"，一直不播放** | 1. 推流未启动<br>2. 协议/端口不对<br>3. 防火墙拦截 | `curl http://localhost:8080/live/test.m3u8` 查看是否返回索引文件 | 确认推流进行中，检查 URL 和端口是否正确 |
| **播放有声音无画面 / 有画面无声音** | 编码格式不兼容（如 H.265 不被浏览器支持） | `ffprobe` 查看流的编码格式 | 重新推流时用 `-vcodec libx264 -acodec aac` 强制 H.264+AAC |
| **播放卡顿，不流畅** | 1. 网络带宽不足<br>2. 推流码率过高<br>3. 播放器缓冲设置过小 | 用 `speedtest-cli` 测速，`ffprobe` 查看流码率 | 降低推流码率（`-b:v 1M`）或增加播放器缓冲 |
| **HLS 延迟特别高（> 30s）** | `EXT-X-TARGETDURATION` 太大（分片太长） | 查看 m3u8 文件中的 `EXTINF` 时长 | 推流时用 `-hls_time 3` 减小分片时长到 3 秒 |
| **VLC 报错"无法打开 rtmp://..."** | 1. SRS 未启动<br>2. 推流 URL 中的 app/stream 名称不对 | `docker ps` 查看 SRS 是否运行，检查 URL 格式 | 确保 URL 格式为 `rtmp://host:1935/app/stream` |
| **ffplay 播放 RTSP 流报错"Connection refused"** | RTSP 服务器未启动或端口不对（默认554） | `telnet <ip> 554` 测试端口连通性 | 确认摄像头/服务器运行正常，防火墙开放 554 端口 |

| 术语 | 英文 | 解释 |
|------|------|------|
| **流媒体** | Streaming Media | 视频/音频数据边传输边播放，不需要下载完整文件 |

| **拉流** | Pull | 服务器主动从视频源（摄像头）获取流 |
| **编码** | Encoding | 将原始视频压缩为 H.264/H.265/AV1 等格式 |
| **封装** | Muxing | 将视频流和音频流打包为 MP4/FLV/TS 等容器格式 |

| **P 帧** | Predicted Frame | 预测帧，依赖前一帧，体积小 |
| **SFU** | Selective Forwarding Unit | WebRTC 多人会议架构，服务器只转发不转码 |
| **RTSP** | Real-Time Streaming Protocol | IP 摄像头主流拉流协议，端口默认 554 |
| **RTMP** | Real-Time Messaging Protocol | 直播推流事实标准，端口默认 1935 |
| **HLS** | HTTP Live Streaming | Apple 开发的分片流媒体协议，浏览器广泛支持 |
| **WebRTC** | Web Real-Time Communication | 浏览器原生实时视频通信，延迟 < 300ms |
| **WHIP** | WebRTC-HTTP Ingestion Protocol | RFC 9725，WebRTC 推流标准（2025） |

## 本篇小结

1. **流 vs 文件**：流媒体的本质是"时序依赖的实时数据传输"，需要处理网络抖动、丢包、音视频同步等挑战
2. **三大场景**：点播（延迟不敏感）、直播（中等延迟）、实时通信（极低延迟），技术栈完全不同
3. **协议演进**：RealPlayer → Flash/RTMP → HLS/CDN → WebRTC → CMAF/WHIP，每代解决前代的痛点
4. **推流 vs 分发**：视频流从采集到播放需要两套协议，流媒体服务器负责中间的协议转换
5. **浏览器限制**：出于安全和技术原因，浏览器无法直接播 RTSP/RTMP，必须通过服务端中转
