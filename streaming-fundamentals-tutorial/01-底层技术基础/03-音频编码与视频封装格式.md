## 一、音频编码基础：为什么音频也需要压缩

读完本节，你能理解音频压缩的必要性，并掌握心理声学模型的核心原理。

未压缩的音频数据量远超想象：

```
PCM 原始音频：
  采样率 44100 Hz × 位深 16bit × 双声道
  = 44100 × 16 × 2 = 1,411,200 bit/s
  = 约 1.4 Mbps（CD 音质）

压缩后的 AAC：
  128 kbps（接近 CD 音质）
  压缩比约 11:1
```

**心理声学模型（Psychoacoustic Model）**是音频压缩的核心：人耳对不同频率的声音敏感度不同，利用这个特性，可以删除人耳感知不到的声音成分（遮蔽效应）。

## 二、AAC：流媒体的标准音频格式

读完本节，你能理解AAC的编码原理，并为不同场景选择合适的AAC Profile。

**AAC（Advanced Audio Coding）** 是 MPEG-4 标准的一部分，是目前流媒体领域使用最广泛的音频编解码器。

### 2.1 AAC 编码技术详解

**MDCT 变换（Modified Discrete Cosine Transform）**：

AAC 使用 MDCT 将时域音频信号转换为频域系数，类似于视频编码中的 DCT，但针对音频信号优化。

```
时域音频采样 → MDCT 变换 → 频域系数 → 量化 → 熵编码 → AAC 比特流
                    ↓
             心理声学模型分析（判断哪些频率可以舍弃）
```

**心理声学模型的三大原理**：

1. **频率遮蔽效应**：强音会掩盖临近频率的弱音。例如，1000Hz 的大声音会让 950Hz 和 1050Hz 的小声音变得听不见。
2. **时间遮蔽效应**：强音前后短时间内的弱音会被掩盖（约 50-200ms）。
3. **听觉阈值**：人耳对 2-5kHz 最敏感，对极低频（< 20Hz）和极高频（> 16kHz）不敏感。

AAC 编码器根据这些原理，对被遮蔽的频率分量进行更粗糙的量化（甚至直接丢弃），从而大幅减少数据量。

### AAC 的规格（Profile）

| Profile | 用途 | 特点 |
|---------|------|------|
| **LC（Low Complexity）** | 最常用，流媒体标准 | 兼容性最好，算法简单 |
| **HE-AAC v1** | 低码率（≤ 64kbps） | 添加 SBR（频谱带宽复制） |
| **HE-AAC v2** | 极低码率（≤ 32kbps） | SBR + PS（参数立体声） |
| **xHE-AAC** | 语音+音乐自适应 | 最新，用于播客/语音通话 |

**经验法则**：
- 音乐/视频配乐：AAC-LC 128kbps（立体声）
- 语音通话/直播背景音：AAC-LC 64kbps 或 HE-AAC 48kbps
- 极低码率场景：HE-AAC v2 24-32kbps

### AAC 的封装方式

AAC 有两种封装格式，在直播中必须注意区别：

| 格式 | 说明 | 使用场景 |
|------|------|---------|
| **ADTS**（Audio Data Transport Stream） | 每帧都有同步头，可单独播放 | HLS/TS 流 |
| **ADIF**（Audio Data Interchange Format） | 只有一个文件头，不能随机 Seek | 文件存储 |
| **RAW AAC** | 无封装头，依赖外部容器 | MP4/FLV 内部 |

```bash
# 提取 AAC 音频（ADTS 格式）
ffmpeg -i input.mp4 -vn -c:a copy output.aac

# 转换为 AAC-LC 128kbps
ffmpeg -i input.mp4 -vn -c:a aac -b:a 128k output.aac

# 查看 AAC 格式信息
ffprobe -v quiet -show_streams -select_streams a input.mp4
```

## 三、Opus：实时通信的最佳选择

读完本节，你能理解Opus的技术优势，并在WebRTC等实时通信场景中正确配置Opus编码器。

**Opus** 是 2012 年发布的开源、无专利费音频编解码器（IETF RFC 6716），是 WebRTC 的默认音频编解码器。

### 3.1 Opus 的混合编码架构

Opus 的最大创新在于**混合编码**：根据音频内容自动选择最适合的编码器。

```
Opus 编码器 = SILK（语音） + CELT（音乐）

音频输入 → 内容分析
            ↓
    ┌───────┴───────┐
    ↓               ↓
  语音特征       音乐特征
    ↓               ↓
  SILK 编码      CELT 编码
    ↓               ↓
    └───────┬───────┘
            ↓
    Opus 比特流
```

**SILK（Speech with Internet and Low Latency Extensions）**：
- 专为语音设计，来自 Skype 的语音编码技术
- 低码率下语音质量最好（6-24 kbps）
- 线性预测编码（LPC），擅长处理周期性语音信号

**CELT（Constrained Energy Lapped Transform）**：
- 专为音乐设计，处理复杂频谱
- 类似 AAC 的 MDCT 变换，但延迟更低
- 支持超宽带（48 kHz 采样率）

**自动切换机制**：
- 纯语音（电话会议）→ 100% SILK
- 纯音乐（音乐直播）→ 100% CELT
- 语音+背景音乐 → 混合模式（各占一定比例）

### Opus 的核心优势

| 特性 | Opus | AAC |
|------|------|-----|
| **延迟** | 2.5-60ms（可调） | 20-50ms（固定） |
| **码率范围** | 6-510 kbps | 8-320 kbps |
| **语音优化** | ✅ 内置 SILK 语音编码 | ❌ 无 |
| **音乐优化** | ✅ CELT 超宽带 | ✅ |
| **专利费** | 免费 | 需要付费 |
| **浏览器支持** | ✅ 100%（WebRTC 必须支持） | ✅ 98% |
| **硬件解码** | ⚠️ 较少 | ✅ 广泛 |

### 3.2 Opus 在 WebRTC 中的应用

WebRTC 强制要求支持 Opus，因为它是唯一能同时满足低延迟、高质量、宽码率范围的音频编解码器。

```javascript
// WebRTC 音频 SDP 协商（Opus 配置）
a=rtpmap:111 opus/48000/2
a=fmtp:111 minptime=10;useinbandfec=1;stereo=1
```

**关键参数**：
- `minptime=10`：最小打包时长 10ms（超低延迟）
- `useinbandfec=1`：启用前向纠错（丢包恢复）
- `stereo=1`：立体声

**Opus 的丢包恢复能力**：

Opus 内置 FEC（Forward Error Correction），即使丢包 10-20%，音质仍可接受。

```
正常传输：
[帧1][帧2][帧3][帧4] → 解码器

丢包情况（帧2丢失）：
[帧1][---][帧3][帧4]
       ↑
  用帧3的冗余数据恢复帧2（FEC）
```

### 什么场景用 Opus vs AAC？

```
WebRTC 视频通话/语音会议    → Opus（延迟 < 20ms，语音质量优）
HLS 点播/直播（浏览器播放） → AAC-LC（兼容性最好）
移动 App 音频存储           → AAC（iOS/Android 硬件支持好）
播客/语音内容               → Opus 或 xHE-AAC
```

## 五、封装格式：容器的作用

读完本节，你能理解为什么需要封装格式，以及封装格式与编解码器的本质区别。

**封装格式（Container Format）** 就是把视频流、音频流、字幕、元数据"打包"在一起的文件格式。

```
┌─────────────────────────────────────┐
│  封装格式（MP4/FLV/TS/MKV）          │
│  ┌──────────┐  ┌──────────────┐    │
│  │ 视频流   │  │ 音频流       │    │
│  │(H.264)   │  │(AAC/Opus)   │    │
│  └──────────┘  └──────────────┘    │
│  ┌──────────┐  ┌──────────────┐    │
│  │ 字幕流   │  │ 元数据       │    │
│  │(SRT/ASS) │  │(时长/分辨率) │    │
│  └──────────┘  └──────────────┘    │
└─────────────────────────────────────┘
```

### 5.1 容器格式 vs 编解码器：核心区别

这是初学者最容易混淆的概念：

| 概念 | 作用 | 类比 | 实例 |
|------|------|------|------|
| **编解码器（Codec）** | 压缩/解压缩音视频数据 | 压缩算法 | H.264, AAC, Opus |
| **封装格式（Container）** | 组织文件结构，存储多条流 | 包装盒 | MP4, MKV, FLV |

**关键区别**：
- H.264 是编解码器，MP4/MKV/TS 都可以装 H.264
- AAC 是编解码器，MP4/FLV/TS 都可以装 AAC
- **同样的 H.264+AAC 编码，换个容器格式，文件扩展名就不同**

```bash
# 相同编码，不同封装（无损转换）
ffmpeg -i input.mp4 -c copy output.mkv  # MP4 → MKV
ffmpeg -i input.mp4 -c copy output.flv  # MP4 → FLV
```

### 5.2 为什么需要容器格式？

**问题 1：音视频同步**

视频流和音频流是独立编码的，容器格式负责记录时间戳（PTS/DTS），确保播放时音画同步。

```
容器格式的时间戳记录：
视频流：[I帧 PTS=0][P帧 PTS=33][P帧 PTS=67]...
音频流：[帧 PTS=0][帧 PTS=21][帧 PTS=42]...
         ↓
    播放器根据 PTS 对齐
```

**问题 2：多轨道支持**

一个电影文件可能包含：
- 视频轨：1080p H.264
- 音频轨 1：英语 AAC
- 音频轨 2：中文 AAC
- 字幕轨 1：中文 SRT
- 字幕轨 2：英文 SRT

容器格式负责索引这些轨道，让播放器可以切换音轨和字幕。

**问题 3：元数据存储**

容器格式存储视频的元信息：
- 时长（Duration）
- 分辨率（Width × Height）
- 帧率（Frame Rate）
- 比特率（Bitrate）
- 创建时间、作者、版权信息

### 5.3 容器格式的结构组成

所有容器格式都包含三个基本部分：

```
┌─────────────────────────────────┐
│ 文件头（Header）                 │
│  - 格式签名（Magic Number）      │
│  - 格式版本                      │
│  - 全局元数据                    │
├─────────────────────────────────┤
│ 索引/元数据区（Metadata）        │
│  - 轨道列表                      │
│  - 时间戳映射表                  │
│  - 关键帧索引（用于 Seek）        │
├─────────────────────────────────┤
│ 媒体数据区（Payload）            │
│  - 视频帧数据                    │
│  - 音频帧数据                    │
│  - 交错存储（Interleaved）        │
└─────────────────────────────────┘
```

**不同容器格式的差异主要体现在**：
- **索引位置**：MP4 的 moov 可以在文件头或文件尾；FLV 的每个 Tag 自带时间戳
- **支持的编解码器**：WebM 只支持 VP8/VP9/AV1，MP4 支持几乎所有编解码器
- **流式特性**：FLV/TS 适合直播（可边写边播），MP4 适合点播（需要完整文件）

## 六、MP4（MPEG-4 Part 14）

MP4 是最常见的视频文件格式，基于 ISO Base Media File Format（ISOBMFF）。

### MP4 的 Box 结构

```
MP4 文件结构：
ftyp box  ─── 文件类型声明
moov box  ─── 元数据容器（关键！）
  ├── mvhd  ─── 视频时长、时间基
  ├── trak  ─── 视频轨道
  │    ├── tkhd  ─── 轨道头
  │    └── mdia  ─── 媒体数据
  │         ├── mdhd  ─── 媒体头
  │         └── minf  ─── 媒体信息
  │              └── stbl  ─── 采样表（关键！）
  │                   ├── stco  ─── 分片偏移量
  │                   └── stss  ─── 关键帧索引
  └── trak  ─── 音频轨道
mdat box  ─── 实际媒体数据
```

**关键问题：moov 的位置**

```
正常 MP4（moov 在末尾）：
[ftyp][mdat (视频数据)][moov (索引)]
                        ↑
                  下载完成才能播放！

Web 优化的 MP4（moov 前置）：
[ftyp][moov (索引)][mdat (视频数据)]
       ↑
  立即可以 Seek，边下载边播放！
```

```bash
# 将 moov 移到文件头（Web 优化）
ffmpeg -i input.mp4 -c copy -movflags +faststart output.mp4

# 验证 moov 位置
ffprobe -v quiet -show_format input.mp4 | grep start_time
```

### fMP4（Fragmented MP4）

fMP4 是 MP4 的分片变体，是 DASH 和 CMAF 的基础格式：

```
fMP4 结构：
[ftyp][moov (初始化段)] [moof+mdat (片段1)] [moof+mdat (片段2)] ...

优点：
- 可以无限追加片段（适合直播）
- 每个片段独立，支持随机访问
- 被 DASH/HLS fMP4/CMAF 广泛采用
```

## 七、FLV：直播的历史选择

读完本节，你能理解FLV格式的流式特性，以及为什么HTTP-FLV仍然是国内直播领域的主流选择。

**FLV（Flash Video）** 是 Adobe 为 Flash Player 设计的流媒体格式，虽然 Flash 已消亡，但 FLV 在直播领域仍广泛使用（通过 HTTP-FLV 协议）。

### 7.1 FLV 的流式结构

FLV 的设计哲学是"边写边播"，这是它适合直播的核心原因。

```
FLV 文件结构：
[FLV Header]  ─── 9字节，签名 + 版本 + 标志
[Tag Size 0]  ─── 始终为 0
[Tag 1]  ─── ScriptTag（元数据：时长/分辨率/帧率）
[Tag 2]  ─── VideoTag（SPS/PPS 初始化，关键！）
[Tag 3]  ─── AudioTag（音频配置）
[Tag 4]  ─── VideoTag（I 帧）
[Tag 5]  ─── AudioTag（音频帧）
...
```

**FLV 的每个 Tag 格式**：
```
[Tag Type 1B][Data Size 3B][Timestamp 3B][Ext 1B][StreamID 3B][Data]
```

**关键特性**：
- 每个 Tag 自带时间戳，不依赖全局索引
- 服务器可以无限追加 Tag，不需要回头修改文件头
- 播放器收到一个完整 Tag 就可以立即解码，无需等待整个文件

### 7.2 HTTP-FLV：为什么不用 RTMP？

虽然 FLV 最初是为 RTMP 协议设计的，但现在直播更多使用 **HTTP-FLV**：

| 协议 | 传输层 | 优势 | 劣势 |
|------|--------|------|------|
| **RTMP** | TCP 1935 | 延迟最低（1-2s） | 企业防火墙封禁、CDN 支持少 |
| **HTTP-FLV** | HTTP 80/443 | 穿透性好、CDN 友好、可用 nginx 反代 | 延迟稍高（2-3s） |
| **HLS** | HTTP | 兼容性最好 | 延迟高（5-10s） |

**HTTP-FLV 的工作原理**：

```
推流端（OBS）→ RTMP → 媒体服务器（SRS/ZLM）→ HTTP-FLV → CDN → 浏览器
                          ↓
                  转换为 HTTP 长连接，持续推送 FLV Tag
```

浏览器通过 `fetch()` 或 `XMLHttpRequest` 建立 HTTP 长连接，服务器持续写入 FLV Tag，浏览器用 MSE（Media Source Extensions）解封装并喂给 `<video>` 标签。

### 为什么直播选 FLV 而非 MP4？

| 特性 | FLV | MP4 |
|------|-----|-----|
| **边生成边播放** | ✅（流式结构，无需 moov） | ❌（需要完整 moov） |
| **断点续传** | ✅ | ❌（标准 MP4 不支持） |
| **追加写入** | ✅（不断追加 Tag） | ❌（需要重写 moov） |
| **随机 Seek** | ⚠️（需要时间戳索引） | ✅（stco 精确偏移） |
| **浏览器原生支持** | ❌（需要 MSE） | ✅（`<video src>`） |
| **文件大小开销** | 小 | 稍大（索引信息多） |

## 八、TS（MPEG-2 Transport Stream）

**TS（Transport Stream）** 是 HLS 的默认切片格式，源自数字电视广播标准（DVB/ATSC）。

### TS 的包结构

```
TS 包：固定 188 字节
┌──────────────────────────────────────────┐
│ 同步字节(1B) │ PID(13bit) │ 控制位(3bit) │
│    0x47      │  节目标识  │  连续计数    │
├──────────────────────────────────────────┤
│ Adaptation Field（可选，用于时间戳）      │
├──────────────────────────────────────────┤
│ Payload（视频/音频数据）                  │
└──────────────────────────────────────────┘
```

**TS 的关键概念**：

| 概念 | 说明 |
|------|------|
| **PAT（Program Association Table）** | 节目列表，指向 PMT |
| **PMT（Program Map Table）** | 每个节目的流列表（PID 映射） |
| **PID** | 包标识符，区分不同流（视频/音频/字幕） |
| **PCR（Program Clock Reference）** | 时间基准，用于音视频同步 |

### TS vs fMP4 用于 HLS

苹果在 HLS v7（iOS 10+/Safari 10+）引入 **fMP4 切片**（替代传统 TS 切片）：

| 对比 | TS 切片 | fMP4 切片 |
|------|---------|-----------|
| 文件大小 | 较大（固定 188B 包） | 较小（无填充） |
| 兼容性 | ✅ 几乎所有设备 | ⚠️ 需要较新系统 |
| CMAF 统一 | ❌ | ✅（与 DASH 共享切片） |
| 加密 | AES-128 | CENC 标准加密 |

## 九、MKV、WebM 与其他格式

| 格式 | 全称 | 主要用途 | 特点 |
|------|------|---------|------|
| **MKV** | Matroska | 本地视频存储 | 支持几乎所有编解码器，开源，无流媒体支持 |
| **WebM** | Web Media | 浏览器网页视频 | MKV 子集，只支持 VP8/VP9/AV1 + Vorbis/Opus |
| **MOV** | QuickTime Movie | Apple 生态 | 与 MP4 相似，但有专有扩展 |
| **AVI** | Audio Video Interleave | 历史遗留 | 老格式，不支持现代编解码器 |
| **MPEG-PS** | Program Stream | DVD | 局域网/设备连接场景 |
| **OGG** | Ogg Container | 开源音频/视频 | 装 Theora 视频 + Vorbis 音频 |

### 9.1 CMAF：统一 HLS 和 DASH 的未来

**CMAF（Common Media Application Format）** 是 2018 年发布的 ISO 标准（ISO/IEC 23000-19），旨在统一 HLS 和 DASH 两大自适应流媒体协议。

**问题背景**：

在 CMAF 之前，CDN 需要存储两套切片：
```
HLS（Apple 生态）→ .ts 切片 + .m3u8 播放列表
DASH（其他平台）→ .m4s 切片 + .mpd 播放列表

相同内容，双倍存储成本！
```

**CMAF 的解决方案**：

使用 **fMP4（Fragmented MP4）** 作为统一的切片格式，HLS 和 DASH 共享相同的媒体切片文件：

```
CMAF 架构：
┌─────────────────────────────────────┐
│ 编码器输出（H.264/AAC）              │
└──────────────┬──────────────────────┘
               ↓
       CMAF fMP4 切片（.m4s）
       [init.mp4][seg1.m4s][seg2.m4s]...
               ↓
        ┌──────┴──────┐
        ↓             ↓
    .m3u8 清单    .mpd 清单
   （HLS 客户端）（DASH 客户端）
```

**技术细节**：

CMAF 切片由两部分组成：
1. **初始化段（Initialization Segment）**：包含 `ftyp` + `moov` box，存储编解码器参数（SPS/PPS/音频配置）
2. **媒体段（Media Segment）**：包含 `moof` + `mdat` box，存储实际音视频帧数据

```bash
# CMAF 初始化段结构
init.mp4:
  [ftyp] - 文件类型：cmfc（CMAF 标识）
  [moov] - 元数据
    └─ [trak] - 轨道信息（不包含实际数据）

# CMAF 媒体段结构
seg001.m4s:
  [moof] - Movie Fragment（本段的时间戳和索引）
  [mdat] - 实际音视频数据
```

**CMAF 的优势**：

| 特性 | 传统方案 | CMAF |
|------|---------|------|
| **存储成本** | 双倍（TS + fMP4） | 单份（共享 fMP4） |
| **延迟** | HLS ≥ 6s，DASH ≥ 4s | LL-HLS/LL-DASH ≤ 2s |
| **兼容性** | HLS 需 iOS 10+/Safari 10+ | 向后兼容 |
| **加密** | HLS 用 AES-128，DASH 用 CENC | 统一 CENC（Common Encryption） |

**实际应用**：

```bash
# 生成 CMAF 切片（HLS + DASH 共用）
ffmpeg -i input.mp4 \
  -c:v libx264 -crf 23 -g 60 \
  -c:a aac -b:a 128k \
  -f dash \
  -seg_duration 2 \
  -use_timeline 1 \
  -use_template 1 \
  -adaptation_sets "id=0,streams=v id=1,streams=a" \
  -hls_playlist 1 \
  output.mpd

# 生成文件：
# output.mpd              # DASH 清单
# output_master.m3u8      # HLS 主清单
# init-stream0.m4s        # 视频初始化段
# init-stream1.m4s        # 音频初始化段
# chunk-stream0-00001.m4s # 视频切片1
# chunk-stream1-00001.m4s # 音频切片1
```

**LL-HLS（Low-Latency HLS）与 CMAF**：

Apple 在 2019 年引入 LL-HLS（iOS 14+/tvOS 14+），基于 CMAF 实现亚2秒延迟：

- **传统 HLS**：6 秒切片 × 3 段缓冲 = 18 秒延迟
- **LL-HLS**：200ms 部分段（Partial Segment）= 1-2 秒延迟

```
LL-HLS 切片结构：
[2秒完整段]
  ├─ [200ms 部分段 1]
  ├─ [200ms 部分段 2]
  ├─ ...
  └─ [200ms 部分段 10]

播放器不等完整段下载完，收到第一个部分段立即开始播放
```

## 十、封装格式对比与选型

```
场景 → 推荐格式
────────────────────────────────────────────────────────
RTMP/HTTP-FLV 直播       → FLV（流式，可边写边播）
HLS 切片（传统）          → TS（.ts 文件，兼容性最好）
HLS 切片（现代/CMAF）     → fMP4（.m4s 文件，更小）
DASH 切片                → fMP4（.m4s 文件）
Web 点播（HTML5 video）   → MP4（moov 前置 faststart）
存储归档                  → MKV（支持最多编解码器）
浏览器 WebRTC             → 内部 RTP 包，记录用 WebM
iOS/Android App          → MP4
数字电视广播              → TS（DVB 标准）
```

**决策速查**：

| 问题 | 答案 |
|------|------|
| 直播服务器写录像文件 | TS 或 fMP4（可追加写入） |
| 浏览器 `<video src>` | MP4（faststart），不要 FLV/TS |
| HLS m3u8 的切片格式 | TS（兼容优先）或 fMP4（新建系统） |
| 存储海量视频降低成本 | H.265/AV1 + MP4（体积最小） |
| 无损保留所有轨道 | MKV（最灵活） |

## 十一、动手实践

```bash
# 1. 查看视频的封装格式和流信息
ffprobe -v quiet -print_format json -show_format -show_streams input.mp4

# 2. 无损转换封装格式（不重新编码）
# MP4 → MKV
ffmpeg -i input.mp4 -c copy output.mkv

# MP4 → FLV
ffmpeg -i input.mp4 -c copy -f flv output.flv

# MP4 → TS（HLS 切片用）
ffmpeg -i input.mp4 -c copy -f mpegts output.ts

# 3. moov 前置（Web 优化）
ffmpeg -i input.mp4 -c copy -movflags +faststart output_web.mp4

# 4. 提取音频轨道
ffmpeg -i input.mp4 -vn -c:a copy audio.aac  # 提取 AAC
ffmpeg -i input.mp4 -vn -c:a libopus -b:a 128k audio.opus  # 转 Opus

# 5. 更换音频编解码器（不重编视频）
ffmpeg -i input.mp4 -c:v copy -c:a aac -b:a 128k output.mp4

# 6. 生成 HLS 切片（TS 格式）
ffmpeg -i input.mp4 \
  -c:v libx264 -crf 23 \
  -c:a aac -b:a 128k \
  -hls_time 6 \
  -hls_list_size 0 \
  -hls_segment_filename 'segment_%03d.ts' \
  output.m3u8

# 7. 生成 HLS 切片（fMP4 格式）
ffmpeg -i input.mp4 \
  -c:v libx264 -crf 23 \
  -c:a aac -b:a 128k \
  -hls_time 6 \
  -hls_segment_type fmp4 \
  -hls_segment_filename 'segment_%03d.m4s' \
  output.m3u8

# 8. 对比 MP4 和 TS 的文件大小（相同内容）
ffmpeg -i input.mp4 -c copy -y mp4_copy.mp4 2>/dev/null
ffmpeg -i input.mp4 -c copy -y ts_copy.ts 2>/dev/null
echo "MP4: $(du -sh mp4_copy.mp4)"
echo "TS:  $(du -sh ts_copy.ts)"
```

## 十二、常见问题排查

**Q：视频有画面无声音？**

```bash
# 检查音频轨道
ffprobe -show_streams input.mp4 | grep codec_name

# 可能原因：
# 1. 音频编解码器不兼容（如 MP3 in MP4）
ffmpeg -i input.mp4 -c:v copy -c:a aac fixed.mp4
# 2. 音频轨道丢失（多路转码时忘加 -c:a）
# 3. 音频编解码器硬件不支持（如旧设备不支持 Opus）
```

**Q：视频无法拖拽进度条（不能 Seek）？**

```bash
# 原因：MP4 的 moov 在文件末尾
# 解决：faststart
ffmpeg -i input.mp4 -c copy -movflags +faststart output.mp4

# 验证 moov 位置（atom 列表）
ffprobe -v trace input.mp4 2>&1 | grep -E "^(moov|mdat)" | head -5
```

**Q：FFmpeg 报错 "moov atom not found"？**

说明文件是损坏的 MP4 或未完成写入的录像文件。FLV/TS 格式不会有此问题，因为它们不依赖文件末尾的索引。

**Q：HLS 切片时出现音视频不同步？**

```bash
# 必须设置固定关键帧间隔，且与 hls_time 对齐
ffmpeg -i input.mp4 \
  -c:v libx264 -crf 23 \
  -g 60 -keyint_min 60 \   # GOP = 2秒（30fps × 2）
  -c:a aac -b:a 128k \
  -hls_time 2 \             # 切片时长 = 2秒（与 GOP 对齐）
  output.m3u8
```

**Q：FLV 文件损坏，只有前几分钟可以播放？**

FLV 直播录像如果服务器崩溃，文件可能没有写完 FLV 结束标记。用 `ffmpeg -i broken.flv -c copy fixed.mp4` 通常可以恢复，FFmpeg 会忽略不完整的 Tag。

## 本篇小结

1. **AAC vs Opus**：AAC 是流媒体/存储标准（兼容性好），Opus 是实时通信标准（低延迟、开源）
2. **封装格式 ≠ 编解码器**：MP4/FLV/TS 是容器，H.264/AAC 是压缩算法
3. **FLV 用于直播**：流式结构，可追加写入，无需完整文件才能播放
4. **TS 用于 HLS**：固定 188 字节包，源自广播标准，可从任意点恢复
5. **MP4 用于点播**：加 `-movflags +faststart` 把 moov 前置，支持边下边播
6. **fMP4 是趋势**：统一 HLS 和 DASH，被 CMAF 标准采用
