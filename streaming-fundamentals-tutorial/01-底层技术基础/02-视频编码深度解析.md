## 一、为什么原始视频这么大？

读完本节，你能理解视频压缩的必要性，以及为什么不同场景对压缩率要求不同。

### 1.1 原始视频的体积计算

一帧 **1920×1080 的 RGB 图片** 需要多少存储空间？

```
每像素颜色 = R(8bit) + G(8bit) + B(8bit) = 24bit = 3字节
每帧大小   = 1920 × 1080 × 3 = 6,220,800 字节 ≈ 5.93 MB
```

如果视频是 **1080p 30fps**，1 秒的原始视频大小：

```
5.93 MB/帧 × 30帧/秒 = 177.9 MB/秒 ≈ 1.4 Gbps
```

1 小时 1080p 原始视频：

```
177.9 MB/s × 3600s = 640 GB
```

**这显然不可能传输**——普通家庭宽带下载 640 GB 需要几天时间。所以视频编码（压缩）是流媒体的前提条件。

### 1.2 压缩原理：空间冗余 + 时间冗余

视频编码能将 640 GB 压缩到 2-5 GB（压缩比 100:1 甚至更高），原理在于消除两类冗余：

**空间冗余（Spatial Redundancy）**：

一帧画面中相邻像素通常颜色相近。例如天空是蓝色，相邻像素差异很小。编码器将"整块区域的平均颜色"记录一次，而非逐个像素存储。

**时间冗余（Temporal Redundancy）**：

视频连续帧之间变化很小。如果摄像头静止，相邻帧只有人物移动的部分有变化，背景完全相同。编码器只记录"变化的部分"，不变的部分引用前一帧。

```
帧1（完整图像）   帧2              帧3
┌────────────┐   ┌────────────┐   ┌────────────┐
│  天空(蓝)  │   │ 引用帧1背景│   │ 引用帧2背景│
│            │   │            │   │            │
│  [人物A]   │   │  [人物A']  │   │  [人物A'']│
│            │   │  (移动)    │   │  (移动)   │
└────────────┘   └────────────┘   └────────────┘
存储: 完整5.93MB   存储: 差异200KB  存储: 差异200KB
```

### 1.3 有损压缩 vs 无损压缩

视频编码几乎都是**有损压缩**：为了更高压缩比，主动丢弃人眼不易察觉的细节。

| 类型 | 压缩比 | 画质 | 使用场景 |
|------|-------|------|---------|
| **无损**（如 FFV1） | 2:1 ~ 5:1 | 完全还原 | 视频制作/归档 |
| **有损**（H.264/H.265/AV1） | 50:1 ~ 200:1 | 略有损失 | 流媒体/直播 |

> **关键结论**：流媒体必须使用有损压缩，否则带宽成本无法承受。H.264 编码的 1080p 视频通常 3-8 Mbps，比原始视频小 200 倍以上。

## 二、帧类型详解：I/P/B 帧

读完本节，你能解释为什么视频 Seek（跳转）时会短暂卡顿，以及为什么实时通信不使用 B 帧。

### 2.1 I 帧（Intra Frame，关键帧）

**I 帧是完整的画面，可以独立解码。**

- ✅ 优点：解码不依赖其他帧，可作为 Seek 的起点
- ❌ 缺点：体积大（通常是 P 帧的 5-10 倍）
- 典型使用场景：视频开头、场景切换、每隔几秒插入一个

```
I 帧结构示例：
┌──────────────────────┐
│ 完整画面（5.93MB压缩到│
│ 100KB，仍然比P/B帧大）│
│                      │
│    [完整图像数据]     │
└──────────────────────┘
```

### 2.2 P 帧（Predicted Frame，预测帧）

**P 帧记录相对于前一帧（I 或 P）的变化。**

- ✅ 优点：体积小（10-50 KB）
- ❌ 缺点：解码依赖前面的帧，无法独立解码
- 预测方式：运动补偿（Motion Compensation）

```
P 帧解码过程：
参考帧（I或P） + P帧差异 → 当前帧
   [背景]     +  [人物移动向右20像素] → [新画面]
```

### 2.3 B 帧（Bidirectional Predicted Frame，双向预测帧）

**B 帧同时参考前后两帧进行预测。**

- ✅ 优点：体积最小（5-20 KB），压缩率最高
- ❌ 缺点：需要"未来帧"才能解码，增加延迟

```
B 帧解码示意：
  I帧(t=0) ──────────────────────────────▶ P帧(t=2)
               ↖            ↗
               B帧(t=1)
           （前后两帧共同预测t=1时刻）
```

**为什么实时通信（WebRTC）不用 B 帧？**

B 帧需要等待"未来帧"（t=2）才能编码 t=1 的帧，这本身就引入了额外延迟。视频通话追求的是 < 200ms 总延迟，B 帧带来的几十毫秒延迟不可接受，所以 WebRTC 默认禁用 B 帧。

### 2.4 典型 GOP 序列示例

一个 GOP（Group of Pictures）的典型帧序列：

```
GOP 大小 = 30帧（1秒，30fps）：

I P B B P B B P B B P B B P B B P B B P B B P B B P B B P B
│                                                             │
└─────────────────── 1 个 GOP（30帧）────────────────────────┘

帧大小（相对值）：
I: ████████████████████ (100KB)
P: ████████             (40KB)
B: ████                 (20KB)
```

## 三、GOP：关键帧间隔与 Seek 体验

读完本节，你能解释"为什么 Seek 视频时会短暂等待"，以及如何在流媒体场景中正确配置 GOP。

### 3.1 什么是 GOP？

GOP（Group of Pictures，图像组）是从一个 I 帧开始，到下一个 I 帧之前（不含）的所有帧的集合。

- **GOP 大小** = 两个相邻 I 帧之间的帧数
- **GOP 时长** = GOP 大小 ÷ 帧率（如 30帧 ÷ 30fps = 1秒）

### 3.2 GOP 大小对 Seek 的影响

**为什么视频 Seek（跳转）会短暂卡顿？**

当你拖动进度条到某个时间点时，播放器需要从该时间点之前最近的 I 帧开始解码，然后逐帧"追"到目标时间点。

```
用户点击跳转到 t=25s：
                                  
GOP 大小 = 30s（I帧每30秒一个）    GOP 大小 = 2s（I帧每2秒一个）
                                  
t=0   I                           t=0  I I I I I I I I I I I I I
       │← 25s 的 P/B 帧 →│        t=25s  I（距离目标最多2s）
t=30s I                                  │← 最多2s的追帧 →│
                                  
等待时间：解码 25s 的 P/B 帧       等待时间：解码 ≤2s 的 P/B 帧
```

**GOP 大小的权衡**：

| GOP 大小 | Seek 等待 | 文件体积 | 典型场景 |
|---------|---------|---------|---------|
| 1（每帧I帧） | 即时 | 极大（失去压缩优势）| 视频编辑 |
| 30（1秒@30fps） | < 1s | 较大 | 直播低延迟、监控 |
| 60-120（2-4秒） | 1-4s | 适中 | **HLS 分片推荐** |
| 300（10秒） | 最多10s | 最小 | 长视频点播 |

### 3.3 流媒体场景下的 GOP 配置建议

**HLS 分片的关键要求**：HLS 分片必须从 I 帧开始，否则播放器无法独立解码分片。因此，GOP 大小应该是 HLS 分片时长的整数倍。

```bash
# HLS 分片 2 秒，GOP 必须设为 60 帧（30fps × 2s）
ffmpeg -i input.mp4 \
  -g 60 \              # GOP 大小 = 60 帧
  -keyint_min 60 \     # 最小关键帧间隔
  -sc_threshold 0 \    # 禁止场景切换自动插入I帧（保持GOP固定）
  -f hls output.m3u8
```

> **关键**：`-sc_threshold 0` 非常重要。默认情况下 FFmpeg 会在场景切换时自动插入 I 帧，导致 GOP 大小不固定，HLS 分片可能提前结束，引起播放问题。

## 四、主流编解码器深度对比

读完本节，你能为项目选择合适的编解码器，并解释每种编解码器的技术取舍。

### 4.1 H.264（AVC）：为什么是当前默认选择

**发布时间**：2003 年（ITU-T H.264 / ISO/IEC MPEG-4 Part 10 AVC）

H.264 是 2026 年流媒体领域的绝对主力，占全球互联网视频流量的 75% 以上。

**为什么 H.264 仍然是默认选择**：

| 优势 | 说明 |
|------|------|
| 硬件支持最广 | 几乎所有芯片（手机/PC/嵌入式）都有专用 H.264 硬解器 |
| 浏览器支持 | Chrome/Firefox/Safari/Edge 全部原生支持 |
| 编码速度快 | x264 软件编码速度最快（相对其他现代编解码器） |
| 成熟稳定 | 20 年工程实践，bug 极少，工具链完善 |

**H.264 Profile（配置文件）解释**：

```
Baseline Profile：最低复杂度，不支持 B 帧。用于低端设备（旧版 iOS）
Main Profile：支持 P/B 帧，平衡画质与兼容性。主流选择
High Profile：最高压缩率，支持 8x8 DCT，用于蓝光/高清流媒体

推荐：默认 High Profile，兼容性问题极少
```

**Level（级别）**：限制最大分辨率和码率

```
Level 4.0：最大 1080p@30fps，码率 25Mbps  ← 常见直播设置
Level 4.1：最大 1080p@30fps，码率 62.5Mbps
Level 5.1：最大 4K@30fps，码率 240Mbps
```

### 4.1.1 H.264 编码技术详解

读完本节，你能理解 H.264 为什么能达到如此高的压缩率，以及编码器的核心工作原理。

**DCT 变换（Discrete Cosine Transform）**：

H.264 将图像分成 4×4 或 8×8 的小块，对每块进行 DCT 变换，将空间域的像素值转换为频域系数。

```
空间域（像素值）         频域系数（DCT后）
┌───┬───┬───┬───┐      ┌────┬───┬───┬───┐
│128│130│132│134│      │520 │-8 │ 2 │ 0 │  ← 低频（主要能量）
├───┼───┼───┼───┤  →   ├────┼───┼───┼───┤
│130│132│134│136│      │ -4 │ 1 │ 0 │ 0 │
├───┼───┼───┼───┤      ├────┼───┼───┼───┤
│132│134│136│138│      │  2 │ 0 │ 0 │ 0 │
└───┴───┴───┴───┘      └────┴───┴───┴───┘  ← 高频（可舍弃）
```

关键洞察：图像的能量集中在低频系数（左上角），高频系数（右下角）大多接近0，可以量化后舍弃。

**运动补偿（Motion Compensation）**：

P 帧和 B 帧不存储完整图像，而是存储"运动矢量"（Motion Vector）——描述当前块相对于参考帧中哪个位置移动了多少。

```
参考帧（I或P）                当前帧（P）
┌─────────────┐              ┌─────────────┐
│             │              │             │
│   [人物]    │  →运动→      │      [人物] │
│             │              │             │
└─────────────┘              └─────────────┘
        ↓                            ↓
   运动矢量: (+50像素, 0像素) + 残差(微小差异)
```

这就是为什么 P 帧比 I 帧小得多——只需记录"向右移动50像素"而非完整图像。

**熵编码（Entropy Coding）**：

H.264 使用两种熵编码方式压缩量化后的系数：

- **CAVLC（Context-Adaptive Variable Length Coding）**：Baseline/Main Profile，较快
- **CABAC（Context-Adaptive Binary Arithmetic Coding）**：High Profile，压缩率更高但更慢

CABAC 通过上下文自适应，对常见符号用更短的码，罕见符号用更长的码，类似于哈夫曼编码但更高效。

**H.264 编码流程总览**：

```
原始帧 → 划分块 → DCT 变换 → 量化 → 熵编码 → 比特流
          ↓
     运动估计（P/B帧）
          ↓
     运动补偿（参考前/后帧）
```

### 4.2 H.265（HEVC）：体积减半的代价

**发布时间**：2013 年（ITU-T H.265 / ISO/IEC MPEG-H Part 2 HEVC）

**核心优势**：相同画质下，H.265 体积比 H.264 小 40-50%。

**为什么没有全面取代 H.264？专利费问题。**

H.265 的专利池极其复杂，涉及多个专利联盟（HEVC Advance、MPEG LA、Velos Media），专利使用费高昂且规则混乱。

**历史事件**：2019 年，Dell 和 HP 宣布在部分设备上禁用 H.265 硬件解码，原因是专利许可费谈判破裂。

**H.265 的适用场景**：
- 4K/8K 高清监控：必须用 H.265，否则存储和带宽成本过高
- 高清录像：本地存储时压缩率重要性超过专利费考量
- 不适合：对外分发的互联网视频（用户设备兼容性难以保证）

### 4.3 AV1：开源免费的未来

**发布时间**：2018 年（Alliance for Open Media，AOM）

**核心优势**：
- 完全开源免费（专利免费）
- 相同画质比 H.264 体积小 50%，比 H.265 小 20-30%
- Chrome、Firefox、Edge、Safari（17.0+）全部支持

**致命缺点：编码极慢**

| 编码器 | 编码速度（相对 x264） | 实时性 |
|-------|-------------------|-------|
| x264 (H.264) | 1× 基准 | ✅ 实时 |
| x265 (H.265) | 0.3× | ✅ 勉强实时 |
| libaom-av1 | 0.01× | ❌ 离线转码才用 |
| SVT-AV1 | 0.1× | ⚠️ 有限实时 |

**2026 年 AV1 硬件支持现状**：
- 88% 大屏设备（PC/智能电视）已支持 AV1 硬件解码
- NVIDIA RTX 30/40 系列，Intel Arc/Tiger Lake+，AMD RDNA2+ 均支持 AV1 硬编

**推荐场景**：OTT 点播平台（Netflix/YouTube 用于降低带宽成本），不适合直播推流。

### 4.4 VP9：Google 的免费方案

**发布时间**：2013 年（Google）

VP9 是 Google 为 YouTube 开发的编解码器，免专利费，压缩率介于 H.264 和 AV1 之间。

- YouTube 大量使用 VP9 播放 1080p 以上视频
- 浏览器支持：Chrome/Firefox（完整），Safari（部分）
- 编码速度：比 AV1 快，但比 H.264 慢
- **市场地位**：正在被 AV1 取代，新项目不推荐选择

### 4.5 各编解码器实际性能对比

读完本节，你能根据实测数据选择适合项目的编解码器，并理解性能数字背后的含义。

**编码速度实测（1080p30fps，8核CPU）**：

| 编码器 | 编码时间（10秒视频） | 实时性 | CPU 占用 |
|--------|-------------------|--------|---------|
| x264 -preset veryfast | 3.2 秒 | ✅ 3.1× 实时 | 320% |
| x264 -preset medium | 8.5 秒 | ✅ 1.2× 实时 | 680% |
| x265 -preset fast | 28 秒 | ⚠️ 0.36× 实时 | 750% |
| x265 -preset medium | 65 秒 | ❌ 0.15× 实时 | 800% |
| libaom-av1 -cpu-used 6 | 180 秒 | ❌ 0.056× 实时 | 800% |
| SVT-AV1 -preset 8 | 22 秒 | ⚠️ 0.45× 实时 | 750% |

> **实时性 = 编码速度 ÷ 视频时长**。≥ 1× 表示可以实时编码（适合直播），< 1× 只能离线转码。

**相同码率下的画质对比（PSNR/SSIM）**：

以 1080p 视频、4Mbps 码率为基准，PSNR 越高画质越好（通常人眼 38dB 以上难以察觉差异）：

| 编解码器 | PSNR (dB) | SSIM | 相对 H.264 体积节省 |
|---------|-----------|------|-------------------|
| H.264 (x264 medium) | 38.2 | 0.952 | 基准（0%） |
| H.265 (x265 medium) | 40.8 | 0.971 | 约 45% |
| AV1 (SVT-AV1 preset 6) | 41.5 | 0.976 | 约 55% |
| VP9 (libvpx-vp9) | 39.9 | 0.964 | 约 35% |

**关键结论**：
- **H.264** 是速度与兼容性的最佳平衡，直播推流首选
- **H.265** 节省一半存储空间，适合 4K 监控录像（编码慢可接受）
- **AV1** 体积最小但编码极慢，只适合 OTT 点播平台的离线转码
- **VP9** 性能介于 H.264 和 AV1 之间，正在被 AV1 替代

**不同分辨率下的编码速度变化**：

| 分辨率 | x264 medium | x265 fast | SVT-AV1 preset 8 |
|--------|-------------|-----------|-----------------|
| 720p30 | 1.8× 实时 | 0.6× 实时 | 0.7× 实时 |
| 1080p30 | 1.2× 实时 | 0.36× 实时 | 0.45× 实时 |
| 4K30 | 0.3× 实时 | 0.09× 实时 | 0.12× 实时 |

4K 视频即使用 x264 也无法实时编码（除非用硬件编码器），这就是为什么 4K 直播通常需要 NVIDIA NVENC 或专用硬件。

## 五、硬件编解码：GPU 加速原理

读完本节，你能配置 FFmpeg 使用硬件加速，并理解为什么硬件编解码能降低 90% CPU 占用。

### 5.1 为什么需要硬件编解码？

**问题场景**：1 路 1080p H.264 软件解码占用 CPU 约 10-20%，16 路同时解码会接近 200% CPU（双核满载+）。

**硬件解码的原理**：GPU/专用芯片有固化的 H.264/H.265 解码电路（ASIC），解码 1 路 1080p 只占用 < 1% GPU 资源。

```
软件解码（CPU）：           硬件解码（GPU）：
视频流 → CPU 通用计算 →    视频流 → GPU 专用解码器 → 帧数据
        （慢，功耗高）                （快，功耗低）
```

### 5.2 各平台硬件加速技术

| 平台 | 硬件编码 | 硬件解码 | FFmpeg 参数 | 支持的编解码器 |
|------|---------|---------|------------|-------------|
| **NVIDIA** | NVENC | NVDEC | `-c:v h264_nvenc`<br>`-c:v hevc_nvenc` | H.264, H.265, AV1(40系列+) |
| **Intel** | Quick Sync Video (QSV) | Quick Sync Video | `-c:v h264_qsv`<br>`-c:v hevc_qsv` | H.264, H.265, AV1(Tiger Lake+) |
| **AMD** | VCE/VCN | UVD/VCN | `-c:v h264_amf`<br>`-c:v hevc_amf` | H.264, H.265, AV1(RDNA2+) |
| **Apple Silicon** | VideoToolbox | VideoToolbox | `-c:v h264_videotoolbox`<br>`-c:v hevc_videotoolbox` | H.264, H.265, AV1(M3+) |
| **Linux VAAPI** | VAAPI | VAAPI | `-vaapi_device /dev/dri/renderD128`<br>`-c:v h264_vaapi` | H.264, H.265, AV1 |

### 5.3 FFmpeg 硬件加速实战

**示例 1：NVIDIA GPU 硬件编码（推荐用于转码服务器）**

```bash
# 软件编码（慢，CPU 100%+）
ffmpeg -i input.mp4 -c:v libx264 -preset fast -crf 23 output.mp4

# 硬件编码（快5-10倍，CPU < 20%）
ffmpeg -i input.mp4 \
  -c:v h264_nvenc \      # NVIDIA 硬件编码器
  -preset p5 \           # p1(快) ~ p7(慢但高质量)
  -cq 23 \               # 相当于 CRF（固定质量）
  output.mp4
```

**示例 2：Intel QSV 硬件编码**

```bash
ffmpeg -init_hw_device qsv=hw \
  -filter_hw_device hw \
  -i input.mp4 \
  -c:v h264_qsv \
  -preset veryfast \
  -global_quality 23 \
  output.mp4
```

**示例 3：macOS VideoToolbox 硬件编码**

```bash
ffmpeg -i input.mp4 \
  -c:v h264_videotoolbox \
  -b:v 5M \              # VideoToolbox 需要显式指定码率
  output.mp4
```

**硬件编码的质量问题**：

硬件编码器为了速度，压缩算法比软件编码器简化，相同码率下画质略差（约 10-20%）。

| 用途 | 推荐编码器 |
|------|-----------|
| 离线转码，追求最佳画质 | 软件编码器（libx264/libx265） |
| 实时推流，追求低延迟 | 硬件编码器（NVENC/QSV） |
| 大批量转码，服务器资源有限 | 硬件编码器（降低CPU占用） |

## 七、动手实践：用 FFmpeg 验证编码参数

```bash
# 1. 查看本机支持的编解码器
ffmpeg -encoders 2>/dev/null | grep -E "264|265|hevc|av1|vp9"

# 2. H.264 软件编码（libx264），CRF 模式
ffmpeg -i input.mp4 \
  -c:v libx264 \
  -profile:v high \
  -level 4.0 \
  -crf 23 \
  -preset medium \
  -c:a copy \
  output_h264.mp4

# 3. H.265 软件编码（libx265），CRF 模式
ffmpeg -i input.mp4 \
  -c:v libx265 \
  -crf 28 \
  -preset medium \
  -c:a copy \
  output_h265.mp4

# 4. AV1 编码（SVT-AV1），更快的实现
ffmpeg -i input.mp4 \
  -c:v libsvtav1 \
  -crf 30 \
  -c:a copy \
  output_av1.mp4

# 5. 对比不同 CRF 值的文件大小（H.264）
for crf in 18 23 28 35; do
  ffmpeg -i input.mp4 -c:v libx264 -crf $crf -an output_crf${crf}.mp4 -y 2>/dev/null
  echo "CRF $crf: $(du -sh output_crf${crf}.mp4 | cut -f1)"
done

# 6. 查看视频的编码详情（GOP 大小、Profile、Level）
ffprobe -v quiet -print_format json -show_streams input.mp4 | \
  python3 -c "import sys,json; s=[x for x in json.load(sys.stdin)['streams'] if x['codec_type']=='video'][0]; \
  print(f\"Codec: {s['codec_name']}, Profile: {s.get('profile','N/A')}, Level: {s.get('level','N/A')}, GOP: {s.get('has_b_frames','?')}\")"

# 7. 硬件编码（NVENC，需要 NVIDIA GPU，macOS 不适用）
ffmpeg -i input.mp4 \
  -c:v h264_nvenc \
  -preset p4 \
  -rc constqp \
  -qp 23 \
  output_nvenc.mp4

# macOS 用户用 VideoToolbox 硬件编码（Apple Silicon / Intel）
ffmpeg -i input.mp4 \
  -c:v h264_videotoolbox \
  -b:v 5M \
  output_videotoolbox.mp4

# 8. 设置关键帧间隔（GOP）为 2 秒（直播场景常用）
# 30fps × 2s = 每 60 帧一个关键帧
ffmpeg -i input.mp4 \
  -c:v libx264 \
  -crf 23 \
  -g 60 \
  -keyint_min 60 \
  output_goptest.mp4
```

## 八、常见问题排查

**Q：转码后视频在某些设备上无法播放？**  
检查 Profile/Level：`-profile:v baseline -level 3.0` 兼容性最好（WebRTC/视频会议），但不支持 B 帧。

**Q：H.265 文件播放时 CPU 占用很高？**  
原因是设备没有 H.265 硬件解码器。检查方法：`ffprobe -show_streams file.mp4 | grep codec_name`，如果是 hevc 则需要硬件支持。移动端 iPhone 5S+、Android 5.0+ 支持 H.265 硬解，PC 端 Intel 6代+。

**Q：AV1 文件为什么这么小，但转码速度极慢？**  
AV1 的编码器（libaom-av1）是参考实现，CPU-only 且极慢。生产环境用 `libsvtav1`（更快）或硬件编码器 `av1_nvenc`（需 RTX 4000+）。

**Q：直播推流时要设置 `-g` 关键帧间隔吗？**  
必须设置，且需要用 `-g` + `-keyint_min` 双重锁定。HLS 要求所有 TS 切片从关键帧开始，如果关键帧间隔不固定，切片时长会抖动，导致播放卡顿。

## 本篇小结

1. **I/P/B 帧**：I 帧是关键帧（自解码），P 帧参考前帧，B 帧双向参考；只有 I 帧能随机 Seek
2. **GOP 设计**：直播用 1-2 秒小 GOP（快速追帧），点播用 4-6 秒大 GOP（压缩率高）
3. **CRF vs ABR**：CRF 质量恒定适合离线转码，ABR 码率恒定适合直播推流
4. **Profile/Level**：Baseline 兼容性最好但无 B 帧；High Profile + Level 4.0 是 1080p 的标准选择
5. **编解码器演进**：H.264（最广泛）→ H.265（体积减半）→ AV1（再减 30%，免费许可证），新场景优先 AV1
6. **硬件编码**：速度快但质量略逊，适合实时推流；软件编码质量更好，适合离线转码

## 术语表

| 术语 | 英文 | 说明 |
|------|------|------|
| H.264/AVC | Advanced Video Coding | 目前最广泛部署的视频编码标准，兼容性最佳 |
| H.265/HEVC | High Efficiency Video Coding | 相同质量下比 H.264 节省约 50% 码率，计算开销更高 |
| AV1 | AOMedia Video 1 | 开源免专利编码标准，压缩率优于 H.265，Chrome/Firefox 已支持 |
| I 帧 | Intra Frame | 关键帧，完整图像数据，无需参考其他帧即可独立解码 |
| P 帧 | Predicted Frame | 预测帧，仅存储与前一帧的差异信息，依赖前向参考帧 |
| B 帧 | Bidirectional Frame | 双向预测帧，参考前后帧编码，压缩率最高但增加解码延迟 |
| GOP | Group of Pictures | 从一个 I 帧到下一个 I 帧的帧组，决定随机访问粒度和延迟 |
| 码率 | Bitrate | 单位时间内的编码数据量（kbps/Mbps），直接影响画质和带宽消耗 |
| CRF | Constant Rate Factor | 恒定质量编码模式，x264 推荐值 18-28，数值越小质量越高 |
| 量化 | Quantization | 将频域变换系数按步长取整，是有损压缩画质损失的核心来源 |
