## 使用说明

将下方提示词发给 AI，让它按阶段逐篇生成学习文档。每生成完一篇回复"继续"即可生成下一篇。

**前置系列（硬性）**：《从零构建 Agent》（`tmp/agent-building-tutorial-v2/`，21 篇，已完结）。
本系列是它的**第二季**：v2 教「从零手写理解原理」（单 agent 主线），本系列教「站上真实
harness 构建生产级多 agent 系统」。读者必须已完成 v2 或具备等价手写经验——本系列
**不再解释 agent loop / 工具注册 / 记忆 / MCP / 评测**这些原理，一律链接回 v2 对应篇。

**结构**：共 18 篇，按学习曲线分成 **6 个 Part**。每个 Part 以一个**里程碑**（H1-H6）收口。

**学习主线**：先把 v2 的后台管理助手**迁移**到主线 harness 上（用 v2 的评测集验收等价），
再依次升级：多模型路由 → 多 agent 协同团队 → skills 与插件生态 → 生产化治理 →
平台化组装与毕业交接。

**本提示词的产出**：一套教学型学习文档。**代码完整列于文章内，但不代建、不代跑**——
读者在自己的工作区跟着文章逐步实现（见「工作方式锁定」）。

**工作方式锁定（本系列与 v2 的最大差异，用户硬约束）**：
- AI **只写文档**。代码（完整文件 + 依赖安装命令 + 运行命令 + 预期输出）全部写在文章里。
- AI **不安装任何依赖、不在磁盘组装代码目录、不代替读者跑验证**；允许做的仅有
  纯标准库的语法级自测（py_compile 级），且产物标注 `<未实测，以官方文档为准>`。
- 读者照文档自己实现并验证；实测回执（成功/失败 + 原因）反馈后记入 `progress.md`，
  后续篇引用回执时注明「读者实测」。
- 读者搭建的目标目录为 `harness_agent/`（与 v2 的 `agent/` 平级），**复用 v2 的
  `mock_backend/` 与场景设定**（张三/李四/角色分配，JWT 后台）——不重贴 v2 代码，链接引用。

## 核心原则

1. **先概念后代码**：每个新机制先一句话大白话 + ASCII 图，再给准确定义和官方出处。
2. **代码完整列于文中，读者实现**：完整文件 + 依赖安装命令 + 运行命令 + 预期输出
   全部写进文章；AI 不安装、不代建目录、不代跑。未经实测的代码必须标注
   `<未实测，以官方文档为准>`，预期输出标注"桌面推演"。读者实测回执记入
   progress.md，后续篇引用时注明。
3. **对比优先**：harness 之间、手写 vs harness、路由策略、通信三路线、拓扑选择、
   skills vs 工具 vs subagent——凡有多方案处给场景化对比表 + "什么时候不选它"。
4. **v2 对位是本系列的灵魂**：每引入一个 harness 机制，先给"v2 我们怎么手写的 →
   harness 对应物是什么 → 差异与代价"对照表，并链接 v2 对应篇。迁移系列的存在
   意义就是这张表——它让读者在 harness 的抽象之下始终看得见原理。
5. **设计要有"为什么"**：多模型、多 agent、skills、插件都必须从"它解决什么问题 /
   不上会怎样 / 过早上会怎样"讲起；复杂度守恒警告贯穿多 agent 与平台化全程。
6. **工程化是分水岭**：可观测、评测、治理在多 agent 环境的每件给可落地的极简做法
   + 生产级工具指针，不许只讲理念。
7. **国内可落地**：主线模型 DeepSeek，多模型矩阵给通义/智谱（OpenAI 兼容），
   私有化给 Ollama/vLLM，安装给国内源。
8. **引用权威**：主线 harness 官方文档、MCP 规范、Claude Code/OpenClaw 的机制文档、
   Anthropic/OpenAI/DeepSeek 官方指南；标注版本号与核验日期。
9. **不堆术语**：新概念先讲"为什么需要它"，再讲它是什么。
10. **Part 内收口**：里程碑（**加粗标注**）落在 Part 内最自然的一篇；Part 最后一篇
    复验里程碑吸收本 Part 增量后仍成立，并给"下一 Part 会暴露什么问题"一句预告。

## 系列结构（共 18 篇 · 6 个 Part，每篇标注覆盖分支与里程碑）

### Part 1 从手写到 harness：选型与迁移（第 1-3 篇）

**目标**：回答"为什么要上 harness"，锁定主线，把 v2 助手原样搬上去并用 v2 评测集验收。
**里程碑 H1**：harness 版助手跑通 v2 evalset 十条用例全绿（行为等价）。

#### 第 1 篇：Harness 全景 — 我们手写的 400 行 vs 生产运行时【H1】
- v2 复盘：手写版攒了哪些零件（loop/注册件/guard/audit/记忆/规划/MCP/subagent/评测/
  trace/治理壳），它们在 v2 里分别几行、解决什么
- harness 的承诺：这些零件运行时原生提供，你写的是"策略与业务"；六件套逐件对位
  （loop=调度、工具=注册表、上下文=管理器、权限=体系、生命周期=检查点、可观测=事件流）
- 2026 版图怎么读：harness 产品（DeepSeek Harness / OpenClaw / Pi / OpenHarness）vs
  编排框架（LangGraph / CrewAI / ADK / MAF / smolagents / deepagents）——两类东西
  解决的问题不同，别混选
- 选型打分卡直接用 v2 第 5 篇决策篇的八件套 + 四能力轴（多模型 / 多 agent /
  多 skill / 多模式），正文链接回 v2 第 5 篇而不重写
- 上 harness 的触发条件（复杂度守恒的 harness 版）：什么时候手写仍是正解
- 动手实践：无代码——给 v2 的 agent/ 目录做一次"运行时缺口自查表"，标出哪些零件
  你愿意交给运行时、哪些必须自己握着（这个决定贯穿全系列）

#### 第 2 篇：主线核验与上手【H2】⭐ 全系列关口
- 按提示词决策规则执行：在线核验 DeepSeek Harness 当前版本/稳定状态/能力清单

### Part 3 多 agent 协同（第 6-9 篇）

**目标**：从 v2 的一只只读 subagent 到真正的 agent 团队——会分工、会通信、会并行、
权限分级，并且知道什么时候不该拆。
**里程碑 H3**：后台多 agent 团队跑通（并行查询 + 写权限独占 + agent 间直接协同），
带量化对比与多 agent 评测。

#### 第 6 篇：从单 agent 到 agent 团队 — 拓扑与分工【A1】
- v2 现状复盘：第 17 篇的层级结构（主 agent + 只读 subagent）解决了什么、没解决什么
  （subagent 之间不能协同、写权限没有多 agent 分级）
- 拓扑菜单：orchestrator-worker（主流）/ pipeline / 对等协作 / 动态组队——
  各自适合的后台场景；复杂度守恒的 harness 版警告（框架让拆分变容易，让判断变稀缺）
- 分工原则：按职责拆（读/写/审计）而不是按步骤拆；写权限独占原则（只有一个
  agent 持有写工具 + 确认闸门）
- 拓扑选择的决策树（结合 v2 第 17 篇五模式选型表的升级版）
- 动手实践：设计后台助手的团队拓扑（不写代码）：画拓扑图、写每个 agent 的
  职责/工具集/权限级别/通信对象四行卡

#### 第 7 篇：agent 间通信与共享状态【A2】
- 三条路线的 harness 实现：共享上下文（v2 一直在用）/ handoff（控制权转移）/
  消息传递（agent 间直接协同——v2 第 17 篇预告的消息路线在此落地）
- 共享状态的设计：什么放共享区（任务清单/事实表）、什么留在私有上下文（过程）；
  状态的检查点与恢复（多 agent 版 checkpoint）
- 消息格式：请求/结果/错误三类的最小协议；背压问题（v2 第 21 篇练习 4 的兑现：
  生产者快过消费者怎么办）
- v2 对位：v2 的嵌套调用（agent 当工具）vs handoff 的本质差异（同步等待 vs
  控制权转移）
- 动手实践：两个 agent 的消息传递最小实现（代码在文中，读者实现），验证
  请求-结果-错误三条路径

#### 第 8 篇：多 agent 协同实战 — 后台助手团队（里程碑 H3）【A3】
- 团队落地：orchestrator + 并行查询组（多个只读 agent 分头查）+ 写入 agent
  （独占 assign_role + 确认闸门）+ 审计观察者（只订阅事件流）
- 并行的实现与代价：并行查询的收益边界（v2 第 17 篇成本账的多 agent 版）；
  汇总损耗（结果合并时的信息丢失）
- 权限分级的物理化：每个 agent 的工具白名单在 harness 里怎么声明；越权用例
  （v2 第 20 篇 governance 的多 agent 版：查询 agent 试图写 → 被拓扑层拦下）
- **里程碑 H3 动手实践**：完整团队跑通"查全部用户并各自核对角色，然后把张三
  提升为管理员"（代码在文中，读者实现），量化对比单 agent 版（v2 第 17 篇
  demo 的对照数据），验证越权用例被拦

#### 第 9 篇：多 agent 的调试与评测【A4】
- 多 agent trace：谁调了谁（调用关系图）、每个 agent 的上下文曲线、消息队列
  深度——v2 trace 三问（想什么/调了什么/结果如何）的多 agent 扩展
- 失败归因：错误发生在哪个 agent（拓扑定位）、哪条消息（协议定位）、哪次调用
  （工具定位）——三层归因法
- 评测集的多 agent 断言：v2 evalset 的扩展——agent 参与断言（哪些 agent 被激活）、
  消息序列断言（handoff/消息的顺序）、聚合终局断言
- 回声与死锁：多 agent 特有的失败模式（互相派活成环、等待死锁）——检测思路
- 动手实践：给第 8 篇的团队加多 agent trace 与两条新评测用例（读者实现），

## 写作规范

1. **按知识点切篇、完整性优先（最高优先）**：篇幅以知识点为单位，不设每篇字数线；
   复杂知识点拆多篇，紧凑的合一篇。唯一红线：不得为凑篇幅裁剪知识点，也不得
   用废话凑数。交稿前自查：本篇清单里每个问题都有实质内容吗？
2. **脚手架从简（装饰性内容总占比 ≤10%）**：篇头"本篇要回答的问题"清单（3-5 条），
   正文按问题逐个讲透，篇尾至多 3 行结论。
3. **动手实践按需添加**：判断标准 ="不亲手做就学不会 / 做了能验证某个设计决策"；
   纯概念篇给不配代码的动脑练习。凡加的动手实践必须代码完整（文件路径/完整
   import/依赖安装/运行命令/预期输出），**由读者实现与验证**——AI 不安装、不
   代建、不代跑；未实测代码标 `<未实测，以官方文档为准>`，预期输出标"桌面推演"；
   读者回执记入 progress.md 后续引用时注明。
4. **语言**：中文。术语首次出现标注英文原文，大小写与官方一致
   （harness / skill / subagent / handoff / MCP / orchestrator）。
5. **代码组织**：读者目标目录 `harness_agent/`（与 v2 的 agent/ 平级，共享
   mock_backend/）；v2 已有实现一律链接引用（`../agent-building-tutorial-v2/`
   相对路径或按实际目录调整），不重贴。
6. **准确性是硬要求（优先于文采）**：版本号、API 签名、star 数、协议行为——每个
   具体论断给出出处；**主线 harness 的 API 事实以生成时官方 docs 为准**（提示词
   里的快照仅是 2026-10-19 记录）；拿不准的一律显式写 `<以官方 docs 为准>`，
