## 1. 为什么需要硬件加速

### 1.1 软件编码的 CPU 瓶颈

当你用 `libx265 -preset medium` 转码一个 1080p H.265 视频时，CPU 会发生什么？

```
┌─────────────────────────────────────────────────────────────┐
│                    软件编码 CPU 开销                          │
│                                                             │
│  1080p H.264 软编（libx264 medium）≈ 1-2 核，约 120fps     │
│  1080p H.265 软编（libx265 medium）≈ 4-8 核，约 25fps      │
│  4K H.265 软编（libx265 medium）  ≈ 全部核心，约 5fps      │
│                                                             │
│  结论：H.265 软编是 H.264 的 4-6 倍 CPU 开销               │
│  多路并发时，CPU 资源迅速耗尽                                │
└─────────────────────────────────────────────────────────────┘
```

**实际测试（Intel i7-10700K，8 核 16 线程）**：

```bash
# 软件编码 H.265
ffmpeg -i input_1080p.mp4 -c:v libx265 -crf 28 -preset medium output.mp4
# 速度：约 25fps，CPU 占用 90%，耗时 2 分钟（处理 1 分钟视频）

# 硬件编码 H.265（NVENC RTX 3060）
ffmpeg -hwaccel cuda -i input_1080p.mp4 -c:v hevc_nvenc -cq 28 output.mp4
# 速度：约 200fps，GPU 占用 20%，CPU 占用 10%，耗时 15 秒
```

**结论**：NVENC 比软编快 **8 倍**，且释放 CPU 给其他业务使用。

---

### 1.2 多路并发场景

**监控录像系统**：16 路摄像头同时转码
```
软件编码：16 × 4 核 = 64 核（不可行，服务器最多 64 核）
硬件编码：1 张 RTX 4000（专业卡）可同时处理 100+ 路
```

**直播 CDN 分发**：1080p → 720p/480p/360p 三档转码
```
软件编码：3 × 4 核 = 12 核/路，10 路直播需要 120 核
硬件编码：1 张 GPU 处理 20-30 路，成本降低 90%
```

---

### 1.3 硬件加速带来的价值

| 维度 | 软件编码 | 硬件编码 |
|------|---------|---------|
| **速度** | 基准 1x | 5-15x |
| **CPU 占用** | 90-100% | 5-15% |
| **GPU 占用** | 0% | 10-30% |
| **电费成本** | 高（CPU 满载功耗大） | 低（GPU 编码功耗低） |
| **并发能力** | 受 CPU 核心数限制 | 单卡支持 10-100 路 |
| **质量** | 最优（更多编码选项） | 略低（约 95% 软编质量） |

**适用场景**：
- ✅ 多路并发转码（监控、直播 CDN）
- ✅ 实时推流（降低延迟）
- ✅ 4K/8K 内容处理（软编太慢）
- ❌ 极限质量归档（软编 veryslow 质量更好）
- ❌ 批量离线处理（如果 CPU 空闲，软编更灵活）

## 2. 硬件加速架构解析

### 2.1 三种加速模式

```
模式 1：仅硬件解码
┌────────┐   ┌──────────┐   ┌────────┐   ┌─────────┐   ┌──────┐
│ Demux  │──▶│ HW Decode│──▶│ Filter │──▶│SW Encode│──▶│ Mux  │
└────────┘   └──────────┘   └────────┘   └─────────┘   └──────┘
  快           GPU            CPU慢         CPU超慢       快
  
适用：多路解码预览、缩略图生成（不重编码）

模式 2：仅硬件编码
┌────────┐   ┌──────────┐   ┌────────┐   ┌──────────┐   ┌──────┐
│ Demux  │──▶│ SW Decode│──▶│ Filter │──▶│ HW Encode│──▶│ Mux  │
└────────┘   └──────────┘   └────────┘   └──────────┘   └──────┘
  快           CPU慢          CPU慢         GPU快          快

适用：输入已是原始格式、或需要复杂滤镜处理

模式 3：全程硬件加速（Zero-Copy Pipeline）
┌────────┐   ┌──────────┐   ┌────────────┐   ┌──────────┐   ┌──────┐
│ Demux  │──▶│ HW Decode│──▶│ HW Filter  │──▶│ HW Encode│──▶│ Mux  │
└────────┘   └──────────┘   └────────────┘   └──────────┘   └──────┘
  快           GPU            GPU             GPU            快

数据全程在 GPU 显存，避免 CPU-GPU 内存拷贝（最快）
```

---

### 2.2 内存拷贝开销

**为什么要避免 CPU-GPU 传输？**

```
典型混合流水线（解码 GPU → 滤镜 CPU → 编码 GPU）：
┌──────────┐   拷贝1   ┌──────┐   拷贝2   ┌──────────┐
│ GPU 解码  │ ──────▶ │ CPU  │ ──────▶ │ GPU 编码  │
│  (显存)   │   慢!!   │(内存)│   慢!!   │  (显存)   │
└──────────┘          └──────┘          └──────────┘

1080p 一帧 YUV420 = 1920×1080×1.5 = 3MB
60fps 视频 = 180MB/s 传输带宽
PCIe 3.0 x16 理论 16GB/s，但实际拷贝开销 ~2GB/s
```

**零拷贝流水线（全程 GPU）**：
```
┌──────────┐          ┌────────────┐          ┌──────────┐
│ GPU 解码  │ ──────▶ │ GPU 滤镜   │ ──────▶ │ GPU 编码  │
│  (显存)   │  无拷贝  │  (显存)    │  无拷贝  │  (显存)   │
└──────────┘          └────────────┘          └──────────┘

数据全程在 GPU 显存，速度提升 30-50%
```

---

### 2.3 FFmpeg 硬件加速参数结构

```bash
ffmpeg \
  -hwaccel cuda \                      # 启用硬件解码（指定加速类型）
  -hwaccel_output_format cuda \        # 解码输出格式（保持在 GPU）
  -i input.mp4 \                       # 输入文件
  -vf scale_cuda=1280:720 \            # 硬件滤镜（GPU 缩放）
  -c:v h264_nvenc \                    # 硬件编码器
  -cq 23 \                             # 质量参数（类似 CRF）
  output.mp4
```

**关键参数解析**：
- `-hwaccel`：解码加速类型（`cuda`/`qsv`/`videotoolbox`/`vaapi`）
- `-hwaccel_output_format`：解码后数据格式（`cuda`/`qsv`/`videotoolbox_vld`/`vaapi`）
- `-hwaccel_device`：选择 GPU 设备（多卡时用，如 `-hwaccel_device 1`）
- 硬件滤镜：`scale_cuda`/`scale_qsv`/`scale_vt`/`scale_vaapi`
- 硬件编码器：`h264_nvenc`/`h264_qsv`/`h264_videotoolbox`/`h264_vaapi`

## 3. NVIDIA NVENC/NVDEC

### 3.1 硬件支持与代次

| GPU 系列 | 架构 | H.264 | H.265 | AV1 | 并发限制 |
|---------|------|-------|-------|-----|---------|
| GTX 10 系（1060+） | Pascal | ✅ | ✅ | ❌ | 消费卡 3 路 |
| GTX 16 系/RTX 20 系 | Turing | ✅ | ✅ | ❌ | 消费卡 3 路 |
| RTX 30 系 | Ampere | ✅ | ✅ | ❌ | 消费卡 3 路 |
| RTX 40 系 | Ada Lovelace | ✅ | ✅ | ✅ | 消费卡 3 路 |
| A/T 系列（专业卡） | 各代 | ✅ | ✅ | 部分 | **无限制** |

**并发限制说明**：
- 消费级显卡（GeForce）：最多 3 路 NVENC 会话
- 专业卡（Tesla/A 系列）：无限制
- 破解方法存在但不推荐生产使用

---

### 3.2 NVENC 编码命令

**H.264 硬件编码**：
```bash
# 基础用法
ffmpeg -i input.mp4 -c:v h264_nvenc -cq 23 output.mp4

# 完整参数（推荐生产配置）
ffmpeg -i input.mp4 \
  -c:v h264_nvenc \
  -preset p4 \           # p1-p7，p1 最快，p7 最慢质量最好
  -tune hq \             # 质量优先（hq/ll/ull/lossless）
  -cq 23 \               # 恒定质量（类似 CRF，0-51）
  -rc vbr \              # 码率控制：vbr/cbr/constqp
  -b:v 0 \               # VBR 模式时不设上限
  -profile:v high \      # H.264 Profile
  -pix_fmt yuv420p \     # 兼容性格式
  output.mp4
```

**H.265 硬件编码**：
```bash
ffmpeg -i input.mp4 \
  -c:v hevc_nvenc \
  -preset p4 \
  -tune hq \
  -cq 28 \               # H.265 CRF 参考值 28（等效 H.264 CRF 23）
  -tag:v hvc1 \          # 兼容 Safari/QuickTime（hvc1 vs hev1）
  output.mp4
```

**AV1 硬件编码（RTX 40+）**：
```bash
ffmpeg -i input.mp4 \
  -c:v av1_nvenc \
  -preset p4 \
  -cq 35 \               # AV1 推荐 CRF 35（等效 H.264 CRF 23）
  output.mp4
```

**NVENC 参数对照表**：

| 参数 | NVENC 写法 | libx264 对应 |
|------|-----------|-------------|
| 恒定质量 | `-cq 23` | `-crf 23` |
| 速度预设 | `-preset p1-p7` | `-preset ultrafast-veryslow` |
| 直播模式 | `-tune ll` | `-tune zerolatency` |
| CBR 直播 | `-rc cbr -b:v 2M` | `-b:v 2M -maxrate 2M -bufsize 2M` |

---

### 3.3 全程 GPU 流水线（零拷贝）

```bash
# NVIDIA 全程 GPU：解码→缩放→编码（无 CPU-GPU 拷贝）
ffmpeg \
  -hwaccel cuda \
  -hwaccel_output_format cuda \
  -i input_4k.mp4 \
  -vf "scale_cuda=1920:1080" \       # GPU 上缩放
  -c:v h264_nvenc -cq 23 \
  -c:a copy \
  output_1080p.mp4

# 多输出同时转码（一次解码，多次编码）
ffmpeg \
  -hwaccel cuda -hwaccel_output_format cuda \
  -i input.mp4 \
  -vf "split=3[v1][v2][v3]" \
  -map "[v1]" -c:v h264_nvenc -cq 23 -s 1920x1080 output_1080p.mp4 \
  -map "[v2]" -c:v h264_nvenc -cq 25 -s 1280x720  output_720p.mp4 \
  -map "[v3]" -c:v h264_nvenc -cq 28 -s 854x480   output_480p.mp4
```

---

### 3.4 NVDEC 硬件解码

```bash
# 仅硬件解码（解码后在 CPU 处理）
ffmpeg \
  -hwaccel cuda \
  -i input.mp4 \
  -vf "scale=1280:720" \             # CPU 滤镜（数据已从 GPU 拷回）

# 查询 GPU 支持的解码格式
ffmpeg -hwaccels
```

**支持硬件解码的格式（NVDEC）**：
H.264、H.265/HEVC、VP8、VP9、AV1（30 系+）、MPEG-2、MPEG-4、VC-1、MJPEG

## 4. Intel QSV

### 4.1 QSV 概述

Intel Quick Sync Video（QSV）是 Intel CPU 集成显卡（iGPU）和独立显卡（Arc）提供的硬件编解码能力。

**优势**：服务器 CPU（如 Xeon）自带 iGPU，无需购买独立显卡即可硬件加速。

**支持情况**：
| 平台 | 支持的编解码 |
|------|------------|
| Intel 6-12 代 CPU iGPU | H.264、H.265 |
| Intel 12 代+ CPU iGPU | H.264、H.265、AV1 解码 |
| Intel Arc 独显 | H.264、H.265、AV1 编解码 |
| Xeon Scalable（2/3 代） | H.264、H.265（服务器首选） |

---

### 4.2 Linux 环境准备

```bash
# 安装 Intel Media Driver（Ubuntu 22.04+）
sudo apt install intel-media-va-driver-non-free

# 验证 QSV 设备可用
ls /dev/dri/renderD128   # Intel GPU 渲染节点
vainfo                   # 查看 VAAPI 支持的格式

# 确认 FFmpeg 支持 QSV
ffmpeg -hwaccels | grep qsv
```

---

### 4.3 QSV 编码命令

```bash
# H.264 QSV 编码
ffmpeg -i input.mp4 \
  -c:v h264_qsv \
  -global_quality 23 \     # 恒定质量（类似 CRF）
  -preset 4 \              # 1-7，1 最快，7 最慢质量好
  output.mp4

# H.265 QSV 编码
ffmpeg -i input.mp4 \
  -c:v hevc_qsv \
  -global_quality 28 \
  -preset 4 \
  output.mp4

# AV1 QSV 编码（Intel Arc / FFmpeg 8.0）
ffmpeg -i input.mp4 \
  -c:v av1_qsv \
  -global_quality 35 \
  -preset 4 \
  output.mp4
```

**QSV 全程 GPU 流水线**：
```bash
ffmpeg \
  -hwaccel qsv \
  -hwaccel_output_format qsv \
  -i input.mp4 \
  -vf "scale_qsv=1280:720" \          # QSV GPU 缩放
  -c:v h264_qsv -global_quality 23 \
  output.mp4
```

**QSV 参数对照**：

| 参数 | QSV 写法 | libx264 对应 |
|------|---------|-------------|
| 恒定质量 | `-global_quality 23` | `-crf 23` |
| 速度预设 | `-preset 1-7` | `-preset ultrafast-veryslow` |
| 低延迟 | `-low_power 1` | `-tune zerolatency` |

## 5. Apple VideoToolbox

### 5.1 VideoToolbox 概述

Apple 平台（macOS/iOS）的硬件编解码框架，M 系列芯片的媒体引擎性能极强。

**支持硬件**：
- Intel Mac：第 6 代+ CPU 集成显卡
- M1/M2/M3 Mac：ProRes/ProRes RAW 硬件加速
- iPhone/iPad：A 系列芯片（A8+）

**支持格式**：
H.264、H.265/HEVC、ProRes、ProRes RAW

---

### 5.2 VideoToolbox 编码命令

```bash
# H.264 VideoToolbox 编码
ffmpeg -i input.mp4 \
  -c:v h264_videotoolbox \
  -q:v 65 \                # 质量参数（0-100，值越小质量越高）
  -realtime 0 \            # 非实时模式（提高质量）
  output.mp4

# H.265 VideoToolbox 编码
ffmpeg -i input.mp4 \
  -c:v hevc_videotoolbox \
  -q:v 65 \
  -tag:v hvc1 \            # Safari 兼容（必需）
  output.mp4

# ProRes 422 编码（M 系列硬件加速）
ffmpeg -i input.mp4 \
  -c:v prores_videotoolbox \
  -profile:v 2 \           # 0=Proxy, 1=LT, 2=Standard, 3=HQ
  output.mov
```

**VideoToolbox 质量参数对照**：

| q:v 值 | 等效 libx264 CRF | 适用场景 |
|--------|-----------------|---------|
| 50 | CRF 18 | 近无损 |
| 65 | CRF 23 | 标准质量（推荐） |
| 75 | CRF 28 | 较低质量 |
| 85 | CRF 33 | 低质量 |

**注意**：`-q:v` 是质量参数（0-100），**不是 CRF**！值越小质量越高。

---

### 5.3 VideoToolbox 全程硬件流水线

```bash
# 解码→缩放→编码（全程硬件）
ffmpeg \
  -hwaccel videotoolbox \
  -i input_4k.mp4 \
  -vf "scale_vt=1920:1080" \          # VideoToolbox GPU 缩放
  -c:v h264_videotoolbox -q:v 65 \
  output.mp4

# M 系列芯片 ProRes 转码（极快）
ffmpeg \
  -hwaccel videotoolbox \
  -i input.mp4 \
  -c:v prores_videotoolbox -profile:v 3 \
  output_prores.mov
```

### 5.4 iOS 设备录屏优化

```bash
# iPhone/iPad 录屏 MOV → MP4（保留硬件编码）
ffmpeg -i iphone_recording.mov \
  -c:v copy \              # 不重编码（已是 H.264）
  -movflags +faststart \   # 优化 MP4 头部

# 如需重新编码（降低码率）
ffmpeg -i iphone_recording.mov \
  -c:v h264_videotoolbox -q:v 70 \
  -movflags +faststart \
  output_compressed.mp4
```

## 6. VAAPI（Linux 开源栈）

### 6.1 VAAPI 概述

Video Acceleration API（VAAPI）是 Linux 平台的通用硬件加速接口，Intel/AMD GPU 均支持。

**优势**：
- 纯开源栈（Mesa + Kernel DRM）
- 无需专有驱动（Intel 和部分 AMD GPU）
- 适合 Linux 服务器生产部署

**环境准备**：
```bash
# 安装 VAAPI 运行时（Ubuntu）
sudo apt install libva-dev vainfo i965-va-driver   # Intel 旧代（6-9 代）
sudo apt install intel-media-va-driver             # Intel 新代（10 代+）
sudo apt install mesa-va-drivers                   # AMD（Radeon）

# 验证设备
ls /dev/dri/renderD128
vainfo --display drm --device /dev/dri/renderD128
```

---

### 6.2 VAAPI 编码命令

```bash
# H.264 VAAPI 编码
ffmpeg \
  -vaapi_device /dev/dri/renderD128 \
  -i input.mp4 \
  -vf "format=nv12,hwupload" \         # 上传到 GPU
  -c:v h264_vaapi \
  -qp 23 \                              # 量化参数（类似 CRF）
  output.mp4

# H.265 VAAPI 编码
ffmpeg \
  -vaapi_device /dev/dri/renderD128 \
  -i input.mp4 \
  -vf "format=nv12,hwupload" \
  -c:v hevc_vaapi \
  -qp 28 \
  output.mp4

# AV1 VAAPI（Intel Arc / FFmpeg 8.0）
ffmpeg \
  -vaapi_device /dev/dri/renderD128 \
  -i input.mp4 \
  -vf "format=nv12,hwupload" \
  -c:v av1_vaapi \
  -qp 35 \
  output.mp4
```

**VAAPI 全程 GPU 流水线**：
```bash
ffmpeg \
  -hwaccel vaapi \
  -hwaccel_device /dev/dri/renderD128 \
  -hwaccel_output_format vaapi \
  -i input.mp4 \
  -vf "scale_vaapi=1280:720" \          # GPU 缩放
  -c:v h264_vaapi -qp 23 \
  output.mp4
```

**Docker 中挂载 GPU**：
```bash
# Linux Docker 挂载 DRI 设备
docker run --device /dev/dri/renderD128 \
  -v /input:/input -v /output:/output \
  ffmpeg-image \
  ffmpeg -hwaccel vaapi -vaapi_device /dev/dri/renderD128 \
  -i /input/input.mp4 -c:v h264_vaapi -qp 23 /output/output.mp4
```

## 7. AMD AMF

### 7.1 AMF 概述

AMD Advanced Media Framework（AMF）是 AMD GPU 的硬件编解码 API，适用于 RX 5000 系列及以上。

**Linux 环境（ROCm + VAAPI）**：AMD 的 Linux 硬件加速通过 VAAPI 接口，使用 `mesa-va-drivers` 或 `amdgpu-pro`。

**Windows 环境**：通过 AMF API 直接调用（需安装 AMD Adrenalin 驱动）。

---

### 7.2 AMF 编码命令

```bash
# H.264 AMF 编码（Windows/Linux）
```

## 8. Vulkan（FFmpeg 8.0 新增）

### 8.1 Vulkan 加速概述

FFmpeg 8.0 引入了基于 Vulkan 的通用 GPU 计算框架，主要用于：
- **复杂滤镜加速**（色彩转换、降噪、超分辨率）

- **ProRes RAW 解码**

**注意**：Vulkan 目前不是 H.264/H.265 的编解码通道，而是滤镜计算加速层。

## 9. 硬件滤镜：全程 GPU 流水线

### 9.1 为什么需要硬件滤镜

**传统混合流水线的瓶颈**：
```
┌─────────┐   拷贝1    ┌─────────┐   拷贝2    ┌─────────┐
│ GPU解码 │ ────────▶ │ CPU滤镜 │ ────────▶ │ GPU编码 │
└─────────┘   慢!!     └─────────┘   慢!!     └─────────┘

1080p 视频每秒 180MB 双向拷贝（解码→CPU + CPU→编码）
4K 视频每秒 720MB 双向拷贝
```

**全程 GPU 流水线**：
```
┌─────────┐          ┌──────────┐          ┌─────────┐
│ GPU解码 │ ───────▶ │ GPU滤镜  │ ───────▶ │ GPU编码 │
└─────────┘  无拷贝   └──────────┘  无拷贝   └─────────┘

数据全程在 GPU 显存，避免 PCIe 带宽瓶颈
4K 视频性能提升 50-80%
```

---

### 9.2 硬件滤镜对照表

| 平台 | 缩放滤镜 | 格式转换 | 叠加滤镜 | 反交错 |
|------|---------|---------|---------|--------|
| NVIDIA CUDA | `scale_cuda` | `hwupload_cuda` | `overlay_cuda` | ❌ |
| Intel QSV | `scale_qsv` | `hwupload_qsv` | `overlay_qsv` | `deinterlace_qsv` |
| Apple VT | `scale_vt` | `hwupload` | ❌ | ❌ |
| VAAPI | `scale_vaapi` | `hwupload` | `overlay_vaapi` | `deinterlace_vaapi` |

---

### 9.3 NVIDIA CUDA 全程 GPU 实例


### 10.1 平台选型决策树


### 10.2 质量 vs 速度权衡

**相同视觉质量下，编码速度对比（1080p H.264）**：

```
软件编码（libx264 medium）：  25fps   ████░░░░░░░░░░░░ 基准
硬件编码（h264_nvenc p4）：   180fps  ████████████████ 7.2x
硬件编码（h264_nvenc p7）：   80fps   █████████░░░░░░░ 3.2x
硬件编码（h264_qsv）：        150fps  ███████████████░ 6.0x
硬件编码（VideoToolbox）：    200fps  ████████████████ 8.0x
```

**相同码率下，质量对比（VMAF 评分，越高越好）**：
```
libx264 medium       ： VMAF 87   ████████████████████ 基准（最高）
h264_nvenc p7（slow）： VMAF 84   ███████████████████░ -3%
```

**结论**：
- 硬件编码质量约为软编的 **93-96%**（VMAF）
- 速度快 **3-8 倍**
- **生产建议**：并发转码用硬件，最终归档用软编 veryslow

### 10.3 坑点与排查

**常见错误及解决**：

| 错误信息 | 原因 | 解决方法 |
|---------|------|---------|
| `No CUDA capable device` | 驱动未安装或版本太旧 | `nvidia-smi` 确认驱动，重装 CUDA |
| `Device or resource busy` | GPU 并发路数已满 | 升级专业卡或降低并发数 |

## 11. Go 工程化集成

### 11.1 检测可用硬件加速

```go
package main

import (
	"os/exec"
	"runtime"
	"strings"
)

type HWAccelType string

const (
	HWAccelNVENC      HWAccelType = "nvenc"
	HWAccelQSV        HWAccelType = "qsv"
	HWAccelVideoToolbox HWAccelType = "videotoolbox"
	HWAccelVAAPI      HWAccelType = "vaapi"
	HWAccelNone       HWAccelType = "none"
)

// DetectHardwareAccel 检测当前系统可用的硬件加速
func DetectHardwareAccel() HWAccelType {
	// 检查 FFmpeg 支持的硬件加速
	cmd := exec.Command("ffmpeg", "-hwaccels")
	output, err := cmd.CombinedOutput()
	if err != nil {
		return HWAccelNone
	}

	hwaccels := string(output)

	// 优先级：NVENC > VideoToolbox > QSV > VAAPI
	if strings.Contains(hwaccels, "cuda") && isNVIDIAAvailable() {
		return HWAccelNVENC
	}

	if runtime.GOOS == "darwin" && strings.Contains(hwaccels, "videotoolbox") {
		return HWAccelVideoToolbox
	}

	if strings.Contains(hwaccels, "qsv") && isQSVAvailable() {
		return HWAccelQSV
	}

	if runtime.GOOS == "linux" && strings.Contains(hwaccels, "vaapi") && isVAAPIAvailable() {
		return HWAccelVAAPI
	}

	return HWAccelNone
}

// isNVIDIAAvailable 检查 NVIDIA GPU 是否可用
func isNVIDIAAvailable() bool {
	cmd := exec.Command("nvidia-smi")
	return cmd.Run() == nil
}

// isQSVAvailable 检查 Intel QSV 是否可用
func isQSVAvailable() bool {
	cmd := exec.Command("vainfo")
	output, err := cmd.CombinedOutput()
	if err != nil {
		return false
	}
	return strings.Contains(string(output), "iHD") || strings.Contains(string(output), "i965")
}

// isVAAPIAvailable 检查 VAAPI 设备是否存在
func isVAAPIAvailable() bool {
	_, err := exec.LookPath("vainfo")
	return err == nil
}

func main() {
	hwaccel := DetectHardwareAccel()
	println("检测到的硬件加速:", string(hwaccel))
}
```

### 11.2 动态构建转码命令

```go
package transcode

import (
	"fmt"
	"os/exec"
)

type TranscodeOptions struct {
	InputPath   string
	OutputPath  string
	Width       int
	Height      int
	CRF         int
	HWAccel     HWAccelType
}

// BuildFFmpegCommand 根据硬件加速类型构建命令
func BuildFFmpegCommand(opts TranscodeOptions) *exec.Cmd {
	args := []string{"-y"}

	// 添加硬件解码参数
	switch opts.HWAccel {
	case HWAccelNVENC:
		args = append(args, "-hwaccel", "cuda", "-hwaccel_output_format", "cuda")
	case HWAccelQSV:
		args = append(args, "-hwaccel", "qsv", "-hwaccel_output_format", "qsv")
	case HWAccelVideoToolbox:
		args = append(args, "-hwaccel", "videotoolbox")
	case HWAccelVAAPI:
		args = append(args, "-hwaccel", "vaapi", "-hwaccel_device", "/dev/dri/renderD128",
			"-hwaccel_output_format", "vaapi")
	}

	// 输入文件
	args = append(args, "-i", opts.InputPath)

	// 硬件滤镜（缩放）
	if opts.Width > 0 && opts.Height > 0 {
		var scaleFilter string
		switch opts.HWAccel {
		case HWAccelNVENC:
			scaleFilter = fmt.Sprintf("scale_cuda=%d:%d", opts.Width, opts.Height)
		case HWAccelQSV:
			scaleFilter = fmt.Sprintf("scale_qsv=%d:%d", opts.Width, opts.Height)
		case HWAccelVideoToolbox:
			scaleFilter = fmt.Sprintf("scale_vt=%d:%d", opts.Width, opts.Height)
		case HWAccelVAAPI:
			scaleFilter = fmt.Sprintf("scale_vaapi=%d:%d", opts.Width, opts.Height)
		default:
			scaleFilter = fmt.Sprintf("scale=%d:%d", opts.Width, opts.Height)
		}
		args = append(args, "-vf", scaleFilter)
	}

	// 硬件编码器
	switch opts.HWAccel {
	case HWAccelNVENC:
		args = append(args, "-c:v", "h264_nvenc", "-cq", fmt.Sprintf("%d", opts.CRF))
	case HWAccelQSV:
		args = append(args, "-c:v", "h264_qsv", "-global_quality", fmt.Sprintf("%d", opts.CRF))
	case HWAccelVideoToolbox:
		qv := 50 + (opts.CRF-18)*3  // CRF 18→50, 23→65, 28→75
		args = append(args, "-c:v", "h264_videotoolbox", "-q:v", fmt.Sprintf("%d", qv))
	case HWAccelVAAPI:
		args = append(args, "-c:v", "h264_vaapi", "-qp", fmt.Sprintf("%d", opts.CRF))
	default:
		args = append(args, "-c:v", "libx264", "-crf", fmt.Sprintf("%d", opts.CRF), "-preset", "medium")
	}

	// 音频复制
	args = append(args, "-c:a", "copy")

	// 输出文件
	args = append(args, opts.OutputPath)

	return exec.Command("ffmpeg", args...)
}
```

### 11.3 进度解析与并发控制

```go
package transcode

import (
	"bufio"
	"context"
	"fmt"
	"os/exec"
	"strconv"
	"strings"
)

type TranscodeProgress struct {
	Frame    int
	FPS      float64
	Speed    float64
	Progress float64 // 0-1
}

// TranscodeWithProgress 带进度回调的硬件加速转码
func TranscodeWithProgress(ctx context.Context, opts TranscodeOptions, onProgress func(TranscodeProgress)) error {
	// 先获取总帧数
	totalFrames, err := getVideoFrameCount(opts.InputPath)
	if err != nil {
		totalFrames = 0  // 获取失败时不报告百分比
	}

	cmd := BuildFFmpegCommand(opts)
	// 追加进度输出参数
	cmd.Args = append(cmd.Args[:len(cmd.Args)-1],
		"-progress", "pipe:1",
		"-nostats",
		opts.OutputPath,
	)

	stdout, err := cmd.StdoutPipe()
	if err != nil {
		return fmt.Errorf("获取 stdout 管道失败: %w", err)
	}
	cmd.Stderr = cmd.Stdout

	if err := cmd.Start(); err != nil {
		return fmt.Errorf("启动 FFmpeg 失败: %w", err)
	}

	// 解析进度
	scanner := bufio.NewScanner(stdout)
	prog := TranscodeProgress{}
	for scanner.Scan() {
		line := scanner.Text()
		kv := strings.SplitN(line, "=", 2)
		if len(kv) != 2 {
			continue
		}
		key, val := strings.TrimSpace(kv[0]), strings.TrimSpace(kv[1])
		switch key {
		case "frame":
			prog.Frame, _ = strconv.Atoi(val)
			if totalFrames > 0 {
				prog.Progress = float64(prog.Frame) / float64(totalFrames)
			}
		case "fps":
			prog.FPS, _ = strconv.ParseFloat(val, 64)
		case "speed":
			s := strings.TrimSuffix(val, "x")
			prog.Speed, _ = strconv.ParseFloat(s, 64)
		case "progress":
			if val == "end" {
				prog.Progress = 1.0
			}
			if onProgress != nil {
				onProgress(prog)
			}
		}
	}

	return cmd.Wait()
}

// getVideoFrameCount 获取视频总帧数
func getVideoFrameCount(path string) (int, error) {
	cmd := exec.Command("ffprobe",
		"-v", "error",
		"-select_streams", "v:0",
		"-count_packets",
		"-show_entries", "stream=nb_read_packets",
		"-of", "default=noprint_wrappers=1:nokey=1",
		path,
	)
	output, err := cmd.Output()
	if err != nil {
		return 0, err
	}
	return strconv.Atoi(strings.TrimSpace(string(output)))
}
```

```bash
  -hwaccel cuda \                          # GPU 解码
  -i test_4k.mp4 \
  -vf "scale=1920:1080" \                  # CPU 缩放（有内存拷贝）
  -c:v h264_nvenc -cq 23 \
  output_mixed.mp4

# 方案 B：全程 GPU 流水线（Zero-Copy）
time ffmpeg \
  -hwaccel cuda -hwaccel_output_format cuda \   # GPU 解码，输出保持在 GPU
  -i test_4k.mp4 \
  -vf "scale_cuda=1920:1080" \                   # GPU 缩放（无内存拷贝）
  -c:v h264_nvenc -cq 23 \
  output_zerocopy.mp4

# 比较速度差异（方案 B 应快 30-50%）
echo "对比完成"
```

## 本篇小结

本篇系统讲解了 FFmpeg 硬件加速的原理与实践：

**核心要点**：

1. **硬件加速的价值**：相比软编速度提升 5-15 倍，CPU 占用降低 80%，多路并发成本大幅下降

2. **三种加速模式**：
   - 仅硬件解码（节省解码 CPU）
   - 仅硬件编码（速度快 5-10 倍）
   - 全程 GPU 零拷贝（最快，避免 PCIe 传输瓶颈）

3. **四大平台速查**：

| 平台 | H.264 | H.265 | AV1 | 质量 |
|------|-------|-------|-----|------|
| NVIDIA NVENC | `h264_nvenc -cq 23` | `hevc_nvenc -cq 28` | `av1_nvenc -cq 35`（RTX40+） | 95% |
| Intel QSV | `h264_qsv -global_quality 23` | `hevc_qsv -global_quality 28` | `av1_qsv`（Arc） | 92% |
| Apple VT | `h264_videotoolbox -q:v 65` | `hevc_videotoolbox -q:v 65` | ❌ | 94% |
| VAAPI | `h264_vaapi -qp 23` | `hevc_vaapi -qp 28` | `av1_vaapi`（Intel Arc） | 92% |

4. **生产选型原则**：
   - 高并发转码 → 硬件加速（必须）
   - 单路极限质量 → 软编 veryslow
   - macOS 开发 → VideoToolbox
   - Linux 服务器 → NVENC（NVIDIA）或 QSV（Intel iGPU）

5. **Go 工程化**：自动检测硬件加速，动态构建最优命令，带进度回调
