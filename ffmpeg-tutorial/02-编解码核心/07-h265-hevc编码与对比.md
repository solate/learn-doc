## H.265 技术改进概览

### 为什么需要 H.265？

**带宽压力**：
- 4K 视频：H.264 需要 20-40 Mbps
- H.265：相同质量只需 10-20 Mbps（节省 50%）

**存储压力**：
- 1 小时 4K H.264：~18 GB
- 1 小时 4K H.265：~9 GB

---

### 核心技术改进

```
H.264 → H.265 技术演进

┌─────────────────────────────────────────────────────┐
│ 1. 编码块大小（CTU）                                  │
│    H.264: 16×16 宏块（Macroblock）                   │
│    H.265: 64×64 编码树单元（CTU）                    │
│    → 更大的编码单元，更好的大块区域压缩               │
│                                                     │
│ 2. 帧内预测方向                                       │
│    H.264: 9 种方向                                   │
│    H.265: 35 种方向                                  │
│    → 更精确的预测，减少残差                          │
│                                                     │
│ 3. 运动补偿精度                                       │
│    H.264: 1/4 像素精度                               │
│    H.265: 1/4 像素精度 + 改进的插值滤波器             │
│    → 更准确的运动估计                                │
│                                                     │
│ 4. 变换块大小                                        │
│    H.264: 4×4, 8×8                                  │
│    H.265: 4×4, 8×8, 16×16, 32×32                   │
│    → 适应不同内容复杂度                              │
│                                                     │
│ 5. 并行处理支持                                      │
│    H.265: Tiles, WPP（Wavefront Parallel Processing）│
│    → 多核 CPU 加速编码                               │
└─────────────────────────────────────────────────────┘
```

---

### 代价：计算复杂度

**编码复杂度对比**：
```
H.264:   ██████                    (基准 1x)
H.265:   ████████████████████████  (约 4-10x)
```

**解码复杂度对比**：
```
H.264:   ████                      (基准 1x)
H.265:   ████████                  (约 2-3x)
```

## H.265 vs H.264 对比

### 压缩效率对比

**实验条件**：
- 源视频：1080p30，60 秒
- 测试配置：CRF 模式，medium preset

```bash
# H.264
ffmpeg -i input.mp4 -c:v libx264 -crf 23 -preset medium output_h264.mp4

# H.265（等效质量）
ffmpeg -i input.mp4 -c:v libx265 -crf 28 -preset medium output_h265.mp4
```

**典型结果**：

| 编码 | 文件大小 | 编码时间 | SSIM | VMAF |
|------|---------|---------|------|------|
| H.264 CRF 23 | 50 MB | 30s | 0.95 | 88 |
| H.265 CRF 28 | 25 MB | 180s | 0.95 | 88 |

**结论**：
- H.265 文件大小约为 H.264 的 **50%**
- H.265 编码时间约为 H.264 的 **6 倍**
- 相同主观质量

---

### 完整对比表

| 维度 | H.264 (AVC) | H.265 (HEVC) |
|------|------------|--------------|
| **压缩率** | 基准 | 提升 50%（相同质量文件小一半） |
| **编码速度** | 快 | 慢 4-10 倍 |
| **解码速度** | 快 | 慢 2-3 倍 |
| **编码复杂度** | 低 | 高 |
| **解码复杂度** | 低 | 中 |
| **硬件加速** | 广泛支持 | 新设备支持 |
| **浏览器支持** | 全支持 | Safari 支持，Chrome/Firefox 部分支持 |
| **移动设备** | 全支持 | iOS 11+，Android 5+ |
| **4K 支持** | 可用 | 优势明显 |
| **8K 支持** | 不推荐 | 适合 |
| **专利费** | 有（但广泛授权） | 有（更复杂） |
| **典型 CRF** | 23 | 28 |

## CRF 值差异

### 为什么 H.265 的 CRF 值更高？

**关键原因**：H.265 的压缩效率更高，相同 CRF 值下质量更好

**经验对应关系**：

| 质量描述 | H.264 CRF | H.265 CRF | 文件大小（1080p 1 小时） |
|---------|----------|----------|---------------------|
| 近无损 | 17-18 | 22-23 | H.264: ~8 GB, H.265: ~4 GB |
| 高质量（推荐） | 20-23 | 25-28 | H.264: ~4 GB, H.265: ~2 GB |
| 中等质量 | 24-27 | 29-32 | H.264: ~2 GB, H.265: ~1 GB |
| 较低质量 | 28-33 | 33-38 | H.264: ~1 GB, H.265: ~500 MB |

**常用配置**：
```bash
# H.264 标准质量
ffmpeg -i input.mp4 -c:v libx264 -crf 23 output_h264.mp4

# H.265 等效质量
ffmpeg -i input.mp4 -c:v libx265 -crf 28 output_h265.mp4
```

---

### CRF 实验对比

```bash
# 生成测试文件
ffmpeg -f lavfi -i testsrc=duration=60:size=1920x1080:rate=30 \
       -f lavfi -i sine=frequency=1000:duration=60 \
       -c:v libx264 -crf 20 test_source.mp4

# H.264 对照组
ffmpeg -i test_source.mp4 -c:v libx264 -crf 23 -preset medium h264_crf23.mp4

# H.265 测试组
for crf in 24 26 28 30 32; do
    ffmpeg -y -i test_source.mp4 -c:v libx265 -crf $crf -preset medium h265_crf${crf}.mp4
done

# 对比文件大小
ls -lh h264_crf23.mp4 h265_crf*.mp4
```

**预期结果**：
```
h264_crf23.mp4:  50 MB
h265_crf24.mp4:  30 MB
h265_crf26.mp4:  25 MB
h265_crf28.mp4:  22 MB  ← 与 H.264 CRF 23 视觉等效
h265_crf30.mp4:  18 MB
h265_crf32.mp4:  15 MB
```

## Preset 与编码速度

### libx265 的 Preset

```
ultrafast > superfast > veryfast > faster > fast > medium > slow > slower > veryslow > placebo
```

**注意**：libx265 多了 `placebo` preset（极慢，几乎不提升质量）

---

### 编码速度对比（H.264 vs H.265）

**测试条件**：1080p30，60 秒，Intel i7-10700K

```bash
# H.264 medium
time ffmpeg -i test.mp4 -c:v libx264 -crf 23 -preset medium h264.mp4
# 实际时间：30 秒

# H.265 medium
time ffmpeg -i test.mp4 -c:v libx265 -crf 28 -preset medium h265.mp4
# 实际时间：180 秒（6 倍慢）

# H.265 fast
time ffmpeg -i test.mp4 -c:v libx265 -crf 28 -preset fast h265_fast.mp4
# 实际时间：90 秒（3 倍慢）

# H.265 ultrafast
time ffmpeg -i test.mp4 -c:v libx265 -crf 28 -preset ultrafast h265_ultrafast.mp4
# 实际时间：45 秒（1.5 倍慢）
```

---

### Preset 对比表（H.265）

| Preset | 编码时间（相对） | 文件大小（相对） | 推荐场景 |
|--------|--------------|--------------|---------|
| ultrafast | 1x | 100% | 实时推流、测试 |
| superfast | 1.5x | 85% | 快速转码 |
| veryfast | 2x | 75% | 日常转码 |
| faster | 2.5x | 70% | |
| fast | 3x | 67% | 生产环境推荐 |
| **medium（默认）** | **4x** | **65%** | 平衡点 |
| slow | 7x | 62% | 归档存储 |
| slower | 12x | 60% | |
| veryslow | 20x | 58% | 极限压缩 |
| placebo | 40x | 57% | 不推荐（性价比低） |

**实际建议**：
- **日常使用**：`fast` 或 `medium`（H.265 本身就慢，不要用更慢的 preset）
- **归档存储**：`slow`（veryslow 和 placebo 收益递减）
- **实时场景**：考虑硬件加速（NVENC/QSV），不用 libx265

## Tune 参数

### libx265 的 Tune 选项

```bash
# 查看可用 tune
ffmpeg -h encoder=libx265 | grep -A 10 "tune"
```

**可用值**：
- `psnr`：优化 PSNR 指标
- `ssim`：优化 SSIM 指标
- `grain`：保留胶片噪点
- `fastdecode`：优化解码速度
- `zerolatency`：最低延迟（实时推流）
- `animation`：动画内容优化

---

### 实时推流配置

```bash
# RTMP 推流（H.265）
ffmpeg -re -i input.mp4 -c:v libx265 \
  -crf 28 \
  -preset veryfast \
  -tune zerolatency \
  -x265-params keyint=60:min-keyint=60:scenecut=0 \
  -c:a aac -b:a 128k \
  -f flv rtmp://server/live/stream_key
```

**注意**：
- H.265 推流兼容性差（大部分 CDN 不支持）
- 建议用 H.264 推流

## Profile 与 Level

### H.265 的 Profile

| Profile | 位深 | 色度采样 | 适用场景 |
|---------|------|---------|---------|
| **Main** | 8-bit | 4:2:0 | 标准视频（默认） |
| Main 10 | 10-bit | 4:2:0 | HDR、4K |
| Main 12 | 12-bit | 4:2:0 | 专业后期 |
| Main 4:4:4 | 8-bit | 4:4:4 | 无损压缩 |

---

### Level

| Level | 最大分辨率 | 最大帧率 | 最大码率 | 适用场景 |
|-------|---------|---------|---------|---------|
| 4.0 | 2048×1080 | 30fps | 12 Mbps | 1080p |
| 4.1 | 2048×1080 | 60fps | 20 Mbps | 1080p60 |
| 5.0 | 3840×2160 | 30fps | 25 Mbps | 4K30 |
| 5.1 | 3840×2160 | 60fps | 40 Mbps | 4K60 |
| 6.0 | 7680×4320 | 30fps | 60 Mbps | 8K30 |

---

### Profile/Level 配置

```bash
# 标准 1080p（默认）
ffmpeg -i input.mp4 -c:v libx265 \
  -crf 28 \
  -profile:v main -level 4.1 \
  output.mp4

# 4K HDR（10-bit）
ffmpeg -i input_hdr.mp4 -c:v libx265 \
  -crf 24 \
  -profile:v main10 -level 5.1 \
  -pix_fmt yuv420p10le \
  -x265-params colorprim=bt2020:transfer=smpte2084:colormatrix=bt2020nc \
  output_hdr.mp4
```

## 高级参数（x265-params）

### 通过 x265-params 传递参数

```bash
# 语法
ffmpeg -i input.mp4 -c:v libx265 \
  -x265-params "param1=value1:param2=value2:..." \
  output.mp4
```

---

### 常用高级参数

**1. 关键帧控制**

```bash
# 固定 GOP 大小（HLS 对齐）
ffmpeg -i input.mp4 -c:v libx265 \
  -x265-params "keyint=60:min-keyint=60:scenecut=0" \
  output.mp4
```

**2. 码率控制微调**

```bash
# 2-Pass 编码（精确码率控制）
ffmpeg -i input.mp4 -c:v libx265 -b:v 4M \
  -x265-params pass=1 \
  -an -f null /dev/null

ffmpeg -i input.mp4 -c:v libx265 -b:v 4M \
  -x265-params pass=2 \
  output.mp4
```

**3. 并行处理**

```bash
# 启用 WPP（Wavefront Parallel Processing）
ffmpeg -i input.mp4 -c:v libx265 \
  -x265-params "wpp=1:pools=8" \
  output.mp4
```

**4. 质量优化**

```bash
# 增加分析深度（提高质量，但更慢）
ffmpeg -i input.mp4 -c:v libx265 \
  -x265-params "aq-mode=3:aq-strength=1.0:rd=6" \
  output.mp4
```

---

### 参数详解

| 参数 | 说明 | 默认值 | 推荐值 |
|------|------|-------|-------|
| `keyint` | 最大关键帧间隔 | 250 | 60-120 |
| `min-keyint` | 最小关键帧间隔 | 自动 | 同 keyint |
| `scenecut` | 场景切换检测阈值 | 40 | 0（禁用，HLS 用） |
| `wpp` | 启用波前并行处理 | 1 | 1 |
| `pools` | 线程池数量 | 自动 | CPU 核心数 |
| `aq-mode` | 自适应量化模式 | 2 | 3（最好） |
| `aq-strength` | 自适应量化强度 | 1.0 | 0.8-1.2 |
| `rd` | 率失真优化级别 | 3 | 4-6（更慢但更优） |

## 兼容性考虑

### 浏览器支持

| 浏览器 | H.264 | H.265 |
|--------|-------|-------|
| Chrome | ✅ | ⚠️ 硬件解码（Win/Mac），Android 无支持 |
| Firefox | ✅ | ❌ 不支持 |
| Safari | ✅ | ✅ macOS 10.13+, iOS 11+ |
| Edge | ✅ | ⚠️ 硬件解码（Win 10+） |

**结论**：Web 视频仍以 H.264 为主，H.265 作为备选

---

### 移动设备支持

| 平台 | H.264 | H.265 |
|------|-------|-------|
| iOS | ✅ 全支持 | ✅ iOS 11+（硬件解码） |
| Android | ✅ 全支持 | ⚠️ Android 5+（硬件解码），低端机可能不支持 |

**建议**：
- iOS：可以用 H.265（省流量）
- Android：优先 H.264（兼容性好）

---

### 硬件解码器支持

| 芯片 | H.264 | H.265 |
|------|-------|-------|
| Intel（第 6 代+） | ✅ | ✅ |
| AMD（Polaris+） | ✅ | ✅ |
| NVIDIA（Maxwell+） | ✅ | ✅ |
| Apple M1/M2 | ✅ | ✅ |
| 手机 SoC（2016+） | ✅ | ⚠️ 视具体型号 |

## 实际场景选择

### 决策流程图

```
需要编码视频
    │
    ├─ 目标设备是什么？
    │   ├─ Web 浏览器 → H.264
    │   ├─ iOS 11+ → H.265（省流量）
    │   ├─ Android → H.264（兼容性）
    │   └─ 本地播放器 → 看分辨率
    │
    ├─ 分辨率是多少？
    │   ├─ ≤1080p → H.264（速度快）
    │   ├─ 4K → H.265（文件小一半）
    │   └─ 8K → H.265 或 AV1
    │
    ├─ 编码时间敏感吗？
    │   ├─ 实时推流 → H.264 + 硬件加速
    │   ├─ 快速转码 → H.264
    │   └─ 离线归档 → H.265
    │
    └─ 存储空间紧张吗？
        ├─ 是 → H.265
        └─ 否 → H.264（速度快）
```

---

### 场景 1：YouTube 上传

**推荐**：H.264
```bash
ffmpeg -i input.mp4 -c:v libx264 \
  -crf 18 -preset slow \
  -profile:v high -level 4.2 \
  -pix_fmt yuv420p \
  -c:a aac -b:a 192k \
  -movflags +faststart \
  output_youtube.mp4
```

**原因**：
- YouTube 会二次转码
- H.264 编码快，上传快
- YouTube 自己做 H.265/VP9/AV1 版本

---

### 场景 2：4K 视频归档

**推荐**：H.265
```bash
ffmpeg -i input_4k.mp4 -c:v libx265 \
  -crf 24 -preset slow \
  -profile:v main -level 5.1 \
  -pix_fmt yuv420p \
  -c:a aac -b:a 256k \
  output_4k_archive.mp4
```

**原因**：
- 4K H.264 文件太大（20-40 GB/小时）
- H.265 节省 50% 存储空间
- 现代设备都能解码

---

### 场景 3：iOS App 视频

**推荐**：H.265
```bash
ffmpeg -i input.mp4 -c:v libx265 \
  -crf 28 -preset fast \
  -profile:v main -level 4.1 \
  -pix_fmt yuv420p \
  -c:a aac -b:a 128k \
  -movflags +faststart \
  output_ios.mp4
```

**原因**：
- iOS 11+ 硬件解码 H.265
- 省流量（移动网络）
- 省存储（App 包大小）

---

### 场景 4：直播推流

**推荐**：H.264
```bash
ffmpeg -re -i input.mp4 -c:v libx264 \
  -preset veryfast -tune zerolatency \
  -crf 23 -maxrate 4M -bufsize 8M \
  -g 60 -keyint_min 60 \
  -c:a aac -b:a 128k \
  -f flv rtmp://server/live/stream
```

**原因**：
- H.265 编码太慢
- 大部分 CDN 不支持 H.265
- 观众端兼容性问题

---

### 场景 5：监控录像

**推荐**：H.265
```bash
ffmpeg -i rtsp://camera/stream -c:v libx265 \
  -crf 32 -preset veryfast \
  -x265-params "keyint=300:min-keyint=300" \
  -c:a aac -b:a 64k \
  -t 3600 \
  output_surveillance.mp4
```

**原因**：
- 长时间存储（节省 50% 空间）
- 不需要实时转码
- 低质量可接受

  -c:a copy \
  output_4k_h265.mp4

# 对比文件大小
ls -lh output_4k_*.mp4

# 验证质量
ffplay output_4k_h264.mp4
ffplay output_4k_h265.mp4

### 实践 6：Go 封装对比分析工具

```go
package main

import (
	"encoding/json"
	"fmt"
	"os/exec"
	"strconv"
)

type VideoInfo struct {
	Streams []struct {
		CodecName string `json:"codec_name"`
		Profile   string `json:"profile"`
		Width     int    `json:"width"`
		Height    int    `json:"height"`
		BitRate   string `json:"bit_rate"`
		Duration  string `json:"duration"`
	} `json:"streams"`
	Format struct {
		Size    string `json:"size"`
		BitRate string `json:"bit_rate"`
	} `json:"format"`
}

func analyzeVideo(path string) (*VideoInfo, error) {
	cmd := exec.Command("ffprobe",
		"-v", "quiet",
		"-print_format", "json",
		"-show_streams",
		"-show_format",
		path,
	)
	output, err := cmd.Output()
	if err != nil {
		return nil, err
	}

	var info VideoInfo
	if err := json.Unmarshal(output, &info); err != nil {
		return nil, err
	}
	return &info, nil
}

func formatSize(sizeStr string) string {
	size, _ := strconv.ParseInt(sizeStr, 10, 64)
	if size > 1024*1024*1024 {
		return fmt.Sprintf("%.2f GB", float64(size)/(1024*1024*1024))
	}
	return fmt.Sprintf("%.2f MB", float64(size)/(1024*1024))
}

func main() {
	files := []string{
		"h264_crf23.mp4",
		"h265_crf28.mp4",
	}

	fmt.Printf("%-30s %-10s %-10s %-15s\n", "文件", "编码", "Profile", "大小")
	fmt.Println(strings.Repeat("-", 70))

	for _, file := range files {
		info, err := analyzeVideo(file)
		if err != nil {
			fmt.Printf("%-30s 分析失败: %v\n", file, err)
			continue
		}

		if len(info.Streams) > 0 {
			stream := info.Streams[0]
			size := formatSize(info.Format.Size)
			fmt.Printf("%-30s %-10s %-10s %-15s\n",
				file, stream.CodecName, stream.Profile, size)
		}
	}
}
```

## 本篇小结

1. **H.265 核心改进**：
   - 编码单元从 16x16 增大到 64x64（CTU）
   - 帧内预测从 9 种增加到 35 种方向
   - 变换块支持 4x4 ~ 32x32
   - 更好的并行处理支持
   - **代价**：编码复杂度增加 4-10 倍

2. **压缩效率**：
   - 相同视觉质量，文件大小约为 H.264 的 **50%**
   - H.264 CRF 23 ≈ H.265 CRF 28（视觉等效）

3. **编码速度**：
   - H.265 比 H.264 慢 **4-10 倍**（medium preset）
   - 不适合实时推流（用硬件加速）

4. **Preset 建议**：
   - 日常：`fast`（H.265 本身慢，medium 已经很慢）
   - 归档：`slow`（veryslow 收益递减）
   - 实时：不用 libx265，用硬件加速

5. **Profile**：
   - `main`：标准 8-bit（默认）
   - `main10`：10-bit HDR/4K

6. **兼容性**：
   - Web：主用 H.264，H.265 仅 Safari 支持
   - 移动：iOS 11+ 和 Android 5+ 支持（硬件解码）
   - 本地：现代播放器均支持

7. **场景选择**：
   - ✅ H.265 适合：4K 内容、本地归档、iOS App、监控存储
   - ✅ H.264 适合：Web 视频、直播推流、Android、需要快速编码

## 关键术语速查表

| 术语 | 英文 | 解释 |
|------|------|------|
| HEVC | High Efficiency Video Coding | H.265 的标准名称 |
| CTU | Coding Tree Unit | H.265 的基本编码单元（最大 64x64） |
| CU | Coding Unit | CTU 的递归子分割单元 |
| PU | Prediction Unit | 预测单元（帧内/帧间预测的基本单位） |
| TU | Transform Unit | 变换单元（DCT 变换的基本单位） |
| WPP | Wavefront Parallel Processing | 波前并行处理（H.265 并行编码技术） |
| Tile | Tile | 瓷砖分割（H.265 并行处理单元，独立解码） |
| 10-bit | 10-bit depth | 10 位色深（相比 8-bit 更多灰阶，HDR 必须） |
| HDR | High Dynamic Range | 高动态范围（亮度范围更大） |
| PQ/SMPTE 2084 | Perceptual Quantization | HDR 传输曲线（用于 HDR10） |
