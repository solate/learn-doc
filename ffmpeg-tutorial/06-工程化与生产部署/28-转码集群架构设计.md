## 1. 为什么需要集群

### 1.1 单机的三个天花板

```
天花板 1：吞吐上限
  16 核机器，1080p 转码 speed ≈ 2.0x，并发 8 路
  → 单机日处理上限 ≈ 8 × 24h × 2.0 = 384 小时视频
  → 一旦日均上传超过 300 小时，队列开始永久积压

天花板 2：单任务延迟
  一部 2 小时 4K 电影，speed 0.3x
  → 单机需要 6.7 小时才能转完
  → 用户等不了，必须把单个任务拆开并行处理

天花板 3：可用性
  单机故障 = 转码服务完全不可用
  在途任务全部丢失，无法平滑升级
```

### 1.2 集群带来的新问题

集群不是免费的，它把「资源不够」换成了「协调复杂」：

| 单机的简单事 | 集群里变复杂 |
|-------------|-------------|
| 任务队列 = channel | 需要 Redis/RabbitMQ，要处理网络分区 |
| 进度写内存 | 需要中心化存储，要考虑写入频率 |
| 文件在本地磁盘 | 需要共享存储（NFS/对象存储），有网络 I/O 开销 |
| 进程崩溃 = 任务失败 | 节点失联时任务归属不明，需要租约机制 |
| 重启恢复 = 扫 DB | 需要区分「节点挂了」和「节点只是慢」 |
| 部署 = 一个容器 | 需要服务发现、滚动升级、健康检查 |

> **判断标准**：如果单机加机器配置（scale up）还能撑 6 个月，就先不要上集群。集群的运维成本远高于换一台更大的机器。

### 1.3 架构演进路径

```
阶段 1：单机单进程（日均 < 100 小时视频）
  ┌──────────────────────┐
  │  API + 转码 同进程     │
  │  channel 队列          │
  │  本地磁盘              │
  └──────────────────────┘

阶段 2：单机分离（日均 100~300 小时）
  ┌──────────┐    ┌──────────────┐
  │ API 服务  │───▶│ 转码服务      │
  │          │ DB │ channel 队列  │
  └──────────┘    └──────────────┘

阶段 3：多 Worker 集群（日均 300~3000 小时）
  ┌──────────┐    ┌─────────┐    ┌──────────┐
  │ API 服务  │───▶│ Redis   │◀───│ Worker×N │
  └──────────┘    │ 队列    │    └──────────┘
                  └─────────┘    共享对象存储

阶段 4：分片并行 + 弹性伸缩（日均 > 3000 小时）
  加入任务分片、竞价实例、多可用区
```

### 2.2 三种角色的职责边界

| 角色 | 职责 | 有状态？ | 副本数 |
|------|------|---------|--------|
| API 服务 | 接收请求、校验、投递队列、查询进度 | 无状态 | 2+（高可用）|
| Worker | 拉取任务、执行 FFmpeg、上报进度 | 无状态（任务状态在 DB）| N（按吞吐需求）|
| Scheduler | 超时检测、失败重入队、分片合并、清理 | **有状态**（需选主）| 1 主 + 1 备 |

> **关键设计**：Worker 必须无状态。Worker 挂了之后，任何一个其他 Worker 都能接手同一个任务——这要求任务的输入输出都在共享存储上，而不是本地磁盘。

### 2.3 为什么 Scheduler 需要选主

```
如果多个 Scheduler 同时运行：
  Scheduler A 检测到任务 T 超时 → 重新入队
  Scheduler B 也检测到任务 T 超时 → 又重新入队
  → 同一任务被执行两次，浪费资源，输出文件互相覆盖

解决：分布式锁选主，只有 leader 执行调度逻辑
```

```go
package scheduler

import (
	"context"
	"time"

	"github.com/redis/go-redis/v9"
	"github.com/rs/zerolog/log"
)

const (
	leaderKey      = "transcode:scheduler:leader"
	leaderTTL      = 15 * time.Second
	renewInterval  = 5 * time.Second
)

// LeaderElector 基于 Redis 的简单选主
type LeaderElector struct {
	rdb      *redis.Client
	nodeID   string
	isLeader bool
}

// NewLeaderElector 创建选主器
func NewLeaderElector(rdb *redis.Client, nodeID string) *LeaderElector {
	return &LeaderElector{rdb: rdb, nodeID: nodeID}
}

// Campaign 参与选主（阻塞运行，成为 leader 后持续续约）
func (e *LeaderElector) Campaign(ctx context.Context, onElected func(context.Context)) {
	ticker := time.NewTicker(renewInterval)
	defer ticker.Stop()

	var leaderCtx context.Context
	var leaderCancel context.CancelFunc

	for {
		select {
		case <-ctx.Done():
			if leaderCancel != nil {
				leaderCancel()
			}
			e.resign(context.Background())
			return
		case <-ticker.C:
			acquired, err := e.tryAcquire(ctx)
			if err != nil {
				log.Warn().Err(err).Msg("选主失败，本轮跳过")
				continue
			}

			if acquired && !e.isLeader {
				// 刚成为 leader，启动调度逻辑
				e.isLeader = true
				leaderCtx, leaderCancel = context.WithCancel(ctx)
				log.Info().Str("node_id", e.nodeID).Msg("成为 Scheduler leader")
				go onElected(leaderCtx)
			} else if !acquired && e.isLeader {
				// 失去 leader 身份，停止调度逻辑
				e.isLeader = false
				if leaderCancel != nil {
					leaderCancel()
				}
				log.Warn().Str("node_id", e.nodeID).Msg("失去 Scheduler leader 身份")
			}
		}
	}
}

// tryAcquire 尝试获取或续约 leader 锁
func (e *LeaderElector) tryAcquire(ctx context.Context) (bool, error) {
	// SET key nodeID NX EX ttl — 抢锁
	ok, err := e.rdb.SetNX(ctx, leaderKey, e.nodeID, leaderTTL).Result()
	if err != nil {
		return false, err
	}
	if ok {
		return true, nil
	}

	// 抢不到，检查是否是自己持有（续约场景）
	cur, err := e.rdb.Get(ctx, leaderKey).Result()
	if err != nil {
		return false, err
	}
	if cur != e.nodeID {
		return false, nil
	}

	// 是自己，续约
	if err := e.rdb.Expire(ctx, leaderKey, leaderTTL).Err(); err != nil {
		return false, err
	}
	return true, nil
}

// resign 主动放弃 leader（优雅退出时调用，加快故障转移）
func (e *LeaderElector) resign(ctx context.Context) {
	// Lua 脚本保证只删除自己持有的锁
	script := redis.NewScript(`
		if redis.call("GET", KEYS[1]) == ARGV[1] then
			return redis.call("DEL", KEYS[1])
		end
		return 0
	`)
	if err := script.Run(ctx, e.rdb, []string{leaderKey}, e.nodeID).Err(); err != nil {
		log.Warn().Err(err).Msg("放弃 leader 锁失败")
	}
}
```

> **生产建议**：这个 Redis 选主实现足够应付转码调度场景（调度逻辑幂等，短暂双主也不会造成严重后果）。如果需要严格的单主保证，用 etcd 的 `concurrency.Election` 或 Kubernetes 的 `leaderelection` 包。

## 3. 分布式任务队列

### 3.1 Redis Stream 作为任务队列

Redis Stream 相比 List 的优势：消费者组保证 at-least-once 投递、ACK 机制、自动 pending 追踪。

```go
package queue

import (
	"context"
	"encoding/json"
	"fmt"
	"time"

	"github.com/redis/go-redis/v9"
	"github.com/rs/zerolog/log"
)

const (
	streamKey     = "transcode:tasks"
	groupName     = "workers"
	pendingTimeout = 10 * time.Minute // 超过此时间未 ACK 的任务视为失败
)

// TaskMessage Redis Stream 消息
type TaskMessage struct {
	TaskID     string `json:"task_id"`
	TenantID   string `json:"tenant_id"`
	VideoID    string `json:"video_id"`
	InputURL   string `json:"input_url"`   // 对象存储 URL
	OutputKey  string `json:"output_key"`  // 对象存储目标 key
	Priority   int8   `json:"priority"`
	ShardIndex int    `json:"shard_index"` // 分片索引，0 表示不分片
	ShardTotal int    `json:"shard_total"` // 分片总数
}

// StreamQueue Redis Stream 队列
type StreamQueue struct {
	rdb      *redis.Client
	workerID string // 唯一标识这个 Worker 实例
}

// NewStreamQueue 创建队列（同时创建消费者组，已存在时忽略）
func NewStreamQueue(rdb *redis.Client, workerID string) (*StreamQueue, error) {
	q := &StreamQueue{rdb: rdb, workerID: workerID}
	// XGROUP CREATE … $ MKSTREAM：$ 表示只消费新消息，MKSTREAM 自动创建 stream
	if err := rdb.XGroupCreateMkStream(context.Background(), streamKey, groupName, "$").Err(); err != nil {
		if err.Error() != "BUSYGROUP Consumer Group name already exists" {
			return nil, fmt.Errorf("创建消费者组失败: %w", err)
		}
	}
	return q, nil
}

// Enqueue 投递任务
func (q *StreamQueue) Enqueue(ctx context.Context, msg TaskMessage) (string, error) {
	data, err := json.Marshal(msg)
	if err != nil {
		return "", fmt.Errorf("序列化任务失败: %w", err)
	}

	id, err := q.rdb.XAdd(ctx, &redis.XAddArgs{
		Stream: streamKey,
		MaxLen: 100000,          // 最多保留 10 万条（MAXLEN ~ 近似截断）
		Approx: true,
		Values: map[string]any{"data": string(data)},
	}).Result()
	if err != nil {
		return "", fmt.Errorf("入队失败: %w", err)
	}
	return id, nil
}

// Dequeue 拉取任务（阻塞最多 5 秒）
func (q *StreamQueue) Dequeue(ctx context.Context) (*TaskMessage, string, error) {
	result, err := q.rdb.XReadGroup(ctx, &redis.XReadGroupArgs{
		Group:    groupName,
		Consumer: q.workerID,
		Streams:  []string{streamKey, ">"},
		Count:    1,
		Block:    5 * time.Second,
	}).Result()
	if err == redis.Nil || len(result) == 0 || len(result[0].Messages) == 0 {
		return nil, "", nil // 无任务
	}
	if err != nil {
		return nil, "", fmt.Errorf("拉取任务失败: %w", err)
	}

	raw := result[0].Messages[0]
	dataStr, ok := raw.Values["data"].(string)
	if !ok {
		return nil, raw.ID, fmt.Errorf("消息格式错误: %v", raw.Values)
	}

	var msg TaskMessage
	if err := json.Unmarshal([]byte(dataStr), &msg); err != nil {
		return nil, raw.ID, fmt.Errorf("反序列化任务失败: %w", err)
	}
	return &msg, raw.ID, nil
}

// Ack 确认任务完成（完成或永久失败后调用）
func (q *StreamQueue) Ack(ctx context.Context, msgID string) error {
	return q.rdb.XAck(ctx, streamKey, groupName, msgID).Err()
}

// ReclaimPending 认领超时的 pending 消息（Scheduler 调用）
func (q *StreamQueue) ReclaimPending(ctx context.Context, schedulerWorkerID string) ([]*TaskMessage, []string, error) {
	// XAUTOCLAIM：把超过 pendingTimeout 且未被 ACK 的消息转移给 schedulerWorkerID
	msgs, _, err := q.rdb.XAutoClaim(ctx, &redis.XAutoClaimArgs{
		Stream:   streamKey,
		Group:    groupName,
		Consumer: schedulerWorkerID,
		MinIdle:  pendingTimeout,
		Start:    "0",
		Count:    50,
	}).Result()
	if err != nil {
		return nil, nil, fmt.Errorf("认领超时任务失败: %w", err)
	}

	var tasks []*TaskMessage
	var ids []string
	for _, m := range msgs {
		dataStr, ok := m.Values["data"].(string)
		if !ok {
			continue
		}
		var msg TaskMessage
		if err := json.Unmarshal([]byte(dataStr), &msg); err != nil {
			log.Warn().Err(err).Str("msg_id", m.ID).Msg("超时消息反序列化失败")
			continue
		}
		tasks = append(tasks, &msg)
		ids = append(ids, m.ID)
	}
	return tasks, ids, nil
}
```

### 3.2 Worker 消费循环

```go
// Worker 转码 Worker
type Worker struct {
	queue    *StreamQueue
	runner   *ffmpeg.JobRunner
	repo     TaskRepo
	workerID string
}

// Run Worker 主循环（持续拉取并处理任务）
func (w *Worker) Run(ctx context.Context) {
	log.Info().Str("worker_id", w.workerID).Msg("Worker 启动")
	for {
		select {
		case <-ctx.Done():
			log.Info().Str("worker_id", w.workerID).Msg("Worker 正常退出")
			return
		default:
		}

		msg, msgID, err := w.queue.Dequeue(ctx)
		if err != nil {
			log.Error().Err(err).Msg("拉取任务失败，等待重试")
			select {
			case <-time.After(5 * time.Second):
			case <-ctx.Done():
			}
			continue
		}
		if msg == nil {
			continue // 无任务，继续轮询
		}

		if err := w.process(ctx, msg, msgID); err != nil {
			log.Error().Err(err).Str("task_id", msg.TaskID).Msg("任务处理失败")
		}
	}
}

// process 处理单个任务
func (w *Worker) process(ctx context.Context, msg *TaskMessage, msgID string) error {
	log.Info().Str("task_id", msg.TaskID).Str("worker_id", w.workerID).Msg("开始处理转码任务")

	if err := w.repo.UpdateStatus(ctx, msg.TaskID, TaskStatusRunning, ""); err != nil {
		log.Warn().Err(err).Str("task_id", msg.TaskID).Msg("更新任务状态失败")
	}

	// 下载原始文件到本地（或直接用 URL 作为 FFmpeg 输入）
	cfg := ffmpeg.JobConfig{
		Args: buildArgs(msg),
		Timeout: ffmpeg.TaskTimeout(msg.VideoID),
	}

	err := w.runner.RunWithRetry(ctx, cfg, ffmpeg.DefaultRetryConfig())
	if err != nil {
		_ = w.repo.UpdateStatus(ctx, msg.TaskID, TaskStatusFailed, err.Error())
		_ = w.queue.Ack(ctx, msgID) // 永久失败，ACK 避免无限重试
		return err
	}

	_ = w.repo.UpdateStatus(ctx, msg.TaskID, TaskStatusSucceeded, "")
	_ = w.queue.Ack(ctx, msgID)
	log.Info().Str("task_id", msg.TaskID).Msg("转码任务完成")
	return nil
}
```

## 4. 任务调度策略

### 4.1 调度维度

```
任务调度需要回答三个问题：

1. 分给哪个 Worker？
   • 能力匹配：GPU 任务 → GPU Worker，软件任务 → CPU Worker
   • 负载均衡：优先选空闲 Worker（轮询/最少任务数）
   • 本地性：任务的输入文件在哪个存储区域，选近的 Worker

2. 什么时候执行？
   • 优先级：付费用户 > 普通用户 > 批量后台
   • 时间窗口：批量任务在低峰期（凌晨）执行
   • 资源预留：高峰期保留 20% Worker 给实时任务

3. 失败了怎么办？
   • 临时错误：指数退避重试（见第 25 篇）
   • 永久错误：立即失败，通知用户
   • Worker 挂掉：Scheduler 认领超时任务，重新入队
```

### 4.2 Worker 能力注册

```go
// WorkerCapability Worker 能力声明
type WorkerCapability struct {
	WorkerID   string   `json:"worker_id"`
	NodeName   string   `json:"node_name"`
	Zone       string   `json:"zone"`         // 可用区（us-east-1a）
	Tags       []string `json:"tags"`         // 能力标签，如 ["gpu", "nvenc"]
	MaxWorkers int      `json:"max_workers"`  // 最大并发转码数
	Current    int      `json:"current"`      // 当前活跃任务数
}

// RegisterCapability Worker 启动时向 Redis 注册，定期续约
func RegisterCapability(ctx context.Context, rdb *redis.Client, cap WorkerCapability) error {
	data, _ := json.Marshal(cap)
	key := fmt.Sprintf("transcode:worker:%s", cap.WorkerID)
	// 每 30 秒续约一次，15 秒超时表示节点可能故障
	return rdb.Set(ctx, key, string(data), 30*time.Second).Err()
}

// ListActiveWorkers 列出所有活跃 Worker
func ListActiveWorkers(ctx context.Context, rdb *redis.Client) ([]*WorkerCapability, error) {
	keys, err := rdb.Keys(ctx, "transcode:worker:*").Result()
	if err != nil {
		return nil, err
	}

	var workers []*WorkerCapability
	for _, key := range keys {
		data, err := rdb.Get(ctx, key).Result()
		if err == redis.Nil {
			continue
		}
		if err != nil {
			continue
		}
		var cap WorkerCapability
		if err := json.Unmarshal([]byte(data), &cap); err != nil {
			continue
		}
		workers = append(workers, &cap)
	}
	return workers, nil
}
```

### 4.3 基于标签的任务路由

```go
// RouteTask 为任务选择合适的队列
func RouteTask(task TaskMessage, workers []*WorkerCapability) string {
	// GPU 任务只投 GPU 队列
	if task.RequiresGPU() {
		for _, w := range workers {
			for _, tag := range w.Tags {
				if tag == "gpu" && w.Current < w.MaxWorkers {
					return "transcode:tasks:gpu"
				}
			}
		}
		// 无可用 GPU Worker，降级到 CPU 队列（带 -c:v libx264）
		log.Warn().Str("task_id", task.TaskID).Msg("GPU Worker 不可用，降级到软件编码")
	}
	return "transcode:tasks:cpu"
}

		}
```

## 5. 任务分片与并行转码

### 5.1 分片的价值

```
一部 4K 电影（2 小时）在 8 核 CPU 上 speed ≈ 0.2x
  → 单机需要 10 小时才能转完

分成 8 片（每片 15 分钟），分发给 8 个 Worker 并行处理：
  → 每片 speed ≈ 0.2x × 8核 = 1.6x（理论值）
  → 每片实际耗时 ≈ 15/1.6 ≈ 9 分钟
  → 8 片并行 + 最后合并（约 1 分钟）≈ 10 分钟
  → 比单机快约 60 倍！

代价：
  • 需要对象存储暂存分片文件（额外存储开销）
  • 关键帧对齐要求（分片点必须在关键帧处）
  • 合并步骤增加复杂度
```

### 5.2 关键帧对齐的分片点

```bash

for t in target_times:
    nearest = min(keyframes, key=lambda k: abs(k - t))
    print(f"目标={t:.1f}s, 实际分片点={nearest:.3f}s, 偏差={abs(nearest-t):.3f}s")
EOF
```

```go
// CheckAndMerge 检查分片是否全部完成，全部成功则触发合并
func (s *Scheduler) CheckAndMerge(ctx context.Context, taskID string) error {
	// 批量查询该任务的所有分片（禁止循环查库）
	shards, err := s.shardRepo.ListByTaskID(ctx, taskID)
	if err != nil {
		return xerr.Wrap(xerr.ErrInternal.Code, "查询分片记录失败", err)
	}
	if len(shards) == 0 {
		return nil
	}

	// 统计各状态数量
	var succeeded, failed int
	outputs := make([]string, len(shards))
	for _, sh := range shards {
		switch sh.Status {
		case ShardStatusSucceeded:
			succeeded++
			outputs[sh.ShardIndex] = sh.OutputKey // 按索引放置，保证顺序
		case ShardStatusFailed:
			failed++
		}
	}

	// 有分片失败，整个任务失败
	if failed > 0 {
		log.Error().Str("task_id", taskID).Int("failed", failed).Msg("存在失败分片，任务终止")
		return s.taskRepo.UpdateStatus(ctx, taskID, TaskStatusFailed, "部分分片转码失败")
	}

	// 未全部完成，等待下一轮检查
	if succeeded < len(shards) {
		log.Debug().Str("task_id", taskID).Int("done", succeeded).Int("total", len(shards)).Msg("分片未全部完成")
		return nil
	}

	// 全部成功，触发合并
	log.Info().Str("task_id", taskID).Int("shards", len(shards)).Msg("所有分片完成，开始合并")
	return s.mergeAndFinalize(ctx, taskID, outputs)
}
```

> **分片顺序至关重要**：`outputs[sh.ShardIndex] = sh.OutputKey` 按索引赋值，而不是 `append`。用 append 的话，DB 返回顺序不确定就会导致合并后的视频段落错乱——这个 bug 很隐蔽，测试时如果分片少可能碰巧是对的。

### 5.6 什么时候不该分片

| 场景 | 是否分片 | 原因 |
|------|---------|------|
| 短视频（< 5 分钟） | ❌ 不分片 | 分片开销（上传下载 + 合并）超过收益 |
| 长视频（> 30 分钟） | ✅ 分片 | 收益明显 |
| 需要全局分析的滤镜 | ❌ 不分片 | `loudnorm` 双通道、`palettegen` 需要全片统计 |
| 两遍编码（two-pass） | ❌ 不分片 | 第一遍需要扫全片 |
| 直播流 | ❌ 不分片 | 实时流无法预先划分 |
| 只做重封装（`-c copy`） | ❌ 不分片 | 本身就很快，几秒完成 |
| 用户等待中的实时任务 | ✅ 分片 | 降低单任务延迟是核心价值 |

## 6. 断点续传与幂等性

### 6.1 为什么必须幂等

```
Redis Stream 是 at-least-once 投递：
  Worker 拉到任务 → 转码成功 → 上传成功 → ACK 前进程崩溃
  → 消息仍在 pending 列表
  → Scheduler 认领后重新投递
  → 另一个 Worker 又转码了一遍

如果不幂等：
  • 浪费一次完整的转码资源
  • 输出文件被覆盖写，如果第二次失败反而破坏了已成功的结果
  • 计费系统重复扣费
```

### 6.2 幂等性实现

```go
// process 幂等的任务处理
func (w *Worker) process(ctx context.Context, msg *TaskMessage, msgID string) error {
	// 幂等检查 1：DB 状态已是成功，直接 ACK
	task, err := w.repo.GetByID(ctx, msg.TaskID)
	if err != nil {
		return xerr.Wrap(xerr.ErrInternal.Code, "查询任务失败", err)
	}
	if task == nil {
		log.Warn().Str("task_id", msg.TaskID).Msg("任务不存在，可能已被删除，直接 ACK")
		return w.queue.Ack(ctx, msgID)
	}
	if task.Status == TaskStatusSucceeded {
		log.Info().Str("task_id", msg.TaskID).Msg("任务已完成，跳过重复执行")
		return w.queue.Ack(ctx, msgID)
	}
	if task.Status == TaskStatusCanceled {
		log.Info().Str("task_id", msg.TaskID).Msg("任务已取消，跳过执行")
		return w.queue.Ack(ctx, msgID)
	}

	// 幂等检查 2：输出文件已存在且完整，直接标记成功
	exists, size, err := w.storage.Head(ctx, msg.OutputKey)
	if err == nil && exists && size > 0 {
		if valid, _ := w.validateOutput(ctx, msg.OutputKey); valid {
			log.Info().Str("task_id", msg.TaskID).Str("key", msg.OutputKey).Msg("输出文件已存在且有效，跳过转码")
			_ = w.repo.UpdateStatus(ctx, msg.TaskID, TaskStatusSucceeded, "")
			return w.queue.Ack(ctx, msgID)
		}
		log.Warn().Str("task_id", msg.TaskID).Msg("输出文件存在但校验失败，重新转码")
	}

	// 幂等检查 3：抢占任务锁，防止两个 Worker 同时处理同一任务
	lockKey := fmt.Sprintf("transcode:lock:%s", msg.TaskID)
	acquired, err := w.rdb.SetNX(ctx, lockKey, w.workerID, 3*time.Hour).Result()
	if err != nil {
		return xerr.Wrap(xerr.ErrInternal.Code, "获取任务锁失败", err)
	}
	if !acquired {
		holder, _ := w.rdb.Get(ctx, lockKey).Result()
		log.Info().Str("task_id", msg.TaskID).Str("holder", holder).Msg("任务已被其他 Worker 持有，跳过")
		return nil // 不 ACK，让持有者完成后 ACK
	}
	defer w.rdb.Del(ctx, lockKey)

	return w.doTranscode(ctx, msg, msgID)
}

// validateOutput 校验输出文件是否可用（用 ffprobe 检查）
func (w *Worker) validateOutput(ctx context.Context, key string) (bool, error) {
	url, err := w.storage.SignedURL(ctx, key, 5*time.Minute)
	if err != nil {
		return false, err
	}
	// ffprobe 能读出 duration 说明文件结构完整
	dur, err := ffmpeg.GetDuration(ctx, url)
	if err != nil {
		return false, err
	}
	return dur > 0, nil
}
```

### 6.3 分片级断点续传

分片任务天然支持断点续传——只重跑失败的分片：

```go
// ResumeTask 恢复中断的分片任务（只重跑未成功的分片）
func (s *Scheduler) ResumeTask(ctx context.Context, taskID string) error {
	shards, err := s.shardRepo.ListByTaskID(ctx, taskID)
	if err != nil {
		return xerr.Wrap(xerr.ErrInternal.Code, "查询分片失败", err)
	}

	// 收集需要重跑的分片索引（批量处理，不在循环里查库）
	var toRetry []*model.TranscodeShard
	for _, sh := range shards {
		if sh.Status == ShardStatusSucceeded {
			continue // 已成功，跳过
		}
		if sh.Attempts >= 3 {
			log.Error().Str("task_id", taskID).Int("shard", int(sh.ShardIndex)).Msg("分片重试次数耗尽")
			return s.taskRepo.UpdateStatus(ctx, taskID, TaskStatusFailed, "分片重试次数耗尽")
		}
		toRetry = append(toRetry, sh)
	}

	if len(toRetry) == 0 {
		log.Info().Str("task_id", taskID).Msg("所有分片已完成，触发合并")
		return s.CheckAndMerge(ctx, taskID)
	}

	// 批量重置状态后重新投递
	ids := make([]string, 0, len(toRetry))
	for _, sh := range toRetry {
		ids = append(ids, sh.ShardID)
	}
	if err := s.shardRepo.BatchUpdateStatus(ctx, ids, ShardStatusPending); err != nil {
		return xerr.Wrap(xerr.ErrInternal.Code, "重置分片状态失败", err)
	}

	for _, sh := range toRetry {
		msg := shardToMessage(taskID, sh)
		if _, err := s.queue.Enqueue(ctx, msg); err != nil {
			log.Error().Err(err).Str("task_id", taskID).Int("shard", int(sh.ShardIndex)).Msg("重新投递分片失败")
		}
	}
	log.Info().Str("task_id", taskID).Int("retry_count", len(toRetry)).Msg("已重新投递失败分片")
	return nil
}
```

> **这是分片架构最大的隐性收益**：一个 2 小时的 4K 转码任务，第 7 个分片失败时，不分片的话要整个重跑 10 小时，分片后只需重跑那 15 分钟。

## 7. 节点管理与故障转移

### 7.1 节点心跳机制

```go
// HeartbeatReporter Worker 心跳上报
type HeartbeatReporter struct {
	rdb      *redis.Client
	workerID string
	cap      *WorkerCapability
	pool     *ffmpeg.WorkerPool
}

// Start 启动心跳上报（每 10 秒上报一次，TTL 30 秒）
func (h *HeartbeatReporter) Start(ctx context.Context) {
	ticker := time.NewTicker(10 * time.Second)
	defer ticker.Stop()

	// 立即上报一次，不等第一个 tick
	h.report(ctx)

	for {
		select {
		case <-ticker.C:
			h.report(ctx)
		case <-ctx.Done():
			// 优雅退出：删除心跳，快速触发故障检测
			h.rdb.Del(context.Background(), h.heartbeatKey())
			return
		}
	}
}

func (h *HeartbeatReporter) report(ctx context.Context) {
	h.cap.Current = int(h.pool.ActiveCount())
	data, _ := json.Marshal(h.cap)
	if err := h.rdb.Set(ctx, h.heartbeatKey(), string(data), 30*time.Second).Err(); err != nil {
		log.Warn().Err(err).Str("worker_id", h.workerID).Msg("心跳上报失败")
	}
}

func (h *HeartbeatReporter) heartbeatKey() string {
	return fmt.Sprintf("transcode:worker:%s", h.workerID)
}
```

### 7.2 故障检测与任务认领

Scheduler 定期扫描 pending 队列中超时的消息，认领并重新分配：

```go
// SchedulerLoop Scheduler 主循环
func (s *Scheduler) SchedulerLoop(ctx context.Context) {
	ticker := time.NewTicker(30 * time.Second)
	defer ticker.Stop()

	for {
		select {
		case <-ticker.C:
			s.recoverPendingMessages(ctx)
			s.checkShardCompletion(ctx)
		case <-ctx.Done():
			return
		}
	}
}

// recoverPendingMessages 认领超时的 pending 消息
func (s *Scheduler) recoverPendingMessages(ctx context.Context) {
	tasks, ids, err := s.queue.ReclaimPending(ctx, s.workerID)
	if err != nil {
		log.Error().Err(err).Msg("认领超时任务失败")
		return
	}
	if len(tasks) == 0 {
		return
	}

	log.Warn().Int("count", len(tasks)).Msg("发现超时任务，重新入队")

	for i, task := range tasks {
		// 超时任务重置状态并重新投递
		if err := s.taskRepo.UpdateStatus(ctx, task.TaskID, TaskStatusPending, ""); err != nil {
			log.Error().Err(err).Str("task_id", task.TaskID).Msg("重置任务状态失败")
			continue
		}
		// ACK 旧消息，重新 Enqueue
		_ = s.queue.Ack(ctx, ids[i])
		if _, err := s.queue.Enqueue(ctx, *task); err != nil {
			log.Error().Err(err).Str("task_id", task.TaskID).Msg("重新入队失败")
		}
	}
}
```

### 7.3 滚动升级策略

```
Worker 滚动升级步骤：

1. 从负载均衡中摘除本节点（或把节点 maxWorkers 设为 0 停止接新任务）
2. 等待在途任务全部完成（通过心跳查看 current = 0）
3. 停止 Worker 进程（发 SIGTERM，触发优雅关闭）
4. 更新镜像，启动新版本
5. 验证新版本心跳正常后，恢复接受任务

Kubernetes 滚动升级自动处理以上步骤，但需要：
  • readinessProbe 在 current > 0 时返回 not ready（停止接新任务）
  • terminationGracePeriodSeconds 足够大（> 最长任务时长 + 合并时间）
```

## 8. 容量规划与成本优化

### 8.1 容量估算公式

```
需要多少 Worker？

输入参数：
  D = 日均上传视频总时长（小时）
  S = 目标转码 speed（单核，如 2.0x 表示 1 小时视频 30 分钟转完）
  P = 转码峰值系数（通常 2~3x，即峰值是均值的 2~3 倍）
  C = 每个 Worker 的 CPU 核数
  T = 每日可用转码时间（秒，通常按 20 小时算，留 4 小时维护窗口）

估算公式：
  所需 Worker 核时 = D × 3600 / S × P
  所需 Worker 核数 = 所需 Worker 核时 / T
  所需 Worker 台数 = ceil(所需 Worker 核数 / C)

示例：
  D = 1000 小时/天
  S = 2.0x（8 核机器，单路 speed=0.25x → 并发 8 路 speed=2.0x）
  P = 2.5（峰值是均值 2.5 倍）
  C = 8 核/台
  T = 72000 秒（20 小时）

  核时 = 1000 × 3600 / 2.0 × 2.5 = 4,500,000 核秒
  核数 = 4,500,000 / 72000 = 62.5 核
  台数 = ceil(62.5 / 8) = 8 台（8 核机器）

结论：8 台 8 核机器，或 4 台 16 核机器
```

### 8.2 成本优化策略

```
策略 1：按优先级使用不同实例类型
  付费用户实时任务 → 按需实例（高可用，贵）
  批量离线任务     → 竞价实例（随时可能被抢占，便宜 60~90%）

策略 2：自动伸缩
  队列深度 > 100 且持续 5 分钟 → 扩容 2 台 Worker
  队列深度 = 0 且持续 30 分钟  → 缩容，保留最小集群（2 台）
  每次伸缩冷却期 10 分钟（防止频繁扩缩）

策略 3：错峰批量任务
  非实时转码任务在凌晨 0:00~6:00 执行
  这个时段服务器空闲，竞价实例价格最低（有些云厂商此时间段便宜 80%）

策略 4：格式自适应降级
  队列积压严重时：暂时降低非 VIP 用户的输出质量
  CRF 23 → CRF 27（文件缩小 50%，转码快 20%，用户轻微感知）
  高峰过后自动恢复
```

**步骤**：

```yaml

version: '3.8'

services:

    image: redis:7-alpine

      - ./test_data:/data
    stop_grace_period: 60s
    depends_on: [redis, postgres]
```

**验证**：

```bash
docker compose -f docker-compose.cluster.yml up -d

# 1. 检查两个 Worker 都注册了心跳
redis-cli keys "transcode:worker:*"

# 2. 查看 Scheduler leader
redis-cli get "transcode:scheduler:leader"

# 3. 提交任务，观察被哪个 Worker 处理
for i in $(seq 1 10); do
```

### 练习 2：模拟 Worker 故障，验证自动恢复

**目标**：确认 Worker 挂掉后，其任务会被 Scheduler 重新分配。

**步骤**：

```bash
# 1. 提交一个长任务（60 秒以上）
curl -X POST http://localhost:8080/api/v1/transcode/submit \
  -d '{"video_id":"v1","input_path":"/data/long.mp4","output_path":"/data/out.mp4"}'

# 2. 确认任务被 worker-1 接管
watch -n 1 "redis-cli get 'transcode:lock:TASK_ID'"

# 3. 任务执行中途强杀 worker-1（模拟节点故障）
docker compose -f docker-compose.cluster.yml kill worker-1

# 4. 等待约 40 秒（心跳超时 30s + Scheduler 扫描周期 30s）
sleep 40

# 5. 观察任务是否被 worker-2 重新接管
docker compose -f docker-compose.cluster.yml logs worker-2 | tail -10
# 应该看到："开始处理转码任务" 日志
```

**预期结果**：约 40 秒后，worker-2 重新接管该任务并完成转码。

### 练习 3：分片并行转码性能对比

**目标**：验证分片并行转码比单任务转码快多少。

**步骤**：

```bash
# 准备一个 10 分钟测试视频
ffmpeg -f lavfi -i testsrc2=duration=600:size=1920x1080:rate=30 \
  -f lavfi -i sine=duration=600 \
  -c:v libx264 -crf 18 -c:a aac -shortest test_10min.mp4

# 方式 A：单任务转码（记录时间）
time ffmpeg -i test_10min.mp4 \
  -c:v libx264 -crf 23 -preset medium \
  -c:a aac -b:a 128k \
  out_single.mp4

# 方式 B：分 4 片并行（各自 2.5 分钟）
for i in 0 1 2 3; do
  START=$((i * 150))
  END=$(((i+1) * 150))
  ffmpeg -ss $START -i test_10min.mp4 \
    -to 150 -c:v libx264 -crf 23 -preset medium \
    -c:a aac -b:a 128k -avoid_negative_ts make_zero \
    -y "shard_$i.mp4" &
done

time wait  # 等所有后台进程完成

# 合并
printf "file 'shard_%d.mp4'\n" 0 1 2 3 > concat.txt
time ffmpeg -f concat -safe 0 -i concat.txt -c copy out_sharded.mp4

# 对比两种输出的时长和大小
ffprobe -v error -show_entries format=duration,size -of csv=p=0 out_single.mp4
ffprobe -v error -show_entries format=duration,size -of csv=p=0 out_sharded.mp4
```

**预期结果**：4 分片并行耗时约为单任务的 1/3（受限于本机核数，不会到 1/4），且两种输出时长相同，文件大小相近（差异 < 5%）。

## 10. 本章总结

### 核心要点

1. **单机瓶颈有三个天花板**：CPU 核数、内存带宽、存储 IOPS。任意一项到顶，集群是唯一出路。

2. **Master-Worker 分离是正确方向**：API/Scheduler 无状态，Worker 可水平扩展，Scheduler 用 Redis SetNX 保证唯一领导。

3. **Redis Stream 比普通队列更可靠**：XREADGROUP 保证 at-least-once，XAUTOCLAIM 自动认领超时消息，天然支持故障恢复。

4. **幂等性是集群稳定性的基础**：DB 状态检查 → 存储 Head 验证 → Redis NX 锁，三层防护确保任务不重复执行。

5. **分片加速有前提**：视频时长 > 10 分钟、格式支持关键帧对齐、输入存储在共享卷上。短视频不值得分片。

6. **合并时用索引赋值**：`outputs[sh.ShardIndex] = key` 而非 `append`，否则 DB 查询顺序不确定时分片顺序会错乱。

7. **节点故障恢复依赖心跳 TTL**：心跳 10s 上报、30s TTL，Scheduler 30s 扫描，最坏 60s 恢复。降低 TTL 可加快恢复，但增加心跳压力。

### 技术选型决策树

```
需要转码集群吗？

单机 CPU 利用率 > 85% 且队列持续积压？
  └── 否 → 先优化单机（调 preset、启用硬件编码）
  └── 是 → 进入集群选型

任务来源稳定可预期（离线批量）？
  ├── 是 → 简单 Master-Worker + 数据库队列即可
  └── 否 → Redis Stream + XREADGROUP（动态负载）

是否需要跨机房容灾？
  ├── 是 → Kafka（跨机房复制、持久化更强）
  └── 否 → Redis Stream 足够

单个视频超过 30 分钟且有实时性要求？
  ├── 是 → 分片并行（注意关键帧对齐 + 索引合并）
  └── 否 → 整体任务投递，更简单

```

### 集群架构演进路径回顾

```
阶段 1：单机 → 多路并发（WorkerPool，无需集群）
阶段 2：主从 → 两台机器，Redis 队列（简单但有 SPOF）
阶段 3：领导者选举 → Scheduler HA，Worker 水平扩展
阶段 4：能力路由 → GPU/CPU 分级，按任务类型分配 Worker
```

## 常见问题排查

| 现象 | 可能原因 | 排查命令 | 解决方法 |
|------|----------|----------|----------|
| 任务长时间卡在 pending | Scheduler 未选举为 Leader | `redis-cli get transcode:scheduler:leader` | 检查 Scheduler 日志，确认心跳是否正常 |
| 同一个任务被执行两次 | Redis NX 锁未生效或 TTL 设置过短 | 查看任务日志中的 `task_id` | 增大锁 TTL，或检查 `SET NX EX` 是否正确 |
| Worker 挂掉后任务不恢复 | XAUTOCLAIM min-idle-time 设置过长 | `XPENDING transcode:tasks GROUP:workers - + 10` | 调小 `ReclaimAfter`（当前 30min），或手动触发认领 |
| 合并后视频片段顺序错乱 | 使用了 `append` 而非索引赋值 | `ffprobe -show_frames merged.mp4 \| grep pts_time` | 改为 `outputs[sh.ShardIndex] = key`，重新合并 |
| 分片任务完成但未触发合并 | `CheckAndMerge` 未被调用，或检查条件判断有误 | 查 DB：`SELECT status FROM transcode_shards WHERE task_id=?` | 确保所有分片 `status=succeeded` 后 `CheckAndMerge` 被触发 |
| Redis Stream 积压 | Worker 处理速度跟不上入队速度 | `XLEN transcode:tasks` | 扩容 Worker；或降低非 VIP 任务的转码质量 |
| 心跳 key 不存在但 Worker 在运行 | Redis 连接中断，心跳上报失败 | Worker 容器内：`redis-cli -h $REDIS_ADDR ping` | 检查网络；可加重试机制到 `HeartbeatReporter.report()` |
| 领导者选举频繁切换（抖动） | Redis 网络抖动导致 SetNX TTL 提前到期 | `redis-cli debug sleep 0` 后观察 | 增大 LeaderTTL（从 10s 改为 30s），增大续约频率 |

## 术语表

| 术语 | 英文 | 解释 |
|------|------|------|
| 领导者选举 | Leader Election | 集群中多个节点通过竞争机制选出唯一的"主节点"，负责协调全局状态 |
| 消费者组 | Consumer Group | Redis Stream 中的概念，同一组内多个消费者竞争处理消息（每条消息只被一个消费者处理）|
| 待确认消息 | Pending Entry List (PEL) | 已投递给消费者但尚未 ACK 的消息列表，XAUTOCLAIM 据此认领超时消息 |
| 幂等性 | Idempotency | 同一操作执行多次与执行一次结果相同，集群容错的基础 |
| 关键帧对齐 | Keyframe-aligned Split | 视频分片的切割点选在 I 帧（关键帧）处，确保分片边界可独立解码 |
| 能力路由 | Capability Routing | 根据 Worker 的硬件能力（GPU/CPU）将任务分发到最合适的节点 |
| 竞价实例 | Spot Instance | 云平台的剩余算力资源，比按需实例便宜 60~90%，但可能被随时抢占 |
| 滚动升级 | Rolling Update | 逐台更新节点，保证服务不中断，与蓝绿发布相对 |
| 分片 | Shard | 将大任务拆分为若干小任务并行处理，最后合并结果 |
| 心跳 | Heartbeat | 节点定期向注册中心发送存活信号，超时则视为节点故障 |
