## 1. 排查方法论

### 1.1 先量化，再优化

```
❌ 错误的排查路径：
   "转码很慢" → 直接改 preset → 好像快了点 → 上线
   → 画质下降用户投诉 → 改回来 → 问题依旧

✅ 正确的排查路径：
   1. 量化现状：speed=0.3x，1 小时视频要 3.3 小时
   2. 确定目标：speed ≥ 1.0x
   3. 定位瓶颈：CPU 100%？还是 I/O wait 高？还是滤镜链慢？
   4. 针对性优化：只改瓶颈那一项
   5. 复测验证：speed 和画质指标都要对比
```

### 1.2 三层排查框架

```
┌─────────────────────────────────────────────────────────┐
│  第一层：命令层（FFmpeg 自身）                             │
│  • 手动跑同样的命令，能否复现？                             │
│  • -loglevel debug 看完整参数解析                          │
│  • 去掉滤镜/换 preset，二分法定位慢在哪                     │
├─────────────────────────────────────────────────────────┤
│  第二层：系统层（资源）                                     │
│  • top/htop：CPU 是否打满？单核还是多核？                   │
│  • iostat：磁盘 I/O wait 是否高？                          │
│  • free：内存是否吃紧、是否在 swap？                        │
├─────────────────────────────────────────────────────────┤
│  第三层：应用层（Go 服务）                                  │
│  • 并发数是否过高导致互相抢占？                             │
│  • 进程是否泄漏（ps aux | grep ffmpeg | wc -l）？          │
│  • 日志中错误分类是否正确（无意义的重试）？                  │
└─────────────────────────────────────────────────────────┘
```

### 1.3 关键指标解读

FFmpeg 运行时输出的这一行包含了最重要的诊断信息：

```
frame= 1250 fps= 42 q=23.0 size=   12800kB time=00:00:50.00 bitrate=2097.2kbits/s speed=1.68x
      ↑          ↑       ↑         ↑              ↑                    ↑              ↑
   已处理帧数  处理速度  量化参数  输出大小      已处理时长          当前码率      实时倍速
```

| 指标 | 含义 | 诊断价值 |
|------|------|----------|
| `speed` | 相对实时的倍速 | **最关键**。< 1.0x 说明比实时播放还慢 |
| `fps` | 每秒处理帧数 | 结合源帧率判断，源 30fps 时 fps=30 即 speed=1.0x |
| `q` | 当前量化参数 | 突然飙高说明码率不够，画质在下降 |
| `bitrate` | 当前平均码率 | 与目标码率对比，判断码率控制是否生效 |
| `size` | 已输出大小 | 长时间不变说明卡住了 |
| `drop`/`dup` | 丢帧/重复帧数 | 出现即说明帧率转换或时间戳有问题 |

## 2. 常见错误速查表

### 2.1 输入相关错误

| 错误信息 | 根因 | 修复方案 |
|----------|------|----------|
| `No such file or directory` | 路径错误 / 容器内路径不存在 | 确认挂载路径；容器内用 `ls` 验证 |
| `Invalid data found when processing input` | 文件损坏 / 格式不匹配 | `ffprobe` 检查；用 `-err_detect ignore_err` 尝试容错读取 |
| `moov atom not found` | MP4 缺 moov box（未正常写完） | 源文件已损坏，尝试 `untrunc` 修复；上游改用优雅终止 |
| `Could not find codec parameters for stream` | 流信息不足 / 探测数据太少 | 加大 `-probesize 50M -analyzeduration 10M` |
| `Protocol not found` | 协议未编译 / 被 whitelist 拦截 | `ffmpeg -protocols` 检查；调整 `-protocol_whitelist` |
| `Server returned 403 Forbidden` | 拉流鉴权失败 / 防盗链 | 检查签名 URL 是否过期（见 第 20 篇）|
| `Immediate exit requested` | 收到 SIGTERM/SIGINT | 正常的优雅终止，非错误 |

### 2.2 编解码相关错误

| 错误信息 | 根因 | 修复方案 |
|----------|------|----------|
| `Unknown encoder 'libx265'` | 构建未包含该编码器 | `ffmpeg -encoders \| grep x265` 确认；换镜像或自编译 |
| `Unknown encoder 'libfdk_aac'` | nonfree 编码器未编译 | 改用内置 `aac`（质量差距很小） |
| `Cannot load libnvcuvid.so` | GPU 驱动/CUDA 库缺失 | 容器加 `NVIDIA_DRIVER_CAPABILITIES=video` |
| `OpenEncodeSessionEx failed: out of memory` | NVENC 会话数超限 | 降低 GPU 并发数（消费级卡通常限 3~8 路） |
| `Specified pixel format yuvj420p is invalid` | 像素格式与编码器不兼容 | 加 `-pix_fmt yuv420p` 显式转换 |
| `height not divisible by 2` | H.264 要求宽高为偶数 | `scale=trunc(iw/2)*2:trunc(ih/2)*2` |
| `Too many packets buffered for output stream` | 某路流数据严重滞后 | 加大 `-max_muxing_queue_size 1024` |
| `Non-monotonous DTS in output stream` | 时间戳非单调递增 | 加 `-fflags +genpts` 或 `-avoid_negative_ts make_zero` |

### 2.3 滤镜相关错误

| 错误信息 | 根因 | 修复方案 |
|----------|------|----------|
| `Cannot find a valid font for the family Sans` | 容器内无字体 | 安装 `font-noto-cjk`（见 第 26 篇 8.1） |
| `Filter overlay has an unconnected output` | 滤镜图标签未闭合 | 检查 `[tag]` 是否配对使用 |
| `Impossible to convert between the formats` | 滤镜间像素格式不兼容 | 中间插入 `format=yuv420p` 或 `format=rgba` |
| `Option 'fontfile' not found` | drawtext 未编译进 freetype | `ffmpeg -filters \| grep drawtext` 确认 |
| `Padded dimensions cannot be smaller than input` | pad 参数小于输入尺寸 | 先 scale 再 pad，检查表达式 |
| `Buffer queue overflow, dropping` | 多路输入速率不匹配 | 检查各路是否都在正常产出帧 |

### 2.4 输出与资源错误

| 错误信息 | 根因 | 修复方案 |
|----------|------|----------|
| `No space left on device` | 磁盘满 | 清理临时文件；加磁盘水位监控 |
| `Cannot allocate memory` | 内存不足 | 降并发；避免 `reverse` 等全量载入操作 |
| `Too many open files` | fd 耗尽 | 提高 `ulimit -n`；检查是否漏关 pipe |
| `Device or resource busy` | GPU/设备被占满 | 排队等待；降低并发 |
| `Broken pipe` | 下游（管道读端）已关闭 | 检查 Go 侧是否提前关了 stdout |
| `Output file is empty, nothing was encoded` | 滤镜图无输出 / 时间范围为空 | 检查 `-ss`/`-t` 是否超出源时长 |

### 2.5 快速诊断命令

```bash
# 1. 只检查文件是否可解码（不产出，最快）
ffmpeg -v error -i input.mp4 -f null - 2>error.log
# error.log 为空 = 文件健康

# 2. 查看完整流信息
ffprobe -v error -show_format -show_streams -print_format json input.mp4

# 3. 检查是否有损坏帧
ffmpeg -v error -i input.mp4 -f null - 2>&1 | grep -i "error\|corrupt"

# 4. 确认某个编码器/滤镜可用
ffmpeg -hide_banner -encoders | grep -E "libx264|libx265|h264_nvenc"
ffmpeg -hide_banner -filters  | grep -E "drawtext|overlay|scale"

# 5. 用 debug 级别看参数如何被解析（排查参数没生效时）
ffmpeg -loglevel debug -i input.mp4 -c:v libx264 -crf 23 out.mp4 2>&1 | head -60
```

## 3. 性能瓶颈定位

### 3.1 用 speed 指标判断瓶颈类型

```
speed < 1.0x 时，先判断瓶颈在哪：

                 ┌──────────────────────┐
                 │  开始诊断             │
                 └──────────┬───────────┘
                            │
                 ┌──────────▼───────────┐
                 │  CPU 是否 100%？      │
                 └──────────┬───────────┘
                     是 ▼         否 ▼
            ┌──────────────┐  ┌──────────────────────┐
            │ CPU 瓶颈      │  │ iostat 查 I/O wait   │
            │ 见 3.2 节     │  └──────────┬───────────┘
            └──────────────┘       高 ▼         低 ▼
                                ┌────────┐  ┌────────────────┐
                                │ I/O    │  │ 可能是滤镜串行  │
                                │ 瓶颈   │  │ 或内存带宽     │
                                │ 见 3.3 │  │ 见 3.4 节      │
                                └────────┘  └────────────────┘
```

### 3.2 CPU 瓶颈排查与优化

```bash
# 1. 确认 CPU 是瓶颈
top -bn1 -p $(pgrep ffmpeg | tr '\n' ',') | grep -E "PID|ffmpeg"
# CPU% 接近 N×100（N = threads 数）说明 CPU 打满

# 2. 分析是哪个编码步骤最耗时
# 用 ffmpeg -benchmark 不输出文件，只跑编码，看纯编码耗时
ffmpeg -benchmark -i input.mp4 -c:v libx264 -crf 23 -preset veryslow -f null -
```

**CPU 优化选项对比**：

| 操作 | 耗时对比 | 画质影响 | 适用场景 |
|------|----------|----------|----------|
| `preset veryslow` → `medium` | 快 3~5x | CRF 模式画质基本无差 | 批量离线转码 |
| `preset medium` → `fast` | 快 1.5x | 轻微下降，几乎不可见 | 实时性要求高 |
| `-threads 0` → `-threads N` | 取决于 N | 无影响 | cgroup 限制场景 |
| 软件编码 → NVENC | 快 5~10x | 同码率下略低（可接受）| 有 GPU 时首选 |
| 软件编码 → VideoToolbox (macOS) | 快 3~8x | 与 NVENC 类似 | Mac/M 系芯片 |

```bash
# 切换到硬件编码（NVIDIA）
ffmpeg -i input.mp4 \
  -c:v h264_nvenc \
  -preset p4 \       # p1(最快,最差) ~ p7(最慢,最好)，推荐 p4~p5
  -rc vbr \
  -cq 23 \           # 对应软件编码的 CRF
  -b:v 0 \
  -c:a aac -b:a 128k \
  output.mp4

# 切换到 VideoToolbox（Apple Silicon）
ffmpeg -i input.mp4 \
  -c:v h264_videotoolbox \
  -b:v 4M \          # VideoToolbox 不支持 CRF，用目标码率
  -c:a aac -b:a 128k \
  output.mp4
```

### 3.3 I/O 瓶颈排查与优化

```bash
# 1. 确认是否 I/O 瓶颈
iostat -x 1 5
# %util 接近 100% = 磁盘 I/O 饱和
# await 高（> 20ms）= I/O 延迟大
# await 低但 %util 高 = 顺序 I/O 带宽打满

# 2. 量化磁盘读写速率
iotop -oad 1 -p $(pgrep ffmpeg)
```

**I/O 优化策略**：

```bash
# 策略 A：输入输出分盘（避免读写同一块磁盘）
# 输入从 SSD，输出到 HDD，临时文件到 tmpfs
ffmpeg -i /ssd/input.mp4 \
  -c:v libx264 -crf 23 \
  -y /hdd/output.mp4

# 策略 B：网络源时增大读取缓冲
ffmpeg -buffer_size 32M \
  -i "http://cdn.example.com/video.mp4" \
  output.mp4

# 策略 C：减少中间文件
# ❌ 错误：两步转码产生大临时文件
ffmpeg -i input.mp4 -c:v libx264 temp.mp4
ffmpeg -i temp.mp4 -vf "scale=720:480" output.mp4

# ✅ 正确：一条滤镜链
ffmpeg -i input.mp4 -vf "scale=720:480" -c:v libx264 output.mp4
```

### 3.4 滤镜链性能分析

```bash
# 开启 ffmpeg 的内置性能分析（8.0 起支持 -filter_stats）
ffmpeg -filter_stats -i input.mp4 \
  -vf "scale=1920:1080,unsharp=5:5:1,eq=contrast=1.2" \
  output.mp4 2>&1 | grep "Slices\|filter"

# 逐个添加滤镜，二分法定位慢的那个
# 基准：只做 scale
time ffmpeg -benchmark -i input.mp4 -vf "scale=1920:1080" -f null -

# 加 unsharp 后
time ffmpeg -benchmark -i input.mp4 -vf "scale=1920:1080,unsharp=5:5:1" -f null -
```

**常见高耗时滤镜**：

| 滤镜 | 耗时等级 | 替代方案 |
|------|----------|----------|
| `unsharp` | ⭐⭐⭐ | `eq` 调对比度更快 |
| `nlmeans`（降噪） | ⭐⭐⭐⭐⭐ | `hqdn3d` 快 10x，质量接近 |
| `reverse` / `areverse` | ⭐⭐⭐⭐ | 无替代，将整段载入内存 |
| `drawtext`（每帧渲染） | ⭐⭐⭐ | 批量生成时预渲染 overlay 图片 |
| `yadif`（去隔行，逐帧） | ⭐⭐⭐ | 来源已是逐行扫描则去掉此滤镜 |
| `scale` 高质量算法 `lanczos` | ⭐⭐⭐ | 改 `bilinear` 快 2x（轻微质量下降）|

## 4. 编码参数调优

### 4.1 CRF 选值与画质关系

CRF（Constant Rate Factor）是 H.264/H.265 最常用的质量控制参数：

```
H.264 CRF 范围：0（无损）~ 51（最差），默认 23
H.265 CRF 范围：0（无损）~ 51（最差），默认 28

视觉等效参考（同等主观质量）：
  H.264 CRF 23  ≈  H.265 CRF 28  ≈  VP9 CRF 33

实际使用区间：
  ≤ 17：几乎无损，文件极大（归档场景）
  18~22：高画质，肉眼难以区分（点播平台推荐）
  23~28：标准画质（CRF 23 是 libx264 默认值，是很好的出发点）
  29~34：明显有损，码率节省明显（低带宽场景）
  ≥ 35：明显块效应，不推荐用于正片

注意：CRF 每差 6，文件大小约差 2 倍
  CRF 23 → CRF 29：文件缩小约 50%，画质下降可感知
```

### 4.2 码率控制模式对比

```bash
# 模式 1：CRF（恒定画质，文件大小不确定）
# 适合：点播、归档、质量优先
ffmpeg -i input.mp4 -c:v libx264 -crf 23 -preset medium output.mp4

# 模式 2：目标码率 CBR（恒定码率）
# 适合：直播推流（带宽固定）
ffmpeg -i input.mp4 -c:v libx264 \
  -b:v 4M -minrate 4M -maxrate 4M -bufsize 8M \
  output.mp4

# 模式 3：目标码率 VBR（可变码率，更高效）
# 适合：存储优化，平均码率可控
ffmpeg -i input.mp4 -c:v libx264 \
  -b:v 4M -maxrate 6M -bufsize 8M \
  output.mp4

# 模式 4：双通道编码（two-pass VBR，最精确的码率控制）
# 适合：需要精确控制文件大小
ffmpeg -i input.mp4 -c:v libx264 -b:v 4M -pass 1 -f null -
ffmpeg -i input.mp4 -c:v libx264 -b:v 4M -pass 2 output.mp4
```

### 4.3 自适应码率（ABR）梯度规划

点播平台通常提供多个清晰度版本：

```bash
# 典型的多码率梯度（HLS ABR）
# 注意：宽高必须为偶数；码率根据内容类型（动画/电影/体育）适当调整

# 360p（移动省流）
ffmpeg -i input.mp4 -vf "scale=640:360" \
  -c:v libx264 -crf 28 -preset fast \
  -c:a aac -b:a 64k \
  360p.mp4

# 480p（标清）
ffmpeg -i input.mp4 -vf "scale=854:480" \
  -c:v libx264 -crf 26 -preset fast \
  -c:a aac -b:a 96k \
  480p.mp4

# 720p（高清）
ffmpeg -i input.mp4 -vf "scale=1280:720" \
  -c:v libx264 -crf 23 -preset medium \
  -c:a aac -b:a 128k \
  720p.mp4

# 1080p（全高清）
ffmpeg -i input.mp4 -vf "scale=1920:1080" \
  -c:v libx264 -crf 21 -preset medium \
  -c:a aac -b:a 192k \
  1080p.mp4
```

```bash
# ✅ 一条命令同时输出多分辨率（利用 FFmpeg 的 filter_complex 共享解码，更高效）
ffmpeg -i input.mp4 \
  -filter_complex "[0:v]split=3[v1][v2][v3]; \
    [v1]scale=1280:720[out720]; \
    [v2]scale=854:480[out480]; \
    [v3]scale=640:360[out360]" \
  -map "[out720]" -c:v libx264 -crf 23 720p.mp4 \
  -map "[out480]" -c:v libx264 -crf 26 480p.mp4 \
  -map "[out360]" -c:v libx264 -crf 28 360p.mp4 \
  -map 0:a -c:a aac -b:a 128k audio.m4a
# 优点：只解码一次，节省 ~40% CPU
```

### 4.4 音频参数调优

```bash
# AAC 码率参考（立体声）
#   64 kbps：语音内容（podcast、有声书）
#  128 kbps：通用音乐（绝大多数场景）
#  192 kbps：高质量音乐（区别人耳极限）
#  256 kbps：发烧级（与 192 差别极小）

# 声道处理
# 双声道 → 单声道（缩小约一半，语音内容合适）
ffmpeg -i input.mp4 -c:v copy -c:a aac -ac 1 -b:a 64k output.mp4

# 多声道 → 双声道（环绕声 → 普通立体声）
ffmpeg -i input.mp4 -c:v copy -c:a aac -ac 2 -b:a 128k output.mp4

# 音量标准化（EBU R128，适合平台统一音量）
ffmpeg -i input.mp4 -c:v copy \
  -af "loudnorm=I=-16:TP=-1.5:LRA=11" \
  -c:a aac -b:a 128k output.mp4
```

## 5. 日志分析技巧

### 5.1 开启详细日志级别

```bash
# 日志级别从低到高：quiet → panic → fatal → error → warning → info → verbose → debug → trace
# 默认 info，排查时用 warning 减少噪音，复杂问题用 debug

# 只看 warning 及以上
ffmpeg -loglevel warning -i input.mp4 -c:v libx264 output.mp4

# 详细模式，排查参数解析
ffmpeg -loglevel verbose -i input.mp4 -c:v libx264 output.mp4

# debug 级别，非常详细（会刷屏）
ffmpeg -loglevel debug -i input.mp4 -c:v libx264 output.mp4 2>&1 | head -100
```

### 5.2 日志保存与分析

```bash
# 保存完整 stderr 到文件（stdout 仍然可用）
ffmpeg -loglevel debug -i input.mp4 -c:v libx264 output.mp4 2>ffmpeg.log

# 实时过滤：只看 error 和 warning
ffmpeg -i input.mp4 -c:v libx264 output.mp4 2>&1 | grep -iE "error|warning|invalid"

# 统计 error 行数
ffmpeg -i input.mp4 -c:v libx264 -f null - 2>&1 | grep -ic "error"
```

```go
// FFmpegLogAnalyzer 分析 FFmpeg 输出日志，提取关键信息
type FFmpegLogAnalyzer struct {
	MaxErrors   int
	MaxWarnings int
}

type LogSummary struct {
	Errors    []string
	Warnings  []string
	FinalFPS  float64
	FinalSpeed float64
	HasCorruptFrames bool
}

// Analyze 分析 FFmpeg stderr 输出
func (a *FFmpegLogAnalyzer) Analyze(stderr string) LogSummary {
	var summary LogSummary
	lines := strings.Split(stderr, "\n")

	for _, line := range lines {
		lower := strings.ToLower(line)
		switch {
		case strings.Contains(lower, "error") && len(summary.Errors) < a.MaxErrors:
			summary.Errors = append(summary.Errors, strings.TrimSpace(line))
		case strings.Contains(lower, "warning") && len(summary.Warnings) < a.MaxWarnings:
			summary.Warnings = append(summary.Warnings, strings.TrimSpace(line))
		case strings.Contains(lower, "corrupt") || strings.Contains(lower, "damaged"):
			summary.HasCorruptFrames = true
		}
	}

	// 提取最后一行进度信息中的 fps 和 speed
	if idx := strings.LastIndex(stderr, "fps="); idx >= 0 {
		fmt.Sscanf(stderr[idx:], "fps=%f", &summary.FinalFPS)
	}
	if idx := strings.LastIndex(stderr, "speed="); idx >= 0 {
		var speedStr string
		fmt.Sscanf(stderr[idx:], "speed=%sx", &speedStr)
		fmt.Sscanf(speedStr, "%f", &summary.FinalSpeed)
	}
	return summary
}
```

## 6. 音视频不同步诊断

### 6.1 不同步的五类根因

```
类型 1：时间戳偏移（最常见）
  症状：整段视频音频始终领先/滞后固定时间
  原因：容器时间戳起始值不一致（音频从 0，视频从 0.5）
  修复：ffmpeg -i in.mp4 -itsoffset 0.5 -i in.mp4 [复杂处理] 或
        ffmpeg -i in.mp4 -avoid_negative_ts make_zero out.mp4

类型 2：帧率不匹配（拼接场景）
  症状：不同片段拼接后逐渐漂移
  原因：各片段帧率不一致（23.976/25/29.97 混合）
  修复：拼接前统一帧率，concat 前加 -r 参数

类型 3：音频重采样引入延迟
  症状：添加特效或变速后开始不同步
  原因：atempo/aresample 处理时引入缓冲延迟
  修复：在音频滤镜链末尾加 aresample=async=1

类型 4：直播推流中的积累漂移
  症状：运行数小时后越来越不同步
  原因：音视频编码线程速率不严格一致
  修复：推流时加 -use_wallclock_as_timestamps 1

类型 5：硬件解码器时间戳精度问题
  症状：使用 NVDEC/VideoToolbox 解码后不同步
  原因：部分硬件解码器时间戳精度低
  修复：切回软件解码；或加 -fps_mode cfr
```

## 7. 画质问题诊断

### 7.1 用客观指标代替肉眼判断

肉眼对比画质极不可靠——显示器、环境光、心理预期都会干扰判断。生产环境应该用客观指标：

| 指标 | 计算方式 | 取值范围 | 与主观感受的相关性 |
|------|----------|----------|-------------------|
| PSNR | 逐像素均方误差 | dB，越高越好 | 弱（对模糊不敏感）|
| SSIM | 结构相似度 | 0~1，越接近 1 越好 | 中等 |
| VMAF | Netflix 机器学习模型 | 0~100，越高越好 | **强**（最接近人眼）|

```bash
# 1. PSNR（最快，但相关性最弱）
ffmpeg -i original.mp4 -i encoded.mp4 \
  -lavfi "psnr" -f null - 2>&1 | grep "PSNR"
# 输出：PSNR y:42.35 u:45.12 v:45.88 average:43.21
# 参考：> 40 dB 优秀，35~40 良好，< 30 明显失真

# 2. SSIM
ffmpeg -i original.mp4 -i encoded.mp4 \
  -lavfi "ssim" -f null - 2>&1 | grep "SSIM"
# 参考：> 0.98 几乎无损，0.95~0.98 良好，< 0.90 明显下降

# 3. VMAF（最准，需要 libvmaf 支持）
ffmpeg -i encoded.mp4 -i original.mp4 \
  -lavfi "libvmaf=model=version=vmaf_v0.6.1:log_path=vmaf.json:log_fmt=json" \
  -f null -
# 参考：> 93 视觉无损，80~93 良好，60~80 可接受，< 60 明显下降

# 4. 一次跑三个指标（注意输入顺序：distorted 在前，reference 在后）
ffmpeg -i encoded.mp4 -i original.mp4 \
  -lavfi "[0:v][1:v]libvmaf=n_threads=4:log_path=vmaf.json" \
  -f null -
```

> **输入顺序容易搞错**：`libvmaf` 要求第一个输入是待测文件（distorted），第二个是参考文件（reference）。搞反了分数会异常偏低。`psnr`/`ssim` 则是第一个输入为待测、第二个为参考。

### 7.2 常见画质问题与成因

| 症状 | 成因 | 修复方案 |
|------|------|----------|
| 大面积块效应（马赛克） | 码率过低 / CRF 过高 | 降低 CRF 或提高目标码率 |
| 画面模糊、细节丢失 | 缩放算法差 / 过度降噪 | 用 `scale=...:flags=lanczos`；减弱降噪强度 |
| 渐变区域出现色带 | 8bit 色深不足 | 输出 10bit：`-pix_fmt yuv420p10le -profile:v main10` |
| 颜色偏灰/发白 | 色彩空间标记丢失 | 显式指定：`-colorspace bt709 -color_primaries bt709 -color_trc bt709` |
| 快速运动画面拖影 | GOP 太长 / B 帧过多 | 缩短 `-g`，降低 `-bf` |
| 边缘出现锯齿 | 缩放未做抗锯齿 | `scale` 加 `flags=lanczos` 或先轻微模糊再缩放 |
| 亮度整体偏暗 | HDR 转 SDR 未做 tone mapping | 见 HDR 处理章节，用 `zscale`+`tonemap` |
| 画面上下有黑边闪烁 | 隔行扫描未处理 | 加 `-vf yadif=1` 去隔行 |

```go
// ProcessGuard 定期清理僵死的 FFmpeg 进程
type ProcessGuard struct {
	maxLifetime time.Duration
	tracked     sync.Map // pid -> startTime
}

// Track 记录新启动的进程
func (g *ProcessGuard) Track(pid int) {
	g.tracked.Store(pid, time.Now())
}

// Untrack 进程正常退出时移除
func (g *ProcessGuard) Untrack(pid int) {
	g.tracked.Delete(pid)
}

// Sweep 扫描并清理超时进程（定时任务调用）
func (g *ProcessGuard) Sweep() {
	now := time.Now()
	g.tracked.Range(func(k, v any) bool {
		pid := k.(int)
		start := v.(time.Time)

		if now.Sub(start) < g.maxLifetime {
			return true
		}

		proc, err := os.FindProcess(pid)
		if err != nil {
			g.tracked.Delete(pid)
			return true
		}

		// 先尝试优雅终止
		if err := proc.Signal(syscall.SIGTERM); err != nil {
			g.tracked.Delete(pid)
			return true
		}
		log.Warn().Int("pid", pid).Dur("lifetime", now.Sub(start)).Msg("清理超时 FFmpeg 进程")

		time.Sleep(5 * time.Second)
		_ = proc.Kill()
		g.tracked.Delete(pid)
		return true
	})
}
```

```go
// ❌ 泄漏：StdoutPipe 未读完就返回，pipe fd 不释放
func badRun(cmd *exec.Cmd) error {
	stdout, _ := cmd.StdoutPipe()
	if err := cmd.Start(); err != nil {
		return err
	}
	// 只读一行就返回，剩余数据堵在 pipe 里，cmd.Wait() 永不返回
	buf := make([]byte, 128)
	_, _ = stdout.Read(buf)
	return cmd.Wait() // 死锁！
}

// ✅ 正确：读完所有输出再 Wait
func goodRun(cmd *exec.Cmd) error {
	stdout, err := cmd.StdoutPipe()
	if err != nil {
		return fmt.Errorf("创建 stdout pipe 失败: %w", err)
	}
	if err := cmd.Start(); err != nil {
		return fmt.Errorf("启动进程失败: %w", err)
	}

	// 必须读到 EOF（或在 goroutine 中持续读）
	done := make(chan struct{})
	go func() {
		defer close(done)
		_, _ = io.Copy(io.Discard, stdout)
	}()

	<-done              // 等读完
	return cmd.Wait()   // 再 Wait，避免死锁
}
```

| 现象 | 根因 | 排查命令 | 修复方案 |
|------|------|----------|----------|
| `speed` 长期 < 1.0x | CPU 不足或 preset 过慢 | `top` 看 CPU%；`-benchmark` 测纯编码 | 调 preset 到 medium/fast；或上硬件编码 |
| CPU 未满但转码慢 | I/O 瓶颈 | `iostat -x 1`，看 `%util` 和 `await` | 输入输出分盘；临时文件放 tmpfs |
| CPU 未满、I/O 也不高 | 滤镜链串行瓶颈 | 二分法逐个加滤镜测耗时 | 替换慢滤镜；开 `-filter_threads` |
| 转码结果比源文件还大 | CRF 过低或源本身已高压缩 | 对比源码率 `ffprobe -show_format` | 提高 CRF；或对已压缩源直接 `-c copy` |
| 输出有色带（渐变不平滑） | 8bit 色深不足 | `ffprobe` 查 `pix_fmt` | 输出 10bit：`-pix_fmt yuv420p10le` |
| 转码后颜色发灰 | 色彩空间元数据丢失 | `ffprobe -show_streams \| grep color` | 显式指定 `-colorspace/-color_primaries/-color_trc` |
| 音频比视频快/慢固定值 | 时间戳起始偏移 | 对比音视频 `start_time` | `-itsoffset` 反向补偿 |
| 长时间直播后越来越不同步 | 编码线程速率漂移 | 对比首尾时间戳差值 | 加 `-use_wallclock_as_timestamps 1` |
| ffmpeg 进程数远超任务数 | 进程泄漏 | `ps aux \| grep -c "[f]fmpeg"` | 补 `GracefulKill`；加 ProcessGuard 定期清扫 |
| Go 服务 fd 持续增长 | StdoutPipe 未读到 EOF | `ls /proc/PID/fd \| wc -l` | 用 goroutine `io.Copy` 读完再 `Wait()` |
| goroutine 数持续增长 | watchdog / 进度解析未退出 | `/debug/pprof/goroutine?debug=1` | 显式 `stopCh`；channel 带 buffer |
| `cmd.Wait()` 永久阻塞 | pipe 缓冲满，进程写不进去 | `cat /proc/PID/wchan` | 必须持续消费 stdout/stderr |
| VMAF 分数异常低（< 20） | 输入顺序搞反了 | 确认第一个输入是待测文件 | `-i encoded.mp4 -i original.mp4` |

## 10. 本章总结

**核心要点**：

1. **方法论**：先量化，再优化。`speed` 是最关键的单一指标——判断瓶颈在 CPU（CPU% 打满）、I/O（`%util` 高）还是滤镜（两者都不高）。

2. **错误速查**：错误信息按输入 / 编解码 / 滤镜 / 资源四类归档。`ffmpeg -v error -i in.mp4 -f null -` 是最快的健康检查——stderr 为空即文件健康。

3. **CPU 优化**：`veryslow → medium` 通常快 3~5 倍而 CRF 模式下画质几乎无差，是性价比最高的一步。有 GPU 时 NVENC 可再快 5~10 倍。

4. **画质评估**：**不要靠肉眼**。PSNR 最快但相关性弱，VMAF 最接近人眼感受。注意 `libvmaf` 的输入顺序是「待测在前，参考在后」。

5. **不同步诊断**：五类根因（时间戳偏移、帧率不匹配、重采样延迟、直播漂移、硬件解码精度）。量化手段是对比音视频 `start_time` 和 `duration`，差值 > 0.2 秒即可感知。

6. **泄漏排查**：FFmpeg 进程泄漏用 `ps aux | grep -c "[f]fmpeg"` 对比活跃任务数；Go 侧 fd 泄漏几乎都是 `StdoutPipe` 没读到 EOF 就 `Wait()` 导致的死锁。

**排查决策树**：

```
转码出问题
  │
  ├─ 报错退出？
  │    └─ 查第 2 节速查表 → 按输入/编解码/滤镜/资源分类定位
  │
  ├─ 能跑但很慢？
  │    ├─ CPU 100% → 降 preset / 上硬件编码 / 调 -threads
  │    ├─ I/O wait 高 → 输入输出分盘 / tmpfs / 减少中间文件
  │    └─ 都不高 → 二分法定位慢滤镜
  │
  ├─ 能跑但画质差？
  │    └─ 先用 VMAF 量化 → 查第 7.2 节症状表 → 针对性调参
  │
  ├─ 音视频不同步？
  │    └─ 对比 start_time/duration → 查第 6.1 节五类根因
  │
  └─ 服务层异常（内存/fd/进程数增长）？
       └─ pprof + /proc 排查 → 查第 8 节泄漏点表
```

## 术语表

| 术语 | 说明 |
|------|------|
| `speed` | FFmpeg 输出的实时倍速，1.0x 表示转码速度等于视频播放速度 |
| CRF | Constant Rate Factor，恒定质量因子，0~51，越小质量越高文件越大 |
| preset | libx264/libx265 的速度-质量预设，从 ultrafast 到 veryslow |
| PSNR | 峰值信噪比，逐像素误差指标，单位 dB，与主观感受相关性较弱 |
| SSIM | 结构相似度，0~1，考虑了图像结构信息，相关性中等 |
| VMAF | Netflix 开源的视频质量评估模型，0~100，与人眼感受相关性最强 |
| `-benchmark` | FFmpeg 参数，输出编码消耗的 utime/stime/rtime，用于纯性能测量 |
| `-f null -` | 输出丢弃，只跑解码/编码流程，用于健康检查和性能测试 |
| 色带（banding） | 渐变区域出现的阶梯状色阶，8bit 色深不足时明显 |
| `itsoffset` | 输入时间戳偏移，用于修正音视频不同步 |
| `aresample=async` | 音频重采样时自动补偿时间戳漂移 |
| GOP | Group of Pictures，两个关键帧之间的帧组，长度由 `-g` 控制 |
| pprof | Go 内置性能分析工具，可采集堆内存、goroutine、CPU profile |
| `/proc/PID/wchan` | Linux 中显示进程在内核中的等待点，用于判断是否卡在 I/O |
