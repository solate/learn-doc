### 模块 1：基础入门（第 1-5 篇）

#### 第 1 篇：FFmpeg 全景与架构解析

- FFmpeg 是什么？三大工具定位：ffmpeg（转码引擎）/ ffprobe（分析工具）/ ffplay（播放器）
- 六大核心库分工：
  - libavformat：封装/解封装（理解各种容器格式）
  - libavcodec：编码/解码（理解各种编解码器）
  - libavfilter：滤镜处理（缩放/水印/拼接）
  - libavutil：公共工具（数据结构/数学运算）
  - libswscale：像素格式转换（YUV/RGB）
  - libswresample：音频重采样（采样率/声道数）
- 处理管道五阶段详解（每个阶段的职责和输入输出）：
  - Demux（解封装）：从容器文件中拆出各条 Stream
  - Decode（解码）：将压缩数据解压为原始帧（YUV 视频 / PCM 音频）
  - Filter（滤镜）：处理原始帧（缩放、水印、拼接等）
  - Encode（编码）：将原始帧重新压缩
  - Mux（封装）：将多条 Stream 打包进容器
- 为什么 `-c copy` 这么快？跳过了哪三步？
- Stream、Codec、Container 的关系（容器 ≠ 编码格式）
- FFmpeg 生态：libav 项目分叉历史、为什么有两套 API
- 动手实践：安装 FFmpeg 8.0，用 ffprobe 分析一个视频文件

#### 第 3 篇：ffprobe 流信息深度分析

- 输出格式：默认文本 vs `-print_format json` vs `-print_format flat`
- 分析流信息（`-show_streams`）：
  - 视频流：codec_name、width/height、r_frame_rate、bit_rate、pix_fmt

- 分析容器信息（`-show_format`）：

#### 第 4 篇：命令行语法完全解析

- FFmpeg 命令的基本结构：`ffmpeg [全局选项] [输入选项] -i 输入 [输出选项] 输出`
- 核心规则：参数顺序决定作用对象（`-i` 前作用于输入，`-i` 后作用于输出）
- 全局选项（任意位置有效）：
  - `-y`（覆盖输出）、`-n`（不覆盖）、`-v`（日志级别）
  - `-threads`（线程数）、`-progress`（进度输出）
- 输入选项（必须紧跟 `-i` 前面）：
  - `-ss`（输入 seek，快速跳转）、`-t`（输入时长）
  - `-f`（强制输入格式）、`-r`（强制输入帧率）
  - `-rtsp_transport tcp`（RTSP 传输方式）
- 输出选项（紧跟输出文件前面）：
  - `-ss`（输出 seek，精确但慢）vs 输入 seek 的区别
  - `-t`（输出时长）、`-to`（输出结束时间点）
  - `-c:v`（视频编码器）、`-c:a`（音频编码器）、`-c copy`（流复制）
- `-map` 流选择详解：
  - 默认行为：自动选最佳流（坑点）
  - `-map 0:v:0`（第 0 个输入的第 0 条视频流）
  - `-map 0:a:1`（选第二音轨）
  - `-map -0:s`（排除字幕流）
  - 多输入合并：`-map 0:v:0 -map 1:a:0`（从两个文件取视频和音频）
- 多输出文件：一次命令生成多个输出（节省解码时间）
- 日志级别：quiet/error/warning/info/verbose/debug（生产环境用 warning）
- 进度输出解析：`-progress /dev/stdout` 输出机器可读格式
- 动手实践：用 `-map` 从一个视频提取多音轨，分别输出

#### 第 5 篇：转封装与流复制（不重编码）

- 什么是转封装（Remux）：只换容器格式，不重新编解码
- `-c copy` 的工作原理：数据包直接从解封装传到封装，跳过解码/滤镜/编码
- 常见转封装场景：
  - FLV → MP4（直播录制后转存）
  - MP4 → MKV（保留多音轨/字幕）
  - TS → MP4（HLS 分片转点播）
  - MOV → MP4（Mac 录屏后转换）
- MP4 faststart：`-movflags faststart` 将 moov box 移到文件头，支持边下边播
- fMP4（Fragmented MP4）：流媒体友好格式，`-movflags frag_keyframe+empty_moov`
- 常见报错与解决：
  - "Non monotonous DTS" 时间戳错乱：`-max_interleave_delta 0`
  - "Discarding invalid packet" 丢包：容器格式不兼容
  - 音视频不同步：先 decode 修复时间戳再 mux
- H.265 in MP4 vs H.265 in MKV：兼容性差异
- 章节（chapters）保留：`-map_chapters 0`
- 动手实践：FLV 批量转 MP4，同时添加 faststart，对比文件大小和首帧延迟


### 模块 2：编解码核心（第 6-11 篇）

#### 第 6 篇：H.264 转码参数详解

- libx264 是什么：FFmpeg 调用的外部 H.264 编码库，工业级最稳定
- 质量控制方式三选一（不要混用）：
  - CRF（Constant Rate Factor）：`-crf 0-51`，23 是默认值，18 是视觉无损
  - ABR（Average Bitrate）：`-b:v 2M`，指定平均码率
  - CBR（Constant Bitrate）：`-b:v 2M -maxrate 2M -bufsize 4M`，直播必须用
- preset 速度 vs 质量权衡：ultrafast/superfast/veryfast/faster/fast/medium/slow/slower/veryslow
  - 相同 CRF 下，越慢 preset 文件越小（CPU 换体积）
  - 直播用 veryfast/faster，点播用 medium/slow
- tune 场景优化：film/animation/grain/stillimage/fastdecode/zerolatency
  - `zerolatency`：直播/推流必加（禁用 B 帧，减少延迟）
- profile 和 level：
  - `baseline`：兼容性最好（老设备/旧浏览器），不支持 B 帧
  - `main`：平衡（手机/平板推荐）
  - `high`：最高压缩（PC 点播推荐）
  - level：`4.1` 是 1080p 30fps 的标准，`5.1` 支持 4K
- 关键帧（I帧）控制：
  - `-g`（GOP 大小）：直播用 `-g 60`（2秒关键帧）
  - `-keyint_min`（最小关键帧间隔）
  - `-force_key_frames "expr:gte(t,n_forced*2)"`（强制每2秒一个关键帧）
- 参考帧 `-refs`：越多压缩率越高，解码越慢
- 两遍编码（2-pass）：第一遍分析，第二遍精确控制码率
- 实用命令合集：点播转码、直播转码、视频监控低码率
- 动手实践：相同内容用不同 CRF/preset 转码，对比文件大小和 PSNR/SSIM 质量指标

#### 第 7 篇：H.265/AV1/VVC 编码器全景与选型

- H.265（HEVC）相比 H.264 的优势：相同质量体积减半
- libx265 编码器：参数与 libx264 类似，但 CRF 建议值是 28（等效 x264 的 23）
- x265 的 preset 更耗时：medium 约等于 x264 的 slow
- H.265 专利问题：HEVC Advance/MPEG LA 专利池，播放端需要授权
  - Dell/HP 曾默认禁用硬件 H.265 解码（2018年事件）
  - 2026年现状：浏览器支持 H.265 仍需特殊处理（Safari 支持，Chrome 部分支持）
- AV1 开源免专利：Alliance for Open Media（Google/Apple/Netflix/Meta 等共同制定）
- AV1 编码器三选一：
  - `libaom-av1`：AOMedia 参考实现，质量最好，速度极慢（比 x264 慢 20-50倍）
  - `libsvtav1`：Intel 主导的快速实现，速度 3-5 倍于 libaom，质量接近
  - `rav1e`：Xiph/Mozilla 实现，Rust 编写，目前不推荐生产
- SVT-AV1 命令示例：`-c:v libsvtav1 -crf 35 -preset 7`（preset 0-13，数字越大越快）
- AV1 vs H.265 实测对比：相同质量 AV1 体积更小 10-20%，但编码速度更慢
- 硬件 AV1 编码：NVENC（RTX 40 系+）、Intel Arc（VAAPI）、Apple Silicon（VideoToolbox）
- **VVC/H.266 —— 下一代编码标准**（2026 年前沿）：
  - 2020 年 ITU-T 标准化，比 H.265 再减 50% 体积（相同质量）
  - FFmpeg 8.0 实验性支持 `libvvenc`（编码）/ `libvvdec`（解码）
  - 编码示例：`-c:v libvvenc -qp 32 output.mp4`
  - 当前限制：编码极慢（约为 H.265 的 1/10 速度），播放器支持有限
  - 适合场景：超长期存档、4K/8K 内容分发带宽敏感场景
  - 2026 年硬件支持：部分 ARM SoC（移动端）已有硬件解码，PC 端 GPU 尚在推进
- **VP9**（Google，YouTube 主力格式）：
  - `libvpx-vp9 -crf 33 -b:v 0`（恒定质量模式）
  - 与 AV1 同属 AOMedia 生态，逐步被 AV1 替代
  - 浏览器兼容性极好（Chrome/Firefox/Edge 全支持）
- 选型决策树（2026 年版）：
  - 兼容性优先（老设备/老浏览器）→ H.264
  - 存储/带宽成本优先 + CDN 分发 → H.265（Safari）或 AV1（Chrome/Firefox）
  - 实时推流 → H.264/H.265（AV1 实时编码需高端 GPU）
  - 长期存档（10年+）→ AV1 或 VVC（无专利问题）
  - 学术研究/实验性质 → VVC
- 动手实践：同一段视频用 H.264/H.265/AV1/VP9 转码，记录编码时间/文件大小/主观质量，制作对比表

#### 第 8 篇：码率控制深度解析

- 为什么码率控制很重要：直播和点播有截然不同的需求
- 三种码率控制模式详解：
  - **CRF（Constant Rate Factor）**：以感知质量为目标，码率随内容复杂度波动
    - 优点：简单，质量稳定；缺点：无法预估文件大小
    - 适合：点播转码、本地存储
  - **VBR（Variable Bitrate）**：设置目标码率，允许浮动
    - `-b:v 2M` + `-bufsize 4M`：目标 2Mbps，缓冲区 4Mb
  - **CBR（Constant Bitrate）**：严格恒定码率
    - `-b:v 2M -maxrate 2M -minrate 2M -bufsize 2M`
    - 适合：直播推流、带宽受限场景（如监控系统）
- ABR（Average Bitrate）：`-b:v 2M` 不加 maxrate，实际是 VBR 的一种
- 两遍编码（2-pass encoding）：
  - 第一遍：`-pass 1 -an -f null /dev/null`（分析，不输出）
  - 第二遍：`-pass 2 -b:v 2M output.mp4`（精确码率控制）
  - 优缺点：体积精确但耗时翻倍，适合点播预处理
- 直播码率控制实践：
  - 为什么直播必须 CBR：推流服务器缓冲区大小固定
  - `-g 60 -tune zerolatency` 配合 CBR
  - VBV（Video Buffering Verifier）参数：bufsize 设为 maxrate 的 2 倍
- 码率阶梯设计（ABR 自适应）：
  - 1080p：6Mbps / 4Mbps / 2Mbps（三档）
  - 720p：3Mbps / 2Mbps / 1Mbps
  - 根据 Netflix/YouTube 公开的编码标准
- VMAF 质量评估：Netflix 开源的感知质量指标，比 PSNR 更接近人眼
- 动手实践：实测 CRF/VBR/CBR 三种模式，比较同码率下的画质和码率曲线

#### 第 9 篇：音频处理完全指南

- 音频基础：采样率（8/16/44.1/48kHz）、位深（16/24/32bit）、声道数（单声道/立体声/5.1）
- 主流音频编码格式：
  - AAC：HLS/DASH/MP4 标配，兼容性最好；Profile：LC/HE-AAC/HE-AACv2
  - Opus：WebRTC 首选，开源免费，低延迟，8-128kbps 全场景
  - MP3：遗留格式，带宽效率低于 AAC，但兼容性极好
  - FLAC：无损压缩，本地存储用
- 常用音频转码：
  - `-c:a aac -b:a 128k`（标准 AAC）
  - `-c:a libopus -b:a 64k`（Opus，同等质量 AAC 一半码率）
  - `-c:a libmp3lame -q:a 2`（MP3 VBR）
- 音频重采样：`-ar 48000`（设置采样率）、`-ac 2`（设置声道数）
  - 视频会议需要 48kHz；电话质量 8kHz；CD 质量 44.1kHz
- 声道映射：
  - 5.1 → 立体声：`-ac 2` 或 `-af "pan=stereo|c0=FC+0.707*FL+0.707*BL|c1=FC+0.707*FR+0.707*BR"`
  - 多音轨选择：`-map 0:a:0`（只保留第一音轨）
- 音量处理：
  - 音量检测：`-af loudnorm=print_format=json -f null /dev/null`
  - 音量归一化（EBU R128）：`-af loudnorm=I=-23:TP=-1.5:LRA=11`
  - 简单音量调整：`-af volume=2.0`（放大2倍）或 `volume=-10dB`
- 混音：两路音频合并 `-filter_complex "[0:a][1:a]amix=inputs=2:duration=first"`
- 音频提取：`-vn -c:a copy output.aac`（从视频中提取音频，不重编码）
- 动手实践：将一个视频的音频归一化到 -23 LUFS（播客/视频平台标准）

#### 第 10 篇：硬件加速完全指南

- 为什么需要硬件加速：1080p H.265 软编需要 4-8 核 CPU，而 NVENC 只占 GPU 5%
- 硬件加速架构：
  - 硬件解码（hwdecode）：节省解码 CPU，适合多路同时解码
  - 硬件编码（hwencode）：速度快 5-10 倍，节省 CPU 用于其他业务
  - 硬件滤镜（hwfilter）：缩放等操作在 GPU 上直接完成，避免内存拷贝
- 四大平台硬件加速：

  **NVIDIA NVENC/NVDEC**（最常见，适合服务器）
  - 解码：`-hwaccel cuda -hwaccel_output_format cuda`
  - 编码：`-c:v h264_nvenc -cq 23`（`-cq` 相当于 CRF）
  - H.265：`-c:v hevc_nvenc`
  - AV1：`-c:v av1_nvenc`（需要 RTX 40 系）
  - 注意：NVENC 有并发会话数限制（消费级 GPU 最多 3 路，专业卡无限制）

  **Intel QSV**（服务器 CPU 集成显卡，省钱）
  - 解码：`-hwaccel qsv -c:v h264_qsv`
  - 编码：`-c:v h264_qsv -global_quality 23`
  - H.265/AV1：`-c:v hevc_qsv` / `-c:v av1_qsv`（需要 Arc 显卡）

  **Apple VideoToolbox**（Mac 开发机，M 系列芯片）
  - 解码：`-hwaccel videotoolbox`
  - 编码：`-c:v h264_videotoolbox -q:v 65`
  - H.265：`-c:v hevc_videotoolbox`
  - 注意：`-q:v` 是质量参数（0-100，65 ≈ CRF 23），不是 CRF

  **VAAPI**（Linux，Intel/AMD GPU，开源栈）
  - 需要 `/dev/dri/renderD128`
  - `-hwaccel vaapi -vaapi_device /dev/dri/renderD128 -hwaccel_output_format vaapi`
  - 编码：`-c:v h264_vaapi -qp 23`

- Vulkan（FFmpeg 8.0 新增）：
  - 跨平台 GPU 计算，主要用于复杂滤镜加速（非编解码）
  - FFv1 编码/解码、ProRes RAW 解码已可用 Vulkan

- 硬件滤镜（全程 GPU，避免内存拷贝）：
  ```
  # NVENC 全程 GPU（解码→缩放→编码）
  ffmpeg -hwaccel cuda -hwaccel_output_format cuda -i input.mp4 \
    -vf scale_cuda=1280:720 -c:v h264_nvenc -cq 23 output.mp4
  ```

- 坑点与排查：
  - "No CUDA capable device"：驱动未安装或 Docker 未挂载 GPU
  - 质量对比：硬件编码质量略低于软件编码（可接受），同 CRF 值
  - 并发限制：NVENC 消费卡 3 路限制可用 patch 解除（生产环境用专业卡）

- 动手实践：对比软编（libx264）vs NVENC（h264_nvenc）的速度和质量

#### 第 11 篇：视频质量评估与码率梯队设计

- 为什么需要质量评估：转码不是越小越好，需要量化质量损失
- **三大质量指标**：
  - PSNR（Peak Signal-to-Noise Ratio）：峰值信噪比，35dB 以上可接受，40dB+ 较好
  - SSIM（Structural Similarity Index）：结构相似度，0-1，0.95+ 较好
  - VMAF（Video Multimethod Assessment Fusion）：Netflix 开发，最接近人眼感知，60-95 分正常
  - 三者关系：PSNR 测像素差异、SSIM 测结构差异、VMAF 综合多维度感知
- 用 FFmpeg 测量质量指标：
  ```bash
  # PSNR（原始文件 vs 压缩文件）
  ffmpeg -i original.mp4 -i compressed.mp4 -lavfi psnr=stats_file=psnr.txt -f null -

  # SSIM
  ffmpeg -i original.mp4 -i compressed.mp4 -lavfi ssim=stats_file=ssim.txt -f null -

  # VMAF（需要编译时启用 --enable-libvmaf）
  ffmpeg -i original.mp4 -i compressed.mp4 \
    -lavfi "[0:v][1:v]libvmaf=log_path=vmaf.json:log_fmt=json" -f null -
  ```
- 解读 VMAF 报告：json 输出包含每帧分数、平均分、最低分
- **码率梯队设计（ABR 自适应比特率）**：
  - 什么是码率梯队：为不同网络条件准备多个清晰度/码率版本
  - Netflix 公开的编码标准（2026 年版参考）：
    | 分辨率 | 高码率 | 中码率 | 低码率 |
    |--------|--------|--------|--------|
    | 1080p  | 6 Mbps | 4 Mbps | 2 Mbps |
    | 720p   | 3 Mbps | 2 Mbps | 1 Mbps |
    | 480p   | 1.5 Mbps | 1 Mbps | 500 kbps |
    | 360p   | 800 kbps | 500 kbps | 300 kbps |
  - 关键帧间隔对 ABR 的影响：所有码率版本必须使用相同的关键帧间隔（通常 2 秒）
  - 音频处理：1080p/720p 用 192kbps AAC，480p 及以下用 128kbps
- **Per-Title Encoding（每片源内容自适应编码）**：
  - 静态画面（幻灯片类）：相同质量码率可以更低
  - 高动态场景（体育赛事）：同质量需要更高码率
  - Netflix/YouTube 都在使用内容感知编码
  - FFmpeg 实现：先用 CRF 模式测量，再确定目标码率
- **2-pass 精确码率控制**：
  - 第一遍（分析）：`-pass 1 -an -f null /dev/null`
  - 第二遍（编码）：`-pass 2 -b:v 4M output.mp4`
  - 优势：文件大小精确可控（误差 < 5%）
  - 劣势：编码时间翻倍，适合 VOD 而非直播
- 质量评估工作流程：
  - 步骤1：用不同 CRF 值转码（18/20/23/26/28）
  - 步骤2：FFmpeg 批量测量 VMAF 分数
  - 步骤3：绘制 VMAF-码率曲线
  - 步骤4：选择 VMAF≥90 对应的最低码率
- 动手实践：写脚本批量评估不同 CRF 值下的 VMAF 分数，输出对比报告


### 模块 3：滤镜系统（第 12-15 篇）

#### 第 12 篇：滤镜系统与滤镜图语法

- 什么是滤镜（Filter）：在解码和编码之间处理原始帧（像素/音频样本）
- `-vf` vs `-af` vs `-filter_complex`：
  - `-vf`：简单视频滤镜（单输入单输出）
  - `-af`：简单音频滤镜
  - `-filter_complex`：复杂滤镜图（多输入多输出、分支合并）
- 滤镜链（Filter Chain）：`-vf "scale=1280:720,unsharp"`（逗号分隔，顺序执行）
- 滤镜图（Filter Graph）语法：
  - **标签（Label）**：`[in]scale=1280:720[scaled]`
  - **输入流**：默认 `[0:v]`，显式 `[1:a]`
  - **分支**：一个输出分两路 `[in]split[a][b]`
  - **合并**：两路输入合一路 `[a][b]overlay[out]`
- 常用视频滤镜速查：
  - `scale`：缩放
  - `crop`：裁剪
  - `overlay`：叠加（水印）
  - `pad`：填充（加黑边）
  - `setpts`：调整时间戳（变速）
  - `fps`：改变帧率
  - `drawtext`：添加文字
  - `subtitles`：嵌入字幕
- 常用音频滤镜：
  - `volume`：音量
  - `atempo`：变速
  - `adelay`：延迟
  - `amix`：混音
  - `loudnorm`：响度归一化
- filter_complex 典型模式：
  ```
  # 两输入一输出（画中画）
  -filter_complex "[0:v][1:v]overlay=W-w-10:H-h-10[out]" -map "[out]"
  
  # 分支后各自处理
  -filter_complex "[0:v]split[a][b]; [a]scale=1920:1080[c]; [b]scale=1280:720[d]"
  ```
- 时间戳问题：滤镜会重新计算 PTS，可能导致音视频不同步（需要 `-vsync` 调整）
- 动手实践：用 filter_complex 实现画中画（主画面 + 小窗预览）

#### 第 13 篇：视频滤镜实战

- 缩放（scale）：
  - 基础：`scale=1280:720`
  - 保持宽高比：`scale=-2:720`（-2 自动计算为偶数）
  - 缩放算法选择：`scale=w=1280:h=720:flags=lanczos`（高质量）
  - 硬件缩放：`scale_cuda=1280:720`（NVENC）、`scale_vaapi=1280:720`
- 裁剪（crop）：
  - `crop=w:h:x:y`（从左上角 x,y 裁剪 w×h 区域）
  - 去除黑边：`crop=iw:ih-40:0:20`（去掉顶部 20px，底部 20px）
  - 动态裁剪：`crop=iw/2:ih/2:x='if(gte(t,5),iw/2,0)':y=0`（5秒后切换）
- 旋转（rotate/transpose）：
  - `transpose=1`（顺时针 90°）
  - `rotate=PI/4`（任意角度）
  - `hflip`（水平翻转）、`vflip`（垂直翻转）
- 水印（overlay）：
  - 基础：`-i video.mp4 -i logo.png -filter_complex "[0:v][1:v]overlay=10:10" output.mp4`
  - 右下角：`overlay=W-w-10:H-h-10`
  - 淡入淡出：`overlay=10:10:enable='between(t,0,5)'`（前5秒显示）
- 字幕（subtitles）：
  - 嵌入 ASS 字幕：`subtitles=subtitle.ass`
  - 动态文字：`drawtext=text='Time\: %{pts\:hms}':x=10:y=10:fontsize=24:fontcolor=white`
  - 滚动字幕：`drawtext=text='Breaking News':x='w-mod(t*100,w+tw)':y=h-40`
- 淡入淡出（fade）：
  - 淡入：`fade=in:0:30`（前 30 帧淡入）
  - 淡出：`fade=out:900:30`（从第 900 帧开始淡出）
- 色彩调整（eq/colorchannelmixer）：
  - 亮度/对比度：`eq=brightness=0.1:contrast=1.2`
  - 黑白：`hue=s=0`
  - 色温调整：`colorchannelmixer`
- 去隔行（yadif）：`yadif=1`（适合老电视信号）
- 稳定（deshake/vidstab）：`vidstabdetect` + `vidstabtransform` 两遍去抖
- 动手实践：给视频右下角加半透明水印，左上角加时间戳

#### 第 14 篇：时间戳、变速与音视频同步

- PTS（Presentation Time Stamp）vs DTS（Decode Time Stamp）：
  - PTS：播放时间（什么时候显示这一帧）
  - DTS：解码时间（什么时候解码这一帧）
  - 有 B 帧时 DTS ≠ PTS（B 帧依赖未来的 P 帧，需要提前解码）
- 时间基（Time Base）：`1/90000`（MPEG-TS）vs `1/1000`（毫秒）vs `1/12800`（音频）
- 视频变速（不改变音高）：
  - `setpts=0.5*PTS`（2 倍速）
  - `setpts=2*PTS`（0.5 倍速）
  - 注意：必须同时调整音频 `atempo=2.0`（音频不能超过 2 倍）
  - 超过 2 倍速需要链式：`atempo=2.0,atempo=2.0`（4 倍速）
- 音频变速（保持音高）：
  - `atempo=1.5`（加速 1.5 倍）
  - `atempo=0.5`（减速）
- 时间重映射（时间拉伸）：
  - 慢动作：`setpts=4*PTS,fps=30`（拍摄 120fps 转 30fps 慢动作）
- 音视频不同步修复：
  - 音频延迟：`-itsoffset 0.5 -i audio.aac`（音频延迟 0.5 秒）
  - 视频延迟：`-itsoffset -0.5 -i video.mp4`
  - 滤镜修复：`-af "adelay=500|500"`（音频延迟 500ms）
- 时间戳错乱修复：
  - `-vsync cfr`（Constant Frame Rate）：强制恒定帧率，FFmpeg 重新计算 PTS
  - `-fps_mode passthrough`（FFmpeg 6.0+）：保持原始时间戳
  - `-fflags +genpts`：强制重新生成 PTS
- 精确裁剪（避免黑屏/跳帧）：
  - 快速但不精确：`-ss 00:01:30 -i input.mp4 -t 10 -c copy output.mp4`
  - 精确但慢：`-i input.mp4 -ss 00:01:30 -t 10 -c:v libx264 output.mp4`
  - 混合方案：`-ss 00:01:20 -i input.mp4 -ss 10 -t 10`（接近关键帧快速 seek，然后精确裁剪）
- 动手实践：将一个 60fps 慢镜头视频（实际 30fps 内容）转为正常 30fps 播放

#### 第 15 篇：多路合成与画面拼接

- 九宫格多分屏（监控墙常用）：
  ```bash
  # 4 分屏（2×2）
  ffmpeg -i 1.mp4 -i 2.mp4 -i 3.mp4 -i 4.mp4 -filter_complex \
  "[0:v]scale=960:540[a]; [1:v]scale=960:540[b]; \
   [2:v]scale=960:540[c]; [3:v]scale=960:540[d]; \
   [a][b]hstack[top]; [c][d]hstack[bottom]; \
   [top][bottom]vstack[out]" \
  -map "[out]" -c:v libx264 -crf 23 output.mp4
  
  # 9 分屏（3×3）：用 xstack 滤镜
  -filter_complex \
  "[0:v][1:v][2:v][3:v][4:v][5:v][6:v][7:v][8:v] \
   xstack=inputs=9:layout=0_0|w0_0|w0+w1_0|0_h0|w0_h0|w0+w1_h0|0_h0+h1|w0_h0+h1|w0+w1_h0+h1[out]"
  ```
- 画中画（PiP）：
  - 右下角小窗：`overlay=W-w-10:H-h-10`
  - 多层叠加：`[0:v][1:v]overlay[tmp]; [tmp][2:v]overlay[out]`
- 视频拼接（concat）：
  - **文件级拼接**（不重编码）：`concat demuxer`
    ```bash
    # 创建文件列表
    echo "file 'video1.mp4'" > list.txt
    echo "file 'video2.mp4'" >> list.txt
    ffmpeg -f concat -safe 0 -i list.txt -c copy output.mp4
    ```
  - **流级拼接**（重编码）：`concat filter`
    ```bash
    ffmpeg -i 1.mp4 -i 2.mp4 -filter_complex \
    "[0:v][0:a][1:v][1:a]concat=n=2:v=1:a=1[outv][outa]" \
    -map "[outv]" -map "[outa]" output.mp4
    ```
- 左右分屏（对比）：`hstack=inputs=2`（水平拼接）
- 上下分屏：`vstack=inputs=2`（垂直拼接）
- 画面过渡效果（xfade）：
  - 淡入淡出过渡：`xfade=transition=fade:duration=1:offset=4`
  - 擦除过渡：`xfade=transition=wipeleft:duration=1`
- 绿幕抠图（chromakey）：
  - `chromakey=0x00ff00:0.3:0.2`（抠掉绿色背景）
  - 常用于虚拟演播室
- 实时合成优化：
  - 多路输入用 `-thread_queue_size 512` 避免丢帧
  - 多核并行：`-filter_complex_threads 4`

### 模块 4：流媒体应用（第 16-20 篇）

#### 第 16 篇：推流与拉流实战

- RTMP 推流（OBS 场景）：
  - 基础推流：`ffmpeg -re -i input.mp4 -c copy -f flv rtmp://server/live/stream`
  - `-re`（实时速度）：按视频帧率推送，不加会瞬间推完
  - 循环推流：`-stream_loop -1 -i input.mp4`
  - 断线重连：`-reconnect 1 -reconnect_streamed 1 -reconnect_delay_max 5`
- RTSP 拉流（摄像头接入）：
  - TCP 传输（穿透 NAT）：`-rtsp_transport tcp -i rtsp://cam/stream`
  - UDP 传输（低延迟）：`-rtsp_transport udp`
  - 认证：`rtsp://username:password@192.168.1.100:554/stream1`
  - 超时参数：`-timeout 5000000`（5 秒，单位微秒）
  - 缓冲优化：`-fflags nobuffer -flags low_delay`（降低延迟）
- SRT 推流（弱网环境）：
  - 推流端（Caller）：`-f mpegts srt://server:9000?mode=caller`
  - 服务端（Listener）：`-i srt://0.0.0.0:9000?mode=listener`
  - 延迟参数：`latency=200`（200ms 缓冲，越大越稳定但延迟越高）
  - 加密：`passphrase=mypassword`
- RTSP → RTMP 转推（摄像头推到直播平台）：
  ```bash
  ffmpeg -rtsp_transport tcp -i rtsp://cam/stream \
    -c:v copy -c:a aac -f flv rtmp://live.example.com/app/stream
  ```
- 多目标推流（一路推多个平台）：
  ```bash
  ffmpeg -re -i input.mp4 -c:v libx264 -c:a aac \
    -f flv rtmp://server1/live/stream1 \
    -f flv rtmp://server2/live/stream2
  ```
- UDP 推流（低延迟局域网）：
  - 推送：`-f mpegts udp://192.168.1.100:1234`
  - 接收：`-i udp://@:1234`
- 超时与重连策略：
  - `-stimeout 5000000`（连接超时）
  - `-rw_timeout 10000000`（读写超时）
  - Shell 脚本实现无限重连（while true + sleep）
- 常见错误排查：
  - "Connection refused"：端口未开或防火墙
  - "Invalid data found"：编码格式不兼容（如 RTMP 不支持 H.265，需 Enhanced RTMP）
  - "Packet queue full"：接收端处理不过来，增大缓冲或降码率
- 动手实践：用 FFmpeg 模拟 OBS 推流到 SRS，并用 VLC 播放验证延迟

#### 第 17 篇：HLS/DASH 切片生成与端到端实战

- HLS 基础概念回顾：Master Playlist + Media Playlist + 分片文件
- 单码率 HLS 生成（VOD）：
  ```bash
  ffmpeg -i input.mp4 -c:v libx264 -crf 23 -c:a aac \
    -f hls -hls_time 4 -hls_playlist_type vod \
    -hls_segment_type fmp4 -hls_segment_filename "seg_%03d.m4s" \
    output.m3u8
  ```
  - `-hls_time 4`：每 4 秒一个分片
  - `-hls_segment_type fmp4`：使用 fMP4（CMAF），不再用传统 TS
  - `-hls_playlist_type vod`：点播模式（EVENT 是直播结束后可回看，LIVE 是纯直播）
- 多码率 ABR（Adaptive Bitrate）：
  ```bash
  # 生成三档码率
  ffmpeg -i input.mp4 \
    -map 0:v -map 0:a -c:v libx264 -c:a aac -b:v 6M -s 1920x1080 -f hls -hls_segment_filename "1080p_%03d.m4s" 1080p.m3u8 \
    -map 0:v -map 0:a -c:v libx264 -c:a aac -b:v 3M -s 1280x720 -f hls -hls_segment_filename "720p_%03d.m4s" 720p.m3u8 \
    -map 0:v -map 0:a -c:v libx264 -c:a aac -b:v 1M -s 854x480 -f hls -hls_segment_filename "480p_%03d.m4s" 480p.m3u8
  
  # 手动创建 Master Playlist（master.m3u8）
  #EXTM3U
  #EXT-X-STREAM-INF:BANDWIDTH=6000000,RESOLUTION=1920x1080
  1080p.m3u8
  #EXT-X-STREAM-INF:BANDWIDTH=3000000,RESOLUTION=1280x720
  720p.m3u8
  #EXT-X-STREAM-INF:BANDWIDTH=1000000,RESOLUTION=854x480
  480p.m3u8
  ```
- FFmpeg 自动生成 Master Playlist（`-var_stream_map`）：
  ```bash
  ffmpeg -i input.mp4 \
    -filter_complex "[0:v]split=3[v1][v2][v3]; \
      [v1]scale=1920:1080[v1out]; \
      [v2]scale=1280:720[v2out]; \
      [v3]scale=854:480[v3out]" \
    -map "[v1out]" -c:v libx264 -b:v 6M -map 0:a -c:a aac \
    -map "[v2out]" -c:v libx264 -b:v 3M -map 0:a -c:a aac \
    -map "[v3out]" -c:v libx264 -b:v 1M -map 0:a -c:a aac \
    -f hls -var_stream_map "v:0,a:0 v:1,a:1 v:2,a:2" \
    -master_pl_name master.m3u8 \
    -hls_segment_filename "stream_%v_%03d.m4s" stream_%v.m3u8
  ```
- LL-HLS（Low-Latency HLS）：
  - `-hls_flags independent_segments`：独立分片
  - `-hls_segment_type fmp4`：必须用 fMP4
  - `-hls_time 1`：1 秒分片（传统 HLS 用 6-10 秒）
  - 结合 HTTP/2 Server Push 和 Blocking Playlist Reload 实现 2-3s 延迟
- DASH 生成：
  ```bash
  ffmpeg -i input.mp4 -c:v libx264 -c:a aac \
    -f dash -seg_duration 4 -use_template 1 -use_timeline 1 \
    -init_seg_name "init-\$RepresentationID\$.m4s" \
    -media_seg_name "chunk-\$RepresentationID\$-\$Number\$.m4s" \
    output.mpd
  ```
- 直播 HLS（滚动窗口）：
  - `-hls_list_size 5`：只保留最近 5 个分片的索引

#### 第 19 篇：低延迟与弱网优化

- 低延迟参数组合（直播/推流）：
  ```bash
  ffmpeg -re -i input.mp4 -c:v libx264 -tune zerolatency \
    -preset veryfast -g 30 -b:v 2M -maxrate 2M -bufsize 2M \
    -c:a aac -b:a 128k -f flv rtmp://server/live/stream
  ```
  - `-tune zerolatency`：禁用 B 帧，减少编码延迟
  - `-g 30`：1 秒关键帧（30fps）
  - CBR 码率控制（避免缓冲区波动）
- RTSP 拉流低延迟：
  ```bash
  ffmpeg -rtsp_transport tcp -fflags nobuffer -flags low_delay \
    -i rtsp://cam/stream -c copy output.mp4
  ```
  - `-fflags nobuffer`：禁用输入缓冲
  - `-flags low_delay`：低延迟模式
- 弱网优化（SRT 协议）：
  - 增大延迟缓冲：`latency=500`（500ms 缓冲，抗 25% 丢包）
  - FEC 前向纠错：`fec=row`（牺牲 10-20% 带宽换稳定）
  - 自适应码率：监控 SRT 统计（`srt-live-transmit` 工具）动态调整
- 丢帧策略（编码端跟不上）：
  - `-vsync drop`：丢弃重复帧
  - `-drop_pkts_on_overflow 1`：溢出时丢包而不是阻塞
- 延迟测量：
  - 端到端延迟 = 编码延迟 + 网络延迟 + 解码延迟 + 渲染延迟
  - 实测方法：屏幕录制自己的直播流，用秒表对比延迟
  - FFmpeg `-benchmark` 参数：测量编码速度
- UDP 推流极致低延迟（局域网监控）：
  ```bash
  # 发送端
  ffmpeg -re -i input.mp4 -c:v libx264 -tune zerolatency -preset ultrafast \
    -f mpegts udp://192.168.1.100:1234?pkt_size=1316
  
  # 接收端
  ffplay -fflags nobuffer -flags low_delay -framedrop udp://@:1234
  ```
- WebRTC 推流（WHIP 协议，200ms 延迟）：
  - FFmpeg 8.0 支持 WHIP：`-f whip https://server/whip/endpoint`
  - 需要配合支持 WHIP 的流媒体服务器（SRS 5.0+/MediaMTX）

### 模块 5：高级主题（第 21-23 篇）

#### 第 21 篇：HDR、色彩空间与 10-bit 编码

- **为什么色彩科学很重要**：错误的色彩空间转换会导致画面颜色偏差，这是最常见的"转码成功但颜色不对"问题
- **色彩空间基础**：
  - 色彩空间（Color Space）：BT.601（SD）、BT.709（HD）、BT.2020（4K HDR）
  - 传输特性（Transfer Characteristics）：Gamma 2.2（SDR）vs PQ/HLG（HDR）
  - 色域（Gamut）：BT.709 覆盖 35.9% sRGB，BT.2020 覆盖 75.8% 可见色域
- **常见坑：SDR 与 HDR 转换**
  ```bash
  # 错误：直接转码 HDR，会导致颜色严重失真
  ffmpeg -i hdr_video.mp4 -c:v libx264 sdr_wrong.mp4

  # 正确：Tone Mapping（色调映射）将 HDR 转为 SDR
  ffmpeg -i hdr_video.mp4 \
    -vf "zscale=t=linear:npl=100,format=gbrpf32le,zscale=p=bt709,tonemap=tonemap=hable:desat=0,zscale=t=bt709:m=bt709:r=tv,format=yuv420p" \
    -c:v libx264 -crf 23 sdr_correct.mp4
  ```
- **HDR 格式全解**：
  - HDR10：静态元数据（MaxCLL/MaxFALL），最常见，开放标准
  - HDR10+：动态元数据（每帧不同亮度映射），三星主导
  - Dolby Vision：动态元数据，专有标准，效果最好，Apple/Netflix 主力
  - HLG（Hybrid Log Gamma）：广播电视用，SDR 设备可向下兼容
- **FFmpeg 处理 HDR 元数据**：
  ```bash
  # 保留 HDR 元数据（转码但不改格式）
  ffmpeg -i hdr_input.mp4 \
    -c:v libx265 -x265-params "hdr-opt=1:repeat-headers=1:colorprim=bt2020:transfer=smpte2084:colormatrix=bt2020nc" \
    -crf 28 output_hdr.mp4

  # 读取 HDR 元数据
  ffprobe -show_streams -select_streams v hdr_video.mp4 | grep -E "color|transfer|primaries"
  ```
- **10-bit 编码**：
  - 为什么用 10-bit：减少色带（Banding）伪像，即使 SDR 内容也受益
  - H.265 10-bit：`-pix_fmt yuv420p10le`（注意播放器支持）
  - H.264 10-bit：Profile High 10，`-pix_fmt yuv420p10le`
  - 文件大小影响：约增加 10-20% 体积
  - 硬件支持：大多数现代 GPU 支持 10-bit 解码
- **色彩空间转换实用场景**：
  - 手机录像（BT.709）→ 视频网站（要求 BT.709，确保正确标注）
  - 相机 Log 素材（S-Log3/Log-C）→ 正常色彩（需要 LUT）
  - 应用 LUT（Look Up Table）：
    ```bash
    # 应用 .cube LUT 文件
    ffmpeg -i input.mp4 -vf "lut3d=file.cube" output.mp4
    ```
- **像素格式（Pixel Format）**：
  - `yuv420p`：最常见，Y:U:V = 4:2:0，适合网络传输
  - `yuv444p`：Y:U:V = 4:4:4，无色度降采样，专业存储用
  - `nv12`：NVIDIA GPU 输出格式，Y + UV 交织
  - 检查像素格式：`ffprobe -show_streams video.mp4 | grep pix_fmt`
- 动手实践：处理一段手机 HDR 视频，分别测试"直接转码"和"Tone Mapping 转码"的色彩差异，截图对比

#### 第 22 篇：字幕处理与多音轨管理

- **字幕格式全解**：
  | 格式 | 特点 | 适用场景 |
  |------|------|----------|
  | SRT | 纯时间码+文字，最简单 | 通用字幕交换 |
  | ASS/SSA | 高级样式（位置/颜色/动画）| 动漫/卡拉OK字幕 |
  | VTT (WebVTT) | Web 标准，HLS 字幕 | 浏览器播放器 |
  | PGS/SUP | 图形字幕（蓝光碟）| 蓝光原盘 |
  | DVB | 广播电视字幕 | 欧洲广播标准 |

- **字幕提取**：
  ```bash
  # 提取 MKV 中的 SRT 字幕（第 0 条字幕流）
  ffmpeg -i input.mkv -map 0:s:0 subtitle.srt

  # 提取 ASS 字幕
  ffmpeg -i input.mkv -map 0:s:1 subtitle.ass

  # 列出所有字幕流
  ffprobe -show_streams -select_streams s input.mkv
  ```

- **软字幕 vs 硬字幕**：
  - 软字幕（Soft Subtitle）：字幕作为独立流，播放器可开关，不修改视频
    - 优点：可随时关闭，支持多语言
    - 缺点：需要播放器支持，某些平台不识别
  - 硬字幕（Hard Subtitle / Burn-in）：字幕渲染进视频画面，永久合并
    - 优点：任何播放器都显示，平台兼容性100%
    - 缺点：不可关闭，损失视觉质量
  ```bash
  # 嵌入硬字幕（SRT 格式）
  ffmpeg -i video.mp4 -vf subtitles=subtitle.srt output.mp4

  # 嵌入 ASS 高级字幕（含样式）
  ffmpeg -i video.mp4 -vf ass=subtitle.ass output.mp4

  # 添加软字幕（保持独立流）
  ffmpeg -i video.mp4 -i subtitle.srt -c copy -c:s mov_text output.mp4
  ```

- **字幕格式转换**：
  ```bash
  # SRT → VTT（用于 HLS）
  ffmpeg -i subtitle.srt subtitle.vtt

  # SRT → ASS（添加样式）
  ffmpeg -i subtitle.srt subtitle.ass
  ```

- **HLS 字幕轨道**（WebVTT + EXT-X-MEDIA）：
  - HLS 支持外部字幕文件（VTT 格式）
  - 在 Master Playlist 中用 `#EXT-X-MEDIA:TYPE=SUBTITLES` 声明
  - 实现多语言字幕（中文/英文/日文轨道切换）

- **多音轨管理**：
  ```bash
  # 列出所有音频流
  ffprobe -show_streams -select_streams a input.mkv

  # 提取单条音轨
  ffmpeg -i input.mkv -map 0:a:0 -c:a copy audio_track1.aac

  # 合并视频 + 多条音轨
  ffmpeg -i video.mp4 -i audio_cn.aac -i audio_en.aac \
    -map 0:v -map 1:a -map 2:a \
    -c:v copy -c:a copy \
    -metadata:s:a:0 language=zho -metadata:s:a:0 title="普通话" \
    -metadata:s:a:1 language=eng -metadata:s:a:1 title="English" \
    output_multilang.mkv

  # 从多音轨文件中提取特定语言音轨
  ffmpeg -i multilang.mkv -map 0:v -map 0:a:m:language:zho \
    -c copy chinese_audio.mkv
  ```

- **MKV 容器高级特性**：
  - 支持无限音轨/字幕轨/视频轨
  - 章节标记（Chapters）：方便跳转
  - 附件（Attachments）：嵌入字幕字体文件（避免字幕显示乱码）
  - 保留章节：`-map_chapters 0 -c:t copy`

- **电影/剧集工作流最佳实践**：
  - 输入：蓝光原盘 MKV（多音轨 + PGS 字幕 + 附件字体）
  - 输出：MP4（单音轨 + 硬字幕），适合手机/平板播放
  - 处理流程：提取 SRT → 清理格式 → 嵌入字幕 → 选择音轨 → 转码

- 动手实践：处理一个带多条音轨和字幕的 MKV 文件，生成：
  1. 带硬字幕的单语言 MP4（手机兼容版）
  2. 保留多音轨多字幕的 MKV（高清存档版）

#### 第 23 篇：特殊格式处理（GIF、图片序列、屏幕录制）

- **GIF 动图生成与优化**：
  - GIF 的局限：最多 256 色，无透明度渐变，体积大
  - 简单生成（质量差）：`ffmpeg -i input.mp4 -t 5 output.gif`
  - **高质量 GIF —— 调色板优化**（必须用两步法）：
    ```bash
    # 第一步：生成专属调色板（256 色最优化）
    ffmpeg -i input.mp4 -vf "fps=12,scale=480:-1:flags=lanczos,palettegen" palette.png

    # 第二步：用调色板生成 GIF
    ffmpeg -i input.mp4 -i palette.png \
      -filter_complex "fps=12,scale=480:-1:flags=lanczos[x];[x][1:v]paletteuse" \
      output_hq.gif
    ```
  - GIF 大小优化：降低帧率（12fps 足够）+ 降低分辨率 + 限制时长（<5秒）
  - GIF vs WebP 动图：WebP 动图体积小 40-70%，但浏览器支持略差（2026年基本已普及）
  - 生成 WebP 动图：`ffmpeg -i input.mp4 -vf fps=12 -loop 0 output.webp`

- **APNG（动态 PNG）**：
  - 比 GIF 支持更多颜色（24位），支持真实透明度
  - 生成：`ffmpeg -i input.mp4 -f apng -plays 0 output.apng`
  - 体积通常比 WebP 大，但兼容性最好

- **图片序列 → 视频（延时摄影）**：
  ```bash
  # 图片序列（按帧率合并）
  ffmpeg -framerate 24 -pattern_type glob -i '*.jpg' \
    -c:v libx264 -pix_fmt yuv420p timelapse.mp4

  # 按文件名顺序（frame_0001.jpg, frame_0002.jpg ...）
  ffmpeg -framerate 24 -i frame_%04d.jpg \
    -c:v libx264 -pix_fmt yuv420p output.mp4

  # 照片轮播（每张显示 3 秒）
  ffmpeg -framerate 1/3 -i photo_%03d.jpg \
    -c:v libx264 -vf fps=25 -pix_fmt yuv420p slideshow.mp4
  ```

- **视频 → 图片序列**：
  ```bash
  # 每帧一张图
  ffmpeg -i input.mp4 -q:v 2 frame_%04d.jpg

  # 只导出关键帧

#### 第 24 篇：FFmpeg 8.0 新特性详解

- FFmpeg 8.0 "Huffman" 发布时间：2025 年 8 月
- 并行转码管道（Parallel transcoding pipeline）：
  - 原理：demux/decode/filter/encode/mux 各阶段并行执行
  - 传统串行：demux → decode → filter → encode → mux（瓶颈在最慢环节）
  - 并行模式：各阶段独立线程，用队列连接
  - 性能提升：多核 CPU 利用率从 20% → 80%
  - 启用方法：`-threads auto -thread_queue_size 512`
- Vulkan 编解码支持：
  - FFv1 编码/解码（无损视频编解码器）
  - ProRes RAW 解码（Apple 专业视频格式）
  - 跨平台 GPU 加速（Linux/Windows/macOS）
  - 使用方法：`-hwaccel vulkan -c:v ffv1_vulkan`
- Enhanced RTMP（扩展 RTMP 协议）：
  - 支持 HEVC（H.265）在 FLV/RTMP 中传输
  - 支持 VP9 和 AV1 编码
  - 向后兼容传统 RTMP（H.264 + AAC）
  - 推流示例：`ffmpeg -i input.mp4 -c:v libx265 -f flv rtmp://server/live/stream`
- VAAPI AV1 编码（Intel GPU 硬件加速）：
  - Intel Arc 显卡支持 AV1 硬件编码
  - 使用方法：`-hwaccel vaapi -c:v av1_vaapi`
  - 性能对比：软编 0.5x → 硬编 5x 实时速度
- D3D12VA 解码（Windows 硬件加速）：
  - 替代旧的 D3D11VA
  - 更好的兼容性和性能
  - 使用方法：`-hwaccel d3d12va`
- 其他改进：
  - 改进的 HLS muxer 性能
  - 更好的 HDR 元数据处理（HDR10/HDR10+/Dolby Vision）
  - 改进的时间码处理
- 动手实践：对比 FFmpeg 7.x vs 8.0 的并行转码性能提升

#### 第 25 篇：Go 集成 FFmpeg 完整方案 ⭐

- exec.Command 调用 FFmpeg：
  ```go

      "-i", inputPath,
      "-c:v", "libx264", "-crf", "23",
      "-c:a", "aac", "-b:a", "128k",

  // 捕获输出（用于进度解析）
  stderr, _ := cmd.StderrPipe()
  cmd.Start()
  
  // 解析进度

  for scanner.Scan() {
      line := scanner.Text()
      if strings.Contains(line, "time=") {
          // 解析 time=00:01:23.45
      }
  }
  cmd.Wait()
  ```
- 进度解析（从 stderr 输出）：
  - FFmpeg 输出格式：`frame=  123 fps= 30 q=28.0 size=    1024kB time=00:00:05.00 bitrate=1677.7kbits/s speed=1.00x`

  ```go
  ctx, cancel := context.WithTimeout(context.Background(), 10*time.Minute)
  defer cancel()

  if err := cmd.Run(); err != nil {
      if ctx.Err() == context.DeadlineExceeded {
          return errors.New("转码超时")
      }
  }
  ```
- 优雅退出（SIGTERM → SIGKILL）：
  ```go
  cmd.Start()
  
  // 监听取消信号
  go func() {
      <-ctx.Done()
      cmd.Process.Signal(syscall.SIGTERM)  // 先发 SIGTERM
      time.Sleep(5 * time.Second)
      cmd.Process.Kill()                   // 5秒后强制 SIGKILL
  }()
  
  cmd.Wait()
  ```
- 资源限制（CPU/内存）：
  ```go
  cmd := exec.Command("ffmpeg", ...)
  cmd.SysProcAttr = &syscall.SysProcAttr{
      Setpgid: true,  // 独立进程组
  }
  
  // 使用 cgroups 限制（Linux）
  // 或在 FFmpeg 参数中限制线程：-threads 4
  ```
- 异步任务队列（避免并发过多）：
  - 使用 channel 作为信号量：`semaphore := make(chan struct{}, maxConcurrent)`
  - 或使用 `golang.org/x/sync/semaphore`
  - 任务状态机：Pending → Processing → Completed/Failed
- 错误处理与重试：
  - 捕获常见错误：`Invalid data found` / `Conversion failed`
  - 指数退避重试：1s / 2s / 4s / 8s
  - 最大重试 3 次，记录失败原因
- ffprobe 集成（视频信息获取）：
  ```go

      "-v", "quiet",

#### 第 27 篇：性能调优与故障排查 ⭐

- 常见错误速查表：
  | 错误信息 | 原因 | 解决方案 |
  |---------|------|---------|
  | `Invalid data found when processing input` | 文件损坏或格式不支持 | ffprobe 检查文件，或忽略错误 `-err_detect ignore_err` |
  | `Conversion failed!` | 编码参数不兼容 | 检查编码器支持的 profile/level |
  | `Unknown encoder 'libx264'` | FFmpeg 编译时未包含该编码器 | 重新编译或使用静态编译版本 |
  | `Permission denied` | 输出路径无写权限 | 检查文件权限或目录是否存在 |
  | `Protocol not found` | 协议未启用（如 rtmp/srt） | 编译时 `--enable-protocol=rtmp` |
  | `Too many packets buffered` | 输入流速度过快 | 增大缓冲 `-max_muxing_queue_size 1024` |
  | `Non-monotonous DTS in output stream` | 时间戳错乱 | 使用 `-fflags +genpts` 重新生成 PTS |
  | `moov atom not found` | MP4 moov 在文件末尾 | 转码时加 `-movflags +faststart` |

- 性能瓶颈定位：
  - **CPU 瓶颈**：`speed < 1.0x`，解决：降低 preset（ultrafast）、启用硬件加速
  - **I/O 瓶颈**：磁盘使用率 100%，解决：使用 SSD、减少临时文件读写
  - **内存瓶颈**：OOM 错误，解决：限制并发数、降低分辨率、分段处理
  - **网络瓶颈**（推拉流）：丢包/重传，解决：使用 SRT、增大缓冲、降码率
- 日志分析技巧：
  - FFmpeg `-loglevel debug`：查看详细编解码信息
  - 提取关键指标：`grep "frame=" ffmpeg.log | tail -n 1`
  - 查看编码器选择：`grep "Stream #0:0" ffmpeg.log`
- 转码速度优化：
  - **最快方案**：`-c copy`（不转码，只转封装）
  - **快速转码**：`-preset ultrafast -tune zerolatency`（牺牲体积）
  - **硬件加速**：NVENC（10x 速度提升）
  - **多线程**：`-threads 0`（自动检测 CPU 核心数）
  - **降低分辨率**：1080p → 720p（速度提升 2-3x）
- 内存泄漏排查：
  - 长时间运行的推拉流任务：监控 RSS 内存增长
  - 使用 Valgrind 检测内存泄漏（编译 debug 版本）
  - 定期重启 Worker（临时方案）
- 时间戳问题调试：
  - 使用 `-copyts` 保留原始时间戳
  - 使用 `-start_at_zero` 从 0 开始
  - 使用 ffprobe 查看 PTS/DTS：`-show_packets`
- 音视频不同步诊断：
  - 原因 1：输入视频本身不同步（用 VLC 播放验证）
  - 原因 2：转码时丢帧（检查 `drop frames` 日志）
  - 原因 3：滤镜处理改变时长（如变速）
  - 解决：`-async 1`（音频同步）、`-vsync cfr`（固定帧率）
- 批量文件处理最佳实践：
  - Shell 循环：
    ```bash

        ffmpeg -i "$file" -c:v libx264 "output/${file%.mp4}.h264.mp4"
    done
    ```

#### 第 28 篇：转码集群架构设计

- 单机 vs 集群：
  - 单机：简单，适合小规模（< 100 视频/天）
  - 集群：可扩展，适合大规模（> 1000 视频/天）
- 架构模式：
  - **Master-Worker 模式**：
    - Master：任务调度、状态管理、监控
    - Worker：纯转码节点，无状态
  - **无主模式**（基于消息队列）：
    - 所有 Worker 平等，从队列拉取任务
    - 无单点故障，易扩展
- 任务调度策略：
  - **FIFO**：先进先出，简单但不灵活
  - **优先级队列**：VIP 用户优先、小文件优先
  - **最短作业优先（SJF）**：预估时长，短任务先执行
  - **资源感知调度**：根据 Worker CPU/内存负载分配
- 任务分片（大文件）：
  - 将 1 小时视频切成 6 个 10 分钟片段
  - 并行转码 → 最后合并（concat demuxer）
  - 适合超长视频（> 2 小时）
- 断点续传（失败重试）：
  - 记录已完成的分片
  - 重试时跳过已完成部分
  - 使用 `-ss` / `-t` 分段转码
- 多码率并行转码：
  - 单个 Worker 转多档（串行）：慢，但资源利用率高
  - 多个 Worker 各转一档（并行）：快，但资源占用峰值高
  - **推荐并行**（集群资源充足时）
- 负载均衡：
  - DNS 轮询（简单但不智能）
  - Nginx 反向代理（支持健康检查）
  - Kubernetes Service（自动负载均衡）
- 容错与高可用：
  - Worker 失败：任务重新入队（心跳检测）
  - Master 失败：使用 etcd/Consul 选主
  - 消息队列失败：持久化消息（RabbitMQ durable queue）
- 成本核算：
  - 转码成本 = CPU 小时数 × 单价
  - AWS EC2 c5.4xlarge（16 核）：$0.68/小时
  - 硬件加速（NVENC）：贵但快，适合低延迟场景
  - Spot 实例：便宜 70%，但可能被中断（适合非紧急任务）
- 性能基准测试（Benchmark）：
  - 1080p → 720p H.264（preset=medium）：0.5x - 1.5x 实时速度
  - 4K → 1080p H.265：0.2x - 0.5x 实时速度
  - NVENC 硬件加速：5x - 10x 实时速度
  - 根据实测数据估算集群规模
- 监控大盘设计：
  - 队列长度趋势图（Grafana）
  - 转码速度分布图（直方图）
  - Worker 健康状态（绿/黄/红）
  - 成本统计（每日转码总时长）
- 动手实践：设计一个支持 1000 并发转码的集群架构方案

## 自动化生成工作流（AI 执行规范）

> 这一节是给执行生成任务的 AI 看的操作手册。它解决三个实际问题：
> **工具单次写入有长度限制**、**上下文会被压缩**、**28 篇要跨多个会话完成**。
> 严格按此执行即可全程无人值守，不需要人工回复"继续"。

### 步骤 0：会话启动时先读进度

每次会话开始（包括上下文压缩后的新窗口），**第一件事**是读进度文件确认从哪继续：

```
读取 <memory>/ffmpeg-tutorial-progress.md
  ├── 文件不存在 → 这是首次启动，创建进度文件，从第 1 篇开始
  └── 文件存在   → 找到第一个未打勾的条目，从那篇开始
                    同时检查该篇文件是否残留 CONTINUATION_MARKER
                      ├── 有残留 → 说明上次写到一半被打断，接着填标记
                      └── 无残留 → 上一篇已完成，开始写下一篇
```

**绝不**因为读到进度文件就向用户汇报进度然后停下，读完直接开始写。

### 步骤 1：单篇生成的分块写入策略

写作工具单次内容有长度上限（约 50 行 / 6000 字符），一篇 800-1700 行的文章必须分块写入。
用 **占位标记链式替换** 解决：

```
第 1 次 Write：文件头 + 目录 + 学习目标 + 第 1 节  (~50 行)
               末尾留 <CONTINUATION_MARKER_XX>

第 2 次 Edit： old_string = <CONTINUATION_MARKER_XX>
               new_string = 第 2-3 节内容 + <CONTINUATION_MARKER_XXB>

第 3 次 Edit： old_string = <CONTINUATION_MARKER_XXB>
               new_string = 第 4-5 节内容 + <CONTINUATION_MARKER_XXC>

... 依此类推，标记后缀 A→B→C→D…

最后一次 Edit：new_string = 术语表 + 页脚，**不再留标记**
```

**为什么这样最稳**：`old_string` 是一个全文唯一的标记 token，不含中文、不含缩进，
匹配永远不会失败。相比"用正文片段做锚点"，这个方法零失败率。

**标记命名规则**：`<CONTINUATION_MARKER_{篇号}{字母}>`，如 `<CONTINUATION_MARKER_25D>`。
篇号隔离确保多篇并行时标记不冲突。

**每篇完成后必须验证**：

```bash
grep -c "CONTINUATION_MARKER" <文件路径>   # 必须输出 0
```

不为 0 说明有标记没填完，继续填，不要进入下一篇。

### 步骤 2：写完一篇立即更新进度

每篇写完（且标记校验通过）后，**立刻**更新进度文件，再开始下一篇：

```markdown
## 状态：N/28 已完成（YYYY-MM-DD）

### 模块 X：名称（a/b ✅）
- [x] 07 - 标题（861 行）      ← 完成的打勾并记行数
- [ ] 08 - 标题                ← 未完成留空
```

进度文件同时记录**下一篇的关键内容要点**（3-6 条），这样即使上下文被压缩，
新窗口读到进度文件就能无缝接续，不需要重读整个提示词。

### 步骤 3：上下文压缩后的续写

上下文压缩是**预期行为，不是错误**。压缩后不要重新规划、不要向用户汇报、不要问"是否继续"：

```
压缩后动作序列：
1. 读 <memory>/ffmpeg-tutorial-progress.md      → 知道进度
2. grep 当前篇的 CONTINUATION_MARKER             → 知道断点
3. 直接 Edit 填标记 或 Write 新篇                → 继续干活
```

判断依据全在文件系统里（进度文件 + 残留标记），不依赖对话记忆。

### 步骤 4：模块完成时同步 README

一个模块的所有文章写完后，更新该模块目录下的 `README.md`：
文章标题、行数、一句话简介。同时更新根 `README.md` 的总进度。

**注意**：README 里的标题必须与实际文件名一致。提示词里的规划标题和最终成文标题
可能有出入（写作过程中常会调整），以**实际文件名为准**回填 README。

### 常见陷阱

| 陷阱 | 后果 | 规避 |
|------|------|------|
| 用正文片段做 `old_string` | 中文/缩进导致匹配失败，反复重试 | 只用唯一标记 token 做锚点 |
| 一次性写整篇 | 触发长度限制被截断，内容丢失 | 严格分块，每次 ~50 行 |
| 写完不更新进度文件 | 上下文压缩后不知道进度，重复生成 | 每篇完成立刻更新 |
| 压缩后向用户汇报并等待 | 流程中断，需人工干预 | 压缩后直接读进度接着写 |
| 新增章节忘了改目录 | 目录与正文不符 | 插入章节同时更新目录锚点 |
| 页脚格式各篇不一 | 系列观感不统一 | 页脚用固定模板，早期定稿别中途改 |
| 章节编号重复（两个"10."） | 目录混乱 | 插入章节后重新核对编号连续性 |
