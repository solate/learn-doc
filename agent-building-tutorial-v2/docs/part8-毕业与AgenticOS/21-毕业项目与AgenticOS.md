# 第 21 篇：毕业项目与 Agentic OS

> **知识地图【G1 视野】· Part 8** · 终篇。上半篇毕业收口：把第 8-20 篇攒的零件组装成终版助手——能力清单、工程壳、选型记录、一张总架构图，外加给真实后台的落地交接单。下半篇换一个视角看这 21 篇：**如果把 agent 世界比作操作系统**——agent 是进程、上下文是内存、MCP 是设备驱动——很多「新问题」突然变成操作系统五十年来已经解决过的老问题。本篇是纯理论篇：不写代码，动脑练习替代动手实践（按系列约定）。

## 本篇要回答的问题

1. 终版助手怎么组装：能力清单（记忆/规划/subagent/MCP）、工程壳（评测/trace/安全/治理/只读开关）、选型记录——各来自哪篇、怎么拼成一张图？

## 2｜下半篇·Agentic OS：一张类比图

### 2.1 八条对应

| OS 概念 | agent 世界 | 我们的实现 | 类比教给我们什么 |
|---|---|---|---|
| **进程** | agent 实例 | agent.py 的一次运行 | 有生命周期（创建/运行/终止）、消耗资源（token）、需要隔离——「agent 是一等公民」的正式含义 |
| **内存（RAM）** | 上下文 | messages 列表 | 易失（进程退出就没）、有限且贵（token 预算）、会溢出——**滚动摘要就是换页（swap）**：放不下的内容压缩到便宜的介质 |
| **磁盘** | 长期记忆 | memory 长期层 | 持久、廉价、但取回要检索（embedding=索引）——存储层次结构的代价模型照搬 |
| **设备驱动** | MCP server | admin_mcp_server | 统一系统调用层把 N×M 变 N+M（13 篇）——驱动的意义就是「屏蔽设备差异，暴露统一接口」 |
| **内核调度** | harness | agent loop + 熔断 + 预算 | 循环=调度器（下一步执行谁）；熔断=OOM killer（资源失控强制终止）；预算=ulimit |
| **进程 fork** | subagent | subagent.py | fork 出独立地址空间（子上下文）；fork 有代价（派发开销，17 篇成本账）——进程模型早就算过这笔账 |
| **权限弹窗** | 写操作确认 | guard + governance | 能力声明（工具 schema=manifest）+ 运行时请求 + 用户授权 + 审计——移动 OS 的权限模型整套照搬 |
| **应用生态** | agent 注册表 | （未实现，平台形态） | 谁装了哪些 agent、各自什么权限、从哪分发——治理的对象从「一个 agent」变成「一群 agent」 |

### 2.2 类比的价值与边界

**价值**：把新概念归位到人类已经花了五十年打磨的抽象。配额、审计、沙箱、调度、存储层次——OS 全都解决过，而且解法经过生产验证。看到「上下文溢出」时想到换页，看到「subagent 派发开销」时想到 fork 代价，看到「agent 权限蔓延」时想到最小权限原则——**类比是免费的工程智慧**。

**边界**：类比是地图不是领土，三条重要的失效处：

1. **没有抢占式调度的硬件基础**——OS 能任意时刻打断进程是因为时钟中断；agent 的取消是协作式的（19 篇：检查点检查），LLM 调用中途无法「抢占」
2. **上下文不是真 RAM**——不能随机访问（只能整体重发让模型自己找），不能真正的写保护（提示词纪律可被注入攻破），「内存管理」的手段比 OS 原始得多
3. **进程隔离靠硬件，agent 隔离靠约定**——MMU 保证进程 A 物理上读不到进程 B；subagent 的「隔离」只是消息传递的纪律，一个全局变量就能穿透（17 篇诚实记录过的毛边）

失效处同样是洞察：它们指出了 agent 基础设施相对 OS 还缺什么——而这正是 2025-2026 产业在补的东西。

### 2.3 这个视角解决什么问题：从松散产物到平台治理

单 agent 时代（本系列 1-20 篇），每个问题单独解决：上下文长了做摘要、工具多了做注册表、危险了加闸门。**平台时代的问题形态变了**：不是一个 agent 怎么写好，是一群 agent 怎么管住。OS 视角给治理五件套一个现成的词汇表：

| 治理件 | OS 对应 | agent 平台的形态 |
|---|---|---|
| 生命周期 | 进程管理（fork/exec/wait） | agent 的创建、版本、灰度、退役——谁在跑哪些版本 |
| 可观测 | syslog / /proc | 集中 trace（18 篇的 trace.jsonl 平台化——Langfuse 们做的事） |
| 配额 | ulimit / cgroup | 每 agent/每用户的 token 与写操作限额（20 篇 §2.3/§5.4） |
| 身份 | uid / capabilities | agent 以谁的身份跑（20 篇 §5.1 用户 token vs service account） |
| 跨 agent 通信 | IPC（管道/消息队列/共享内存） | agent 间消息传递（17 篇 §3.3 预告的消息路线） |

与第 2 篇的呼应：第 2 篇用经典理论解释**agent 内部**（ReAct 是它的呼吸、Plan-and-Execute 是它的前瞻、Reflexion 是它的自省）——那是个体的生理学；本篇的 OS 视角解释**agent 之间与之上**（调度、配额、IPC、注册表）——那是城市规划。两个视角合起来，一个 agent 从内到外才算被完整描述过。

## 3｜趋势与演化路径

### 3.1 2025-2026 的三股趋势

**AgentOS 定位**——把 agent 当一等公民的操作环境：身份、权限、可观测、调度作为平台原语提供（Manus 的 AgentOS 是这一定位的代表产品，官方口径见其官网）。本篇 §2 的类比图，产业正在把它做成真产品。

**agent 网关 / agent server（harness 产品化）**——第 5 篇核验过版图（2026-10-19）：DeepSeek Harness、OpenClaw、Pi、OpenHarness 等把「loop + 工具 + 上下文管理 + 权限」打包成可部署的运行时——就是「内核」从自研变成发行版。我们手写的 400 行是教学版内核，它们是生产版。

**多 agent 编排平台**——CrewAI、AutoGen、Google ADK、Microsoft Agent Framework、deepagents 等（17 篇已引、第 5 篇 §3.3 有版本/star 核验）——「进程管理器 + IPC」的产品化。

### 3.2 演化路径与「写到多大上什么组件」

我们走过的路恰好是三段演化的前两段：

```
裸 agent + 工具          →    harness + MCP + 治理        →    agent 平台
（7-8 篇）                     （9-20 篇，当前位置 ✓）           （注册表/网关/配额中心，未做）
一个人一个任务                  要给别人用、要敢上线               一群 agent 要管住
```

「写到多大上什么组件」清单（触发条件式——和第 15 篇 MCP 决定同一精神：不为想象中的规模预付复杂度）：

| 规模信号 | 该上的组件 | 不上会怎样 | 我们 |
|---|---|---|---|
| 单人、单任务、偶尔用 | 裸 agent + 工具 | 不会怎样——这就是它的完整形态 | 7-8 篇 |
| 单人、任务多变、跨会话 | 记忆（会话+长期） | 每次从头解释，用户疲劳 | 11 篇 |
| 单任务变复杂（多步依赖） | 规划模式 | 长链路靠模型现场发挥，错一步全盘重来 | 12 篇 |
| 工具要跨系统/跨语言复用 | MCP | N 个消费方 × M 个系统，胶水代码平方增长 | 14-15 篇（备用） |
| 查询过程又长又脏 | subagent | 主上下文被过程淹没，贵且漂移 | 17 篇 |
| **要给别人用（demo→产品）** | 评测 + trace + 交互介入 + 治理壳 | 盲改 prompt、出事靠 print 复盘、越权即事故 | 18-20 篇 |
| 多用户并发 | 身份 + 配额 + 限流 | 一个用户跑飞，所有人买单 | 20 篇（清单已备） |
| 多个 agent 要管 | 注册表 + 集中 trace + 配额中心 + IPC | 治理混沌：谁在跑、花多少、谁授权的，无人能答 | 未做（平台形态） |

用法：拿这张表当**升级检查表**——你的真实场景亮起哪个信号，就上哪一行；信号没亮就别上（第 17 篇复杂度守恒 + 第 15 篇触发条件，一以贯之）。

## 4｜动脑练习（纯理论篇，不写代码）

**练习 1｜画你自己的终版架构图**：§1.4 给了参考答案（含 OS 概念标注）。合上它，凭 21 篇的记忆画一张自己的——画不出来的组件就是值得重读的那篇。判卷标准：八条 OS 类比（§2.1）每条都能在你的图上指出来。

**练习 2｜给自己的场景定档**：拿 §3.2 的清单，标出你当前真实场景亮起的信号行——然后检查你的架构是否恰好停在那里（没超前也没欠账）。把结论写下来，这就是你的「写到多大」决定书。

**练习 3｜写落地交接单**：假设你要把这套助手交接给另一位工程师接手真实后台的落地。交接单至少包含：对接项（/api/v1+JWT、baseURL、演示账号处置）、身份与租户（用户 token、租户键清单——§2.3 那 5.4 的表）、审计三级与查询入口、限额数值、部署形态与启动命令、评测集怎么跑（回归纪律）、直连→MCP 的触发条件（白纸黑字）。模板就是第 20 篇 §6.6 的清单加「负责人/截止日」两列——写完它，你就有了一份能直接开周会用的文档。

**练习 4｜找类比的漏洞**（思考题）：§2.2 给了三条失效处。第四条藏在第 19 篇——提示：OS 的管道（pipe）是双向字节流，agent 间的「消息传递」缺了什么字节流天然有、消息没有的性质？（方向：背压/流控——生产者比消费者快时会发生什么。）

## 本篇结论

1. 终版助手 = 六件能力（工具/安全/注入防御/记忆/规划/互操作/subagent）+ 三层工程壳（评测/可观测/交互/治理），每个零件都有「为什么在这」的选型记录——组装清单、总架构图、落地交接单三件交付物齐。
2. Agentic OS 八条类比（进程/内存/磁盘/驱动/内核/fork/弹窗/生态）把治理词汇表从 OS 白拿过来，但三条失效处（无抢占、无随机访问、隔离靠约定）标出了 agent 基础设施真正缺的东西。
3. 演化三段走完前两段：裸 agent→harness+治理；第三段（平台）用「写到多大上什么组件」清单触发——不为想象中的规模预付复杂度，这是全系列一以贯之的最后一条纪律。
