## 1｜为什么拆——以及为什么不拆

### 1.1 四个动机

| 动机 | 解决的问题 | 我们经历过的痛 |
|---|---|---|
| **上下文隔离** | 过程性中间结果污染主上下文，挤占 token 预算 | 第 11 篇：查十个文件找一个事实，过程日志全进主上下文 |
| **token 分摊** | 每轮全量重发（第 3 篇铁律）下，消息越多越贵 | 第 11 篇滚动摘要就是单 agent 内的缓解；隔离是结构性解法 |
| **并行** | 独立子任务可以同时跑（查 A 和查 B 互不依赖） | 本系列教学版顺序执行，并行属时延优化（第 16 篇已声明边界） |
| **职责边界** | 不同子 agent 拿不同工具子集，权限物理隔离 | 第 16 篇 HITL 表的「职责边界」行：子 agent 没有写工具，想越权也没工具可调 |

### 1.2 复杂度守恒警告

**多 agent 不消灭复杂度，只搬运复杂度**：单 agent 的复杂度在上下文管理（消息越长越难维持纪律），多 agent 的复杂度在**接口**——派发任务的措辞、结果汇总的格式、子 agent 失败时主 agent 怎么收场。拆得越多，接口越多，每个接口都是一个「翻译损耗 + 出错面」。Claude Code 的 subagent 也好、市面上的多 agent 框架也好，都逃不出这条：**协作的收益必须大于接口的成本，否则 flat 更好**。判定信号第 16 篇 §3.2 给过（中间结果无价值 / 工具结果大而脏 → 层级；强耦合 → 扁平），本篇实践会用数据验证它。

## 2｜五种模式：选型表与实例对位

| 模式 | 一句话 | 对位实例（第 16 篇拆解对象） | 适合 | 不适合 |
|---|---|---|---|---|
| **orchestrator-worker** | 主 agent 拆活派发、收结果、管全局 | Claude Code 主 + subagent；**我们的 M5** | 任务可拆成独立子任务，子结果只需摘要回传 | 子任务间强耦合、每步输出都是下一步输入 |
| **planner-executor** | 先出计划，再按计划执行（计划与执行分离） | 我们第 12 篇 planner 的单体内版本；多 agent 化=planner 和 executor 各一个 agent | 计划本身复杂、需要专门「想清楚」的阶段 | 简单任务（计划成本 > 执行成本，第 12 篇三笔开销） |
| **verifier** | 执行者产出，独立检查者复核 | 第 12 篇 self-correct 的「独立 verifier 写法」多 agent 化 | 高风险操作、正确性可程序化判定 | 检查者与执行者用同一上下文（独立性是它的全部价值） |
| **debate** | 多 agent 观点对抗，仲裁者定夺 | 学术研究场景多（规格清单的 AutoGen/CrewAI 支持） | 开放性判断题（方案选型、评审） | 事实性任务（对就是对，吵不出新事实，纯烧 token） |
| **对称协作** | 对等分工、共享状态 | OpenHands 的事件流形态可容纳 | 长流水线、角色对等的协作 | 需要统一决策点的任务（没有主心骨会震荡）

**选型口诀**：先问「要不要拆」（§1 的判定信号），再问「拆成什么形状」——管理助手这类工具型场景，九成落在 orchestrator-worker；planner-executor 在第 12 篇已经以单体形态吃到了八成收益。

## 3｜通信机制：三条路线

### 3.1 共享上下文（我们一直在用的）

所有角色读写同一个 `messages` 列表——第 12 篇的 planner 与 executor 其实就是共享上下文的「逻辑分角色」：同一循环里先规划后执行。优点：零翻译损耗，一切对彼此可见。缺点：**没有隔离**——上下文预算、纪律维持、错误污染全是共享的。它是 flat 的本质。

### 3.2 嵌套调用（agent 当工具）——本篇落地

subagent 在主 agent 的视角里**就是一个工具**：有名字、描述、参数 schema（派发措辞即参数）、返回文本（汇总即结果）。内部它自带完整 loop。对比第 14 篇的 MCP 工具，边界就一句话：**工具是确定性函数，子 agent 是自带 loop 的工具**——输入到输出的映射里藏着一轮又一轮「调模型、执行工具、观察」。Claude Code 的 subagent 就是这个形态（第 16 篇事件流图）。

```
 主 agent 上下文                        subagent 上下文（独立 messages）
 ─────────────                        ─────────────────────
 [1] 用户任务
 [2] 调工具 query_via_subagent ─────→ [3] 装子 system + 任务
                                      [4] 独立 loop（login/查询…）
 [5] 工具结果 = 子的最终答复 ←──────── [5'] 过程留在子上下文，烧完即弃
 [6] 基于答复继续（写操作照走闸门）
```

### 3.3 消息传递（平台化形态，预告）

独立进程/会话 + 显式消息协议（请求/响应/事件各是独立实体）——多 agent 编排平台与 P8 的 Agentic OS 视角（agent 像进程、跨 agent 通信像 IPC）住在这层。本系列不实现，第 21 篇用视角收口时回来。

**取舍一句话**：共享上下文=零损耗无隔离；嵌套调用=接口窄、隔离好、子 agent 不能中途反问主 agent（只能一口气跑完给结论）；消息传递=最灵活、最重。复杂度从低到高，隔离与灵活性从低到高——没有免费午餐。

## 4｜成本账：多 agent 一定更贵，值不值看这笔

多 agent 的三项额外成本：

1. **派发开销**：子 agent 每次启动都要装自己的 system prompt + 工具清单（第 3 篇：每轮全量重发，system 也算钱）；
2. **汇总损耗**：子的过程 → 结论的压缩是有损翻译，主 agent 拿到的是摘要不是全貌；
3. **延迟串行化**：派发 → 等待 → 收结果（教学版顺序执行；并行化可摊掉一部分，但派发/汇总两头的开销摊不掉）。

**值不值的粗算**（用第 11 篇的 token 直觉）：设主任务若 flat 跑，过程消息共 P 条、结论 C 条；层级跑，主上下文只装 C、子上下文装 P+派发 D。当 **P 远大于 C**（查十个文件找一个事实），隔离省下的主上下文预算（P−C，且每轮都重发所以是乘数效应）> 派发开销 D，值；当 P≈C（每步输出都是下一步的输入），纯亏。本篇实践会给出实测数字。

## 5｜动手实践：里程碑 M5——只读查询 subagent + 扁平/层级对比

### 5.1 设计（动手前先想清的三件事）

1. **拆什么**：查询链（login / get_users / get_user_roles）下放给 subagent；主 agent 只留 `query_via_subagent` + `assign_role`——对位 orchestrator-worker，主 agent 管全局与写操作，worker 管查询。
2. **权限怎么走**：子工具集**物理只读**（`ReadOnlyToolset` 没有 assign_role，想写也没工具）；写操作仍在主 agent、仍挂闸门——第 9-14 篇的保护零丢失。
3. **状态怎么共享**：教学版子 agent 与主 agent 同进程嵌套，`admin_tools._token` 天然共享（login 在子里跑，token 存同一进程内存，主 agent 的 assign_role 直接用）——这是 §3.1 共享上下文与 §3.2 嵌套调用的**混合形态**，也是诚实的教学点：生产形态里子 agent 常是独立进程（MCP server 形态），登录态共享要显式设计（第 20 篇治理清单记一笔）。

### 5.2 代码：subagent.py

核心三件：`ReadOnlyToolset`（只读视图，注册件接口同形）、`_run_subagent`（嵌套 run_agent：换 toolset → 跑 → 还原）、`HierarchicalToolset`（主 agent 的新工具集：subagent 工具 + assign_role）。全文：

```python
# subagent.py — 第 17 篇：只读查询 subagent（「agent 当工具」的最小形态）
# 对位第 16 篇事件流图：主 agent 的视角里，query_via_subagent 就是一个普通工具
# （有名字/描述/参数 schema）；工具的实现是「再跑一个 run_agent」——子 agent 有自己的
# messages、自己的轮次与工具调用，跑完只把最终答复作为工具结果回填主上下文。
# 中间过程（搜了几页、翻了几个角色清单）留在子上下文里烧完即弃——这就是上下文隔离。
# 职责边界用物理手段：子工具集只有只读三件（login/get_users/get_user_roles），
# 写工具 assign_role 不下放——subagent 想写也没有工具可调（权限的「结构化」版本，
# 第 16 篇 §4 HITL 表「职责边界」一行的落地）。
# 诚实声明：本文件与 demo_m5_compare.py 一起桩测通过（零 LLM token，见第 17 篇实践节）；
#           真实 DeepSeek 下的行为 <未实测，以官方文档为准>。
import json

import agent
import admin_tools

# 子工具集：只读三件（写工具不下放）。注册件接口同形，run_agent 直接可用。
_READ_ONLY = ("login", "get_users", "get_user_roles")


class ReadOnlyToolset:
    """admin_tools 的只读视图：同一批 schema/实现/校验，唯独没有 assign_role。
    与 admin_tools / MCPToolset 暴露同一组注册件接口（第 8 篇 §3.1 的形状）。"""

    def __init__(self):
        self.TOOL_SCHEMAS = [s for s in admin_tools.TOOL_SCHEMAS
                             if s["function"]["name"] in _READ_ONLY]
        self.TOOL_REGISTRY = {n: admin_tools.TOOL_REGISTRY[n] for n in _READ_ONLY}
        self.SCHEMA_BY_NAME = {n: admin_tools.SCHEMA_BY_NAME[n] for n in _READ_ONLY}

    def validate_args(self, function_schema, args):
        return admin_tools.validate_args(function_schema, args)   # 校验原样复用


_READONLY = ReadOnlyToolset()

# 子 agent 的 system prompt：只讲查询纪律，不提写操作与闸门（它根本没有写工具）。
SUB_SYSTEM_PROMPT = (
    "你是后台管理系统的只读查询助手，通过工具查询用户与角色信息。规则：\n"
    "1. 涉及用户、角色的事实必须调用工具获取，禁止编造 user_id / role_id；\n"
    "2. 调用查询工具前必须先 login（演示账号写在工具说明里）；\n"
    "3. 回答只汇总事实（user_id、角色名），保持简短——你的答复会被上层直接引用。"
)

# 主 agent 看到的工具描述：告诉它「复杂查询交给子代理，自己只管写操作」。
SCHEMA = {
    "type": "function",
    "function": {
        "name": "query_via_subagent",
        "description": (
            "把只读查询任务（查用户、查角色、汇总用户清单等）交给只读查询子代理完成，"
            "返回简明事实汇总。涉及写操作（改角色）时不要用它——写操作由你自己在确认后执行。"
            "需要查多个对象或多页信息时优先用它，一次要齐，避免主对话被查询细节填满。"
        ),
        "parameters": {
            "type": "object",
            "properties": {
                "query": {"type": "string",
                          "description": "用一句话说清要查什么（如：查张三和李四现在的角色）"},
            },
            "required": ["query"],
        },
    },
}


def _run_subagent(client, query: str) -> str:
    """嵌套 run_agent：临时切换全局 toolset 为只读子集，跑完还原。
    （agent.toolset 是模块级全局——教学版的已知毛边：嵌套调用要手动换装/还原；
    生产做法是把 toolset 作为 run_agent 的参数传入，第 20 篇重构清单记一笔。）"""
    outer = agent.toolset
    agent.toolset = _READONLY
    try:
        return agent.run_agent(client, query, messages=[
            {"role": "system", "content": SUB_SYSTEM_PROMPT},
            {"role": "user", "content": query}])
    finally:
        agent.toolset = outer


def build_subagent_tool(client):
    """产出主 agent 用的工具实现：(**kwargs) → 子 agent 的最终答复文本。"""

    def query_via_subagent(query: str) -> str:
        return _run_subagent(client, query)

    return query_via_subagent


class HierarchicalToolset:
    """层级版工具集（M5 对比实验的 B 组）：query_via_subagent + assign_role。
    对位 Claude Code 的主 agent：把查全交给 subagent，自己只保留写操作（挂闸门）。"""

    def __init__(self, client):
        impl = build_subagent_tool(client)
        self.TOOL_SCHEMAS = [SCHEMA, admin_tools.SCHEMA_BY_NAME and
                             next(s for s in admin_tools.TOOL_SCHEMAS
                                  if s["function"]["name"] == "assign_role")]
        self.TOOL_REGISTRY = {"query_via_subagent": impl,
                              "assign_role": admin_tools.TOOL_REGISTRY["assign_role"]}
        self.SCHEMA_BY_NAME = {s["function"]["name"]: s["function"] for s in self.TOOL_SCHEMAS}

    def validate_args(self, function_schema, args):
        return admin_tools.validate_args(function_schema, args)   # 白名单只对 assign_role 生效
```

一个值得停一秒的设计毛边（诚实记录）：`agent.toolset` 是模块级全局，嵌套调用要手动「换装/还原」（`_run_subagent` 的 try/finally）。教学版这样写是因为不想为第 17 篇重构第 3 篇以来的 loop 签名；生产的正确做法是把 toolset 作为参数传入 run_agent——**全局状态是嵌套的天敌**，这条记入第 20 篇重构清单。

def _call(idx, name, **args):

        id=f"call_m5_{idx}", type="function",

class BranchScriptedLLM:
    """按 system prompt 分流的剧本桩：主循环与子上下文各用各的剧本，
    同时记录每个分支的 LLM 调用数与每次调用收到的 messages 长度（=上下文增长曲线）。"""

    def __init__(self):
        self._scripts = {"main": iter(SCRIPT_HIER_MAIN), "sub": iter(SCRIPT_HIER_SUB)}
        self.stats = {"main": [], "sub": []}
        outer = self

        class _Completions:
            def create(self, **kwargs):
                return outer._next(kwargs.get("messages", []))

        class _Chat:
            completions = _Completions()
        self.chat = _Chat()

    def _next(self, messages):
        branch = "sub" if (messages and messages[0].get("content") ==
                           subagent.SUB_SYSTEM_PROMPT) else "main"
        self.stats[branch].append(len(messages))
        return next(self._scripts[branch])

    def use_flat(self):
        """A 组：只有主上下文，剧本换 flat 版。"""
        self._scripts["main"] = iter(SCRIPT_FLAT)
        self.stats = {"main": [], "sub": []}

### 5.4 实测结果（2026-10-19 本机，Python 3.12.15）

```text
=== 量化对比（同一任务，两版语义等价前提下的结构差异） ===
指标                                A 扁平                        B 层级
主上下文峰值消息数（隔离的直接度量）    14                            6
主循环 LLM 调用数                     7                             3
子上下文 LLM 调用数（B 独有）          0                             6（峰值 12 条）
总 LLM 调用数（成本账）                7                             9
主上下文工具调用                      6 次（login/查×4/assign）      2 次（query_via_subagent, assign_role）
终局状态（等价验收）                   张三=['r-admin']               张三=['r-admin']

=== demo_m5_compare：PASS——两版终局一致、层级版主上下文更小、子上下文确实在工作 ===
```

三行结论（数据 → 判断）：

1. **主上下文峰值 14 → 6 条消息**：查询细节被隔离在子上下文（峰值 12 条，烧完即弃），主 agent 只见结论——上下文隔离成立，且按第 3 篇「每轮全量重发」的乘数效应，省的是每一轮的钱。
2. **总 LLM 调用 7 → 9 次**：多 agent 更贵坐实（子 agent 重装 system+工具清单的派发开销）——省的是主上下文预算，付的是总 token；任务里查询占比越大、复用轮次越多，这笔交易越划算。
3. **写操作仍只在主 agent、闸门照挂**：职责边界（子物理只读）+ 确认策略（主持有）零丢失——层级化不必以牺牲第 9-14 篇的保护为代价，但**必须显式设计**，否则会像第 14 篇警告的那样静默丢层。

## 本篇结论

1. 拆多 agent 的判定不看规模看结构：中间结果无价值 / 工具结果大而脏 → orchestrator-worker；强耦合 → 保持 flat——复杂度只被搬运，不被消灭。
2. 通信三路线（共享上下文 / 嵌套调用 / 消息传递）是隔离与灵活性的阶梯；教学版落地嵌套调用：子 agent=自带 loop 的工具，权限用物理只读画界。
3. M5 实测：主上下文峰值 14→6 条消息（隔离收益）、总调用 7→9 次（派发成本）、保护零丢失——这笔账每个任务拆之前都该先算一遍。
