## 1｜多轮对话与「被打断」：三种形态，三种语义

### 1.1 我们已有的两种多轮，缺的第三种

| 形态 | 已有实现 | 特点 |
|---|---|---|
| 对话级多轮 | `--chat` + 记忆（第 11 篇） | 轮与轮之间人机交替，每轮一个完整任务 |
| 会话级恢复 | `--checkpoint` / `--resume`（第 16 篇） | 进程死了，把消息快照读回来继续 |
| **任务级多轮**（本篇） | 无 | **一个任务执行到一半**，用户要插话、喊停、改需求 |

前两种的共性：交互点都在「任务与任务之间」——agent 干活时，用户是旁观者。第三种才是真实运维现场的形态：批量任务跑到第 7 条，用户发现第 3 条就弄错了，此刻他能做什么？Ctrl-C 是唯一选项，而它的语义是「杀进程」：进度丢失、已执行的不会回滚、下次从头再来。

### 1.2 打断的三种形态

| 形态 | 用户意图 | 期望语义 |
|---|---|---|
| 插话 | 补充信息，**不**要求停止 | 当前步骤做完，吸收新输入再继续 |
| 喊停 | 立即停止 | 取消——且要回答「已做的怎么办」 |
| 改需求 | 修正方向 | 剩余部分按新指令，已完成的通常不追溯 |

三种形态对 agent 的要求完全不同：插话要的是**吸收**（新信息进上下文）、喊停要的是**取消**（干干净净停下并交代现状）、改需求要的是**替换**（剩余计划重算）。把它们混成同一个「中断」处理，是交互做烂的第一原因。

### 1.3 取消语义：协作式与抢占式

取消有两派做法：

**抢占式（preemptive）**——任意时刻掐断执行。工程载体是 cancellation token / `asyncio.Task.cancel()`：调 `task.cancel()` 后，任务在下一个 await 点抛 `CancelledError`。它的问题恰恰是「太彻底」：LLM 请求已经发出去了，掐断本地协程不退款；工具调用打到一半的 HTTP 请求，掐断后服务端可能已执行——**你取消了客户端，取消不了服务端**。

**协作式（cooperative）**——执行流跑到**检查点**时主动问「还要继续吗」。粒度完全由检查点位置决定：

| 检查点位置 | 粒度 | 问题 |
|---|---|---|
| 每个工具调用前 | 最细 | 一轮问五次，确认疲劳，用户开始无脑回车 |
| 每轮 LLM 之后 | 中 | 单任务内合理；批量任务还是太细 |
| **每条任务之间** | 批量任务天然粒度 | 单条内部不可打断（接受），条与条之间全权可控 |
| 任务完成时 | 最粗 | 等于没有 |

CLI 教学版选协作式 + 条间检查点：实现是纯同步代码，语义清晰（「已完成的条目不回滚、未开始的不执行」），而且**和写操作的原子性对齐**——单条任务本身不长（十几秒），条间检查已覆盖 90% 的打断需求。生产里 Web 形态（第 20 篇）会用 SSE 流式 + 前端按钮发取消指令，落到后端仍是「跑到检查点检查取消标志」——协作式的检查点思想不变，只是触发方式从终端 input 变成消息通道。

### 1.4 暂停-恢复：任务级 checkpoint

第 16 篇的会话 checkpoint 存的是**消息快照**（对话级），本篇要存的是**任务进度**：

| | 会话 checkpoint（第 16 篇） | 任务 checkpoint（本篇） |
|---|---|---|
| 存什么 | 完整 messages 列表 | `{指令, 剩余条目, 已完成, 跳过}` |
| 恢复什么 | 一段对话的上下文 | 一个多步任务还剩哪些没做 |
| 写的时机 | 每轮 LLM 之后 | 每条任务完成之后 |
| 消费者 | `--resume` 重启会话 | 续跑批量任务 |

两者互补不互斥：批量任务里每条执行时可以照常开会话 checkpoint（单条内崩溃可恢复单条），条间再写任务 checkpoint（整批进度可恢复）。写频率的取舍：**每条完成即存**——崩了最多重做一条；代价是多一次文件写，批量场景完全可接受。

## 2｜人工介入：分级、方式与时机

### 2.1 风险分级表：交互成本随破坏性增长

| 级别 | 操作类型 | 本系统例子 | 交互策略 |
|---|---|---|---|
| L0 只读 | 无副作用 | 查用户、查角色 | **不问**——每次都问会训练用户无脑按 y，闸门失去意义（第 9 篇已论证） |
| L1 可逆写 | 覆盖式、可撤销 | 改角色（覆盖式分配，改错了再改回） | 执行前确认（现有 guard 的 y/N） |
| L2 不可逆 | 删除、出站（发邮件/付费）、敏感数据导出 | 删用户、导出全量手机号 | 确认 + **要求用户复述关键参数**（「输入用户名以确认」）；摘录影响面（「将删除 3 个用户」） |
| L3 批量/外溢 | 批量写、影响他人 | 一次改 20 人的角色 | **批量计划先审**（改动清单过目）+ 执行中逐条可拒 |

分级的原则只有一句：**问，本身有成本**。确认疲劳（confirmation fatigue）是真实事故源——每天弹 50 次确认框的系统，第 3 天起用户就闭着眼按 y。所以策略不是「越安全越问」，而是「破坏性越大问得越重」：L0 静默、L1 一次确认、L2 参数复述、L3 计划审批。

### 2.2 介入的三种方式

对第 1.2 节三种打断形态的「应答」，恰好是三种介入方式：

| 介入方式 | 对应打断形态 | 本篇实践的载体 |
|---|---|---|
| 确认后继续 | 插话/常规写操作 | 介入点回车 / guard 的 y |
| 修正指令 | 改需求 | 介入点输入新指令文本 |
| 彻底中止 | 喊停 | 介入点 q（批量级）/ guard 的 N（单条级） |

注意两级控制的分工：**guard 管单条**（这一次 assign_role 放不放行），**介入点管全局**（整个批量还要不要继续、方向要不要改）。拒绝一条 ≠ 中止批量——用户可能只是对李四那条有疑问，而不是不想跑了。两级各自独立，是本篇实践的核心设计。

### 2.3 停下来问的四个信号

「闷头干错」和「问得太勤」之间的平衡点，靠四个信号判断——**任意一个亮起就该停下来问**：

| 信号 | 表现 | 本系统的样子 |
|---|---|---|
| 确定性低 | 模型连续试错、兜底链在吃错误 | 同一工具连续报错重试（第 7 篇兜底路径被反复触发） |
| 破坏性高 | 操作落在 L2+ | 要删数据、要出站 |
| 信息不足 | 关键参数查不到 | 搜「王五」返回空——目标不存在，继续猜着写就是编造 |
| 多选浮现 | 多个候选满足描述 | 搜「张」返回张三张四张五——「张」指谁？ |

第四个信号值得强调：**多选浮现时闷头选一个，等于替用户做了他没授权的选择**。哪怕选对了，交互上也是错的——用户下次不敢把模糊指令交给你。信息不足和多选的共同解法是「停下来问」，而确定性低和破坏性高的共同解法是「停下来报」——把现状摆出来让用户裁决，而不是自己消化。

## 3｜长任务：进度、断点续跑与超时兜底

### 3.1 进度可见

长任务静默是 Ctrl-C 的第一诱因——用户不知道它是卡死了还是在干活。进度可见的最低标准：**第 k/n 条 + 每条一行结果摘要**。批量任务的进度天然离散（条目数），打点容易；单任务长执行（一次跑很久的搜索/分析）则要靠 agent 主动汇报中间发现——那是第 12 篇规划模式的「步骤完成事件」，本系列教学版用 print 实现，生产用 SSE 事件流（第 20 篇）。

### 3.2 断点续跑的工程细节：原子写

checkpoint 写入有个不起眼但致命的细节：**不能直接 `open(path, "w")` 写**。写大文件写到一半进程崩了（或磁盘满），留下半个 JSON——下次恢复时 `json.load` 抛异常，**checkpoint 本身成了不可恢复的损坏文件**。正确姿势是原子写：先写临时文件，写完再 `os.replace(tmp, path)`——POSIX 上 rename 是原子操作，目标文件要么是旧的完整版、要么是新的完整版，永远不存在半个。

### 3.3 超时兜底：四层，每层都要有「之后怎么办」

| 层 | 已有实现 | 超时之后干什么 |
|---|---|---|
| 工具层 | `admin_tools` 的 HTTP `timeout=60`（第 8 篇） | 抛异常 → execute_tool 兜底链转错误文本回喂模型（第 9 篇） |
| LLM 层 | SDK `timeout` / `max_retries`（第 6 篇） | SDK 自动重试；重试耗尽抛异常给上层 |
| 循环层 | `MAX_ITERATIONS=10` 熔断（第 7 篇） | RuntimeError → `run_safely` 转成明确报错答复，不静默 |
| **任务层（本篇）** | 批量条目数 × 单条预算 | 超预算中止 + **报告已完成部分**（checkpoint 里就有） |

前四篇攒的兜底在这里合流成一个观察：**每层超时都必须有「超时之后干什么」的答案**——重试、降级、熔断、报告，四选一；唯独「静默挂起」不可接受。任务层是最后补齐的一块：批量跑到第 15 条超预算了，正确行为不是全丢，而是「停下 + 已完成 14 条在 checkpoint 里 + 剩余 6 条列给用户看」。

## 4｜怪问题速查表：症状 → 兜底 → 出处

真实使用里的高频怪问题，大半在前 18 篇已经埋了兜底，这里收拢成一张表（新问题标「本篇/第 20 篇补」）：

| 症状 | 兜底 | 出处 |
|---|---|---|
| 参数幻觉（编 user_id） | schema 校验 + 错误文本回喂模型自纠 | 第 7/9 篇 |
| 乱调工具（调用不存在的） | 注册表拦截，返回可用工具清单 | 第 9 篇 |
| 编结果（没查就说查了） | 先查后写纪律 + 评测集终局对拍 | 第 8 篇 / 第 18 篇 |
| 上下文漂移（长对话忘了早前约束） | 滚动摘要 + 记忆三层（摘要永在上下文） | 第 11 篇 |
| tool 结果过大（列表撑爆上下文） | 工具描述写明分页；记忆层 token 预算 | 第 10/11 篇 |
| 答非所问（收尾答非所问/答错对象） | 终止判定读结构信号不读文本；评测集照妖镜 | 第 3 篇 / 第 18 篇 |
| **同一调用原样重发（回环）** | 兜底靠「同样错误不要重发」纪律 + 熔断兜底；工程版加**指纹检测**：滑动窗口记 `(tool, args)` 指纹，N 次重复即注入提醒或强制中止 | 第 7 篇；检测器本篇给思路、教学版不实现 |
| **并发与限流（多用户同用）** | 单用户版无此问题；多用户要身份、配额、并发隔离 | 第 20 篇 |
| **模型输出不稳定（同问不同答）** | 结构化断言的评测集回归 + 参数温度策略（第 4 篇） | 第 18 篇 |

回环检测展开两句：教学版的熔断（10 轮上限）是**事后兜底**——回环已经烧了 10 轮 token 才断。指纹检测是**事中拦截**：维护最近 K 次 `(工具名, 参数)` 的列表，新调用进来先查重，命中即向 messages 注入一条 system 提醒（「你已用完全相同的参数调用过 X，请改变策略或向用户说明」），连续命中则强制中止。为什么教学版不实现：我们的任务单条不超过 5 轮，回环从未真实发生——**没有失败模式支撑的防御是负债**（第 18 篇评测集的同一条原则，用在代码上）。

## 5｜与权限系统的搭配：交互侧

### 5.1 提示粒度与频次

批量 20 条逐条 y/N 就是 2.1 节说的确认疲劳现场。策略分层：

- **批量计划先审**（L3 策略）：开跑前把 20 条的改动清单摆出来确认一次——用户审的是「方向」
- **执行中逐条可拒**（介入点）：跑的过程中任何一条都可以 s 跳过或 q 中止——用户管的是「节奏」
- 写操作闸门（guard）在批量场景可以降级为「记录 + 不问」或维持逐条问，取决于风险级别——L1 批量可合并确认，L2 永远逐条

### 5.2 放行一次 vs 永久白名单

「放行一次」是默认（现有 guard 的语义：这次 y 只管这次）。往上还有两档：

- **本会话放行**：同一会话内同类操作不再问。实现载体现成——第 16 篇的 `hooks.run_before`：before 钩子里查一个会话级集合，命中即放行并注记审计。三五行的代码量，教学版不实现（会话内批量已由介入点覆盖）。
- **永久白名单**：**危险的一档**。权限蔓延（privilege creep）的经典路径——三个月前放行「批量改角色」时理由充分，如今组织规则早变了，白名单还在。若一定要有，必须配三件：过期时间、放行理由留档、审计里单独成态。

### 5.3 审计对齐：交互里发生的一切「人的决定」都要对得上

第 9 篇给审计定了 `denied` 单独成态（「人说了不」是追责时最重要的一类记录）。本篇的交互扩展后，审计面要跟上：**中止**（q）不发生在工具层，工具审计看不见——它落在任务 checkpoint（剩余条目即「中止时的现场」）+ 退出时的终端日志。交互侧与审计侧的对齐清单：

| 人的决定 | 留在哪 |
|---|---|
| 放行单条写操作（y） | 审计该条 status=ok |
| 拒绝单条写操作（N） | 审计该条 status=denied |
| 跳过某条（s） | 任务 checkpoint 的 skipped |
| 中止批量（q） | 任务 checkpoint 的 remaining + 终端输出 |
| 改需求（新指令文本） | 任务 checkpoint 的 task 变更 + 旧新指令都在（覆盖前先存？教学版只存最新——生产应存变更历史） |

### 5.4 身份选型预告

交互侧最后一个大问题：agent 以谁的身份调后台——登录用户的 token（操作即用户本人，审计天然对齐，但权限受限于用户）还是专用 service account（权限可独立配置，但「agent 干的」和「用户干的」在审计里混在一起）？这是第 20 篇 RBAC 架构侧的核心议题，本篇只埋钩子。

## 动手实践：可打断的批量任务——三个场景

实践目标（规格 D4/D5 的动手要求）：实现「跑批前打断 + 写操作确认 + 中途改需求」三个场景，验证体验与日志。

### 6.1 设计：一个函数，三个角色

批量任务：**把张三、李四、王五提升为编辑者**（王五在系统里不存在——批量里的边界条目，顺便验证 2.3 节「信息不足」信号的处理）。

核心是一个 `run_batch` 函数，它把本篇的概念全部落位：

```
run_batch(client, task, items, input_fn, done, skipped)
   │
   │  循环：还有剩余条目吗？
   ▼
[介入点]（§1.3 条间检查点）── 回车 ──▶ 执行本条（内部走完整 agent loop + guard 闸门）
   │         ├─ s ──▶ 跳过本条，记入 skipped
   │         ├─ q ──▶ 彻底中止：存任务 checkpoint（§1.4），退出
   │         └─ 文本 ▶ 修正指令：替换 task，当前条目用新指令重新面对（§2.2）
   ▼
每条完成 → 存任务 checkpoint（§3.2 原子写：崩了最多重做一条）
```

三个角色各管一段：**介入点管全局节奏**（继续/跳过/中止/改向）、**guard 管单条写操作**（y/N）、**任务 checkpoint 管进度**（remaining/done/skipped）。测试形态沿用第 8/17/18 篇的诚实证据模式：ScriptedLLM 剧本 × 真实 HTTP 后台，零 LLM token；人的输入与确认都用预设序列回放。

# ---------- 桩：剧本 LLM / 脚本化输入（与第 18 篇 run_eval.py 同构） ----------

def _call(idx, name, **args):
    return types.SimpleNamespace(
        id=f"call_p19_{idx}", type="function",
        function=types.SimpleNamespace(name=name,
                                       arguments=json.dumps(args, ensure_ascii=False)))


def _resp(tool_calls=None, content=None):
    msg = types.SimpleNamespace(content=content, reasoning_content=None, tool_calls=tool_calls)
    return types.SimpleNamespace(choices=[types.SimpleNamespace(
        message=msg, finish_reason="stop" if not tool_calls else "tool_calls")])


class ScriptedLLM:
    """剧本桩：按顺序吐预设响应（第 8 篇手法）。"""

    def __init__(self, script):
        self._it = iter(script)
        outer = self

        class _Completions:
            def create(self, **kwargs):
                return next(outer._it)

        class _Chat:
            completions = _Completions()
        self.chat = _Chat()


def item_script(idx, name, uid, role, denied=False):
    """单条「查→写」剧本：login→搜人→查角色→分配（被拒则收尾如实说明）。
    denied=True 时第 5 个响应是「用户拒绝后的收尾答复」——对应 guard 回喂的拒绝文本。"""
    calls = [
        _resp([_call(idx, "login", username="admin", password="admin123")]),
        _resp([_call(idx + 1, "get_users", keyword=name)]),
        _resp([_call(idx + 2, "get_user_roles", user_id=uid)]),
        _resp([_call(idx + 3, "assign_role", user_id=uid, role_id=role)]),
    ]
    if denied:
        calls.append(_resp(content=f"用户拒绝了本次写操作，{name} 的角色保持不变。"))
    else:
        calls.append(_resp(content=f"已把 {name}（{uid}）设置为 {role}。"))
    return calls


def notfound_script(idx, name):
    """边界条目剧本：login→搜人（真实后台返回空）→如实说明（§2.3 信息不足：停下来报）。"""
    return [
        _resp([_call(idx, "login", username="admin", password="admin123")]),
        _resp([_call(idx + 1, "get_users", keyword=name)]),
        _resp(content=f"系统里没有找到叫「{name}」的用户，无法为其分配角色。"),
    ]


def scripted_inputs(*answers):
    """把预设回答串成 input_fn：回放时把提示与回答一起打印，transcript 可读。"""
    it = iter(answers)

    def fn(prompt=""):
        ans = next(it)
        print(f"{prompt}{ans}")
        return ans
    return fn


def patch_confirms(*answers):
    """把 guard.confirm 换成预设 y/N 序列（第 8 篇起的桩测手法）。返回还原函数。"""
    real = guard.confirm
    it = iter(answers)

    def scripted(name, args, _input=input):
        return real(name, args, _input=lambda _p: next(it))
    guard.confirm = scripted

    def restore():
        guard.confirm = real
    return restore

# ---------- 任务 checkpoint：进度快照（§3.2 原子写） ----------

def save_state(task, remaining, done, skipped):
    """任务级 checkpoint：记「指令 + 剩余 + 已完成 + 跳过」。
    原子写：先写 .tmp 再 os.replace——写到一半崩溃不会留下半个坏快照
    （POSIX 上 rename 原子；直接 open(w) 写大文件中途崩 = 文件损坏，恢复时 json.load 就炸）。"""
    data = {"task": task, "remaining": remaining, "done": done, "skipped": skipped}
    tmp = STATE_FILE + ".tmp"
    with open(tmp, "w", encoding="utf-8") as f:
        json.dump(data, f, ensure_ascii=False)
    os.replace(tmp, STATE_FILE)


def load_state():
    if not os.path.exists(STATE_FILE):
        return None
    with open(STATE_FILE, encoding="utf-8") as f:
        return json.load(f)


# ---------- 核心函数：可打断的批量循环 ----------

def run_batch(client, task, items, input_fn=input, done=None, skipped=None):
    """逐条执行批量任务，条与条之间是介入点（本篇全部交互概念的落位处）。
    task 是带 {name} 占位的指令模板（改需求时用户输入的也是这种模板，§6.5 有讨论）；
    done/skipped 供续跑时传入（从 checkpoint 恢复的进度）。
    返回 (done, remaining)——remaining 非空 = 被中止/未做完。"""
    done, skipped = done or [], skipped or []
    queue = list(items)
    total = len(done) + len(queue)
    while queue:
        name = queue[0]
        print(f"\n[批量] 第 {len(done) + 1}/{total} 条：{name}｜当前指令：{task}")
        answer = input_fn("[介入] 回车=执行 / s=跳过 / q=中止并保存 / 输入新指令=改需求 > ")
        cmd = answer.strip()
        if cmd.lower() == "q":                     # 彻底中止：存进度，退出（喊停的应答）
            save_state(task, queue, done, skipped)
            print(f"[批量] 已中止。已完成 {done}；剩余 {queue} 已存任务 checkpoint（可续跑）")
            return done, queue
        if cmd.lower() == "s":                     # 跳过：不执行不重试，记入 skipped
            queue.pop(0)
            skipped.append(name)
            save_state(task, queue, done, skipped)
            print(f"[批量] 跳过 {name}")
            continue
        if cmd:                                    # 改需求：替换指令，当前条目重新面对
            task = cmd
            save_state(task, queue, done, skipped)
            print(f"[批量] 指令已改为：{task}（作用于剩余全部条目，已完成的 {len(done)} 条不追溯）")
            continue
        queue.pop(0)                               # 回车：执行本条（完整 agent loop + guard）
        question = task.replace("{name}", name)
        result = agent.run_safely(client, question)
        done.append(name)
        save_state(task, queue, done, skipped)     # 每条完成即存：崩了最多重做一条
        print(f"[批量] {name} 处理完：{(result or '')[:40]}")
    print(f"\n[批量] 全部完成：{done}（跳过 {skipped}）")
    return done, []

## 本篇结论

1. 打断有三态（插话/喊停/改需求），取消选协作式：检查点定粒度——条与条之间是批量任务的天然位置；已完成的条目不回滚、未开始的不执行，进度落任务 checkpoint（与 16 篇的会话快照互补）。
2. 人工介入按破坏性分级（L0 静默→L3 计划审批），三种方式（确认后继续/修正指令/彻底中止）对应打断三态；guard 管单条、介入点管全局——拒绝一条不等于中止批量，两级各自独立。
3. 长任务三件套：进度可见（第 k/n 条）、断点续跑（原子写 checkpoint）、超时兜底四层各有「之后怎么办」；怪问题大半已有兜底，收拢成速查表——新暴露的并发与限流问题留给第 20 篇。

下一篇：交互关过了，还差最后一道——以什么身份、什么形态、什么边界把助手真正挂到生产系统上。第 20 篇（里程碑 M6）：生产化、安全与既有系统治理。
