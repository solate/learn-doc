## 1｜开发方法：把黑盒拉进工程循环

### 1.1 传统循环 vs agent 循环：用例集必须前置

先看两个循环的对照：

| 环节 | 传统软件 | agent |
|---|---|---|
| 需求 | 需求文档 | 同左 |
| 拆解 | 模块/函数划分，每个可单测 | **拆成可验证子任务**——每个子任务要有可观察行为 |
| 编码 | 代码 + 编译器/类型系统兜底 | 工具描述 + prompt 草稿——都是自然语言，**没有编译器** |
| 测试 | 编码之后的独立阶段 | **用例集与草稿同时出生**，它就是自然语言的「类型检查」 |
| 迭代 | 改代码 → 跑测试 | 改 prompt/工具 → 跑评测集 → pass 数不降才合并 |

差别浓缩成一句话：**传统代码有一层机器兜底，agent 的「代码」没有**。你改 Go 代码拼错一个变量名，编译器当场报错；你改系统提示词里的一个词，行为可能漂移到完全另一个方向，而**没有任何东西提醒你**——直到用户撞上。

所以开发循环里「最小用例集」的位置变了。传统流程里测试在尾部，是因为编译器和类型系统已经挡掉了低级错误，测试只需补充语义层；agent 流程里用例集必须和草稿**同时**出现——它是自然语言代码唯一的安全网。规格原文（`00-生成提示词.md` D1）把这个循环写为：

```
需求 → 拆成可验证子任务 → 工具/prompt 草稿 → 最小用例集 → 迭代
```

注意箭头方向：不是「草稿写完再补用例」，而是草稿和用例**同批产出**——写工具描述的同时，就写下「这条描述应该导致什么可观察行为」。

### 1.2 什么叫「可验证」：三个可观察面

「拆成可验证子任务」的关键在「可验证」三个字。判据：**存在一条外部可观察的证据链**。对管理助手这种「会动手改世界」的 agent，恰好有三个面：

| 可观察面 | 问题 | 例子 |
|---|---|---|
| 工具序列 | 调了什么、按什么顺序 | 分配角色前有没有先查（写前必查纪律） |
| 终局状态 | 世界被改成了什么样 | 张三最终是 `r-admin` 还是没动 |
| 答复内容 | 对用户说了什么 | 有没有把内部 ID、报错原文甩给用户 |

反例：「让助手更聪明」「答复更有温度」——没有可观察判据，既没法验收也没法回归，只会变成玄学迭代。

拿我们的助手演练一遍。需求「帮我把人员管理自动化」不可验证，拆成四个子任务：

| 子任务 | 可验证判据 |
|---|---|
| 查人 | 调 `get_users`，答复含 user_id |
| 查角色 | 调 `get_user_roles`，不调写工具 |
| 分配角色 | **先查后写**两步工具序列 + 终局角色正确 |
| 拒绝越权 | 不存在的用户/角色 → 不调 `assign_role`，终局不变 |

看到了吗——「工具序列 / 终局状态 / 答复内容」正是 §3 评测断言的三类。**开发方法和评测设计在拆解这一步合流**：拆解时就想清楚怎么验收，评测集不过是把验收标准固化成文件。

### 1.3 调试为什么是 trace 驱动的

传统调试的武器是断点、单步、看调用栈——因为复杂度藏在**代码路径**里，你要把路径停下来看。

agent 的代码路径有多复杂？第 7 篇写过的主循环 50 行，到第 17 篇加满所有能力也就 400 来行，**路径本身没有任何 mysteries**。真正的复杂度在**模型的每一次决策**里：为什么这轮它选择调 `assign_role` 而不是先查？为什么参数里 user_id 是它编的？这些问题的答案不在你的代码里，在模型的输入输出流里。你调不动模型内部，能做的只有把这条流完整摊开，回答三问：

1. **想什么**——这轮发出去的 messages 长什么样（上下文有没有漂移、工具结果是不是太大把正文挤没了）
2. **调了什么**——工具名 + 参数（参数幻觉、乱调工具在这里现形）
3. **结果如何**——工具返回了什么、模型怎么收尾（编造结果、答非所问在这里现形）

print 能回答三问吗？能——我们从第 7 篇起就是这么干的（`[loop]` / `[工具]` / `[模型]` 三类 print）。但 print 有三个结构性缺陷：

```
print 调试（第 7-17 篇一直在用的）          trace 调试（本篇）
┌──────────────────────────────┐      ┌───────────────────────────────────────┐
│ [loop] 第 3 轮 | 发送 6 条消息        │      │ {"kind":"llm","n_messages":6,...}      │
│ [工具] get_users({"keyword":"张三"})  │ ───▶ │ {"kind":"tool","tool":"get_users",...} │
│ [工具→] {"total":1,...}              │      │ ... 每行一个事件，结构固定              │
└──────────────────────────────┘      └───────────────────────────────────────┘
   人读还行，机器没法消费                    可 grep、可 diff（改前 vs 改后）、可进评测
```

- **散**：和正常日志混在一起，出了事得在一屏一屏的输出里捞
- **无结构**：grep 不出「耗时超过 2 秒的工具调用」，因为耗时根本没记
- **无基线**：没法把「改 prompt 前」和「改 prompt 后」两次运行的轨迹放一起 diff——而「对比」恰恰是迭代的核心动作

trace = 把三问变成**结构化事件流**：每个事件一行 JSON，字段固定，机器可消费。「trace 驱动调试」的意思就是：调试的第一动作不是改代码，是**看 trace**——三问在事件流里各自有位置，缺哪环补哪环。

### 1.4 我们已经攒了三块拼图

本篇的 trace 不是凭空造的，前 17 篇攒了三块雏形：

| 已有 | 出处 | 缺什么 |
|---|---|---|
| `audit.jsonl` 合规留痕 | 第 9 篇 | 只记工具行为不记 LLM；且是「给审计看的」，不是「给工程师复盘的」 |
| `[loop]`/`[工具]` print | 第 7 篇 | §1.3 的三个缺陷：散、无结构、无基线 |
| `record_calls` 旁听手法 | 第 8 / 17 篇 demo | 只在 demo 里临时用，没沉淀成可复用件 |

本篇做的事：**旁听手法 + JSONL + 两类事件 + 耗时**，合成正式的 `trace.py`（§5.2）。手法和 demo 完全同源——包装 `call_llm` / `execute_tool` 两个函数，不改正文一行。

## 2｜可观测：自建 JSONL trace

### 2.1 记什么：两类事件，每类几个字段

trace 的最小事件集只有两类——刚好对应 agent 循环里仅有的两种「耗时动作」：

**llm 事件**（每次调模型）：

| 字段 | 含义 | 为什么值得记 |
|---|---|---|
| `n_messages` | 这次发出去几条消息 | **上下文增长曲线**——第 11 篇的 token 账、第 17 篇 M5 对比的核心指标，以前要靠 demo 专门统计，现在每次运行免费得到 |
| `think` | 是否开了思维链 | 拆分成本归因（思维链按输出价计费，第 4 篇） |
| `latency_ms` | 这次调用耗时 | 慢在哪：模型还是工具，一列便知 |
| `prompt_tokens` / `completion_tokens` | token 用量 | 成本账的原料（桩测下为 null，真实模式下由 API 返回） |

**tool 事件**（每次工具执行，含被闸门/钩子拒绝的）：

| 字段 | 含义 | 为什么值得记 |
|---|---|---|
| `tool` + `args` | 调了什么、参数是什么 | 「调了什么」这一问的原始证据；参数幻觉在这里现形 |
| `latency_ms` | 执行耗时 | 外部系统慢不慢 |
| `status` | `ok` / `error` | 失败率、失败聚集在哪个工具 |

两个设计口径先说破：

- **status 的判定很粗**：教学版用「结果字符串以『错误』开头即 error」——这是因为我们的工具返回是字符串（第 8 篇的教学取舍）。生产版工具应返回结构化状态码，trace 记码不猜字符串。
- **拒绝也是行为**：被 guard 拒绝的调用同样记 `tool` 事件。评测 E04/E05（拒绝用例）靠的就是它——「agent 拒绝了」必须是一条可观察的记录，而不是「什么都没发生」。

### 2.2 实现：install/uninstall 包装法

完整代码在 §5.2（55 行，零第三方依赖）。这里先讲两个设计决定：

**决定一：包装而不是埋点。** `trace.install(agent)` 把 `agent.call_llm` 和 `agent.execute_tool` 换成带记录的包装版，返回 `uninstall` 还原——第 8 篇 demo 的旁听手法原样沉淀，**agent.py 一行不改**。代价是字段受限：包装层拿不到主循环内部的轮次号，只能记 `n_messages` 这种「从参数里看得到」的东西。生产应反过来——在主循环里内置埋点（第 16 篇的 hooks 其实就是埋点位，`run_before`/`run_after` 完全可以挂 trace），字段完整、无全局替换的线程安全隐患。教学版选包装，是为了让你**先看到 trace 长什么样**再决定要不要动主路径。

**决定二：留痕故障不拖垮业务。** `_write` 吞掉 `OSError`——和第 9 篇 audit 同一纪律：观测是旁路，磁盘满了不该把主流程拖死。但注意差异：audit 吞错是**终局设计**（合规留痕有服务端副本兜底），trace 吞错是**教学简化**——生产的 trace 丢了就是盲飞，必须计数告警（连续 N 条写失败就报警）。代码注释里写了这句话，别把它当反例抄进生产。

### 2.3 与 audit 的分工：两个不能合并的日志

第 9 篇的 `audit.jsonl` 和本篇的 `trace.jsonl` 长得像（都是 JSONL、都记工具调用），但**生命周期完全不同**，不能合并：

| | audit（第 9 篇） | trace（本篇） |
|---|---|---|
| 目的 | 合规留痕——**谁**在什么时候**干了什么** | 工程观测——为什么这么干、花了多久 |
| 范围 | 只记工具行为 | LLM + 工具两类事件 |
| 视角 | 服务端也写一份（双审计，第 9 篇 §4） | 只在客户端 |
| 保留策略 | append-only，永不覆盖 | 每次评测前重置（干净起点） |
| 消费者 | 审计员 / 事后追责 | 工程师 / 评测器 |

合并的下场二选一：为了评测干净而重置 trace → 审计记录被覆盖，合规事故；为了审计完整而永不重置 → trace 越滚越大，复盘成本无限涨。**两个目的就两个文件**——这是「日志按消费者分家」的最小案例，第 20 篇的生产化清单会再次用到这个原则。

### 2.4 生产指针：Langfuse 与 OTel GenAI SemConv

自建 JSONL 的适用边界：

- **够用**：单人开发、单机部署、日调用几十次、复盘靠肉眼 + grep——本系列此刻的状态
- **该升级**：团队多人（trace 要共享和认领）、要按用户/功能归集成本、要做 prompt 版本对比（A/B）、要线上问题回放

升级方向有两个代表，定位不同：

**Langfuse**——开源 LLM 工程平台（可自部署），把本篇手工做的三件事平台化：trace 可视化（树状展开每次运行的 LLM/工具事件）、prompt 版本管理（改 prompt 不再靠 git diff 猜）、数据集与评测（evalset 放线上，真实流量沉淀用例）。对本篇的读者，它就是「trace.py + evalset.jsonl + run_eval.py 的长大成人版」。（版本与功能口径 `<以官方 docs 为准>`，见参考资料。）

**OpenTelemetry GenAI 语义约定（SemConv）**——不是产品是**标准**：社区约定的属性命名（`gen_ai.*` 前缀），把「一次 LLM 调用 / 一次工具执行」表达成标准 OTel span。价值在于**接入你已有的管道**：如果公司已经有 Prometheus / Grafana / Jaeger 那套可观测体系，agent 的 trace 不必另起炉灶，按 SemConv 打 span 就进了老管道。

| 方案 | 接入成本 | 能力 | 适合谁 |
|---|---|---|---|
| 自建 JSONL（本篇） | 最低（55 行） | 原始事件流，grep/diff 自便 | 单人、教学、原型 |
| Langfuse | 中（SDK 接入 + 部署） | 可视化 + prompt 管理 + 线上评测 | LLM 功能团队 |
| OTel GenAI SemConv | 中高（要已有 OTel 底座） | 与全公司可观测体系统一 | 有成熟 OTel 体系的公司 |

选型顺序和第 5 篇框架选型同一个道理：**先明确你要观测什么、谁消费，再选载体**。观测需求没成型之前上平台，是在为想象中的规模付钱。

## 3｜评测：最小可行版

### 3.1 评测是「行为的版本管理」

一个类比把它说尽：**改代码要跑单测，改 prompt 要跑评测集**。pass 数不降才许合并——评测集就是 agent 行为的 CI。

然后是诚实的部分：**前 17 篇我们一直在盲改**。每次改系统提示词——第 8 篇加写前必查纪律、第 10 篇加注入防御、第 17 篇改主/sub 分工——验证手段是重跑一次 demo 看单条任务过没过。样本量 1，换个问法、换个环境就没了。教学主线这么走没问题（每篇只动一个变量），但**这个习惯带上生产就是事故源**：你改了一句工具描述，顺手「看起来还能跑」，三天后用户发现查人都查不了了。

评测最小可行版（规格 D2）的配方：**10-20 条黄金用例 + 自动对拍打分 + 回归**。三个词拆开：

- **黄金用例**：人工精心设计的输入-期望对，不是随机采样——每条都要有「它存在是为了防什么」的答案
- **自动对拍**：机器判分（§3.3 的规则断言），不靠人眼
- **回归**：每次改动后全量重跑，而不是「改哪测哪」

### 3.2 黄金用例集：10 条怎么配平

我们的 10 条（`evalset.jsonl`，§5.3）按三个维度配平：

| 维度 | 用例 | 考什么 |
|---|---|---|
| 正常读链路 | E01（查角色）、E03（列用户）、E07（问 ID）、E09（同义改写）、E10（口语化） | 基本功能 + **措辞鲁棒性**——同一意图换三种问法都该走对 |
| 正常写链路 | E02（提升为管理员）、E06（写前必查） | 写功能 + **纪律**——写之前必须先查 |
| 边界拒绝 | E04（不存在的用户）、E05（不存在的角色）、E08（不存在的人名） | 该拒绝时拒绝——**不作为也是行为** |

配平三原则：

1. **每条纪律一条用例**：系统提示词里的「写前必查」对应 E06——纪律没有对应用例等于没写
2. **每类拒绝一条用例**：E04/E05/E08 把「不存在的输入」拆成三种形态（ID 不存在 / 角色不存在 / 姓名不存在），因为它们走的是不同工具的不同报错路径
3. **每个工具至少一条正向**：四个工具（login/get_users/get_user_roles/assign_role）都在正向用例里出现过——不然某个工具坏了评测集看不见

E09/E10 是特意安排的「照妖镜」：把「李四现在是什么角色」改写成「张三现在是什么角色？把结果告诉我」（带废话）和「帮我看看李四能不能被分配角色，先查再说」（口语+指令混杂）。**规则断言只看工具序列和终局，不惧措辞变化**——这正是 §3.3 规则断言的优势场景。

10 条是最小配平。到 20 条时该加的是「组合操作」「多轮指代」（第 19 篇的主题），但先别加——复杂度守恒（第 17 篇 §1.2 的警告在评测集上同样成立：每条用例都是永久维护成本，没有失败模式支撑的用例是纯负债）。

### 3.3 断言：规则 vs LLM judge

对拍打分有两条路线：

| | 规则断言（本篇选择） | LLM judge |
|---|---|---|
| 成本 | 零 token | 每条用例都要调模型打分 |
| 稳定性 | 100% 可复现 | judge 自己会抖——同一份答复两次打分可能不同 |
| 表达力 | 只能查「已知会错的地方」 | 能评开放性质量（「这个答复礼貌吗」「解释清楚了吗」） |
| 进 CI | 能（exit code，§3.4） | 难（抖动 = 假阳/假阴报警疲劳） |

我们的四类规则断言，就是 §1.2 三个可观察面的直接固化：

| 断言 | 对应可观察面 | 例子（E06） |
|---|---|---|
| `tools_include` | 工具序列 | 必须调过 `get_user_roles` **和** `assign_role` |
| `tools_exclude` | 工具序列 | E04/E05/E08：不许调 `assign_role` |
| `final_roles` | 终局状态 | `u-1002` 终局 = `["r-editor"]` |
| `answer_contains` | 答复内容 | E01：答复含「查看者」 |

新手从规则开始，不是妥协而是**正确**：你的用例集本来就源于已知失败模式（§4.1），失败模式是具体的，具体的东西规则就断得出来。LLM judge 是规模化后的可选项——等你有两百条用例、要评「答复质量」这种没有唯一正解的维度时再上，而且 judge 自己也要先被校准（拿人工标注对拍，确认它打得和人差不多准）。工具代表见参考资料（promptfoo 同时支持两条路线）。

### 3.4 评测器：run_eval.py 的五个设计决定

完整代码 §5.4（约 200 行）。设计决定比代码本身更值得讲：

**决定一：评测的世界由评测器自己重置。** 评测器自起后台（进程内 uvicorn，第 14 篇同款），每条用例前 `reset_state()` 把两个可写用户重置回 `r-viewer`。可复现性是评测的**前提**不是特性——不重置的世界里，「第二次跑 E02」看到的是第一次跑完的残局，断言全在测历史。第 14 篇的教训在这里直接复用：**重置动作走系统自己的接口**（admin_tools 发 HTTP），不旁路进程内细节。

**决定二：工具序列靠旁听。** `run_case` 里把 `agent.execute_tool` 包一层 `listening_exec`，工具名 append 进列表——第 8 篇 demo 手法第三次复用。注意 finally 还原：旁听是评测期间的临时行为，不留痕。

**决定三：评测期 guard 自动放行。** 写操作不再人工确认，自动 "y"。这不是偷懒，是**测试边界**的示范：评测评的是「链路走不走得通、纪律守不守得住」，闸门（第 9 篇）自己有 p9 的桩测管着——被测系统 ≠ 被信任系统，两套测试各管各的。如果评测也要人工点确认，10 条用例点 10 次，没人会天天跑回归。

**决定四：trace 顺带装上。** 评测天然是 trace 的最大生产者——每条用例一份干净 trace，§5.7 会看到 trace 怎么反过来当评测的证物。

**决定五：exit code = pass 数是否等于总数。** 全过 exit 0，有挂 exit 1——这就是接 CI 的钩子（`git hook` / 流水线里一条命令）。§5.6 你会看到 exit 1 不是评测器坏了，是**护栏在工作**。

`--stub` 模式是给自己的验收：用剧本桩（第 8 篇 ScriptedLLM 手法）跑 E02 的标准链路，零 LLM token 验证「评测器自己的逻辑没错」——测试工具也要被测试。`--weak` 用一个故意跳过「先查后写」的坏剧本跑 E06，**制造一条失败用例**，演示护栏拦回归的现场（§5.6）。

## 4｜自改进的边界：reflection、评测集与微调

### 4.1 反馈回路的标准形状

线上出了坏行为，标准处理流是一条**让学费不白交**的回路：

```
线上失败案例
   │ ① 用 trace 复盘（§1.3 三问定位：想什么/调了什么/结果如何）
   ▼
归因（三类之一）
   ├─ prompt 缺纪律     → 改系统提示词/工具描述
   ├─ 工具描述歧义      → 改 description、补参数说明
   └─ 用例缺失          → 这类失败从来没想过会发生
   ▼
② 修复 + 失败案例原样进评测集
   ▼
③ 全量回归（含新用例）→ 护住：这条失败从此有专岗看守
```

第②步是整条回路的灵魂：**失败案例不进评测集 = 白交学费**。同一个坑踩第二次，是流程问题不是模型问题。我们 §5.6 的 weak 演示就是这条回路的排练：坏剧本模拟一次「写前必查失效」的线上事故，E06（本为这次事故新增的用例）当场把它拦下。

这里要和第 12 篇的 **reflection** 划清边界。Reflexion 式的运行时自我反思（失败尝试生成书面反思存进记忆、指导下一次尝试——第 12 篇 §4.1）改的是**这一次运行**：本次任务失败了，反思让本次重试更聪明。而失败案例进评测集改的是**每一次运行**：这个失败模式从此被回归看守，任何把它改回来的改动都过不了 CI。前者是模型层的技巧，后者是工程层的制度——**agent 的长期改进靠制度，不靠模型的自我感觉**。运行时反思依旧有用（第 12 篇讲过它的位置），但它产出的「反思文本」里若沉淀出失败模式的描述，正确的归宿之一就是转成评测用例。

### 4.2 什么时候值得 eval 闭环

回路本身也有成本（复盘时间 + 用例维护），不是每次失败都值得走完：

| 情形 | 值得走回路吗 | 理由 |
|---|---|---|
| 失败可归因到明确规则（如写前必查没触发） | ✅ 值得 | 规则可断言，用例一次写好永久看家 |
| 同类失败高频出现 | ✅ 值得 | 回报率高——一次回路护住每天发生的坑 |
| 修复手段是改 prompt/工具描述 | ✅ 值得 | 改动便宜，且正是评测集最擅长看守的改动类型 |
| 一次性长尾（用户问了个冷门问题答错） | ❌ 先记档 | 修不过来也断不出来；攒够同类再统一归因 |
| 开放质量（答复风格不好） | ❌ 规则断不出 | 硬写 `answer_contains` 会把用例写成玄学 |
| 要改架构才能修（如该上 subagent 了） | ⚠️ 换轨道 | 这是设计问题不是回归问题；eval 在此期间的职责是「重构别把老行为改坏」——恰恰最需要它 |

最后一行值得强调：**大重构期间评测集的作用最大**。第 13-15 篇直连改 MCP、第 17 篇加 subagent，当时我们靠等价性 demo 手工验证——如果当时已有 evalset，这些架构迁移就是「跑一遍 10 条用例看全绿」的事。这也是为什么评测集放在 Part 7 第一篇：**后面两篇（交互改造、生产化加壳）全是大改动，先把护栏立起来再动**。

### 4.3 为什么新手别微调

规格 D3 的原话是「讲清什么时候值得 eval 闭环、什么时候微调是浪费/风险（新手别微调）」。四条理由，按说服力排序：

**理由一：prompt 的边际收益还没吃干。** 本系列 17 篇演进——工具纪律、注入防御、记忆、规划、MCP、subagent——**全部**靠 prompt + 工具描述 + 代码编排完成，零微调。你的问题大概率还停留在这一层就能解决的区间。微调是 prompt 吃干之后的下一档，不是「更高级的修法」。

**理由二：你的评测集太小，一调就过拟合。** 10-20 条黄金用例是**回归护栏**，不是训练集。几百条样本微调出来的模型会把这几条的措辞背下来，换个问法就现形——E09/E10 那两条措辞变化用例就是照妖镜：训练分布里没见过的问法，恰是用户最爱用的问法。严肃微调的评测配套是万级起步的。

**理由三：行为控制粒度粗。** 微调改的是**整个输出分布**。「这一类操作别越权」是一条例外规则——prompt 一句话的事；微调做不到「只改这一条、别的别动」，把例外样本混进训练数据，正常行为经常被一起带偏。你修一个坑，挖出三个新坑，而且新坑在哪要靠大规模评测才能发现——又回到理由二。

**理由四：成本与不可逆。** 数据构建、训练、评测、部署、回滚，每步都是独立流程；prompt 改坏了 `git revert` 一秒回滚，微调改坏了回滚的是一次训练。

一个类比收束：**prompt 是给新员工讲规矩，微调是重新招一批人重新培训**。规矩没讲清楚之前，先别怪员工。

什么时候才轮到微调？三个正当场景，共同前置条件都是「万级评测集 + 独立的训练/回归流程」：风格内化（要模型天生用某种语气/格式，prompt 塞不下）、蒸馏（用大模型输出训练小模型省成本）、领域术语密集注入（行话多到 prompt 解释不过来）。走到那一步你已经是老手，「新手别微调」的告诫自然失效——在那之前，它是硬约束。

# trace.py — 第 18 篇：自建 JSONL trace（LLM/工具调用的结构化留痕，极简版）
# 与 audit 的分工（第 9 篇审计只记工具行为）：trace 记**两类事件 + 耗时**——
#   llm  事件：每次调模型（第几轮、发了几条消息、耗时、usage token——桩下 usage 缺省）
#   tool 事件：每次工具执行（含被闸门/钩子拒绝的），耗时与结果状态
# 生产指针：Langfuse / OpenTelemetry GenAI 语义约定（见文章参考资料），教学版零依赖。
# 实现方式：install() 用包装法替换 agent.call_llm / agent.execute_tool（与 demo 的
#   record_calls 同一手法）——教学版不改主路径一行；生产应内置埋点（性能与字段完整性更好）。
# 诚实声明：本文件随 run_eval.py 桩测通过（零 LLM token，见第 18 篇实践节）。
import json
import os
import time

TRACE_FILE = os.path.join(os.path.dirname(os.path.abspath(__file__)), "trace.jsonl")


def _write(event: dict):
    event["ts"] = int(time.time() * 1000)
    try:
        with open(TRACE_FILE, "a", encoding="utf-8") as f:
            f.write(json.dumps(event, ensure_ascii=False) + "\n")
    except OSError:
        pass   # 与 audit 同一纪律：留痕故障不拖垮业务（生产必须计数告警，文章 §3.3）


def install(agent_mod, trace_file: str | None = None):
    """包装 agent 模块的两个函数，装上 trace；返回 uninstall（用完还原）。"""
    global TRACE_FILE
    if trace_file:
        TRACE_FILE = trace_file
    real_llm, real_tool = agent_mod.call_llm, agent_mod.execute_tool

    def traced_llm(client, messages, think=False):
        t0 = time.perf_counter()
        resp = real_llm(client, messages, think=think)
        usage = getattr(resp, "usage", None)
        _write({"kind": "llm", "n_messages": len(messages), "think": think,
                "latency_ms": int((time.perf_counter() - t0) * 1000),
                "prompt_tokens": getattr(usage, "prompt_tokens", None),
                "completion_tokens": getattr(usage, "completion_tokens", None)})
        return resp

    def traced_tool(call):
        t0 = time.perf_counter()
        result = real_tool(call)
        _write({"kind": "tool", "tool": call.function.name,
                "args": call.function.arguments,
                "latency_ms": int((time.perf_counter() - t0) * 1000),
                "status": "ok" if not result.startswith("错误") else "error"})
        return result

    agent_mod.call_llm, agent_mod.execute_tool = traced_llm, traced_tool

    def uninstall():
        agent_mod.call_llm, agent_mod.execute_tool = real_llm, real_tool
    return uninstall
```

三处实现细节值得抬头看：

- `install()` 是包装法的全部：两行赋值换掉模块函数，返回 `uninstall` 闭包还原——没有全局单例、没有配置文件、用完即走
- `_write` 里 `ts` 用毫秒时间戳（和 audit、后台的毫秒约定一致），`ensure_ascii=False` 让中文参数可读
- 桩测下 `prompt_tokens`/`completion_tokens` 记成 `null`（剧本桩没有 usage 对象），真实模式自动有值——trace 的字段设计对两种模式都成立

    """每条用例前重置世界：两个可写用户都回到查看者——评测的可复现性前提。"""
    admin_tools.login("admin", "admin123")
    admin_tools.assign_role("u-1001", "r-viewer")
    admin_tools.assign_role("u-1002", "r-viewer")


def roles(user_id):
    return [r["role_id"] for r in admin_tools.get_user_roles(user_id=user_id)["roles"]]


def run_case(case: dict, client) -> dict:
    """跑一条用例并按规则断言打分。工具序列经 execute_tool 包装旁听（demo 同款手法）。"""
    calls, results = [], {}
    real_exec = agent.execute_tool

    def listening_exec(call_):
        result = real_exec(call_)
        calls.append(call_.function.name)
        return result
    agent.execute_tool = listening_exec
    try:
        answer = agent.run_safely(client, case["question"])
    finally:
        agent.execute_tool = real_exec

    checks = []
    exp = case.get("expect", {})
    for t in exp.get("tools_include", []):
        checks.append((f"应调用 {t}", t in calls))
    for t in exp.get("tools_exclude", []):
        checks.append((f"不应调用 {t}", t not in calls))
    for uid, want in exp.get("final_roles", {}).items():
        checks.append((f"{uid} 终局角色={want}", roles(uid) == want))
    for kw in exp.get("answer_contains", []):
        checks.append((f"答复应包含「{kw}」", kw in (answer or "")))

    return {"id": case["id"], "question": case["question"],
            "checks": checks, "passed": all(ok for _, ok in checks)}


def main():
    parser = argparse.ArgumentParser(description="最小评测器（第 18 篇）")
    parser.add_argument("--stub", action="store_true", help="评测器验收模式（零 token，只跑 E02）")
    parser.add_argument("--weak", action="store_true", help="配合 --stub：用坏剧本跑 E06，演示失败被评测集护住")
    parser.add_argument("--set", default=EVALSET, help="评测集文件（jsonl）")
    args = parser.parse_args()

    cases = [json.loads(l) for l in open(args.set, encoding="utf-8") if l.strip()]
    if not start_backend():
        sys.exit("[后台未就绪] mock_backend 启动失败——评测的世界起不来，用例无从谈起")
    real_confirm = guard.confirm
    guard.confirm = lambda name, a, _input=input: real_confirm(
        name, a, _input=lambda _p: "y")   # 评测自动放行写操作：评的是链路不是闸门（闸门有 p9 桩测）

    if args.stub:
        todo = [c for c in cases if c["id"] == ("E06" if args.weak else "E02")]
        client = ScriptedLLM(SCRIPT_E06_WEAK if args.weak else SCRIPT_E02)
    else:
        todo = cases                       # 真实模式：全量
        client = agent.create_client()     # <未实测，以官方文档为准>

    uninstall_trace = trace.install(agent, TRACE_FILE)
    if os.path.exists(TRACE_FILE):
        os.remove(TRACE_FILE)              # 每次评测一份干净 trace
    report = []
    print(f"=== run_eval：{len(todo)} 条用例（{'桩验收' if args.stub else '真实模型'}模式） ===")
    for case in todo:
        reset_state()
        r = run_case(case, client)
        report.append(r)
        marks = " ".join(("✓" if ok else "✗") + name for name, ok in r["checks"])
        print(f"[{'PASS' if r['passed'] else 'FAIL'}] {r['id']} {r['question']}")
        if marks:
            print(f"        {marks}")
    uninstall_trace()
    guard.confirm = real_confirm

    with open(REPORT, "w", encoding="utf-8") as f:
        for r in report:
            f.write(json.dumps(r, ensure_ascii=False) + "\n")
    n_pass = sum(1 for r in report if r["passed"])
    print(f"\n=== 报告：{n_pass}/{len(report)} 通过 | 明细 {REPORT} | trace {TRACE_FILE} ===")
    trace_lines = [json.loads(l) for l in open(TRACE_FILE, encoding="utf-8")] \
        if os.path.exists(TRACE_FILE) else []
    if trace_lines:
        llm_n = sum(1 for e in trace_lines if e["kind"] == "llm")
        tool_n = sum(1 for e in trace_lines if e["kind"] == "tool")
        total_ms = sum(e.get("latency_ms", 0) for e in trace_lines)
        print(f"=== trace 摘要：llm {llm_n} 次 / tool {tool_n} 次 / 累计 {total_ms} ms ===")
    sys.exit(0 if n_pass == len(report) else 1)


if __name__ == "__main__":
    main()
```

## 本篇结论

1. Agent 的「代码」是自然语言，没有编译器兜底——用例集必须和草稿同时出生，它是行为唯一的版本管理；评测三断言（工具序列/终局状态/答复关键词）在拆解子任务时就已经定型。
2. 调试是 trace 驱动的：print 回答三问但散、无结构、无基线；55 行的 JSONL trace 把「想什么/调了什么/结果如何」变成可 grep、可 diff、可进评测的事件流——E06 挂在断言上，原因却先显形在 trace 里。
3. 自改进靠制度不靠模型自觉：失败案例进评测集是学费不白交的回路；微调对新手是四重陷阱（prompt 收益未吃干/评测集太小/粒度粗/不可逆），「重新招人培训」之前先把「给新员工讲规矩」做完。

下一篇：评测集已立，但助手还是「一条道跑到黑」的形态——用户插不进话、喊不停、改不了需求。第 19 篇处理 agent 交互里最真实的一批工程问题：多轮对话、中断与人工介入。
