## 1｜分界线：从"聊天"到"自主 agent"

读完本节你能理解：为什么"会调用工具"和"能自主干活"是两回事，以及"自主"这个词的准确含义。

### 1.1 三级能力阶梯

同样是"用大模型"，按能力可以分成三级，逐级上升：

```
第 0 级  普通聊天 (chat)
  你 -> "张三是谁?"  ->  模型 -> "张三是个常见的名字…"
                              只能靠训练时记住的知识，读不到你系统里的数据

第 1 级  单次工具调用 (function calling / tool use)
  你 -> "查张三"  ->  模型: "我要调 get_user(name=张三)"
                        -> 你的代码真去查 -> 结果喂回 -> 模型答 "张三，ID 1001"

第 2 级  自主 agent (autonomous agent)
  你 -> "把张三账号停用，顺便看看他有没有超额"
       -> 模型自己决定: 先查用户 -> 再查订单 -> 最后调停用接口
          （几步、什么顺序、要不要重试，都是模型当场定的）
```

区分这三级的不是"模型聪不聪明"，而是**控制流（control flow）由谁掌握**：

- 第 0、1 级：下一步做什么，**写死在你的代码里**。
- 第 2 级：下一步做什么，**模型在运行时自己决定**；你的代码退居"执行器 + 回传结果"。

对后端工程师有个熟悉的类比：第 1 级像你写死的一条调用链 `A -> B -> C`；第 2 级则是把 `A/B/C` 交给一个"看情况自己挑"的调度器，而且它挑的顺序你事先不知道。

### 1.2 "自主"的准确含义

"自主（autonomous）"在 agent 语境里**不是"无人监管"，而是"由模型自己决定行动序列"**。这个划分最常被引用的出处是 Anthropic 的 *Building Effective Agents*：

- **Workflow（工作流）**：LLMs and tools are orchestrated through **predefined code paths**——路径预先写在代码里。
- **Agent（智能体）**：LLMs **dynamically direct their own processes and tool usage**, maintaining control over how they accomplish tasks——模型动态决定自己的流程与工具使用。

一句话记法：**路径写死在代码里 = workflow；路径由模型当场决定 = agent。**

### 1.3 什么时候用 workflow，什么时候才上 agent

"自主"不是免费的：路径由模型决定，就意味着**不确定、更贵、更难调**。所以分界线不是"越自主越高级"，而是"任务路径能不能预先写死"。这正是 Anthropic 反复强调的一条——能用简单方案解决的就别上 agent。

| 维度 | Workflow | Agent |
|---|---|---|
| 路径由谁定 | 开发者，写在代码里 | 模型，运行时决定 |
| 适合任务 | 步骤固定、可预测 | 步骤数无法预判、开放式的任务 |
| 可预测性 | 高 | 低 |
| 成本 / 延迟 | 低 | 高，多一步就多一次模型调用 |
| 调试 | 容易，失败能定位到某一步 | 难，需要 trace 和护栏 |

具体到本书主线——"后台管理助手"（Go 后台 + RBAC + 多租户）：

- 如果需求永远是"查用户 -> 展示"，那是**一条固定流程**，用 workflow 足矣，别上 agent。
- 一旦需求变成"我说一句话，你自己决定要不要登录、先查谁、要不要改角色"，路径无法预先写死，才轮到 agent（这也是第 8 篇要接上的场景）。

> 一个容易被混淆的点：**"是否每步都问人"（人机协同）和"路径谁定"是两件独立的事**。一个 agent 可以每一步都停下来等你确认，仍然是 agent；一条 workflow 也可以全自动跑完。本篇说的"自主"只指后者——路径谁定。

## 2｜一次 tool call 全流程拆解

读完本节你能理解：从你打一句话到模型返回结果，中间到底有哪几步、哪几步在你的代码里发生。这是全系列最重要的一张时序图。

### 2.1 谁在干活：三方分工

先记住角色，再看时序：

- **你的程序**（agent 代码 / harness）：唯一能真正"干活"的一方——发 HTTP 请求、查数据库、调接口。
- **模型（LLM）**：只会"写文本"。它**不能自己发 HTTP、不能连你的数据库**，它只能"说"——包括说出"我想调哪个工具、参数是什么"。
- **工具（tool）**：你注册给模型的那些能力，本质是一段你的代码（打个 REST 接口、跑个 SQL）。

关键认知：**模型输出的是"意图"，不是"执行"**。真正把意图变成动作的，永远是你的代码。

### 2.2 一次 tool call 的时序图

下面这张图是全书的地基。左边是"你的代码"，中间是"模型服务"，右边是"真实世界（你的后台）"：

```
  你的代码 (harness)              模型服务 (LLM API)            真实世界 (后台)
       |                                |                            |
  (1)  |--- messages + tools ---------> |                            |
       |    "查张三"                      |                            |
       |    工具清单: get_user/assign...  |                            |
       |                                |                            |
       |                          (2) 模型"看到"有这些工具           |
       |                              决定: 该调 get_user           |
       |                                |                            |
  (3)  |<-- tool_calls: -------------- |                            |
       |    [{name:"get_user",           |                            |
       |      arguments:'{"q":"张三"}'}] |                            |
       |    stop_reason: "tool_use"      |                            |
       |                                |                            |
  (4)  |--- 你的代码解析参数、校验、         |                            |
       |    真正发起 HTTP / 查询 -----------+-------------------------> |
       |                                |      GET /api/v1/users?q=张三 |
       |                                |                            |
  (5)  |<-- 真实结果 (200, JSON) ----------+----------------------------|
       |                                |                            |
  (6)  |--- 把结果作为 tool_result -------> |                            |
       |    追加进 messages，再请求一次      |                            |
       |                                |                            |
       |                          (7) 模型基于结果继续              |
       |                              要么再调工具、要么收尾         |
       |                                |                            |
  (8)  |<-- 最终自然语言答复 ------------- |                            |
       |    "张三是 admin，已停用"          |                            |
```

要点：

- **(2) 是"决策"，不是"执行"**。模型只是决定要不要调、调哪个、参数填什么——它一个字节都没发出去。
- **(4) 是你的代码在干活**。真正发起 HTTP、查库、写库的，永远是你的程序。
- **(6) 是"循环"的来源**。把工具结果喂回去再问一次；如果模型还想调工具，就回到 (3)，循环下去——这就是 agent loop 的雏形（第 3 篇展开）。

### 2.3 消息里到底传了什么

模型不认识你的函数，只认识一串**结构化的消息**。以 OpenAI 兼容接口（DeepSeek 即用此格式）为例，一次往返大致是这样四种角色在轮转：

```
system      : "你是后台管理助手，只能查当前租户的数据…"   ← 规则
user        : "查一下张三"                              ← 人的话
assistant   : tool_calls=[{name:"get_user", args:{...}}]  ← 模型要调工具
tool        : tool_call_id=xxx, content="{...真实结果...}"  ← 工具结果喂回
```

三种主流接口对这套消息的字段命名略有差异（OpenAI 用 `tool_calls`；Anthropic 用 `tool_use` / `tool_result` 内容块 + `stop_reason:"tool_use"`；DeepSeek 走 OpenAI 兼容格式），但**机制完全一样**：模型产出"调用意图" -> 你的代码执行 -> 结果回填 -> 再问模型。第 6 篇会把三种姿势并排拆开对比。

## 3｜为什么需要 agent 这一层：它是编排层

读完本节你能理解：为什么"模型 + 工具"之外必须再有一层代码，这一层到底解决什么问题。

把上一节的图压缩成一句话矛盾：

- **模型不会发起 HTTP**——它只会生成文本，天生够不着你的后台。
- **代码不会决定下一步**——它是确定性的，不会"看情况挑工具、根据结果改主意"。

两边各缺一半：模型有"判断力"但没"手脚"，代码有"手脚"但没"判断力"。**agent 就是补上这个缺口的编排层（orchestration layer）**：把模型的判断翻译成真实动作，再把真实结果翻译回模型的输入，循环往复。

用后端语言类比，这层很像你熟悉的 **Controller / Service 编排**，只不过原来由人写的 `if/else` 决策，现在换成了模型输出：

```
传统编排（你写死）              agent 编排（模型定）
--------------------------    --------------------------
if (needUser) {               while (!done) {
    user = queryUser();         resp = llm(messages, tools)
}                               if (resp.wantsTool) {
if (user.needRole) {               result = exec(resp.tool, resp.args)
    assignRole(user);              messages += result
}                               } else { done = true }
                              }
```

这层代码在业界有个名字：**harness（智能体运行时）**——驱动"感知 -> 思考 -> 行动 -> 观察"循环的那套工程化基础设施。它要处理的全是后端工程师熟悉的问题：工具怎么注册、参数怎么校验、结果怎么回填、循环怎么终止、出错怎么兜底、上下文会不会爆。第 3 篇会把 harness 拆到底。

> 一句话记住本篇的立场：**agent 不是玄学，是一层你亲手写的编排代码。** 模型的"智能"只是这层代码里的一个函数调用。

## 4｜核心词表：先把六个词钉死

读完本节你能理解：后面 20 篇反复出现的六个词，各指什么。每个都先给大白话，再给准确定义与出处。这是全书唯一的装饰性速查表，正文不再重复罗列。

**LLM（Large Language Model，大语言模型）**
大白话：一个"根据前文猜下一个词"的巨型函数，猜得足够好，看起来就像会思考。
定义：在海量文本上训练、以自回归方式逐个 token 预测输出的神经网络语言模型。本书默认的 DeepSeek 模型即 OpenAI 兼容接口的 LLM。

**Prompt（提示词）**
大白话：你发给模型的那段话——既有"你要扮演什么角色"的规矩，也有用户的问题。
定义：提交给模型的完整输入文本，通常分 `system`（系统规则）、`user`（用户输入）、`assistant`（模型上一轮输出）等角色。工程上"prompt 怎么写"直接决定 agent 质量。

**Function Calling（函数调用）** 与 **Tool Use（工具使用）**
大白话：让模型"点菜"——你给它一份菜单（工具清单），它说"我要点第 3 道，参数是这些"，但**做菜还是你来做**。
定义：把工具的 JSON Schema 描述随请求一起发给模型，模型返回结构化的调用意图（工具名 + 参数），由调用方执行后再把结果回填的机制。OpenAI 侧称 *function calling*，Anthropic 侧称 *tool use*，两者是同一个机制的不同叫法。**注意：模型从不执行你的函数**——官方文档明确写着实现由你提供。

**Workflow vs Agent（工作流 vs 智能体）**
大白话：同样是"用模型干活"，一个是"照着剧本走"（workflow），一个是"见招拆招"（agent）。
定义：Anthropic *Building Effective Agents* 的原始区分——workflow 是 "LLMs and tools are orchestrated through predefined code paths"（路径预先写在代码里）；agent 是 "LLMs dynamically direct their own processes and tool usage"（模型动态决定自己的流程与工具使用）。判定只看一条：**控制流归谁**。

**Harness（智能体运行时 / agent loop 的工程化实现）**
大白话：把"问模型、执行工具、喂回结果、再问"这个循环真正跑起来的那层代码，以及配套的工具注册、权限、日志、持久化。
定义：驱动 agent"感知 -> 思考 -> 行动 -> 观察"循环的工程化运行时。它不是模型的一部分，而是环绕模型的基础设施。成熟参考包括 Claude Code、Cursor、OpenHands、OpenClaw。本系列第 3 篇专讲它，第 6 篇借拆解成熟系统深化。**注意**：行业对 harness 尚无唯一权威定义，此处采用本系列的约定用法（与提示词规格一致）。

> 六个词的关系一句话串起来：**LLM** 读 **Prompt**，通过 **Function Calling / Tool Use** 点菜，**Harness** 负责把菜做好并让它接着点，而这一切的"路径是写死还是自定"就决定了它是 **Workflow** 还是 **Agent**。

## 5｜学习路线图：21 篇怎么走，学完能做出什么

读完本节你能理解：整本书的 8 个 Part 各自解决什么问题、每学完一个 Part 你能看到什么成品，以及怎么自测。

全系列围绕**一个 demo**（后台管理助手，Go 后台 + RBAC + 多租户）演进，遵循"需求驱动"：先给你一个能干的底板，再依次暴露它的短板、用新能力补齐，最后工程化收口。

### 5.2 8 个 Part × 里程碑

每个 Part 以一个**看得见的成品**收口。学到哪、离毕业多远，一眼可辨：

**必修 vs 选学**：

- **必修**：P1-P3（心智 + 第一个 agent + 主线 demo）、P7（能不能上线的分水岭）。
- **强烈建议**：P4（记忆/规划是 agent 从玩具变工具的关键）、P5（MCP 是 2025-2026 事实标准）。
- **按需/选学**：P6（多智能体复杂度高，先掌握单 agent 再上；本书会明说"什么时候不该用"）、P8（视野篇，不写新代码）。
- **可跳读**：第 2 篇经典理论（P1）——若只想动手，可以先做第 3 篇回来看；但认真读它，后面每个设计决策都会对上号。

### 5.3 怎么自测：三个门槛

不用等学完，每过一个 Part 就自测一次——**能讲清楚、能指出取舍、能跑起来**，三条都过才算真学会：

1. **能讲清楚**（P1 起）：不看笔记，用 PMTA（Planning / Memory / Tool use / Action，第 2 篇定义）拆解一个现成 agent（比如你正在用的 Claude Code），逐个指认构件。
2. **能指出取舍**（P2 起）：对任一设计选择说出"什么时候不用它"——例如"这条任务该用 workflow 还是 agent""该手写还是上框架"。
3. **能跑起来**（P3 起）：每过一个里程碑，不看教程把成品重跑一遍并看到预期输出（P2 的 M1 起，每个里程碑都带运行命令 + 预期输出 + 自检清单）。

> 一个反直觉的自测信号：如果你把某篇的知识点背得很熟，却说不出"不这么做会出什么事故"，说明还没真懂。本系列每个设计都从"解决什么问题 / 不解决会出什么事故"讲起，就是为了防这个坑。

## 动手实践：亲眼看到一次结构化 tool call

读完本文你能验证：模型返回的不是一段散文，而是**结构化的调用意图（工具名 + 参数）**——这是后面所有 agent 代码的原材料。这是本书第一个、也是最小的实验。

### 准备

需要一个支持 function calling、且 OpenAI 兼容的模型服务。本系列默认用 DeepSeek（国产、便宜、国内直连）：

```bash
# 1) 建虚拟环境（uv 或 pip 二选一）
uv venv && source .venv/bin/activate        # 或用: python -m venv .venv && source .venv/bin/activate
# 2) 装 SDK（国内可加镜像：-i https://pypi.tuna.tsinghua.edu.cn/simple）
pip install openai
# 3) 配置 key（不要把 key 写进代码或用 git 跟踪）
export DEEPSEEK_API_KEY="sk-你的key"          # 到 https://platform.deepseek.com 申请
```

### 脚本（整段，可直接跑）

保存为 `demo_tool_call.py`。注意：这段代码<未实测，以官方文档为准>——它只是"触发一次 tool_use 返回"，不执行任何真实查询。

```python
# demo_tool_call.py —— 最小验证：亲眼看一次结构化的 tool call
# <未实测，以官方文档为准>
import json
import os
from openai import OpenAI

# DeepSeek 提供 OpenAI 兼容接口：只改 base_url + key 即可换供应商
client = OpenAI(
    api_key=os.environ["DEEPSEEK_API_KEY"],
    base_url="https://api.deepseek.com",
)

# 给模型的"菜单"：一个工具的 JSON Schema 描述
tools = [{
    "type": "function",
    "function": {
        "name": "get_user",
        "description": "按姓名查询后台用户，返回用户ID、状态、角色。",
        "parameters": {
            "type": "object",
            "properties": {
                "name": {"type": "string", "description": "用户姓名，如 张三"},
            },
            "required": ["name"],
        },
    },
}]

resp = client.chat.completions.create(
    model="deepseek-flash",                      # 现行模型名；旧名 deepseek-chat 已停用（考据见第 4 篇 §1.2）
    messages=[{"role": "user", "content": "帮我查一下张三"}],
    tools=tools,                                 # 把菜单一起发过去
)

choice = resp.choices[0]
msg = choice.message
print("finish_reason:", choice.finish_reason)    # 期望: tool_calls

if msg.tool_calls:
    call = msg.tool_calls[0]
    print("tool name :", call.function.name)                  # 期望: get_user
    print("arguments :", json.loads(call.function.arguments)) # 期望: {'name': '张三'}
else:
    print("模型没调工具，直接答:", msg.content)
```

### 运行与预期输出

```bash
python demo_tool_call.py
```

期望看到（**注意 `arguments` 是一个可被 `json.loads` 解析的字符串——这就是"结构化参数"**，不是一段散文）：

```
finish_reason: tool_calls
tool name : get_user
arguments : {'name': '张三'}
```

如果 `finish_reason` 是 `tool_calls`、且能解析出 `{'name': '张三'}`，说明你已经亲手触发了 agent 的最基本动作。**这一步成功后你会立刻意识到**：模型只"点了菜"（`get_user` + 参数），却没查任何数据——查数据必须由你的代码来做（回到第 2 节的时序图 (4)）。

> 想省 token：这个实验每次只花几十个 token。若模型偶发不调工具（直接回答"我没有查询能力"），把系统提示写得更明确，或在 `messages` 里补一句 "必要时请调用工具再回答" —— 这也是第 4 篇"提示策略"的伏笔。
>
> 换供应商：把 `base_url` 改成通义/智谱的 OpenAI 兼容地址、`model` 换成对应模型名即可（第 4 篇给全表）。模型名与地址以各家官方 docs 为准，本书不逐一锁死。

## 本篇结论

Agent 不是玄学，而是一层你亲手写的编排代码（harness）：模型负责"判断"，你的代码负责"执行"，两者靠结构化的 tool call 消息往返。
判定 workflow 还是 agent，只看一件事——控制流由代码预先写死，还是由模型运行时决定。
