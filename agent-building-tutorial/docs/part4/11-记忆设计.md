## 1｜痛点回放：为什么"记不住"

第 10 篇收口时预告的两个痛点，第一个就是它。现场是这样的：

```text
$ python main.py "帮我看下张三现在是什么角色"
  → login → list_users → get_user_roles → 回答完毕

$ python main.py "那把他也加上运营吧"          ← 新进程
  → login → ……"他"是谁？"也"是什么？助手一脸茫然。
```

信息在三个层次上丢失，一层比一层深：

| 层 | 丢什么 | M2 现状 |
|---|---|---|
| 进程 | 本次运行的全部状态（token、消息） | 每条命令新进程，全丢 |
| 上下文窗口 | REPL 多轮后历史装不下 | 还没走到（每轮都是"第一轮"） |
| 跨会话 | 用户偏好、历史决策 | 每次都当陌生人，偏好重说 |

P2·3 讲过一个关键认知：agent 的"记忆"从来不是模型自带的能力，而是**你喂给它的
messages**——喂什么记得什么，进程一死全没。所以"记忆"是 host 层（harness）的工程
问题，不是模型的义务。

那"把历史全塞回去"行不行？三个理由说不行：

1. **成本线性涨**——每轮把全部历史塞进 prompt，token 消耗随轮数线性增长（聊天类
   应用的账单大头就是这个）；
2. **注意力稀释**——上下文越长，关键信息越容易被淹没，越老的消息越容易被忽略；
3. **串话与污染**——旧任务、无关会话的信息混进来，误导当前判断。

所以本章的顺序就是记忆设计的五个必答问题：**分几层（§2）→ 记什么（§3）→ 何时
写、何时取（§4）→ 装不下怎么办（§5）→ 放哪里（§6）**。

## 2｜三层记忆模型

```
    用户消息
       │
       ▼
┌──────────── in-context（本次调用真正发给模型的 messages）────────────┐
│  system 人设/规则 + 记忆召回（偏好、摘要）+ 最近 N 轮原文 + 本轮新消息   │
└──────────────────────────────────────────────────────────────────────┘
       │  调用 LLM（工具循环在这里发生）
       ▼
┌──────── session 工作记忆（跨进程、跨轮，TTL 小时~天）────────┐
│  滚动摘要、最近若干轮、本轮任务进展   → Redis / RDBMS 会话表  │
└───────────────────────────────────────────────────────────────┘
       │  回合结束"提炼"（写）                    ▲ 召回（读）
       ▼                                          │
┌──────── persist 长期记忆（跨会话，长期）───────────────┐
│  用户偏好、身份事实、重要决策历史  → Postgres 表 + pgvector │
└─────────────────────────────────────────────────────────┘
```

三层各自的账本：

| 层 | 是什么 | 存哪 | 寿命 / 时效 | token 成本 | 典型内容 |
|---|---|---|---|---|---|
| **in-context** | 本次调用真正发给模型的 messages | 进程内存（一次请求） | 单次调用 | **每次都付**（最贵） | 摘要 + 偏好召回 + 近 N 轮 + 本轮消息 |
| **session** | 工作记忆：跨轮、跨进程的会话状态 | Redis（TTL 天然匹配）/ RDBMS 会话表 / SQLite | 小时 ~ 天（TTL 到期即忘） | 只在**召回进上下文**时付 | 滚动摘要、最近消息、任务进展 |
| **persist** | 长期记忆：跨会话 | Postgres 结构化表 + pgvector | 长期（直到过期/删除） | 只在**被检索命中**时付 | 用户偏好、身份事实、重要决策 |

三条关键认知：

1. **存哪里不花 token，取什么进上下文才花**——三层设计归根结底是在回答"从下层往上
   层取什么、取多少"；
2. 每层都要回答**两个时机问题**：何时**写**（固化下去）、何时**读**（召回上来）；
3. 三层不是三选一，是全部都在用——类比 CPU 的寄存器 / 内存 / 磁盘：每个程序员都
   不会问"我该只用哪一级"，而是问"什么放哪一级、什么时候换入换出"。记忆同理。

## 3｜什么该记、什么该忘

每个候选信息过一遍"三问过滤器"：

1. **能不能查到？** ——能通过工具查到的，不要记。（这是 P3·8"别让模型猜，给它查询
   工具"的姊妹原则：**能查的不要记，查不到的才要记**。用户列表明天就变了，你记的
   那一刻就开始过期。）
2. **会不会重复用？** ——一次性的中间状态不记（本轮算到一半的临时结果）。
3. **是关于"用户/关系"的，还是关于"世界"的？** ——关于世界的大量知识属于 RAG 的
   地盘（§7）；记忆记的是"你和这个助手之间发生过什么"。

| 信息 | 去哪 | 为什么 |
|---|---|---|
| 显式偏好（"以后都帮我把新员工配只读"） | persist | 跨会话复用，且系统接口查不到 |
| 身份 / 组织事实（"我在运营组"） | persist | 同上；必须带时间戳（会变） |
| 重要决策（"给张三配了运营"） | persist | 供追溯"谁在何时改了什么"；正式的留痕在审计（P3·9），记忆记的是摘要 |
| 本轮任务进展 / 最近操作 | session | 只服务"接着刚才"；TTL 到期即忘 |
| 用户列表、角色目录 | **都不记** | 能查到（`list_users` / `list_roles`）；记了反而过期误导 |
| 凭证（token / 密码） | **任何层都不进** | P3·9 的红线延伸到记忆——token 放 Redis 是"换个更合适的存放处"，不是"进上下文" |
| 敏感个人信息 | 谨慎（脱敏或不记） | 记忆是长期资产，也是长期负债 |

### 三个实战问题

**① 串话（cross-talk）**——A 用户的偏好串进了 B 用户的会话。多租户后台里这不是
小概率：`t-001` 的张三是运营组的，`t-002` 的张三是只读的，记忆键里少一个租户维度
就会把两个人的画像搅在一起。防法：**一切记忆读写都带 `{tenant}:{user}` 维度**——
Redis key 前缀、表结构的 `tenant_id` 列，和你后台的 RBAC / 多租户规则是同一个思路。

**② 语义漂移**——摘要在摘要之上再摘要，越滚越失真："新员工配只读"→ 三轮之后变成
"给员工配角色"。防法：① 摘要写成**要点/结构化槽**（`偏好：新员工→只读角色`），
不写散文；② 重要事实不许只活在摘要里——**升级到 persist 层存原文**；③ 定期从原始
记录重建摘要。

**③ 回忆失败的后果**——过期记忆被当成事实用：张三上个月已调岗，记忆里还是"运营组"。
设计对策：每条记忆带 `created_at`，召回时**连时间一起给模型**（"这是 3 周前记的"），
让模型自己会算时效；写级操作（分配角色这类）执行前**用工具核实现状**——记忆省的是
"重复盘问用户"，不是"省掉核实"。

## 4｜记忆的读写策略

### 写：何时把信息固化进记忆槽

| 触发点 | 时机 | 例子 |
|---|---|---|
| **显式信号** | 用户说"记住……" → 立即写 persist | "记住，我们团队先看再改" |
| **回合结束提炼** | 每轮结束，让 LLM 提炼"候选事实" → 过 §3 三问 → 写 | 从"那把他加上运营吧"提炼出"用户主动调整过张三的角色" |
| **离线任务** | 夜间批量把 session 压进 persist（§5） | 一整天的会话 → 提炼出偏好变化 |

工程细节两条：

- **幂等去重**：`INSERT OR IGNORE` / `ON CONFLICT DO NOTHING`——"新员工配只读"
  说三遍，只留一条；进阶做法是语义去重（向量相似度 > 阈值即合并，§5）。
- **谁来写**：**宿主层写**（沿用 P3"工具调用过宿主"的原则）——不让模型直接写库；
  高影响记忆（比如"以后写操作都自动批准"这种授权类偏好）写之前跟用户确认。

### 读：哪些记忆进上下文

不是"全部塞回去"，而是**召回**：三个召回器一起工作——

- **最近**（时间序）：近 N 轮原文，保证"接着刚才"的连贯；
- **相关**（语义检索）：按当前消息去 persist 里找相关记忆（§8 实测③给出最小实现）；
- **重要**（pin / 权重）：用户明确说重要的、或系统规则性的记忆，常驻召回。

两条纪律：

- **召回有预算**：给记忆在上下文里划固定配额（比如 15%），超了就按分数砍——这是
  P2·3 的 token 预算在记忆层面的落地（P7·20 展开）；
- **召回带来源**：每条召回记忆带上时间/出处，模型才有依据判断"这条还作数吗"。

## 5｜压缩与整理：为什么会忘、怎么不丢

### 近 N 轮 + 摘要（这是压缩的基本盘）

机制：保留最近 N 轮的原文，更老的折叠进一段滚动摘要。触发时机三种设计：

1. **在线即时**：未摘要消息超过阈值 → 立即折叠（实现最简单，摘要延迟进入用户等待
   路径——教学、小规模够用，本篇实测都用它）；
2. **在线异步**：计数超阈值只标记，摘要任务扔后台线程——用户不等待，实现复杂一档；
3. **定时离线**：夜间批量把全天会话压进 persist——重活彻底离开请求路径。

**单层 vs 层级（hierarchical）摘要**：

| | 单层 | 层级 |
|---|---|---|
| 结构 | 摘要 + 近 N 轮 | 远期梗概 + 中期摘要 + 近期原文 |
| 适合 | 单会话、几十轮 | 超长会话、长期陪伴型助手 |
| 代价 | 远期细节全丢 | 实现与维护复杂 |

层级摘要就是你记忆的方式：上周的事记得细节，去年的只记得大概。**先用单层，扛不住
再分层**——不要一上来就上多级。

### 遗忘策略：把"该忘的"忘掉

| 策略 | 机制 | 用在哪 |
|---|---|---|
| **TTL** | 到期自动删 | session（Redis 原生能力）；短期事实 |
| **LRU** | 容量满时淘汰最久未用的 | 缓存式记忆（近期工具结果、临时文件摘要） |
| **语义去重** | 相似度 > 阈值 → 合并/替换旧条目 | persist（防"同一偏好存了八遍"的膨胀） |
| **降级** | 原文 → 摘要 → 再摘要 | 超预算的历史逐级降级 |

一句话小结：**"忘"应该是被设计掉的（TTL / LRU / 折叠），而不是意外丢失**。区分
两件事——设计好的"忘"是省钱省注意力；没有设计的"丢"（摘要丢要点、串话、无来源）
是事故。

## 6｜存储后端选型

选型三问：**存什么**（会话态 / 事实 / 向量）、**活多久**（TTL / 长期）、**谁怎么查**
（key 查 / SQL 过滤 / 语义检索）。一张总表：

| 记忆类型 | 教学最小版 | 生产版（本项目） | 什么时候用 |
|---|---|---|---|
| 会话状态（摘要 + 近期消息） | SQLite / JSONL | **Redis**（TTL 天然匹配）或 RDBMS 会话表 | 跨轮、跨进程、多副本共享 |
| 长期事实 / 偏好 | SQLite 表 | **Postgres 结构化表**（本项目同栈） | 精确查询（`WHERE tenant_id AND user_id`） |
| 需语义召回的记忆 | 内存列表全量算 | **pgvector**（Postgres 原生扩展） | 记忆条目多，"最近 + 精确查"不够用 |
| 大规模文档知识 | — | pgvector 起步 → **Qdrant / Milvus**（规模化） | 见 §7；百万级向量 + 高并发才值得独立向量库 |

**Redis 在本项目背的三个具体职责**：

1. **会话记忆**——TTL 精确匹配"会话过期即忘"（§8 实测④A）；
2. **token / 工具结果缓存**——回看 P3·9：token 现在存进程内存，每条命令重新登录。
   挪进 Redis 后多进程共享，一次登录处处可用——顺手治了 M2 的一个遗留；
3. **并发锁**——同一会话的并发请求串行化，避免两个进程同时压缩把摘要写乱。

**为什么 pgvector 优先**（而不是直接上独立向量库）：

- **同库同事务**：记忆和业务数据都在 Postgres，JOIN、事务、备份一套搞定；
- **少一个组件**：独立向量库多一份运维（备份、监控、升级、鉴权）；
- **SQL 里直接过滤**：`WHERE tenant_id=... AND user_id=... ORDER BY embedding <=> ...`
  ——多租户过滤和向量检索一条语句解决，天然满足你的租户隔离规则。

什么时候才值得上 Qdrant / Milvus：向量到百万级以上、检索 QPS 高、需要专门的
分片 / 量化 / 多向量字段能力。原则：**先证明 pgvector 顶不住，再换**。

（还有一个中间档：Chroma 这类**嵌入式向量库**——不独立部署、进程内嵌，教学和
单机小项目顺手的选项；代价是不像 Postgres 那样能和你现有数据同库同事务，多租户
场景的隔离也得自己做。你后台已是 Postgres 栈，pgvector 是更顺的那条路。）

落地节奏：**SQLite/JSONL（教学，验证机制）→ Redis + Postgres/pgvector（本项目落地）**。

## 7｜RAG 分界线

一句话分清：**记忆是"你和这个助手之间发生过什么"；RAG 是"助手要懂的外部知识"**。

| | 记忆（本篇） | RAG（知识检索） |
|---|---|---|
| 内容来源 | 对话与操作中自然产生 | 文档 / 知识库导入 |
| 增长方式 | 随使用慢慢长 | 一次性摄取一大批 |
| 核心难点 | 记什么、忘什么、串话、漂移 | 切分、召回率、重排、时效 |
| 引擎 | 向量检索 + 结构化查询 | （同为）向量检索 + 重排 |
| 我们场景 | **主线**——管理助手当下 99% 是记忆问题 | 到"要回答制度/手册问题"时才需要 |

**什么时候真需要 RAG**：助手要回答"不在对话里、也不在系统接口里"的知识。比如公司
有一份《IT 制度手册》，"新员工入职要过哪些审批"这种问题，答案应该在手册里被检索
出来——这才是 RAG 的场景。而"新员工默认配只读"这种偏好，目前来自**用户亲口告诉
它**（记忆），不是从文档里搜的。

注意两边共用同一个引擎：**向量检索**。所以本篇实测③把它的机制打通，你以后接 RAG
时缺的只是"文档装载 + 切分 + 摄取"这一段。

典型坑（先建立认知，完整 RAG 管线到真实落地时展开）：

1. **检索跑偏**：不相关的低分结果也硬召回——**"没有相关"必须能被表达**（§8 实测③
   里的阈值召回就是这个设计）；
2. **上下文爆炸**：一次召回过多的结果，把上下文挤爆——配额 + top-k + 重排；
3. **时效**：文档会过期、记忆会过期——都带时间戳，给模型判断依据；
4. **召回内容是"不可信输入"**：回连 P3·10 的攻击链——网页/文档进上下文就是间接
   注入的通道。检索到的内容权限级别应低于用户输入（P7·20 展开）。

## 8｜动手实践

环境说明：①②③ 三个实验**零依赖**（纯标准库，Python 3.9+ 可跑）；④ 生产版需要一个
Redis + 一个 Postgres（docker compose 在 ④ 给出）。

### ① 裁剪策略核心实验：验证"旧信息不丢、token 不涨"

先不落库，把"近 N 轮 + 摘要"的纯逻辑跑明白（`memory_check.py` 核心节选）：

```python
class WindowedMemory:
    """近 N 轮原文 + 滚动摘要：超出窗口的旧消息立即折叠进 summary，
    不留"既不进摘要、也不进上下文"的中间地带。"""

    def __init__(self, recent=4, threshold=12):
        self.recent = recent        # 保留最近 4 轮原文
        self.threshold = threshold  # 未摘要消息超过 12 条 → 折叠一次
        self.archive = deque()
        self.summary = ""           # 滚动摘要（真实实现 = LLM 生成）
        self.compress_count = 0

    def add(self, msg):
        self.archive.append(msg)
        if len(self.archive) > self.threshold:
            self._compress()

    def _compress(self):
        keep = self.recent * 2
        n = len(self.archive) - keep
        old = [self.archive.popleft() for _ in range(n)]
        kept = [m["content"] for m in old
                if any(f in m["content"] for f in FACTS)]   # 规则式摘要器（占位）
        self.summary += "".join(f"[{k}]" for k in kept)
        self.compress_count += 1

    def context(self):
        head = [{"role": "system", "content": f"历史摘要：{self.summary}"}] if self.summary else []
        return head + list(self.archive)     # archive 规模有上界：threshold 条
```

### ② 把记忆装回 agent：`agent/memory.py` + main.py 三处改造

把 ① 的逻辑和 SQLite 持久化合体，成为可以装进 `agent/` 项目的正式模块——这就是
本项目"记忆短板"的最小生产形态（写入 `agent/memory.py`）：

```python
"""memory.py — 会话记忆：近 N 轮 + 摘要裁剪 + SQLite 持久化（零依赖可跑）。

真实实现里 _summarize() 换成一次 LLM 调用（见文末），其余不变。
"""
import sqlite3
import time

RECENT_TURNS = 6      # 保留最近 6 轮原文（12 条消息）
SUMMARIZE_AT = 16     # 未摘要消息超过 16 条 → 折叠一次


class Memory:
    def __init__(self, db_path="memory.db", session_id="s-1", tenant="t-001", user="u-1001"):
        self.session_id, self.tenant, self.user = session_id, tenant, user
        self.compress_count = 0
        self.db = sqlite3.connect(db_path)
        self.db.executescript("""
        CREATE TABLE IF NOT EXISTS sessions (
            session_id TEXT PRIMARY KEY, summary TEXT NOT NULL DEFAULT '', updated_at INTEGER NOT NULL);
        CREATE TABLE IF NOT EXISTS messages (
            id INTEGER PRIMARY KEY AUTOINCREMENT, session_id TEXT NOT NULL,
            role TEXT NOT NULL, content TEXT NOT NULL, created_at INTEGER NOT NULL);
        CREATE TABLE IF NOT EXISTS facts (
            id INTEGER PRIMARY KEY AUTOINCREMENT, tenant_id TEXT NOT NULL, user_id TEXT NOT NULL,
            fact TEXT NOT NULL, created_at INTEGER NOT NULL, UNIQUE(tenant_id, user_id, fact));
        """)
        # 会话行必须存在：否则首次压缩时 UPDATE 无行可改，摘要会被静默丢弃
        self.db.execute("INSERT OR IGNORE INTO sessions VALUES (?,?,?)", (self.session_id, "", 0))
        self.db.commit()

    # ---------- 读：组装进 LLM 的历史上下文（摘要 + 最近若干轮 + 长期偏好）----------
    def load_context(self):
        summary = self.db.execute("SELECT summary FROM sessions WHERE session_id=?",
                                  (self.session_id,)).fetchone()[0]
        msgs = self.db.execute("SELECT role, content FROM messages WHERE session_id=? ORDER BY id",
                               (self.session_id,)).fetchall()
        facts = [f[0] for f in self.db.execute("SELECT fact FROM facts WHERE tenant_id=? AND user_id=?",
                                               (self.tenant, self.user))]
        ctx = []
        if facts:
            ctx.append({"role": "system", "content": "用户长期偏好：" + "；".join(facts)})
        if summary:
            ctx.append({"role": "system", "content": "历史摘要：" + summary})
        ctx += [{"role": r, "content": c} for r, c in msgs]
        return ctx

    # ---------- 写：每轮结束调用 ----------
    def add_turn(self, user_msg, assistant_msg):
        now = int(time.time())
        for role, content in (("user", user_msg), ("assistant", assistant_msg)):
            self.db.execute("INSERT INTO messages(session_id,role,content,created_at) VALUES (?,?,?,?)",
                            (self.session_id, role, content, now))
        if self._pending() > SUMMARIZE_AT:
            self._compress()
        self.db.commit()

    def remember(self, fact):
        self.db.execute("INSERT OR IGNORE INTO facts(tenant_id,user_id,fact,created_at) VALUES (?,?,?,?)",
                        (self.tenant, self.user, fact, int(time.time())))
        self.db.commit()

    # ---------- 压缩：超出窗口的旧消息 → 折叠进摘要并删除 ----------
    def _pending(self):
        return self.db.execute("SELECT COUNT(*) FROM messages WHERE session_id=?",
                               (self.session_id,)).fetchone()[0]

    def _compress(self):
        keep = RECENT_TURNS * 2
        old = self.db.execute("SELECT id, role, content FROM messages WHERE session_id=? ORDER BY id LIMIT ?",
                              (self.session_id, self._pending() - keep)).fetchall()
        if not old:
            return
        new_part = self._summarize(old)          # ← 真实实现：这里是一次 LLM 调用
        row = self.db.execute("SELECT summary FROM sessions WHERE session_id=?",
                              (self.session_id,)).fetchone()
        merged = (row[0] + "；" if row and row[0] else "") + new_part
        self.db.execute("UPDATE sessions SET summary=?, updated_at=? WHERE session_id=?",
                        (merged, int(time.time()), self.session_id))
        self.db.execute("DELETE FROM messages WHERE id IN (%s)" % ",".join(str(i) for i, _, _ in old))
        self.compress_count += 1

    def _summarize(self, old):
        """规则式占位（零依赖可跑）；真实实现 = 一次 LLM 调用（见下）。"""
        lines = [f"{r}：{c}" for _, r, c in old if any(k in c for k in ("记住", "以后", "习惯", "默认"))]
        return "；".join(lines) or f"（省略 {len(old)} 条旧消息）"
```

### ③ 向量召回最小实现（纯标准库，零依赖）

"相关召回"靠向量检索。不装任何库、不连任何服务，把机制跑穿（`vector_demo.py`）：

```python
"""教学版 embedding：按关键词组数出 8 维特征向量（真实版 = 模型推理）。"""
import math

DIMS = ["角色权限", "用户账号", "时间", "查看", "修改", "团队", "系统", "冗余"]
WORDS = [["角色", "权限", "只读", "运营", "管理员"], ["用户", "员工", "账号", "张三", "李四"],
         ["上次", "以前", "习惯", "以后"], ["看", "查", "状态"],
         ["改", "配", "分配", "添加", "加"], ["团队", "组", "部门"], ["后台", "系统", "服务"], []]


def embed(text):
    v = [sum(w in text for w in group) for group in WORDS]
    n = math.sqrt(sum(x * x for x in v))
    return [x / n for x in v] if n else v            # 归一化后，点积 = 余弦相似度


def cos(a, b):
    return sum(x * y for x, y in zip(a, b))          # 两向量都已归一化

MEMORIES = ["新员工默认配只读角色", "张三在运营组，负责拉新", "上次帮李四改过权限",
            "团队习惯：先看现状再改动", "后台服务跑在 127.0.0.1:8899"]
MAT = [embed(m) for m in MEMORIES]                    # 入库时算好向量（离线一次）


def recall(query, top_k=2, threshold=0.30):
    """召回：算相似度 → 排序取 top-k → 过阈值的才进上下文。"""
    qv = embed(query)
    hits = sorted(((MEMORIES[i], cos(MAT[i], qv)) for i in range(len(MEMORIES))),
                  key=lambda x: -x[1])[:top_k]
    return [(m, s) for m, s in hits if s >= threshold]


for q in ["新来的员工应该给什么角色？", "上次李四的权限谁改的？",
          "后台服务在哪台机器上？", "今天天气怎么样？"]:
    print(f"Q: {q}")
    for m, s in recall(q):
        print(f"   {s:.3f} 召回 → {m}")
    print()
```

实测输出（编写环境原样）：

```text
Q: 新来的员工应该给什么角色？
   0.866 召回 → 新员工默认配只读角色
   0.816 召回 → 张三在运营组，负责拉新

Q: 上次李四的权限谁改的？
   1.000 召回 → 上次帮李四改过权限
   0.816 召回 → 新员工默认配只读角色

Q: 后台服务在哪台机器上？
   1.000 召回 → 后台服务跑在 127.0.0.1:8899

Q: 今天天气怎么样？
   ✗ 没有相似度 ≥ 0.30 的记忆 —— 判定「无相关记忆」，不硬塞进上下文
```

三条解读：

1. **正确的记忆排第一**（三条查询都对）；
2. **相邻记忆被带回是特性也是风险**（"李四的权限"带回了"新员工配只读"，0.816）——
   所以 top-k 是"候选"不是"答案"，条数上限 + 阈值要一起用；
3. **"没有相关"能被表达**（第四条全部低于阈值 → 不召回）——这是 §7"检索跑偏"的
   解药，也是防"硬编记忆"的安全阀。

手工特征只能演示机制；真实生产的 `embed()` 换成 **fastembed**（本地模型推理，
PyPI 包 `fastembed`，2026-10 版本 0.9.0）或供应商的 embedding API 即可，`recall()`
的逻辑一字不改。本例故意用纯标准库把每一步摊开——工程实现里这些向量运算交给
numpy / pgvector 完成（快得多），语义质量交给训练好的 embedding 模型。

## 本篇结论

1. **记忆是分层的工程问题**：in-context（每次调用付费）/ session（TTL 工作记忆）/
   persist（长期事实与偏好）——存哪里不花 token，**取什么进上下文才花**；串话靠
   `{tenant}:{user}` 隔离，漂移靠要点式摘要 + 原文升级，时效靠时间戳 + 工具核实。
2. **"忘"要设计成机制**：近 N 轮 + 摘要（超出窗口即折叠）、TTL / LRU / 语义去重，
   把该忘的忘掉、让上下文规模有界——实测里 40 轮对话压到 300+ 字符级别且旧事实
   不丢，就是"压缩"与"记住"并存的样子。
3. **存储选型一步一档**：教学 SQLite/JSONL → 落地 Redis（会话、token 缓存、锁）+
   Postgres 结构化表 + pgvector（同库同事务、租户过滤一条 SQL）；独立向量库
   （Qdrant/Milvus）等"证明 pgvector 顶不住"再上。记忆与 RAG 共用向量检索引擎，
   分界线是"关于你我"还是"关于世界"。
