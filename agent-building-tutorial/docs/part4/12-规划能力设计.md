## 1｜痛点回放：一步干到底

第 10 篇收口预告的第二个痛点。现场是这样的：

```text
$ python main.py "把所有没配角色的人都加上只读"
  → list_users            → 拿到 3 个用户
  → get_user_roles(1001)  → 已有管理员
  → assign_role(1002, 2003) → 也行
  → ……筛到几个人了？还剩谁？忘了。
  → 或者干脆：把所有用户都"加"一遍（幂等救了它，但用户要的是"没配角色的"）
```

三条行为特征，你对号入座：

1. **每步都是局部最优**——看着眼前状态选下一个工具，没有全局走法；
2. **没有全局视图**——不知道走到哪了、还剩多少、什么时候该停；
3. **错了不回头**——第三步才发现假设错了（比如 1002 是停用账号），不会撤销前面
   的操作重新来，而是硬着头皮往前试。

根因：模型把"多步任务"压成了一次次**直觉式决策**。P2·4 讲过"规划前置 + 反思收尾"
的 prompt 写法——那是最薄的一层隐性规划。本篇要做的事：**把"怎么做"从黑盒里拿出来，
变成一个显式的、结构化的、宿主能校验的对象**。

### Planning 在 PMTA 坐标里的位置

回看第 2 篇的 PMTA 坐标系：**P（Planning）/ M（Memory）/ T（Tool use）/ A（Action）**。

```text
        T 工具提供"可能性"             P 规划决定"路径"
   ┌──────────────────────┐      ┌──────────────────────────┐
   │ 能做什么：login /     │      │ 按什么顺序做、什么时候停、 │
   │ list_users / assign… │ ───► │ 错了怎么办、什么时候问人    │
   └──────────────────────┘      └──────────────────────────┘
```

- **工具（T）**是在第 3 篇一路建到第 10 篇的——给 agent 打开了"能做什么"的抽屉；
- **规划（P）**决定"怎么走"——同样的工具集，会不会规划，是两个物种。

第 11 篇解决了 **M**（记住偏好），本篇解决 **P**——**M3 = 记住偏好（11）+ 先计划
再执行（12）**，两篇合起来收口。

## 2｜从隐式到显式

规划有三档形态，能力递增、成本也递增：

| 档位 | 机制 | 我们能看见什么 | 典型问题 |
|---|---|---|---|
| **隐式** | 模型"心里"盘算后直接调工具（推理模型的长思维链也算） | 只有工具调用序列 | 错了不知道为什么错，没法教它改 |
| **ReAct** | 每步显式输出"思考 → 行动"，观察后继续 | 思考文本 + 工具调用 | 有迹可循，但仍是走一步看一步 |
| **Plan-and-Execute** | **先产出完整计划**（结构化步骤），再逐步执行 | 计划本身 + 每步状态 | 计划质量成为上限；多一次生成开销 |

### ReAct：思考 → 行动 → 观察

ReAct（Reason + Act）把"想"变成显式文本，每一步是"三拍"：

```text
Thought:   用户要"所有没配角色的人"，我得先拿全量用户，再逐个查角色
Action:    list_users()
Observation: [{1001, 张三}, {1002, 李四}, {1003, 王五}]
Thought:   先查 1001
Action:    get_user_roles(1001)
Observation: ["2001"]（已配）→ 跳过
Thought:   再看 1002
...
```

关键认知：**Thought 不只是给模型自己看的，更是写给宿主和用户看的**——可审计
（出问题能看到它在哪一步想歪了）、可干预（人可以在任何一步之间喊停）。

其实 M2 的 loop 已经是 ReAct 的骨架——模型在 tool_calls 之间的 `content` 就是
Thought 的位置，我们在 `log_step` 里能看到它。要做的是**显式引导**：在 system
prompt 里加一句"调工具前先用一句话说明当前在想什么、为什么选这个工具"——对
**关着 thinking 的 `deepseek-flash`**（第 4 篇：简单任务关掉思考更快更省），这几乎是
把 ReAct 的 Thought 补回 prompt 里的唯一办法；对**开着 thinking** 的调用，它则是
"外显要求"（模型内部有思维链，但那是它自己的推理，不等于写给宿主看的思考说明）。
两态下多步任务的稳定性都会提升。

### Plan-and-Execute：先想完，再走

先让模型输出一份**完整计划**，再逐步执行、逐步更新状态：

```json
[
  {"step": 1, "tool": "list_users", "args": {}, "done_when": "拿到全部用户 id"},
  {"step": 2, "tool": "get_user_roles", "args": {"user_id": "（上一步结果）"},
   "done_when": "知道每个用户当前的角色"},
  {"step": 3, "tool": "assign_role", "args": {"user_id": "（没配角色的人）", "role_id": "2003"},
   "done_when": "3 个没配角色的用户都返回 ok"}
]
```

两种形态怎么选：

| | ReAct | Plan-and-Execute |
|---|---|---|
| 什么时候"想" | 边走边想 | 先想完再走（执行中可改） |
| 全局视图 | 无（只有当前步） | 有——计划就是路线图 |
| 人介入的黄金时机 | 每步之间 | **计划生成后**（先审计划再开跑） |
| token 开销 | 小（每步几十字思考） | 计划生成一次 + 执行全程携带计划 |
| 适合 | 短任务 / 探索性 / 反馈密集 | 多步 / 依赖明确 / 高风险可先审 |
| 失败模式 | 绕圈、健忘 | 计划本身烂：一步错，步步错 |

### 计划的表示：怎么让模型输出"能执行"而不是"像话"

"像话"的计划长这样：

> 先查一下所有用户，然后看看谁没有角色，最后给这些人加上只读。

人能看懂，但**执行引擎没法跑**——"看看谁没有角色"是哪一步？"最后"是几步？翻译
过程全靠执行者临场发挥，发挥就有歧义。

"能执行"的计划是结构化的，每个步骤三个字段，**每一条都对着一个工程机制**：

| 字段 | 约束 | 拦什么 |
|---|---|---|
| `tool` | 必须是**宿主已知工具集**里的名字 | 幻觉工具名（实测场景 C） |
| `args` | 必须是对象，形状可校验 | 参数瞎编（P3·10 参数校验上移到计划层） |
| `done_when` | 必须**可观察**（能从工具返回值判断） | "假装完成"——这一步是计划与愿望清单的分界线 |

还有第四条隐性要求：**步骤间数据引用**（第 3 步要用第 2 步查到的 id）——在计划
里用占位符表达（"上一步结果"），执行时替换成真实值。

这就是 P2·7 埋的钩子兑现的时刻：当时学的结构化输出（`response_format` JSON 模式），
现在成了计划的载体。

## 3｜计划的生命周期

### 生成 → 校验 → 执行

**生成**两种做法：一次专职调用（用户请求 → 计划 JSON）；或计划作为主循环第一步
（模型先输出计划再开干）。

**校验**放在宿主层（同 P3"工具调用过宿主"的原则——计划是模型输出，同样是**不可信
输入**）：schema 检查（是数组吗、字段齐吗、工具名存在吗、args 是对象吗），失败就把
**错误清单喂回模型重生成**，而不是执行到一半才发现。这一层顺手把幻觉工具名拦在门外。

**执行**有轻重两种模式，先想清楚再选：

| | 轻模式：计划注入 loop | 重模式：宿主执行引擎 |
|---|---|---|
| 工具谁调 | 模型（照着计划导航） | 宿主（按计划逐步调用） |
| 计划遵守度 | 松——模型可即兴发挥 | 严——不按计划调不出去 |
| 改造量 | 小（加提示词 + 校验 + 注入） | 大（执行器 + 状态机 + 结果替换） |
| 拦截能力 | 复用自己的 `run_tool` 钩子 | 每步可审可暂停可重试 |
| 适合 | 起步、灵活任务 | 高风险 / 审计要求高的任务 |

**起步用轻模式**（本篇动手 ② 就是这个），重模式等有明确治理需求再上。

### 重规划：工具结果推翻了计划

执行中最常见的转折：第 1 步的观察与计划假设不符（要查的用户不存在、角色名对不上、
接口返回变了）。此时要**重规划**——把「原计划 + 已完成到哪 + 失败观察」一起喂给模型，
重新生成剩余步骤。设计要点三条：

1. **重规划必须带失败观察**——不然模型会生成同样的烂计划（"为什么失败"是重规划的
   全部输入价值）；
2. **重规划要有预算**——限次（比如 2 次），超了就中止并如实汇报。否则模型会在
   "改计划 → 失败 → 再改"里空转烧 token；
3. **重规划的第三种出路：降级目标**——做不到原目标时，改成"如实汇报现状"也是有效
   计划（§6 实测场景 B 的完整演示）。

### 回退与回滚：写操作执行到一半失败了怎么办

- **回退（rollback）**：撤销已做——需要每个写操作有"反操作"（撤销角色分配 = 再调
  一次删除）。现实里很多操作**没有反操作**（通知已发出）或反操作有副作用（审计里
  已经留痕）。
- 所以关键不是"失败时怎么撤"，而是**设计时让它不怕失败**：
  1. **先只读后写**（P3·9 的原则上升到计划结构）——把侦察类步骤全排前面，确认无
     误再动手；读到一半失败，什么都没脏；
  2. **检查点（commit point）**——把计划切成"可放弃段"和"承诺点"：承诺点之前失败，
     整段放弃重来；之后失败，转为**向前修复**（fix-forward，用新操作纠正而不是撤销）；
  3. **高风险写操作排后段**——前面全是读，最后才是写，且逐个过确认钩子；
  4. **幂等设计**——让"重做一遍"是安全的（P3·8 的 assign 幂等就是在给这一步铺路）。

```
计划结构上的安全排序：
[读 侦察 读 读] ← 可放弃段（失败：整段重来，零损失）
      ├─ 检查点（人审 / 确认钩子）
[写 写 写]       ← 承诺段（失败：向前修复，不假装成功）
```

## 4｜反思与验证

计划跑完（或跑歪）之后的自我检查，两种写法：

**① 执行后质疑（critic pass）**——任务完成后加一轮独立核对：

```text
用户要的是 X。你实际做了 Y（工具调用记录如下）。
逐条核对：X 的每一条要求是否都满足？有没有多余动作？
```

发现不符 → 补做或纠正。成本：一次额外的 LLM 调用。

**② 执行中质疑（step check）**——每步观察喂回时附带"这符合本步 done_when 吗"，
发现不对立即停，而不是跑完再算账。成本高（每步一次检查）但**发现早**。

**verifier（独立检查）**的核心原则：**生成者 ≠ 检查者**。

- 规则能查的用规则：分配成功了吗？**再查一次接口**（§6 实测里 `done_when` 的判定
  就是这个模式的雏形）；
- 主观判断用独立 LLM 调用：换个 prompt（甚至换个模型）当检查员；
- 为什么强调"独立"：让同一个模型检查自己的输出，它会**自我强化**（给自己打高分、
  替自己的错误找理由）——ReAct / Reflexion 这类反思方法的有效性，很大程度建立在
  "观察来自环境而非模型的自我报告"上。

**量化留到 P7·18**：本篇只能说"感觉变好了"——规划到底让成功率涨了几个点、token 多
花了多少，要用黄金用例集实测（评测篇的事）。先记住观察点：**任务成功率、工具调用
步数、重规划次数、无效调用（瞎试）占比**。

## 5｜什么时候规划帮倒忙

规划不是免费的——它有明确的成本账：

| 形态 | 额外开销 | 什么时候值 |
|---|---|---|
| 直接执行 | 0 | 单工具任务 |
| ReAct 提示 | 每步几十字 Thought | 2 步以上、路径不太确定 |
| Plan-and-Execute | 计划生成一次 + 全程携带计划上下文 | 多步 / 高风险 / 要人审 |

**简单任务别规划**：单工具任务加一套计划流程 = 纯浪费 token + 多一个失败面（计划
本身可能就是错的）。规划的价值随**步数和依赖关系**上升，随任务的**确定性**下降。

决策表（起步版）：

| 任务形态 | 用什么 |
|---|---|
| 单工具单步（"查下张三的角色"） | 直接执行 |
| 2~5 步、路径清晰 | ReAct 提示（"先想再干"进 system） |
| 多步 / 多依赖 / 高风险 / 要人审 | Plan-and-Execute（轻或重模式） |

**动态升级**（元规则，写进 system）："如果你已经调用了 5 次工具还没收敛，停下来，
把任务拆成计划再继续。"——让模型自己在"走不动"时切换形态，比一开始就强制计划
更省。

## 6｜动手实践

### ① 计划校验器 + 执行引擎 + 重规划路径（纯标准库实测）

三个场景跑穿"校验 → 执行 → 失败 → 重规划 → 降级汇报"整条链（`plan_check.py`，
用 stub 工具和写死的模型输出保证可复现；编写环境实测原样输出）：

```python
TOOLS = {"list_users", "get_user_roles", "assign_role", "list_roles", "respond"}

def validate_plan(plan):
    """宿主层校验：把"像话"拦在"能执行"门外。"""
    if not isinstance(plan, list) or not plan:
        return False, ["计划必须是步骤数组且非空"]
    errors = []
    for i, step in enumerate(plan, 1):
        if not isinstance(step, dict):
            errors.append(f"步骤 {i}: 不是对象（像话但不能执行的步骤）")
            continue
        missing = [k for k in ("tool", "args", "done_when") if k not in step]
        if missing:
            errors.append(f"步骤 {i}: 缺字段 {', '.join(missing)}")
        if "tool" in step and step["tool"] not in TOOLS:
            errors.append(f"步骤 {i}: 未知工具 {step['tool']!r}（幻觉工具名）")
        if "args" in step and not isinstance(step["args"], dict):
            errors.append(f"步骤 {i}: args 必须是对象")
    return (not errors), errors

def satisfied(step, obs):
    """done_when 判定（教学规则版）：出错不算；查询结果为空也不算——
    "没报错" ≠ "拿到了"。"""
    if "error" in obs:
        return False
    if isinstance(obs.get("data"), list) and not obs["data"]:
        return False
    return True
```

```text
场景 A：顺利路径（3 步全满足完成条件）
  [1/3] list_users {"keyword": "张三"}
        观察 {"data": [{"id": "1001", "name": "张三"}]}
        ✓ 拿到张三的 user_id
  [2/3] get_user_roles {"user_id": "1001"}
        观察 {"data": ["2001"]}
        ✓ 拿到当前角色列表
  [3/3] assign_role {"user_id": "1001", "role_id": "2002"}
        观察 {"ok": true}
        ✓ 分配返回 ok
  ✔ 计划完成（重规划 0 次）

场景 B：第一步就查不到用户（故意安排的失败用例）
  计划 v1（基于模型瞎猜的 id=1002）
  [1/2] get_user_roles {"user_id": "1002"}
        观察 {"error": "HTTP 404 用户 1002 不存在"}
        ✗ 未满足：拿到李四当前角色
  ↻ 重规划 1/2：失败观察喂回模型，重新生成剩余步骤……
  [1/2] list_users {"keyword": "李四"}
        观察 {"data": []}
        ✗ 未满足：确认李四存在并拿到 id
  ↻ 重规划 2/2：失败观察喂回模型，重新生成剩余步骤……
  [1/1] respond {"text": "系统里查不到叫「李四」的用户，无法分配角色。请确认姓名拼写，或先创建用户。"}
        观察 {"ok": true, "message": "系统里查不到叫「李四」的用户，无法分配角色。请确认姓名拼写，或先创建用户。"}
        ✓ 向用户说明未做任何变更
  ✔ 计划完成（重规划 2 次）——没有瞎试、没有假装成功

场景 C：校验器把'像话'拦在'能执行'门外
  valid = False
  - 步骤 1: 未知工具 'search_user'（幻觉工具名）
  - 步骤 2: 缺字段 tool, done_when
  - 步骤 3: 不是对象（像话但不能执行的步骤）
  → 错误清单喂回模型重生成，而不是执行到一半才发现
```

三处解读（都是可以搬进你系统的设计）：

1. **场景 B 的精髓在中间那次失败**：`list_users` 返回空列表**没有报错**，但
   `done_when`（"确认李四存在"）没被满足——判定器必须防"没报错就通过"。写这篇时
   第一版就栽在这：空列表被判成功，工具一路跑到了带占位符的假参数。（所以
   `done_when` 要"可观察"——"拿到 id"比"查询成功"好。）
2. **重规划限预算**（`max_replans=2`）：两次之后仍不行，就中止并如实汇报——预算
   之外还留了一个更优雅的出路：**降级目标**（v3 改成 `respond` 如实说明）。
3. **"如实汇报"也是计划的合法终点**——比"假装成功"和"无限重试"都强。这是计划
   和 PMTA 的 A（行动）合流的地方：动作不一定是调业务工具，也可以是"诚实地告诉
   用户做不到"。

### ② 给 agent 加"先计划再执行"（轻模式改造）

两步改造，`agent/` 项目增量。**第一步：计划生成器**（新函数，挂在 main.py 里）：

```python
PLAN_SYSTEM = """你是任务规划器。根据用户请求和可用工具，输出执行计划。
只输出 JSON 对象 {"plan": [步骤数组]}，不要解释。每个步骤三个字段：
{"tool": "工具名", "args": {...}, "done_when": "这一步完成的判定标准"}
规则：
- 只使用工具清单里存在的工具名
- done_when 必须可观察（能从工具返回值判断真假）
- 拿不准的 id 先用查询工具查证，不要猜（不要心算）
- 不需要多步的任务就输出单步计划；步骤数控制在 5 以内
可用工具：{tools}"""

def make_plan(client, user_input, tool_names, feedback=""):
    resp = client.chat.completions.create(
        model="deepseek-flash",
        messages=[{"role": "system", "content": PLAN_SYSTEM.format(tools=tool_names)},
                  {"role": "user", "content": user_input + feedback}],
        response_format={"type": "json_object"})       # 结构化输出（P2·7 的钩子到这里兑现）
    plan = json.loads(resp.choices[0].message.content)["plan"]   # json_object 模式要求顶层是对象，计划数组包一层
    ok, errors = validate_plan(plan)                    # ① 测过的校验器
    if not ok:                                          # 错误清单喂回，重生成一次
        return make_plan(client, user_input, tool_names,
                         feedback="\n上次计划不合法：" + "；".join(errors))
    return plan
```

> 逻辑已在 ① 实测；`make_plan` 部分需要 LLM key，**未在编写环境整跑**（按 DeepSeek
> OpenAI 兼容接口的 `response_format` 用法编写，`<以官方 docs 为准>`）——这也是 ③
> 留给你在自己环境验证的部分。

**第二步：把计划注入主循环**（轻模式的核心——计划变成 SYSTEM 的一部分，工具还是
模型自己调）：

def plan_to_text(plan):
    return "当前执行计划：\n" + "\n".join(
        f"{i}. {s['tool']}({s['args']})  完成条件：{s['done_when']}"
        for i, s in enumerate(plan, 1))

# main.py：需要规划的任务（PLAN_MODE=1 时）
plan = make_plan(client, user_input, TOOL_NAMES)
system_with_plan = SYSTEM + "\n\n" + plan_to_text(plan) + \

## 本篇结论

1. **规划 = 把"怎么做"从黑盒里拿出来**：ReAct（边走边想，Thought 显式化）→
   Plan-and-Execute（先想完再走）；计划的三个字段（tool / args / done_when）就是
   "能执行"的门槛——**done_when 可观察**是计划与愿望清单的分界线（"没报错"≠"拿到了"）。
2. **计划的生命周期里宿主握三件事**：校验（拦幻觉工具名与坏形状，错误清单喂回重生
   成）、重规划（必须带失败观察 + 限预算 + 允许降级为"如实汇报"）、回退设计（先只读
   后写 + 检查点 + 幂等，而不是指望失败时能撤销）。
3. **规划不是越多越好**：成本账 + 决策表——单步直干、数步用 ReAct 提示、多步高风险
   才上 Plan-and-Execute；反思要找**独立检查者**（生成者 ≠ 检查者），"规划真的变好了
   吗"的量化验证留给 P7·18 评测篇。
