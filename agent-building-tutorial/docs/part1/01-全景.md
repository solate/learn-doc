## 1｜分界线：普通聊天 → 工具调用 → 自主 agent

很多人把"会用 ChatGPT 聊天"理解成"AI 很智能"，把"能自己干活"理解成"多聊几轮"。
这中间其实隔着**三个明确台阶**。先把台阶画出来，全系列都是在这条线上往上爬的。

### 台阶一：普通聊天（chatbot）

模型只会做一件事：**给一段文本，回一段文本**。它既不会上网，也不会动你的数据库，
甚至不知道自己"不会"——你问它"帮我查一下订单 10086 的状态"，它只能"编"一个回答。

关键特征：**对话的下一步由人决定**。你问一句，它答一句，它永远不会主动去做点什么。

### 台阶二：function calling / tool use（工具调用）

模型多了一项能力：**输出的位置上可以放"我想调用某个工具 + 参数"的结构化声明**。

比如你问"北京今天冷不冷？"，模型可以返回一段特殊结构，大意是：

```json
{
  "name": "get_weather",
  "arguments": "{\"city\": \"北京\"}"
}
```

读法：**"我（模型）想调用 get_weather，参数是 city=北京"**。注意两个动词：是"想"，
不是"调"——模型永远不执行任何代码、不发任何 HTTP 请求，它只是**声明意图**。
真正拿着这个声明去查天气、把结果拿回来塞给模型的，是模型外面的宿主程序。

这个台阶的产物：模型可以"接住"任意外部能力了，只要写清楚"工具长什么样"给它看
（工具的名字、参数、用途——就是把信息写成它看得懂的结构）。

### 台阶三：自主 agent（autonomous agent）

台阶二仍然是一问一答：人问 → 模型声明"我想调 get_weather" → 宿主执行 → 把结果给模型 →
模型给最终答复。**每一步的"下一步"还是人发起的**。

自主 agent 补上的是**循环（loop）**：模型调完第一个工具、看到结果之后，
**不等人开口，自己决定要不要再调一个工具、再查一次、再多试一次**，直到任务完成或满足终止条件。

于是"查北京天气"变成：模型看一眼工具清单 → 发现要先查"北京在哪"（假设有这个工具）→
再查天气 → 看到结果 → 决定"够了，回答用户"。全程用户只说了一句话。

**"自主"指什么？** 三把尺子：

1. **能自己决定下一步动作**——不是每一步都靠人喂指令；
2. **一个任务在 loop 里多步完成**——调工具、看结果、再决策，可能来回好几轮；
3. **有明确的终止/放手条件**——任务完成、达到最大轮数、或主动回头问用户。

对照一下（这张表后面反复会用到）：

| 形态 | 谁决定下一步 | 模型能不能说"我要调工具" | 有没有循环 |
|---|---|---|---|
| 普通聊天 | 人 | 无 | 无 |
| 工具调用（function calling） | 人（一问一答） | 能（只声明意图） | 无 |
| 自主 agent | 模型（在 loop 内部） | 能 | 有（直到终止） |

> 这个"workflow vs agent"的分野是 Anthropic 官方指南《Building Effective Agents》
> 的开篇定调：**workflow 是走预先写死的固定路径，agent 是模型动态决定路径（控制流）**。
> 本系列讲的"agent"都指后者——不是"接了大模型就叫 agent"。
>
> 出处：Anthropic, [Building Effective Agents](https://www.anthropic.com/research/building-effective-agents)

## 2｜一次工具调用的完整流程

把台阶二放大成时序图，看一次 `tool call` 到底怎么走完。假设模型当前有两个工具：
`get_weather(city)` 和 `get_udid`（凑数举例，不重要）。

```
用户                      agent loop（编排层）                        LLM
 │──"北京今天冷不冷？"────▶│                                             │
 │                        │ 1.组装对话历史 + 工具清单(JSON Schema)       │
 │                        │───────────────────────────────────────────▶│
 │                        │                                             │──"我要调 get_weather，参数 city=北京"
 │                        │◀──────── tool_calls（结构化声明）──────────│
 │                        │ 2.校验参数 → 3.真的执行 get_weather("北京")    │
 │                        │      (向天气服务发 HTTP，得到 "5℃，多云")      │
 │                        │ 4.把结果作为 tool_result 追加进对话历史         │
 │                        │───────────────────────────────────────────▶│
 │                        │                                             │──"北京今天 5℃左右，多云，体感偏冷"
 │                        │◀─────── 最终的自然语言答复 ────────────────│
 │◀──"北京今天 5℃左右，多云。"──│                                             │
```

六个步骤，逐个拆（这是全系列最底层的骨架，第 3 篇会深度解剖）：

1. **组装请求**：把对话历史 + 工具清单（每个工具的名字、参数、用途，按它能看懂的结构）
   一起发给 LLM。
2. **模型返回声明**：LLM 不是"现在去执行"，而是返回 `tool_calls` 数组——"我想调
   `get_weather`，`arguments` 是 `{"city": "北京"}`"。**命令与执行分离**是理解 agent 的第一课。
3. **宿主校验并执行**：编排层拿到声明，先校验参数（`"city"` 是字符串、必填、长度合理一次），
   再调用真正的函数/接口。模型那一句"我想调"本身**没有任何副作用**，副作用全在这里发生。
4. **结果回填**：把工具的真实返回值包装成 `tool_result` 追加进对话——对模型而言，
   它就是"看到了失败或成功的结果"的又一条消息。
5. **再次交给模型**：带着结果再问一次 LLM，让它决定"够了，回答用户"还是"还要再调"。
6. **返回给用户**：最终的自然语言答复。

两个必须记住的认知：

- **模型只"声明"、宿主只"执行"**。模型永远不碰 HTTP、不碰文件、不碰数据库；所有真实世界
  的副作用都发生在编排层。
- **这一步还不是 agent**。上面的图里"下一步"仍由用户发起；把第 4→5 步连成循环、让模型
  自己决定"再调哪个工具"，才升级成台阶三。这就是第 1 节说的"自主"。

## 3｜为什么需要 agent：模型不会发起 HTTP，代码不会决定下一步

台阶二、台阶三都很顺理成章，那等一会儿——**为什么不直接叫模型自己调接口，非要中间垫
一个编排层？** 因为建模这件事本身的能力边界，决定了必然要有这层垫料。

### 模型不会发起 HTTP

LLM 的输入和输出都是**文本**。它天生没有"发请求""写文件""执行命令"这些能力——
它连"我现在真的去查了天气"都做不到，只能输出"我想查天气"这段文字。
你可以在系统提示词里写一万遍"请连接数据库"，它也只会回复一段像 SQL 的话，而不会真的连上。

要让模型的影响力触达真实世界，**必须有一个宿主进程负责"替它动手"**——这个宿主就是编排层。

### 代码不会决定下一步

反过来，传统程序（后端、脚本）倒是能执行 HTTP、读写数据库，但它每一步走哪个分支是**写死**
在开发者脑子里的。若需求变成"根据工具返回的结果，决定下一步调用哪个工具"，写死逻辑
根本写不完——工具组合是天文数字。

所以需要一层能"动态决策"的中枢：**它读模型的输出，决定执行哪个工具，把结果喂回去，
再看模型下一步怎么走。** 这个中枢就是 agent loop（也叫 agent core / harness）。

### agent loop = 编排层 = 中枢

`agent loop` 的全名其实就是上面那张时序图的**第 1、3、4、5 步的循环**，四个阶段：

```
感知（观察）→ 思考（LLM 决策）→ 行动（工具执行/文本输出）→ 再感知 → …
```

- **思考**：模型看到上下文 + 工具清单，决定"下一步是调工具还是回答"；
- **行动**：宿主执行工具（真的发 HTTP），或输出最终答复；
- **感知**：把工具结果、环境反馈带回上下文；
- 回到思考：看到结果，重新决策。

顺带预告：这个四阶段，就是第 2 篇要讲的经典 AI 智能体理论在 2026 年的映射，也是贯穿
全系列的 PMTA 坐标系（Planning / Memory / Tool use / Action）的最简形态。

> **harness**（agent loop / agent core）：驱动"感知→思考→行动→观察"循环的工程化运行时。
> 它管的不只是循环本身，还管工具注册、上下文管理、权限、事件流、可观测等"两侧基础设施"
> （Claude Code、Cursor、OpenHands、OpenClaw 都是它的工程实例）。这个词本系列高频出现，
> 第 3 篇专门把它讲透。

如同 OpenAI 官方《A Practical Guide to Building Agents》给出的最小定义：**agent 的
四个构件是 Instruction（指令）、Model（模型）、Tools（工具）、Loop（编排循环）**——
而后面两个（Tools、Loop）恰恰是"聊天"和"agent"的分水岭。

> 出处：OpenAI, [A Practical Guide to Building Agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)

## 4｜学习路线图：21 篇怎么走到"自己做出一个 agent"

本系列 21 篇、8 个 Part，每个 Part 以**一个可见的里程碑**收口。全系列只有一条主线：
**先做一个"能干活但有缺憾"的后台管理助手，再一层层补齐短板、工程化，最后用 Agentic OS
的视角看规模化。**

| Part | 篇 | 学完你能拿出什么 | 里程碑 |
|---|---|---|---|
| P1 | 1-2 | 坐标系 + 术语（概念与理论为主） | 无（理论地基） |
| P2 | 3-7 | 亲手写出的最小 agent（看得懂每一行） | **M1**：终端里跑起你自己的最小 agent，能回答预置问题并调用工具 |
| P3 | 8-10 | 后台管理助手 v1（直连 REST） | **M2**：说一句话，自动完成"登录 → 查用户/角色 → 分配角色 → 答复" |
| P4 | 11-12 | 记忆 + 规划 | **M3**：助手记住你的偏好/最近操作；面对复杂任务会"先列计划再执行" |
| P5 | 13-15 | MCP 标准化 | **M4**：MCP 版助手跑通 + Python Agent ↔ Go MCP Server 桥接 |
| P6 | 16-17 | 多智能体 | **M5**：主 agent + 只读查询 subagent 分工，能量化 token/延迟对比 |

| P8 | 21 | 毕业收口 | 终版助手组装 + Agentic OS 视野 + 落地方案交接单 |

每个里程碑都自带动手验证（README「逐篇进度表」的 Part 分组行都标了各里程碑的验证状态），
学到哪、离"毕业"还多远，一眼可辨。

**这条线为什么是这个顺序？** 需求驱动。先搭底座（P2），然后把底座**接上真实系统**
形成第一个"能干活"的助手（P3）；你会发现它"忘事、不会拆任务"（P4 补能力）；
再把工具升级成跨客户端标准（P5 MCP）；借鉴成熟 agent 落地多智能体（P6）；
最后工程化上线（P7）并做视野收口（P8）。每一步都在解决上一步暴露的痛点，
知识点不是孤立堆叠，而是管线里长出来的。

**必修 / 选学**

- 全系列 21 篇均为必修主线——它们合起来才覆盖"做一个可用 agent"的全部构件；
- 每篇的**动手实践是按需加的**：纯理论篇（第 2、21 篇）只配"动脑练习"，不需要动手也算过；

**怎么自测**

1. **里程碑就是考题**：每到一个里程碑，跑通它（有运行命令 + 预期输出），跑不通就回去重读
   该 Part 对应篇；
2. **每篇动手实践有预期输出**：做完能对照"预期输出"自判对错，不许"感觉差不多"；
3. **用 PMTA 复盘每个成品**：第 2 篇拿到坐标后，每完成一个版本，就站在"Planning /
   Memory / Tool use / Action"四个角各问一句"我的 agent 有没有这一块"，缺什么补什么。

### 动手实践：一行 Python，亲眼看"结构化参数"

**目标**：让 DeepSeek 返回一条 `tool_use`（工具调用声明），你亲眼看到它不是"跑到网上
查了天气"，而是**结构化地声明了"我想调 get_weather，参数 city=北京"**——为第 2-3 节
的"模型只声明、宿主才执行"补上实感。

新建 `demo_tool_use.py`（当前阶段脚本直接放在教程根目录即可；`agent/` 工程目录从
第 7 篇才开始建）：

```python
"""第 1 篇动手实践：触发一次 tool_use，亲眼看结构化参数。

<未实测，接口以 OpenAI 兼容调用为准；适用 DeepSeek/通义/智谱等兼容端点>
本脚本只做"声明"，不执行任何工具——执行是后面章节舞台的事。
"""
import json
import os

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()  # 从 .env 读 DEEPSEEK_API_KEY

client = OpenAI(
    api_key=os.environ["DEEPSEEK_API_KEY"],
    base_url="https://api.deepseek.com",  # DeepSeek 官方 OpenAI 兼容端点
)

# 给模型看的"工具清单"：名字 + 用途 + 参数结构（JSON Schema）
tools = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "查询指定城市的当前天气状况",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "城市名，例如『北京』"}
                },
                "required": ["city"],
            },
        },
    }
]

resp = client.chat.completions.create(
    model="deepseek-flash",
    messages=[
        {"role": "system", "content": "当用户询问天气时，调用 get_weather 工具。"},
        {"role": "user", "content": "北京今天冷不冷？"},
    ],
    tools=tools,        # 把工具清单交给模型
    tool_choice="auto", # 让它自己决定要不要用工具
)

# 打印模型返回的完整消息，重点看 tool_calls：
print(json.dumps(resp.choices[0].message.model_dump(), ensure_ascii=False, indent=2))
```

运行：

```bash
source .venv/bin/activate   # 若用 uv：已经在 uv 环境里
python demo_tool_use.py
```

  "content": null,

**从输出里看三件事**：

1. **它没发任何网络请求**——`get_weather` 默认要去"天气服务"发 HTTP，但脚本里没有任何真实
   执行逻辑；模型只是**声明了意图**。这个声明本身不发生任何副作用——"执行"这一步从来不
   属于 LLM，只属于编排层。
2. **参数是结构化 JSON**——`arguments` 是 `{"city": "北京"}`，字符串形式但可解析。这意味着
   宿主程序可以安全地取出来、校验、再调用真实函数。
3. **它还不是 agent**——没有循环：你问一句，它答一句"我要调 X"。把"调 → 看结果 → 再问"
   循环起来（第 3-7 篇的活），才升级成台阶三的自主 agent。

> 附带一见：`deepseek-flash` 从 V4.1 起**默认开启思考模式**，打印里可能还会多出一个
> `reasoning_content` 字段（模型"想"的过程）。它对我们有个硬规则——**带 `tools` 的请求，
> 历史的 `reasoning_content` 必须完整回传，否则会 400**。第 4 篇专门讲；第 7 篇的 agent
> loop 已天然遵守。

天气时要用工具"。把 `system` 那行改得更明确，再跑。这正是第 7 篇要讲的"工具描述怎么写，
模型才看得懂"的现场版。

## 本篇结论

1. **三层台阶**决定 agent 的本质：聊天不决策、工具调用只"声明意图"、自主 agent 在 loop 里
   自己决定下一步直到终止。
2. **模型只声明、宿主只执行**——一次 tool call 是"声明 → 校验 → 执行 → 结果回填 → 再决策"
   的六步，循环起来就是 agent loop（harness），这就是必须存在的"编排层"。
3. **路线**：M1→M6 步步递进（最小 agent → 接真实后台 → 记忆规划 → MCP → 多智能体 → 工程化），
   每个里程碑就是你的自考题，学完能组装出"会调用后台接口的管理助手"。
