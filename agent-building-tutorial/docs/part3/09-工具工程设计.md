## 1｜先看"裸奔版"的三个伤口

第 8 篇的 M2 闭环能跑了——工具层 13 条用例全过。但那是一个**裸奔版**：顺利时优雅，
边界处全是"靠模型自觉"。今天逐一把伤口摆出来，再逐个装件。

**伤口①：认证脆弱。** token 有效期 1 小时，过期后所有业务工具收到 401。第 8 篇的处理是
"401 文本喂回 → 模型自己补一次 login"（M2 自检第 5 条你验证过这个人肉自愈）——能救回来，
但代价是：**token 什么时候死、要不要重登，这种事占用了模型的注意力**。模型每次都要
"看到 401 → 推理 → 再调 login"，多花一个回合，还有概率胡思乱想（换参数硬试、向用户
道歉）。token 的生死是**确定性的机械问题**——机械问题就该留给代码。

**伤口②：错误"一锅端"。** 第 8 篇的错误文本是 `查询失败：HTTP 404 {...}`——能读，但
404（用户不存在，重试一万次也一样）和 500（服务端抖动，稍后可能就好）混在同一句话里，
模型没法"区别对待"。**错误文本是给模型的决策输入**——它值得被设计，而不是拼字符串。

**伤口③：写操作无护栏。** `assign_role` 现在是"说了就做"：没有确认、没有留痕。人类
管理员在后台点"分配角色"还要弹窗确认一次，agent 反而一路绿灯——说不过去。

## 2｜认证与会话：把 token 的生死收回宿主

改造后的"后台管理工具"整段如下（替换第 8 篇的同名段落；`API_BASE` 等常量保持不变，
顶部 import 区补一行 `import time`）。

```python
# ============ 后台管理工具（第 9 篇升级版：整段替换第 8 篇的版本）============
API_BASE = "http://127.0.0.1:8000/api/v1"
AUDIT_FILE = "audit.jsonl"    # 审计日志（agent/ 目录下生成，记得加进 .gitignore）
_TIMEOUT = 10
_token = None                 # 登录 token 存进程内存，不进对话历史
_creds = None                 # 记住登录凭证，供 token 过期后自动重登（同样不进对话历史）


def audit(event):
    """审计日志：每行一条 JSON 追加落盘——给"事后的人"看，不是给模型看。"""
    line = {"ts": time.strftime("%Y-%m-%d %H:%M:%S"), **event}
    with open(AUDIT_FILE, "a", encoding="utf-8") as f:
        f.write(json.dumps(line, ensure_ascii=False) + "\n")


def login(username, password):
    """后台登录。幂等：已有 token 时直接复用（过期由 _request 的 401 自动重登兜底）。"""
    if _token:
        return "已登录（复用现有 token）。"
    return _do_login(username, password)


def _do_login(username, password):
    """真正发登录请求；成功后 token 与凭证存入进程内存。"""
    global _token, _creds
    resp = requests.post(f"{API_BASE}/login",
                         json={"username": username, "password": password},
                         timeout=_TIMEOUT)
    if resp.status_code != 200:
        return f"登录失败：HTTP {resp.status_code} {resp.text}"
    _token = resp.json()["data"]["token"]
    _creds = (username, password)
    return "登录成功，token 已在本进程内存持有（有效期 1 小时）。"


def _auth_headers():
    return {"Authorization": f"Bearer {_token}"}


def _request(method, path, **kw):
    """统一请求入口：自动带 token；曾登录过且收到 401 → 自动重登一次再重试。

    所有业务工具都走这里——认证逻辑只写一处、对模型透明：
    模型看到的是"工具成功/失败"，token 的生死是宿主（token 管理）的事。
    """
    url = f"{API_BASE}{path}"
    resp = requests.request(method, url, headers=_auth_headers(), timeout=_TIMEOUT, **kw)
    if resp.status_code == 401 and _creds:
        audit({"event": "relogin", "reason": "got 401, relogin and retry once"})
        _do_login(*_creds)                       # 重登；失败也无妨，重试会再次 401
        resp = requests.request(method, url, headers=_auth_headers(), timeout=_TIMEOUT, **kw)
        # 只自动重试这一次：仍失败就原样返回，交给 _shape 喂回模型
    return resp


def _shape(resp):
    """把响应统一塑成"给模型的文本"：成功给 data；失败给 状态码+body+处置提示。"""
    if resp.status_code == 200:
        return json.dumps(resp.json()["data"], ensure_ascii=False)
    hint = {400: "请求参数不合法，修正后重试",
            401: "认证失败（自动重登也没救回来，检查凭证）",
            404: "目标不存在，不要重试",
            500: "服务端错误，可稍后重试"}.get(resp.status_code, "未知错误")
    return f"调用失败：HTTP {resp.status_code}（{hint}）{resp.text}"


def list_users(keyword=""):
    """按用户名或姓名查用户（返回 user_id 等）——把名字翻译成 ID 的第一步。"""
    return _shape(_request("GET", "/users", params={"keyword": keyword}))


def list_roles():
    """查后台全部角色目录（role_id / role_code / role_name）。"""
    return _shape(_request("GET", "/roles"))


def get_user_roles(user_id):
    """查指定用户当前拥有的角色。"""
    return _shape(_request("GET", f"/users/{user_id}/roles"))


def assign_role(user_id, role_id):
    """给用户分配一个角色（幂等：已有则不变）。"""
    resp = _request("POST", f"/users/{user_id}/roles", json={"role_id": role_id})
    if resp.status_code == 200:
        return "分配成功：" + json.dumps(resp.json()["data"], ensure_ascii=False)
    return _shape(resp)
```

**四处关键设计**（认证这节的 B1 知识点都在这）：

1. **登录幂等**：`if _token: return "已登录（复用现有 token）"`——模型多调一次 login 无害。
   为什么敢这么"乐观"（不实际验证 token 还有效）？因为 `_request` 的 401 自动重登兜底：
   **幂等 + 兜底 = 双保险**，比"每次 login 都先发一个验证请求"省一次往返。
2. **`_creds` 记住凭证**：自动重登时不用再问模型要密码——凭证同样只存进程内存。
3. **`_request` 统一入口，401 自动重登一次**：所有业务工具走同一个函数，认证逻辑只写
   一处。"只重试一次"是刻意的——把第 7 篇 `MAX_STEPS` 的刹车思想用在请求层，防重登死循环。
4. **对模型透明**：token 过期→重登→重试的全程，模型只看到"工具调用成功"。注意它与
   M2 自检第 5 条的差别：第 8 篇模型自愈要花掉一个回合 + 一段上下文；现在零成本。
   这就是工程化的分工——**确定性的繁琐归代码，判断归模型**。

**失败恢复（重登也没用怎么办）**：密码改了、账号被禁 → 重登后重试仍 401 → `_shape` 把
"认证失败（自动重登也没救回来，检查凭证）"喂回模型 → 模型向用户报告。**自动修复只做
保底一次，剩下的交给人。**

## 3｜错误处理链：错误也是"给模型的输入"

### 错误文本的组成公式

`_shape` 里的失败分支给出了公式：**状态码（机器可读）+ 处置提示（决策线索）+ body
原样（可溯源）**。处置提示（hint 表）是**宿主在集成时写下的知识**——404 别重试、500 可
稍后重试、401 检查凭证。模型读到的不再是"一坨错误"，而是"怎么了 + 该怎么办"。

### 兜底链全景：四层，每层只管一类错误

```text
模型 ◀─ run_tool 兜底 except（网络异常 / 工具自身 bug —— 最外层的网，第 7 篇就有）
     ◀─ _shape（HTTP 非 200：状态码 + body + hint）
     ◀─ _request（401：自动重登一次）
     ◀─ 工具函数（正常业务逻辑）
```

每一层都遵守同一条铁律：**任何错误都变形为文本喂回模型，绝不把循环搞崩**。分层的意义
是"每层只处理自己认识的错误，认识的消化掉（如 401 重登），不认识的往上抛"。

**实测记录（本环境原样输出）**——三类错误各来一发：

```text
# ① 404：状态码 + hint + body
get_user_roles(9999) -> 调用失败：HTTP 404（目标不存在，不要重试）{"detail":"用户不存在"}

# ② 人为破坏 token（模拟过期）后调业务工具 → 自动重登成功，模型无感
get_user_roles(1001) -> {"list": [{"role_id": "2001", "role_code": "admin", "role_name": "管理员"}]}

# ③ 目标服务没启动：网络异常被最外层兜底网接住（文本按你本机端口显示）
工具执行出错：ConnectionError: HTTPConnectionPool(host='127.0.0.1', port=8000):
Max retries exceeded with url: /api/v1/users?keyword= (Caused by NewConnectionError(...)…
```

### 哪些错误**不该**自动重试

| 错误 | 自动重试？ | 理由 |
|---|---|---|
| 401（token 过期）| ✅ 重登后重试**一次** | 机械问题，有确定修复动作 |
| 400 / 404 | ❌ | 参数错、目标不存在——重试一万次结果一样，喂回让模型修正 |
| 500 / 网络超时 | 🔶 可重试，本篇不做 | 值得重试但涉及时机/退避策略，属"可靠性工程"，P7·20 展开 |

（第 6 篇讲 SDK 的 `max_retries` 时给过同一张决策表的"网络层版本"——现在补上了
"工具层版本"，两张表配成一套。）

## 4｜护栏三件套：确认钩子 / 先只读后写 / 审计落盘

### ① 二次确认钩子（装在宿主层）

改动在 `main.py`：加一个危险工具名单、一个确认函数，`run_tool` 里拦截：

```python
# 顶部 import 行改为：
from tools import TOOLS_SCHEMA, registry, audit

# 危险写操作名单：执行前必须获得用户确认
DANGEROUS_TOOLS = {"assign_role"}


def confirm(tool_name, args):
    """二次确认钩子（教学版：终端 y/N；Web/IM 形态见 P7·19）。"""
    answer = input(f"[confirm] 即将执行危险操作 {tool_name} {args}，确认吗？(y/N) ")
    return answer.strip().lower() == "y"


def run_tool(tc):
    """⑤ 执行一个 tool_call；任何错误都变成文本喂回模型，绝不把循环搞崩。"""
    name = tc.function.name
    try:
        args = json.loads(tc.function.arguments or "{}")
    except json.JSONDecodeError as e:
        return f"参数不是合法 JSON（{e}）。请修正后重试。"
    fn = registry.get(name)
    if fn is None:
        return f"工具不存在：{name}。可用工具：{list(registry)}"
    if name in DANGEROUS_TOOLS:                   # 护栏：危险操作先过确认钩子
        if not confirm(name, args):
            audit({"event": "rejected", "tool": name, "args": args})
            return "用户拒绝了本次操作，未执行。请向用户说明未做任何变更，不要重试。"
    audit({"event": "tool_call", "tool": name, "args": args})
    try:
        result = str(fn(**args))
    except Exception as e:                        # 兜底网：网络异常等一切未处理错误
        result = f"工具执行出错：{type(e).__name__}: {e}。如参数有误请修正后重试。"
    audit({"event": "tool_result", "tool": name, "result": result[:120]})
    return result
```

**为什么装在宿主层（`run_tool` 里），而不是工具函数里？** 三个理由，每个都是设计原则：

1. **一处名单管所有写操作**——将来加新的写工具，只改 `DANGEROUS_TOOLS` 一行；
   如果确认写在工具里，每个工具都要复制一遍确认逻辑；
2. **工具保持"纯粹"**——工具只负责"做事"，"要不要批准"是宿主的**政策**。将来换更细的
   权限系统（比如按角色放行，P7·20），工具一行都不用动；
3. **拒绝时根本不进入工具函数**——"不执行"是最强的安全：没有半途而废的操作、没有
   回滚需求。

这正是 P2·3 画的 harness 服务层里**"权限"服务**的第一件实体（第一件是第 8 篇的"工具
注册"）。注意拒绝分支的返回文本——**拒绝也是一条数据**："用户拒绝了…不要重试"既让
模型知道发生了什么，又明确掐掉了它"再试一次"的念头（模型会把这句话当指令读）。

### ② 先只读后写（两层含义）

- **给模型的规则**：SYSTEM 加一条——
  `5. 执行写操作（assign_role）前，先查询现状（get_user_roles），并向用户说明将要做的变更。`
  这样人在确认提示里看到的不是孤零零一句"assign_role {user_id:1001…}"，而是知道
  "张三目前是管理员，即将新增运营"的上下文（模型会在对话里先说出来）。
- **给系统的策略**：上线初期**只给 agent 读工具**，写工具暂缓放入（或对特定用户开放）——
  "能力逐步放开"原则。它和确认钩子的关系：钩子防"误操作"，只读策略防"没想清楚的批量
  操作"，两层不互相替代。权限分级在 P7·20 展开。

### ③ 审计日志落盘

`audit()`（见第 2 节代码）每次工具调用记两条：`tool_call`（含完整参数）+ `tool_result`
（结果摘要），另有 `relogin`、`rejected` 两种事件。关键的设计立场：

**审计是给"事后的人"看的，不是给模型看的。** 它与第 7 篇的 `log_step`（模型迭代日志，
调试用）分离：log_step 回答"agent 在想什么"，audit 回答"谁在什么时候让 agent 干了什么"。
出事了（"谁把张三提成了管理员？"），答案就在这几行 JSON 里，而不是模型的自述里。

{"ts": "2026-10-16 17:12:29", "event": "tool_result", "tool": "get_user_roles", "result": "{\"list\": [{\"role_id\": \"2001\"…
{"ts": "2026-10-16 17:12:29", "event": "rejected", "tool": "assign_role", "args": {"user_id": "1001", "role_id": "2002"}}

> 注意审计里**密码与 token 也是明文**——教学版够用，但这提示了审计系统自身的敏感数据
> 治理（脱敏、访问控制）是真实工程要单独处理的（P7·20 治理篇）。`audit.jsonl` 记得加进
> `.gitignore`；生产环境应落集中式日志/数据库而不是本地文件。

## 动手实践：给 M2 闭环装三件套，验证边界

**改动清单**（都在 `agent/` 里）：

1. `tools.py`：后台部分**整段替换**为第 2 节代码；顶部 import 区补 `import time`；
2. `main.py`：按第 4 节替换 `run_tool`，加 `DANGEROUS_TOOLS` 与 `confirm`，
   import 行加 `audit`；SYSTEM 补第 5 条规则；
3. `.gitignore` 加一行 `audit.jsonl`。

**四个验证场景**（服务端沿用第 8 篇的 `target_service`，先启动）：

```text
场景 1 · token 过期自动重登
  把 target_service 里 TOKEN_TTL 改成 10（秒）→ 重启服务 → 跑：
    python -c "import tools; print(tools.login('admin','admin123'))"
  → 等 10 秒 → 再跑一条业务调用（或直接问 agent"张三有哪些角色"）
  预期：业务调用照常返回数据（宿主自己重登了）；audit.jsonl 里能看到 relogin 事件。
  快捷实验（不改 TTL）：login 后把 tools._token 手动改成 'broken' 再调业务工具，同效。

场景 2 · 二次确认（拒绝路径）
  python main.py "给张三加上运营"
  预期：终端出现 [confirm] 提示 → 输入 n → agent 汇报"未执行/未做任何变更"；
  再查一次张三的角色，确认服务端数据没变（拒绝 = 真的没执行）。

场景 3 · 二次确认（放行路径）
  同上一句话，确认提示时输入 y → 变更成功；audit.jsonl 有 tool_call + tool_result。

场景 4 · 网络兜底
  停掉 target_service → 问一句"张三有哪些角色"
  预期：agent 不崩，收到 "工具执行出错：ConnectionError…"，并向你解释"后台服务可能
  没启动"（模型对异常文本的解读）；重启服务后恢复正常。
```

**自检清单（六条全过）**：

- [ ] **自动重登**：场景 1 成功，audit 里能看到 `relogin` 事件
- [ ] **模型无感**：走 agent 时"重登"不占对话回合（对比 M2 自检第 5 条的人工自愈）
- [ ] **拒绝生效**：场景 2 输 n 后，复查角色确认**数据未变**，agent 明确报告未执行
- [ ] **放行生效**：场景 3 输 y 后角色已变，审计三类事件齐全
- [ ] **网络兜底**：场景 4 不崩、有合理解释
- [ ] **闭环回归**：第 8 篇的一句话闭环（现在中间多了确认提示）仍然完整跑通

最后一条是纪律：**加装不能破坏已验收的东西**——P3·10 收口时还会整体复验一次 M2。

## 本篇结论

1. **认证收回宿主**：登录幂等 + 401 自动重登（只一次）+ 失败喂回——token 的生死对模型
   透明；机械问题归代码，判断归模型。
2. **错误分层**：状态码 + hint + body 的"决策输入"格式；`_request`（重登）→ `_shape`
   （格式化）→ `run_tool`（兜底网）三层各管一类，任何错误都变形为文本喂回。
3. **护栏三件套都在宿主层**：确认钩子（拒绝也要喂回且明确"不要重试"）、先只读后写
   （规则层 + 策略层）、审计落盘（给事后的"人"看，与调试日志分离）。
