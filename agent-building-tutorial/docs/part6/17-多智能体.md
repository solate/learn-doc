## 1｜为什么拆：四个动机与一条守恒律

先说清楚：单 agent 的瓶颈从来不是"不够聪明"，而是三条硬约束——**上下文有限、
执行串行、职责单点**。拆多 agent 是给这三条开的四种药：

| 动机 | 解决什么 | 证据 / 实例 |
|---|---|---|
| **上下文隔离** | 主上下文不被探索过程淹没 | Claude Code 的 Explore"把探索结果留在主对话之外"（16 篇） |
| **分工 / 专精** | 每类工作有独立的提示词与工具集 | Anthropic Research：subagent"distinct tools, prompts, and exploration trajectories——reduces path dependency" |
| **并行** | 互相独立的子任务同时跑 | Anthropic：3-5 subagent 并行 + 每个 3+ 并发工具，复杂查询耗时 -90% |
| **职责边界** | 生成者 ≠ 检查者；读写分离 | 我们 P4·12 的 verifier 原则；16 篇"只读 subagent 就别给它写工具" |

第三条动机旁边必须钉一个常被误解的点：**"token 分摊"分的是窗口压力，不是账单**。
拆出去的工作在子 agent 那里照样烧 token，总量反而更高（Anthropic 的实测是
15×）——§4 会用本机实测把这件事看你亲眼看到。

第四条动机旁边钉第二条：

> **复杂度守恒律**：拆多 agent 不是消灭复杂度，而是把它从"上下文里"搬到
> "协调里"。

Anthropic 写下了早期翻车现场当证据：**给简单查询 spawn 50 个 subagent**、subagent
之间互相重复劳动、用海量更新互相打扰。所以它的官方建议里有那句冷静的：
"most coding tasks involve fewer truly parallelizable tasks than research"。

**决策门槛三条**（三条全过才考虑拆）：

1. 单 agent 已经**跑通**、只是被上下文/串行拖慢（不是还没跑通就想拆）；
2. 任务能分解为**低依赖**子任务（"共享上下文强依赖"的任务不适合——Anthropic 原话；
   我们场景 = 需要连续对话上下文的写操作链）；
3. 隔离收益**可量化**（§5 的实验就是干这个的）。

落到"后台管理助手"：**批量排查类**任务（"把最近异常操作过的用户都翻出来，
逐个核对角色"）是天然的可分解探索——适合；"把张三的角色改成 viewer"是一两次
工具调用——不适合，直接自己做。

## 2｜五种协作模式

把 16 篇的实例 + 经典文献收敛，常见协作模式就五种：

| 模式 | 一句话 | 代表实现 | 适合 | 成本档 |
|---|---|---|---|---|
| **orchestrator-worker** | 中心 agent 动态拆解 → 派 worker → 汇总 | Anthropic Research；CC 主 agent + subagents | 可并行分解的探索/研究 | 中-高 |
| **planner-executor** | 先产出计划（可审），再照计划执行 | Cursor Plan Mode（人审后建）；我们 P4·12 重模式 | 复杂、多步、错一步代价高 | 中 |
| **verifier**（evaluator-optimizer） | 一稿一评，循环改进 | 《Building Effective Agents》的 evaluator-optimizer；P4·12 critic pass | 有明确验收标准、质量优先 | 中 |
| **debate** | 多方独立作答、互相批判、多轮收敛 | arXiv 2305.14325 研究线 | 高风险判断题 | 高（最贵） |
| **对称协作 / handoff** | 控制权整体移交给另一个 agent | openai-agents 的 handoffs 原语 | 分诊、专家路由 | 低-中 |

三个要点：

- **模式可叠加**。实战里最常见的组合是 orchestrator + verifier：worker 出结果，
  verifier 过一道（CC 的嵌套示例就是 reviewer 派生 verifier）。我们的 M5 只上
  orchestrator 的迷你版，verifier 已在 P4·12 有过。
- **planner-executor 的"planner 独立出来"不一定需要第二个模型**。P4·12 的重模式
  已经证明：同一次 LLM 调用序列里，"先出计划、宿主校验、再执行"就有收益；真拆
  成两个 agent 的价值在于**不同上下文/不同提示词/不同模型**（Cursor 的 Plan Mode
  则更进一步：计划先给人审）。
- **实现层不必从零**。P2·5 盘点过的 langgraph 就是做图编排的现成框架——本系列
  仍然手写，因为**模式先于框架**：先知道自己在用哪种模式，再挑工具；反过来
  （先拿框架再找用法）只会得到一堆胶水代码。

## 3｜三种通信机制

拆完之后，关键问题是"它们怎么说话"。三种机制，本质区别在**控制权**：

| 机制 | 控制权 | 子 agent 看到什么 | 回来什么 | 实例 |
|---|---|---|---|---|
| **共享上下文** | 无变化（其实没拆） | 全部历史 | —（同一人分饰两角） | "你既是规划者又是执行者"式提示词 |
| **嵌套调用**（agent 当工具） | 留在调用方 | 任务描述 + 自己的 system prompt | 最终摘要 | CC subagents；Anthropic Research；**本篇 M5** |
| **消息传递 / 交接**（handoff） | 整体移交 | 会话控制权 | —（由接手者继续） | openai-agents 的 handoffs |

"共享上下文"是最容易自欺的一种——提示词里写"你现在切换到审查者角色"，上下文
没变、偏差也不会变；它适合微任务，不是真拆分。

**嵌套调用**是性价比最高的默认：我们的管理助手 loop 一行不改，subagent 就是一个
`ask_scout(question)` 工具调用——和第 9 篇往 registry 里加一个工具完全同构。
Claude Code 的 subagents（只见任务描述、只回摘要）和 Anthropic Research 的
subagent 都是这个形态。

**消息传递 / 交接**适合"后半段换人更合适"的场景（客服分诊：售前 agent 判断是
退款问题 → 直接把会话交给退款 agent），我们在管理助手里暂用不上，知道有这个
选项即可。

**选型速问**（五模式的一次性判断版）：

- 任务能拆成互不依赖的几块吗？能 → **orchestrator-worker**（不能就别拆）；
- 错一步代价高、值得先审吗？值得 → 先 **planner-executor**；
- 有明确验收标准吗？有 → 在任意模式上**叠一个 verifier**；
- 是判断题且错不起吗？是 → 考虑 **debate**（最贵，留给高风险）；
- 后半段换个人更合适吗？是 → **handoff**。

三条工程注意（都来自前面篇目的教训）：

1. **回传物要设计**。Anthropic 的委派四要素可以直接抄进任何 `ask_xx` 工具的描述
   里："objective / output format / tools / boundaries"——原话警告是"Without
   detailed task descriptions, agents **duplicate work, leave gaps, or fail to
   find necessary information**"。16 篇实践 A 的 doc-scout 写"汇报格式：结论+出处"
   就是同一件事。
2. **失败也要回传**。子 agent 超时、报错、步数超限，都要变成一条**形状化结果**
   喂回主 agent（"查询失败：超时，建议缩小范围"），主 agent 继续——这正是第 16
   篇 hooks 阻断时"把拒绝回填给模型"的同款原则。
3. **写操作别外包**。子 agent 只读、写留主 agent + 确认钩子——第 16 篇的两条理由
   原样成立（子 agent 的编辑不参与会话恢复；审批链难做）。M5 直接采用。

还有一个"传话失真"的进阶技巧，先记住名字：**大结果传引用，不传全文**。
Anthropic 的做法是 subagent 输出写文件、只把引用回传（原文："Subagent output to a
filesystem to minimize the 'game of telephone'"）。我们的 scout 回传的是一句摘要，
暂时够用；等 subagent 产出整张表、整份报告时，就该学这一招。

## 4｜成本账：多 agent 什么时候"值"

Anthropic 给出的数字值得贴在墙上：

> "agents typically use about **4×** more tokens than chat interactions, and
> multi-agent systems use about **15×** more tokens than chats. For economic
> viability, multi-agent systems require tasks where the value of the task is
> high enough to pay for the increased performance."

三本账，逐本算：

| 账本 | 多 agent 的变化 | 原因 |
|---|---|---|
| **token** | ↑（15× 量级） | 子 agent 各读各的上下文；返回的摘要又进主上下文；协调本身也要调用 |
| **延迟** | 并行 ↓ / 串行 ↑ | 独立子任务并行能省（Anthropic -90%）；但"嵌套且等待"是纯叠加——CC 文档明说主 agent 会**等**后台 subagent 的结果 |
| **可维护性** | ↓ | 每多一个 agent 就多一份提示词面（SCOUT_SYSTEM）、一个漂移源；调试要跨上下文追 |

**规模规则也要抄**（Anthropic 把它嵌进了提示词，因为"模型自己不会判断该用多少
力气"）：

| 任务复杂度 | Anthropic 的规则 | 我们场景的翻译 |
|---|---|---|
| 简单事实查找 | 1 agent，3-10 次工具调用 | 一两个工具的活——**不拆** |
| 直接对比 | 2-4 个 subagent，每个 10-15 次调用 | 多用户/多租户并列核对——可拆 |
| 复杂研究 | >10 个 subagent，明确分工 | 本系列场景暂不涉及 |

M5 代码里的 `MAX_STEPS = 5` 就是这条规则的落点：**scout 是"一次查询任务"级别，
给 5 步上限**，超了回一条"拆小一点再问"——防止它无限翻查把 15× 的账单刷爆。

## 5｜动手实践（里程碑 M5）：给管理助手加"只读查询 subagent"

### 5.1 设计：先画图，再写码

```
你 ──▶ 主 agent（全工具 + confirm + audit.jsonl，零改动）
         │ 判断"这题要翻查" → 调 ask_scout(question)
         ├── ask_scout（宿主侧工具）──▶ scout 小循环
         │       messages = [SCOUT_SYSTEM, question]     ← 独立、从空开始
         │       工具 = 只读三件套（从 server schema 过滤出的子集）
         │       ≤5 步；只回一句结论
         ◀── 摘要回填成一条 tool 结果 ──┘
         ▼ 主 agent 拿摘要回答你
```

三个设计决定：

| 决定 | 选择 | 理由 |
|---|---|---|
| 形态 | **agent 当工具** | 主 loop 零改动；scout 就是一个普通工具（第 9 篇的同构） |
| 工具子集 | schema 过滤 + 运行时双保险 | 子 agent 的"权限"= 给它的工具清单（16 篇原话：工具集就是权限） |
| 回传物 | 一句摘要（含出处） | 先简单；等产出变大再学"写文件传引用"（§3） |

### 5.2 代码：scout.py + main.py 三处改动

`scout.py`（新增文件，~40 行）：

```python
# scout.py —— 只读查询 subagent：把"翻查"外包出去的一个工具
import json
from audit import audit

READONLY_TOOLS = {"list_users", "list_roles", "get_user_roles"}   # 对照 server.py 清单
MAX_STEPS = 5            # 规模规则：一次查询任务 ≤5 步（§4）
SCOUT_SYSTEM = """你是只读查询员。规则：
- 只调用工具的"读"操作查事实，绝不写
- 汇报格式：结论 + 数据出处（用过哪些工具）；查不到就说"查不到"
- 只回最终结论，不回中间过程"""


def make_scout(chat, toolbox):
    """chat(messages, tools) 是宿主注入的记账版模型调用；返回 ask_scout 函数。"""
    readonly_schema = [t for t in toolbox.tools_schema()
                       if t["function"]["name"] in READONLY_TOOLS]

    def ask_scout(question):
        messages = [{"role": "system", "content": SCOUT_SYSTEM},
                    {"role": "user", "content": question}]
        for step in range(MAX_STEPS):
            resp = chat(messages, readonly_schema)
            msg = resp.choices[0].message
            messages.append(msg)
            if not msg.tool_calls:
                audit({"event": "subagent_done", "steps": step + 1,
                       "question": question[:80]})
                return msg.content or "（子代理没有给出内容）"
            for tc in msg.tool_calls:
                name = tc.function.name
                if name not in READONLY_TOOLS:          # 双保险：schema 之外再拦一次
                    result = "子代理不允许调用 %s（只读策略）" % name
                else:
                    audit({"event": "subagent_call", "tool": name})
                    result = toolbox.call(name, json.loads(tc.function.arguments or "{}"))
                messages.append({"role": "tool", "tool_call_id": tc.id,
                                 "content": str(result)})
        return "（子代理步数超限，未得出结论——把问题拆小一点再问）"

    return ask_scout
```

### 5.3 对照实验（A/B）：量化"值不值"

同一句任务跑两遍（建议任务：**"把系统里所有角色列出来，并查一下张三的角色是
不是其中之一"**——单次问答装不下、又不用写操作）：

- **A 基线**：把 `TOOLS_SCHEMA = toolbox.tools_schema() + [SCOUT_SCHEMA]` 改回
  `= toolbox.tools_schema()`（scout 下线），跑；记录三指标；
- **B 主+scout**：恢复挂载，跑；记录同一句任务的三指标。

填写这张表（真实数字来自你的 `TOKENS["n"]` 与秒表）：

| 指标 | A 单 agent | B 主+scout | 谁赢 |
|---|---|---|---|
| token 合计（usage 累计） | | | |
| 端到端延迟（秒） | | | |
| 主上下文最终消息数 | | | |

**预期形状（先说出答案，再对数据）**：

- 小任务上，**B 的 token 更多、可能更慢**——这不是 bug，是 §4 的 15× 现场版；
- 但 **B 的"主上下文消息数"应明显小于 A**——买的就是这个；
- 如果 B 三项全赢，先怀疑任务被拆得太碎（协调成本被隐藏了）。

三行结论（M5 的产出物，照抄框架填真值）：

### 5.4 机制级本地实测（我做的部分，非 LLM）

上面的 A/B 要等你跑真实 API；但"为什么 B 总量更大、主路径更小"这个**机制**，
纯标准库就能演示清楚。口径：**每次模型调用的成本 = 它当次读到的全部消息的字符数**
（真实 API 每轮都重读整段上下文，这正是 agent 越跑越贵的原因）；字符数 ÷ 4 ≈ token。

```python
# -*- coding: utf-8 -*-
"""第 17 篇机制演示：单 agent vs 主+scout 的上下文与成本差异（纯 stdlib，非 LLM 实测）。

计费口径：每次"模型调用"的成本 = 它当次读到的全部消息的字符数。
真实 API 每一轮都要重读整段上下文——这正是 agent 贵、且上下文越滚越贵的原因。
字符数 ÷ 4 ≈ token 数（粗估），用于相对比较。
"""
import json


def size(msgs):
    return sum(len(json.dumps(m, ensure_ascii=False)) for m in msgs)


# ---- 剧本：查 3 组数据再汇总（3 次工具 + 1 次回答 = 4 次模型调用）----
QUERIES = ["list_users(keyword=张三)", "get_user_roles(user_id=1001)", "list_roles()"]
SUMMARY = "张三：角色 admin；系统共 3 个角色"


class Stats:
    def __init__(self):
        self.calls = 0
        self.charged = 0
        self.peak = 0

    def call(self, msgs):
        self.calls += 1
        cost = size(msgs)
        self.charged += cost
        self.peak = max(self.peak, cost)
        return cost


def run_single():
    """A：单 agent——全部过程都堆在同一个上下文里"""
    st = Stats()
    msgs = [{"role": "system", "content": "你是管理助手"},
            {"role": "user", "content": "查一下张三的角色，并列出系统所有角色"}]
    for q in QUERIES:
        st.call(msgs)
        msgs.append({"role": "assistant", "tool_calls": [q]})
        msgs.append({"role": "tool", "content": "（结果 %s）" % q})
    st.call(msgs)  # 第 4 次调用：写最终回答
    msgs.append({"role": "assistant", "content": SUMMARY})
    return st, msgs


def run_split():
    """B：主 agent + scout——scout 在自己的上下文里查完，只回一句摘要"""
    s_st, m_st = Stats(), Stats()
    # ---- scout 的小循环（独立上下文，从 2 条起步）----
    s_msgs = [{"role": "system", "content": "你是只读查询员，只回结论"},
              {"role": "user", "content": "查张三的角色 + 系统所有角色"}]
    for q in QUERIES:
        s_st.call(s_msgs)
        s_msgs.append({"role": "assistant", "tool_calls": [q]})
        s_msgs.append({"role": "tool", "content": "（结果 %s）" % q})
    s_st.call(s_msgs)
    s_msgs.append({"role": "assistant", "content": SUMMARY})
    # ---- 主 agent：只看到问题 + scout 的一句话摘要 ----
    m_msgs = [{"role": "system", "content": "你是管理助手"},
              {"role": "user", "content": "查一下张三的角色，并列出系统所有角色"}]
    m_st.call(m_msgs)  # 调用 1：决定派 ask_scout
    m_msgs.append({"role": "assistant", "tool_calls": ["ask_scout(question=...)"]})
    m_msgs.append({"role": "tool", "content": SUMMARY})
    m_st.call(m_msgs)  # 调用 2：向用户汇报
    m_msgs.append({"role": "assistant", "content": "已查明：" + SUMMARY})
    return m_st, s_st, m_msgs


sa, a_msgs = run_single()
print("A 单 agent   ：模型调用 %d 次 | 合计请求量 ≈%d 字符 | 单次峰值 ≈%d 字符 | 主上下文最终 %d 条消息"
      % (sa.calls, sa.charged, sa.peak, len(a_msgs)))
mb, sb, b_msgs = run_split()
print("B 主+scout   ：模型调用 %d 次 | 合计请求量 ≈%d 字符 | 主路径峰值 ≈%d 字符 | 主上下文最终 %d 条消息"
      % (mb.calls + sb.calls, mb.charged + sb.charged, mb.peak, len(b_msgs)))
print("   ├ scout 部分：调用 %d 次 | 合计 ≈%d 字符 | 峰值 ≈%d 字符" % (sb.calls, sb.charged, sb.peak))
print("   └ main  部分：调用 %d 次 | 合计 ≈%d 字符 | 峰值 ≈%d 字符" % (mb.calls, mb.charged, mb.peak))
print()
print("隔离检查：main 的上下文里有没有 scout 的中间查询结果？",
      "（结果" in json.dumps(b_msgs, ensure_ascii=False))
print("换算（÷4 ≈ token）：A 合计 ≈%d tok / 峰值 ≈%d tok；B 合计 ≈%d tok / 主路径峰值 ≈%d tok"
      % (sa.charged // 4, sa.peak // 4, (mb.charged + sb.charged) // 4, mb.peak // 4))
print("结论：B 总量是 A 的 %.2f 倍，但主路径峰值只有 A 的 %.0f%% —— 买的是隔离，不是省钱。"
      % ((mb.charged + sb.charged) / sa.charged, 100.0 * mb.peak / sa.peak))
```

本机实测输出（Python 3.9，纯标准库）：

```text
A 单 agent   ：模型调用 4 次 | 合计请求量 ≈1082 字符 | 单次峰值 ≈443 字符 | 主上下文最终 9 条消息
B 主+scout   ：模型调用 6 次 | 合计请求量 ≈1386 字符 | 主路径峰值 ≈204 字符 | 主上下文最终 5 条消息
   ├ scout 部分：调用 4 次 | 合计 ≈1094 字符 | 峰值 ≈446 字符
   └ main  部分：调用 2 次 | 合计 ≈292 字符 | 峰值 ≈204 字符

隔离检查：main 的上下文里有没有 scout 的中间查询结果？ False
换算（÷4 ≈ token）：A 合计 ≈270 tok / 峰值 ≈110 tok；B 合计 ≈346 tok / 主路径峰值 ≈51 tok
结论：B 总量是 A 的 1.28 倍，但主路径峰值只有 A 的 46% —— 买的是隔离，不是省钱。
```

读三个数：**总量 1.28×**（隔离不是免费的）、**主路径峰值 46%**（收益在这里）、
**隔离检查 False**（main 的上下文里确实没有 scout 的中间结果——打印的是
"存不存在"，False = 干净）。scout 自己那 4 次调用的账单（≈1094 字符）和单 agent
几乎一样——**它并不便宜，它只是把债记在了别处**。
