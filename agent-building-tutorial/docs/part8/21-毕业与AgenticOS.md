## 1｜上半篇·毕业收口：终版助手组装清单

### 1.1 能力清单（PMTA 四块各自有什么）

| 能力块 | 来自哪几篇 | 落地产物 |
|---|---|---|
| **Memory 记忆** | P2·3 上下文管理、P4·11 三层记忆 | 滚动摘要 + `{tenant}:{user}` 会话键 + 长期记忆表（pgvector 可选） |
| **Planning 规划** | P4·12 规划设计 | `PLAN_SYSTEM` 提示 + `done_when` 可观察步骤 + 重规划钩子（限预算） |
| **Tool use 工具** | P2·7 手写、P3·8-10 直连、P5·13-15 MCP | 5 工具（login/list_users/list_roles/get_user_roles/assign_role），可两版（直连 / MCP server） |
| **Action 行动** | P2·3 loop、P7·19 介入、P7·20 guard | agent loop + y/c/n 确认 + 三层壳（只读开关/租户注入/审计） |
| **多体协作** | P6·17 多智能体 | 只读 scout subagent（agent-as-tool，写操作不外派） |

### 1.2 工程壳清单（"敢上线"的五个壳）

| 壳 | 来自 | 验收方式 |
|---|---|---|
| 评测报告 | P7·18 | `cases.json` 黄金用例跑回归，通过率落报告 |
| trace | P7·18 | JSONL 事件流（含 `prompt_cache_hit_tokens`） |
| 安全壳 | P7·20 §4 | 注入边界（工具结果=不可信输入）+ 密钥三铁律 + 审计脱敏 |
| 治理壳 | P7·20 §5 | 身份（service account）+ RBAC + 租户三层防线 + 审计 + 限额 |
| 只读开关 | P7·20 §6 | `guard.py` 实测通过（只读拦截 + `tenant_override` 留痕） |

### 1.3 选型记录（三个格子，每个都写"决定 + 理由 + 复核日期"）

这个模板别省——**半年后你会忘了当时为什么这么选**：

```markdown
## 选型记录（复核日期：____）
- 路线：直连 / MCP ── 理由（引用 P5·15 六维信号）：____
- 身份：service account（最小权限角色 ____）/ 用户 token ── 理由：____
- 形态：CLI / Web / 嵌入（§P7·20 §3 判据）── 理由：____
```

样例填法（用本教程场景）：路线=MCP（信号："多客户端复用"满足——Claude Code 也要用
同一个 server）；身份=service account（读多写少 + 强审计）；形态=Web（团队用）。

### 1.4 交接单（给"下一步真实落地"）

```markdown
## 落地交接单
- [ ] 对接：/api/v1 + JWT；工具清单冻结为 5 个（写权限逐项开通）
- [ ] 身份：给 agent 建只读角色；写操作走 y/c/n 确认
- [ ] key：存储位置、轮换周期（不进 git/日志/上下文）
- [ ] 限流：每用户次数 / 每租户 token 预算 / 并发上限
- [ ] 审计：服务端化 + 8 事件全集 + 脱敏 + 留存 ≥6 个月
- [ ] trace：字段与 P7·18 对齐；接 Langfuse / OTel 与否
- [ ] 只读开关：上线初期默认开；开放写操作的评审条件：____
- [ ] 评测集：首版 10 条；此后每修一个 bug 固化一条（P7·18 纪律）
- [ ] 负责人与节奏：owner ____；复盘周期 ____
- [ ] 直连 or MCP 最终决定：____（理由写入选型记录）
```

## 2｜下半篇·Agentic OS：八个类比

### 2.1 一张图 + 八个类比

```
┌─────────────────────────────────────────────────┐
│ 应用层（谁在用）           CLI 壳 / Web 壳 / 后台内嵌  │
├─────────────────────────────────────────────────┤
│ 内核 = harness（P6·16 拆过的三层中间层）             │
│   调度：agent loop（P2·3）· 规划器（P4·12）          │
│   进程表：会话与任务检查点（P7·19）                   │
│   系统调用：run_tool + guard（P7·20）               │
├───────────────┬─────────────────────────────────┤
│ 驱动层         │ 存储层（记忆层次 P4·11）            │
│ MCP servers   │  上下文（RAM）                    │
│ 文件/后台 API  │  会话记忆（SSD）                  │
│ （P5·13-15）  │  长期记忆（磁盘）                  │
├───────────────┴─────────────────────────────────┤
│ 权限层（"系统权限弹窗"）                              │
│   confirm y/c/n（P7·19）· 只读开关 · 租户注入 · 审计   │
├─────────────────────────────────────────────────┤
│ 生态：agent 注册表 / MCP Registry（P5·13）           │
└─────────────────────────────────────────────────┘
```

| OS 概念 | agent 世界 | 学过哪篇 |
|---|---|---|
| 进程 | 一个 agent 实例（一次任务的运行） | P2·3 agent loop |
| 内存（RAM） | 上下文窗口（用完即"断电丢失"） | P2·3 / P4·11 |
| 磁盘 | 长期记忆（持久化、按需换入） | P4·11 三层记忆 |
| 设备驱动 / 系统调用 | MCP server / 工具 | P5·13-15 |
| 内核调度 | harness（loop + 编排 + 中断检查） | P2·3 / P6·16 |
| 进程 fork | subagent（独立上下文窗口） | P6·17 |
| 权限弹窗 | HITL 确认（y/c/n）、只读开关 | P6·16 / P7·19-20 |
| 应用生态 / 包管理 | agent 注册表、MCP Registry | P5·13 |

### 2.2 这个视角解决什么问题

它把散落的工程点重新排成"平台该有的样子"——平台治理五问，每一问我们都已经
垫过工具：

| 平台治理关注 | 单 agent 版（已学） | 平台级的形态 |
|---|---|---|
| 生命周期 | 会话起止、检查点（P7·19） | agent 从注册到下线（kagent 用 CRD 管） |
| 可观测 | JSONL trace（P7·18） | 多 agent 汇总面板（Langfuse/OTel） |
| 配额 | 每租户限额（P7·20） | 平台级调度与预算（agentgateway 的 budget 控制） |
| 身份 | "第四种主体"（P7·20） | 平台身份体系 + 委托链 |
| 跨 agent 通信 | 嵌套调用/交接（P6·17） | A2A 协议、agent 网关 |

结论一句话：**从"造一个 agent"到"运营一群 agent"，增量几乎全在治理面**——这正是
第 16-20 篇一直在垫的东西，所以平台化不是新学问，是旧零件的重新装箱。

### 2.3 趋势与代表（2025-2026，核验数据见篇头）

怎么读这张表：**看它们的接口在标准化什么——标准化发生的地方，就是行业共识
正在形成的地方**（MCP 已定型、A2A 在收敛）。

| 代表 | 是什么 | 对我们的意义 |
|---|---|---|
| **agentgateway**（5.4k★） | 网关：LLM/MCP/A2A + Guardrails | P7·20 的"限额/路由/审计"在平台级变成了网关的活 |
| **kagent**（4k★） | K8s 原生：Agent = CRD | "生命周期治理"交给 K8s 声明式管理 |
| **MCP Registry** | 工具/SERVER 的"应用商店" | 生态复用的入口（P5·13） |
| **Dify / Coze Studio** | 低代码/应用平台 | 提醒：平台化产品已存在——自研前先对照买/建 |
| **多 agent 编排平台**（LangGraph 4.3w★ 等；框架层 P2·5/P6·17 已介绍） | 编排框架走向平台 | 框架 → 平台差的正是治理面（托管/持久化/可观测打包） |
| **DeepSeek Harness**（开发者预览） | 模型厂的 agent 开发脚手架（含主流工具的官方集成） | 信号：**"内核"正在被模型厂商品化**——你手写的 loop 不再是壁垒，治理与领域接入才是 |

### 2.4 演化路径："写到多大上什么组件"

三段总览与下面的规模表互为经纬：**裸 agent + 工具**（第 3-7 篇）→ **harness + MCP +
治理**（第 8-20 篇）→ **agent 平台**（§2.3 的那些代表在做的方向）。每一段的升级
都不是"想上"，而是被新出现的"多方"推着上：

| 规模 | 典型形态 | 该上的组件 | 先别急着上 |
|---|---|---|---|
| 1 人自用 | CLI，1 agent + 5 工具 | .env、audit.jsonl、MAX_STEPS | 平台、队列、多 agent |
| 小团队（≤10 人） | Web 壳 + 只读默认 | 会话 Redis、评测用例集、只读开关、审计服务端化 | MCP 网关、K8s |
| 多团队 / 多租户 | MCP 收窄 + 治理壳 | 租户隔离、限额、密钥服务、trace 成本报表 | 多 agent 编排 |
| 对外平台 | 平台化 | agent 注册表、网关（agentgateway 式）、配额与生命周期（kagent 式） | ——（走到这一步再选） |

两条心法：① **组件跟着"多方"长**——第二个用户/第二个 agent/第二个团队出现时，
才升级对应的那格；② **复杂度守恒律**（P6·17）在平台层同样成立：平台把治理做成
"组件"，就是把复杂度从每个人身上搬进系统里。

## 3｜与第 2 篇闭环：PMTA 的平台化收束

第 2 篇给的 PMTA（Planning / Memory / Tool use / Action，源自 CoALA）是"一个
agent 的零件清单"；21 篇结束时，四个零件各自长成了平台里的一个构件：

| PMTA | 经典理论对应（P1·2） | 21 篇后长成 |
|---|---|---|
| **Planning** | goal-based | 规划器 + 重规划（P4·12）→ 平台的调度与任务队列 |
| **Memory** | model-based / learning | 三层记忆（P4·11）→ 平台的记忆服务（RAM/SSD/磁盘） |
| **Tool use** | 行动机制的延伸 | 手写工具（P2·7）→ MCP（P5）→ 网关（agentgateway 式） |
| **Action** | reflex / utility 的出口 | loop 执行（P2·3）→ 权限弹窗 + 审计（P7·19-20） |

一句话收束：**这套 21 篇，就是把 PMTA 从"一个 agent 的零件清单"养到"一群 agent
的操作系统"的过程。**

## 全系列结语

从第 1 篇的"一次 tool call 全流程"到这里，你走过的路径是：
**看懂分界线 → 手写 loop（M1）→ 接上真实系统（M2）→ 它会记会想（M3）→ 工具有了
标准（M4）→ 学会分工（M5）→ 敢上线（M6）→ 看清上面还有一层 OS。**

最想让你带走三件事：

1. **非确定性要用工程接住**——评测、确认、检查点、回滚，四样缺一不可；"模型会
   犯错"不是缺陷，是设计前提。
2. **接口标准化的地方就是行业共识**——MCP 定格了什么，你就顺着它走；下一个
   （A2A？）来临时，判断方法同样。
3. **组件跟着规模长**——从 5 行 loop 到 agent 平台，每一步都是被需求推着走的；
   别在 1 人自用时造平台，也别在多租户时还守着 jsonl。

**下一步**：这份系列到此收官——继续读代码不如动手交付。想开始真实落地（把交接单
做成可分阶段执行的设计文档），回复「**落地**」；本篇审阅后照常回复「**继续**」
即确认收尾。
