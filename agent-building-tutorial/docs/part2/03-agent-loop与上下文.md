## 1｜agent loop 的五阶段

第 1 篇给的时序图是"一次工具调用"，看的是单个点；这一篇把它**展开成循环**看整个旋转。

agent loop 的工程化拆法，固定为五个阶段：

```
   ┌────────────────────────────────────────────────────────────┐
   │  agent loop（编排层）                                        │
   │                                                            │
   │  ①获取输入    ②组装上下文    ③调LLM出结果    ④解析          │
   │  (用户新指令      历史+        文本 或         文本?         │
   │   或工具结果)     工具清单     tool_calls      tool_calls?    │
   │       ▲              ▲           │              │           │
   │       │              │           │              ▼           │
   │       │              │           │         ⑤行动             │
   │       │ tool_result  │           │       ·文本输出→回用户→停  │
   │       └── 回填 ◀─────┼───────────┼───────·执行工具→追加结果   │
   │                      └───────────┼────────▶ 回到②           │
   └────────────────────────────────────────────────────────────┘
```

五步拆开：

1. **获取输入**：两种东西都会进循环——用户的新指令，或上一步工具执行的结果。它们只是
   "新来的两条消息"，没有本质区别，统一追加进上下文。
2. **组装请求**：把 `SYSTEM`（系统提示词：你是谁、规则、工具清单）+ 全部历史 + 上一步结果，
   一起发给 LLM。**这一阶段的产物就是模型当时能"看到"的整个世界**。
3. **调 LLM**：拿到模型的输出。模型只会输出两类东西：一个**最终答复**（文本），或一组
   **`tool_calls` 声明**（"我想调 X，参数是…"）；极端情况还会"求助"（主动要你把控制权还
   给用户，第 19 篇展开）。
4. **解析**：宿主判断模型给出的是文本还是声明。这一步在真实系统里含"参数 JSON 校验"
   （模型声明了但参数不合法怎么办——第 7 篇踩坑）。
5. **行动**：分岔口——
   - 是文本 → 作为最终答复交给用户，**循环终止**；
   - 是声明 → 宿主真的去执行工具（副作用发生处），把结果当作一条 `tool_result` **追加**
     进上下文，然后回到第 ② 步，带着新事实再问一次模型。

第 5 步的"回填 → 回到②"就是循环的**引擎**：模型每看一次"执行后的世界"，就再决策一次，
直到它认为任务完成。第 1 篇"自主三把尺子"里"能自己决定下一步"指的就是——**决定权一直在
循环的第 ②③ 步，不在用户。**

伪代码（把真实工具都省成名字，读结构）：

```text
messages = [SYSTEM, 用户首条指令]
loop:
    out = llm(messages + 工具清单)       # ②③：模型只看到 messages 里的世界
    if out 是最终文本: return 文本        # ④⑤：完成，交给用户
    if out 是 tool_calls:
        校验参数
        result = 执行工具(out.name, out.args)   # ⑤：副作用发生在这
        messages.append(tool_result(result))   # ⑤：结果成为"世界的新状态"
        # —— 回到 loop 顶部，带着新状态再决策 ——
```

> 呼应第 2 篇：这一圈的"上下文"就是 model-based 里的**内部状态**——砍掉它，模型立刻失忆；
> 而第 ③ 步"要不要调工具、要不要停下"的决策权，正是 agent 与普通程序的分界。

## 2｜从 loop 到 harness：LLM+tools 之外的两侧基础设施

loop 是 agent 的**内核**（核心逻辑），但一个"能干活、可维护、敢上线"的 agent 远不止内核。
把 loop 需要的所有"周边"列出来，你就知道 harness 补的是什么：

| harness 服务 | 回答的问题 | 发生什么 |
|---|---|---|
| **调度 / 治理** | loop 会不会失控？ | 并发与限流、超时、取消（第 19 篇） |
| **工具注册表** | 模型知道有哪些工具、真的能执行吗？ | 把工具节的 JSON Schema 喂给模型；按名字取缔执行函数（本篇 demo 的 `TOOLS` 字典就是这个表的雏形）|
| **事件流** | 每一步发生什么，能被谁看到？ | 把"LLM 每步输出 / 工具执行 / 终止"广播出去 → UI、日志、trace（第 18 篇）|
| **权限** | 模型能让 agent 做什么、不能做什么？ | 工具白名单、危险操作确认（第 9、19 篇）|
| **持久化** | 会话能续吗？断电丢吗？ | checkpoint、会话存储（第 16 篇）|
| **可观测** | 出问题怎么排查？花了多少钱？ | 每次调用的 token 数/耗时/成本 → trace（第 18 篇）|

这些不全是 loop 循环逻辑，但它们全是"让 agent 可用可管"的**两侧基础设施**——合起来就叫
**harness（agent loop / agent core 的工程化运行时）**。一张分层图：

```
┌─ 应用层 ────────────────────────────────┐   CLI / 编辑器 / Web / 嵌入系统
│  提示输入、展示输出、触发会话            │
├─ 服务层（harness）───────────────────────┤   ← 本篇说的"两侧基础设施"
│  调度 · 工具注册 · 事件流 · 权限 · 持久化 │   （第 9/16/18/19/20 篇逐个加）
├─ 核心层（agent core）───────────────────┤
│  五阶段 loop + 上下文管理                 │   ← 本篇亲手写的部分
├─ 模型 + 工具 ────────────────────────────┤   DeepSeek / Ollama + 你的函数
```

业界对照：Claude Code 是"模型 + harness + 编辑器应用"的完整产品（第 16 篇拆它的 subagent、
hooks、checkpoint）；[OpenClaw](https://github.com/openclaw/openclaw) 是 harness 概念最贴近
的开源代码参考。本系列的主线是从**核心层手写**开始（你马上就要动手），服务层按需在
P6/P7 逐个加——先理解内核，再武装外壳。

> 一个提醒：别被"harness"吓到。它就等于**"loop 内核 + 让它可用可管的所有周边"**，
> 不神秘。第 1 篇词表里的定义到这儿就已经拆完了。

## 3｜上下文管理：为什么 agent 会"忘事"

第 2 篇说"上下文 = model-based 的内部状态"。但内部状态**不是免费的**，矛盾就在这：

- 模型**无状态**：每次请求它只"看到"你通过 messages 递给它的东西，除此之外一无所知。
- 而 messages **会越堆越长**：每转一轮，历史里就多几轮对话 + 几次工具结果。

于是两个现实问题同时出现：

**① 为什么会"忘"**——三种情况：
- 上下文太长，直奔模型上下文窗口上限（不同模型的窗口大小不同，以各厂商 `官方 docs`
  为准），请求直接报错/截断；
- 你手动裁剪（trim）了旧消息，把关键的旧信息也一起砍了；
- 你什么都没做，但**预算**（每次请求都按输入 token 计费）涨到肉疼。

所以"忘事"在工程上不是玄学，是**"上下文里放不下 / 被裁掉了 / 太贵了"**，三种原因。

> **token 怎么算**：token 不是字数，是模型的"容量与计价单位"。经验比例：1 个英文字符
> ≈ 0.3 个 token，1 个汉字 ≈ 0.6 个 token（官方估算口径；精确计数以 API 返回的 `usage`
> 字段为准，官方也提供离线 tokenizer 供本地预估）。推论：同样一段话，中文比英文"占地"
> 更大——中文会话的历史预算要按"字数的六成"预估，压缩中文历史收益更明显。

**② 手段三件套** ——*裁剪 / 压缩 / 总结*（本系列里 P4·11 的记忆篇会把它们并入"三层记忆 +
压缩整理"讲深，这里先给最小认知）：

| 手段 | 做法 | 什么时候用 | 代价 |
|---|---|---|---|
| **裁剪（trim）** | 砍掉最老的部分消息 | 上下文快超限、旧轮次不再相关 | 粗暴：可能砍掉还在用的信息 |
| **压缩（summarize into window）** | 保留"近 N 轮原始 + 更早的全压缩成一段摘要" | 会话长、但要保留"发生过什么" | 摘要=有损压缩，细节可能丢 |
| **总结（compact / 摘要续接）** | 把整个旧对话浓缩成"上下文：会话摘要"，新会话基于摘要继续 | 跨会话、或上下文即将爆 | 同上，且摘要本身要花 token 生成 |

类比：你在用 **Claude Code** 时打的 `/compact` 就是"总结/压缩"的工程化——
它会把你没聊完的历史压缩成一段摘要，让你能用更短的上下文继续干活（具体命令行为以
[Claude Code 官方文档](https://docs.anthropic.com/en/docs/claude-code/overview) 为准）。

**先想清楚要什么、再谈手段**：上下文管理的第一原则不是技巧，是**只留"这次任务接下来还能
用到的"，其余交给压缩/总结**。第 6 篇会看它的成本、第 11 篇会给完整的三层记忆方案。

## 4｜终止条件：loop 什么时候停下来

loop 的动力来自第 5 步的"回填 → 回到②"。**动力越足，越要刹车**。三个来源的终止条件
协同兜底：

| 终止条件 | 谁触发 | 说明 |
|---|---|---|
| **任务完成** | 模型 | 模型判断"该回答用户了"，输出最终文本 → 正常结束 |
| **最大迭代数**（max steps）| 宿主（代码） | 无论模型怎么说，转够 N 轮就强制停——防"死循环鬼打墙"（模型不停要调工具）|
| **工具超时** | 宿主 | 单个工具跑超时就中止并报错回填，不让整个 loop 卡死 |
| **用户确认/打断** | 用户 | 需要人工授权或用户喊停时停下（第 9、19 篇展开）|

工程上"任务完成"判定最常见也最脆，多数 agent 会用两种兜底：**模型显式说明"完成" + 宿主
观测到"这一轮没返回 tool_calls 且给了文本"**。而 max steps 是我们**一定**要有的硬刹车——
本篇动手实践的"场景 2"就是它上岗的样子。

## 动手实践：15 行主循环，不接 LLM 先跑通

**目标**：把第 1、2 节的五阶段循环，亲手写成能跑的代码——**不接真模型**，用一个
"假 LLM"代替，让循环先"转"起来，亲眼看到"模型声明 → 宿主执行 → 结果回填 → 再决策"
这个节奏，以及 max steps 怎么刹车。

新建 `demo_loop.py`（主循环就是 `agent_loop` 那一个函数，约 15 行；两端的 `mock_llm` 和
`get_time` 是给循环当演员的替身）：

```python
"""第 3 篇动手实践：最小 agent loop 骨架（不接真 LLM，用假模型跑通循环）"""
import time

def mock_llm(messages):
    """假装是 LLM：看最后一条消息的 role/content 就决定"调工具"还是"直接答"。"""
    for m in messages:                                        # 规则①：场景2 优先——
        if m["role"] == "user" and m["content"] == "一直调":  #   用户说"一直调"→模型永远想调工具
            return {"type": "tool_call", "name": "get_time", "args": {}}
    if messages[-1]["role"] == "tool_result":                 # 规则②：看到工具结果 → 给出最终答复
        return {"type": "text", "content": "搞定，我回答你。"}
    if "几点" in messages[-1]["content"]:                    # 规则③：场景1 该调就调
        return {"type": "tool_call", "name": "get_time", "args": {}}
    return {"type": "text", "content": f"答复：{messages[-1]['content']}"}

def get_time():
    return time.strftime("%H:%M:%S")

TOOLS = {"get_time": get_time}                                # 工具注册表（harness 服务层雏形）

def agent_loop(initial_user_msg, max_steps=5):
    messages = [{"role": "user", "content": initial_user_msg}]
    step = 0
    while True:
        step += 1
        if step > max_steps:                                  # 终止条件：宿主硬刹车
            print("达到最大迭代数，终止。")
            break
        model_out = mock_llm(messages)                        # ③ 调 LLM
        if model_out["type"] == "text":                       # ④⑤ 模型直接答 → 完成
            print(f"agent: {model_out['content']}")
            break
        name, args = model_out["name"], model_out["args"]    # 模型声明"我要调工具"
        result = TOOLS[name](**args)                          # ⑤ 宿主执行工具（副作用发生处）
        print(f"  → 调工具 {name}({args}) = {result}")
        messages.append({"role": "tool_result", "name": name, "content": result})  # ⑤ 结果回填
    print(f"（共 {step} 步）")

if __name__ == "__main__":
    print("== 场景 1：正常一问一调 ==")
    agent_loop("现在几点？", max_steps=3)
    print("\n== 场景 2：模型疯了不停要调工具（max_steps 拦住）==")
    agent_loop("一直调", max_steps=3)
```

运行：

```bash
python demo_loop.py
```

预期输出（时间数值随运行时变化，节奏与行数一致）：

```text
== 场景 1：正常一问一调 ==
  → 调工具 get_time({}) = 16:19:54
agent: 搞定，我回答你。
（共 2 步）

== 场景 2：模型疯了不停要调工具（max_steps 拦住）==
  → 调工具 get_time({}) = 16:19:54
  → 调工具 get_time({}) = 16:19:54
  → 调工具 get_time({}) = 16:19:54
达到最大迭代数，终止。
（共 4 步）
```

（本脚本已在本环境实测运行通过；`mock_llm` 的返回值结构模拟了真实 LLM 的 `tool_calls`/文本，真实接口细节以第 6 篇的官方文档为准。）

**看完输出，你要能指认三件事**：

1. **模型声明与宿主执行分离**：`get_time` 的调用发生在 `TOOLS[name](**args)` 那行——模型
   只是"说"要调，`mock_llm` 从不执行时间函数。这正是第 1 篇"模型只声明、宿主才执行"在
   代码里的样子。
2. **结果回填让模型"看到"**：场景 1 里模型第二轮的决策依据，就是它"看到"了第一条
   `tool_result`。把 `messages.append(...)` 那行注释掉再跑，模型就会对同一句话答非所问——
   你亲手切换了它有没有"内部状态"。
3. **max_steps 是宿主兜底的刹车**：场景 2 里模型"疯"了（mock 规则故意的），第 4 轮被
   `step > max_steps` 拦下。没有它，这就是个死循环。

进阶（别在本文做，记着）：把 `mock_llm` 换成真实调用（第 6 篇教三种姿势 + API key）、
把工具换成后台接口（第 8 篇起的主线 demo），loop 不用改——因为**内核只依赖"LLM 输出该有
的形状"和"工具注册表"这两个接口**，这正是用 15 行骨架换来的架构红利。

## 本篇结论

1. **agent loop 五阶段**（获取输入 → 组装上下文 → 调 LLM → 解析 → 行动/回填）是 agent 的
   引擎；"模型只声明、宿主才执行"在代码里是 `TOOLS[name](**args)` 那一行的分离。
2. **harness = loop 内核 + 两侧基础设施**（调度 / 工具注册 / 事件流 / 权限 / 持久化 / 可观测）——
   先手写内核，服务层按需加。
3. **忘事 = 上下文放不下/被裁掉/太贵**，手段是裁剪 / 压缩 / 总结；**必须常驻的刹车 =
   max steps**（外加完成判定、工具超时、用户打断）。
