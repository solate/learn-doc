## 1｜打断：三种"停"，一套取消语义

术语先行：这套语义的工程名是**取消**（cancellation）——对应 cancellation token，
一个共享的"已请求停止"标志（本节的 `CANCEL`，真实版就是 `threading.Event`）。

用户的"打断"其实是三件不同的事：

| 打断 | 用户想要 | 系统该做的 |
|---|---|---|
| **喊停** | 别跑了 | 停止推进；**保留已完成的工作**；汇报进度 |
| **插话** | 补一句/改个条件 | 消息进队列，在**步边界**注入，不切断正在执行的工具 |
| **改需求** | 换个目标重来 | 同"插话"，但可能触发重规划（第 12 篇） |

Claude Code 的两条原话，正好是两条设计律：

1. **"Claude keeps the work done so far"**——中断不丢工。停止 = 不再往前走，
   不是把走过的路擦掉。落到工程：停止时要**落盘进度**（16 篇 checkpoint 的
   任务级版本）。
2. **"passes it to Claude as soon as those tool calls finish, within the same
   turn"**——插话的落点在**步边界**。工具执行到一半被注入新指令，等于把一次
   操作砍成两截——半成品状态是最难收拾的（回连第 16 篇：连 checkpoint 都不敢
   追踪"执行到一半"的状态）。

工程模式就三件小事：

```python
# ① 取消标志：真实版 = threading.Event（Ctrl-C 回调 / 前端"停止"按钮里置位）
# ② 中断检查点：放在每一"步"开始前——工具内部不设检查点（工具是事务边界）
for i, task in enumerate(tasks, 1):
    if CANCEL.is_set():                 # ← 唯一的检查点，就在这
        save_progress(done)             # 停止的三件事之一：落盘
        return "已停止：完成 %d/%d" % (len(done), len(tasks))   # 之二：汇报进度
        # 之三：把"已停止"作为结果返回给上层（不是抛异常炸掉，回连 16 篇"拒绝也是结果"）
    done.append(run_one(task))
```

"暂停"与"取消"是两种语义：**暂停**=同进程挂起等恢复（交互场景，内存态可以留）；
**取消**=结束当前执行、靠落盘的进度续跑（跑批场景，进程都能退）。我们的场景里，
跑批用取消、对话用暂停。

## 2｜介入三方式：从 y/N 升级到 y/c/n

第 10 篇的 `confirm()` 只有二选一（yes / no）。真实使用中少了最重要的一档——
**"不要这么做，但可以那样做"**：

| 方式 | 用户意图 | 工具结果回填给模型的内容 | 审计事件 |
|---|---|---|---|
| 确认后继续（y） | 就照这个做 | 正常执行结果 | `approved` |
| **修正指令（c）** | 换个做法 | "用户拒绝了本次操作，并提出修正指令：…（按此调整计划）" | `rejected`（带修正文本） |
| 彻底中止（n） | 全停下来 | "用户中止；不要重试" | `aborted` |

**修正指令的工程本质**（本篇最重要的一小节）：用户的话是**作为工具结果回填**的，
不是宿主越过工具直接改写对话。两条理由：回填走的是既有协议（模型下次调用就能
看到）；"用户拒绝了 + 修正要求"是一个**完整的动作结果**，模型据此重排计划——
这与 Claude Code 允许在 Yes/No 上按 `Tab` **附一句备注交给 Claude** 是同一种设计。

```python
# main.py：confirm() 的升级（对第 10 篇的 diff 约为 +8 行）
def confirm(tool, args):
    print("要执行：%s %s" % (tool, args))
    ans = input("y=继续  c=修正指令  n=中止 > ").strip().lower()
    if ans == "c":
        return "c", input("给模型的修正指令：")
    return ans, ""

# run_tool 里（原二选一分支替换）：
choice, fix = confirm(name, args) if name in DANGEROUS_TOOLS else ("y", "")
if choice != "y":
    audit({"event": "rejected" if choice == "c" else "aborted",
           "tool": name, "fix": fix})
    if choice == "c":
        return "用户拒绝了本次操作，并提出修正指令：%s。请按此调整计划。" % fix
    return "用户中止了本次操作。请向用户说明，不要重试。"
```

**中立的注意**：彻底中止后，"文件/数据已被改掉的部分"怎么办——第 16 篇的
rewind 语义在这里兑现：代码回退与对话回退是两条线，可以分开恢复（CC 的
`/rewind` 菜单前两项就是这个分工）。

## 3｜何时停下来问：四个信号与一条判据

"该不该停下来问"是全文最难的判断。四个信号，命中越多越该问：

| 信号 | 表现 | 例（我们的场景） |
|---|---|---|
| **破坏性高** | 失败不可逆或代价大 | 删用户、批量停用（写/删/付费/出站/敏感数据——第 16 篇三类风险） |
| **确定性低** | 模型自己对结果没把握（措辞含糊、多义输入） | "把不活跃的都处理掉"——"不活跃"定义是什么？ |
| **信息不足** | 缺关键参数且无法从上下文补 | "把张三的角色改一下"——改成什么？ |
| **多选浮现** | 多个都合理的方案 | 三条都能达成目标的执行路径 |

一条总的判据代替所有纠结：**错了修得回吗？修的成本多大？** 修得回、成本低
（只读查询、可撤销的草稿）→ 放行，别问；修不回（删除、外发、花钱）→ 必问。

另一头的反面同样要防：**问得太勤，人会开始盲按 y**——"同意"按钮按成肌肉记忆，
确认就失效了。这是权限设计里的"狼来了"：第 16 篇 Cursor 用分级 + 分类器来减少
提示次数，同一个目的。设计目标不是"问得少"或"问得多"，而是**让每一次问都值得
被认真读**。三条交互细则：

1. **选项设计成三档**（y/c/n），自由文本最难用，盲按最难防的是"是/否"；
2. **提示里带"为什么问"**：展示参数与影响范围（DELETE user 1001，会影响其
   角色关联）——CC 的提示展示命令原文和"requires approval"就是这条；
3. **一次授权 ≠ 永久授权**——但把"以后不再问"做成显式选项（下一节）。

## 4｜长任务：进度、续跑、超时

**进度上报**：颗粒度=步骤级（不是 token 级，人是看"到哪了"不是"烧了多少"）；
数据源就是第 18 篇的 trace——"已完成 3/10，当前：查用户C"直接由事件流生成。

**断点续跑**：任务级检查点 = 进度清单 + **幂等提醒**。恢复时从 `done` 之后
续跑；两条规矩：

- **只读步骤**：重查无害，重跑即可；
- **写操作步骤**：必须幂等（幂等键/upsert）——"第 3 步重跑一遍不会多删一次"，
  或者干脆"完成的写步骤不重跑，只重跑未完成段"。

**超时四层**（每层都有自己的兜底）：

| 层 | 典型值 | 超时后 |
|---|---|---|
| 单次 LLM 调用 | 60-120s | 重试一次（第 3 篇的透明重登同款思路） |
| 单次工具调用 | 10-30s（读）——写得谨慎些 | 重试一次；写操作不自动重试（第 9 篇"不该重试"表） |
| 单个子任务 | 预算级（如 scout 的 MAX_STEPS=5） | 标记失败，**继续下一个**（跑批不能因一条卡死全停） |
| 整个回合 | 配置项 | 保存检查点 + 上报"未完成及原因" |

注意超时和步数预算是两回事：**MAX_STEPS 防的是"绕圈"，超时防的是"卡死"**，
都要有。

## 5｜十个怪问题的兜底表

这一节是"实战汇"的核心——真实世界会用各种姿势教 agent 做人。每个问题一行：
症状 → 兜底动作 → 前面哪篇已经埋好了：

| # | 症状 | 兜底动作 | 出处 |
|---|---|---|---|
| 1 | **参数幻觉**（编工具名/参数） | 工具名清单校验 + 参数 JSON/类型校验，错误喂回 | P3·9 `_shape` |
| 2 | **乱调工具**（该查不查、不该调乱调） | 工具断言评测 + 提示层"先只读后写" | P7·18 / P3·10 |
| 3 | **编结果**（没查就答） | 提示词要求"引用工具结果" + 用例断言"必须调过 X" | P7·18 |
| 4 | **上下文漂移**（聊几轮忘了目标） | 滚动摘要 + 目标重述 + checkpoint | P4·11 / P6·16 |
| 5 | **结果过大**（一次拉几千行） | 截断（`result[:120]` 已成习惯）→ 分页 → 大结果外置传引用 | P6·17 |
| 6 | **回环**（同一调用重复转圈） | **回环检测器**（见下，新增） | 本篇 |
| 7 | **烧钱**（步数/花费失控） | 步数预算 + token 记账 + trace 成本报表 | P6·17 / P7·18 |
| 8 | **并发限流**（多人同用被 429） | 宿主侧排队/信号量 + 429 退避（尊重 Retry-After） | 通用 |
| 9 | **串话**（多租户/多用户状态污染） | 会话隔离键 `{tenant}:{user}` + audit 带身份 | P4·11 |
| 10 | **错误滚雪球**（对错误无限重试） | "不该重试"判定表 + 错误形状化 | P3·9 |

表外同族还有一类**答非所问**（无视刚拿到的工具结果、自说自话往下答）：兜底=
提示层"以工具结果为准"+ 任务重述（把目标再贴一遍进上下文），与第 4 行的上下文
漂移是同一副药。

其中第 6 条本篇顺手实现——回环检测器，8 行挂进 loop：

```python
# 回环检测：连续出现相同的 (工具, 参数) 就是转圈信号
def detect_loop(recent_calls, tool, args, threshold=3):
    recent_calls.append((tool, json.dumps(args, sort_keys=True, ensure_ascii=False)))
    tail = recent_calls[-threshold:]
    return len(tail) == threshold and len(set(tail)) == 1

# agent_loop 里，run_tool 之前：
if detect_loop(RECENT, name, args):
    return ("检测到你在重复同一个调用（%s %s）。停下来：换一个思路，"
            "或者向用户报告你卡在哪里。" % (name, args))
```

（提示消息本身也是"形状化结果"——给模型一条明确的出路，而不是静默拦截。）

## 6｜权限交互侧：粒度、寿命与审计

**第一步是分级**：把操作按后果分档——"写/删/付费/出站/敏感数据"展开到本项目
（沿用 P3·10 的读 < 写 < 执行阶梯）：

| 操作类 | 本项目例子 | 确认策略 |
|---|---|---|
| 只读查询 | 查用户、查角色 | **白名单不问**（只读高频动作） |
| 可逆写 | `assign_role` 改角色 | **每类问**（第一次遇到问一次，确认后可进白名单） |
| 不可逆/破坏性 | 删用户、批量停用 | **每次问**（破坏性操作，白名单不放行） |
| 出站/付费 | 外发消息、调付费接口 | **每次问** + 展示目标与范围（P6·16 三类风险的另两类） |
| 敏感数据 | 批量导出用户名单 | **每次问**，或脱敏（不外发原始数据）后降档 |

"提示粒度三档"= 上表右列的三种策略：每次问 / 每类问 / 白名单不问——按风险
自上而下从紧到松。

**放行的寿命**——Claude Code 的分法值得直接抄（两种寿命对应两种确定性）：

| 操作类 | "不再问"的寿命 | 理由 |
|---|---|---|
| 文件修改 | **直到会话结束** | 工作区状态随会话变化，跨会话信任不成立 |
| Bash 命令 / Web 域名 | **永久**（按仓库 + 命令/域名粒度） | 粒度足够具体，可展示、可审计 |
| 只读（工作目录内） | 免问 | 风险最低 |

配套的是那条原则：**只有当提示能完整展示"这条规则会放行什么"时，才给"不再问"
选项**——展示不了范围的，只给一次性放行。抄到我们的系统里，就是给
`DANGEROUS_TOOLS` 补一个 `allowlist.json`（tool + 参数模式 + 作用域），并且：

- 永久规则**必须可展示**（`assign_role(user_id=*, role_id=viewer)` 这种能一眼
  看全的范围才可以存）；范围展示不全的只给"本次"；
- **写规则本身要进审计**（`{"event": "rule_added", ...}`）——权限变更和操作
  一样是审计对象（P7·20 会把这个话题接到 RBAC 架构面）。

**审计对齐**：本篇三种介入 + 授权变更，全部落在 audit 的事件里：
`approved` / `rejected`（带修正）/ `aborted` / `rule_added`——第 10 篇立的
"审计四事件"到这里正好集齐交互侧的完整闭环。

顺带一句留白：以上都是**交互侧**；"用户 token vs 专用 service account"的身份
选型属于架构侧，见第 20 篇。

## 7｜动手实践：三个场景，一次跑通

### 7.1 脚本（纯 stdlib；"用户"按剧本动作，保证输出可复现）

```python
# -*- coding: utf-8 -*-
"""interact_demo.py —— 第 19 篇三场景演练（纯 stdlib；"用户"按剧本动作，保证输出可复现）

场景 1：跑批前打断（cancel 语义 + 进度落盘）
场景 2：写操作确认三选一（y 继续 / c 修正指令 / n 中止）
场景 3：中途改需求（排队消息，在「步与步之间」注入）

真实版：剧本换成 Ctrl-C / 前端停止按钮 / stdin —— 见文章 §7.3。
"""
import json

# ============ 场景 1：跑批前打断 ============
print("== 场景 1：跑批前打断 ==")
cancel = False                      # 真实版 = threading.Event()（Ctrl-C 回调里 .set()）
done = []

steps = ["查用户A", "查用户B", "查用户C", "查用户D", "查用户E"]
for i, s in enumerate(steps, 1):
    if cancel:                      # 中断检查点：每一步开始前
        json.dump({"done": done}, open("task_ckpt.json", "w", encoding="utf-8"),
                  ensure_ascii=False)
        print("[任务] 优雅停止：完成 %d/%d，进度已存 task_ckpt.json" % (len(done), len(steps)))
        break
    done.append(s)
    print("[任务] 第 %d 步完成：%s" % (i, s))
    if i == 2:                      # ← 剧本：此时"用户"按下停止
        print("[用户] 算了，先别跑了 → cancel 置位")
        cancel = True
else:
    print("[任务] 全部完成")

ckpt = json.load(open("task_ckpt.json", encoding="utf-8"))
print("[恢复] 新进程读检查点：已完成 %s → 从第 %d 步续跑\n"
      % (ckpt["done"], len(ckpt["done"]) + 1))

# ============ 场景 2：写操作确认三选一 ============
print("== 场景 2：写操作确认（y 继续 / c 修正指令 / n 中止）==")
ANSWER_SCRIPT = ["c", "不要删，把张三的角色改成 viewer", "y"]   # 脚本化"用户输入"
audit = []


def ask_user(tool, args):
    """真实版=input(...)；这里按剧本取答案，保证演示可复现。"""
```

## 本篇结论

1. **打断的本质是"取消 + 保全"**：中止检查点放在**步边界**（工具是事务边界）、
   停止要落盘进度并把"已停止"作为结果返回；插话走队列、同回合内步边界注入。
2. **介入从 y/N 升级为 y/c/n**：修正指令的工程本质是"用户的话作为工具结果
   回填"；"何时停下来问"用一条判据——**错了修得回吗、修的成本多大**。
3. **十个怪问题各有兜底，且大半前面已埋好**：本篇新增回环检测器；权限交互侧
   抄 Claude Code 的分法——"不再问"按操作类给不同寿命，且**能完整展示范围的
